# 第 12 章　调度任务与线程

*Chapter 12: Scheduling Tasks and Threads*

现代浏览器必须处理用户输入、请求远程文件、运行各种回调，并最终渲染到屏幕上，同时还要保持快速与响应灵敏。这就需要一个统一的任务抽象，来跟踪浏览器中待处理的工作。此外，浏览器的工作还必须拆分到多个 CPU 线程（thread）上，让不同的线程并行运行任务，以最大化响应能力。

## 12.1 任务与任务队列

到目前为止，我们浏览器所做的大部分工作都来自用户操作，比如滚动、按下按钮和点击链接。但随着我们浏览器运行的 Web 应用越来越复杂，它们开始查询远程服务器、播放动画、预取信息以备后用。用户动作缓慢而审慎，在操作之间留出长长的空隙让浏览器从容跟进；而应用却可能要求极高。这就要求我们换一个视角：浏览器现在面对的是一条永远做不完的任务队列。

现代浏览器通过多任务处理、优先级排序和工作去重来适应这一现实。浏览器可能做的每一项工作——加载页面、运行脚本、响应用户操作——都被转换成一个任务（task），以便在之后执行。所谓任务，就是一个可以在之后执行的函数（连同它的参数）：

```python
class Task:
    def __init__(self, task_code, *args):
        self.task_code = task_code
        self.args = args
    def run(self):
        self.task_code(*self.args)
        self.task_code = None
        self.args = None
```

注意构造函数参数以及对 task_code 的调用中特殊的 *args 语法。这种语法表示一个 Task 可以用任意数量的参数构造，这些参数随后以列表 args 的形式可用。而用 *args 调用函数，则会把列表重新拆开成多个参数。

任务的要点在于：它可以在某个时刻被创建，然后在稍后的时刻由某种任务运行器（task runner）按照某种调度算法（scheduling algorithm）执行。¹ 在我们的浏览器中，任务运行器会把任务存储在一个先进先出（first-in, first-out）的队列（queue）里：

```python
class TaskRunner:
    def __init__(self):
        self.tab = tab
        self.tasks = []
    def schedule_task(self, task):
        self.tasks.append(task)
```

等到该运行任务的时候，我们的任务运行器只需从队列中取出第一个任务并运行它即可：²

```python
class TaskRunner:
    def run(self):
        if len(self.tasks) > 0:
            task = self.tasks.pop(0)
            task.run()
```

要运行这些任务，我们需要调用 TaskRunner 上的 run 方法，这可以在主事件循环（event loop）里完成：

```python
class Tab:
    def __init__(self):
        self.task_runner = TaskRunner(self)
def mainloop(browser):
    while True:
        # ...
        browser.active_tab.task_runner.run()
```

TaskRunner 让我们可以选择在什么时机处理不同的任务。这里，我选择在浏览器运行的每个任务之间都检查一次用户事件，这样当任务很多时浏览器会更灵敏。我还选择只运行活动标签页（active tab）上的任务，这意味着后台标签页不会拖慢我们的浏览器。

有了这个简单的任务运行器，我们现在可以把任务排入队列并在稍后执行了。举个例子：目前，加载网页时，我们的浏览器会先下载并运行所有脚本，然后才执行渲染步骤。这让页面加载变慢了。我们可以通过为运行脚本创建任务来修复这个问题：

```python
class JSContext:
    def run(self, script, code):
        try:
            self.interp.evaljs(code)
        except dukpy.JSRuntimeError as e:
            print("Script", script, "crashed", e)
class Tab:
    def load(self, url, payload=None):
        # ...
        for script in scripts:
            # ...
            try:
                header, body = script_url.request(url)
            except:
                continue
            task = Task(self.js.run, script_url, body)
            self.task_runner.schedule_task(task)
```

现在，我们的浏览器要等 load 完成并且事件循环再次轮到时才会运行脚本。而且如果要运行的脚本很多，页面加载期间我们仍能处理用户事件。

> **深入探索**
> 即使在浏览器之外 [3]，JavaScript 也使用基于任务的事件循环 [2]。例如，JavaScript 使用消息传递，通过异步 [4] API 处理输入输出，并具有运行至完成（run-to-completion）语义。当然，这种编程模型源自早期浏览器的实现，如今它也成为用任务来架构浏览器的另一个重要理由。

## 12.2 定时器与 setTimeout

任务也是支持若干 JavaScript API 的自然方式，这些 API 要求在将来的某个时刻运行某个函数。例如，setTimeout [5] 可以让你从现在起若干毫秒之后运行一个 JavaScript 函数。下面这段代码会在一秒后向控制台打印 "Callback"：

```javascript
function callback() { console.log('Callback'); }
setTimeout(callback, 1000);
```

与第 9 章的 addEventListener 一样，我们将通过把回调保存在一个 JavaScript 变量中并创建一个句柄（handle）来实现 setTimeout，Python 侧的代码可以通过该句柄调用它：

```javascript
SET_TIMEOUT_REQUESTS = {}
function setTimeout(callback, time_delta) {
    var handle = Object.keys(SET_TIMEOUT_REQUESTS).length;
    SET_TIMEOUT_REQUESTS[handle] = callback;
    call_python("setTimeout", handle, time_delta)
}
```

导出的 setTimeout 函数将创建一个定时器，等待所请求的时间段，然后请求 JavaScript 运行时运行该回调。最后这一步将通过 __runSetTimeout 完成：³

```javascript
function __runSetTimeout(handle) {
    var callback = SET_TIMEOUT_REQUESTS[handle]
    callback();
}
```

现在来实现这个 API 的 Python 侧。我们可以使用 Python threading [7] 模块中的 Timer [6] 类。这个类的用法如下：⁴

```python
import threading
def callback():
    # ...
threading.Timer(1.0, callback).start()
```

这会在一秒后运行 callback。很简单！但 threading.Timer 会在一个新的 Python 线程上执行其回调，这就带来了很多挑战。回调不能直接调用 evaljs：那样一来，JavaScript 就会同时运行在两个 Python 线程上，这可不是什么好事。⁵ 因此，作为一种变通，回调会向任务队列添加一个新 Task 来调用 __runSetTimeout。这样做的缺点是回调可能被延迟，但好处是 JavaScript 只会在主线程上执行。

来实现它：

```python
SETTIMEOUT_JS = "__runSetTimeout(dukpy.handle)"
class JSContext:
    def __init__(self, tab):
        # ...
        self.interp.export_function("setTimeout",
            self.setTimeout)
    def dispatch_settimeout(self, handle):
        self.interp.evaljs(SETTIMEOUT_JS, handle=handle)
    def setTimeout(self, handle, time):
        def run_callback():
            task = Task(self.dispatch_settimeout, handle)
            self.tab.task_runner.schedule_task(task)
        threading.Timer(time / 1000.0, run_callback).start()
```

但这还不够正确。现在有两个线程在访问 task_runner：主线程负责运行任务，定时器线程负责添加任务。这是一个竞态条件（race condition）[9]，可能导致各种糟糕的事情发生，所以我们必须确保同一时刻只有一个线程访问 task_runner。

为此我们使用一个 Condition [10] 对象，它在同一时刻只能被一个线程持有。每个线程在读写 task_runner 之前都要先尝试获取（acquire）condition，从而避免同时访问。⁶ Condition 类实际上就是一个锁（Lock）[11]，再加上「能够一直等待直到某个状态条件出现」的功能。如果你眼下没有别的工作可做，就获取 condition 然后调用 wait。这会让线程停在这一行代码上。当有新工作到来时，比如在 schedule_task 中，调用 notify_all 就会唤醒那个调用了 wait 的线程。

```python
class TaskRunner:
    def __init__(self, tab):
        # ...
        self.condition = threading.Condition()
    def schedule_task(self, task):
        self.condition.acquire(blocking=True)
        self.tasks.append(task)
        self.condition.notify_all()
        self.condition.release()
    def run(self):
        task = None
        self.condition.acquire(blocking=True)
        if len(self.tasks) > 0:
            task = self.tasks.pop(0)
        self.condition.release()
        if task:
            task.run()
        self.condition.acquire(blocking=True)
        if len(self.tasks) == 0:
            self.condition.wait()
        self.condition.release()
```

如果已经没有事情可做，在 run 循环的末尾调用 wait 非常重要。否则这个线程会倾向于耗掉大量 CPU，还会不断地获取和释放 condition。这种无谓的忙碌不仅会拖慢计算机，还会导致 Timer 的回调在飘忽不定的时间点上发生，因为两个线程在争抢这把锁。⁷

使用锁时，务必记住最终要释放锁，并且持有它的时间要尽可能短。例如，上面的代码在运行任务之前就释放了锁。这是因为任务一旦从队列中移除，其他线程就再也无法访问它，所以运行任务期间不需要持有锁。

不过，这里的 setTimeout 代码现在是线程安全的了，但还有另一个 bug：如果我们从一个页面导航到另一个页面，前一个页面上仍然待处理的 setTimeout 回调可能还会试图执行。这很容易预防：在 JSContext 上加一个 discarded 字段，并在加载新页面时设置它：

```python
class JSContext:
    def __init__(self, tab):
        # ...
        self.discarded = False
    def dispatch_settimeout(self, handle):
        if self.discarded: return
        self.interp.evaljs(SETTIMEOUT_JS, handle=handle)
class Tab:
    def load(self, url, payload=None):
        # ...
        if self.js: self.js.discarded = True
        self.js = JSContext(self)
        # ...
```

> **深入探索**
> 遗憾的是，Python 目前有一个全局解释器锁（global interpreter lock）[12]（GIL），所以 Python 线程并不能真正并行运行。Python 的这个不幸限制对我们这个浏览器有些影响，但对真实浏览器没有影响，所以本章里我大多假装 GIL 不存在。而且也许未来某个版本的 Python 会把它去掉 [13]。尽管有全局解释器锁，我们仍然需要锁，因为 Python 线程可以在字节码操作之间或者调用 C 库期间让出执行权。这意味着并发访问和竞态条件仍然可能发生。⁸

## 12.3 长寿命线程

线程还可以用来为浏览器添加多任务处理能力。例如，第 10 章我们实现了 XMLHttpRequest 类，它允许脚本向服务器发起请求。但在我们的实现中，等待请求完成期间整个浏览器都会卡死。这显然很糟。⁹ Python 的 Thread 类能让我们做得更好：

```python
threading.Thread(target=callback).start()
```

这段代码会创建一个新线程然后立即返回。随后回调在新线程上并行运行，而最初的线程继续执行后面的代码。

我们将用线程来实现异步的 XMLHttpRequest 调用。具体来说，我们让浏览器启动一个线程，在该线程上执行请求并解析响应，然后调度一个 Task 把响应送回给脚本。

与 setTimeout 一样，我们把回调存储在 JavaScript 一侧，并用句柄来引用它：

```javascript
XHR_REQUESTS = {}
function XMLHttpRequest() {
    this.handle = Object.keys(XHR_REQUESTS).length;
    XHR_REQUESTS[this.handle] = this;
}
```

当脚本调用 XMLHttpRequest 对象上的 open 方法时，我们现在允许 is_async 标志为 true：¹⁰

```javascript
XMLHttpRequest.prototype.open = function(method, url, is_async) {
    this.is_async = is_async;
    this.method = method;
    this.url = url;
}
```

send 方法需要把 is_async 标志和句柄一并传过去：

```javascript
XMLHttpRequest.prototype.send = function(body) {
    this.responseText = call_python("XMLHttpRequest_send",
        this.method, this.url, body, this.is_async, this.handle);
}
```

在浏览器一侧，XMLHttpRequest_send 处理器将分三部分。第一部分解析 URL 并做安全检查：

```python
class JSContext:
    def XMLHttpRequest_send(
        self, method, url, body, isasync, handle):
        full_url = self.tab.url.resolve(url)
        if not self.tab.allowed_request(full_url):
            raise Exception("Cross-origin XHR blocked by CSP")
        if full_url.origin() != self.tab.url.origin():
            raise Exception(
                "Cross-origin XHR request not allowed")
```

接着，我们定义一个函数来完成请求，并把运行回调的任务排入队列：

```python
class JSContext:
    def XMLHttpRequest_send(
        self, method, url, body, isasync, handle):
        # ...
        def run_load():
            headers, response = full_url.request(self.tab.url, body)
            task = Task(self.dispatch_xhr_onload, response, handle)
            self.tab.task_runner.schedule_task(task)
            return response
```

注意这个任务运行的是 dispatch_xhr_onload，我们马上就会定义它。

最后，根据 is_async 标志，浏览器要么立即调用这个函数，要么在一个新线程中调用它：

```python
class JSContext:
    def XMLHttpRequest_send(
        self, method, url, body, isasync, handle):
        # ...
        if not isasync:
            return run_load()
        else:
            threading.Thread(target=run_load).start()
```

注意在异步情形下，XMLHttpRequest_send 方法启动一个线程后立即返回。该线程将与浏览器的主工作并行运行，直到请求完成。

为了把结果传回 JavaScript，我们会在 dispatch_xhr_onload 中调用 __runXHROnload 函数：

```python
XHR_ONLOAD_JS = "__runXHROnload(dukpy.out, dukpy.handle)"
class JSContext:
    def dispatch_xhr_onload(self, out, handle):
        if self.discarded: return
        do_default = self.interp.evaljs(
            XHR_ONLOAD_JS, out=out, handle=handle)
```

__runXHROnload 方法只是从 XHR_REQUESTS 中取出相关对象并调用它的 onload 函数：

```javascript
function __runXHROnload(body, handle) {
    var obj = XHR_REQUESTS[handle];
    var evt = new Event('load');
    obj.responseText = body;
    if (obj.onload)
        obj.onload(evt);
}
```

正如你所见，任务不仅让浏览器本身、也让运行在浏览器中的应用能够把工作推迟到以后执行。

> **深入探索**
> XMLHttpRequest 在推动 Web 演进的历程中扮演了关键角色。在 20 世纪 90 年代，点击一个链接或提交一个表单都需要加载一个新页面。有了 XMLHttpRequest，网页就能表现得非常像一个动态应用了；GMail 就是早期著名的例子。¹¹ 如今，使用 DOM 修改而不是页面加载来更新自身状态的 Web 应用被称为单页应用（single-page app）[14]。单页应用催生了交互性更强、更复杂的 Web 应用，这反过来又让浏览器的速度和响应能力变得更加重要。
>
> 第一个使用 XMLHttpRequest 的应用是 1999 年的 Outlook Web Access [16]，但这个 API 花了一段时间才进入其他浏览器。

## 12.4 渲染的节奏

任务的意义不只是实现几个 JavaScript API。一旦某件事变成了 Task，由任务运行器来控制它何时运行：也许是现在，也许是稍后，也许至多每秒一次，甚至活动页面与非活动页面采用不同的频率，或者按照它的优先级来定。浏览器甚至可以拥有多个任务运行器，针对不同的使用场景分别优化。

现在，你可能很难看出浏览器要如何决定优先运行哪个 JavaScript 回调，或者它为什么想以固定的节奏执行 JavaScript 任务。但除了 JavaScript 之外，浏览器还必须渲染页面，而且你可能还记得第 2 章说过，我们希望浏览器渲染页面的速度恰好跟上显示硬件的刷新速度。在大多数电脑上，这是每秒 60 次，也就是每帧 16 ms。然而，即使以今天的计算机，维持这么高的帧率也相当困难，对我们的玩具浏览器来说更是过高的标准。

所以，让我们把每秒 30 帧——每帧 33 ms——定为我们刷新率（refresh rate）的目标：¹²

```python
REFRESH_RATE_SEC = .033
```

现在，绘制一帧的工作被分摊在 Tab 和 Browser 之间。Tab 需要调用 render 来计算一个显示列表（display list）。然后 Browser 需要对这个显示列表（以及浏览器镶边的显示列表）进行光栅化并绘制。我们把这些 Browser 侧的任务放进它们自己的方法里：

```python
class Browser:
    def raster_and_draw(self):
        self.raster_chrome()
        self.raster_tab()
        self.draw()
```

我们并不需要每个标签页每帧都重绘自己，因为用户一次只能看到一个标签页。我们只需要活动标签页重绘自己。因此，应该由 Browser 来控制何时更新显示，而不是各个 Tab 自己。所以，我们来写一个 schedule_animation_frame 方法¹³，它调度一个渲染活动标签页的任务：

```python
class Browser:
    def schedule_animation_frame(self):
        def callback():
            active_tab = self.active_tab
            task = Task(active_tab.render)
            active_tab.task_runner.schedule_task(task)
        threading.Timer(REFRESH_RATE_SEC, callback).start()
```

注意，每次调度一帧时，我们都会设置一个定时器来调度下一帧。我们可以在启动浏览器时启动这个过程。在顶层循环中，在活动标签页上运行一个任务之后，浏览器需要进行光栅化和绘制，以防那个任务是一个渲染任务：

```python
def mainloop(browser):
    while True:
        # ...
        browser.active_tab.task_runner.run()
        browser.raster_and_draw()
        browser.schedule_animation_frame()
```

现在，我们每 33 ms 就会调度一个新的渲染任务，正如我们所期望的那样。

> **深入探索**
> 任何特定的刷新率都没有什么特别之处。有些显示器每秒刷新 72 次，刷新更频繁 [17] 的显示器也正变得越来越常见。电影通常以每秒 24 帧拍摄（尽管有些导演倡导 48 帧 [18]），而电视节目传统上采用每秒 30 帧。一致性往往比实际帧率更重要：稳定的每秒 24 帧看起来可能比在 60 帧与 24 帧之间波动的帧率流畅得多。

## 12.5 用脏位优化

如果你在自己电脑上运行它，CPU 占用率很可能会飙升，电池也会开始耗电。这是因为我们每一帧都在调用 render，也就是说，我们的浏览器现在在不停地计算样式、构建布局树、绘制显示列表。这些工作大多是浪费的，因为在大多数帧上，网页根本没有变化，旧的样式、布局树和显示列表与新生成的同样可用。

让我们用脏位（dirty bit）来修复这个问题。脏位是一小块状态，用来告诉我们某个复杂的数据结构是否是最新的。既然我们想知道的是是否需要运行 render，那就把这个脏位命名为 needs_render：

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.needs_render = False
    def set_needs_render(self):
        self.needs_render = True
    def render(self):
        if not self.needs_render: return
        # ...
        self.needs_render = False
```

这个标志的一个好处是，现在我们可以在 HTML 发生变化时设置 needs_render，而不是直接调用 render。渲染仍然会发生，只是在稍后。这让脚本运行得更快，尤其是当它们多次修改页面的时候。请在修改 DOM 的 innerHTML_set、load、click 和 keypress 中做出这个改动。

例如，在 load 中这样做：

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.set_needs_render()
```

在 innerHTML_set 中这样做：

```python
class JSContext:
    def innerHTML_set(self, handle, s):
        # ...
        self.tab.set_needs_render()
```

还有更多对 render 的调用；你应该把它们全部找出来并修改……不过，让我们仔细看一下 click。

现在，当有什么东西变化时，我们不再立即渲染。这意味着当某个方法被调用时，布局树（以及样式）可能已经过时了。通常这不是问题，但有一种重要情形例外：点击处理。这是因为我们需要读取布局树来确定被点击的是什么对象，这意味着布局树必须是最新的。为了修复这个问题，在 click 的开头加一个对 render 的调用：

```python
class Tab:
    def click(self, x, y):
        self.render()
        # ...
```

我们的实现还有一个问题：现在每当活动标签页运行一个任务，浏览器就会执行一次 raster_and_draw。但有时那个任务只是在运行并不触碰网页的 JavaScript，这时调用 raster_and_draw 就是浪费。我们可以用另一个脏位来避免这种情况，我把它称为 needs_raster_and_draw：¹⁴

```python
class Browser:
    def __init__(self):
        self.needs_raster_and_draw = False
    def set_needs_raster_and_draw(self):
        self.needs_raster_and_draw = True
    def raster_and_draw(self):
        if not self.needs_raster_and_draw:
            return
        # ...
        self.needs_raster_and_draw = False
```

每当 Browser 修改了浏览器镶边（browser chrome）的某些内容，或者 Tab 修改了自己的渲染结果时，我们都需要调用 set_needs_raster_and_draw。浏览器镶边会被事件处理器修改：

```python
class Browser:
    def handle_click(self, e):
        if e.y < self.chrome.bottom:
            # ...
            self.set_needs_raster_and_draw()
    def handle_key(self, char):
        if self.chrome.keypress(char):
            # ...
            self.set_needs_raster_and_draw()
    def handle_enter(self):
        if self.chrome.enter():
            # ...
            self.set_needs_raster_and_draw()
```

这里我需要做一个小改动，让 enter 返回是否做了什么事情：

```python
class Chrome:
    def enter(self):
        if self.focus == "address bar":
            self.browser.active_tab.load(URL(self.address_bar))
            self.focus = None
            return True
        return False
```

Tab 在运行完 render 之后也应该设置这个脏位：

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.browser = browser
    def render(self):
        # ...
        self.browser.set_needs_raster_and_draw()
```

构造 Tab 时需要传入 browser 参数：

```python
class Browser:
    def new_tab(self, url):
        new_tab = Tab(self, HEIGHT - self.chrome.bottom)
        # ...
```

现在，渲染管线只在必要时才会运行，浏览器的性能应该又可以接受了。

> **深入探索**
> 这种基于调度、基于任务的渲染方式，是运行复杂交互式应用所必需的，但直到 2010 年代，在这样的 Web 应用已经普及很久之后，所有现代浏览器才全部采用了它。因为这通常需要对庞大的浏览器代码库进行大规模重构。例如，Chromium 直到最近 [19] 才完成 100% 的迁移工作以充分利用这一模型，当然，（永远）还有剩余的工作要做。

## 12.6 动画帧

保持稳定渲染节奏的一个重大理由是让动画流畅运行。网页可以用 requestAnimationFrame [20] API 来设置这样的动画。这个 API 允许脚本在浏览器运行渲染管线之前运行代码，从而让动画尽可能流畅。它是这样工作的：

```javascript
function callback() { /* Modify DOM */ }
requestAnimationFrame(callback);
```

通过调用 requestAnimationFrame，这段代码做了两件事：调度一个渲染任务，并请求浏览器在那个渲染任务的开头、任何浏览器渲染代码之前调用 callback。这让网页作者可以修改页面，并确信它会被立即渲染出来。

这个 JavaScript API 的实现很直接。和之前一样，我们把回调存储在 JavaScript 一侧：

```javascript
RAF_LISTENERS = [];
function requestAnimationFrame(fn) {
    RAF_LISTENERS.push(fn);
    call_python("requestAnimationFrame");
}
```

在 JSContext 中，当这个方法被调用时，我们需要调度一个新的渲染任务：

```python
class JSContext:
    def __init__(self, tab):
        # ...
        self.interp.export_function("requestAnimationFrame",
            self.requestAnimationFrame)
    def requestAnimationFrame(self):
        task = Task(self.tab.render)
        self.tab.task_runner.schedule_task(task)
```

然后，当 render 真正被调用时，我们需要回调 JavaScript，像这样：

```python
class Tab:
    def render(self):
        if not self.needs_render: return
        self.js.interp.evaljs("__runRAFHandlers()")
        # ...
```

这个 __runRAFHandlers 函数有点绕：

```javascript
function __runRAFHandlers() {
    var handlers_copy = RAF_LISTENERS;
    RAF_LISTENERS = [];
    for (var i = 0; i < handlers_copy.length; i++) {
        handlers_copy[i]();
    }
}
```

注意，__runRAFHandlers 需要在运行任何回调之前把 RAF_LISTENERS 重置为空数组。这是因为某个回调可能自己又调用 requestAnimationFrame。如果这发生在这类回调执行期间，规范规定应该调度第二个动画帧。也就是说，我们必须确保把当前帧的回调与下一帧的回调分开存储。

这种情形看起来像是个极端案例（corner case），但实际上非常重要，因为页面正是靠这样一帧接一帧地迭代调度来运行动画的。例如，下面是一个简单的计数器「动画」：

```javascript
var count = 0;
function callback() {
    var output = document.querySelectorAll("div")[1];
    output.innerHTML = "count: " + (count++);
    if (count < 100)
        requestAnimationFrame(callback);
}
requestAnimationFrame(callback);
```

这段脚本会让 100 个动画帧任务在渲染事件循环上运行。在此期间，我们的浏览器会显示一个从 0 数到 99 的动画。用我们的 HTTP 服务器提供这个示例网页：

```python
def do_request(session, method, url, headers, body):
    elif method == "GET" and url == "/count":
        return "200 OK", show_count()
# ...
def show_count():
    out = "<!doctype html>"
    out += "<div>";
    out += "  Let's count up to 99!"
    out += "</div>";
    out += "<div>Output</div>"
    out += "<script src=/eventloop.js></script>"
    return out
```

加载它，观察从 0 到 99 的动画。

到目前为止，我们的实现有一个缺陷：一个不留神的开发者可能会多次调用 requestAnimationFrame，从而调度出比预期更多的动画帧。如果之后出现了其他 JavaScript 任务，它们可能会被拖延很多很多帧。

幸运的是，渲染有它的特殊之处：连续出现两个渲染任务永远没有意义，因为页面在这两帧之间不会变化。为了避免出现两个渲染任务，我们给 Browser 加一个名为 needs_animation_frame 的脏位，指示是否真的需要调度一个渲染任务：

```python
class Browser:
    def __init__(self):
        self.animation_timer = None
        # ...
        self.needs_animation_frame = True
    def schedule_animation_frame(self):
        # ...
        if self.needs_animation_frame and not self.animation_timer:
            self.animation_timer = \
                threading.Timer(REFRESH_RATE_SEC, callback)
            self.animation_timer.start()
```

注意我还检查了是否不存在 animation_timer 对象；这可以避免同时运行两个定时器。

当请求一个动画帧时，标签页会设置 needs_animation_frame 标志：

```python
class JSContext:
    def requestAnimationFrame(self):
        self.tab.browser.set_needs_animation_frame(self.tab)
class Tab:
    def set_needs_render(self):
        # ...
        self.browser.set_needs_animation_frame(self)
class Browser:
    def set_needs_animation_frame(self, tab):
        if tab == self.active_tab:
            self.needs_animation_frame = True
```

注意，set_needs_animation_frame 只有在从活动标签页调用时才会真正设置这个脏位。这保证了非活动标签页无法干扰活动标签页。除了防止脚本调度过多的动画帧之外，这套机制还确保了：如果我们的浏览器持续慢于每秒 30 帧，也不会积压出一个不断增长的渲染任务队列。

> **深入探索**
> 在 requestAnimationFrame API 出现之前，开发者们用 setTimeout 来近似实现它。这确实能以（大致）固定的节奏运行动画，但由于它与浏览器的渲染循环不对齐，事件有时会在回调与渲染之间被处理，这可能迫使浏览器执行一次多余的、不必要的渲染。requestAnimationFrame 不仅避免了这一点，还让浏览器在网页标签页或窗口被切到后台、最小化或以其他方式被节流时关掉渲染工作，同时仍允许其他后台任务继续运行，比如把你的工作保存到云端。

## 12.7 剖析渲染

现在我们有了一套每 33 ms 调度一个渲染任务的系统。但如果渲染耗时超过 33 ms 才能完成呢？在回答这个问题之前，让我们先给浏览器加上插桩（instrumentation），测量渲染到底花了多少时间。在优化之前先做测量非常重要，因为结果往往会出人意料。

为了给浏览器插桩，我们让它输出 Chrome 的 chrome://tracing [22]、Firefox Profiler [23] 或 Perfetto UI [24] 所使用的 JSON [21] 追踪（trace）格式。¹⁵

首先，让我们把实际的文件和格式封装到一个类里：

```python
class MeasureTime:
    def __init__(self):
        self.file = open("browser.trace", "w")
```

一个追踪文件就是一个带有 traceEvents 字段¹⁶的 JSON 对象，该字段包含一列追踪事件（trace event）：

```python
class MeasureTime:
    def __init__(self):
        # ...
        self.file.write('{"traceEvents": [')
```

每个追踪事件有若干字段。ph 和 name 字段定义事件类型。例如，把 ph 设为 M、name 设为 process_name，可以让我们修改所显示的进程名：

```python
class MeasureTime:
    def __init__(self):
        # ...
        ts = time.time() * 1000000
        self.file.write(
            '{ "name": "process_name",' +
            '"ph": "M",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "cat": "__metadata",' +
            '"args": {"name": "Browser"}}')
        self.file.flush()
```

新的名字（"Browser"）通过 args 传入，其他字段都是必填的。由于我们的浏览器只有一个进程，进程 ID 我就直接传 1，而对于元数据类追踪事件，类别（category）必须是 __metadata。ts 字段存储时间戳；由于这是第一个事件，它将设定整条追踪的起始时间，所以务必填入真实的当前时间。

我们会在启动浏览器时创建这个 MeasureTime 对象，这样就可以用它来测量浏览器各个组件的耗时：

```python
class Browser:
    def __init__(self):
        self.measure = MeasureTime()
```

现在，让我们在浏览器做有意思的事情时添加追踪事件。我们特别需要 B 和 E 事件，它们标记某段有意思的计算的开始和结束。由于已经有了那个初始追踪事件，后续每个追踪事件前面都需要一个逗号：

```python
class MeasureTime:
    def time(self, name):
        ts = time.time() * 1000000
        self.file.write(
            ', { "ph": "B", "cat": "_",' +
            '"name": "' + name + '",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "tid": 1}')
        self.file.flush()
```

这里，传给 time 的 name 参数应描述开始的是什么类型的计算，而且它必须与传给对应的 stop 事件的 name 相匹配：

```python
class MeasureTime:
    def stop(self, name):
        ts = time.time() * 1000000
        self.file.write(
            ', { "ph": "E", "cat": "_",' +
            '"name": "' + name + '",' +
            '"ts": ' + str(ts) + ',' +
            '"pid": 1, "tid": 1}')
        self.file.flush()
```

只需调用 time 和 stop，我们就能测量标签页渲染：

```python
class Tab:
    def render(self):
        if not self.needs_render: return
        self.browser.measure.time('render')
        # ...
        self.browser.measure.stop('render')
```

对 raster_and_draw，以及所有调用 evaljs 运行 JavaScript 的代码，都照此办理。

最后，当我们结束追踪（也就是关闭浏览器窗口）时，我们想让这个文件保持为合法的 JSON 文件：

```python
class MeasureTime:
    def finish(self):
        self.file.write(']}')
        self.file.close()
class Browser:
    def handle_quit(self):
        # ...
        self.measure.finish()
```

顺便说一句，请注意我很小心地在每次写入之后都 flush。这是为了确保：一旦浏览器崩溃，所有可能帮我调试的日志事件都已经被安全地写到磁盘上了。¹⁷

## 12.8 双线程

嗯，一种选择当然是优化光栅化与绘制，甚至优化 render 本身，下一章我们会这么做。但另一种选择——复杂，但值得，而且所有主流浏览器都在做——是采用多线程架构，让 render 步骤与光栅化及绘制步骤并行执行。这不仅会加速渲染管线（从 85 ms 降到 62 ms），我们还能在一个线程上执行 JavaScript，同时在另一个线程上运行开销很大的 raster_and_draw 任务。

我们把这两个线程称为浏览器线程（browser thread）¹⁸和主线程（main thread）。¹⁹浏览器线程对应于 Browser 类，负责光栅化与绘制。它还负责与浏览器镶边的交互。而主线程对应于一个 Tab，负责运行脚本、加载资源和渲染，以及运行事件处理器和回调等相关任务。如果你打开了多个标签页，就会有多个主线程（每个标签页一个），但浏览器线程只有一个。

多线程架构颇为棘手，所以让我们先做一点规划。首先，已经存在的那个线程——你启动浏览器时运行的那个——将是浏览器线程。每当我们创建一个标签页时，我们会创建一个主线程。这两个线程需要通信，以处理事件并在屏幕上绘制。

当浏览器线程需要与主线程通信、向它通报事件时，它会把任务放到主线程的 TaskRunner 上。²⁰主线程需要与浏览器线程通信，以请求动画帧并把显示列表发送给它进行光栅化与绘制；主线程将通过 browser 上的两个方法做到这一点：请求动画帧的 set_needs_animation_frame，以及发送显示列表的 commit。因此，渲染一帧的整体控制流是：

1. 主线程中运行的代码通过 set_needs_animation_frame 请求一个动画帧，也许是在响应某个事件处理器时，或者由于 requestAnimationFrame。
2. 浏览器线程事件循环在主线程的 TaskRunner 上调度一个动画帧。
3. 主线程执行它那部分渲染工作，然后调用 browser.commit。
4. 浏览器线程对显示列表进行光栅化并绘制到屏幕上。

让我们实现这个设计。首先，我们给每个 TaskRunner 添加一个 Thread，它将成为该标签页的主线程。这个线程需要在循环中运行，从任务队列取出任务并执行它们。我们把这个循环放在 TaskRunner 的 run 方法里。

```python
class TaskRunner:
    def __init__(self, tab):
        # ...
        self.main_thread = threading.Thread(
            target=self.run,
            name="Main thread",
        )
    def start_thread(self):
        self.main_thread.start()
```

注意我给线程起了名字；这是个好习惯，有助于调试。我们也给浏览器线程起个名字：

```python
class Browser:
    def __init__(self):
        # ...
        threading.current_thread().name = "Browser thread"
```

从顶层的 while True 循环中删去对 run 的调用，因为那个循环现在要在浏览器线程中运行。而 run 将拥有自己的循环：

```python
class TaskRunner:
    def run(self):
        while True:
            # ...
```

由于这个循环永远运行，主线程将无限期存活。所以如果浏览器退出，我们会希望它也请求主线程退出：

```python
class Browser:
    def handle_quit(self):
        for tab in self.tabs:
            tab.task_runner.set_needs_quit()
```

set_needs_quit 方法会在 TaskRunner 上设置一个标志，每次循环时都会检查它：

```python
class TaskRunner:
    def set_needs_quit(self):
        self.condition.acquire(blocking=True)
        self.needs_quit = True
        self.condition.notify_all()
        self.condition.release()
    def run(self):
        while True:
            self.condition.acquire(blocking=True)
            needs_quit = self.needs_quit
            self.condition.release()
            if needs_quit:
                return
            # ...
            self.condition.acquire(blocking=True)
            if len(self.tasks) == 0 and not self.needs_quit:
                self.condition.wait()
            self.condition.release()
```

Browser 不应该再直接调用 Tab 上的任何方法。相反，为了处理事件，它应该在主线程上调度任务。例如，加载是这样做的：

```python
class Browser:
    def schedule_load(self, url, body=None):
        self.active_tab.task_runner.clear_pending_tasks()
        task = Task(self.active_tab.load, url, body)
        self.active_tab.task_runner.schedule_task(task)
    def new_tab(self, url):
        # ...
        self.schedule_load(url)
```

在加载新页面之前，我们需要清除所有待处理任务，因为那些先前的任务现在已经无效了：

```python
class TaskRunner:
    def clear_pending_tasks(self):
        self.condition.acquire(blocking=True)
        self.tasks.clear()
        self.pending_scroll = None
        self.condition.release()
```

我们还需要把 new_tab 拆成一个会获取锁的版本和一个不获取锁的版本（new_tab_internal）：

```python
class Browser:
    def new_tab(self, url):
        self.lock.acquire(blocking=True)
        self.new_tab_internal(url)
        self.lock.release()
    def new_tab_internal(self, url):
        new_tab = Tab(self, HEIGHT - self.chrome.bottom)
        self.tabs.append(new_tab)
        self.set_active_tab(new_tab)
        self.schedule_load(url)
```

这样一来，像 Chrome 的 click 方法这类已经持有锁的方法，就可以直接调用 new_tab_internal 了。²¹

```python
class Chrome:
    def click(self, x, y):
        if self.newtab_rect.contains(x, y):
            self.browser.new_tab_internal(
                URL("https://browser.engineering/"))
    def enter(self):
        if self.focus == "address bar":
            self.browser.schedule_load(URL(self.address_bar))
```

事件处理器大体相似，只是我们需要小心区分影响浏览器镶边的事件和影响标签页的事件。以 handle_click 为例。如果用户点击的是浏览器镶边（即 e.y < self.chrome.bottom），我们可以在浏览器线程里就地处理。但如果用户点击的是网页，我们就必须在主线程上调度一个任务：

```python
class Browser:
    def handle_click(self, e):
        if e.y < self.chrome.bottom:
            # ...
        else:
            # ...
            tab_y = e.y - self.chrome.bottom
            task = Task(self.active_tab.click, e.x, tab_y)
            self.active_tab.task_runner.schedule_task(task)
```

同样的逻辑也适用于按键：

```python
class Browser:
    def handle_key(self, char):
        if not(0x20 <= ord(char) < 0x7f): return
        if self.chrome.keypress(char):
            # ...
        elif self.focus == "content":
            task = Task(self.active_tab.keypress, char)
            self.active_tab.task_runner.schedule_task(task)
```

对 Browser 到 Tab 的其他调用也照此办理。

现在，浏览器线程会告诉主线程该做什么了。反方向的通信要更微妙一些。

> **深入探索**
> 线程最初是通过抢占式多任务处理来提升响应能力的机制，而如今它们还能让浏览器提高吞吐量，因为连手机都有好几个核心。不过不同的 CPU 架构各有差异，浏览器工程师（比如你！）必须根据具体情况或多或少地利用硬件并行性。例如，有些设备比其他设备拥有更多 CPU 核心 [27]，有些对电池功耗更敏感，还有些设备上诸如监听无线电台之类的系统进程，可能会限制浏览器实际可用的并行度。

## 12.9 提交显示列表

我们已经有了一个 set_needs_animation_frame 方法，但我们还需要一个 commit 方法，供 Tab 在创建完显示列表之后调用。如果你仔细看看我们的光栅化与绘制代码，会发现要绘制一个显示列表，我们还需要知道 URL（用于更新浏览器镶边）、文档高度（用于分配尺寸正确的表面），以及滚动位置（用于绘制表面的正确部分）。

让我们建一个简单的类来存储这些数据：

```python
class CommitData:
    def __init__(self, url, scroll, height, display_list):
        self.url = url
        self.scroll = scroll
        self.height = height
        self.display_list = display_list
```

运行动画帧时，Tab 应该构造一个这样的对象并把它传给 commit。为了不让 render 变得太令人困惑，我们把这件事放进一个新的 run_animation_frame 方法，并把 __runRAFHandlers 也移到那里。²²

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.browser = browser
    def run_animation_frame(self):
        self.js.interp.evaljs("__runRAFHandlers()")
        self.render()
        commit_data = CommitData(
            self.url, self.scroll, document_height, self.display_list)
        self.display_list = None
        self.browser.commit(self, commit_data)
```

可以把 CommitData 对象想象成从主线程发送给浏览器线程的东西。这意味着主线程之后不应再访问它，也正是出于这个原因，我把 display_list 字段重置了。现在，Browser 应该调度 run_animation_frame：

```python
class Browser:
    def schedule_animation_frame(self):
        def callback():
            # ...
            task = Task(self.active_tab.run_animation_frame)
            # ...
```

在 Browser 一侧，新的 commit 方法需要读出它收到的所有数据，并按需调用 set_needs_raster_and_draw。由于这个调用来自另一个线程，我们需要获取锁。另一个重要步骤是：在下一次 commit 发生之前，不要清除 animation_timer 对象。否则多个渲染任务可能同时排入队列。最后，把 scroll 保存到 active_tab_scroll，把 url 保存到 active_tab_url。

```python
class Browser:
    def __init__(self):
        self.lock = threading.Lock()
        self.active_tab_url = None
        self.active_tab_scroll = 0
        self.active_tab_height = 0
        self.active_tab_display_list = None
    def commit(self, tab, data):
        self.lock.acquire(blocking=True)
        if tab == self.active_tab:
            self.active_tab_url = data.url
            self.active_tab_scroll = data.scroll
            self.active_tab_height = data.height
            if data.display_list:
                self.active_tab_display_list = data.display_list
            self.animation_timer = None
            self.set_needs_raster_and_draw()
        self.lock.release()
```

记得更新 Chrome 类来使用这个新的 url 字段，因为我们不希望运行在浏览器线程上的镶边去读取运行在主线程上的标签页。

注意，commit 是在主线程上被调用的，却获取了浏览器线程的锁。因此，commit 是两个线程同时「停下来」的关键时刻。²³还要注意，浏览器线程有可能收到来自非活动标签页的 commit，²⁴所以在复制任何已提交的数据之前，要先拿 tab 参数与活动标签页比较。

现在我们有了浏览器锁，浏览器线程访问它的任何变量时也都需要获取这个锁。例如，在 set_needs_animation_frame 中这样做：

```python

        # ...
        self.lock.release()
```

在 schedule_animation_frame 中，回调的内部和外部都需要获取锁：

```python

    def schedule_animation_frame(self):
        def callback():
            self.lock.acquire(blocking=True)
            # ...
            self.lock.release()
            # ...
        self.lock.acquire(blocking=True)
        # ...
        self.lock.release()
```

还要给 raster_and_draw、handle_down、handle_click、handle_key 和 handle_enter 加上锁。

我们也不希望主线程的渲染比浏览器线程的光栅化与绘制更快。所以我们应该只在光栅化和绘制完成之后才调度动画帧。²⁵幸运的是，这正是我们已经在做的：

```python
def mainloop(browser):

        # ...
        browser.raster_and_draw()
        browser.schedule_animation_frame()
```

就这样：现在我们应该是在一个线程上做 render，在另一个线程上做光栅化和绘制了！

## 12.11 线程化滚动

把主线程与浏览器线程分开，意味着主线程可以运行大量 JavaScript 而不会明显拖慢浏览器。但特别慢的 JavaScript 仍然可能拖慢浏览器。例如，想象一下我们的计数器加上了下面这个人为的减速：

```javascript
function callback() {
    for (var i = 0; i < 5e6; i++);
    // ...
}
```

现在，计数器的每一跳都有一个人为的停顿，期间主线程被卡在运行 JavaScript 中。这意味着它无法响应任何事件；例如，如果你按住向下键，滚动会又卡又烦人。我建议你亲手试试，见识一下它有多烦人，因为现代浏览器通常不会有这种卡顿（jank）。²⁸

要修复这个问题，需要由浏览器线程来处理滚动，而不是主线程。这比看起来更难，因为滚动偏移（scroll offset）既可能受浏览器影响（当用户滚动时），也可能受主线程影响（当加载新页面或通过 JavaScript 改变文档高度时）。现在浏览器线程和主线程并行运行，它们对滚动偏移的看法可能不一致。

我们能做到的最好方式，是保留两个滚动偏移：一个在浏览器线程上，一个在主线程上。重要的是，浏览器线程的滚动偏移是相对于浏览器那份显示列表的，而主线程的滚动偏移是相对于主线程那份显示列表的，两者可能略有不同。我们会让浏览器线程在渲染时把滚动偏移发送给主线程，但如果新的一帧有需要，主线程必须能够覆盖那个滚动偏移。

来实现它。首先，我们需要在 Browser 上存储一个 active_tab_scroll 变量，并在用户滚动时更新它：

```python
class Browser:
    def __init__(self):
        # ...
        self.active_tab_scroll = 0
    def clamp_scroll(self, scroll):
        height = self.active_tab_height
        maxscroll = height - (HEIGHT - self.chrome.bottom)
        return max(0, min(scroll, maxscroll))
    def handle_down(self):
        self.lock.acquire(blocking=True)
        if not self.active_tab_height:
            self.lock.release()
            return
        self.active_tab_scroll = self.clamp_scroll(
            self.active_tab_scroll + SCROLL_STEP)
        self.set_needs_raster_and_draw()
        self.needs_animation_frame = True
        self.lock.release()
```

这段代码调用 set_needs_raster_and_draw 用新的滚动偏移重绘屏幕，同时设置 needs_animation_frame，让主线程在将来异步地收到这个滚动偏移。尽管浏览器线程已经处理完了滚动，尽快把新值同步回主线程仍然很重要，因为点击处理这类 API 依赖它。

切换标签页时滚动偏移也需要变化，但这种情形下我们还不知道正确的滚动偏移。我们需要主线程先运行起来，为另一个标签页提交一个新的显示列表，到那时我们也会得到新的滚动偏移。把标签页切换（在 load 和 handle_click 中）移到一个新方法 set_active_tab 里，它只是简单地调度一个新的动画帧：

```python
class Browser:
    def set_active_tab(self, tab):
        self.active_tab = tab
        self.active_tab_scroll = 0
        self.active_tab_url = None
        self.needs_animation_frame = True
```

到目前为止，这些只是在更新浏览器线程上的滚动偏移。但主线程最终需要知道滚动偏移，这样才能把它传回 commit。所以，当 Browser 为 run_animation_frame 创建渲染任务时，它应该把滚动偏移传进去。run_animation_frame 函数随后可以在做任何其他事情之前先存储滚动偏移。给 run_animation_frame 加一个 scroll 参数：

```python
class Browser:
    def schedule_animation_frame(self):
        # ...
        def callback():
            self.lock.acquire(blocking=True)
            scroll = self.active_tab_scroll
            self.needs_animation_frame = False
            task = Task(self.active_tab.run_animation_frame, scroll)
            self.active_tab.task_runner.schedule_task(task)
            self.lock.release()
        # ...
```

但主线程也需要能够修改滚动偏移。我们将添加一个 scroll_changed_in_tab 标志来跟踪它是否这样做过，并且只有在 scroll_changed_in_tab 还不为 true 时，才存储浏览器线程的滚动偏移。²⁹

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.scroll_changed_in_tab = False
    def run_animation_frame(self, scroll):
        if not self.scroll_changed_in_tab:
            self.scroll = scroll
        # ...
```

我们会在两种情况下设置 scroll_changed_in_tab：加载新页面时，以及浏览器线程的滚动偏移超出页面底部时：

```python
class Tab:
    def load(self, url, payload=None):
        self.scroll = 0
        self.scroll_changed_in_tab = True
    def clamp_scroll(self, scroll):
        height = math.ceil(self.document.height + 2*VSTEP)
        maxscroll = height - self.tab_height
        return max(0, min(scroll, maxscroll))
    def run_animation_frame(self, scroll):
        # ...
        self.render()
        # ...
        self.browser.commit(self, commit_data)
        self.scroll_changed_in_tab = False
    def render(self):
        # ...
        clamped_scroll = self.clamp_scroll(self.scroll)
        if clamped_scroll != self.scroll:
            self.scroll_changed_in_tab = True
        self.scroll = clamped_scroll
        # ...
```

如果主线程没有覆盖浏览器的滚动偏移，我们就在提交数据里把滚动偏移设为 None：

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        scroll = None
        if self.scroll_changed_in_tab:
            scroll = self.scroll
        commit_data = CommitData(
            self.url, scroll, document_height, self.display_list)
        # ...
```

这种情况下，浏览器线程可以忽略滚动偏移：

```python
class Browser:

        if tab == self.active_tab:
            # ...
            if data.scroll != None:
                self.active_tab_scroll = data.scroll
```

## 12.12 线程化样式与布局

现在我们有了分开的浏览器线程和主线程，而且有些操作已经在浏览器线程上执行了，我们浏览器的线程架构已经开始类似于真实浏览器了。³²但为什么不把更多浏览器组件移到更多线程中去呢？那不是能让浏览器更快吗？

一言以蔽之：是的。现代浏览器有几十个线程 [32]，它们共同让浏览器更快、更灵敏。例如，光栅化与绘制常常在自己的线程上运行，这样即使正在准备新的一帧，浏览器线程也能处理事件。同样，现代浏览器通常有一组网络或输入/输出（I/O）线程，把与网络或文件系统的所有交互都从主线程上移走。

另一方面，浏览器的某些部分不容易线程化。例如，想想渲染管线的前半段：样式、布局和绘制。在我们的浏览器中，这些都在主线程上运行。但它们能搬到自己的线程上去吗？

原则上，可以。浏览器要做的只是正确实现所有 Web API 规范，并在脚本和 requestAnimationFrame 回调完成之后再绘制到屏幕上。规范在它所谓的「更新渲染（update-the-rendering）」[33] 步骤中详细说明了这一点。这些步骤完全没有提到样式或布局——因为样式和布局，正如绘制（paint 和 draw）一样，都是浏览器的实现细节。规范的「更新渲染」步骤列出的是在绘制到屏幕之前必须发生的、JavaScript 可观察的事情。

然而在实践中，目前没有任何一个现代浏览器在主线程之外的其他线程上运行样式或布局。³³原因很简单：有很多 JavaScript API 可以查询样式或布局状态。例如，getComputedStyle [35] 要求先计算样式，getBoundingClientRect [36] 要求先做布局。³⁴如果网页调用了这些 API 之一，而样式或布局又不是最新的，那它就必须当场被计算出来。这类计算被称为强制样式（forced style）或强制布局（forced layout）：样式或布局被「强制」立即发生，而不是像通常那样可能发生在 33 ms 之后。正是由于这些强制样式和强制布局的情形，浏览器必须能够在主线程上计算样式和布局。³⁵

解决这些矛盾的一种可能方式，是乐观地把样式和布局移出主线程，类似于在网页没有对滚动调用 preventDefault 时乐观地采用线程化滚动。这是个好主意吗？也许是，但强制样式和强制布局并不只是由 JavaScript 执行引起的。一个例子是我们对 click 的实现，它会在命中测试（hit testing）之前导致一次强制渲染：

```python
class Tab:
    def click(self, x, y):
        self.render()
        # ...
```

把命中测试移出主线程、或者对着旧版本的布局树做命中测试、或者想出某种别的技术方案，都是可能的（但非常困难）。因此，把样式和布局「乐观地」移出主线程并非不可能，只是极具挑战。话虽如此，浏览器开发者总是在寻找提速的方法，而且我预计在未来的某个时刻，样式和布局终将被移到它们自己的线程上。也许做出这一步的人就是你？

> **深入探索**
> 浏览器渲染管线深受图形学和游戏的影响。许多高性能游戏由事件循环驱动，在每个事件上更新场景图（scene graph）[37]，把场景图转换成显示列表，再把显示列表转换成像素。但在游戏里，程序员事先知道会提供什么样的场景图，并可以针对这些图调优图形流水线。游戏可以在启动时把深度优化的代码和预渲染好的数据上传到 CPU 和 GPU 的内存中。浏览器则相反，需要处理任意的网页，不可能花太多时间去优化任何东西。这带来了一套截然不同的取舍，也是浏览器常常感觉不如游戏华丽流畅的原因。

## 12.13 小结

本章演示了现代浏览器核心的双线程渲染系统。需要记住的要点有：

- 浏览器把工作组织成任务队列，任务包括运行 JavaScript、处理用户输入和渲染页面等。
- 目标是以 30 Hz 的节奏持续向屏幕生成帧，这意味着绘制每个动画帧的预算是 33 ms。
- 浏览器有两个参与渲染的关键线程。
- 主线程运行 JavaScript 以及那个特殊的渲染任务。
- 浏览器线程把显示列表绘制到屏幕上、处理/分发输入事件，并执行滚动。
- 主线程通过 commit 与浏览器线程通信，commit 会同步这两个线程。

此外，你也看到了把任务在两个线程之间挪动有多难，比如在浏览器线程上滚动所涉及的挑战，或者强制样式和强制布局如何使渲染管线难以与 JavaScript 完全隔离。

## 12.15 练习

**12.1　setInterval。** setInterval [38] 类似于 setTimeout，但它会按给定的节奏反复运行，直到 clearInterval [39] 被调用。实现这些 API。请务必在一个同时使用 requestAnimationFrame 且渲染管线有繁重工作要做的页面中，以各种节奏测试 setInterval。记录 setInterval 任务的实际计时；它的节奏有多稳定？

**12.2　任务计时。** 修改 Task，在每次任务执行时添加追踪事件。你要为这些追踪事件起个好名字。一种选择是使用 task_code 的 __name__ 字段，它会得到该任务运行的 Python 函数的名字。

**12.3　基于时钟的帧计时。** 目前，我们的浏览器把每个动画帧恰好调度在前一个完成之后 33 ms。这实际上会导致动画帧率的节奏慢于 33 ms。在我们的浏览器中修复这个问题：使用绝对时间而不是帧间固定延迟来调度动画帧。另外，把主线程的动画帧调度改为发生在光栅化与绘制之前而不是之后，让两个线程能够同时做动画工作。

**12.4　调度。** 随着越来越多种类的复杂任务出现在事件队列中，就越需要精心调度它们，以确保渲染节奏尽可能接近 33 ms，同时避免任务饿死（starvation）。实现一个带优先级系统的任务调度器，平衡这两种需求：优先处理渲染任务和输入处理，降低（但不要完全饿死）那些最终来自 setTimeout 之类 JavaScript API 的任务的优先级。在一个用大量基于 setTimeout 的任务压垮系统的网页上测试它。

**12.5　线程化加载。** 加载页面时，我们的浏览器目前要依次等待每个样式表或脚本资源加载完成。这带来了不必要的缓慢，尤其是在糟糕的网络环境下。改为让你的浏览器并行发出所有网络请求。不过，你仍然必须按照源代码顺序处理样式等资源。使用 Thread 的 join 方法可能很方便，它会阻塞调用 join 的线程，直到被 join 的线程完成。

**12.6　网络线程。** 真实浏览器通常有一个单独的线程处理网络（以及其他 I/O）。任务被添加到这个线程的方式与主线程类似。实现第三个网络线程，并把所有网络任务放到它上面。

**12.7　优化调度。** 在复杂网页上，浏览器可能跟不上期望的节奏。与其徒劳地试图跟上而持续把 CPU 跑满，不如实现一个帧时间估计器，基于先前的帧估计浏览器的真实节奏，并相应地调整 schedule_animation_frame。这样一来，复杂页面会一致地变慢，而不是出现随机的减速。

**12.8　光栅与绘制线程。** 目前，如果输入事件在浏览器线程正在光栅化或绘制时到达，该输入事件不会被立即处理。由于光栅化和绘制很慢，这尤其成问题。通过添加一个由浏览器线程控制的单独的光栅与绘制线程来修复它。在光栅与绘制线程做它的工作期间，浏览器线程应当可以处理输入事件。注意：SDL 不是线程安全的，所以所有直接使用 SDL 的步骤仍然需要在浏览器线程上执行。
