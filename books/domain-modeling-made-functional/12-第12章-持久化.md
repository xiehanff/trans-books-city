# 第 12 章 持久化

*Chapter 12: Persistence*

在本书中,我们一直把领域模型设计成"持久化无关"(persistence-ignorant)的——不让设计因为存储数据或与其他服务交互等实现问题而变形。

但在大多数应用中,总会有一些状态需要比某个进程或工作流的生命周期存活得更久。到了这一步,我们就需要求助于某种持久化机制,比如文件系统或数据库。遗憾的是,当我们从完美的领域迈向混乱的基础设施世界时,几乎总会出现不匹配的情况。

本章旨在帮助你处理与持久化领域驱动数据模型相关的问题。我们会先讨论一些高层原则,例如命令查询分离,然后再转向底层实现。特别地,我们将看到以两种不同的方式持久化我们的领域模型:先是在 NoSQL 文档数据库(document database)中,然后是在传统的关系数据库(relational database)中。

到本章结束时,你应该已经掌握了把数据库或其他持久化机制集成到应用中所需的全部工具。

不过,在深入持久化的具体机制之前,先来看看一些有助于在领域驱动设计的背景下处理持久化的通用准则:

- 把持久化推到边缘。
- 把命令(更新)与查询(读取)分离。
- 限界上下文必须拥有自己的数据存储。

## 把持久化推到边缘

正如我们前面讨论过的,理想情况下,我们希望所有函数都是"纯"(pure)的,这会让它们更容易推理和测试。

从外部世界读取或向其写入的函数不可能是纯的,因此在设计工作流时,我们要避免在工作流内部出现任何类型的 I/O 或持久化相关逻辑。这通常意味着把工作流分成两部分:

- 一个以领域为中心的部分,包含业务逻辑;
- 一个"边缘"(edge)部分,包含与 I/O 相关的代码。

例如,假设我们有一个实现支付发票逻辑的工作流。在一个把领域逻辑和 I/O 混杂在一起的模型中,实现可能会被设计成这样:

1. 从数据库加载发票。
2. 应用这笔付款。
3. 如果发票已全额支付,在数据库中将其标记为已全额支付,并发布一个 InvoicePaid 事件。
4. 如果发票未全额支付,在数据库中将其标记为部分支付,并且不发布任何事件。

这段代码在 F# 中可能长这样:

```fsharp
// 工作流混杂了领域逻辑和 I/O
let payInvoice invoiceId payment =
  // 从数据库加载
  let invoice = loadInvoiceFromDatabase(invoiceId)

  // 应用付款
  invoice.ApplyPayment(payment)

  // 处理不同的结果
  if invoice.IsFullyPaid then
    markAsFullyPaidInDb(invoiceId)
    postInvoicePaidEvent(invoiceId)
  else
    markAsPartiallyPaidInDb(invoiceId)
```

问题在于这个函数不是纯函数,而且很难测试。

让我们把纯的业务逻辑抽取成一个 applyPayment 函数,它不碰数据库,而是返回一个关于下一步做什么的决策,我们称之为 InvoicePaymentResult:

```fsharp
type InvoicePaymentResult =
  | FullyPaid
  | PartiallyPaid of ...

// 领域工作流:纯函数
let applyPayment unpaidInvoice payment :InvoicePaymentResult =
  // 应用付款
  let updatedInvoice = unpaidInvoice |> applyPayment payment

  // 处理不同的结果
  if isFullyPaid updatedInvoice then
    FullyPaid
  else
    PartiallyPaid updatedInvoice
  // 返回 PartiallyPaid 或 FullyPaid
```

这个函数完全是纯的。它不加载任何数据——它需要的所有数据都作为参数传进来。它也不保存任何数据。它做出一个决策,但把该决策作为选择类型(choice type)返回,而不是立即付诸行动。因此,要测试这个函数中的逻辑是否正常工作是很容易的。

一旦写好了这个函数,我们就会把它用作限界上下文边界处某个命令处理器(command handler)的一部分,在边界上 I/O 是允许的,像这样:

```fsharp
type PayInvoiceCommand = {
  InvoiceId : ...
  Payment : ...
  }

// 位于限界上下文边缘的命令处理器
let payInvoice payInvoiceCommand =
  // 从数据库加载
  let invoiceId = payInvoiceCommand.InvoiceId
  let unpaidInvoice =
    loadInvoiceFromDatabase invoiceId  // I/O

  // 调用纯领域
  let payment =
    payInvoiceCommand.Payment          // 纯
  let paymentResult =
    applyPayment unpaidInvoice payment // 纯

  // 处理结果
  match paymentResult with
  | FullyPaid ->
    markAsFullyPaidInDb invoiceId      // I/O
    postInvoicePaidEvent invoiceId     // I/O
  | PartiallyPaid updatedInvoice ->
    updateInvoiceInDb updatedInvoice   // I/O
```

注意,这个函数本身不做任何决策,它只是处理由内部那个以领域为中心的函数所做出的决策。因此,这个函数其实不需要用单元测试来测试,因为持久化逻辑通常很琐碎。当然,这并不是说它不该被测试,而是把它作为端到端集成测试的一部分来测试可能更划算。

你可以把这个复合函数想象成一份三明治——边缘是 I/O,中间是纯逻辑,如图所示(示意图:最外层是"加载数据(I/O)",中间是"纯领域逻辑(做出决策)",最外层另一侧是"保存数据/发布事件(I/O)",即 I/O → 纯 → I/O 的三明治结构)。

不过,如果我们确实想单独测试这个函数,只需要给它添加额外的函数参数,用来表示我们调用的所有 I/O 动作,像这样:

```fsharp
// 位于限界上下文边缘的命令处理器
let payInvoice
  loadUnpaidInvoiceFromDatabase // 依赖
  markAsFullyPaidInDb           // 依赖
  updateInvoiceInDb             // 依赖
  payInvoiceCommand =

  // 从数据库加载
  let invoiceId = payInvoiceCommand.InvoiceId
  let unpaidInvoice =
    loadUnpaidInvoiceFromDatabase invoiceId

  // 调用纯领域
  let payment =
    payInvoiceCommand.Payment
  let paymentResult =
    applyPayment unpaidInvoice payment

  // 处理结果
  match paymentResult with
  | FullyPaid ->
    markAsFullyPaidInDb(invoiceId)
    postInvoicePaidEvent(invoiceId)
  | PartiallyPaid updatedInvoice ->
    updateInvoiceInDb updatedInvoice
```

现在你就可以用惯常的方式为这些参数提供桩(stub),轻松地测试这个函数了。

当然,像这样使用 I/O 的复合函数应该位于应用的顶层——要么在"组合根"(composition root)中,要么在某个控制器(controller)中。

### 基于查询做决策

上面的例子假设所有数据都可以在领域函数外面加载好,然后再传给它。但如果你需要在"纯"代码的正中间基于数据库读取结果来做决策,该怎么办?

解决方案是保持纯函数完好无损,但把它们夹在非纯的 I/O 函数之间,像这样(示意图:数据流按 I/O 与纯逻辑交替排列——I/O 读取 → 纯决策 → I/O 写回 → I/O 读取 → 纯决策 → I/O 写回,纯函数负责业务逻辑和决策,I/O 函数负责读写数据)。

纯函数包含业务逻辑并做出决策,而 I/O 函数负责读写数据。

例如,假设我们需要扩展这个工作流:付款之后,我们要计算欠款总额,如果金额太大,就给客户发送一条警告消息。加上这些额外需求后,管道中的步骤大概会是这样:

```fsharp
--- I/O ---
从数据库加载发票

--- 纯 ---
执行付款逻辑

--- I/O ---
对输出的选择类型做模式匹配:
  若 "FullyPaid" -> 在数据库中将发票标记为已支付
  若 "PartiallyPaid" -> 把更新后的发票保存到数据库

--- I/O ---
从数据库加载所有未付发票的金额

--- 纯 ---
把这些金额加起来,判断总额是否过大

--- I/O ---
对输出的选择类型做模式匹配:
  若 "OverdueWarningNeeded" -> 给客户发送消息
  若 "NoActionNeeded" -> 什么都不做
```

如果 I/O 和逻辑混合得太多,简单的"三明治"就可能变成"千层蛋糕"。在这种情况下,你可能想把工作流拆成更短的迷你工作流,正如"长时间运行的工作流"一章所讨论的那样。这样,每个工作流都能保持为一个小而简单的三明治。

### Repository 模式在哪里?

在最初的领域驱动设计一书里,有一个访问数据库的模式叫 Repository 模式(Repository pattern)。如果你熟悉那本书,可能会想知道这个模式如何与函数式方法相契合。

答案是:它不契合。Repository 模式是在依赖可变性的面向对象设计中隐藏持久化的好办法。但当我们把一切都建模为函数并把持久化推到边缘时,就不再需要 Repository 模式了。

这种方法在可维护性上也有好处:我们不再需要一个拥有几十个方法的单一 I/O 接口(其中大多数方法在某个工作流中根本用不到),而是为每个具体的 I/O 访问定义一个独立的函数,并且只在需要时使用它们。

## 命令查询分离

我们要看的下一个原则是命令查询分离(Command-Query Separation,CQS)。

在领域建模的函数式方法中,我们所有的对象都被设计为不可变的。让我们也把存储系统想象成某种不可变对象。也就是说,每次我们改变存储系统中的数据时,它就变换成自己的一个新版本。

例如,如果想以函数式的方式对"插入一条记录"建模,我们可以把插入函数看作有两个参数:要插入的数据,以及数据存储的原始状态。插入完成后,该函数的输出是添加了这份数据之后的数据存储的新版本。

在代码中,我们可以用这个类型签名来建模:

```fsharp
type InsertData = DataStoreState -> Data -> NewDataStoreState
```

与数据存储交互有四种基本方式:"创建"(Create,即"插入" insert)、"读取"(Read,即"查询" query)、"更新"(Update)和"删除"(Delete)。我们刚刚看了"插入"——把其他几种也画成示意图:

- 插入 Insert:输入 DataStoreState 和 Data,输出 NewDataStoreState;
- 读取 Read:输入 DataStoreState 和 Query,输出 Data(不改变状态);
- 更新 Update:输入 DataStoreState 和 Data,输出 NewDataStoreState;
- 删除 Delete:输入 DataStoreState 和 Key,输出 NewDataStoreState。

或者用代码表示:

```fsharp
type InsertData = DataStoreState -> Data -> NewDataStoreState
type ReadData = DataStoreState -> Query -> Data
type UpdateData = DataStoreState -> Data -> NewDataStoreState
type DeleteData = DataStoreState -> Key -> NewDataStoreState
```

其中有一个与别的不同。很明显,我们有两类不同的操作:

- 插入、更新和删除操作会改变数据库的状态,并且(一般而言)不返回任何有用的数据;
- 而读取或查询操作不改变数据库的状态,并且是四者中唯一返回有用结果的操作。

命令查询分离正是建立在这些区别之上的设计原则。它指出:返回数据的代码("查询")不应与更新数据的代码("命令")混在一起。或者更简单地说:问一个问题不应该改变答案。

应用到函数式编程上,CQS 原则提出:

- 返回数据的函数不应该有副作用;
- 有副作用(更新状态)的函数不应该返回数据——也就是说,它们应该是返回 unit 的函数。

这没什么新鲜的——我们在整个设计过程中一直都是这么做的——不过现在让我们把它具体应用到数据库上。

我们来整理一下这些函数签名。

在输入侧,我们可以把 DataStoreState 替换成某种指向数据存储的句柄(handle),比如一个 DbConnection。

输出(NewDataStoreState)对现实世界的数据存储来说并不适用,因为数据存储是可变的,不会返回一个新状态。因此我们可以把那个类型替换成 Unit 类型。

现在我们的签名会是这样:

```fsharp
type InsertData = DbConnection -> Data -> Unit
type ReadData = DbConnection -> Query -> Data
type UpdateData = DbConnection -> Data -> Unit
type DeleteData = DbConnection -> Key -> Unit
```

DbConnection 类型是特定于某个具体数据存储的,所以我们会想用偏函数应用(partial application)或类似技术把这个依赖对调用方隐藏起来(参见"偏函数应用"一节),这意味着从领域代码的角度看,我们与持久化相关的函数是与具体数据库无关的,其签名会是这样:

```fsharp
type InsertData = Data -> Unit
type ReadData = Query -> Data
type UpdateData = Data -> Unit
type DeleteData = Key -> Unit
```

这正是我们在前面几章中看到过的。

当然,由于我们处理的是 I/O 以及可能出现的错误,实际的签名还需要包含一些效果(effect)。常见的做法是创建一个别名,比如 DataStoreResult 或 DbResult,其中包含 Result 类型,可能还包含 Async,于是我们的签名会是这样:

```fsharp
type DbError = ...
type DbResult<'a> = AsyncResult<'a,DbError>

type InsertData = Data -> DbResult<Unit>
type ReadData = Query -> DbResult<Data>
type UpdateData = Data -> DbResult<Unit>
type DeleteData = Key -> DbResult<Unit>
```

### 命令查询职责隔离

人们常常禁不住想对读取和写入复用同一批对象。例如,如果我们有一个 Customer 记录,我们可能会用下面这样的带副作用的函数把它保存到数据库,并从数据库加载:

```fsharp
type SaveCustomer = Customer -> DbResult<Unit>
type LoadCustomer = CustomerId -> DbResult<Customer>
```

然而,出于若干原因,读取和写入复用同一类型并不是一个好主意。

首先,查询返回的数据往往与写入时所需的数据不同。例如,查询可能返回反规范化(denormalized)的数据或计算出来的值,但写数据时不会用到这些。此外,在创建新记录时,像自动生成的 ID 或版本号这样的字段不会被用到,查询却会把它们返回回来。与其让一个数据类型身兼数职,不如为每种特定用途分别设计数据类型。在 F# 中,按需创建任意多的数据类型是很容易的,我们之前已经见过了。

避免复用的第二个原因是,查询和命令往往会各自独立演化,因此不应该耦合在一起。例如,你可能发现随着时间推移,你需要对同一份数据做三四种不同的查询,却只有一个更新命令。如果查询类型和命令类型被迫相同,就会很别扭。

最后,出于性能原因,有些查询可能需要一次返回多个实体。例如,加载订单时,你可能还想一并加载与该订单关联的客户数据,而不是为了拿客户再跑一趟数据库。当然,把订单保存到数据库时,你只会用对客户的引用(CustomerId),而不是整个客户对象。

基于这些观察,很明显,从领域建模的角度看,查询和命令几乎总是不同的,因此应该用不同的类型来建模。查询类型与命令类型的这种分离,自然而然地导向一种把它们隔离到不同模块中的设计,使它们真正解耦、可以独立演化。一个模块负责查询(称为读模型,read model),另一个负责命令(写模型,write model),这就是命令查询职责隔离(Command-Query Responsibility Segregation,CQRS)。

例如,如果我们想为客户分别建立读模型和写模型,可以定义一个 WriteModel.Customer 类型和一个 ReadModel.Customer 类型,于是数据访问函数会是这样:

```fsharp
type SaveCustomer = WriteModel.Customer -> DbResult<Unit>
type LoadCustomer = CustomerId -> DbResult<ReadModel.Customer>
```

### CQRS 与数据库隔离

CQRS 原则也可以应用到数据库上。在这种情况下,你会有两个不同的数据存储:一个为写入优化(无索引、支持事务等),另一个为查询优化(反规范化、大量索引等)。

当然这是"逻辑"视图——你并不需要有物理上分开的两个数据库。例如在关系数据库中,"写"模型可以就是一些表,而"读"模型可以是在这些表上预定义的视图(view)。

如果你的数据存储确实是物理分开的,就必须实现一个特殊的流程,把数据从"写存储"复制到"读存储"。这是额外的工作,所以你必须权衡分开数据存储带来的设计收益是否值得。更重要的是,读侧的数据相比写侧的数据可能是过时的,这意味着读存储是"最终一致"(eventually consistent)而非立即一致的。这可能是也可能不是问题,取决于你的领域(另见关于一致性的讨论)。

不过,一旦你决定把读和写隔离开,你就可以灵活地使用多个不同的读存储,每个都针对某个特定领域优化。特别地,你可以有一个包含来自多个限界上下文的聚合数据的读存储,这对做报表或分析非常有用。

### 事件溯源

CQRS 常与事件溯源(event sourcing)联系在一起。[34]

在事件溯源方法中,当前状态并不作为单个对象来持久化。相反,每当状态发生变更,就持久化一个代表该变更的事件(比如 InvoicePaid)。这样,旧状态与新状态之间的每次差异都被记录下来,有点像版本控制系统。为了在工作流开始时恢复当前状态,要把之前所有的事件重放一遍。这种方法有很多优点,尤其是它契合许多领域里"一切都要审计"的模型。正如人们所说:"会计不用橡皮擦。"事件溯源是一个庞大的话题,我们在这里没有足够的篇幅深入讲解。

## 限界上下文必须拥有自己的数据存储

关于持久化的另一条关键准则是:每个限界上下文在数据存储方面必须与其他上下文隔离。这意味着:

- 限界上下文必须拥有自己的数据存储及相应的模式(schema),并且可以随时更改它们,而无须与其他限界上下文协调;
- 其他任何系统都不能直接访问该限界上下文拥有的数据。相反,客户端要么使用该限界上下文的公共 API,要么使用某种数据存储的副本。

这里的目标一如既往,是确保限界上下文保持解耦、能够独立演化。如果系统 A 访问了系统 B 的数据存储,那么即使两个代码库完全独立,这两个系统实际上仍然因为共享数据而耦合在一起。

"隔离"的实现方式可以因设计需求和运维团队的要求而异。在一个极端,每个限界上下文都可以拥有一个物理上独立的数据库或数据存储,与所有其他上下文完全分开部署。在另一个极端,所有上下文的数据都可以存放在一个物理数据库中(让部署更容易),但使用某种命名空间机制让每个上下文的数据在逻辑上保持分离。

### 处理来自多个领域的数据

那报表和商业分析系统怎么办?它们需要访问来自多个上下文的数据,但我们刚刚才说过这是个坏主意。

解决方案是把"报表"或"商业智能"(Business Intelligence)当作一个独立的领域,把其他限界上下文拥有的数据复制到一个专为报表设计的独立系统中。这种做法虽然更费工夫,却能让源系统和报表系统独立演化,并让各自都针对自己的关注点做优化。当然,这种方法并不新鲜——OLTP[35] 与 OLAP[36] 系统之间的区分已经存在几十年了。

把数据从其他限界上下文弄到商业智能上下文有多种办法。"纯"的办法是让它订阅其他系统发出的事件。例如,每当创建一个订单,就会触发一个事件,商业智能(或称 BI)上下文可以监听该事件,并在自己的数据存储中插入一条相应记录。这种做法的优点是,商业智能上下文只是又一个领域,在设计上不需要任何特殊对待。

另一种办法是使用传统的 ETL 过程[37],把数据从源系统复制到 BI 系统。它的优点是初期实现起来更容易,但可能带来额外的维护成本,因为当源系统更改其数据库模式时,ETL 过程很可能也要跟着改。

注意,在商业智能领域内部,几乎不需要正式的领域模型。更重要的可能是开发一个多维数据库(俗称"立方体"/cube),高效地支持即席查询(ad hoc query)和多种不同的访问路径。

我们可以用类似的办法处理运维所需的数据。我们把"运维智能"(Operational Intelligence)当作一个独立的领域,然后把日志、指标以及其他各类数据发送给它,供分析和报表使用。

## 使用文档数据库

我们已经讨论了持久化的一些通用原则。现在将完全切换话题,深入一些实现示例,从所谓的"文档数据库"开始——它被设计用来以 JSON 或 XML 格式存储半结构化数据。

持久化到文档数据库很容易。我们使用上一章(第 11 章"序列化")讨论过的技术,把领域对象转换成 DTO,再转换成 JSON 字符串(或 XML 字符串等),然后通过存储系统的 API 进行存储和加载。

例如,如果我们使用 Azure blob 存储来保存 PersonDto 对象,可以这样搭建存储:

```fsharp
open Microsoft.WindowsAzure
open Microsoft.WindowsAzure.Storage
open Microsoft.WindowsAzure.Storage.Blob

let connString = "... Azure 连接字符串 ..."
let storageAccount = CloudStorageAccount.Parse(connString)
let blobClient = storageAccount.CreateCloudBlobClient()

let container = blobClient.GetContainerReference("Person");
container.CreateIfNotExists()
```

然后只需几行代码就可以把一个 DTO 保存到 blob:

```fsharp
type PersonDto = {
  PersonId : int
  ...
  }

let savePersonDtoToBlob personDto =
  let blobId = sprintf "Person%i" personDto.PersonId
  let blob = container.GetBlockBlobReference(blobId)
  let json = Json.serialize personDto
  blob.UploadText(json)
```

就是这么简单。同样地,我们可以使用上一章的反序列化技术编写从存储中加载数据的代码。

## 使用关系数据库

关系数据库的模型与大多数代码的模型差异很大,传统上这造成了很多痛苦——即所谓的对象与数据库之间的"阻抗失配"(impedance mismatch)。

用函数式编程原则开发的数据模型往往与关系数据库更兼容,主要因为函数式模型不把数据和行为混在一起,所以记录的保存和获取更直接。尽管如此,我们仍需要处理一些问题。让我们看看关系数据库模型与函数式模型如何对比。

首先是个好消息:关系数据库中的表与函数式模型中的记录集合对应得很好。而且数据库中面向集合的操作(SELECT、WHERE)与函数式语言中面向列表的操作(map、filter)是相似的。

所以我们的策略是,使用上一章的序列化技术来设计可以直接映射到表的记录类型。例如,假设我们有这样一个领域类型:

```fsharp
type CustomerId = CustomerId of int
type String50 = String50 of string
type Birthdate = Birthdate of DateTime

type Customer = {
  CustomerId : CustomerId
  Name : String50
  Birthdate : Birthdate option
  }
```

那么对应的表设计就很直接:

```sql
CREATE TABLE Customer (
  CustomerId int NOT NULL,
  Name NVARCHAR(50) NOT NULL,
  Birthdate DATETIME NULL,
  CONSTRAINT PK_Customer PRIMARY KEY (CustomerId)
)
```

坏消息是,关系数据库只存储字符串或整数这样的基元类型(primitive),这意味着我们不得不把自己精心设计的领域类型(如 ProductCode 或 OrderId)拆包(unwrap)。

更糟的是,关系表不能很好地映射到选择类型。这是我们需要更详细探讨的问题。

### 把选择类型映射到表

我们应该如何在关系数据库中为选择类型建模?如果我们把选择类型看作一个只有一层的继承层次结构,就可以借用一些把对象层次结构映射到关系模型的方法。[38]

对映射选择类型最有用的两种方法是:

- 所有分支(case)共存于同一张表;
- 每个分支各有一张表。

例如,假设我们有一个像下面这样的 Contact 类型,它包含一个选择类型,我们想把它存进数据库:

```fsharp
type Contact = {
  ContactId : ContactId
  Info : ContactInfo
  }

and ContactInfo =
  | Email of EmailAddress
  | Phone of PhoneNumber

and EmailAddress = EmailAddress of string
and PhoneNumber = PhoneNumber of string
and ContactId = ContactId of int
```

第一种方法("所有分支放在一张表")类似于前面讨论过的做法。我们只用一张表来存储所有分支的全部数据,这反过来意味着:(a)我们需要一个或多个标志位来指示当前使用的是哪个分支;(b)表中必须有一些只为部分分支所用的可为 NULL 的列。

```sql
CREATE TABLE ContactInfo (
  -- 共享数据
  ContactId int NOT NULL,
  -- 分支标志
  IsEmail bit NOT NULL,
  IsPhone bit NOT NULL,
  -- "Email" 分支的数据
  EmailAddress NVARCHAR(100), -- 可为 NULL
  -- "Phone" 分支的数据
  PhoneNumber NVARCHAR(25), -- 可为 NULL
  -- 主键约束
  CONSTRAINT PK_ContactInfo PRIMARY KEY (ContactId)
)
```

我们为每个分支使用了一个 bit 字段标志,而不是单个 Tag VARCHAR 字段,因为这样稍微更紧凑、也更容易建索引。

第二种方法(每个分支各有一张表)意味着,除了主表之外,我们还创建两张子表,每个分支一张。所有表共享同一个主键。主表存储 ID 和一些指示当前活跃分支的标志,而子表存储各分支的数据。作为复杂性增加的交换,我们在数据库中获得了更好的约束(比如子表中可以有 NOT NULL 列)。

```sql
-- 主表
CREATE TABLE ContactInfo (
  -- 共享数据
  ContactId int NOT NULL,
  -- 分支标志
  IsEmail bit NOT NULL,
  IsPhone bit NOT NULL,
  CONSTRAINT PK_ContactInfo PRIMARY KEY (ContactId)
)

-- "Email" 分支的子表
CREATE TABLE ContactEmail (
  ContactId int NOT NULL,
  -- 分支专属数据
  EmailAddress NVARCHAR(100) NOT NULL,
  CONSTRAINT PK_ContactEmail PRIMARY KEY (ContactId)
)

-- "Phone" 分支的子表
CREATE TABLE ContactPhone (
  ContactId int NOT NULL,
  -- 分支专属数据
  PhoneNumber NVARCHAR(25) NOT NULL,
  CONSTRAINT PK_ContactPhone PRIMARY KEY (ContactId)
)
```

当各分支关联的数据非常庞大且几乎无共同之处时,这种"多表"方法可能更好;但在其他情况下,我们默认使用第一种"单表"方法。

### 把嵌套类型映射到表

如果某个类型还包含其他类型,该怎么办?应该如何处理?一般性的建议是这样的:

- 如果内部类型是一个拥有自身标识的 DDD 实体(Entity),它应该存储在单独的表中;
- 如果内部类型是一个没有自身标识的 DDD 值对象(Value Object),它应该与父数据"内联"(inline)存储。

例如,我们的 Order 类型包含一个 OrderLine 值的列表。OrderLine 类型是一个实体,因此它应该存储在自己的表中,并带有一个指向其父对象的指针(外键,foreign key)。

```sql
CREATE TABLE [Order] (
  OrderId int NOT NULL,
  -- 以及其他列
)

CREATE TABLE OrderLine (
  OrderLineId int NOT NULL,
  OrderId int NOT NULL,
  -- 以及其他列
)
```

另一方面,Order 类型包含两个 Address 值,它们是值对象。因此,对应的 Order 表应当直接包含 Address 的所有列。

```sql
CREATE TABLE [Order] (
  OrderId int NOT NULL,

  -- 内联收货地址值对象
  ShippingAddress1 varchar(50)
  ShippingAddress2 varchar(50)
  ShippingAddressCity varchar(50)
  -- 以此类推

  -- 内联账单地址值对象
  BillingAddress1 varchar(50)
  BillingAddress2 varchar(50)
  BillingAddressCity varchar(50)
  -- 以此类推

  -- 其他列
)
```

### 从关系数据库读取

在 F# 中,我们倾向于不使用对象关系映射器(ORM),而是直接使用原生 SQL 命令。最方便的方式是使用 F# 的 SQL 类型提供器(type provider)。这样的类型提供器有好几种——本例中我们将使用 FSharp.Data.SqlClient 类型提供器。[39]

使用类型提供器而非典型的运行时库,特别之处在于:SQL 类型提供器会在编译时创建与 SQL 查询或 SQL 命令相匹配的类型。如果 SQL 查询有误,你会得到编译时错误,而不是运行时错误。而如果 SQL 是正确的,它会生成一个与该 SQL 代码的输出完全匹配的 F# 记录类型。

假设我们想用 CustomerId 读取单个 Customer。下面是用类型提供器实现的做法。

首先,我们定义一个编译时使用的连接字符串,它通常指向一个本地数据库:

```fsharp
open FSharp.Data

[<Literal>]
let CompileTimeConnectionString =
  @"Data Source=(localdb)\MsSqlLocalDb; Initial Catalog=DomainModelingExample;"
```

然后我们把查询定义为一个名为 ReadOneCustomer 的类型,像这样:

```fsharp
type ReadOneCustomer = SqlCommandProvider<"""
  SELECT CustomerId, Name, Birthdate
  FROM Customer
  WHERE CustomerId = @customerId
  """, CompileTimeConnectionString>
```

在编译时,类型提供器会在本地数据库上运行这个查询并生成一个类型来表示它。这类似于 SqlMetal[40] 或 EdmGenerator[41] 工具,区别在于不会生成单独的文件——类型是就地创建的。之后我们使用这个类型时,会提供一个与编译时不同的"生产"连接。

接下来,正如我们在上一章序列化示例中所做的那样,我们应该创建一个 toDomain 函数。这个函数先验证数据库中的各字段,然后用 result 表达式把它们组装起来。

也就是说,我们会把数据库当作一个不可信的数据源,像对待其他任何数据源一样加以验证,所以 toDomain 函数需要返回 Result<Customer,_> 而不是普通的 Customer。代码如下:

```fsharp
let toDomain (dbRecord:ReadOneCustomer.Record) : Result<Customer,_> =
  result {
    let! customerId =
      dbRecord.CustomerId
      |> CustomerId.create
    let! name =
      dbRecord.Name
      |> String50.create "Name"
    let! birthdate =
      dbRecord.Birthdate
      |> Result.bindOption Birthdate.create
    let customer = {
      CustomerId = customerId
      Name = name
      Birthdate = birthdate
      }
    return customer
    }
```

这样的代码我们在第 11 章"序列化"中已经见过了。不过这里有一个新东西。数据库中的 Birthdate 列可为 NULL,所以类型提供器把 dbRecord.Birthdate 字段做成了 Option 类型。但 Birthdate.create 函数不接受 option。为了解决这个问题,我们创建一个名叫 bindOption 的小辅助函数,让一个"道岔函数"(switch function)能作用于 option:

```fsharp
let bindOption f xOpt =
  match xOpt with
  | Some x -> f x |> Result.map Some
  | None -> Ok None
```

像这样编写自定义的 toDomain 函数并处理所有这些 Result 有点繁琐,但一旦写好,我们就能确信永远不会有未处理的错误。

另一方面,如果我们非常确信数据库中永远不会包含坏数据,并且愿意在出现坏数据时直接 panic,那么可以改为对非法数据抛出异常。在这种情况下,我们可以把代码改成使用 panicOnError 辅助函数(它把错误的 Result 转换成异常),这又意味着 toDomain 函数的输出是不再包裹在 Result 里的普通 Customer。代码如下:

```fsharp
let toDomain (dbRecord:ReadOneCustomer.Record) : Customer =

  let customerId =
    dbRecord.CustomerId
    |> CustomerId.create
    |> panicOnError "CustomerId"

  let name =
    dbRecord.Name
    |> String50.create "Name"
    |> panicOnError "Name"

  let birthdate =
    dbRecord.Birthdate
    |> Result.bindOption Birthdate.create
    |> panicOnError "Birthdate"

  // 返回客户
  {CustomerId = customerId; Name = name; Birthdate = birthdate}
```

其中 panicOnError 辅助函数大概长这样:

```fsharp
exception DatabaseError of string

let panicOnError columnName result =
  match result with
  | Ok x -> x
  | Error err ->
    let msg = sprintf "%s: %A" columnName err
    raise (DatabaseError msg)
```

无论用哪种方式,一旦有了 toDomain 函数,我们就可以编写读取数据库并把结果作为领域类型返回的代码了。例如,下面这个 readOneCustomer 函数会执行 ReadOneCustomer 查询,然后把它转换成领域类型。

```fsharp
type DbReadError =
  | InvalidRecord of string
  | MissingRecord of string

let readOneCustomer (productionConnection:SqlConnection) (CustomerId customerId) =
  // 通过实例化我们之前定义的类型来创建命令
  use cmd = new ReadOneCustomer(productionConnection)

  // 执行命令
  let records = cmd.Execute(customerId = customerId) |> Seq.toList

  // 处理可能出现的各种情况
  match records with
  // 一条都没找到
  | [] ->
    let msg = sprintf "Not found. CustomerId=%A" customerId
    Error (MissingRecord msg)  // 返回一个 Result

  // 恰好找到一条
  | [dbCustomer] ->
    dbCustomer
    |> toDomain
    |> Result.mapError InvalidRecord

  // 找到多条?
  | _ ->
    let msg = sprintf "Multiple records found for CustomerId=%A" customerId
    raise (DatabaseError msg)
```

首先注意,我们现在显式地传入一个 SqlConnection 作为"生产"连接。

其次,我们要处理三种可能的情况:没找到记录、恰好找到一条、找到多条。我们需要决定哪些情况应当作为领域的一部分来处理,哪些情况绝不该发生(可以作为 panic 来处理)。在本例中,我们认定记录缺失是可能的,将作为 Result.Error 处理;而找到多条记录则作为 panic 处理。

处理这些五花八门的情况看起来工作量不小,但好处在于,你是在明确地对各种可能的错误做出决策(而且这一点在代码中有据可查),而不是假定一切正常,然后在后续某处吃到 NullReferenceException。

当然,我们可以遵循"万物皆参数"原则让这段代码更整洁,做一个通用函数,比如 convertSingleDbRecord,把表名、ID、记录和 toDomain 转换器都作为参数传进去:

```fsharp
let convertSingleDbRecord tableName idValue records toDomain =
  match records with
  // 一条都没找到
  | [] ->
    let msg = sprintf "Not found. Table=%s Id=%A" tableName idValue
    Error msg  // 返回一个 Result

  // 恰好找到一条
  | [dbRecord] ->
    dbRecord
    |> toDomain
    |> Ok   // 返回一个 Result

  // 找到多条?
  | _ ->
    let msg = sprintf "Multiple records found. Table=%s Id=%A" tableName idValue
    raise (DatabaseError msg)
```

有了这个通用辅助函数,代码可以缩减到寥寥几行:

```fsharp
let readOneCustomer (productionConnection:SqlConnection) (CustomerId customerId) =
  use cmd = new ReadOneCustomer(productionConnection)
  let tableName = "Customer"

  let records = cmd.Execute(customerId = customerId) |> Seq.toList
  convertSingleDbRecord tableName customerId records toDomain
```

### 从关系数据库读取选择类型

我们可以用同样的方式读取选择类型,只是要更复杂一些。

假设我们使用单表方法存储 ContactInfo 记录,并想用 ContactId 读取单个 ContactInfo。和之前一样,我们先把查询定义为一个类型,像这样:

```fsharp
type ReadOneContact = SqlCommandProvider<"""
  SELECT ContactId,IsEmail,IsPhone,EmailAddress,PhoneNumber
  FROM ContactInfo
  WHERE ContactId = @contactId
  """, CompileTimeConnectionString>
```

接下来,我们创建一个 toDomain 函数。这个函数先检查数据库中的标志(IsEmail),判断要创建 ContactInfo 的哪个分支,然后用子 result 表达式为每个分支组装数据(可组合性万岁!)

```fsharp
let toDomain (dbRecord:ReadOneContact.Record) : Result<Contact,_> =
  result {
    let! contactId =
      dbRecord.ContactId
      |> ContactId.create

    let! contactInfo =
      if dbRecord.IsEmail then
        result {
          // 获取不应为 NULL 的基元字符串
          let! emailAddressString =
            dbRecord.EmailAddress
            |> Result.ofOption "Email expected to be non null"
          // 创建 EmailAddress 简单类型
          let! emailAddress =
            emailAddressString |> EmailAddress.create
          // 提升为 ContactInfo 的 Email 分支
          return (Email emailAddress)
          }
      else
        result {
          // 获取不应为 NULL 的基元字符串
          let! phoneNumberString =
            dbRecord.PhoneNumber
            |> Result.ofOption "PhoneNumber expected to be non null"
          // 创建 PhoneNumber 简单类型
          let! phoneNumber =
            phoneNumberString |> PhoneNumber.create
          // 提升为 ContactInfo 的 PhoneNumber 分支
          return (Phone phoneNumber)
          }

    let contact = {
      ContactId = contactId
      Info = contactInfo
      }
    return contact
    }
```

可以看到,例如在 Email 分支中,数据库里的 EmailAddress 列是可为 NULL 的,所以类型提供器生成的 dbRecord.EmailAddress 是一个 Option 类型。因此我们必须先用 Result.ofOption 把 Option 转换成 Result(以防它缺失),然后创建 EmailAddress 类型,再把它提升为 ContactInfo 的 Email 分支。

这比前面的 Customer 例子还要复杂,但同样地,我们由此获得了极强的信心:绝不会有意外错误。

顺便说一下,如果你想知道 Result.ofOption 函数的代码长什么样,就在这里:

```fsharp
module Result =
  /// 把一个 Option 转换成一个 Result
  let ofOption errorValue opt =
    match opt with
    | Some v -> Ok v
    | None -> Error errorValue
```

和之前一样,一旦有了 toDomain 函数,就可以把它与我们先前创建的 convertSingleDbRecord 辅助函数配合使用。

```fsharp
let readOneContact (productionConnection:SqlConnection) (ContactId contactId) =
  use cmd = new ReadOneContact(productionConnection)
  let tableName = "ContactInfo"

  let records = cmd.Execute(contactId = contactId) |> Seq.toList
  convertSingleDbRecord tableName contactId records toDomain
```

可以看到,创建 toDomain 函数才是苦活。一旦完成,实际的数据库访问代码就相对简单了。

你可能在想:这不是太费劲了吗?难道不能用 Entity Framework 或 NHibernate 之类的东西自动完成所有这些映射?答案是否定的——如果你还想保证领域的完整性的话。前面提到的那些 ORM 无法验证电子邮件地址和订单数量,处理不了嵌套的选择类型,等等。是的,编写这类数据库代码很乏味,但这个过程是机械且直接的,而且它并不是编写应用程序中最难的部分!

### 写入关系数据库

写入关系数据库遵循与读取相同的模式:我们把领域对象转换成 DTO,然后执行插入或更新命令。

做数据库插入最简单的方式,是让 SQL 类型提供器生成一个表示表结构的可变类型,然后我们只需设置该类型的各字段。

下面是个演示。首先,我们用类型提供器为所有表建立类型:

```fsharp
type Db = SqlProgrammabilityProvider<CompileTimeConnectionString>
```

现在我们可以定义一个 writeContact 函数,它接收一个 Contact,并设置数据库中对应 ContactInfo 的所有字段:

```fsharp
let writeContact (productionConnection:SqlConnection) (contact:Contact) =

  // 从领域对象中提取基元数据
  let contactId = contact.ContactId |> ContactId.value
  let isEmail,isPhone,emailAddressOpt,phoneNumberOpt =
    match contact.Info with
    | Email emailAddress->
      let emailAddressString = emailAddress |> EmailAddress.value
      true,false,Some emailAddressString,None
    | Phone phoneNumber ->
      let phoneNumberString = phoneNumber |> PhoneNumber.value
      false,true,None,Some phoneNumberString

  // 创建新行
  let contactInfoTable = new Db.dbo.Tables.ContactInfo()
  let newRow = contactInfoTable.NewRow()
  newRow.ContactId <- contactId
  newRow.IsEmail <- isEmail
  newRow.IsPhone <- isPhone
  // 用可选类型映射到数据库中的 NULL
  newRow.EmailAddress <- emailAddressOpt
  newRow.PhoneNumber <- phoneNumberOpt

  // 添加到表
  contactInfoTable.Rows.Add newRow

  // 把变更推送到数据库
  let recordsAffected = contactInfoTable.Update(productionConnection)
  recordsAffected
```

另一种控制力更强的做法是使用手写的 SQL 语句。例如,要插入一个新的 Contact,我们先定义一个表示 SQL INSERT 语句的类型:

```fsharp
type InsertContact = SqlCommandProvider<"""
  INSERT INTO ContactInfo
  VALUES (@ContactId,@IsEmail,@IsPhone,@EmailAddress,@PhoneNumber)
  """, CompileTimeConnectionString>
```

现在我们可以定义一个 writeContact 函数,它接收一个 Contact,从选择类型中提取出基元值,然后执行该命令。

```fsharp
let writeContact (productionConnection:SqlConnection) (contact:Contact) =

  // 从领域对象中提取基元数据
  let contactId = contact.ContactId |> ContactId.value
  let isEmail,isPhone,emailAddress,phoneNumber =
    match contact.Info with
    | Email emailAddress->
      let emailAddressString = emailAddress |> EmailAddress.value
      true,false,emailAddressString,null
    | Phone phoneNumber ->
      let phoneNumberString = phoneNumber |> PhoneNumber.value
      false,true,null,phoneNumberString

  // 写入数据库
  use cmd = new InsertContact(productionConnection)
  cmd.Execute(contactId,isEmail,isPhone,emailAddress,phoneNumber)
```

## 事务

到目前为止的所有代码都采用"一个聚合 = 一个事务(transaction)"的形式。但在很多情况下,我们有许多东西需要原子地一起保存——要么全部成功,要么全部不做。

一些数据存储在其 API 中支持事务。对服务的多次调用可以加入到同一个事务中,像这样:

```fsharp
let connection = new SqlConnection()
let transaction = connection.BeginTransaction()

// 在同一个事务中
// 对数据库做两次独立的调用
markAsFullyPaid connection invoiceId
markPaymentCompleted connection paymentId

// 完成
transaction.Commit()
```

一些数据存储只在所有操作都在单个连接中完成时才支持事务。在实践中,这意味着你必须把多个操作合并到一次调用中,像这样:

```fsharp
let connection = new SqlConnection()
// 对服务做一次调用
markAsFullyPaidAndPaymentCompleted connection paymentId invoiceId
```

但有时,你面对的是多个不同的服务,根本没办法做跨服务的事务。

Gregor Hohpe 的文章《Starbucks Does Not Use Two-Phase Commit》指出,企业通常不需要跨系统的事务,因为其开销和协调成本太过沉重和缓慢。相反,我们假设大多数时候事情都会顺利,然后用对账(reconciliation)流程来检测不一致,并用补偿事务(compensating transaction)来纠正错误。

例如,下面简单演示了一个用来回滚数据库更新的补偿事务:

```fsharp
// 做第一次调用
markAsFullyPaid connection invoiceId
// 做第二次调用
let result = markPaymentCompleted connection paymentId

// 若第二次调用失败,则做补偿事务
match result with
| Error err ->
  // 为错误做补偿
  unmarkAsFullyPaid connection invoiceId
| Ok _ -> ...
```

## 结语

在本章中,我们首先考察了持久化的一些高层原则:把查询与命令分离、把 I/O 保持在边缘,以及确保限界上下文拥有自己的数据存储。然后,我们深入到与关系数据库打交道的底层机制中。

这也把我们带到了本书第三部分的结尾。我们现在拥有了设计和实现一个完整限界上下文所需的全部工具:领域内部的纯类型和纯函数(第 9 章"实现:组合管道")、错误处理(第 10 章"实现:处理错误")、边缘处的序列化(第 11 章"序列化"),以及本章讲的用于存储状态的数据库。

但我们还没有完全结束。正如那句军事名言所说:"任何计划都敌不过与敌人的首次接触。"那么,当我们学到新东西、需要更改设计时会发生什么?这将是下一章也就是最后一章的主题。
