# 第 6 章 领域中的完整性与一致性

*Chapter 6: Integrity and Consistency in the Domain*

在上一章中，我们学习了使用 F# 类型系统进行领域建模的基础知识。我们构建了一组丰富的类型，它们既表示了领域，又是可编译的，还能用来指导实现。

既然我们已经花了这么大的功夫对领域进行恰当的建模，就应该再采取一些预防措施，确保该领域中的任何数据都是有效且一致的。目标是创建一个始终包含可信数据的限界上下文（bounded context），以区别于不可信的外部世界。如果我们能确保所有数据值始终有效，实现就能保持整洁，我们也能避免编写防御式代码（defensive coding）。

在本章中，我们将讨论可信领域建模的两个方面：完整性（integrity）与一致性（consistency）。

这里的完整性（或称有效性）是指一段数据遵循正确的业务规则。例如：

- 我们说过 UnitQuantity 介于 1 到 1000 之间。我们是必须在代码中反复检查这一点，还是可以始终信赖它为真？
- 一张订单必须始终至少有一条订单行（order line）。
- 订单在送往发货部门之前，必须已有经过验证的收货地址。

这里的一致性是指领域模型的不同部分对事实的认知保持一致。下面是一些例子：

- 订单的账单总金额应该是各订单行金额之和。如果总额对不上，数据就不一致。
- 下单时必须创建相应的发票（invoice）。如果订单存在而发票不存在，数据就不一致。
- 如果订单使用了折扣券码（discount voucher code），该券码必须被标记为已使用，以免再次被使用。如果订单引用了该券码，而券码没有被标记为已使用，数据就不一致。

我们如何确保这种数据完整性与一致性？这些正是本章要探讨的问题。一如既往，我们能在类型系统中承载的信息越多，所需的文档就越少，代码被正确实现的可能性也就越大。

## 简单值的完整性

在前面关于简单值建模的讨论中，我们看到它们不应该用 string 或 int 来表示，而应该用面向领域的类型，例如 WidgetCode 或 UnitQuantity。

但我们不应止步于此，因为在真实世界的领域中，几乎不存在无界的整数或字符串。这些值几乎总会以某种方式受到约束（constraint）：

- OrderQuantity 也许可以用有符号整数表示，但业务几乎不可能希望它是负数，或者是四十亿。
- CustomerName 可以用字符串表示，但这并不意味着它应该包含制表符或换行符。

在我们的领域中，我们已经见过一些这样的受限类型。WidgetCode 字符串必须以特定字母开头，而 UnitQuantity 必须介于 1 到 1000 之间。下面是我们迄今为止的定义方式，约束以注释标明：

```fsharp
type WidgetCode = WidgetCode of string   // 以 "W" 开头，后接 4 位数字
type UnitQuantity = UnitQuantity of int  // 介于 1 到 1000 之间
type KilogramQuantity = KilogramQuantity of decimal // 介于 0.05 到 100.00 之间
```

我们并不想让这些类型的使用者去阅读注释，而是希望确保：只有满足约束的值，才能被创建为这些类型的值。此后，由于数据是不可变的，其内部值再也不需要被检查。你可以放心地在任何地方使用 WidgetCode 或 UnitQuantity，完全不需要任何形式的防御式编码。

听起来很棒。那么，我们如何确保约束得到强制执行？

答案与在任何编程语言中的做法一样——把构造函数（constructor）设为私有，再另用一个函数来创建有效值、拒绝无效值并返回错误。在函数式编程（FP）社区中，这种方式有时被称为「智能构造函数」（smart constructor）方法。下面是把这一方法应用于 UnitQuantity 的例子：

```fsharp
type UnitQuantity = private UnitQuantity of int
//                  ^ 私有构造函数
```

现在，由于构造函数是私有的，无法从包含该类型的模块外部创建 UnitQuantity 值。不过，如果我们在包含上述类型定义的同一模块中编写代码，就可以访问该构造函数。

我们可以利用这一点来定义一些帮助我们操作该类型的函数。首先创建一个与类型完全同名的子模块（UnitQuantity），然后在其中定义一个 create 函数，它接受一个 int 并返回 Result 类型（如「错误建模」（Modeling Errors）一节所述），用来表示成功或失败。这两种可能性在它的函数签名中一目了然：int -> Result<UnitQuantity,string>。

```fsharp
// 定义一个与类型同名的模块
module UnitQuantity =

  /// 为 UnitQuantity 定义一个「智能构造函数」
  /// int -> Result<UnitQuantity,string>
  let create qty =
    if qty < 1 then
      // 失败
      Error "UnitQuantity can not be negative"
    else if qty > 1000 then
      // 失败
      Error "UnitQuantity can not be more than 1000"
    else
      // 成功——构造返回值
      Ok (UnitQuantity qty)
```

**与旧版本 F# 的兼容性（Compatibility with Older Versions of F#）**

与非泛型类型同名的模块在 F# v4.1（VS2017）之前的版本中会引发错误，因此你需要修改模块定义，为其加上 CompilationRepresentation 特性（attribute），像这样：

```fsharp
type UnitQuantity = ...

[<CompilationRepresentation(CompilationRepresentationFlags.ModuleSuffix)>]
module UnitQuantity =
  ...
```

私有构造函数的一个缺点是，你不能再直接用它来做模式匹配（pattern matching）并提取被包装的数据。一种解决办法是在 UnitQuantity 模块中再定义一个 value 函数，专门用来提取内部值：

```fsharp
/// 返回被包装的值
let value (UnitQuantity qty) = qty
```

来看看这一切在实践中如何运作。首先，如果我们尝试直接创建 UnitQuantity，会得到一个编译器错误：

```fsharp
let unitQty = UnitQuantity 1
//            ^ 类型 'UnitQuantity' 的联合分支
//              不可访问
```

但如果我们改用 UnitQuantity.create 函数，就没问题了：我们会得到一个 Result，随后可以对它进行模式匹配：

```fsharp
let unitQtyResult = UnitQuantity.create 1

match unitQtyResult with
| Error msg ->
  printfn "Failure, Message is %s" msg
| Ok uQty ->
  printfn "Success. Value is %A" uQty
  let innerValue = UnitQuantity.value uQty
  printfn "innerValue is %i" innerValue
```

如果你有很多这样的受限类型，可以用一个辅助模块来收纳构造函数的公共代码，以减少重复。限于篇幅，这里不展开，但本书示例代码的 Domain.SimpleTypes.fs 文件中有一个例子。

最后值得一提的是，private 并不是在 F# 中隐藏构造函数的唯一方式，还有其他技巧，比如使用签名文件（signature file），但我们不在此讨论。

## 度量单位

对于数值，还有一种既能记录需求又能确保类型安全的方法：使用度量单位（unit of measure）。采用度量单位后，数值会用自定义的「度量（measure）」来标注。例如，我们可以像这样为 kg（千克）和 m（米）定义度量单位：

```fsharp
[<Measure>]
type kg

[<Measure>]
type m
```

然后像这样用这些度量单位来标注一些值：

```fsharp
let fiveKilos = 5.0<kg>
let fiveMeters = 5.0<m>
```

你不需要为所有 SI 单位都定义 measure 类型，它们已经包含在 Microsoft.FSharp.Data.UnitSystems.SI 命名空间中。

一旦定义完毕，编译器就会强制检查度量单位之间的兼容性，不匹配就会报错：

```fsharp
// 编译错误
fiveKilos = fiveMeters
//          ^ 期望 float<kg>，但给定的是 float<m>

let listOfWeights = [
  fiveKilos
  fiveMeters  // <-- 编译错误
  //             度量单位 'kg' 与度量单位 'm' 不匹配
  ]
```

在我们的领域中，我们可以用度量单位来确保 KilogramQuantity 真的是千克，这样你就不会不小心用磅为单位的值来初始化它。我们可以把这一点编码进类型：

```fsharp
type KilogramQuantity = KilogramQuantity of decimal<kg>
```

这样一来我们有了两重检查：<kg> 确保数字的单位正确，而 KilogramQuantity 强制执行最大值与最小值上的约束。对我们这个特定领域来说，这或许有点设计过度，但在其他情况下可能很有用。

度量单位并不只限于物理单位。你可以用它来标明超时的正确单位（避免混淆秒和毫秒）、空间维度（避免混淆 x 轴和 y 轴），或者货币，等等。

使用度量单位不会带来任何性能损失。它们只被 F# 编译器使用，在运行时没有任何开销。

## 用类型系统强制不变式

不变式（invariant）是一个无论发生什么都会保持为真的条件。例如，本章开头我们说过，UnitQuantity 必须始终介于 1 到 1000 之间，这就是一个不变式的例子。

我们还说过，一张订单必须始终至少有一条订单行。与 UnitQuantity 的情况不同，这个不变式可以直接在类型系统中表达。要确保列表不为空，我们只需定义一个 NonEmptyList（非空列表）类型。它不是 F# 内置的，但自己定义很容易：

```fsharp
type NonEmptyList<'a> = {
  First: 'a
  Rest: 'a list
  }
```

这个定义本身就要求必须至少有一个元素，因此 NonEmptyList 保证永远不会为空。

当然，你还需要一些辅助函数，比如 add、remove 等。你可以自己定义，也可以使用提供该类型的第三方库，例如 FSharpx.Collections。[24]

现在可以把 Order 类型改写为使用这个类型，而不是普通的列表类型：

```fsharp
type Order = {
  ...
  OrderLines : NonEmptyList<OrderLine>
  ...
  }
```

经过这一改动，「订单中始终至少有一条订单行」这一约束现在会被自动强制执行。代码成了自文档化的代码，而且我们刚刚彻底消除了为这条需求编写单元测试的必要。

## 在类型系统中承载业务规则

再来看另一个建模挑战：我们能只用类型系统来记录业务规则吗？也就是说，我们希望用 F# 类型系统来表达什么是有效、什么是无效，让编译器替我们检查，而不是依靠运行时检查或代码注释来维护这些规则。

这里有一个真实世界的例子。假设我们的公司 Widgets Inc 会存储客户的电子邮件地址。但同时假设，并非所有电子邮件地址都应被同等对待。有些电子邮件地址已经过验证（verified）——即客户收到了验证邮件并点击了验证链接——而另一些电子邮件地址没有经过验证，我们无法确定它们是否有效。此外，假设有一些业务规则正基于这种区别，例如：

- 验证邮件只应发送给未验证的电子邮件地址（避免向已验证的客户滥发邮件）。
- 密码重置邮件只应发送给已验证的电子邮件地址（以防出现安全漏洞）。

那么，我们该如何在设计中表示这两种不同的情况？标准做法是使用一个标志（flag）来指示是否发生过验证，像这样：

```fsharp
type CustomerEmail = {
  EmailAddress : EmailAddress
  IsVerified : bool
  }
```

但这种做法存在一些严重的问题。首先，IsVerified 标志应该在何时、为何被设置或取消，并不清楚。例如，如果客户的电子邮件地址变了，该标志应该被重置为 false（因为新地址尚未验证）。然而，设计中没有任何东西把这条规则显式地表达出来。开发者很容易在电子邮件地址变更时忘记做这件事，更糟的是，他们可能压根不知道这条规则（因为它埋没在某处的注释里）。

还存在安全漏洞的可能。开发者可能写出意外把该标志设为 true 的代码——哪怕针对的是未验证的地址——这将导致密码重置邮件被发送到未验证的地址。

那么，更好的建模方式是什么？

答案一如既往：关注领域。当领域专家谈论「已验证」和「未验证」的邮件时，你应当把它们建模为两种不同的东西。在这里，当领域专家说「客户的邮件要么已验证、要么未验证」时，我们应当把它建模为两种类型之间的选择（choice），像这样：

```fsharp
type CustomerEmail =
  | Unverified of EmailAddress
  | Verified of EmailAddress
```

但这仍然无法防止我们不小心传入一个未验证的 EmailAddress，从而意外创建出 Verified 分支。为了解决这个问题，我们按一贯的做法：创建一个新类型！具体来说，我们要创建一个 VerifiedEmailAddress 类型，它与普通的 EmailAddress 类型不同。现在我们的选择类型变成了这样：

```fsharp
type CustomerEmail =
  | Unverified of EmailAddress
  | Verified of VerifiedEmailAddress // 不同于普通的 EmailAddress
```

精彩之处在于：我们可以给 VerifiedEmailAddress 一个私有构造函数，让普通代码无法创建该类型的值——只有验证服务才能创建它。

这意味着，如果我拿到一个新的电子邮件地址，我必须用 Unverified 分支来构造 CustomerEmail，因为我手头没有 VerifiedEmailAddress。构造 Verified 分支的唯一途径是拥有一个 VerifiedEmailAddress，而获得 VerifiedEmailAddress 的唯一途径是电子邮件验证服务本身。

这是重要设计准则「让非法状态不可表示」（Make illegal states unrepresentable）的一个例子。我们正试图把业务规则承载到类型系统中。如果做得恰当，无效的情形在代码中根本无法存在，我们也就永远不需要为它们编写单元测试。取而代之的是，我们拥有了「编译期」单元测试。

这种做法的另一个重要好处是，它实际上把领域记录得更清楚了。与其用一个简化的 EmailAddress 去兼任两种角色，我们现在有了两个截然不同的类型，各自伴随着不同的规则。而且通常，一旦创建了这些更细粒度的类型，我们立刻就能为它们找到用武之地。

例如，我现在可以明确声明：发送密码重置邮件的工作流必须以 VerifiedEmailAddress 作为输入参数，而不是普通的电子邮件地址。

```fsharp
type SendPasswordResetEmail = VerifiedEmailAddress -> ...
```

有了这个定义，我们就不用担心有人因为没读文档而不小心传入普通的 EmailAddress、破坏业务规则了。

再看另一个例子。假设我们有一条业务规则：我们需要某种方式来联系客户：

「客户必须拥有电子邮件地址或邮政地址。」

该如何表示这条规则？显而易见的做法是创建一个同时具有 Email 和 Address 属性的记录（record），像这样：

```fsharp
type Contact = {
  Name: Name
  Email: EmailContactInfo
  Address: PostalContactInfo
  }
```

但这是个错误的设计，它暗示 Email 和 Address 都是必需的。那我们把它们改成可选的：

```fsharp
type Contact = {
  Name: Name
  Email: EmailContactInfo option
  Address: PostalContactInfo option
  }
```

但这也不对。照现在这样，Email 和 Address 可能同时缺失，那就违反了业务规则。

当然，我们可以添加专门的运行时验证检查来确保这种情形不会发生。但我们能不能做得更好，直接在类型系统中表示它？能！

诀窍在于仔细审视这条规则。它暗示客户处于以下情形之一：

- 只有电子邮件地址
- 只有邮政地址
- 电子邮件地址和邮政地址都有

总共只有三种可能。怎么表示这三种情形？当然是用选择类型（choice type）！

```fsharp
type BothContactMethods = {
  Email: EmailContactInfo
  Address : PostalContactInfo
  }

type ContactInfo =
    | EmailOnly of EmailContactInfo
    | AddrOnly of PostalContactInfo
    | EmailAndAddr of BothContactMethods
```

然后我们就可以在主要的 Contact 类型中使用这个选择类型，像这样：

```fsharp
type Contact = {
  Name: Name
  ContactInfo : ContactInfo
  }
```

同样，我们所做的对开发者有利（不可能意外地丢失全部联系信息——又少写一个测试），对设计本身也有利。这个设计非常清楚地表明只有三种可能的情形，以及这三种情形分别是什么。我们不需要去查文档，看代码本身就够了。

### 在我们的领域中让非法状态不可表示

我们的设计中，有没有可以把这套方法付诸实践的地方？

我能想到设计中的一个方面与电子邮件验证的例子非常相似。在验证流程中，我们记录过存在未验证的邮政地址（如 UnvalidatedAddress）和已验证的邮政地址（ValidatedAddress）。

通过以下做法，我们可以确保永远不会混淆这两种情形，同时确保正确地使用验证函数：

- 创建两个截然不同的类型：UnvalidatedAddress 和 ValidatedAddress
- 给 ValidatedAddress 一个私有构造函数，并确保它只能由地址验证服务创建

```fsharp
type UnvalidatedAddress = ...

type ValidatedAddress = private ...
```

验证服务接受一个 UnvalidatedAddress，返回一个可选的 ValidatedAddress（用 option 来表示验证可能失败）。

```fsharp
type AddressValidationService =
  UnvalidatedAddress -> ValidatedAddress option
```

为了强制执行「订单在送往发货部门之前必须已有经验证的收货地址」这条规则，我们再创建两个不同的类型（UnvalidatedOrder 和 ValidatedOrder），并要求 ValidatedOrder 记录中的收货地址必须是一个 ValidatedAddress。

```fsharp
type UnvalidatedOrder = {
  ...
  ShippingAddress : UnvalidatedAddress
  ...
  }

type ValidatedOrder = {
  ...
  ShippingAddress : ValidatedAddress
  ...
  }
```

现在，我们无需编写任何测试就能保证：ValidatedOrder 中的地址都经过地址验证服务的处理。

## 一致性

到目前为止，本章讨论的都是如何在领域中强制执行数据的完整性，最后我们来看看与之相关的一致性概念。

本章开头我们见过一些一致性需求的例子：

- 订单的账单总金额应该是各订单行金额之和。如果总额对不上，数据就不一致。
- 下单时必须创建相应的发票。如果订单存在而发票不存在，数据就不一致。
- 如果订单使用了折扣券码，该券码必须被标记为已使用，以免再次被使用。如果订单引用了该券码而券码没有被标记为已使用，数据就不一致。

正如这里所描述的，一致性是一个业务术语，而不是技术术语，而且一致性的含义永远取决于具体情境。例如，如果产品价格变了，是否应该立即把所有未发货的订单更新为新价格？如果客户的默认地址变了呢？是否应该立即用新地址更新所有未发货的订单？这些问题没有唯一正确的答案——取决于业务的需要。

不过，一致性会给设计带来沉重的负担，代价可能很高，因此只要有可能，我们就想避免对一致性的需求。在需求收集阶段，产品负责人常常会提出某种既不可取也不切实际的一致性级别。然而在很多情况下，对一致性的需求是可以避免或延后的。

最后，重要的是要认识到：一致性与持久化的原子性是相互关联的。例如，如果订单不会被原子地持久化，那么确保订单内部一致就毫无意义。如果订单的不同部分被分开持久化，而其中一部分保存失败，那么之后任何人加载这张订单，加载到的都是一张内部不一致的订单。

### 单个聚合内部的一致性

在第 5 章「用类型进行领域建模」（Domain Modeling with Types）中，我们介绍了聚合（aggregate）的概念，并指出它既充当一致性边界（consistency boundary），又充当持久化单元。下面来看看它在实践中如何运作。

假设我们要求订单的总金额等于各行金额之和。确保一致性最简单的办法，就是直接从原始数据计算信息，而不是把它存储起来。就这个例子而言，每次需要总额时（在内存中或用 SQL 查询）把订单行加总一遍即可。

如果确实需要持久化这份额外数据（比如在顶层 Order 中额外存储一个 AmountToBill），就必须确保它保持同步。也就是说，一旦某一行被更新，总额也必须随之更新，才能保持数据一致。显然，唯一「知道」如何维护一致性的组件就是顶层的 Order。这正是所有更新都应在订单层面而非订单行层面进行的好理由——订单就是强制实施一致性边界的聚合。下面这段代码演示了它大致如何工作：

```fsharp
/// 传入三个参数：
/// * 顶层订单
/// * 要修改的订单行的 id
/// * 新价格
let changeOrderLinePrice order orderLineId newPrice =

  // 用 orderLineId 在 order.OrderLines 中找到 orderLine
  let orderLine = order.OrderLines |> findOrderLine orderLineId

  // 用新价格构造新版本的 OrderLine
  let newOrderLine = {orderLine with Price = newPrice}

  // 构造新的订单行列表，用新行替换旧行
  let newOrderLines =
    order.OrderLines |> replaceOrderLine orderLineId newOrderLine

  // 计算新的 AmountToBill
  let newAmountToBill = newOrderLines |> List.sumBy (fun line -> line.Price)

  // 用新的订单行构造新版本的订单
  let newOrder = {
      order with
        OrderLines = newOrderLines
        AmountToBill = newAmountToBill
      }

  // 返回新订单
  newOrder
```

聚合也是原子性的单元，因此，举例来说，如果我们要把这张订单保存到关系数据库，就必须确保订单头和所有订单行在同一个事务中一起插入或更新。

### 不同上下文之间的一致性

如果需要在不同的上下文之间进行协调呢？来看看上面清单中的第二个例子：

- 下单时必须创建相应的发票。如果订单存在而发票不存在，数据就不一致。

开票属于计费领域，而不属于接单领域。这是否意味着我们需要把手伸进另一个领域去操纵它的对象？当然不是。我们必须保持每个限界上下文相互隔离、彼此解耦。

那使用计费上下文的公开 API 如何？就像这样：

```fsharp
请求计费上下文创建发票
如果创建成功：
   在接单上下文中创建订单
```

这种做法比看上去要棘手得多，因为你还必须处理任意一边更新失败的情形。确实存在一些跨独立系统正确同步更新的办法（比如两阶段提交，two-phase commit），但实践中很少需要它。Gregor Hohpe 在他的文章《Starbucks Does Not Use Two-Phase Commit》（星巴克并不使用两阶段提交）[25] 中指出，在真实世界里，企业一般并不要求每个流程都整齐划一地推进——即等待所有子系统完成一个阶段之后再进入下一个阶段。相反，协调是通过消息异步完成的。偶尔会出岔子，但处理偶发错误的代价，往往远低于让一切保持同步的代价。

例如，假设我们不要求立即创建发票，而是向计费领域发送一条消息（或事件），然后继续订单处理的其余部分。

那么现在，如果那条消息丢失了、发票没有被创建，会发生什么？

一种选择是什么也不做。这样客户白得了商品，企业只能把成本核销掉。如果错误很少、代价也很小（比如咖啡店的情形），这或许是个完全够用的解决方案。

另一种选择是检测到消息丢失后重发它。这基本上就是对账（reconciliation）流程所做的事：比较两份数据，如果对不上，就修正错误。

第三种选择是创建一个补偿动作（compensating action），用它「撤销」先前的动作或修正错误。在接单场景中，这就相当于取消订单并请客户把商品寄回！更现实地说，补偿动作可以用来做诸如修正订单中的错误、发放退款之类的事情。

在以上三种情形中，都不需要限界上下文之间僵硬的协调。

如果我们确实有一致性需求，就需要实现第二或第三种选择。但这种一致性不会立即生效，而是要经过一段时间后系统才会变得一致——这就是「最终一致性」（eventual consistency）。最终一致性不是「可有可无的一致性」：系统在将来某个时刻达到一致，这一点依然非常重要。

举个例子。假设产品价格发生变化后，我们想更新所有尚未发货订单的价格。如果需要立即一致性（immediate consistency），那么在更新产品记录中的价格时，我们还必须更新所有受影响的订单，而且全部要在同一个事务中完成。这可能需要一些时间。而如果产品价格变化时我们不要求即时一致，则可以改为创建一个 PriceChanged 事件，由它触发一系列 UpdateOrderWithChangedPrice 命令（command）去更新未完成的订单。这些命令会在产品记录中的价格变更之后的一段时间才被处理，也许是几秒之后，也许是几小时之后。最终，订单都会被更新，系统也将归于一致。

### 同一上下文中聚合之间的一致性

那么，同一限界上下文中聚合之间的一致性又该如何确保呢？假设两个聚合需要彼此保持一致。我们应当在同一个事务中一起更新它们，还是分开更新、依靠最终一致性？我们该采取哪种做法？

一如既往，答案是：视情况而定。一般来说，一条实用的准则是「每个事务只更新一个聚合」。如果涉及多个聚合，我们就应当像上面描述的那样使用消息和最终一致性，即使两个聚合处于同一个限界上下文之中。但有时候——尤其是当业务把某个工作流视为单一事务时——把所有受影响的实体都纳入事务也许是值得的。经典例子是两个账户之间的转账：一个账户增加，另一个账户减少。

```fsharp
开始事务
向 accountA 增加 X 金额
从 accountB 扣除 X 金额
提交事务
```

如果这些账户由 Account 聚合表示，那么我们就是在同一个事务中更新两个不同的聚合。这不一定是个问题，但它可能是一条线索，提示你可以通过重构对领域获得更深入的认识。例如在这类场景中，转账往往拥有自己的标识符，这意味着它本身就是一个 DDD 实体（Entity）。既然如此，何不就把它建模成实体？

```fsharp
type MoneyTransfer = {
  Id: MoneyTransferId
  ToAccount : AccountId
  FromAccount : AccountId
  Amount: Money
  }
```

经过这一改动，Account 实体依然存在，但它们不再直接负责增加或扣除金额。取而代之，Account 的当前余额将通过遍历引用它的 MoneyTransfer 记录计算得出。我们不仅重构了设计，还加深了对领域的认识。

这也说明，如果重用聚合并不合理，你不必勉强为之。如果只是为某个用例就需要定义一个新聚合，放手去做。

### 多个聚合作用于同一数据

前面我们强调过，聚合的作用是强制执行完整性约束。那么，当多个聚合作用于同一份数据时，如何确保这些约束得到一致的强制执行呢？例如，我们可能有一个 Account 聚合和一个 MoneyTransfer 聚合，它们都作用于账户余额，也都必须确保余额不会变成负数。

在许多情况下，如果约束用类型来建模，就可以在多个聚合之间共享。例如，「账户余额绝不能低于零」这一需求可以用 NonNegativeMoney 类型来建模。如果这种方式不适用，你可以使用共享的验证函数。这是函数式模型优于面向对象模型的一点：验证函数不依附于任何特定对象，也不依赖全局状态，因此可以轻松地在不同的工作流中重用。

## 收尾

在本章中，我们学习了如何确保领域内部的数据是可信的。

我们看到，对简单类型使用「智能构造函数」，对更复杂的类型使用「让非法状态不可表示」，意味着我们可以用类型系统本身来强制执行多种完整性规则，从而得到更多自文档化的代码，也减少了对单元测试的需求。

我们还讨论了在单个限界上下文内部以及限界上下文之间维护数据一致性的问题，结论是：除非你是在单个聚合内部工作，否则应当为最终一致性而非立即一致性而设计。

在下一章中，我们将把这些付诸实践，对下单（order-placing）工作流进行建模。
