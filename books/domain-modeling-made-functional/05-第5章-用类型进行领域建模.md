# 第 5 章 用类型进行领域建模
*Chapter 5: Domain Modeling with Types*

在第 1 章讨论共享心智模型的重要性时，我们强调过：代码也必须反映这个共享模型，开发者不应该在领域模型和源代码之间做有损转换。理想情况下，我们希望源代码本身也能充当文档，也就是说，领域专家和其他非开发人员应该能够评审代码、检查设计。

这是一个现实可行的目标吗？我们可以像这样直接使用源代码，从而避免依赖 UML 图之类的东西吗？

答案是肯定的。在本章中，你将学习如何用 F# 类型系统来捕获领域模型——它既足够精确、可以作为代码使用，又能以一种领域专家和其他非开发人员读得懂的方式来表达。我们将看到，类型可以取代大部分文档，而这一能力有一个强大的好处：实现永远不会与设计脱节，因为设计就体现在代码本身之中。

## 回顾领域模型

我们先来回顾一下之前创建的领域模型：

```fsharp
context: Order-Taking

// ----------------------
// 简单类型
// ----------------------

// 产品代码
data ProductCode = WidgetCode OR GizmoCode
data WidgetCode = string starting with "W" then 4 digits
data GizmoCode = ...
```

```fsharp
// 订单数量
data OrderQuantity = UnitQuantity OR KilogramQuantity
data UnitQuantity = ...
data KilogramQuantity = ...

// ----------------------
// 订单生命周期
// ----------------------

// ----- 未验证状态 -----
data UnvalidatedOrder =
    UnvalidatedCustomerInfo
    AND UnvalidatedShippingAddress
    AND UnvalidatedBillingAddress
    AND list of UnvalidatedOrderLine

data UnvalidatedOrderLine =
    UnvalidatedProductCode
    AND UnvalidatedOrderQuantity

// ----- 已验证状态 -----
data ValidatedOrder = ...
data ValidatedOrderLine =  ...

// ----- 已定价状态 -----
data PricedOrder = ...
data PricedOrderLine = ...

// ----- 输出事件 -----
data OrderAcknowledgmentSent = ...
data OrderPlaced = ...
data BillableOrderPlaced = ...

// ----------------------
// 工作流
// ----------------------

workflow "Place Order" =
    input: UnvalidatedOrder
    output (on success):
        OrderAcknowledgmentSent
        AND OrderPlaced (to send to shipping)
        AND BillableOrderPlaced (to send to billing)
    output (on error):
        InvalidOrder

// 等等
```

本章的目标就是把这个模型变成代码。

## 识别领域模型中的模式

尽管每个领域模型各不相同，但许多模式会反复出现。

我们来看一个典型领域中的一些模式，并看看模型中的各个组成部分如何与它们对应。

简单值。这是由字符串、整数等原始类型表示的基本构建块。但请注意，它们实际上并不是字符串或整数。领域专家不会用 int 和 string 来思考，而是用 OrderId 和 ProductCode 这样的概念来思考——这些概念是通用语言（ubiquitous language）的一部分。

用 AND 组合的值。这些是由紧密关联的数据构成的组。在纸面世界中，它们通常是文档或文档的子组件：姓名、地址、订单等等。

用 OR 表示的选择。我们的领域中有一些表示“二者择一”的东西：一张订单或一张报价单、一个 UnitQuantity 或一个 KilogramQuantity。

工作流。最后，我们还有带输入和输出的业务过程。

在接下来几节中，我们将看看如何用 F# 类型来表示这些不同的模式。

## 为简单值建模

我们先来看领域的构建块：简单值。

在收集需求的时候我们已经发现，领域专家通常不用 int 和 string 思考，而是用 OrderId 和 ProductCode 这样的领域概念来思考。此外，确保 OrderId 和 ProductCode 不会被弄混也很重要。比方说，不能因为它们都用 int 表示，就认为它们可以互换。因此，为了让这些类型明确区分开来，我们将创建一种“包装类型（wrapper type）”——一种把原始表示包装起来的类型。

正如前面提到的，在 F# 中创建包装类型最简单的方式，就是创建一个“单例联合”（single-case union）类型，也就是只含一个分支的选择类型。

下面是一个例子：

```fsharp
type CustomerId =
  | CustomerId of int
```

由于只有一个分支，我们总是把整个类型定义写在一行，像这样：

```fsharp
type CustomerId = CustomerId of int
```

为了把这类包装类型与复合类型（如记录）以及它们内部包含的原始类型（如 string 和 int）区分开，我们把它们称作“简单类型（simple type）”。

在我们的领域中，简单类型可以这样建模：

```fsharp
type WidgetCode = WidgetCode of string
type UnitQuantity = UnitQuantity of int
type KilogramQuantity = KilogramQuantity of decimal
```

单例联合（single case union）的定义包含两个部分：类型名和“分支”标签：

```fsharp
type CustomerId = CustomerId of int
//   ^类型名      ^分支标签
```

从上面的例子可以看到，（唯一的）分支的标签通常与类型名相同。这意味着在使用这种类型时，构造和解构也可以使用同一个名字，接下来就会看到。

### 使用单例联合

要创建一个单例联合的值，我们把分支名当作构造函数（constructor function）来用。也就是说，我们先定义一个像这样的简单类型：

```fsharp
type CustomerId = CustomerId of int
//                ^这个分支名就是构造函数
```

现在就可以用分支名作为构造函数来创建它了：

```fsharp
let customerId = CustomerId 42
//                ^这是一个接受 int 参数的函数
```

像这样创建简单类型，可以确保我们不会意外混淆不同的类型。例如，如果我们创建了一个 CustomerId 和一个 OrderId，然后尝试比较它们，就会得到一个编译器错误：

```fsharp
// 定义一些类型
type CustomerId = CustomerId of int
type OrderId = OrderId of int

// 定义一些值
let customerId = CustomerId 42
let orderId = OrderId 42

// 尝试比较它们——编译器错误！
printfn "%b" (orderId = customerId)
//                      ^ 此表达式应具有
//                      类型 'OrderId'
```

再比如，我们定义了一个接受 CustomerId 作为输入的函数，那么试图给它传一个 OrderId 又是一个编译器错误：

```fsharp
// 定义一个使用 CustomerId 的函数
let processCustomerId (id:CustomerId) = ...

// 用 OrderId 调用它——编译器错误！
processCustomerId orderId
//                ^ 此表达式应具有类型
//                  'CustomerId'，但此处
//                  的类型是 'OrderId'
```

要解构（或者说“解开”）一个单例联合，我们可以用分支标签做模式匹配：

```fsharp
// 构造
let customerId = CustomerId 42

// 解构
let (CustomerId innerValue) = customerId
//              ^ innerValue 被设置为 42

printfn "%i" innerValue  // 打印 "42"
```

直接在函数定义的参数中解构也非常常见。这样做不仅能让我们立刻访问内部值，F# 编译器还会为我们推断出正确的类型。例如，在下面的代码中，编译器推断出输入参数是一个 CustomerId：

```fsharp
// 解构
let processCustomerId (CustomerId innerValue) =
  printfn "innerValue is %i" innerValue

// 函数签名
// val processCustomerId : CustomerId -> unit
```

### 受约束的值

几乎在所有情况下，简单类型都会以某种方式受到约束，比如必须处于某个范围内，或者必须匹配某个模式。在真实世界的领域中，几乎不会有无限取值范围的整数或字符串。

我们将在下一章讨论如何强制实施这些约束（见“简单值的完整性”一节）。

### 避免简单类型的性能问题

把原始类型包装成简单类型，是确保类型安全、在编译期防止许多错误的好办法。不过，它在内存占用和效率上确实有一定代价。对于典型的业务应用来说，性能的小幅下降应该不成问题；但对于要求高性能的领域（比如科学计算或实时领域），你可能就要多加小心了。例如，遍历一个巨大的 UnitQuantity 值数组会比遍历原始 int 数组慢。

不过有两种办法可以让你鱼与熊掌兼得。

第一种，你可以用类型别名代替简单类型来做领域文档。这种写法没有任何开销，但代价是失去类型安全。

```fsharp
type UnitQuantity = int
```

第二种，从 F# 4.1 开始，你可以使用值类型（即 struct）而不是引用类型。包装本身仍有开销，但把它们存进数组时，内存占用是连续的，因此对缓存更友好。

```fsharp
[<Struct>]
type UnitQuantity = UnitQuantity of int
```

最后，如果你要处理大型数组，可以考虑把整个原始值的集合定义成一个类型，而不是使用简单类型的集合：

```fsharp
type UnitQuantities = UnitQuantities of int[]
```

这样就能两全其美。你可以高效地处理原始数据（例如做矩阵乘法），同时在高层保留类型安全。把这种思路继续推广，就会走向面向数据设计（data-oriented design），[23] 也就是现代游戏开发中使用的做法。

你甚至可能发现，通用语言中正好有一个词用来指代这种被视为整体的集合，比如“DataSample（数据样本）”或“Measurements（测量值）”。如果有，那就用它！

一如既往，性能是个复杂的话题，取决于你具体的代码和环境。通常最好的做法是先用最直接的方式为领域建模，然后再去做调优和优化。

## 为复杂数据建模

在为领域编写文档时，我们用 AND 和 OR 来表示更复杂的模型。在第 4 章“理解类型”中，我们学习了 F# 的代数类型系统，也看到它同样是用 AND 和 OR 从简单类型创建复杂类型。

现在让我们迈出这顺理成章的一步：用代数类型系统来为领域建模。

### 用记录类型建模

在我们的领域中，许多数据结构是由 AND 关系构建的。例如，我们最初那个简单的 Order 是这样定义的：

```fsharp
data Order =
    CustomerInfo
    AND ShippingAddress
    AND BillingAddress
    AND list of OrderLines
    AND AmountToBill
```

它可以直接翻译成一个 F# 记录结构，像这样：

```fsharp
type Order = {
  CustomerInfo : CustomerInfo
  ShippingAddress : ShippingAddress
  BillingAddress : BillingAddress
  OrderLines : OrderLine list
  AmountToBill : ...
  }
```

我们为每个字段起了一个名字（“CustomerInfo”“ShippingAddress”）并指定了类型（CustomerInfo、ShippingAddress）。

这样做暴露出了许多关于领域、尚未回答的问题——我们目前并不知道这些类型究竟是什么。ShippingAddress 和 BillingAddress 是同一个类型吗？“AmountToBill”应该用什么类型来表示？

理想情况下，我们可以请领域专家来帮忙解答。例如，如果专家们把账单地址和收货地址当作不同的东西来谈论，那么即使它们结构相同，最好也在逻辑上保持分离。随着你对领域理解的加深或需求的变化，它们可能会朝不同的方向演化。

### 为未知类型建模

在设计过程的早期阶段，你常常无法对某些建模问题给出确定的答案。例如，得益于通用语言，你会知道自己需要建模哪些类型的名字，却不知道它们的内部结构。

这不是问题——你可以用“最佳猜测”来表示结构未知的类型，或者也可以把它建模成一个显式未定义的类型，让它充当占位符，直到你在设计过程的后期有了更好的理解。

如果想用 F# 表示一个未定义的类型，可以使用异常类型 exn，并为它起一个别名 Undefined：

```fsharp
type Undefined = exn
```

然后就可以在设计模型中使用 Undefined 别名了，像这样：

```fsharp
type CustomerInfo = Undefined
type ShippingAddress = Undefined
type BillingAddress = Undefined
type OrderLine = Undefined
type BillingAmount = Undefined

type Order = {
  CustomerInfo : CustomerInfo
  ShippingAddress : ShippingAddress
  BillingAddress : BillingAddress
  OrderLines : OrderLine list
  AmountToBill : BillingAmount
  }
```

采用这种方式，你就可以继续用类型为领域建模，并让代码通过编译。但当你尝试编写处理这些类型的函数时，就会被逼着用更好的东西替换掉 Undefined。

### 用选择类型建模

在我们的领域中，还看到了许多“在别的东西之间做选择”的东西，比如：

```fsharp
data ProductCode =
    WidgetCode
    OR GizmoCode

data OrderQuantity =
    UnitQuantity
    OR KilogramQuantity
```

怎样用 F# 类型系统来表示这些选择呢？显然是用选择类型（choice type）！

```fsharp
type ProductCode =
  | Widget of WidgetCode
  | Gizmo of GizmoCode

type OrderQuantity =
  | Unit of UnitQuantity
  | Kilogram of KilogramQuantity
```

同样，对于每个分支，我们需要创建两个部分：“标签”（分支标签，位于“of”之前）以及与该分支关联的数据的类型。上面的例子表明，分支标签（比如 Widget）不必与关联的类型名（WidgetCode）相同。

## 用函数为工作流建模

到目前为止，我们已经有了为所有数据结构建模的办法——也就是通用语言中的“名词”。那么“动词”，也就是业务过程呢？

在本书中，我们将把工作流和其他过程建模为函数类型。例如，假设我们有一个验证订单表单的工作流步骤，可以这样为它写文档：

```fsharp
type ValidateOrder = UnvalidatedOrder-> ValidatedOrder
```

从这段代码可以清楚地看出，ValidateOrder 过程把一个未验证的订单变换成一个已验证的订单。

### 处理复杂的输入与输出

每个函数都只有一个输入和一个输出，但有些工作流可能有多个输入或输出。这该怎么建模呢？

先从输出开始。如果某个工作流有一个输出 A 和一个输出 B，我们可以创建一个记录类型把它们都存起来。我们在下单工作流中已经见过这种情况：输出需要是三个不同的事件，所以我们创建一个复合类型，把它们作为一条记录保存：

```fsharp
type PlaceOrderEvents = {
  AcknowledgmentSent : AcknowledgmentSent
  OrderPlaced : OrderPlaced
  BillableOrderPlaced : BillableOrderPlaced
  }
```

采用这种方式，下单工作流就可以写成一个函数类型：以原始的 UnvalidatedOrder 作为输入，返回 PlaceOrderEvents 记录：

```fsharp
type PlaceOrder = UnvalidatedOrder -> PlaceOrderEvents
```

另一方面，如果某个工作流的输出是“A 或 B”，那我们可以创建一个选择类型来同时容纳两者。例如，我们曾简要讨论过把收到的邮件归类为报价单或订单。那个过程至少有两种不同的输出选择：

```fsharp
workflow "Categorize Inbound Mail" =
    input: Envelope contents
    output:
        QuoteForm (put on appropriate pile)
        OR OrderForm (put on appropriate pile)
        OR ...
```

这个工作流很容易建模：只要创建一个新类型（比如 CategorizedMail）来表示这些选择，然后让 CategorizeInboundMail 返回这个类型。我们的模型可能是这样：

```fsharp
type EnvelopeContents = EnvelopeContents of string
type CategorizedMail =
  | Quote of QuoteForm
  | Order of OrderForm
  // 等等

type CategorizeInboundMail = EnvelopeContents -> CategorizedMail
```

现在来看输入的建模。如果工作流的输入是在多个选项中选择（OR），我们可以创建一个选择类型。但如果一个过程有多个全都必需的输入（AND），比如下面的“计算价格”，我们就可以在两种方案之间做选择。

```fsharp
"Calculate Prices" =
    input: OrderForm, ProductCatalog
    output: PricedOrder
```

第一种也是最简单的做法，是把每个输入作为独立的参数传入，像这样：

```fsharp
type CalculatePrices = OrderForm -> ProductCatalog -> PricedOrder
```

另一种做法是创建一个新的记录类型把它们都装进去，比如下面这个 CalculatePricesInput 类型：

```fsharp
type CalculatePricesInput = {
  OrderForm : OrderForm
  ProductCatalog : ProductCatalog
  }
```

现在这个函数就变成这样：

```fsharp
type CalculatePrices = CalculatePricesInput -> PricedOrder
```

哪种做法更好？在上面的例子中，由于 ProductCatalog 是一个依赖而不是“真正的”输入，我们想用独立参数的做法。这让我们能够使用依赖注入的函数式等价物。等我们在“注入依赖”一节实现订单处理管道时再详细讨论。

另一方面，如果两个输入总是同时需要、且彼此强关联，那么用记录类型可以把这一点表达清楚。（在某些情况下，你可以用元组作为简单记录类型的替代品，但一般来说，使用命名的类型更好。）

### 在函数签名中记录效果

我们刚刚看到，ValidateOrder 过程可以这样写：

```fsharp
type ValidateOrder = UnvalidatedOrder -> ValidatedOrder
```

但这假定了验证总能成功、总能返回一个 ValidatedOrder。当然，实践中并非如此，所以更好的做法是在函数签名中返回 Result 类型，以指明这种情况：

```fsharp
type ValidateOrder =
  UnvalidatedOrder -> Result<ValidatedOrder,ValidationError list>

and ValidationError = {
  FieldName : string
  ErrorDescription : string
  }
```

这个签名告诉我们：输入是一个 UnvalidatedOrder；如果成功，输出是一个 ValidatedOrder；但如果验证失败，结果是一个 ValidationError 列表，其中每项又包含对错误的描述以及它涉及的字段。

函数式编程的人使用“效果（effects）”这个词来描述一个函数在其主要输出之外所做的事情。通过在这里使用 Result，我们就记录下了 ValidateOrder 可能有“错误效果”这一事实。这在类型签名里说得很清楚：我们不能假定函数总会成功，而应该准备好处理错误。

类似地，我们可能想记录某个过程是异步的——它不会立即返回。该怎么做呢？当然还是用另一个类型！

在 F# 中，我们用 Async 类型来表明一个函数会有“异步效果”。因此，如果 ValidateOrder 既有异步效果又有错误效果，我们就可以把函数类型写成这样：

```fsharp
type ValidateOrder =
  UnvalidatedOrder -> Async<Result<ValidatedOrder,ValidationError list>>
```

这个类型签名记录了两件事：(a) 当我们尝试获取返回值的内容时，代码不会立即返回；(b) 当它返回时，结果可能是一个错误。

像这样把所有效果显式列出很有用，但也会让类型签名变得丑陋而复杂，所以我们通常会为它创建一个类型别名，让它好看一些。

```fsharp
type ValidationResponse<'a> = Async<Result<'a,ValidationError list>>
```

然后这个函数就可以这样记录：

```fsharp
type ValidateOrder =
  UnvalidatedOrder -> ValidationResponse<ValidatedOrder>
```

## 身份问题：值对象

我们已经基本理解了如何为领域类型和工作流建模，接下来看一种重要的数据类型分类方法：依据它们是否拥有持久的身份来分类。

在 DDD 术语中，拥有持久身份的对象称为实体（Entity），没有持久身份的对象称为值对象（Value Object）。我们先从值对象开始讨论。

在许多情况下，我们正在处理的数据对象没有身份——它们是可以互换的。例如，一个值为“W1234”的 WidgetCode 实例，与其他任何值为“W1234”的 WidgetCode 是同一个东西。我们不需要区分它们谁是谁——它们彼此相等。

在 F# 中可以这样演示：

```fsharp
let widgetCode1 = WidgetCode "W1234"
let widgetCode2 = WidgetCode "W1234"
printfn "%b" (widgetCode1 = widgetCode2)  // 打印 "true"
```

“没有身份的值”这一概念在领域模型中频繁出现，而且不仅限于简单类型，复杂类型同样如此。例如，一个 PersonalName 记录类型可能有两个字段——FirstName 和 LastName——所以它比一个简单的 string 更复杂；但它同样是一个值对象，因为两个字段都相同的姓名是可互换的。从下面的 F# 代码可以看到这一点：

```fsharp
let name1 = {FirstName="Alex"; LastName="Adams"}
let name2 = {FirstName="Alex"; LastName="Adams"}
printfn "%b" (name1 = name2)  // 打印 "true"
```

“地址”类型也是值对象。如果两个值的街道地址、城市和邮编都相同，它们就是同一个地址：

```fsharp
let address1 = {StreetAddress="123 Main St"; City="New York"; Zip="90001"}
let address2 = {StreetAddress="123 Main St"; City="New York"; Zip="90001"}
printfn "%b" (address1 = address2)  // 打印 "true"
```

你可以从领域的讨论方式中判断出这些东西是值对象：谈到它们时，人们会说“Chris 和我同名”。也就是说，尽管 Chris 和我是不同的人，但我们的名字相同。名字没有独一无二的身份。类似地，“Pat 的通信地址和我一样”意味着我的地址和 Pat 的地址内容相同，因此相等。

### 为值对象实现相等性

当我们用 F# 的代数类型系统为领域建模时，所创建的类型默认就会实现这种基于字段的相等性测试。我们不需要自己编写任何特殊的相等性代码，这一点很棒。

准确地说，在 F# 中，两个（同类型的）记录值在其所有字段都相等时相等；两个选择类型在其分支相同、且与该分支关联的数据也相等时相等。这称为结构化相等（structural equality）。

## 身份问题：实体

然而，我们经常要为真实世界中确实拥有独一无二身份的事物建模，即使它们的组成部分发生了变化。例如，即使我改了名字或搬了家，我仍然是同一个人。

在 DDD 术语中，我们把这类东西称为实体（Entity）。

在业务场景中，实体通常是某种单据：订单、报价单、发票、客户档案、产品说明表等等。它们有一个生命周期，并被各种业务过程从一个状态变换到另一个状态。

“值对象”与“实体”之间的区分取决于上下文。以一部手机的生命周期为例：在制造过程中，每部手机都被赋予一个唯一的序列号——一个独一无二的身份——所以在那个上下文中，手机会被建模为实体。而在销售时，序列号无关紧要——所有规格相同的手机都可以互换——它们可以被建模为值对象。可一旦某部特定的手机卖给了某位特定的客户，身份又变得重要起来，它就应该被建模为实体：即使换了屏幕或电池，客户仍然把它看作同一部手机。

### 实体的标识符

实体需要在任何变化之下仍保持稳定的身份。因此，为它们建模时，我们需要给它们一个唯一的标识符或键（key），比如“Order ID”或“Customer ID”。

例如，下面的 Contact 类型有一个 ContactId，即使 PhoneNumber 或 EmailAddress 字段变了，它也保持不变：

```fsharp
type ContactId = ContactId of int

type Contact = {
  ContactId : ContactId
  PhoneNumber : ...
  EmailAddress: ...
  }
```

这些标识符从哪里来？有时候，标识符由真实世界的领域本身提供——纸质订单和发票上向来都写着某种编号——但有时我们也需要自己创建人工标识符，比如使用 UUID、自动递增的数据库表或 ID 生成服务。这是个复杂的话题，所以在本书中我们只假设所有标识符都已由客户端提供给我们。

### 在数据定义中加入标识符

既然我们已经把某个领域对象识别为实体，那该如何把标识符加到它的定义中呢？

给记录类型加标识符很简单——加一个字段就行。但如果是给选择类型加标识符呢？标识符应该放在“里面”（与每个分支关联），还是放在“外面”（不与任何分支关联）？

举个例子，假设一张发票（Invoice）有两种情况：已支付和未支付。如果采用“外面”的方式建模，我们会得到一个包含 InvoiceId 的记录，然后在这个记录里面放一个选择类型 InvoiceInfo，其中保存每种发票各自的信息。代码大致是这样的：

```fsharp
// 未支付情况的信息（不含 id）
type UnpaidInvoiceInfo = ...

// 已支付情况的信息（不含 id）
type PaidInvoiceInfo = ...

// 组合起来的信息（不含 id）
type InvoiceInfo =
  | Unpaid of UnpaidInvoiceInfo
  | Paid of PaidInvoiceInfo

// 发票的 id
type InvoiceId = ...

// 顶层的发票类型
type Invoice = {
  InvoiceId : InvoiceId // 在两个子分支的“外面”
  InvoiceInfo : InvoiceInfo
  }
```

这种做法的问题在于：某个分支的数据分散在不同组成部分之间，很难轻松地单独处理。

实践中更常见的做法是用“里面”的方式存储 ID，即每个分支各自持有标识符的一份副本。应用到我们的例子中，我们会创建两个独立的类型，每个分支一个（UnpaidInvoice 和 PaidInvoice），它们各自拥有自己的 InvoiceId，然后再定义一个顶层的 Invoice 类型，表示两者之间的选择。代码大致是这样的：

```fsharp
type UnpaidInvoice = {
  InvoiceId : InvoiceId // id 存放在“里面”
  // 以及未支付情况的其他信息
  }

type PaidInvoice = {
  InvoiceId : InvoiceId // id 存放在“里面”
  // 以及已支付情况的其他信息
  }

// 顶层的发票类型
type Invoice =
  | Unpaid of UnpaidInvoice
  | Paid of PaidInvoice
```

这种做法的好处是：现在做模式匹配时，所有数据（包括 ID）都可以在一处直接访问：

```fsharp
let invoice = Paid {InvoiceId = ...}

match invoice with
  | Unpaid unpaidInvoice ->
    printfn "The unpaid invoiceId is %A" unpaidInvoice.InvoiceId
  | Paid paidInvoice ->
    printfn "The paid invoiceId is %A" paidInvoice.InvoiceId
```

### 为实体实现相等性

前面我们看到，F# 默认的相等性测试会用到记录的所有字段。但比较实体时，我们只想用一个字段——标识符。这意味着，要在 F# 中正确地为实体建模，就必须改变默认行为。

一种做法是重写相等性测试，使其只用标识符。要改变默认行为，我们需要做以下几件事：

重写 Equals 方法

重写 GetHashCode 方法

给类型加上 CustomEquality 和 NoComparison 特性（attribute），告诉编译器我们要改变默认行为

对 Contact 类型做完这些之后，得到的结果是：

```fsharp
[<CustomEquality; NoComparison>]
type Contact = {
  ContactId : ContactId
  PhoneNumber : PhoneNumber
  EmailAddress: EmailAddress
  }
  with
  override this.Equals(obj) =
    match obj with
    | :? Contact as c -> this.ContactId = c.ContactId
    | _ -> false
  override this.GetHashCode() =
    hash this.ContactId
```

这是一种我们还没见过的新语法：F# 的面向对象语法。我们只是在这里用它演示相等性重写，面向对象的 F# 超出了本书范围，所以在书的其他地方不会再使用它。

定义好类型之后，我们可以创建一个联系人：

```fsharp
let contactId = ContactId 1

let contact1 = {
  ContactId = contactId
  PhoneNumber = PhoneNumber "123-456-7890"
  EmailAddress = EmailAddress "bob@example.com"
  }
```

再创建一个 ContactId 相同、但内容不同的联系人：

```fsharp
// 同一个联系人，但电子邮件地址不同
let contact2 = {
  ContactId = contactId
  PhoneNumber = PhoneNumber "123-456-7890"
  EmailAddress = EmailAddress "robert@example.com"
  }
```

最后，当我们用 = 比较它们时，结果是 true：

```fsharp
// 即使电子邮件地址不同，结果仍为 true
printfn "%b" (contact1 = contact2)
```

这是面向对象设计中的常见做法，但它悄悄改变了默认的相等性行为，偶尔会让你栽跟头。因此，一种（往往更可取的）替代方案是干脆禁止对对象做相等性测试：加上 NoEquality 类型标注，像这样：

```fsharp
[<NoEquality; NoComparison>]
type Contact = {
  ContactId : ContactId
  PhoneNumber : PhoneNumber
  EmailAddress: EmailAddress
  }
```

现在，当我们试图比较带这种标注的值时，会得到一个编译器错误：

```fsharp
// 编译器错误！
printfn "%b" (contact1 = contact2)
//            ^ Contact 类型不支持
//              相等性比较
```

当然，我们仍然可以直接比较 ContactId 字段，像这样：

```fsharp
// 没有编译器错误
printfn "%b" (contact1.ContactId = contact2.ContactId) // true
```

“NoEquality”做法的好处是：它消除了“对象层面的相等到底指什么”的任何歧义，迫使我们显式表达。

最后，在某些情况下，可能有多个字段都用于相等性测试。此时，你可以很容易地暴露一个把它们组合起来的合成 Key 属性：

```fsharp
[<NoEquality;NoComparison>]
type OrderLine = {
  OrderId : OrderId
  ProductId : ProductId
  Qty : int
  }
  with
  member this.Key =
    (this.OrderId,this.ProductId)
```

然后，需要比较的时候，就可以使用 Key 字段，像这样：

```fsharp
printfn "%b" (line1.Key = line2.Key)
```

### 不可变性与身份

正如我们在第 4 章“理解类型”中看到的，F# 这类函数式编程语言中的值默认是不可变的，也就是说，到目前为止定义的所有对象在初始化之后都无法更改。

这对我们的设计有什么影响？

对值对象来说，不可变性是必需的。想想我们在日常语言中怎么使用它们：如果我们改动了某个姓名的一部分，我们会说这是一个新的、不同的名字，而不是“数据不同的同一个名字”。

对实体来说，情况有所不同。我们预期与实体关联的数据会随时间变化；否则要一个恒定的标识符干什么？那么，不可变的数据结构怎样才能做到这一点呢？答案是：我们在保留身份的同时，复制一份带有变更后数据的实体。这么多的复制看起来像是很多额外的工作，但在实践中并不是问题。事实上，在整本书中我们都会处处使用不可变数据，你将会看到，不可变性很少成为麻烦。

下面是一个在 F# 中更新实体的例子。首先，我们从一个初始值开始：

```fsharp
let initialPerson = {PersonId=PersonId 42; Name="Joseph"}
```

要复制一个记录、只更改其中部分字段，F# 使用 with 关键字，像这样：

```fsharp
let updatedPerson = {initialPerson with Name="Joe"}
```

完成这次复制之后，updatedPerson 值的 Name 与 initialPerson 值不同，但 PersonId 相同。

使用不可变数据结构的一个好处是：任何变更都必须在类型签名中显式体现。例如，如果想写一个修改 Person 中 Name 字段的函数，我们不能使用下面这种签名：

```fsharp
type UpdateName = Person -> Name -> unit
```

这个函数没有输出，这暗示什么都没有改变（或者说 Person 是被作为副作用原地修改的）。相反，我们的函数必须有一个把 Person 类型作为输出的签名，像这样：

```fsharp
type UpdateName = Person -> Name -> Person
```

这清楚地表明：给定一个 Person 和一个 Name，会返回某种原始 Person 的变体。

## 聚合

让我们更仔细地看看与我们的设计特别相关的两个数据类型：Order 和 OrderLine。

首先，Order 是实体还是值对象？显然是实体——订单的细节可能随时间变化，但它仍然是同一张订单。

那么 OrderLine 呢？例如，如果我们修改了某个订单行的数量，它还是同一个订单行吗？在大多数设计中，回答“是”都合情合理：即使数量或价格随时间变化，它仍然是同一个订单行。所以 OrderLine 也是实体，有自己的标识符。

但现在有一个问题：如果你修改了一个订单行，是否也修改了它所属的订单？

在这种情况下，答案显然是肯定的：修改一个订单行也就修改了整个订单。事实上，拥有不可变的数据结构使这一点不可避免。如果我有一个包含不可变 OrderLine 的不可变 Order，那么仅仅复制某个订单行并不会连带复制 Order。要修改 Order 中包含的一个 OrderLine，我需要在 Order 这一层做修改，而不是在 OrderLine 那一层。

例如，下面是更新一个订单行价格的伪代码：

```fsharp
/// 我们传入三个参数：
/// * 顶层的订单
/// * 我们想修改的订单行的 id
/// * 新的价格
let changeOrderLinePrice order orderLineId newPrice =

  // 1. 用 orderLineId 找到要修改的行
  let orderLine = order.OrderLines |> findOrderLine orderLineId

  // 2. 用新价格生成新版本的 OrderLine
  let newOrderLine = {orderLine with Price = newPrice}

  // 3. 创建一个新的行列表，
  //    用新行替换旧行
  let newOrderLines =
    order.OrderLines |> replaceOrderLine orderLineId newOrderLine

  // 4. 生成整个订单的新版本，
  //    用新的行替换所有旧行
  let newOrder = {order with OrderLines = newOrderLines}

  // 5. 返回新订单
  newOrder
```

最终结果（即函数的输出）是一个新的 Order，其中包含一个新的行列表，而其中一行有了新价格。你可以看到，不可变性会在数据结构中引发涟漪效应：修改一个低层组件，可能迫使高层组件也随之更改。

因此，即使我们只是修改 Order 的一个“子实体”（一个 OrderLine），也总是必须在 Order 本身这一层操作。

这是一种非常常见的情形：我们有一组实体，每个都有自己的 ID，同时还有某个包含它们的“顶层”实体。在 DDD 术语中，这样一组实体称为聚合（aggregate），而顶层实体称为聚合根（aggregate root）。在这个例子中，聚合由 Order 和 OrderLine 的集合共同组成，聚合根就是 Order 本身。

### 聚合保证一致性与不变量

聚合在数据更新时扮演着重要角色。聚合充当一致性边界：当聚合的一部分被更新时，其他部分可能也需要更新，以确保一致性。

例如，我们可能会扩展这个设计，在顶层 Order 中额外存储一个“总价”。显然，如果其中某个订单行的价格变了，总价也必须更新，以保持数据一致。这件事会在上面的 changeOrderLinePrice 函数中完成。显然，唯一“知道”如何保持一致性的组件就是顶层的 Order——聚合根——所以这也是在订单层而不是订单行层做所有更新的又一个理由。

聚合也是实施所有不变量（invariants）的地方。假设你有一条规则：每张订单至少要有一个订单行。那么当你尝试删除多个订单行时，聚合会确保在只剩最后一行时报错。

我们将在第 6 章“领域中的完整性与一致性”中进一步讨论这个话题。

### 聚合引用

假设我们需要把客户的信息与 Order 关联起来。一种诱人的做法是把整个 Customer 作为 Order 的一个字段，像这样：

```fsharp
type Order = {
  OrderId : OrderId
  Customer : Customer  // 关联客户的信息
  OrderLines : OrderLine list
  // 等等
  }
```

但想一想不可变性带来的涟漪效应。如果我改动了客户的任何部分，我就必须连带改动订单。这真的是我们想要的吗？

好得多的设计是只存储对客户的引用，而不是整个客户记录。也就是说，我们只在 Order 类型中存储 CustomerId，像这样：

```fsharp
type Order = {
  OrderId : OrderId
  CustomerId : CustomerId  // 对关联客户的引用
  OrderLines : OrderLine list
  // 等等
  }
```

采用这种方式，当我们需要客户的完整信息时，会先从 Order 中取出 CustomerId，再从数据库中单独加载相关的客户数据，而不是把它作为订单的一部分一起加载。

换句话说，Customer 和 Order 是相互独立的不同聚合。它们各自负责自己的内部一致性，而它们之间唯一的联系就是通过各自根对象的标识符。

这就引出了聚合的另一个重要方面：聚合是持久化的基本单元。如果你想从数据库加载或保存对象，就应该加载或保存整个聚合。每个数据库事务应该只处理一个聚合，不应包含多个聚合，也不应跨越聚合边界。更多信息见“事务”一节。

类似地，如果想序列化一个对象、把它通过网络发送出去，你也总是发送整个聚合，而不是它的一部分。

需要说明的是，聚合并不是随便一组实体的集合。例如，一个客户列表是一组实体，但它不是 DDD 意义上的“聚合”，因为它没有作为根的顶层实体，也不是在充当一致性边界。

下面总结一下聚合在领域模型中的重要作用：

聚合是一组可以被视为单一单元的领域对象，其中的顶层实体充当“根”。

对聚合内部对象的所有修改，都必须经由顶层、施加到根上；聚合充当一致性边界，确保聚合内的所有数据在同一时间被正确地一并更新。

聚合是持久化、数据库事务和数据传输的原子单元。

正如你所见，定义聚合是设计过程的重要组成部分。有时，一起使用的实体属于同一个聚合（OrderLine 和 Order），有时则不属于（Customer 和 Order）。这正是与领域专家协作的关键所在：只有他们能帮助你理解实体之间的关系和一致性边界。

在这整个建模过程中我们还会见到大量聚合，所以从现在起我们将使用这套术语。

### 更多领域驱动设计词汇

值对象、实体、聚合——以下是本章引入的新的 DDD 术语：

值对象是没有身份的领域对象。两个所含数据相同的值对象被视为相同。值对象必须是不可变的：任何一部分改变，它就变成了另一个不同的值对象。值对象的例子有姓名、地址、位置、金额和日期。

实体是拥有内在身份的领域对象，这个身份在其属性变化时依然保持。实体对象通常有一个 ID 或键字段，两个 ID/键相同的实体被视为同一个对象。实体通常表示有生命期和变更历史的领域对象，比如某种单据。实体的例子有客户、订单、产品和发票。

聚合是一组相关对象的集合，它们被视为单一组件，既用来保证领域内的一致性，也用来作为数据事务中的原子单元。其他实体只应通过聚合的标识符来引用它，该标识符就是聚合中“顶层”成员（称为“根”）的 ID。

## 综合运用

本章中我们已经创建了大量类型，现在退后一步，看看它们如何作为一个整体、一个完整的领域模型组合在一起。

首先，我们把所有这些类型放进一个名为 OrderTaking.Domain 的命名空间中，用命名空间把这些类型与其他命名空间分开。换句话说，我们用 F# 的命名空间来表示 DDD 的限界上下文（bounded context），至少目前如此。

```fsharp
namespace OrderTaking.Domain

// 类型如下
```

接下来加上简单类型。

```fsharp
// 产品代码相关
type WidgetCode = WidgetCode of string
  // 约束：以 "W" 开头，后接 4 位数字
type GizmoCode = GizmoCode of string
  // 约束：以 "G" 开头，后接 3 位数字
type ProductCode =
  | Widget of WidgetCode
  | Gizmo of GizmoCode

// 订单数量相关
type UnitQuantity = UnitQuantity of int
type KilogramQuantity = KilogramQuantity of decimal
type OrderQuantity =
  | Unit of UnitQuantity
  | Kilos of KilogramQuantity
```

这些都是值对象，不需要标识符。

另一方面，订单拥有一个在变化中保持不变的身份——它是一个实体——所以我们必须为它建模一个 ID。我们不知道这个 ID 是 string、int 还是 Guid，但我们知道需要它，所以暂时先用 Undefined。其他标识符也照此处理。

```fsharp
type OrderId = Undefined
type OrderLineId = Undefined
type CustomerId = Undefined
```

现在可以勾勒出订单及其组成部分了：

```fsharp
type CustomerInfo = Undefined
type ShippingAddress = Undefined
type BillingAddress = Undefined
type Price = Undefined
type BillingAmount = Undefined

type Order = {
  Id : OrderId             // 实体的 id
  CustomerId : CustomerId  // 客户引用
  ShippingAddress : ShippingAddress
  BillingAddress : BillingAddress
  OrderLines : OrderLine list
  AmountToBill : BillingAmount
  }

and OrderLine = {
  Id : OrderLineId  // 实体的 id
  OrderId : OrderId
  ProductCode : ProductCode
  OrderQuantity : OrderQuantity
  Price : Price
  }
```

在上面的代码片段中，我们使用了 and 关键字，允许对尚未声明的类型做前向引用。解释见“在文件与项目中组织类型”一节。

最后，以工作流本身作结。工作流的输入 UnvalidatedOrder 将“原样”由订单表单构建，所以它只包含 int 和 string 之类的原始类型。

```fsharp
type UnvalidatedOrder = {
  OrderId : string
  CustomerInfo : ...
  ShippingAddress : ...
  ...
  }
```

工作流的输出需要两个类型。第一个是工作流成功时的事件类型：

```fsharp
type PlaceOrderEvents = {
  AcknowledgmentSent : ...
  OrderPlaced : ...
  BillableOrderPlaced : ...
  }
```

第二个是工作流失败时的错误类型：

```fsharp
type PlaceOrderError =
  | ValidationError of ValidationError list
  | ...  // 其他错误

and ValidationError = {
    FieldName : string
    ErrorDescription : string
    }
```

最后，我们可以定义表示下单工作流的顶层函数：

```fsharp
/// "Place Order"（下单）过程
type PlaceOrder =
  UnvalidatedOrder -> Result<PlaceOrderEvents,PlaceOrderError>
```

显然，还有许多细节需要充实，但完成这项工作的流程现在应该已经清楚了。

不过，我们这个订单处理工作流的模型还不完整。例如，我们要如何建模订单的不同状态：已验证、已定价等等？

### 重温挑战：类型能取代文档吗？

在本章开头，我们给自己出了一个挑战：能不能把领域需求捕获进类型系统，并且让领域专家和其他非开发人员也能评审？

那么，看看上面列出的领域模型，我们应该感到满意。我们得到了一个完整的领域模型，它以 F# 类型的形式而非文本写成，而我们设计出的这些类型，看起来几乎与之前用 AND 和 OR 记法编写的领域文档一模一样。

想象你是一个非开发人员。要把这段代码当作文档来理解，你需要学会什么？你需要理解简单类型（单例联合）、AND 类型（带花括号的记录）、OR 类型（带竖线的选择）以及“过程”（输入、输出和箭头）的语法，仅此而已。它当然比 C# 或 Java 这类传统编程语言可读性好得多。

## 收尾

在本章中，我们学习了如何使用 F# 类型系统，通过简单类型、记录类型和选择类型为领域建模。自始至终，我们使用的都是领域的通用语言，比如 ProductCode 和 OrderQuantity，而不是 string、int 这类以开发者为中心的词。我们从头到尾都没有定义过 Manager 或 Handler 这样的类型！

我们还学习了不同种类的身份，以及如何用类型为 DDD 的值对象和实体概念建模。我们还引入了“聚合”的概念，把它当作保证一致性的一种手段。

接着，我们创建了一组类型，它们与本章开头的文本文档长得非常相似。最大的区别在于：所有这些类型定义都是可编译的代码，可以与应用程序其余的代码放在一起。这进而意味着，应用程序代码永远与领域定义保持同步；如果任何领域定义发生了变化，应用程序将无法通过编译。我们不需要费力让设计与代码保持同步——设计即代码！

这种“用类型当文档”的做法非常通用，你显然也能把它应用到其他领域。由于此时尚无任何实现，在与领域专家协作时，它是快速尝试想法的绝佳方式。当然，因为它只是文本，领域专家无需特殊工具就能轻松评审，甚至可能亲自写上几个类型！

不过，设计的若干方面我们还没有涉及。如何确保简单类型始终受到正确的约束？如何强制实施聚合的完整性？我们要如何建模订单的不同状态？这些话题将在下一章中讨论。
