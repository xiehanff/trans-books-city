# 第 20 章　寄存器分配

*Chapter 20: Register Allocation*

到目前为止，你一直把每个伪寄存器（pseudoregister）的空间都分配在栈上。这种策略很简单，但效率低得可怜。由于指令并不总能直接操作内存中的值，你有时需要生成额外的指令，在这些栈位置和寄存器之间来回复制值。更糟的是，你生成的汇编代码不得不频繁访问内存，尽管寄存器要快得多。现在就来解决这些问题。你将为编译器收尾：添加一个寄存器分配（register allocation）遍（在本章开头的示意图中以粗体标出），把伪寄存器分配到硬寄存器（hard register）而不是内存位置。你将使用图着色（graph coloring）这一经典的寄存器分配技术来得到这种分配。

初版寄存器分配器跑起来之后，你还要再交给它一项任务：清理汇编生成阶段产生的一些不必要的 mov 指令。最终版的分配器会先执行寄存器合并（register coalescing），再把伪寄存器分配到硬寄存器。寄存器合并这一步会寻找源和目的可以合并（coalesce）为单一操作数的 mov 指令，从而可以把这条指令删掉。

寄存器分配里什么都有：高层次的理论、底层的细节、全新的概念，还有前几章里熟悉的技术。而它的回报也非常令人满足：到本章结束时，你生成的代码效率会大幅提升。我认为，以它为全书收尾再合适不过。

开始之前，先来看一个例子，它说明了寄存器分配为什么是一种威力强大的优化。

## 寄存器分配实战

来看看清单 20-1 中这个极小的 C 函数。

```c
int f(int x, int y) {
    return 10 - (3 * y + x);
}
```

*清单 20-1：一个极小的 C 函数*

首先，我们的编译器会把它变成清单 20-2 中这个极小的 TACKY 函数。

```text
f(x, y):
    tmp0 = 3 * y
    tmp1 = tmp0 + x
    tmp2 = 10 - tmp1
    Return(tmp2)
```

*清单 20-2：清单 20-1 的 TACKY 代码*

这个清单给出的是优化阶段之后的 f 的定义。（特别是，我们已经优化掉了在每个 TACKY 函数末尾添加的、作为缺失 return 语句兜底的额外 Return(0)。）

接下来，我们把清单 20-2 转换为清单 20-3 中的汇编代码。

```asm
f:
  ❶ movl    %edi, %x
    movl    %esi, %y
  ❷ movl    $3, %tmp0
    imull   %y, %tmp0
    movl    %tmp0, %tmp1
    addl    %x, %tmp1
    movl    $10, %tmp2
    subl    %tmp1, %tmp2
  ❸ movl    %tmp2, %eax
    ret
```

*清单 20-3：清单 20-2 的汇编代码*

我们先设置函数的参数 ❶，然后计算 tmp0、tmp1 和 tmp2 ❷，最后返回 tmp2 ❸。清单中的操作数 %x、%y、%tmp0、%tmp1 和 %tmp2 指的是对应的伪寄存器；本章我会一直使用这种记法。

现在我们依次尝试三种方法，用真实的操作数替换这些伪寄存器。第一种是用栈地址替换，这正是我们编译器目前的做法。第二次尝试，我们用硬寄存器替换它们，但事先不执行寄存器合并；这是寄存器分配器初始版本的做法。第三种，我们先执行寄存器合并，再把伪寄存器替换为硬寄存器。这是完成的分配器处理这个程序的方式。（先说明一下术语：本章中我用「寄存器」一词统称伪寄存器和硬寄存器。）

### 第一回合：把所有东西放到栈上

按目前的形式，我们的编译器会按照表 20-1 把每个伪寄存器替换成一个栈槽（stack slot）。

| 伪寄存器 | 实际位置 |
| --- | --- |
| x | -4(%rbp) |
| y | -8(%rbp) |
| tmp0 | -12(%rbp) |
| tmp1 | -16(%rbp) |
| tmp2 | -20(%rbp) |

*表 20-1：用栈地址替换伪寄存器*

这会得到清单 20-4 中的汇编代码。

```asm
f:
    movl    %edi, -4(%rbp)
    movl    %esi, -8(%rbp)
    movl    $3, -12(%rbp)
  ❶ imull   -8(%rbp), -12(%rbp)
  ❷ movl    -12(%rbp), -16(%rbp)
  ❸ addl    -4(%rbp), -16(%rbp)
    movl    $10, -20(%rbp)
  ❹ subl    -16(%rbp), -20(%rbp)
    movl    -20(%rbp), %eax
    ret
```

*清单 20-4：用栈地址替换伪寄存器之后的清单 20-3*

把每个伪寄存器都替换成内存地址之后，指令 ❶、❷、❸、❹ 变得非法，指令修复遍需要修复它们。它会在 ❶ 之前插入一条额外的指令，把 ❶ 的目的操作数装入一个硬寄存器，之后再添加一条指令把结果存回 -12(%rbp)。它还会插入指令，把 ❷、❸ 和 ❹ 的源操作数装入硬寄存器。在寄存器分配的语境下，如果我们把某个伪寄存器的内容存到栈上而不是硬寄存器里，就说它被溢出（spill）到了内存。为了在寄存器和内存之间搬运被溢出的值而插入的额外指令，称为溢出代码（spill code）。

最终我们会得到清单 20-5 中的汇编代码。我用粗体标出了溢出代码，方便辨认。（我还略去了设置和拆除栈帧的指令，它们与此处无关。本章后面的汇编程序中同样会略去这些指令。）

```asm
f:
    --snip--
    movl    %edi, -4(%rbp)
    movl    %esi, -8(%rbp)
    movl    $3, -12(%rbp)
    movl    -12(%rbp), %r11d
    imull   -8(%rbp), %r11d
    movl    %r11d, -12(%rbp)
    movl    -12(%rbp), %r10d
    movl    %r10d, -16(%rbp)
    movl    -4(%rbp), %r10d
    addl    %r10d, -16(%rbp)
    movl    $10, -20(%rbp)
    movl    -16(%rbp), %r10d
    subl    %r10d, -20(%rbp)
    movl    -20(%rbp), %eax
    --snip--
    ret
```

*清单 20-5：加入溢出代码之后的清单 20-4*

这段代码效率低得惊人。几乎每条指令都在访问内存，我们还浪费大量时间把数据从一个地方搬到另一个地方。举个特别离谱的例子：我们把 3 * y 的结果存进 -12(%rbp)，紧接着又把它复制到 -16(%rbp)——这花了两条 mov 指令——而此后再也没用过 -12(%rbp)。

### 第二回合：寄存器分配

换一种更合理的策略试试。这一次，我们用硬寄存器而不是栈地址来替换每个伪寄存器，如表 20-2 所示。

| 伪寄存器 | 实际位置 |
| --- | --- |
| x | %edx |
| y | %ecx |
| tmp0 | %r8d |
| tmp1 | %r9d |
| tmp2 | %edi |

*表 20-2：用硬寄存器替换伪寄存器*

我们把 x、y、tmp0 和 tmp1 替换为在原始汇编程序中完全没出现过的寄存器，把 tmp2 替换为原始程序中使用了的 EDI。这没有问题，因为只有在不再需要 EDI 做别的事情之后，我们才会使用 tmp2。本章稍后会看到如何更系统地推理：哪些从伪寄存器到硬寄存器的映射是安全的，哪些可能引起冲突。

这次没有溢出代码，所以我就不再分别给出指令修复遍之前和之后的清单了，直接看最终汇编代码，见清单 20-6。

```asm
f:
    --snip--
    movl    %edi, %edx
    movl    %esi, %ecx
    movl    $3, %r8d
    imull   %ecx, %r8d
    movl    %r8d, %r9d
    addl    %edx, %r9d
    movl    $10, %edi
    subl    %r9d, %edi
    movl    %edi, %eax
    --snip--
    ret
```

*清单 20-6：寄存器分配之后清单 20-3 的最终汇编代码*

这是巨大的进步：我们不再访问内存，指令总数也更少。如果愿意，甚至可以省略设置和拆除栈帧的指令，因为我们根本没用到栈。但我们搬运数据的次数还是超出了需要。比如，我们把函数参数从 EDI 和 ESI 复制到新位置，而不是让它们留在原地。我们还把 tmp0（现在在 %r8d 中）复制到 tmp1（现在在 %r9d 中），而连续两次计算本来直接用 tmp0 也完全可以。这不是寄存器分配器的错，只是前面的遍生成了低效的 TACKY 和汇编代码。但只要在寄存器分配上多用心，我们就能替前面的遍收拾残局。正因如此，我们的寄存器分配器还要再加一步：寄存器合并。

### 第三回合：带合并的寄存器分配

最后一种方法分两步。第一步，合并寄存器：逐个查看函数中的每条 mov 指令，判断它的操作数能否合并到一起。第二步，把剩余的伪寄存器替换为硬寄存器，就像上一轮尝试那样。

再来看清单 20-3 中最初的汇编程序。它包含四条源和目的都是寄存器的 mov 指令，这里以粗体标出：

```asm
f:
    movl    %edi, %x
    movl    %esi, %y
    movl    $3, %tmp0
    imull   %y, %tmp0
    movl    %tmp0, %tmp1
    addl    %x, %tmp1
    movl    $10, %tmp2
    subl    %tmp1, %tmp2
    movl    %tmp2, %eax
    ret
```

有时候，把值从一个寄存器复制到另一个寄存器确实必要。例如，如果之后还要用 EDI 传递另一个函数参数，我们就得把 x 从 EDI 复制出来。但在这个例子中，把 x 合并进 EDI 是安全的，因为第一条 mov 指令之后我们不再需要 EDI 做别的事情。同样的逻辑也适用于其余三条 mov 指令。我们不会同时需要在源操作数和目的操作数中存放不同的值，所以把它们合并到一起是安全的。我们把 x 合并进 EDI、y 合并进 ESI、tmp1 合并进 tmp0、tmp2 合并进 EAX。

表 20-3 总结了我们要合并哪些寄存器对，并给出每对中保留在程序里的成员。

| 合并的对 | 保留的寄存器 |
| --- | --- |
| %edi, %x | %edi |
| %esi, %y | %esi |
| %tmp0, %tmp1 | %tmp0 |
| %tmp2, %eax | %eax |

*表 20-3：合并寄存器*

我们还会删掉全部四条 mov 指令，因为它们不再有任何用处。清单 20-7 给出结果汇编代码，更新过的操作数以粗体标出。

```asm
f:
    movl    $3, %tmp0
    imull   %esi, %tmp0
    addl    %edi, %tmp0
    movl    $10, %eax
    subl    %tmp0, %eax
    ret
```

*清单 20-7：寄存器合并之后的清单 20-3*

这看起来合理多了！我们把 x 和 y 留在 EDI 和 ESI 里——它们本来就是通过这两个寄存器传进来的——而不是复制到新位置。计算返回值时，我们直接把结果存进 EAX，而不是算完之后再复制进 EAX。计算 3 * y + x 时，我们也不再使用两个独立的临时寄存器分别算中间结果和最终结果，而是全程只用 tmp0。

还没完：我们仍需把 tmp0 替换成硬寄存器。除了 ESI、EDI 和 EAX，任何寄存器都行——就选 ECX 吧。清单 20-8 展示了我们最终得到的汇编代码。

```asm
f:
    --snip--
    movl    $3, %ecx
    imull   %esi, %ecx
    addl    %edi, %ecx
    movl    $10, %eax
    subl    %ecx, %eax
    --snip--
    ret
```

*清单 20-8：带合并的寄存器分配之后清单 20-3 的最终汇编代码*

不带合并的寄存器分配从两方面改进了我们的代码：减少了内存访问次数和程序中的溢出代码量。有了寄存器合并，我们进一步改进代码，删掉了前面的遍生成的大量不必要的 mov 指令。

现在我们大致知道自己要做什么了，接下来看看寄存器分配如何融入整个编译器流水线。

## 更新编译器流水线

寄存器分配器在可用硬寄存器很多时效果最好，所以我们要做的第一件事，就是把所有剩余的硬寄存器加入汇编 AST，包括至今一直避开的被调用者保存（callee-saved）寄存器。我们还要对 TACKY 到汇编的转换做一处小改动：在这一遍中，往后端符号表里记录每个函数用哪些硬寄存器传递参数和返回值。

接下来实现寄存器分配器本身。它紧接在程序从 TACKY 转换为汇编之后运行，先于其他所有后端编译遍。与第 19 章实现的优化很相似，这一遍会独立处理每个汇编函数。

即使做了寄存器分配，程序里可能仍有一些伪寄存器留下来。这有几个原因。第一，如果一个函数同时使用大量伪寄存器，硬寄存器可能不够用。这时我们就得把一些伪寄存器溢出到内存。寄存器分配器不会替换被溢出的伪寄存器，只会把它们留在程序里，交给下一遍处理。第二，有些伪寄存器表示具有静态存储期的变量，它们必须待在内存而不是寄存器里。如果你完成了第二部分，还会遇到另外一些必须待在内存里的对象，包括别名变量、结构体和数组。寄存器分配器也不会碰它们。

为了处理这些漏网之鱼，我们会在寄存器分配器之后立刻运行原有的伪操作数替换遍。这个遍不需要任何改动；它会像以前一样处理找到的伪操作数，只是找到的数量会少得多。

接下来，我们更新指令修复遍，让它负责保存和恢复被调用者保存寄存器。所有现有的改写规则——包括生成溢出代码的规则——都保持不变。由于我们仍会把一些伪寄存器替换为内存位置，某些时候仍然需要生成溢出代码。

最后，我们扩展代码生成阶段，以支持本章引入的新硬寄存器。此时你可以先把新的寄存器分配阶段写成桩。然后，我们最后一次更新汇编 AST。

## 扩展汇编 AST

到目前为止，汇编 AST 只包含为特定用途使用的寄存器，比如传参或改写指令。它不包含任何被调用者保存寄存器：RBX、R12、R13、R14 和 R15。现在我们把这五个寄存器加进来，供寄存器分配器使用。我们还会添加 pop 指令，用于在函数末尾恢复被调用者保存寄存器。如果你完成了第二部分，还应该添加其余的 XMM 寄存器，XMM8 到 XMM13。这些寄存器不是被调用者保存的。

注意，pop 只接受寄存器，不接受其他操作数。AST 更新完了，接下来看从 TACKY 到汇编的转换。

## 把 TACKY 转换为汇编

这一遍只有一处改动。我们不改变生成的汇编，只是把额外的信息记录到后端符号表。具体来说，我们要记录每个函数的参数分别用哪些寄存器传递。下一节会看到，寄存器分配器需要这些信息来判断哪些硬寄存器和伪寄存器冲突。

假设有如下函数声明：

```c
int foo(int i, int j);
```

我们会记录 foo 的参数通过前两个参数传递寄存器 RDI 和 RSI 传递。即使 foo 定义在别的翻译单元中，我们也要跟踪这个信息，因为在给调用 foo 的函数分配寄存器时会用到它。

如果你完成了第二部分，还应跟踪每个函数的返回值用哪些寄存器传递。给定函数声明

```c
double foo(int i, double d);
```

我们会记录 foo 的参数通过 RDI 和 XMM0 传递，返回值也通过 XMM0 传递。要确定一个函数用哪些寄存器传递参数和返回值，我们使用第 18 章在 classify_parameters 和 classify_return_value 辅助函数中实现的同样逻辑。注意，我们可能会遇到返回类型或参数类型不完整的函数声明。对这些函数记录什么信息都无所谓，因为无论是定义还是调用它们，在当前翻译单元中都是非法的；我们只需在处理它们时不崩溃。最简单的做法就是记录它们不通过寄存器传递任何值。

接下来构建寄存器分配器本身。

## 用图着色做寄存器分配

我们的编译器将把寄存器分配建模为图着色问题。给图着色是指给每个顶点（vertex）分配一个标签（传统上称为「颜色」），使每个顶点与其所有邻居（neighbor）的颜色都不同。如果一个图可以用 k 种或更少的颜色着色，它就是可 k-着色（k-colorable）的。图 20-1 展示了一个 3-着色的图。

*图 20-1：一个 3-着色的图*

（文字描述：若干顶点由边（edge）相连，每个顶点被标上三种颜色之一，且任意一条边两端的顶点颜色互不相同。）

图着色本身就是一个重要的研究领域；数学家从 19 世纪就开始研究如何给图着色了！它与寄存器分配相关，是因为它抓住了把伪寄存器分配给硬寄存器的两个基本约束：可用的硬寄存器数量有限，而且有些寄存器会彼此干涉（interfere），也就是不能占据同一物理位置。如果两个伪寄存器干涉，就必须把它们分配到两个不同的硬寄存器。伪寄存器也可能与硬寄存器干涉，这意味着不能把它分配给那个硬寄存器。

图着色让我们能表达这两类干涉，并以统一的方式处理它们。为了把寄存器分配转化为图着色问题，我们先构建一张寄存器干涉图（register interference graph）：顶点代表伪寄存器和硬寄存器，任意两个干涉的寄存器之间连一条边。然后，我们给图着色，每种颜色对应一个硬寄存器。最后，根据颜色把每个伪寄存器分配给相应的硬寄存器。由于每个寄存器与其所有邻居的颜色都不同，我们绝不会把两个互相干涉的伪寄存器分配到同一个硬寄存器，也绝不会把伪寄存器分配给与它干涉的硬寄存器。

拿清单 20-10 中的汇编函数试试这个技术。

```asm
divide_and_subtract:
  ❶ movl    %edi, %a
  ❷ movl    %esi, %b
    movl    %a, %eax
  ❸ cdq
    idivl   %b
  ❹ movl    %eax, %tmp
    subl    %b, %tmp
    movl    %tmp, %eax
    ret
```

*清单 20-10：一个小的汇编函数*

这个函数接受两个参数，把它们复制进伪寄存器 a 和 b。它计算 a / b - b，把结果存进 tmp，最后在 EAX 中返回 tmp 的值。我们需要弄清这个函数里哪些寄存器干涉，以便构建干涉图。首先，很容易看出 a 和 b 干涉。如果把它们映射到同一个硬寄存器，定义 b ❷ 时就会破坏 a。这是个问题，因为此时 a 仍然是活跃的（live）。你在第 19 章学过：如果一个变量的当前值可能在此后的程序中被使用，它就是活跃的，否则就是死的。这个定义同样适用于寄存器。寄存器活跃时，我们必须保留它的值，所以不能在同一位置存放别的值。寄存器死了，就可以随意用别的值覆盖它。这给了我们一条检测干涉的简单规则：如果在更新其中一个寄存器时另一个是活跃的，这两个寄存器就干涉。

这条规则还告诉我们 b 与 tmp 干涉，因为定义 tmp ❹ 时 b 是活跃的。但 a 和 tmp 不干涉；定义 tmp 时 a 已经死了，所以把它们映射到同一个硬寄存器没有问题。

接下来想想哪些硬寄存器与伪寄存器干涉。ESI 与 a 干涉，因为定义 a ❶ 时 ESI 是活跃的。如果把 a 映射到 ESI，我们就会在把函数的第二个参数复制到 b 之前把它破坏掉。EAX 与 b 干涉，因为当我们把 a 复制到 EAX 为除法做准备时，b 是活跃的。最后一处干涉不那么明显。记住，cdq 指令把 EAX 的值符号扩展到 EDX ❸。由于 cdq 在 b 活跃时隐式更新 EDX，它使 EDX 与 b 干涉；如果把 b 映射到 EDX，这条指令就会破坏它。（类似地，idiv 指令隐式更新 EAX 和 EDX，所以如果这两个寄存器还没与 b 干涉，这条指令也会使它们与 b 干涉。）

最后，各硬寄存器彼此之间都干涉。这有点同义反复；它们不能占据同一物理位置，因为它们本来代表的就是不同的物理位置。不过，我们仍要在干涉图中体现这一点，以保证每个硬寄存器拿到自己的颜色。

弄清了哪些寄存器干涉之后，我们来构图。为了让图相对小、易读，我们假装仅有的硬寄存器是 EDI、ESI、EAX 和 EDX。真实的寄存器干涉图会包含我们能分配给伪寄存器的每一个硬寄存器，即使汇编程序没有用到它们。但它们会排除 RSP、RBP，以及指令修复期间使用的临时（scratch）寄存器。

图 20-2 给出了清单 20-10 中函数的干涉图。

*图 20-2：divide_and_subtract 的寄存器干涉图*

（文字描述：干涉图的顶点为 a、b、tmp、EDI、ESI、EAX、EDX。干涉关系为：a 与 b 干涉，a 与 ESI 干涉；b 与 tmp、EAX、EDX 干涉；tmp 只与 b 干涉；EDI、ESI、EAX、EDX 两两互相干涉。其余顶点对之间没有边。）

这张图编码了我们刚刚识别出的所有干涉：a 与 ESI 和 b 干涉；b 除 a 外还与 tmp、EAX、EDX 干涉；四个硬寄存器两两干涉。

现在我们尝试对这张图做 k-着色，k 是图中硬寄存器的数量。在这个小例子中 k 为 4。图 20-2 有多种可能的 4-着色，图 20-3 展示了其中几种。

*图 20-3：divide_and_subtract 的寄存器干涉图的三种有效 4-着色*

（文字描述：三种着色都给四个硬寄存器各分配一种互不相同的颜色，并让每个伪寄存器与某个硬寄存器同色。第一种着色中，a 与 EDX 同色、b 与 EDI 同色、tmp 与 EAX 同色；另外两种只是把这些伪寄存器换成不同的硬寄存器组合。）

这些着色中的任何一种——或者我们能想出的任何其他 4-着色——都给出有效的寄存器分配。每个寄存器的颜色都与其任何邻居不同。而且由于 k 个硬寄存器两两干涉，每种颜色恰好分配给一个硬寄存器，从而形成从颜色到硬寄存器的 1:1 映射。

给图着色之后，我们把每个伪寄存器替换为得到相同颜色的硬寄存器。如果采用图 20-3 的第一种着色，就把 a 替换为 EDX、b 替换为 EDI、tmp 替换为 EAX，得到清单 20-11 中的汇编代码。

```asm
divide_and_subtract:
    movl    %edi, %edx
    movl    %esi, %edi
    movl    %edx, %eax
    cdq
    idivl   %edi
    movl    %eax, %eax
    subl    %edi, %eax
    movl    %eax, %eax
    ret
```

*清单 20-11：按图 20-3 的第一种着色替换 divide_and_subtract 中的寄存器*

注意，给图着色产生了两个不同的映射：一个是从所有寄存器到颜色的映射，一个是从颜色到硬寄存器的映射。概念上，每种颜色代表一个硬寄存器，但在给图着色之前我们不知道具体是哪个。如果我们直接用硬寄存器的名字当颜色，或者提前把每个硬寄存器与某种颜色绑定，那么在给图其余部分着色之前，就得先把每个硬寄存器预着色（precolor）成对应的颜色。预着色给图着色问题增加了更多约束，使找到有效着色变得更难。有些图着色的实现要求预着色顶点；好在我们的不需要。

**使用活跃范围而非伪寄存器**

我们的寄存器分配器把伪寄存器映射到硬寄存器。但大多数寄存器分配器解决的是一个稍有不同的问题：它们把活跃范围（live range）映射到硬寄存器。活跃范围是程序中某个伪寄存器活跃的一段区域。同一个伪寄存器可能有多个活跃范围（也就是说，它可能在程序中几段互不相连的区域里活跃）。这些活跃范围可以安全地分配给不同的硬寄存器。来看一个简单（尽管不太现实）的例子：

```asm
two_live_ranges:
  ❶ movl    $1, %x
    addl    %x, var(%rip)
  ❷ movl    $2, %x
    movl    %x, %eax
    ret
```

在这个例子中，x 有两个活跃范围。第一个从定义 x ❶ 开始，到下一条指令把它加到静态变量 var 上之后结束。第二个从重新定义 x ❷ 开始，到紧接着使用它的那条指令之后结束。把程序改写为显式引用这两个活跃范围：

```asm
two_live_ranges:
    movl    $1, %x.1
    addl    %x.1, var(%rip)
    movl    $2, %x.2
    movl    %x.2, %eax
    ret
```

现在很清楚，我们不需要把 x.1 和 x.2 分配到同一个硬寄存器。典型的寄存器分配器一开始会识别每个伪寄存器的各个活跃范围，并给每个活跃范围单独命名，就像我们刚才对 two_live_ranges 做的那样。然后它把这些活跃范围（而不是伪寄存器）作为干涉图中的顶点。这减少了分配器放置每个活跃范围时所受的约束，使找到有效的寄存器分配更容易。

我们构建的是不识别活跃范围的简化版寄存器分配器，所以直接用原始汇编代码中的伪寄存器作为干涉图的顶点。（容易混淆的一点是，识别活跃范围并不完全等同于我们在第 19 章讨论的活性分析（liveness analysis）。我们的分配器会执行活性分析来得知每个寄存器何时活跃，但识别活跃范围是一个更复杂的过程，活性分析只是其中的第一步。）

如果你想构建一个使用活跃范围而非伪寄存器的更复杂寄存器分配器，可以在第 669 页的「延伸资源」中找到几篇有用的参考文献。

### 检测干涉

之前我说过，如果在更新一个寄存器时另一个是活跃的，这两个寄存器就干涉。我们用这条规则判断了 divide_and_subtract 中哪些寄存器干涉；它帮我们识别了伪寄存器之间的干涉以及伪寄存器与硬寄存器之间的干涉。但关于这条规则还有两个要点需要讲。

第一点：只有在更新其中一个寄存器之后另一个立刻活跃时，两个寄存器才干涉。下面是个简短的例子：

```asm
movl    4(%rdi), %x
movl    %x, %eax
ret
```

在这段代码中，RDI 持有某个内存地址——大概是某个结构体或数组的地址。这段代码的第一条指令把内存中 RDI + 4 处存储的值复制进 x。在这条指令之前，RDI 是活跃的；之后就死了。RDI 和 x 不干涉。如果把 x 映射到 RDI，第一条 mov 指令会覆盖 RDI 中的地址。但这没有关系，因为我们不会再使用那个地址。

第二点：只有当两个寄存器的值不同时，它们才干涉。具体来说，指令 mov src, dst 不会使 src 和 dst 干涉，即使此后 src 仍然活跃。例如在清单 20-12 中，x 和 y 不干涉。

```asm
movl    $1, %y
movl    %y, %x
addl    %x, %ecx
addl    %y, %eax
```

*清单 20-12：mov 指令的源操作数在该指令之后仍然活跃的汇编片段*

如果把 x 和 y 分配到同一个硬寄存器，第二条 mov 指令不会用新值覆盖 x，而是完全不产生任何效果。等我们做寄存器合并时，甚至会有意把 x 和 y 放进同一个寄存器，以便把这条指令整个删掉。

由 mov 指令连接的两个寄存器仍可能因为别的原因干涉，如清单 20-13 所示。

```asm
movl    $1, %y
movl    %y, %x
addl    $1, %y
addl    %x, %y
```

*清单 20-13：后续指令使 mov 指令的两个操作数发生干涉的汇编片段*

在这段代码中，第二条 mov 指令没有使 x 和 y 干涉，但随后的 add 指令使它们干涉了，因为它在 x 活跃时更新了 y。在这种情况下，把 x 和 y 放进同一个寄存器是不安全的。

## 基本寄存器分配器

现在我们对寄存器分配器的工作方式有了大致了解，来实现它吧！清单 20-17 描述了如何为单个函数分配寄存器。

```text
allocate_registers(instructions):
    interference_graph = build_graph(instructions)
    add_spill_costs(interference_graph, instructions)
    color_graph(interference_graph)
    register_map = create_register_map(interference_graph)
    transformed_instructions = replace_pseudoregs(instructions, register_map)
    return transformed_instructions
```

*清单 20-17：顶层寄存器分配算法*

我们先构建干涉图。然后基于每个寄存器的使用频率计算溢出代价，并把这一信息标注到图上。接着给图着色，为每个顶点标注颜色。如果无法给每个顶点着色，就用上一步算出的溢出代价来决定溢出什么。要溢出一个顶点，只需让它保持未着色。

最后一步是替换所有着了色的伪寄存器。在 create_register_map 中，我们构造一个从着色伪寄存器到同色硬寄存器的映射。最后改写函数体，把每个伪寄存器替换为映射中相应的硬寄存器。

先把 allocate_registers 写成桩吧。然后我们逐个实现这些步骤。

### 寄存器分配期间处理多种类型

如果你完成了第二部分，就需要把清单 20-17 的整个算法运行两遍：一遍分配通用寄存器，一遍分配 XMM 寄存器。每一遍运行时，只在干涉图中包含相应类型的寄存器。第二部分的新特性还会改变构建干涉图的其他一些细节。到实现 build_graph 时再仔细看这些变化。

构建干涉图之后的各个步骤——包括计算溢出代价、给图着色、替换伪寄存器——无论处理的是浮点寄存器还是通用寄存器都完全一样。第二部分的其他特性也不会影响这些步骤。

### 定义干涉图

先定义干涉图的数据结构。清单 20-18 给出一种可行的表示。

```text
node = Node(operand id, operand* neighbors, double spill_cost, int? color, bool pruned)
graph = Graph(node* nodes)
```

*清单 20-18：寄存器干涉图的定义*

图中每个顶点对应汇编 AST 中的一个 Pseudo 或 Register 操作数。我们要跟踪每个顶点的邻居、溢出代价和颜色。颜色用整数 1 到 k 表示，k 是可用硬寄存器的数量。color 字段是可选的，因为我们可能无法给每个顶点着色。pruned 标志要到给图着色时才会用到，在那之前可以忽略。创建新顶点时，应把 spill_cost 初始化为 0.0、color 初始化为 null、pruned 初始化为 False。

这里的 node 定义比实际需要的更宽松；operand 类型包含常量和内存位置，而我们绝不会把它们加进干涉图。你也可以用只能表示寄存器的专用 node_id 类型来替代 operand。我采用更宽松的定义，是为了不必在整个分配器中来回转换 operand 和 node_id。

### 构建干涉图

终于可以构建干涉图了！我们先走一遍支持第一部分汇编 AST 的 build_graph 实现，然后讨论如何修改它以支持第二部分的汇编 AST。

构建这张图的过程相当繁琐，我们把它拆成几步。清单 20-19 用伪代码展示这些步骤。

```text

  ❷ add_pseudoregisters(interference_graph, instructions)
    cfg = make_control_flow_graph(instructions)
  ❸ analyze_liveness(cfg)
  ❹ add_edges(cfg, interference_graph)

```

*清单 20-19：构建干涉图*

我们从一个包含所有硬寄存器的图开始 ❶。（据我所知，这种图没有标准术语，我就叫它基础图（base graph）。）接着，为函数中出现的每个伪寄存器插入一个顶点 ❷。最后，弄清哪些寄存器互相干涉。由于这取决于每个时刻哪些寄存器活跃，我们需要对汇编代码执行活性分析。与第 19 章一样，这个分析接受一张控制流图（它与干涉图不是一回事！），并用活性信息标注它 ❸。最后，我们利用这些信息确定往干涉图里加哪些边 ❹。下面仔细看每一步。

#### 把伪寄存器加入图

这一步很直白：遍历每条指令的每个操作数，判断是否把它加入图。汇编函数中出现的每个伪寄存器都应进图，具有静态存储期的除外。add_pseudoregisters 的伪代码我就省了，没什么可写的。

#### 活性分析

我们已经知道活性分析的工作原理，第 19 章就实现过。现在需要一个新的实现，分析的是汇编而不是 TACKY，跟踪的是寄存器而不是变量。好在基本逻辑相同，甚至可以复用一些现有代码。

首先构建控制流图。这与从 TACKY 函数构建控制流图完全一样，只是基本块边界处的具体指令不同：我们不再寻找 Label、Return、Jump、JumpIfZero 和 JumpIfNotZero 这些 TACKY 控制流指令，而是寻找它们对应的汇编指令：汇编的 Label 指令、Ret、Jmp 和 JmpCC。你已经写过把 TACKY 转换为控制流图的代码；理想情况下，可以重构它使其也能处理汇编。

接下来看活性分析本身的三个组成部分：迭代算法、汇聚算子和传递函数。迭代算法与第 19 章的一模一样，你应该能直接使用已写好的实现。

汇聚算子仍用集合并集。不过，我们要换一种方式处理控制流图中的 EXIT 节点。原来的汇聚算子假定函数退出时静态变量是活跃的。现在我们不再关心静态变量，因为它们不在干涉图里。我们要担心的是硬寄存器：特别是持有函数返回值的 EAX。清单 20-20 定义了新的汇聚算子，相对清单 19-24 中定义的原汇聚算子的唯一改动以粗体标出。

```text
meet(block):
    live_registers = {}
    for succ_id in block.successors:
        match succ_id with
        | EXIT -> live_registers.add(Reg(AX))
        | ENTRY -> fail("Malformed control-flow graph")
        | BlockId(id) ->
            succ_live_registers = get_block_annotation(succ_id)
            live_registers.add_all(succ_live_registers)

    return live_registers
```

*清单 20-20：汇编代码活性分析的汇聚算子*

我们忽略了被调用者保存寄存器在 EXIT 也是活跃的这一事实。我们可以这样做，因为如果我们最终用到了这些寄存器，指令修复遍会把它们「溢出」——也就是说，在函数开头把它们的值保存到栈上，返回前再恢复。假定这些寄存器在 EXIT 是死的，我们才真的能用它们。如果把它们加到这里的活动寄存器集合中，我们会得出结论：它们在整个函数中都活跃，而且与每一个伪寄存器干涉。

传递函数是活性分析中与上一章差异显著的部分。基本思想相同：使用时把寄存器加入活跃集合，更新时移除。但具体细节不同，因为我们处理的指令集和以前不一样。

首先写一个辅助函数 find_used_and_updated，告诉我们每条指令使用和更新哪些操作数。接下来要实现的传递函数和 add_edges 函数都会用到它。清单 20-21 给出 find_used_and_updated 的伪代码。

```text
find_used_and_updated(instruction):
    match instruction with
    | Mov(src, dst) -> ❶
        used = [src]
        updated = [dst]
    | Binary(op, src, dst) -> ❷
        used = [src, dst]
        updated = [dst]
    | Unary(op, dst) ->
        used = [dst]
        updated = [dst]
    | Cmp(v1, v2) ->
        used = [v1, v2]
        updated = []
    | SetCC(cond, dst) ->
        used = []
        updated = [dst]
    | Push(v) ->
        used = [v]
        updated = []
    | Idiv(divisor) ->
        used = [divisor, Reg(AX), Reg(DX)]
        updated = [Reg(AX), Reg(DX)]
    | Cdq ->
        used = [Reg(AX)]
        updated = [Reg(DX)]
    | Call(f) ->
        used = <在后端符号表中查找参数传递寄存器> ❸
        updated = [Reg(DI), Reg(SI), Reg(DX), Reg(CX), Reg(R8), Reg(R9), Reg(AX)]
    | _ ->
        used = []
        updated = []
    return (used, updated)
```

*清单 20-21：识别每条指令使用和更新的操作数*

记住，这份清单只涵盖第一部分的汇编指令。Mov 最直白：使用源、更新目的 ❶。add src, dst 这样的二元指令使用源和目的、更新目的 ❷。Unary、Cmp、SetCC 和 Push 指令读取和更新哪些操作数也一目了然。

有些指令会使用它们没有明确提及的寄存器。Idiv 用源操作数去除存放在 EAX 和 EDX 中的值，所以它使用全部三个值；它把结果存进 EAX 和 EDX，所以更新这两个寄存器。Cdq 把 EAX 符号扩展到 EDX，也就是使用 EAX、更新 EDX。

Call 使用持有被调函数参数的寄存器；我们可以在后端符号表里查到它们——汇编生成遍时我们把它们记录在了那里 ❸。它更新所有调用者保存（caller-saved）寄存器——无论是否用它们传递被调函数的参数——因为被调函数可能破坏这些寄存器。这使得所有调用者保存寄存器与调用函数时活跃的任何伪寄存器干涉，于是我们的图着色算法会把这些伪寄存器分配给被调用者保存寄存器。

如果一条指令既使用又更新同一个寄存器——比如 Binary 指令既使用又更新其目的操作数——务必把该寄存器同时放进 used 和 updated 两个列表。在传递函数中，我们只关心它被使用，因为那使它活跃。而在 add_edges 中再次使用这个辅助函数时，我们只关心它被更新，因为那使它干涉同一时刻活跃的其他寄存器。

现在可以写传递函数了，见清单 20-22。

```text
transfer(block, end_live_registers):
    current_live_registers = end_live_registers

    for instruction in reverse(block.instructions):
      ❶ annotate_instruction(instruction, current_live_registers)
      ❷ used, updated = find_used_and_updated(instruction)
        for v in updated:
            if v is a register:
                current_live_registers.remove(v)

        for v in used:
            if v is a register:
                current_live_registers.add(v)

  ❸ annotate_block(block.id, current_live_registers)
```

*清单 20-22：汇编活性分析的传递函数*

这是逆向分析，所以按逆序分析汇编指令。处理一条指令时，先记录紧随其后活跃的寄存器 ❶，再计算紧挨在它之前活跃的寄存器。我们调用刚写的辅助函数确定它使用和更新哪些操作数 ❷，然后从当前活跃寄存器集合中移除它更新的寄存器，加入它使用的寄存器。（如果一条指令使用并更新同一个寄存器，我们会先把它从活跃集合中移除，紧接着再加回来。）处理完每条指令后，记录块开头活跃的寄存器 ❸。

我们不跟踪常量和内存操作数，但活跃寄存器集合可能仍包含一些我们不关心的操作数（具体来说，就是具有静态存储期的伪寄存器）。把它们留在活性分析结果里没什么坏处；下一步使用这些结果时忽略它们即可。

#### 添加边

有了活性信息，终于可以确定往图里加哪些边了。清单 20-23 给出这步的伪代码。

```text
add_edges(liveness_cfg, interference_graph):
    for node in liveness_cfg.nodes:
        if node is EntryNode or ExitNode:
            continue

        for instr in node.instructions:
            used, updated = find_used_and_updated(instr)

          ❶ live_registers = get_instruction_annotation(instr)

            for l in live_registers:
              ❷ if (instr is Mov) and (l == instr.src):
                    continue

                for u in updated:
                  ❸ if (l and u are in interference_graph) and (l != u):
                        add_edge(interference_graph, l, u)
```

*清单 20-23：向干涉图添加边*

我们之前学到：更新一个寄存器时另一个活跃，二者就干涉。现在逐条查看指令，确定它产生了哪些干涉。处理单条指令时，先调用 find_used_and_updated 查出它更新哪些操作数。（这个函数返回的第一个列表 used 会被忽略，因为我们不关心指令使用了什么。）然后查出该指令紧随其后活跃的寄存器 ❶。

接着，在 live_registers 中的每个寄存器与 updated 中的每个寄存器之间添加边。Mov 指令是特例：如果当前指令是 Mov，在遍历活跃寄存器集合时要跳过它的源，避免在源和目的之间加边 ❷。

在两个顶点之间加边之前，要确认两个顶点都已在干涉图中。还要确认它们不同，因为我们不想从一个顶点到它自己加边 ❸。

#### 构建图时处理其他类型

现在处理第二部分添加的所有特性。由于 XMM 寄存器和通用寄存器是分开分配的，我们要构建两张干涉图，从每个寄存器类别各自的基础图开始。XMM 寄存器的基础图有 14 个顶点，包含 XMM0 到 XMM13，但不包含临时寄存器 XMM14 和 XMM15。在 add_pseudoregisters 中，把伪寄存器加入图之前要检查它的类型。分配 XMM 寄存器时，只把 Double 类型的伪寄存器加入图。分配通用寄存器时，排除 Double 伪寄存器，包含其余所有标量类型：Longword、Quadword 和 Byte。

浮点寄存器之外，还有一些细节要改。别名伪寄存器不应被分配到寄存器，所以要把它们从图中排除。这里可以复用上一章的取地址分析：只需在程序从 TACKY 转换为汇编之前重新执行该分析。如果一个变量在 TACKY 程序中是别名变量，它在汇编中仍然是。

活性分析要体现第二部分实现的新调用约定。meet 函数不能假定函数退出时 EAX 活跃；它应查询后端符号表，得知函数用哪些寄存器传递返回值。这些寄存器在 EXIT 都是活跃的。

我们还要更新 find_used_and_updated 辅助函数。首先，它需要正确处理 Memory 和 Indexed 操作数。这些操作数指定内存位置，但地址计算中使用了寄存器。使用这类操作数时，我们读取它引用的寄存器，即使写的是它指定的内存位置。例如，指令 movl $1, 4(%rax) 使用 RAX 而不是更新它；指令 leaq (%rax, %rcx, 4), %rdi 同时使用 RAX 和 RCX，更新 RDI。其次，find_used_and_updated 必须识别所有 XMM 寄存器都是调用者保存的，因此会被 Call 指令更新。最后，这个函数要处理第二部分新增的所有汇编指令，不过没什么特别棘手的。

### 计算溢出代价

构建图之后，我们为每个寄存器标注溢出代价。如果无法给图中每个顶点着色，这些代价将帮助我们决定溢出哪个（或哪些）顶点。我们会尝试以最小化所有被溢出顶点总代价的方式给图着色。

硬寄存器不能溢出，所以我们给每个硬寄存器赋无穷大的溢出代价。要估计每个伪寄存器的溢出代价，只需数它在汇编代码中出现的次数。例如，遇到指令 movl $1, %x，就把 x 的溢出代价加一；看到指令 addl %x, %x，就把 x 的溢出代价加二。理由是：伪寄存器使用得越频繁，溢出它所引入的内存访问和新指令就越多。

坦白说，这种计算溢出代价的方式很糟糕。它忽略了一个基本事实：有些指令比另一些执行得更频繁。显然，在一个执行一百万次的循环里使用伪寄存器，其溢出代价应该比在只执行一次的指令中使用大得多。很难精确预测某条指令会执行多少次，但一种办法是用循环嵌套深度粗略代替执行频率。采用这种做法的编译器在计算溢出代价时，会给更深嵌套循环中的指令赋更大的权重。

可惜，我们完全不知道程序里的循环在哪里。发现循环需要实现一种全新的分析，而本章已经够长了。如果你想自己实现这种分析，我在第 669 页的「延伸资源」里列了几篇关于识别循环的参考文献。

### 给干涉图着色

到了给图着色的时候！我们的目标是最小化未着色顶点的总溢出代价（理想情况是给每个顶点都着上色，使总溢出代价为零）。但精确图着色算法——寻找最优着色的那种——在实践中太慢。我们改用近似算法。它未必找到最优着色，但通常能找到相当不错的。

我们的图着色算法基于一个简单的观察：总能给邻居数少于 k 的顶点着色，因为总存在至少一种它的邻居都没使用的颜色。这个观察称为 degree < k 规则。（顶点的邻居数称为它的度（degree）；如果一个顶点有 k 个或更多邻居，就说它具有显著度（significant degree）。）degree < k 规则给了我们分解问题的方法。首先，临时移除任何邻居数少于 k 的顶点，这称为对图剪枝（pruning）。然后，用某种方式给图其余部分着色（暂时先不管怎么做）。最后，把剪掉的顶点逐个放回。放回一个顶点时，给它分配一种不与任何已着色邻居冲突的颜色。由于每个顶点的邻居数少于 k，总会有至少一种可用颜色。

#### 处理溢出

对许多干涉图，我们都可以用上一节的方法剪掉所有顶点，无需任何溢出就能给图着色。但也有另一些图会卡住：某个时刻每个顶点都有 k 个或更多邻居。假设我们想对图 20-12 做 3-着色。

*图 20-12：一张每个顶点都有三个或更多邻居的图*

（文字描述：图中每个顶点的度数都不小于三，无法直接应用 degree < k 规则。）

如果尝试剪这张图，立刻就会卡住：每个顶点都至少有三个邻居！为了脱困，我们仍然选一个顶点剪掉。把它放上栈，然后照常继续算法。这个顶点是溢出候选（spill candidate），因为放回时我们可能无法给它着色。如果走运，它的邻居不会用光所有颜色，我们就能给它着色；如果不走运，它的邻居会用完全部 k 种颜色，我们就只能溢出它。

我们想选溢出代价低的候选。但我们也想选未剪掉邻居众多的候选，因为剪掉我们的溢出候选会降低其邻居的度数，帮助我们避免稍后溢出它们。为了平衡这两个目标，我们选择 spill cost / degree 值最小的顶点，其中 degree 是尚未剪掉的邻居数。

注意，我们绝不会选硬寄存器作为溢出候选，因为它们的 spill cost / degree 永远是无穷大。只要图中还有伪寄存器，我们总会选伪寄存器而不是硬寄存器作为候选。如果伪寄存器都没了，寄存器总数必然是 k 个或更少，一定能把每个寄存器都剪掉。

有些图不存在有效的 k-着色，这让溢出在所难免。对另一些图，有效着色存在，但能否找到全凭运气：它取决于从图中移除顶点的确切顺序，以及放回它们时恰好怎么着色。

这一次我们把 A 和 E 分配了相同的颜色，从而能给 C 着色而不必溢出。在这么小的例子里，很容易看出给这些顶点分配相同颜色是更好的选择。但没有一种通用规则能帮我们避免图 20-13 那种不必要的溢出；这正是该算法是近似算法的原因。如果改用精确算法，可以避免不必要的溢出，但如前所述，精确算法代价太高，不实用。

#### 实现图着色算法

用这个算法做过几个例子之后，来看伪代码，见清单 20-24。

```text
color_graph(g):
    remaining = <g 中未剪枝的顶点>
  ❶ if remaining is empty:
        return

    // 选择下一个要剪枝的顶点
    chosen_node = null

    for node in remaining:
        degree = length(<顶点的未剪枝邻居>)
        if degree < k:
          ❷ chosen_node = node
            break

    if chosen_node is null:
        // 选择溢出候选
        best_spill_metric = infinity
        for node in remaining:
            degree = length(<顶点的未剪枝邻居>)
            spill_metric = node.spill_cost / degree
            if spill_metric < best_spill_metric:
              ❸ chosen_node = node
                best_spill_metric = spill_metric

    chosen_node.pruned = True

    // 给图其余部分着色
  ❹ color_graph(g)

    // 给这个顶点着色
    colors = [1, 2, . . ., k]
    for neighbor_id in chosen_node.neighbors:
        neighbor = get_node_by_id(g, neighbor_id)
        if neighbor.color is not null:
            colors.remove(neighbor.color)

  ❺ if colors is not empty:
        if chosen_node is a callee-saved hard register:
            chosen_node.color = max(colors)
        else:
            chosen_node.color = min(colors)
        chosen_node.pruned = False

    return
```

*清单 20-24：图着色算法*

我们递归地给图着色。每一步先剪掉一个顶点，递归调用去给图其余部分着色，然后把顶点放回并着色。在基线情形中，所有顶点都已剪掉，无事可做 ❶。

在递归情形中，先选一个要剪的顶点，这份清单称之为 chosen_node。我们选第一个找到的未剪枝邻居少于 k 个的顶点 ❷。（如果分配的是通用寄存器，k 为 12；如果分配 XMM 寄存器，k 为 14。）如果这个搜索落空，就选 spill cost / degree 值最小的顶点 ❸。剪枝只需把顶点的 pruned 属性设为 True。然后递归调用 color_graph 给图中其余顶点着色 ❹。

从递归调用返回后，我们尝试给 chosen_node 分配颜色。取整数列表 1 到 k（代表所有可能颜色），删掉已分配给 chosen_node 某个邻居的颜色。chosen_node 的某些邻居可能没有颜色——要么因为被溢出，要么因为比 chosen_node 先剪掉、要稍后才着色——这些顶点直接忽略即可。

如果列表中还有颜色，就把其中一种分配给 chosen_node ❺。如果可用颜色不止一种，算法并不挑剔选哪种。虽然这里选的颜色可能影响最终溢出多少个顶点，但这种影响不可预测；不存在能全面最小化溢出的选色策略。所以，我们带着另一个目标选色：让伪寄存器优先分配到调用者保存而不是被调用者保存的硬寄存器。（我们希望尽量少用被调用者保存寄存器，以省去保存和恢复它们的开销。）当 chosen_node 代表被调用者保存的硬寄存器时，我们给它分配编号最大的可用颜色；否则分配编号最小的可用颜色。采用这一策略，着色算法倾向于把编号较大的颜色分给被调用者保存寄存器，把编号较小的颜色分给调用者保存寄存器和伪寄存器。只有在没有更小编号的颜色可用时（例如它和每个调用者保存寄存器都冲突），伪寄存器才会拿到较大编号的颜色。选好颜色后，把 pruned 属性设回 False。这并非必须——我们不会再用这个属性——但它标记该顶点已放回图中。

如果列表中没有颜色了，就只能溢出 chosen_node。具体来说，就是不给它分配颜色。我们也不更新它的 pruned 属性，因为不把它放回图。注意，我们没有显式地把顶点压栈、弹栈。递归算法自然地按正确顺序给顶点着色，从最后剪掉的顶点开始。

### 构建寄存器映射并改写函数体

图着色完成后，寄存器分配器的其余部分就相当简单了。我们构建一个从伪寄存器到硬寄存器的映射，用它来替换汇编代码中的伪寄存器。构建映射的同时，我们还要记录用到了哪些被调用者保存寄存器，以便在指令修复遍中保存和恢复它们。清单 20-25 演示如何构造该映射。

```text
create_register_map(colored_graph):

    // 构建从颜色到硬寄存器的映射
    color_map = <空映射>
    for node in colored_graph.nodes:
        match node.id with
        | Reg(r) ->
            color_map.add(node.color, r)
        | Pseudo(p) -> continue

    // 构建从伪寄存器到硬寄存器的映射
    register_map = <空映射>
    callee_saved_regs = {}
    for node in colored_graph.nodes:
        match node.id with
        | Pseudo(p) ->
            if node.color is not null:
              ❶ hardreg = color_map.get(node.color)
                register_map.add(p, hardreg)
                if hardreg is callee saved:
                  ❷ callee_saved_regs.add(hardreg)
        | Reg(r) -> continue

  ❸ record_callee_saved_regs(<当前函数名>, callee_saved_regs)

    return register_map
```

*清单 20-25：构建从伪寄存器到硬寄存器的映射*

首先遍历图中的硬寄存器，构建从颜色到硬寄存器的映射。记住，颜色与硬寄存器之间是 1:1 映射，因为 k 个硬寄存器中的每一个都必须分配到 k 种可能颜色中互不相同的一种。接着遍历所有伪寄存器。如果某个伪寄存器被分配了颜色，就把它映射到同色的硬寄存器，可以在 color_map 里查到 ❶。如果没被分配颜色，就不加入映射。

构建 register_map 的同时，我们记录这个函数将使用的被调用者保存寄存器集合。每当添加一条从伪寄存器到被调用者保存硬寄存器的映射，就把该硬寄存器加入集合 ❷。我们要记录每个函数的 callee_saved_regs 集合，以便把这个信息传递给指令修复阶段 ❸。（这份清单没有指明记录到哪里；你可以把它放进函数定义本身、后端符号表或其他数据结构，怎么方便怎么来。）分配 XMM 寄存器时可以跳过这一步，因为没有 XMM 寄存器是被调用者保存的。

最后改写汇编代码：把每条指令中的每个伪寄存器替换为寄存器映射中相应的硬寄存器。映射里没有的伪寄存器保持不变。顺便，我们删除源和目的最终落在同一硬寄存器的 mov 指令。例如，如果 tmp1 和 tmp2 都映射到 EAX，就可以把

```asm
my_fun:
    movl    %edi, %tmp1
    addl    $5, %tmp1
  ❶ movl    %tmp1, %tmp2
  ❷ movl    %tmp2, %eax
    ret
```

改写为：

```asm
my_fun:
    movl    %edi, %eax
    addl    $5, %eax
    ret
```

❶ 和 ❷ 都会被改写成 movl %eax, %eax，毫无作用，所以都可以从最终汇编程序中删掉。

这种删除多余 mov 指令的收尾工作与寄存器合并有关，本章稍后会实现它。但两者有一些重要区别。寄存器合并会刻意把由 mov 连接的寄存器（如 tmp1 和 tmp2）合并到一起，然后删除它们之间的 mov 指令。这整个过程发生在给图其余部分着色之前。我们在这里做的要简单得多：并不试图合并寄存器，但如果碰巧给一条 mov 指令的两个操作数分配了相同的颜色，我们就顺手利用一下。

即使实现了寄存器合并，这种着色后的清理仍然有用。稍后会看到，寄存器合并遍并不完美；有时会漏掉一对本来值得合并的寄存器。如果我们运气好，给这对寄存器分配了相同的颜色，最后这一步仍能删掉它们之间的 mov 指令。

到这里，我们就有了一个能用的寄存器分配器！只需在测试之前更新指令修复和代码生成遍。

## 带被调用者保存寄存器的指令修复

如果函数使用了任何被调用者保存寄存器，我们需要在函数开头保存它们的值、在结尾恢复。保存方式是把它们压入当前栈帧其余部分之上的栈中。例如，某函数需要 16 字节栈空间存放局部变量，并且使用了 R12 和 R13，我们就在函数体最开头插入下面三条指令：

```text
Binary(Sub, Quadword, Imm(16), Reg(SP))
Push(Reg(R12))
Push(Reg(R13))
```

最开始的 Sub 指令分配当前栈帧，与前几章相同。新的 Push 指令紧随其后。（如果你跳过了第二部分，第一条指令会是 AllocateStack 而不是 Sub。）

返回之前，通过出栈恢复这些寄存器的值，也就是把函数中的每条 Ret 指令改写为：

```text
Pop(R13)
Pop(R12)
Ret
```

被调用者保存寄存器可以按任意顺序压栈，但必须按相反的顺序出栈，保证每个寄存器最终恢复原值。由于函数尾声的其余部分是在代码生成阶段添加的，我们最终会在恢复被调用者保存寄存器之后立刻释放栈帧：

```asm
popq    %r13
popq    %r12
movq    %rbp, %rsp
popq    %rbp
ret
```

我们还得保证整个栈帧——包括保存到栈上的被调用者保存寄存器的值——按 16 字节对齐。假设伪操作数替换遍为某函数的局部变量分配了 20 字节栈空间。通常我们会从 RSP 减去 32 字节来保持正确的栈对齐。但如果该函数使用了一个被调用者保存寄存器，最初就应该减去 24 字节：

```text
Binary(Sub, Quadword, Imm(24), Reg(SP))
Push(Reg(BX))
```

显式从 RSP 减 24 字节，再通过压入 RBX 减去另外 8 字节，总共仍是减 32 字节，所以栈依然正确对齐。清单 20-26 演示了执行这种棘手计算的一种方法。

```text
calculate_stack_adjustment(bytes_for_locals, callee_saved_count):
    callee_saved_bytes = 8 * callee_saved_count
    total_stack_bytes = callee_saved_bytes + bytes_for_locals
  ❶ adjusted_stack_bytes = round_up(total_stack_bytes, 16)
  ❷ stack_adjustment = adjusted_stack_bytes - callee_saved_bytes
    return stack_adjustment
```

*清单 20-26：把被调用者保存寄存器计入在内的栈空间计算*

在这份清单中，bytes_for_locals 是伪操作数替换期间分配的栈空间字节数，callee_saved_count 是函数使用的被调用者保存寄存器数量。我们先计算被调用者保存的值将占用多少字节，把它与 bytes_for_locals 相加后向上取整到 16 的倍数，得到栈帧总大小 ❶。从这个值倒推，减去被调用者保存的值将占用的字节数，就得到需要显式从 RSP 减去的字节数 ❷。

## 寄存器合并

我们的寄存器分配器已经能正确工作了。但正如本章开头的例子所示，加入合并步骤后，它生成的代码效率会更高。那个早期例子也让我们大致了解了这个过程：逐个查看把值从一个寄存器复制到另一个寄存器的 mov 指令，判断是否合并其源和目的。做出这些决定之后，改写汇编代码：替换被合并的寄存器，删除不再需要的 mov 指令。

为了决定合并哪些寄存器，我们要参考干涉图。当两个条件满足时，我们就合并一对寄存器。第一个条件显而易见：这两个寄存器不能互相干涉。清单 20-13 的例子（重录如下）说明了为什么必须有这个条件：

```asm
movl    $1, %y
movl    %y, %x
addl    $1, %y
addl    %x, %y
```

由于我们在 x 活跃时更新 y，这两个寄存器干涉。如果合并它们，第一条 add 指令会破坏 x，最终算出 2 + 2 而不是 1 + 2。

第二个条件更微妙：只有当合并不会迫使我们溢出更多寄存器时，才合并一对寄存器。要理解合并为什么会导致溢出，看清单 20-27。

```asm
f:
    movl    %edi, %arg
    movl    %arg, %tmp
    addl    $1, %tmp
    imull   %arg, %tmp
    movl    $10, %eax
    subl    %tmp, %eax
    ret
```

*清单 20-27：合并会导致溢出的汇编函数*

这个汇编函数计算 10 - (arg + 1) * arg。在这个例子中，我们假装只有 EDI 和 EAX 两个可用硬寄存器，所以 k 为 2。图 20-15 给出这份清单的干涉图，它显然可 2-着色。

清单 20-27 的第一条 mov 指令看起来是可能的合并候选。（第二条不是，因为 arg 和 tmp 干涉。）但如果试着把 arg 合并进 EDI，就会遇到麻烦。我们最终会得到清单 20-28 中的汇编代码。

现在这张图无法 2-着色了。由于 tmp 与两个硬寄存器都干涉，我们只能溢出它。性能非但没有提升，反而更糟了！把 tmp 溢出到内存的代价，超过了删除一条 mov 指令的收益。为了避免这种情况，我们采用一种叫保守合并（conservative coalescing）的策略：只有当能事先确定合并不会让干涉图更难着色时，才合并两个寄存器。不过在深入保守合并之前，我们需要学习如何让干涉图保持最新。

### 更新干涉图

每当我们决定合并一对寄存器，都要更新干涉图；否则，后续的合并决定就会基于错误的信息。执行这种更新有两种方式。第一种是立刻改写汇编代码并从头重建图。问题在于构建干涉图很慢。单个函数中我们可能合并几十甚至几百条 mov 指令，但重建几百次干涉图的开销承受不起。

快得多的方法是在现有干涉图中直接把两个顶点合并，不回溯汇编代码。图 20-17 中，我们用这个方法把伪寄存器 tmp2 合并进 EAX。

*图 20-17：更新干涉图以反映合并决定*

（文字描述：合并前，tmp2 与 EAX 各有各的邻居；合并后，tmp2 的每条边都改为连向 EAX，tmp2 顶点从图中移除。）

我们假定原本与 tmp2 干涉的任何寄存器现在都与 EAX 干涉。要让干涉图反映这个变化，只需把 tmp2 的每个邻居连一条边到 EAX，然后移除 tmp2。

但这种更新图的方式也有问题：它并不总是准确！图中可能出现一些寄存器之间的多余边，而它们其实并不干涉。清单 20-29 给了个有点做作的例子。

```asm

    movl    %edi, %tmp2
    addl    %tmp1, %tmp2
    movl    %tmp2, %eax
    ret
```

*清单 20-29：把第一个参数复制到两个不同伪寄存器的函数*

注意 tmp1 和 tmp2 干涉：第二条 mov 指令在 tmp1 仍然活跃时更新 tmp2。我们来试着把 tmp1 合并进 EDI，并用这种快速、简单的方法相应更新图。图 20-18 展示图将如何变化。

*图 20-18：更新清单 20-29 的干涉图*

（文字描述：把 tmp1 合并进 EDI 后，tmp1 与 tmp2 之间的边变成了 tmp2 与 EDI 之间的边——但实际上，改写代码后 tmp2 与 EDI 并不干涉。）

但当我们真正用 EDI 替换 tmp1 时，会发现它与 tmp2 的干涉消失了！清单 20-30 展示更新后的汇编代码。

```asm

    addl    %edi, %tmp2
```

*清单 20-30：把 tmp1 合并进 EDI 之后的清单 20-29*

我们之前学过，指令 mov src, dst 永远不会使 src 和 dst 干涉。最初，指令 movl %edi, %tmp2 造成了 tmp1 与 tmp2 之间的干涉。现在我们把 tmp1 合并进了 EDI，它就不再造成干涉了。

虽然并不完全准确，我们的快速更新方法仍然有用。它给出真实干涉图的一个保守近似：它包含图中应有的所有顶点和边，但也可能多出几条边。如果这张图告诉我们两个寄存器可以安全合并，那它们肯定安全。但如果只依赖这个方法，我们会错过一些合并机会。比如，只看图 20-18，我们不会意识到可以把 tmp2 合并进 EDI。更糟的是，如果尝试给这张图着色，可能会不必要地溢出寄存器。

所以两种更新方法我们都要用。每次决定合并一对寄存器，就通过合并顶点做一次快速更新。然后，在检查完每条 mov 指令并改写汇编代码之后，从头重建图。我们重复这个「构建-合并」循环，直到再也找不到可合并的寄存器为止。把快速、近似的内层循环与缓慢、精确的外层循环结合起来，可谓两全其美：我们既能抓住每一个合并机会，把准确的干涉图交给着色阶段，又不会在每次合并决定后浪费时间重建图。

### 保守合并

理解了合并如何改变图之后，我们可以推理它何时可能导致溢出。根本问题在于：合并两个顶点后，合并得到的顶点的度数比原来两个都高，这可能使它更难剪枝。它的溢出代价也很可能比原来两个顶点都高，因为它被使用得更频繁。

我们用两个保守合并测试来确保合并得到的顶点在给图着色时不会惹麻烦。Briggs 测试保证我们不会溢出合并后的顶点。George 测试保证我们不会溢出其他任何顶点——除非它们在原图中本来就是潜在的溢出候选。只有当两个伪寄存器通过 Briggs 测试时，我们才合并它们。伪寄存器与硬寄存器之间只要通过两个测试中的任何一个，我们就合并；这种情况下可以更宽松，因为我们已经知道硬寄存器不会溢出。两个测试都以发明者的名字命名；首次提出它们的论文的链接见第 669 页的「延伸资源」。

有必要澄清保守合并测试到底保证了什么，因为这有点反直觉。如果你能在从不选择溢出候选的情况下完全剪枝原图，这些测试保证合并后的图同样如此。这种情况下，我们可以肯定合并不会引起任何溢出。

但如果你无法完全剪枝原图，预测合并的影响就更难了，因为选定溢出候选之后会发生什么，很大程度上取决于运气。本章前面已经见过这样的例子：给图 20-12 着色时，按不同顺序剪枝决定了溢出候选最终是能着色还是真的被溢出。合并寄存器也可能产生类似的连锁反应。如果运气不好，这些效应可能导致一次原本可以避免的溢出。

换句话说，如果给原图着色需要选择溢出候选，给合并后的图着色可能也需要——而到那时，没有任何办法确定接下来会发生什么。在这种情况下，保守合并测试仍然给我们两个宝贵的保证。第一，合并后的顶点本身不会溢出。第二，在卡住、不得不选出第一个溢出候选的那一刻，每个顶点的度数都与我们不做合并而卡住时相同或更低。这意味着，总体而言，与不做合并相比，我们更可能成功剪掉更多顶点、溢出更少。

现在更仔细地看看 Briggs 和 George 测试。我们会定义这两个测试，并走几个例子来演示它们为什么有效。

#### Briggs 测试

记住：如果一个顶点有 k 个或更多邻居，它就具有显著度。Briggs 测试允许我们在合并后顶点的显著度邻居少于 k 个时合并两个顶点。给图着色时，我们能剪掉所有度不显著的邻居；合并后的顶点自身的度也随之变得不显著——它剩下的邻居少于 k 个——于是也能剪掉它。

来看一个例子，考虑图 20-19 中的干涉图。

（文字描述：图中包含 x、y、a、z 以及硬寄存器 ESI、EDI、EAX 等顶点；x 与 y 互不干涉，整张图可以直接剪枝完毕。）

正如这些例子所示，Briggs 测试阻止我们把一张可着色的图变成不可着色的。它还给出另一个保证：如果合并得到的顶点有可能溢出，我们绝不会合并。看看图 20-23。

*图 20-23：不能合并 tmp1 和 tmp2 的干涉图*

假设我们想把 tmp2 合并进 tmp1。这显然不会让图更难着色；它对干涉图的效果与整个删掉 tmp2 一样。但出于另一个原因，合并这两个顶点是个坏主意：无论是否与 tmp2 合并，我们都无法给 tmp1 着色，所以合并只会推高 tmp1 的溢出代价，让情况更糟。

这个例子通不过 Briggs 测试，因为合并后 tmp1 将有三个具有显著度的邻居（与合并前一样）。如果一个顶点可能无法着色，Briggs 测试就不允许合并它。

最后，稍微调整这个例子，来说明 Briggs 测试的一个局限。想象我们改为把 tmp2 合并进 EDI 而不是 tmp1。与上一个例子一样，这不会让图更难着色。它同样通不过 Briggs 测试，因为 EDI 将有三个具有显著度的邻居。但有一个重要区别：EDI 是硬寄存器，不会溢出。这意味着把 tmp2 合并进 EDI 没有任何坏处：它不会迫使我们溢出 EDI，也不会让其他顶点更难着色。在这类情况下，我们将用 George 测试找出 Briggs 测试漏掉的合并机会。

#### George 测试

把伪寄存器与硬寄存器合并时，我们知道合并后的寄存器不会溢出。我们担心的是一种略有不同的后果：如果硬寄存器变得更难剪枝，它的邻居也可能变得更难剪枝。最终，这种变化可能迫使我们溢出原本能着色的顶点。在涉及硬寄存器的情形中，我们会同时使用 Briggs 测试和 George 测试，尽可能多地识别合并机会。Briggs 测试证明我们能剪掉合并后的顶点，因此它不会干扰其他顶点的着色。George 测试证明我们不会让合并后顶点的邻居更难剪枝（因此不会让这些顶点或图其余部分更难着色），即使我们无法剪掉合并后的顶点本身。通过这两个测试中任何一个的顶点对，都可以合并。

George 测试说：如果 p 的每个邻居都满足以下两个条件之一，就可以把伪寄存器 p 合并进硬寄存器 h：

- 它的邻居少于 k 个。
- 它已经与 h 干涉。

如果某个邻居满足第一个条件，给图着色时我们一定能剪掉它。如果满足第二个条件，合并后它的邻居与之前完全相同（除 p 之外），所以我们没有让它更难剪枝；说不定还变容易了。

合并 h 和 p 也不会让 h 的任何邻居更难剪枝。唯一可能的途径是阻止我们剪掉 h 本身，但 h 通过合并获得的任何新邻居的度都不显著，所以不会影响我们剪掉 h 的能力。

再来看图 20-23 的干涉图，理解这为什么成立：

之前我们判断把 tmp2 合并进 EDI 是安全的，因为 EDI 不会溢出，而且这个变化不会让其他任何顶点更难着色。但我们也看到这个情形通不过 Briggs 测试，因为 EDI 将有三个具有显著度的邻居。现在改用 George 测试。这个测试会通过，因为 tmp2 的两个邻居都已与 EDI 干涉。我们的分配器会把 tmp2 合并进 EDI，因为只要通过两个测试之一，它就会合并。

关于 George 测试还有一个糟糕的细节要提。记住，每次合并决定之后，我们都用快速、近似的方法更新图。这种近似方法可能在图中留下一些边，连接实际上并不干涉的寄存器。因此，对寄存器 p 和 h 应用 George 测试时，我们可能以为 p 的某个邻居 n 也与 h 干涉，而实际并非如此。我们可能因此错误地断定 p 和 h 通过了 George 测试并合并它们。

听起来很糟，但它只是稍微削弱了 George 测试提供的保证。之前我声称 George 测试保证不会让合并后顶点的邻居更难剪枝。它实际保证的是：不会让它们比当前这轮合并开始之前——也就是上一次从头重建干涉图时——更难剪枝。

这个较弱的保证仍然成立，因为只有在构建干涉图时 n 确实与 h 干涉、而之后某次合并决定移除了那条干涉的情况下，近似图才会保留 n 与 h 之间的边。本质上，如果先前的某次合并决定通过移除 n 与 h 之间的边让 n 或 h 更容易剪枝，我们可能因为把那条边放回去而意外地让它们又变难剪枝。不过，我们绝不会让事情比当前这轮合并开始之前更糟。（还应记住，Briggs 和 George 测试的目的是提升性能，而不是保证正确性；即使某个「坏」的合并决定两个测试都通不过，也不会改变程序的可观察行为。）

**Briggs 与 George 测试的局限**

Briggs 和 George 测试有一个共同的基本局限：它们都只通过考察顶点及其邻居来猜测能否剪枝，而不考虑邻居的邻居、再往外的邻居，等等。这些信息并不总能让我们识别出最终能剪枝某个顶点。下面的干涉图展示了这个问题：它通不过 Briggs 测试，尽管合并是安全的。

（文字描述：这张图与我们之前讨论 Briggs 测试时看过的图 20-19 相同，只是给 a 增加了一些额外邻居；这些额外邻居的度都很低，可以立刻剪掉。）

这张图与我们讨论 Briggs 测试时的图 20-19 完全相同，只是给 a 加了一些额外邻居。这些额外邻居不影响我们给图着色的能力，因为它们可以立刻全部剪掉。现在试着把 x 合并进 y。

（文字描述：把 x 合并进 y 之后的图：y 有三个具有显著度的邻居：ESI、EDI 和 a。）

很容易看出这张图仍可着色。但它通不过 Briggs 测试，因为 y 现在有三个具有显著度的邻居：ESI、EDI 和 a。如果这个测试再往前走一步，我们会看到 ESI、EDI 和 a 自身的显著度邻居都少于三个，所以它们全都能剪掉——但测试没有走这一步，它在考虑完 y 的直接邻居后就停了。George 测试有一模一样的问题：它会被那些一开始邻居很多、但几轮剪枝后邻居就少于 k 个的顶点绊倒。

提出 George 测试的同一篇论文，提出了一个叫迭代寄存器合并（iterated register coalescing）的算法来克服这一局限。这项技术的要点是：可以在给图剪枝和合并寄存器之间交替进行。一轮剪枝之后，Briggs 和 George 测试往往能识别出之前找不到的合并机会。例如，我们可以先剪掉本框第一个干涉图中度不显著的顶点，再应用 Briggs 测试合并 x 和 y。迭代寄存器合并仍是一种保守方法，所以不会找到每一个合并机会，但能抓住许多我们更简单的策略漏掉的机会。

两种保守合并测试、它们提供的保证以及它们有效的原因，我们都看过了。现在只剩下实现它们。

### 实现寄存器合并

第一项任务是把「构建-合并」循环加入顶层寄存器分配算法。清单 20-31 给出更新后的算法，新增部分以粗体标出。

```text
allocate_registers(instructions):
    while True:
        interference_graph = build_graph(instructions)
        coalesced_regs = coalesce(interference_graph, instructions)
        if nothing_was_coalesced(coalesced_regs):
            break
        instructions = rewrite_coalesced(instructions, coalesced_regs)
    add_spill_costs(interference_graph, instructions)
    color_graph(interference_graph)
    register_map = create_register_map(interference_graph)
    transformed_instructions = replace_pseudoregs(instructions, register_map)
    return transformed_instructions
```

*清单 20-31：把寄存器合并加入顶层寄存器分配算法*

在这个循环中，我们先构建干涉图，然后寻找可合并的寄存器。如果找到，就改写汇编代码并重新开始整个过程；否则退出循环，照常运行分配器的其余部分。

我们用 coalesced_regs 记录哪些寄存器被合并到了一起，它是一种不相交集（disjoint-set）数据结构。我们来写这个数据结构的一个简单实现，然后定义 coalesce 和 rewrite_coalesced 函数。

#### 不相交集

顾名思义，不相交集数据结构表示多个互不相交的值集合，每个集合由一个代表成员标识。不相交集支持两种操作：union 合并两个集合，find 查找某个集合的代表成员。在我们的场景中，集合中的值是 Reg 和 Pseudo 操作数。最初每个寄存器自成一个集合。合并寄存器时，我们用 union 操作把这些集合并到一起。改写汇编代码时，我们用 find 把每个寄存器替换为其所在集合的代表成员。

实现不相交集有几种方法，我们用一种容易理解的简单实现。清单 20-32 定义了我们的实现。

```text
init_disjoint_sets():
  ❶ return <空映射>

union(x, y, reg_map):
 ❷ reg_map.add(x, y)

find(r, reg_map):
 ❸ if r is in reg_map:
        result = reg_map.get(r)
      ❹ return find(result, reg_map)
    return r

nothing_was_coalesced(reg_map):
 ❺ if reg_map is empty:
        return True
    return False
```

*清单 20-32：不相交集的基础实现*

我们用一张映射来跟踪哪些集合被合并到了一起。最初这张映射为空 ❶。要合并代表成员分别为 x 和 y 的两个集合，union 操作插入一条从 x 到 y 的映射 ❷。这使 y 成为新集合的代表成员。把伪寄存器合并进硬寄存器时，务必让硬寄存器充当集合的代表成员；我们不想在稍后改写代码时用伪寄存器替换硬寄存器。

要查找包含寄存器 r 的集合的代表成员，find 操作先检查 r 是否映射到别的寄存器 ❸。如果没有，r 自己就是所在集合的代表成员，直接返回它。否则，在映射中查它得到 result，也就是我们先前把 r 合并进去的那个寄存器，然后递归调用 find ❹，沿映射链从 r 一直走到它的代表成员。例如，先把 a 合并进 b、再把 b 合并进 c，我们会沿着 a 到 b 再到 c 的映射，确定 a 的代表成员是 c。

这份清单中定义的最后一个操作是 nothing_was_coalesced，它只是检查映射是否为空 ❺。

#### coalesce 函数

coalesce 函数逐个查看汇编代码中的 mov 指令，决定合并哪些寄存器，并在刚定义的不相交集结构中记录这些决定。我们来看清单 20-33，它给出这个函数的伪代码。

```text
coalesce(graph, instructions):
    coalesced_regs = init_disjoint_sets()

    for i in instructions:
        match i with
        | Mov(src, dst) ->
          ❶ src = find(src, coalesced_regs)
            dst = find(dst, coalesced_regs)

          ❷ if (src is in graph
                and dst is in graph
                and src != dst
              ❸ and (not are_neighbors(graph, src, dst))
              ❹ and conservative_coalesceable(graph, src, dst)):

                if src is a hard register:
                    to_keep = src
                    to_merge = dst
                else:
                    to_keep = dst
                    to_merge = src

              ❺ union(to_merge, to_keep, coalesced_regs)
                update_graph(graph, to_merge, to_keep)

        | _ -> continue

    return coalesced_regs
```

*清单 20-33：决定合并哪些寄存器*

我们首先初始化一个新的不相交集结构 coalesced_regs，用来跟踪合并了哪些寄存器。然后遍历指令列表。遇到 Mov 指令时，用 find 查出它当前的源和目的 ❶，因为 src 和 dst 可能已经被合并进了别的寄存器。注意，这些操作数可能是常量或内存地址，而不是寄存器。这没有关系；如果 coalesced_regs 里没有 x 的映射，find(x, coalesced_regs) 就返回 x，无论 x 是寄存器还是别的什么操作数。

接下来，我们判断是否合并这条指令的源和目的 ❷。首先检查二者是否都在干涉图中（这可以防止我们试图合并常量或内存操作数）。然后确保它们是两个不同的寄存器，因为没有理由把一个寄存器和它自己合并。这些检查通过后，我们检验之前学到的两个条件：src 和 dst 必须不干涉 ❸，而且合并它们必须不会让图更难着色 ❹。第二个条件用 conservative_coalesceable 函数来检验，稍后回到它。

如果 src 和 dst 满足所有这些条件，就合并它们！现在必须确定汇编代码里保留哪一个、替换哪一个。如果有一个操作数是硬寄存器，就保留它、替换另一个。如果两个都是伪寄存器，就任意地选择保留 dst。我们调用 union 真正执行合并 ❺，然后更新干涉图。清单 20-34 定义了执行这个更新的函数。

```text
update_graph(graph, x, y):

    node_to_remove = get_node_by_id(graph, x)
    for neighbor in node_to_remove.neighbors:
        add_edge(graph, y, neighbor)
        remove_edge(graph, x, neighbor)

    remove_node_by_id(graph, x)
```

*清单 20-34：更新干涉图*

这个函数取出 x 的每个邻居，移除它与 x 之间的边，改为加一条到 y 的边，然后把 x 从图中移除。

#### conservative_coalesceable 函数

coalesce 的其余部分都就位了，来看清单 20-35，它定义了保守合并测试。

```text
conservative_coalesceable(graph, src, dst):

        return True
  ❷ if src is a hard register:

      ❼ if length(neighbor_node.neighbors) < k:

```

*清单 20-35：保守合并测试*

在 conservative_coalesceable 中，我们先试 Briggs 测试 ❶。Briggs 测试失败且 src 或 dst 是硬寄存器时，再试 George 测试 ❷。使用 George 测试时，要确保把硬寄存器作为第一个参数、伪寄存器作为第二个，因为它并不对这两种寄存器一视同仁。

应用 Briggs 测试时，我们先构造 combined_neighbors，也就是与 x 或 y 干涉的顶点集合。然后遍历这个集合，查每个邻居的度 ❸。如果某个顶点与 x 和 y 都干涉，合并 x 和 y 会让它的度减一，所以要相应调整 ❹。如果 combined_neighbors 中具有显著度的顶点少于 k 个，就返回 True ❺。

应用 George 测试时，我们遍历伪寄存器的邻居，确保每个邻居要么与硬寄存器干涉 ❻，要么度不显著 ❼。只要发现一个邻居这两个条件都不满足，就返回 False。如果每个邻居都满足条件，就返回 True。

*清单 20-36：决定合并哪些寄存器之后改写指令*

我们用 find 操作替换每条指令中的每个操作数。（这里和 coalesce 中一样，我们依赖 find 正确处理非寄存器操作数。）如果 Mov 指令更新后的源和目的相同，我们就在改写后的代码中省略这条指令 ❶。一个附带的好处是：这也会删掉那些在合并寄存器之前本来就多余的 Mov 指令。

## 延伸资源

本章构建的寄存器分配器使用的是经典 Chaitin-Briggs 算法的简化版。本节告诉你到哪里找关于这个算法的原始论文、几章以更平易近人的方式介绍它们的教科书章节，以及一些关于更具体主题的其他有用参考文献。

**关键论文**

Gregory Chaitin 等人 1981 年的论文《Register Allocation via Coloring》描述了最初的图着色寄存器分配器（https://doi.org/10.1016/0096-0551(81)90048-5）。它引入了本章的大多数基本概念，包括如何构建干涉图并给它着色。

Chaitin 在 1982 年发表了同一分配器的更新描述《Register Allocation & Spilling via Graph Coloring》（https://doi.org/10.1145/872726.806984）。

Preston Briggs、Keith Cooper 和 Linda Torczon 1994 年的论文《Improvements to Graph Coloring Register Allocation》描述了 Chaitin 设计的一个改进版本（https://doi.org/10.1145/177492.177575）。Chaitin-Briggs 这个名字指的就是这个改进后的算法。这篇论文提出了把溢出候选放上栈、稍后再尝试着色而不是立刻溢出的技术。（Briggs 等人把这项技术称为乐观着色（optimistic coloring）。）它还引入了 Briggs 测试和保守合并的一般概念；Chaitin 的原始设计合并得很激进，即使这让图更难着色。这篇论文还描述了本章没有涉及的一些技术，比如重物化（rematerialization）。

**教科书章节**

Steven Muchnick 的《Advanced Compiler Design and Implementation》（Morgan Kaufmann，1997）第 16 章给出了一个使用与 Chaitin-Briggs 类似算法的寄存器分配器。最显著的差别是它不使用保守合并；与 Chaitin 最初的分配器一样，它合并得很激进。我觉得 Muchnick 关于如何把硬寄存器纳入干涉图、如何检测干涉以及分配器整体结构的讲解特别有用。

Keith Cooper 和 Linda Torczon 的《Engineering a Compiler》第 2 版（Morgan Kaufmann，2011）第 13 章出色地概述了范围很广的各种寄存器分配方法，包括 Chaitin-Briggs 算法和本章没有讨论的另外几种。我借鉴了他们关于干涉的定义以及合并时如何更新干涉图的讨论；他们特别清楚地解释了为什么既需要快速、不精确的更新，也需要缓慢、完整的更新。（你也可以参考这本书 2022 年出版的第三版。）

**注意**

如果你想实现我们跳过的那些 Chaitin-Briggs 部分，这两份资料都很好。如果你想把溢出代码生成集成进寄存器分配器，Muchnick 那一章特别有用。两本书都讨论了如何用活跃范围（Muchnick 称之为 webs）而不是伪寄存器作为干涉图的顶点，也都给出了比我们使用的更好的溢出代价度量。

**保守合并**

George 测试来自 Lal George 和 Andrew Appel 的《Iterated Register Coalescing》（https://doi.org/10.1145/229542.229546）。这篇论文的要点是：如果在合并与剪枝之间交替进行，就能合并更多寄存器；George 测试在文中只是作为一个次要的实现细节出现。

关于 George 和 Briggs 测试的非正式讨论和大量例子，见 Phillip Gibbons 在 Carnegie Mellon 的编译器优化课程幻灯片（https://www.cs.cmu.edu/afs/cs/academic/class/15745-s19/www/lectures/L23-Register-Coalescing.pdf）。

Max Hailperin 的《Comparing Conservative Coalescing Criteria》严格定义了 Briggs 和 George 测试究竟证明了什么——这是原始论文的作者们从未费心去做的事（https://doi.org/10.1145/1065887.1065894）。我在第 656 页「保守合并」一节开头对这些测试保证的讨论，很大程度上依赖 Hailperin 的论文。注意，他的某些论断并不适用于我们的图着色实现，因为他使用预着色，而我们没有。

**识别循环**

要计算更精确的溢出代价，就需要检测程序中的循环。这些资料讨论如何识别循环：

Alfred Aho 等人的《Compilers: Principles, Techniques, and Tools》第 2 版（Addison-Wesley，2006）第 9 章第 6 节。

Phillip Gibbons 在 Carnegie Mellon 编译器优化课程上关于归纳变量优化的讲义幻灯片（https://www.cs.cmu.edu/afs/cs/academic/class/15745-s19/www/lectures/L8-Induction-Variables.pdf）。这是很好的起点，但这些幻灯片不够详细，不能作为循环分析的独立指南。你可能需要把它们与前一条参考文献或其他教科书配合使用。
