# 第 15 章　支持嵌入式内容

*Chapter 15: Supporting Embedded Content*

虽然我们的浏览器已经能够渲染复杂的样式、视觉效果和动画，但这一切基本上都只作用于文本。然而，网页中还包含各种非文本的嵌入式内容（embedded content），从图像到其他网页不一而足。对嵌入式内容的支持对浏览器的架构、性能、安全性以及开放的信息获取都有重大影响，并在整个 web 的历史进程中扮演了关键角色。

## 15.1　图像（Images）

图像（image）无疑是 web 上最流行的嵌入式内容，¹ 最早可以追溯到 1993 年初 [1]。² 网页通过 `<img>` 标签来引入图像，写法如下：

```html
<img src="https://browser.engineering/im/hes.jpg">
```

这个例子渲染出来的效果如图 15.1 所示。

*图 15.1　1969 年一位使用 Hypertext Editing System 的计算机操作员。（来自 Wikipedia 的 Gregory Lloyd [3]，CC BY-SA 4.0 International [4]。）*

幸运的是，实现图像并不太难，所以我们直接开始吧。在我们的浏览器中显示图像有四个步骤：

1. 从 URL 下载图像。
2. 将图像解码（decode）为内存中的一个缓冲区。
3. 在页面上对图像进行布局。
4. 在显示列表（display list）中绘制图像。

先从「从 URL 下载图像」开始。自然，这要通过 HTTP 完成，而我们已经有了一个 `request` 函数。不过，到目前为止我们下载的所有内容——HTML、CSS 和 JavaScript——都是文本，图像则通常使用二进制数据格式。我们需要扩展 `request` 以支持二进制数据。改动非常小：不再给 `makefile` 传递 `"r"` 标志，而是传递一个表示二进制模式的 `"b"` 标志：

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
        response = s.makefile("b")
        # ...
```

现在，每次从 `response` 读取时，得到的都是二进制数据的字节，而不是包含文本数据的 `str`，因此我们需要修改一些 HTTP 解析器代码，显式地对数据解码：

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
        statusline = response.readline().decode("utf8")
        # ...
        while True:
            line = response.readline().decode("utf8")
            # ...
        # ...
```

注意，我在读取主体（body）时并没有加 `decode` 调用；这是因为主体可能确实是二进制数据，我们希望把二进制数据直接返回给浏览器。这样一来，所有既有的、希望得到文本数据的 `request` 调用都需要对响应进行解码。例如，在 `load` 中，你需要做类似这样的事情：

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        headers, body = url.request(self.url, payload)
        body = body.decode("utf8", "replace")
        # ...
```

通过给 `decode` 传递 `replace` 作为第二个参数，我让 Python 用一个特殊字符替换无效字符，而不是抛出异常。请确保在浏览器中所有调用 `request` 的地方都做这个修改，包括 `XMLHttpRequest_send` 内部以及 `load` 中的其他几处。

而下载图像时，我们不会调用 `decode`；我们会直接使用二进制数据。

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        images = [node
            for node in tree_to_list(self.nodes, [])
            if isinstance(node, Element)
            and node.tag == "img"]
        for img in images:
            src = img.attributes.get("src", "")
            image_url = url.resolve(src)
            assert self.allowed_request(image_url), \
                "Blocked load of " + str(image_url) + " due to CSP"
            header, body = image_url.request(url)
```

一旦下载了图像，我们需要把它变成一个 Skia `Image` 对象。这需要以下代码：

```python
class Tab:
    def load(self, url, payload=None):
        for img in images:
            # ...
            img.encoded_data = body
            data = skia.Data.MakeWithoutCopy(body)
            img.image = skia.Image.MakeFromEncoded(data)
```

这里有两个棘手的步骤：先用 `MakeWithoutCopy` 方法把下载到的数据转成 Skia `Data` 对象，再用 `MakeFromEncoded` 把它转成图像。

因为我们用的是 `MakeWithoutCopy`，`Data` 对象只存储了对既有 `body` 的引用，并不拥有这份数据。这一点很关键，因为编码后的图像数据可能很大——也许好几兆字节——复制它会浪费内存和时间。但这也意味着，一旦 `body` 被垃圾回收，这些数据就会失效；这正是我把 `body` 保存在 `encoded_data` 字段中的原因。³

这些下载和解码步骤都可能失败；一旦失败，我们会加载一张「碎图（broken image）」占位图（我用的是 Wikipedia 上的这一张 [5]）：

```python
BROKEN_IMAGE = skia.Image.open("Broken_Image.png")
class Tab:
    def load(self, url, payload=None):
        for img in images:
            try:
                # ...
            except Exception as e:
                print("Image", image_url, "crashed", e)
                img.image = BROKEN_IMAGE
```

现在我们已经下载并保存了图像，接下来要使用它。这只需要调用 Skia 的 `drawImageRect` 函数：

```python
class DrawImage(PaintCommand):
    def __init__(self, image, rect):
        super().__init__(rect)
        self.image = image
    def execute(self, canvas):
        canvas.drawImageRect(self.image, self.rect)
```

不过，`drawImageRect` 的内部实现有点复杂，值得展开讲讲。回想一下，`Image` 对象是用 `MakeFromEncoded` 方法创建的。这个名字提醒我们：下载到的图像并不是原始的图像字节。事实上，你所知道的所有图像格式——JPG、PNG 以及许多更冷门的格式——都用各种精巧的算法对图像数据进行了编码。因此，图像在使用之前需要解码。⁴

Skia 对解码应用了各种聪明的优化，比如直接把图像解码到它最终的大小，并尽可能长时间地缓存解码后的图像。⁵ 这是因为原始图像数据可能相当庞大：⁶ 一个像素通常存储为 4 个字节，因此一台 1200 万像素的相机（如今手机上就很常见）单张图像就会产生 48 MB 的原始数据。

由于图像解码可能如此昂贵，Skia 还提供了多种可用的解码算法，其中一些更快，但成像质量更差。⁷ 例如，有快速、简单的「最近邻（nearest neighbor）」算法，也有较慢但质量更高的「双线性（bilinear）」乃至「Lanczos [8]」算法。⁸

为了让网页作者能控制这个性能瓶颈，有一个 `image-rendering` [9] CSS 属性用来指示使用哪种算法。我们把它作为 `DrawImage` 的一个参数加上：

```python
def parse_image_rendering(quality):
    if quality == "high-quality":
        return skia.FilterQuality.kHigh_FilterQuality
    elif quality == "crisp-edges":
        return skia.FilterQuality.kLow_FilterQuality
    else:
        return skia.FilterQuality.kMedium_FilterQuality

class DrawImage(PaintCommand):
    def __init__(self, image, rect, quality):
        # ...
        self.quality = parse_image_rendering(quality)
    def execute(self, canvas):
        paint = skia.Paint(
            FilterQuality=self.quality,
        )
        canvas.drawImageRect(self.image, self.rect, paint)
```

但要谈这个参数从哪里来，或者更一般地说，要在我们的浏览器里真正看到下载的图像，我们首先需要把图像加进浏览器的布局树。

> **深入探索**
> HTTP 的 `Content-Type` 头让 web 服务器告诉浏览器，一份文档包含的是文本还是二进制数据。这个头包含一个称为 MIME 类型（MIME type）[10] 的值，例如 HTML、CSS 和 JavaScript 分别对应 `text/html`、`text/css` 和 `text/javascript`；PNG 和 JPEG 图像对应 `image/png` 和 `image/jpeg`；此外还有针对各种字体、视频、音频和数据格式的许多其他类型 [11]。⁹ 有意思的是，我们在上面的代码中并不需要指定图像格式。这是因为许多图像格式以「魔数（magic bytes）」[12] 开头；例如 PNG 文件总是以字节 137 开头，后面跟着字母 "PNG"。这些魔数往往比 web 服务器提供的 MIME 类型更可靠，因此这种「格式嗅探（format sniffing）」在浏览器及其支持库中很常见。

## 15.2　嵌入式布局（Embedded Layout）

凭借你在前几章积累的经验，你大概能猜到如何把图像加进浏览器的布局和绘制流程。我们需要创建一个 `ImageLayout` 类；给 `BlockLayout` 的 `recurse` 方法加一个新的 `image` 分支；并从 `ImageLayout` 的 `paint` 方法生成一条 `DrawImage` 命令。

在做这些的时候，你可能会想起为 `<input>` 元素做过非常相似的事情。事实上，文本框和按钮与图像非常相似：两者都是 DOM 的叶节点、都被放进文本行、都受文本基线影响，并且都绘制自定义内容。¹⁰ 既然它们如此相似，我们不妨让两者复用同一份代码。

让我们把现有的 `InputLayout` 拆分成一个叫做 `EmbedLayout` 的超类，包含现有的大部分代码，以及一个包含 input 专属代码的新子类 `InputLayout`：¹¹

```python
class EmbedLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
    def layout(self):
        self.zoom = self.parent.zoom
        self.font = font(self.node.style, self.zoom)
        if self.previous:
            space = self.previous.font.measureText(" ")
            self.x = \
                self.previous.x + space + self.previous.width
        else:
            self.x = self.parent.x

class InputLayout(EmbedLayout):
    def __init__(self, node, parent, previous):
        super().__init__(node, parent, previous)
    def layout(self):
        super().layout()
```

思路是：`EmbedLayout` 为各种嵌入式内容提供公共的布局代码，而它的子类（比如 `InputLayout`）提供该类内容的专属代码。不同类型的嵌入式内容可能有不同的宽度和高度，所以这部分应该发生在各子类中，`paint` 的定义也一样：

```python
class InputLayout(EmbedLayout):
    def layout(self):
        # ...
        self.width = dpx(INPUT_WIDTH_PX, self.zoom)
        self.height = linespace(self.font)
        self.ascent = -self.height
        self.descent = 0
    def paint(self):
        # ...
```

`ImageLayout` 现在可以从 `EmbedLayout` 继承大部分行为，只是宽和高取自图像本身：

```python
class ImageLayout(EmbedLayout):
    def __init__(self, node, parent, previous):
        super().__init__(node, parent, previous)
    def layout(self):
        super().layout()
        self.width = dpx(self.node.image.width(), self.zoom)
        self.img_height = dpx(self.node.image.height(), self.zoom)
        self.height = max(self.img_height, linespace(self.font))
        self.ascent = -self.height
        self.descent = 0
```

注意，图像的高度取决于元素的字体大小。这虽然奇怪，但图像布局实际就是这样工作的：一行上即使只有一张很小的图像，这一行仍然要高到能容纳文本。¹² 其深层原因是，作为一种内联布局，图像被设计成与相关文本一起流动，这意味着图像的底部应当与文本基线（baseline）[15] 对齐。这也是我们在上面的代码中保存 `img_height` 的原因。

另外，在上面的代码中，我在 `EmbedLayout` 的子类上引入了新的 `ascent` 和 `descent` 字段。它们将在 `LineLayout` 的 `layout` 中使用，取代现有的 ascent/descent 布局代码。这还要求在 `TextLayout` 上引入这些字段：

```python
class LineLayout:
    def layout(self):
        # ...
        max_ascent = max([-child.ascent
                        for child in self.children])
        baseline = self.y + max_ascent
        for child in self.children:
            if isinstance(child, TextLayout):
                child.y = baseline + child.ascent / 1.25
            else:
                child.y = baseline + child.ascent
        max_descent = max([child.descent
                        for child in self.children])
        self.height = max_ascent + max_descent
```

```python
class TextLayout:
    def layout(self):
        # ...
        self.ascent = self.font.getMetrics().fAscent * 1.25
        self.descent = self.font.getMetrics().fDescent * 1.25
```

绘制图像也很直接：

```python
class ImageLayout(EmbedLayout):
    def paint(self):
        cmds = []
        rect = skia.Rect.MakeLTRB(
            self.x, self.y + self.height - self.img_height,
            self.x + self.width, self.y + self.height)
        quality = self.node.style.get("image-rendering", "auto")
        cmds.append(DrawImage(self.node.image, rect, quality))
        return cmds
```

现在我们需要在 `BlockLayout` 中创建 `ImageLayout`。input 元素是在一个 `input` 方法中创建的，所以我们可以创建一个非常相似的 `image` 方法。但 `input` 本身就在很大程度上是 `word` 的翻版，这样会产生大量重复代码。这些方法中唯一不同的部分，是计算新内联子节点宽度的那部分；其余大部分逻辑都是共享的。

我们不如把共享的代码重构为 `text`、`image` 和 `input` 都可以调用的新方法。首先，所有这些方法都需要一个字体，用来确定在内联元素之后要留出多少空间；¹³ 我们为此写一个函数：

```python
def font(style, zoom):
    weight = style["font-weight"]
    variant = style["font-style"]
    size = float(style["font-size"][:-2]) * 0.75
    font_size = dpx(size, zoom)
    return get_font(font_size, weight, variant)
```

还有处理行布局的共享代码；我们把它放进一个新的 `add_inline_child` 方法。我们需要传入 HTML 节点、元素，以及要实例化的布局类（外加一个只给 `TextLayout` 用的 `word` 参数）：

```python
class BlockLayout:
    def add_inline_child(self, node, w, child_class, word=None):
        if self.cursor_x + w > self.x + self.width:
            self.new_line()
        line = self.children[-1]
        previous_word = line.children[-1] if line.children else None
        if word:
            child = child_class(node, word, line, previous_word)
        else:
            child = child_class(node, line, previous_word)
        line.children.append(child)
        self.cursor_x += w + \
            font(node.style, self.zoom).measureText(" ")
```

现在我们可以用一种令人满意的方式重新定义 `word` 和 `input`：

```python
class BlockLayout:
    def word(self, node, word):
        node_font = font(node.style, self.zoom)
        w = node_font.measureText(word)
        self.add_inline_child(node, w, TextLayout, word)
    def input(self, node):
        w = dpx(INPUT_WIDTH_PX, self.zoom)
        self.add_inline_child(node, w, InputLayout)
```

加 `image` 就容易了：

```python
class BlockLayout:
    def recurse(self, node):
        # ...
        elif node.tag == "img":
            self.image(node)
    def image(self, node):
        w = dpx(node.image.width(), self.zoom)
        self.add_inline_child(node, w, ImageLayout)
```

当然，图像也获得与 input 元素相同的内联布局模式：

```python
class BlockLayout:
    def layout_mode(self):
        # ...
        elif self.node.tag in ["input", "img"]:
            return "inline"
    def should_paint(self):
        return isinstance(self.node, Text) or \
            (self.node.tag not in \

```

现在布局树中有了 `ImageLayout` 节点，我们将向显示列表绘制 `DrawImage` 命令，并把图像显示在屏幕上！

## 15.3　修改图像尺寸（Modifying Image Sizes）

到目前为止，图像在屏幕上的尺寸就是它的像素尺寸，可能经过缩放。¹⁵ 但事实上，让作者能控制嵌入式内容的尺寸通常很有价值。实现方式有好几种，¹⁶ 其中一种是特殊的 `width` 和 `height` 属性。¹⁷

如果这两个属性都存在，事情就相当简单：我们在布局元素时直接从它们读取，既在 `image` 中：

```python
class BlockLayout:
    def image(self, node):
        if "width" in node.attributes:
            w = dpx(int(node.attributes["width"]), self.zoom)
        else:
            w = dpx(node.image.width(), self.zoom)
        # ...
```

也在 `ImageLayout` 中：

```python
class ImageLayout(EmbedLayout):
    def layout(self):
        # ...
        width_attr = self.node.attributes.get("width")
        height_attr = self.node.attributes.get("height")
        image_width = self.node.image.width()
        image_height = self.node.image.height()
        if width_attr and height_attr:
            self.width = dpx(int(width_attr), self.zoom)
            self.img_height = dpx(int(height_attr), self.zoom)
        else:
            self.width = dpx(image_width, self.zoom)
            self.img_height = dpx(image_height, self.zoom)
        # ...
```

这工作得很好，但有一个重大缺陷：如果宽高比与底层图像的尺寸不一致，图像最终会被奇怪地拉伸。有时这是故意的，但通常是失误。所以浏览器允许作者只指定 `width` 和 `height` 中的一个，并用图像的宽高比（aspect ratio）计算另一个。¹⁸

实现这个宽高比调整很容易：

```python
class ImageLayout(EmbedLayout):
    # ...
    def layout(self):
        # ...
        aspect_ratio = image_width / image_height
        if width_attr and height_attr:
            # ...
        elif width_attr:
            self.width = dpx(int(width_attr), self.zoom)
            self.img_height = self.width / aspect_ratio
        elif height_attr:
            self.img_height = dpx(int(height_attr), self.zoom)
            self.width = self.img_height * aspect_ratio
        else:
            # ...
        # ...
```

> 我们的浏览器从加载后的图像尺寸计算宽高比，但在图像加载之前，这个信息是不可用的。在真实浏览器中，图像是异步加载的，而且图像尺寸可能随 [20] 布局参数而变化，这就成了一个真正的问题。不知道宽高比，可能导致图像加载时发生布局偏移（layout shift）[21]，让用户不胜其烦。`aspect-ratio` 属性 [22] 是网页应对这一问题的一种方式。

## 15.4　交互式部件（Interactive Widgets）

到目前为止，我们的浏览器有两种嵌入式内容：图像和 input 元素。两者虽然都重要且被广泛使用，¹⁹ 但它们无法提供地图、PDF、广告和社交媒体控件等复杂嵌入式内容用例所需的可定制性²⁰和灵活性。因此在现代浏览器中，这类需求通过 `<iframe>` 元素把一个网页嵌入另一个网页来处理。²¹

在语义上，`<iframe>` 类似于标签页中的标签页——它有自己的 HTML 文档、CSS 和脚本。而在布局方面，`<iframe>` 又很像 `<img>` 标签，同样有 `width` 和 `height` 属性。因此，实现基本的 iframe 只需要处理以下三个显著差异：

- iframe 没有 browser chrome（浏览器自带的界面装饰，如地址栏和工具栏）。因此，任何页面导航都必须从页面内部发生（通过 `<a>` 元素或脚本），或者作为包含 `<iframe>` 元素的网页上导航的副作用。点击 iframe 中的链接，导航的也是该 iframe，而不是顶级页面。
- iframe 可以共享一个渲染事件循环（rendering event loop）。²² 在真实浏览器中，跨源（cross-origin）[27] iframe 通常被「站点隔离（site isolated）」，即出于安全原因 [28]，iframe 拥有自己的 CPU 进程。在我们的浏览器中，我们让所有 iframe（包括嵌套的——没错，iframe 里还能再套 iframe！）使用同一个渲染事件循环。
- 跨源 iframe 与包含它的页面在脚本上相互隔离。也就是说，iframe 中的脚本不能访问 [29] 包含页面的变量或 DOM；包含页面中的脚本也不能访问 iframe 的变量或 DOM。但同源（same-origin）iframe 可以。

这些差异我们后面会逐一处理，现在先着手实现「标签页中的标签页」这个想法。我们要做的是把 `Tab` 类拆成两部分：`Tab` 拥有事件循环和脚本环境，`Frame` 负责其余的一切。

像这样复杂的重构，值得先详细规划一番。`Tab` 将：

- 作为 `Browser` 与各 `Frame` 之间的接口来处理事件；
- 代理帧之间的通信；
- 启动动画帧和渲染；
- 为标签页中的所有帧绘制并持有显示列表；
- 构建并持有可访问性树；
- 向浏览器线程提交（commit）。

而新的 `Frame` 类将：

- 为它的 HTML 文档持有 DOM、布局树和滚动偏移；
- 在它的 DOM 和布局树上执行样式和布局；
- 为它的 HTML 文档实现加载和事件处理（焦点、点击测试等）。

创建这两个类，并据此把方法在两者之间分拆。自然而然，每个 `Frame` 都需要持有其 `Tab` 的引用；能访问父帧和对应的 `<iframe>` 元素也很方便：

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        self.tab = tab
        self.parent_frame = parent_frame
        self.frame_element = frame_element
        # ...
```

现在来看 `Frame` 是在哪里创建的。第一处是 `Tab` 的 `load` 方法，它需要创建根帧（root frame）：

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.root_frame = None
    def load(self, url, payload=None):
        self.history.append(url)
        # ...
        self.root_frame = Frame(self, None, None)
        self.root_frame.load(url, payload)
```

注意，`load` 的核心内容现在位于 `Frame` 中，因为 `Frame` 拥有 HTML 树。`Frame` 还可以为 `<iframe>` 元素构造子 `Frame`：

```python
class Frame:
    def load(self, url, payload=None):
        # ...
        iframes = [node
                    for node in tree_to_list(self.nodes, [])
                    if isinstance(node, Element)
                    and node.tag == "iframe"
                    and "src" in node.attributes]
        for iframe in iframes:
            document_url = url.resolve(iframe.attributes["src"])
            if not self.allowed_request(document_url):
                print("Blocked iframe", document_url, "due to CSP")
                iframe.frame = None
                continue
            iframe.frame = Frame(self.tab, self, iframe)
        # ...
```

由于 iframe 可能有子资源（以及子帧！），加载起来可能很慢，所以我们应该像对待脚本一样异步加载它们：

```python
class Frame:
    def load(self, url, payload=None):
        for iframe in iframes:
            # ...
            task = Task(iframe.frame.load, document_url)
            self.tab.task_runner.schedule_task(task)
```

而且正因为它们是异步的，我们需要记录它们是否已经加载完毕，以避免尝试渲染一个尚未加载的 iframe：

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.loaded = False
    def load(self, url, payload=None):
        self.loaded = False
        ...
        self.loaded = True
```

这样，我们就在单个标签页内得到了一棵帧树。但由于有时需要直接访问任意一个帧，我们再给每个帧一个标识符，我称之为窗口 ID（window ID）：

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.window_id = len(self.tab.window_id_to_frame)
        self.tab.window_id_to_frame[self.window_id] = self
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.window_id_to_frame = {}
```

现在帧能被创建了，我们来着手把这些帧渲染到屏幕上。

> **深入探索**
> 在相当长的一段时间里，浏览器还支持以插件（plugin）形式存在的嵌入式内容，比如 Java applet [30] 或 Flash [31]。但插件通常要自己实现渲染、沙箱和 UI 原语，这带来了性能、安全性和可访问性方面的问题 [32]。随着时间推移，新的 API 逐渐弥合了 web 原生内容与「非 web」插件之间的差距，²³ 插件因此变得不那么常见了。就我个人而言，我认为这是件好事：web 的要义在于让信息对所有人都可访问，而这需要开放标准，嵌入式内容也不例外。

## 15.5　Iframe 渲染（Iframe Rendering）

渲染工作被分摊给 `Tab` 和它的各个 `Frame`：`Frame` 负责样式和布局，`Tab` 负责可访问性和绘制。²⁴ 我们需要实现这种拆分，还要添加从 `Tab` 触发每个 `Frame` 渲染的代码。

先从拆分渲染管线开始。这里的主方法仍然是 `Tab` 的 `run_animation_frame` 和 `render`，它们会遍历所有已加载的 iframe：

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        for (window_id, frame) in self.window_id_to_frame.items():
            if not frame.loaded:
                continue
            frame.js.dispatch_RAF(frame.window_id)
            # ...
    def render(self):
        self.browser.measure.time('render')
        for id, frame in self.window_id_to_frame.items():
            if frame.loaded:
                frame.render()
        if self.needs_accessibility:
            # ...
        if self.needs_paint:
            # ...
        # ...
```

在这段代码中，我用到了一个新的 `dispatch_RAF` 方法：

```python
class JSContext:
    def dispatch_RAF(self):
        self.interp.evaljs("window.__runRAFHandlers()")
```

注意，`needs_accessibility`、`pending_hover` 等标志仍然在 `Tab` 上，因为它们与 `Tab` 负责的那部分渲染相关。与此同时，样式和布局现在发生在 `Frame` 中：

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.needs_style = False
        self.needs_layout = False
    def set_needs_render(self):
        self.needs_style = True
        self.tab.set_needs_accessibility()
        self.tab.set_needs_paint()
    def set_needs_layout(self):
        self.needs_layout = True
        self.tab.set_needs_accessibility()
        self.tab.set_needs_paint()
    def render(self):
        if self.needs_style:
            # ...
        if self.needs_layout:
            # ...
```

同样，这些脏位（dirty bit）移到了 `Frame` 上，因为它们与帧负责的那部分渲染相关。

与图像不同，iframe 没有固有尺寸（intrinsic size）[34]：`<iframe>` 元素的布局尺寸不依赖于它的内容。²⁵ 这意味着父子帧之间需要发生一项关键的额外通信：一个帧应该被布局得多宽、多高？这由 iframe 元素的属性和 CSS 定义：

```python
class BlockLayout:
    # ...
    def layout_mode(self):
        # ...
        elif self.node.tag in ["input", "img", "iframe"]:
            return "inline"
    def recurse(self, node):
        # ...
        elif node.tag == "iframe" and \
            "src" in node.attributes:
            self.iframe(node)
    # ...
    def iframe(self, node):
        if "width" in self.node.attributes:
            w = dpx(int(self.node.attributes["width"]),
                    self.zoom)
        else:
            w = IFRAME_WIDTH_PX + dpx(2, self.zoom)
        self.add_inline_child(node, w, IframeLayout, self.frame)
    def should_paint(self):
        return isinstance(self.node, Text) or \
            (self.node.tag not in \
                ["input", "button", "img", "iframe"])
```

`IframeLayout` 的布局代码与此类似，同样继承自 `EmbedLayout`，但没有宽高比那段代码：

```python
class IframeLayout(EmbedLayout):
    def __init__(self, node, parent, previous, parent_frame):
        super().__init__(node, parent, previous, parent_frame)
    def layout(self):
        # ...
        if width_attr:
            self.width = dpx(int(width_attr) + 2, self.zoom)
        else:
            self.width = dpx(IFRAME_WIDTH_PX + 2, self.zoom)
        if height_attr:
            self.height = dpx(int(height_attr) + 2, self.zoom)
        else:
            self.height = dpx(IFRAME_HEIGHT_PX + 2, self.zoom)
        self.ascent = -self.height
        self.descent = 0
```

多出的两个像素为之后要加的边框留出空间，每侧各一像素。注意，如果未指定宽度，iframe 会使用一个默认值 [37]，它是很久以前按照当时的平均屏幕尺寸选定的：

```python
IFRAME_WIDTH_PX = 300
IFRAME_HEIGHT_PX = 150
```

不过，这段代码是在父帧中运行的。我们需要把这个宽度和高度传递给子帧，使它在布局期间知道自己的宽高。为此，我们在子帧中加一个字段：

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        # ...
        self.frame_width = 0
        self.frame_height = 0
```

我们可以在父帧完成布局时设置它们：

```python
class IframeLayout(EmbedLayout):
    def layout(self):
        # ...
        if self.node.frame:
            self.node.frame.frame_height = \
                self.height - dpx(2, self.zoom)
            self.node.frame.frame_width = \
                self.width - dpx(2, self.zoom)
```

你可能会惊讶，我并没有在这里对子帧调用 `set_needs_render`。这是个取巧的做法：`width` 和 `height` 属性只能通过 `setAttribute` 改变，而缩放只会在 `zoom_by` 和 `reset_zoom` 中改变。不过，所有这些事件处理器都需要让全部帧失效，为此我们改用一个新的方法，取代 `Tab` 上如今已不复存在的旧 `set_needs_render`。请把所有这些调用点都改为调用新方法（另外还有影响所有帧样式的深色模式改动）：

```python
class Tab:
    def set_needs_render_all_frames(self):
        for id, frame in self.window_id_to_frame.items():
            frame.set_needs_render()
```

（前面 `IframeLayout` 代码里的）这个条件判断只是为了处理（不常见的）iframe 被 CSP 拦截的情况。

当然，根帧会铺满整个窗口：

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.root_frame.frame_width = WIDTH
        self.root_frame.frame_height = self.tab_height
```

注意，这里有一个微妙的依赖顺序。我们需要父帧先于子帧做布局，这样子帧布局时才拥有最新的宽度和高度。这一顺序由 Python（3.7 及以上版本）替我们保证，其字典按插入顺序排序；但如果你是用另一种语言跟着实现，可能需要在渲染前先对帧排序。

现在帧已完成样式和布局，只剩下绘制了。与布局和样式不同，一个标签页中的所有帧产生的是单一、统一的显示列表，所以我们需要递归地进行。我们让 `Tab` 绘制根 `Frame`：

```python
class Tab:
    def render(self):
        if self.needs_paint:
            self.display_list = []
            paint_tree(self.root_frame.document, self.display_list)
            self.needs_paint = False
```

布局树的大多数 `paint` 方法都不需要改动，但要绘制 `IframeLayout`，我们需要在 `paint_tree` 中绘制子帧：

```python
def paint_tree(layout_object, display_list):
    cmds = layout_object.paint()
    if isinstance(layout_object, IframeLayout) and \
        layout_object.node.frame and \
        layout_object.node.frame.loaded:
        paint_tree(layout_object.node.frame.document, cmds)
    else:
        for child in layout_object.children:
            paint_tree(child, cmds)
    cmds = layout_object.paint_effects(cmds)
    display_list.extend(cmds)
```

不过，在把这些命令放进显示列表之前，我们需要添加边框、裁剪超出可用可视区域的 iframe 内容，并对坐标系做变换：

```python
class IframeLayout(EmbedLayout):
    def paint_effects(self, cmds):
        # ...
        diff = dpx(1, self.zoom)
        offset = (self.x + diff, self.y + diff)
        cmds = [Transform(offset, rect, self.node, cmds)]
        inner_rect = skia.Rect.MakeLTRB(
            self.x + diff, self.y + diff,
            self.x + self.width - diff, self.y + self.height - diff)
        internal_cmds = cmds
        internal_cmds.append(Blend(1.0, "destination-in", None, [
                        DrawRRect(inner_rect, 0, "white")]))
        cmds = [Blend(1.0, "source-over", self.node, internal_cmds)]
        paint_outline(self.node, cmds, rect, self.zoom)
        cmds = paint_visual_effects(self.node, cmds, rect)
        return cmds
```

`Transform` 把子帧内容平移过来，使其左上角从正确的位置开始，²⁶ `ClipRRect` 把 iframe 的内容裁剪到边框内侧，而 `paint_outline` 添加边框。要触发 outline，只需把下面这条加入浏览器的 CSS 文件：

```css
iframe {
    outline: 1px solid black;
}
```

最后，我们还要把 iframe 加入可访问性树。与显示列表一样，可访问性树跨所有帧是全局的。我们可以让 iframe 创建 iframe 节点：

```python
class AccessibilityNode:
    def __init__(self, node):
        # ...
        else:
            # ...
            elif node.tag == "iframe":
                self.role = "iframe"
```

要构建这样的节点，我们只需递归进入该帧：

```python
class AccessibilityNode:
    def build_internal(self, child_node):
        if isinstance(child_node, Element) \
            and child_node.tag == "iframe" and child_node.frame \

            child = AccessibilityNode(child_node.frame.nodes)
        # ...
```

这样，iframe 就显示在屏幕上了。下一步是与它们交互。

> **深入探索**
> 在 iframe 出现之前，还有 `<frameset>` 和 `<frame>` [39] 元素。`<frameset>` 取代 `<body>` 标签，把浏览器窗口切分给多个 `<frame>`；这是除本书所讲的布局系统之外的一种早期替代布局系统。Frame 的导航混乱、可访问性差，又缺乏 `<iframe>` 的灵活性，如今已很少使用。"iframe" 这个名字多少是在向这些元素致敬——它是 "inline frame"（内联框架）的缩写。

## 15.6　Iframe 输入事件（Iframe Input Events）

现在 iframe 已经能渲染到屏幕上了，让我们用用户输入来形成闭环。我们想支持点击 iframe 内部的内容，也想在 iframe 内部按 Tab 键切换焦点或滚动。

在高层面，事件处理器只是把事件委托给根帧：

```python
class Tab:
    def click(self, x, y):
        self.render()
        self.root_frame.click(x, y)
```

当点击命中一个 iframe 时，它会把点击传递给子帧，然后立即返回，因为 iframe 会捕获点击事件。注意，在递归进入子帧时，我是如何从（绝对的）点击 x、y 坐标中减去 iframe 的绝对 x、y 偏移的：

```python
class Frame:
    def click(self, x, y):
        # ...
        while elt:
            # ...
            elif elt.tag == "iframe":
                abs_bounds = \
                    absolute_bounds_for_obj(elt.layout_object)
                border = dpx(1, elt.layout_object.zoom)
                new_x = x - abs_bounds.left() - border
                new_y = y - abs_bounds.top() - border
                elt.frame.click(new_x, new_y)
                return
```

现在，点击 `<a>` 元素就能正常工作了，也就是说，你可以让一个帧导航到新页面。而且由于 `Frame` 拥有 `Tab` 过去拥有的全部加载与导航逻辑，这一切无须更多改动就能直接工作！

让我们把其他交互也做起来，先从聚焦元素开始。每个标签页同一时刻只能聚焦一个元素，所以我们仍然把焦点存在 `Tab` 上，但我们还需要存储聚焦元素所在的 iframe：

```python
class Tab:
    def __init__(self, browser, tab_height):
        self.focus = None
        self.focused_frame = None
```

当某个 iframe 试图聚焦一个元素时，它把自己设为聚焦的 iframe，但在此之前，它需要取消之前聚焦的 iframe 的焦点：

```python
class Frame:
    def focus_element(self, node):
        # ...
        if self.tab.focused_frame and self.tab.focused_frame != self:
            self.tab.focused_frame.set_needs_render()
        self.tab.focused_frame = self
        # ...
```

我们需要重新渲染之前聚焦的 iframe，让它不再绘制焦点轮廓。

另一个交互是按 Tab 键在当前帧的可聚焦元素之间循环。让我们把 `advance_tab` 的逻辑移入 `Frame`，由 `Tab` 直接分发过去：²⁷

```python
class Tab:
    def advance_tab(self):
        frame = self.focused_frame or self.root_frame
        frame.advance_tab()
```

对 `keypress` 和 `enter` 做同样的处理，它们用于与文本输入框和按钮交互。

我们需要支持的另一大交互是滚动。我们把滚动偏移存进每个 `Frame`：

```python
class Frame:
    def __init__(self, tab, parent_frame, frame_element):
        self.scroll = 0
```

你可能还记得第 13 章：为了提高响应速度，滚动既发生在 `Browser` 内部，也发生在 `Tab` 内部。那已经相当复杂了，所以为了简单起见，我们只支持在根帧上做线程化滚动。我们需要一个新的提交参数，让浏览器线程知道根帧是否处于聚焦状态：

```python
class CommitData:
    def __init__(self, url, scroll, root_frame_focused, height,
        display_list, composited_updates, accessibility_tree, focus):
        # ...
        self.root_frame_focused = root_frame_focused
class Tab:
    def run_animation_frame(self, scroll):
        root_frame_focused = not self.focused_frame or \
                self.focused_frame == self.root_frame
        # ...
        commit_data = CommitData(
            # ...
            root_frame_focused,
            # ...
        )
        # ...
```

浏览器线程会在 `commit` 中保存这个信息，并在用户请求滚动时使用它：

```python
class Browser:
    def commit(self, tab, data):
        # ...
            self.root_frame_focused = data.root_frame_focused
    def handle_down(self):
        self.lock.acquire(blocking=True)
        if self.root_frame_focused:
            # ...
        task = Task(self.active_tab.scrolldown)
        self.active_tab.task_runner.schedule_task(task)
        self.lock.release()
```

当标签页被要求滚动时，它滚动的是聚焦的帧：

```python
class Tab:
    def scrolldown(self):
        frame = self.focused_frame or self.root_frame
        frame.scrolldown()
        self.set_needs_paint()
```

如果滚动的是根帧以外的帧，我们就直接设置 `needs_composite`，让浏览器从头开始重新光栅化：

```python
class Tab:
    def run_animation_frame(self, scroll):
        # ...
        for (window_id, frame) in self.window_id_to_frame.items():
            if frame == self.root_frame: continue
            if frame.scroll_changed_in_frame:
                needs_composite = True
                frame.scroll_changed_in_frame = False
        # ...
```

关于滚动，还有一处细节。滚动之后，我们要对滚动位置做钳制（clamp），防止用户滚出页面最后一个内容。目前 `clamp_scroll` 用窗口高度来决定最大滚动量；我们把这个函数移到 `Frame` 内部，让它可以使用当前帧的高度：

```python
class Frame:
    def scrolldown(self):
        self.scroll = self.clamp_scroll(self.scroll + SCROLL_STEP)
    def clamp_scroll(self, scroll):
        height = math.ceil(self.document.height + 2*VSTEP)
        maxscroll = height - self.frame_height
        return max(0, min(scroll, maxscroll))
```

请确保在所有地方都使用 `clamp_scroll` 方法。例如，在 `scroll_to` 中：

```python
class Frame:
    def scroll_to(self, elt):
        # ...
        self.scroll = self.clamp_scroll(new_scroll)
```

还有一些可访问性悬停交互需要支持。这很难，因为可访问性交互发生在浏览器线程中，而浏览器线程掌握的信息有限：

- 可访问性树不知道 iframe 在哪里，所以在进入一个帧时，它不知道如何变换悬停坐标。
- 它也不知道 iframe 有多大，所以不会忽略那些被裁剪在 iframe 边界之外的内容。²⁸
- 它还不知道一个帧滚动了多远，所以无法针对已滚动的帧做调整。

我们将创建 `AccessibilityNode` 的一个子类来存储这些信息：

```python
class FrameAccessibilityNode(AccessibilityNode):
    pass
```

我们在每个 iframe 节点之下创建这样一个节点：

```python
class AccessibilityNode:
    def build_internal(self, child_node):
        if isinstance(child_node, Element) \
            and child_node.tag == "iframe" and child_node.frame \
            and child_node.frame.loaded:
            child = FrameAccessibilityNode(child_node)
```

对 `FrameAccessibilityNode` 做点击测试（hit test）时，会使用帧的边界来忽略帧边界之外的点击，并按帧的坐标系调整点击位置（注意我们如何减去帧的缩放后的边框宽度）：

```python
class FrameAccessibilityNode(AccessibilityNode):
    def __init__(self, node, parent=None):
        super().__init__(node, parent)
        self.scroll = self.node.frame.scroll
        self.zoom = self.node.layout_object.zoom
    def hit_test(self, x, y):
        bounds = self.bounds[0]
        if not bounds.contains(x, y): return
        new_x = x - bounds.left() - dpx(1, self.zoom)
        new_y = y - bounds.top() - dpx(1, self.zoom) + self.scroll
        node = self
        for child in self.children:
            res = child.hit_test(new_x, new_y)
            if res: node = res
        return node
```

点击测试现在应该可以工作了，但被悬停的节点绘制到屏幕上时，其边界仍然不对。为此，我们需要一个返回 `AccessibilityNode` 绝对屏幕矩形的方法。而这个方法又需要父指针，以便沿可访问性树向上回溯，所以我们先加上父指针：

```python
class AccessibilityNode:
    def __init__(self, node, parent=None):
        # ...
        self.parent = parent
    def build_internal(self, child_node):
        # ...
            child = FrameAccessibilityNode(child_node, self)
        else:
            child = AccessibilityNode(child_node, self)
```

现在，我们可以编写映射到绝对坐标的方法了。它会遍历所有的边界矩形，并把它们一路映射到根。注意 `FrameAccessibilityNode` 有一个特例，因为它自身的边界位于包含该 iframe 的那个帧的坐标系中。

```python
class AccessibilityNode:
    def absolute_bounds(self):
        abs_bounds = []
        for bound in self.bounds:
            abs_bound = bound.makeOffset(0.0, 0.0)
            if isinstance(self, FrameAccessibilityNode):
                obj = self.parent
            else:
                obj = self
            while obj:
                obj.map_to_parent(abs_bound)
                obj = obj.parent
            abs_bounds.append(abs_bound)
        return abs_bounds
```

这个方法会调用 `map_to_parent` 来调整边界。对大多数可访问性节点，我们什么都不用做，因为它们与父节点处于同一个坐标系：

```python
class AccessibilityNode:
    def map_to_parent(self, rect):
        pass
```

而 `FrameAccessibilityNode` 则要针对 iframe 的位置和裁剪做调整：

```python
class FrameAccessibilityNode(AccessibilityNode):
    def map_to_parent(self, rect):
        bounds = self.bounds[0]
        rect.offset(bounds.left(), bounds.top() - self.scroll)
        rect.intersect(bounds)
```

现在，你应该能悬停在节点上，并让我们的可访问性子系统把它们读出来了。

好了，现在浏览器的所有用户交互形式都能正确地沿帧树递归了。是时候给 iframe 添加更多能力了。

> **深入探索**
> 我们的浏览器只能在浏览器线程上滚动根帧，而真实浏览器投入了大量工作 [40]，让尽可能多的滚动（包括 iframe 的滚动）发生在浏览器线程上。难点在于处理包含块、堆叠顺序 [41]、滚动条 [42]、变换和 iframe 等众多冷门组合：一旦滚动放在浏览器线程上，所有这些复杂交互都必须从主线程传给浏览器线程，并被双方正确解释。

## 15.7　Iframe 脚本（Iframe Scripts）

现在用户已经能与 iframe 交互了——那脚本与 iframe 的交互呢？当然，每个帧都已经可以运行脚本——但目前每个 `Frame` 都有自己的 `JSContext`，所以这些脚本无法真正相互作用。恰恰相反，同源 iframe 应当运行在同一个 JavaScript 上下文中，应当能访问彼此的全局变量、调用彼此的函数、修改彼此的 DOM，如图 15.7 所示。我们来实现它。

示意图（文字描述）：Browser（浏览器）之下有多个 Tab（标签页）；同一个 Tab 内可以包含多个 Frame（帧），例如两个 Origin A 的 Frame 和一个 Origin B 的 Frame；属于同一源（Origin A）的多个 Frame 共享同一个 JS Context（JS 上下文），属于其他源（Origin B）的 Frame 则使用另一个 JS Context。整体关系可概括为：Browser → Tab → Frame（同源者共用）→ JS Context。

*图 15.7　同一标签页内的多个帧可以共享单个 JSContext。*

要让两个帧的 JavaScript 环境相互作用，我们需要把它们放进同一个 `JSContext`。于是，与其让每个 `Frame` 拥有自己的 `JSContext`，不如把 `JSContext` 存在 `Tab` 上，放在一个把源（origin）映射到 JavaScript 上下文的字典里：

```python
class Tab:
    def __init__(self, browser, tab_height):
        # ...
        self.origin_to_js = {}
    def get_js(self, url):
        origin = url.origin()
        if origin not in self.origin_to_js:
            self.origin_to_js[origin] = JSContext(self, origin)
        return self.origin_to_js[origin]
```

然后，每个 `Frame` 会向 `Tab` 请求它的 JavaScript 上下文：

```python
class Frame:
    def load(self, url, payload=None):
        # ...
        self.js = self.tab.get_js(url)
        # ...
```

这样，多个页面的脚本就共用一个 JavaScript 上下文了。但现在我们得想办法让它们的变量各自待在各自的命名空间里。关键在于 `window` 全局变量，它的类型是 `Window`。在浏览器中，`window` 指向全局对象（global object）[43]，所以与其写一个像 `a` 这样的全局变量，你总可以写成 `window.a`。²⁹ 为了让实现保持简单，在我们的浏览器中，脚本将总是需要通过 `window` 来引用变量和函数。³⁰ 我们的运行时也要做同样的事情：

```javascript
window.console = { log: function(x) { call_python("log", x); } }
// ...
window.Node = function(handle) { this.handle = handle; }
// ...
```

对 runtime.js 文件中的每个函数和变量都做同样的处理。如果漏掉一个，你就会得到这样的错误：

```text
dukpy.JSRuntimeError: ReferenceError: identifier 'Node'
    undefined
    duk_js_var.c:1258
    eval src/pyduktape.c:1 preventsyield
```

如果你看到这个错误，说明你需要找到该写 `window.Node` 而不是 `Node` 的地方。你还需要修改 `EVENT_DISPATCH_JS`，给类名加上 `window` 前缀：

```python
EVENT_DISPATCH_JS = \
    "new window.Node(dukpy.handle)" + \
    ".dispatchEvent(new window.Event(dukpy.type))"
```

> **怪癖**
> 之前章节的示例也需要类似修整才能工作。例如，`setTimeout` 可能需要改成 `window.setTimeout`。

为了让多个帧的脚本在同一个 JavaScript 上下文里和平共处，我们将创建多个 `Window` 对象：`window_1`、`window_2` 等等。在运行某个帧的脚本之前，我们会把 `window` 设为该帧的 `Window` 对象，这样脚本使用的就是正确的 `Window`。³¹

首先，在创建 `JSContext` 时定义 `Window` 类：

```python
class JSContext:
    def __init__(self, tab, url_origin):
        self.url_origin = url_origin
        # ...
        self.interp.evaljs("function Window(id) { this._id = id };")
```

现在，当一个帧被创建并想使用某个 `JSContext` 时，它需要先请求创建一个 window 对象：

```python
class JSContext:
    def add_window(self, frame):
        code = "var window_{} = new Window({});".format(
            frame.window_id, frame.window_id)
        self.interp.evaljs(code)
class Frame:
    def load(self, url, payload=None):
        # ...
        self.js = self.tab.get_js(url)
        self.js.add_window(self)
        # ...
```

在运行任何 JavaScript 之前，我们要更改 `window` 全局变量指向哪个 window：

```python
class JSContext:
    def wrap(self, script, window_id):
        return "window = window_{}; {}".format(window_id, script)
```

我们可以用它来，例如，为每个 `Frame` 建立初始的运行时环境：

```python
class JSContext:
    def add_window(self, frame):
        # ...
        self.interp.evaljs(self.wrap(RUNTIME_JS, frame.window_id))
```

每当我们使用 `evaljs` 时，都需要调用 `wrap`，这也意味着要给很多方法加上 window ID 参数。例如，在 `run` 中我们会加一个 `window_id` 参数：

```python
class JSContext:
    def run(self, script, code, window_id):
        try:
            code = self.wrap(code, window_id)
            self.interp.evaljs(code)
        except dukpy.JSRuntimeError as e:
            print("Script", script, "crashed", e)
```

并从 `load` 方法传入该参数：

```python
class Frame:
    def load(self, url, payload=None):
        for script in scripts:
            # ...
            task = Task(self.js.run, script_url, body,
                self.window_id)
            # ...
```

各种事件分发 API 也一样。例如，要分发一个事件，我们需要 `window_id`：

```python
class JSContext:
    def dispatch_event(self, type, elt, window_id):
        # ...
        code = self.wrap(EVENT_DISPATCH_JS, window_id)
        do_default = self.interp.evaljs(code,
            type=type, handle=handle)
```

同样，`click`、`submit_form` 和 `keypress` 也需要传递 window ID 参数；这些代码片段我就略去了。注意，你应当已经修改了 runtime.js 文件，把 `LISTENERS` 存在 `window` 对象上，这意味着每个 `Frame` 都有自己的一组可分发的监听器：

```javascript
window.LISTENERS = {}
// ...
window.Node.prototype.dispatchEvent = function(evt) {
    var type = evt.type;
    var handle = this.handle
    var list = (window.LISTENERS[handle] &&
        window.LISTENERS[handle][type]) || [];
    for (var i = 0; i < list.length; i++) {
        list[i].call(this, evt);
    }
    return evt.do_default;
}
```

对 `requestAnimationFrame` 做同样的处理：传递 window ID，并对代码做包装，使它正确引用 `window`。

对于从 JavaScript 到浏览器的调用，我们需要 JavaScript 把它调用所在的 window ID 传进来：

```javascript
window.document = { querySelectorAll: function(s) {
    var handles = call_python("querySelectorAll", s, window._id);
    return handles.map(function(h) { return new window.Node(h) });
}}
```

然后在浏览器这一侧，我们可以用这个 window ID 取回 `Frame` 对象：

```python
class JSContext:
    def querySelectorAll(self, selector_text, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        selector = CSSParser(selector_text).selector()
        nodes = [node for node
                in tree_to_list(frame.nodes, [])
                if selector.matches(node)]
        return [self.get_handle(node) for node in nodes]
```

`innerHTML` 和 `style` 中也需要类似的处理，因为我们需要在相关的 `Frame` 上调用 `set_needs_render`。

最后，对于 `setTimeout` 和 `XMLHttpRequest` 这类「先由 JavaScript 调用浏览器、之后浏览器再回调 JavaScript」的机制，我们同样需要从 JavaScript 传入 window ID，并在回调 JavaScript 时使用该 window ID。本节我省略了许多代码改动，因为它们相当重复。你可以在自己的代码库里搜索 `evaljs`，找到所有需要修改的位置。

现在，我们已经把不同的帧隔离开了。接下来，让它们互动起来。

> **深入探索**
> 同源 iframe 可以访问彼此的状态，跨源的则不能。但一个晦涩的 `domain` [45] 属性允许 iframe 更改自己的源，在某些情况下让自己进入或退出同源状态。我个人认为它是一个误设计：它难以安全地实现，还会干扰各种沙箱技术；我希望它最终能从 web 上移除。作为替代，有各种各样的头 [46] 可以让 iframe 选择减少共享，以换取更好的安全性和性能。

## 15.8　帧间通信（Communicating Between Frames）

我们已经成功地把多个 `Frame` 的 JavaScript 运行在单个 `JSContext` 里，并对它们做了一定程度的隔离，使它们不会弄乱彼此的状态。但这一切的目的，正是允许同源帧之间进行一些交互。现在就来实现它。

两个帧交互的最简单方式，是通过 `Window` 对象上的 `parent` 属性访问彼此的状态。如果两个帧同源，这就让一个帧可以调用另一个帧的方法、访问其变量、修改其浏览器状态。由于我们已让这些同源帧共享一个 `JSContext`，实现起来并不难。基本上，我们需要一种「从一个 window ID 得到其父帧 window ID」的方法：

```python
class JSContext:
    # ...
    def parent(self, window_id):
        parent_frame = \
            self.tab.window_id_to_frame[window_id].parent_frame
        if not parent_frame:
            return None
        return parent_frame.window_id
```

在 JavaScript 一侧，我们现在需要根据 window ID 查找对应的 `Window` 对象。做法有很多，但最简单的是维护一个全局映射表：

```python
class JSContext:
    def __init__(self, tab, url_origin):
        # ...
        self.interp.evaljs("WINDOWS = {}")
```

每个窗口创建时，我们把它加进这个全局映射表：

```python
class JSContext:
    def add_window(self, frame):
        # ...
        self.interp.evaljs("WINDOWS[{}] = window_{};".format(
            frame.window_id, frame.window_id))
```

现在，`window.parent` 就可以在这个全局映射表中查找正确的 `Window` 对象：

```javascript
Object.defineProperty(Window.prototype, 'parent', {
    configurable: true,
    get: function() {
        var parent_id = call_python('parent', window._id);
        if (parent_id != undefined) {
            var parent = WINDOWS[parent_id];
            if (parent === undefined) parent = new Window(parent_id);
            return parent;
        }
    }
});
```

注意，`WINDOWS` 中的查找有可能失败——当父帧与当前帧不同源、因此没有运行在同一个 `JSContext` 中时就会如此。在这种情况下，这段代码会返回一个具有该 id 的全新 `Window` 对象。但 iframe 是不允许跨源访问彼此的文档的（也不允许调用各种其他不安全的 API），所以要添加一个方法来检查这种情况并抛出异常：

```python
class JSContext:
    def throw_if_cross_origin(self, frame):
        if frame.url.origin() != self.url_origin:
            raise Exception(
                "Cross-origin access disallowed from script")
```

然后，在所有访问文档的 `JSContext` 方法中使用它：³²

```python
class JSContext:
    def querySelectorAll(self, selector_text, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...
    def setAttribute(self, handle, attr, value, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...
    def innerHTML_set(self, handle, s, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...
    def style_set(self, handle, s, window_id):
        frame = self.tab.window_id_to_frame[window_id]
        self.throw_if_cross_origin(frame)
        # ...
```

于是，同源 iframe 可以通过 `parent` 通信。那跨源 iframe 呢？允许它们访问彼此的变量或调用彼此的方法是不安全的，所以浏览器转而允许一种消息传递（message passing）[47] 机制——这是一种在两个不同事件循环之间进行结构化通信的技术，不需要任何共享状态或锁。

JavaScript 中的消息传递是这样工作的：你在想与之对话的 `Window` 对象上调用 `postMessage` API [48]，消息本身作为第一个参数，第二个参数是 `*`：³³

```javascript
window.parent.postMessage("...", '*')
```

这会把第一个参数³⁴发送给父帧，父帧通过在其 `Window` 对象上处理 `message` 事件来接收消息：

```javascript
window.addEventListener("message", function(e) {
    console.log(e.data);
});
```

注意，在第二个代码片段中，`window` 是接收方的 `Window`，与第一个片段中的 `window` 是不同的 `Window`。

来实现 `postMessage`，先从接收方开始。由于这个事件发生在 `Window` 上而不是 `Node` 上，我们需要一个新的 `WINDOW_LISTENERS` 数组：

```javascript
window.WINDOW_LISTENERS = {}
```

每个监听器都会收到一个 `MessageEvent` 对象：

```javascript
window.MessageEvent = function(data) {
    this.type = "message";
    this.data = data;
}
```

事件监听与分发代码和 `Node` 的相同，只是位于 `Window` 上并使用 `WINDOW_LISTENERS`。直接复制那些方法即可：

```javascript
Window.prototype.addEventListener = function(type, listener) {
    // ...
}
Window.prototype.dispatchEvent = function(evt) {
    // ...
}
```

接收方就这么多；现在来看发送方。首先实现 `postMessage` API 本身。注意，这里的 `this` 是接收方，即目标窗口：

```javascript
Window.prototype.postMessage = function(message, origin) {
    call_python("postMessage", this._id, message, origin)
}
```

在浏览器中，`postMessage` 会在 `Tab` 上调度一个任务：

```python
class JSContext:
    def postMessage(self, target_window_id, message, origin):
        task = Task(self.tab.post_message,
            message, target_window_id)
        self.tab.task_runner.schedule_task(task)
```

调度任务是必要的，因为 `postMessage` 是一个异步 API；发送同步消息可能需要同步多个 `JSContext`、甚至多个进程，这会带来大量开销，并且很可能导致死锁。

这个任务会找到目标帧并调用一个分发方法：

```python
class Tab:
    def post_message(self, message, target_window_id):
        frame = self.window_id_to_frame[target_window_id]
        frame.js.dispatch_post_message(
            message, target_window_id)
```

后者再调用我们刚写的 JavaScript `dispatchEvent` 方法：

```python
POST_MESSAGE_DISPATCH_JS = \
    "window.dispatchEvent(new window.MessageEvent(dukpy.data))"
class JSContext:
    def dispatch_post_message(self, message, window_id):
        self.interp.evaljs(
            self.wrap(POST_MESSAGE_DISPATCH_JS, window_id),
            data=message)
```

现在，你应该可以使用 `postMessage` 在帧之间安全地发送消息了，³⁵ 包括运行在不同 `JSContext` 中的跨源帧。

> **深入探索**
> 广告通常通过 iframe 投放，是 web 沙箱、嵌入和动画原语的重度用户。因此，它们是性能与用户体验 [51] 问题的一个棘手来源。例如，广告分析 [52] 对广告经济很重要，却涉及运行大量代码和测量大量数据。一些 web API（比如 Intersection Observer [53]）的存在，基本上就是为了让分析计算更高效。当然，广告拦截器大概是最受欢迎的浏览器扩展 [54]。

## 15.9　隔离与时序（Isolation and Timing）

iframe 在第 10 章讨论的内容之上，又增添了一整套新的安全挑战。把一个网页嵌入另一个网页的能力，在两个页面互不信任时会带来同等大小的安全风险——无论是把不受信任的页面嵌入你自己的页面，还是反过来，攻击者把你的页面嵌入他们自己的恶意页面。无论哪种情况，我们都想保护你的页面免受另一个帧带来的任何安全或隐私风险。³⁶

出发点是：跨源 iframe 无法通过 JavaScript 直接相互访问。这很好——但如果 JavaScript 引擎中的一个漏洞（比如缓冲区溢出（buffer overrun）[55]）让 iframe 绕过了这些保护呢？不幸的是，这类漏洞相当常见，浏览器必须对其设防。例如，如今的浏览器会把来自不同源的帧放在不同的操作系统进程中运行，并利用操作系统的特性来限制这些进程的访问权限。

浏览器的其他部分会混合多个帧的内容，比如我们浏览器中标签页级别的显示列表。这意味着，光栅化器（rasterizer）中的一个漏洞可能让一个帧接管光栅化器，进而读取最终来自另一个帧的数据。这看起来像是一种相当复杂的攻击，但它确实发生过，所以现代浏览器使用沙箱（sandboxing）[56] 技术来防范。例如，Chromium 可以把光栅化器放进自己的进程，并用一个叫做 seccomp 的 Linux 特性来限制该进程可以发起哪些系统调用。这样一来，即使某个漏洞攻陷了光栅化器，这个光栅化器也无法通过网络外传数据，从而防止隐私数据泄露。

这些隔离与沙箱特性看起来可能「简单直接」，就像我们在第 13 章添加的浏览器线程「简单直接」一样。但实际上，浏览器 API 之多意味着实现中充满微妙之处，最终会变得极其复杂。例如，Chromium 花了很多年才发布第一个站点隔离（site isolation）[28] 的实现。

近年来，由于被称为 Spectre 和 Meltdown [57] 的 CPU 缓存时序攻击，站点隔离变得重要得多。简而言之，这类攻击让攻击者可以通过测量某些 CPU 操作的耗时，读取内存中任意位置的数据——如果两个帧在同一个进程中，还包括另一个帧的数据。把敏感内容放进不同的 CPU 进程（它们各自拥有独立的内存地址空间）是对这类攻击的良好防护。

话虽如此，这类时序攻击可能非常微妙，无疑还有更多尚未被发现。为了削弱这一威胁，如今的浏览器会阻止访问高精度计时器，因为它们能提供时序攻击通常所需的精确计时数据。例如，浏览器降低了 `Date.now`、`setTimeout` 等 API 的精度。

更糟的是，有些浏览器 API 看起来不像计时器，却可以被用作计时器。³⁷ 这些 API 很有用，浏览器并不想移除它们；但也没有办法让它们「精度更低」，因为它们本来就不是时钟。浏览器现在要求父帧和子帧的 HTTP 响应中带上某些可选的 HTTP 头 [60]，才特别允许使用 `SharedArrayBuffer`，尽管这并非完美的解决方案。

> **深入探索**
> 当我为这个网站 [62] 上的嵌入式浏览器部件 [61] 添加 JavaScript 支持时，`SharedArrayBuffer` 问题就造成了麻烦。我用 `SharedArrayBuffer` 来支持从 `JSContext` 到浏览器的同步调用，而这需要用到浏览器出于安全原因加以限制的 API。设置安全头行不通，因为第 14 章嵌入了一个 YouTube 视频，而在我写作本书时，YouTube 并不发送这些头。最后，我的解决办法是不嵌入浏览器部件，而是请读者 [63] 打开一个新的浏览器窗口。

## 15.10　总结（Summary）

本章介绍了浏览器如何处理图像和 iframe 等嵌入式内容用例。重申要点：

- 非 HTML 的嵌入式内容——图像、视频、canvas、iframe、input 元素和插件——都可以嵌入网页。
- 嵌入式内容带来它自身的性能问题——比如图像解码时间——需要专门的优化。
- iframe 是特别重要的一类嵌入式内容，随着时间推移，它取代了浏览器插件，成为把复杂内容轻松嵌入网页的标准方式。
- iframe 把 web 的全部复杂性——渲染、事件处理、导航、安全——引入浏览器对嵌入式内容的处理。不过，这种复杂性是合理的，因为它们支撑起广告、视频和社交媒体按钮等重要的跨源用例。

而且，正如我们希望你在本章看到的，这些功能没有哪个实现起来太难——不过，正如你将在练习中看到的，要把它们实现好，需要大量对细节的关注。

## 15.12　练习（Exercises）

### 练习 15.1　Canvas 元素（Canvas element）

实现 `<canvas>` 元素、`getContext` [64] API 的 2D 部分，以及 `CanvasRenderingContext2D` [65] 上的一些绘制命令。Canvas 的布局与 iframe 一样，包括默认的宽度和高度。你应当在调用 `getContext("2d")` 时分配一个尺寸合适的 Skia 表面（surface），并实现一些向 canvas 绘制的 API。³⁸ 大多数 API 方法到 Skia 等价物的转换都应该是直截了当的。

### 练习 15.2　背景图像（Background images）

元素可以有 background-image [67]。实现这个 CSS 属性的基础部分：`background-image` 属性的 `url(...)` 值。如果 `background-image` 属性实际上没有被任何元素用到，请避免加载该图像。想要更大的挑战，还可以让网页通过 `background-size` [68] CSS 属性设置背景图像的尺寸。

### 练习 15.3　object-fit

实现 `object-fit` [69] CSS 属性。它决定 `<img>` 元素中的图像相对于其容器元素的尺寸调整方式。这需要裁剪宽高比不同的图像。

### 练习 15.4　懒加载（Lazy loading）

下载图像可能消耗不少流量。³⁹ 虽然浏览器默认会立即下载页面上的所有图像，但 img 元素上的 `loading` 属性 [70] 可以指示浏览器只下载那些接近页面可见区域的图像。这种优化一般称为懒加载（lazy loading）[71]。请实现 `loading`。确保图像加载完成之前和之后，页面都能被正确布局。

### 练习 15.5　Iframe 宽高比（Iframe aspect ratio）

实现 `aspect-ratio` CSS 属性，并在只指定 `width` 或 `height` 之一时（如果你做了练习 15.4，也包括图像尚未加载时），用它为 iframe 和图像提供隐式尺寸。

### 练习 15.6　图像占位符（Image placeholders）

在懒加载的基础上，实现尚未加载图像的占位样式。做法是设置 0 × 0 的尺寸，除非指定了 `width` 或 `height`。另外，如果缺少 `alt` 属性或 `alt` 为空，还要支持隐藏「碎图」。⁴⁰

### 练习 15.7　媒体查询（Media queries）

实现 `width` [72] 媒体查询。确保它在 iframe 内部也有效。还要确保即使 iframe 的宽度被其父帧改变，它也依然有效。

### 练习 15.8　postMessage 的目标源（Target origin for postMessage）

实现 `postMessage` 的 `targetOrigin` 参数。该参数是一个字符串，指明允许接收消息的帧的源。

### 练习 15.9　多帧焦点（Multi-frame focus）

在我们的浏览器中，按 Tab 键会在聚焦帧内部的元素之间循环。但这意味着，只靠键盘无法访问其他帧中的可聚焦元素。请修复它：在一帧中遍历完所有可聚焦元素后，移动到其他帧。

### 练习 15.10　Iframe 历史（Iframe history）

确保 iframe 会影响浏览器历史。例如，如果你点击 iframe 内的一个链接，然后按后退按钮，应当在 iframe 内部后退。还要确保当用户以不同顺序点击多个帧中的链接时，它也能正确工作。⁴¹

### 练习 15.11　由脚本增删 iframe（Iframes added or removed by script）

`innerHTML` API 可能导致 iframe 被添加或删除，但我们的浏览器在这种情况发生时并不会加载或卸载它们。请修复这个问题：新的 iframe 应被加载，旧的 iframe 应被卸载。

### 练习 15.12　X-Frame-Options

实现这个头 [73]，它禁止一个网页出现在 iframe 中。
