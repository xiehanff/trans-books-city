# 第 16 章　复用先前的计算

*Chapter 16: Reusing Previous Computations*

合成（compositing，见第 13 章）让动画更流畅，但它对那些会影响布局的交互——比如文本编辑或 DOM 修改——无能为力。幸运的是，我们可以把布局树（layout tree）当作一种缓存（cache），只重新计算发生变化的部分，从而避免冗余的布局工作。这种失效（invalidation）技术传统上既复杂又容易出 bug，但我们会采用一种有原则的方法和简单的抽象，让它变得可控。

## 16.1 编辑内容

在第 13 章中，我们用合成来平滑地动画化 transform 或 opacity 这类 CSS 属性。但我们无法以这种方式动画化 width 或 font-size 这类会引发布局（layout-inducing）的属性，因为它们不仅改变显示列表（display list），还会改变布局树。虽然最好避免动画化会引发布局的属性，但许多会改变布局树的用户交互都需要保持响应灵敏。

文本编辑就是一个很好的例子。人们打字相当快，所以哪怕几帧的延迟都会让人分心。但编辑会改变 HTML 树，进而改变布局树。我们的浏览器目前每次都是从头重建布局树，这在复杂页面上可能非常慢。举个例子，在我们的浏览器中加载本章的网页版 [1]，并在本段之后出现的输入框中打字……你会发现它实在太慢了——光是 render 就要 1.7 秒（见图 16.1）！

*图 16.1　未做任何失效优化时打字的示例。*

在 input 元素中打字这种情形本可以特判处理，¹ 但还有一些文本编辑 API 无法特判。例如，contenteditable 属性可以让任何元素变得可编辑。²

让我们在浏览器中实现一个最基础版本的 contenteditable——它既是一个实用的特性，也是对失效机制的一次很好的检验。首先，我们需要让带 contenteditable 属性的元素可以聚焦（focusable）：³

聚焦到可编辑节点之后，打字应当能编辑它。真实的浏览器会处理光标移动和各种复杂情况，但我会保持简单，只是把每个字符追加到可编辑元素的最后一个文本节点上。首先我们需要找到那个文本节点：

注意，如果可编辑元素没有文本子节点，我们就新建一个。然后，把输入的字符添加到这个元素上：


这已经足以让编辑工作了，不过再画一个光标会更方便——它能确认该元素已聚焦，并显示编辑将发生的位置。让我们在 BlockLayout 中完成这件事：

## 16.2 为什么要失效？

从根本上说，在我们的浏览器里编辑这个页面之所以慢，是因为页面相当大。毕竟，慢的不是处理按键：向 Text 节点追加一个字符几乎不花时间。花时间的是之后重新渲染整个页面。

我们希望交互即使在巨大而复杂的页面上也足够快，所以我们希望重新渲染页面的时间与改动的规模成正比，而不是与页面的规模成正比。我把这称为增量性能原则（principle of incremental performance），它对处理大型复杂的 Web 应用至关重要。它不仅让文本编辑变快，还意味着开发者可以一次只考虑一个改动的性能影响，而不必考虑整个页面的内容。因此，增量性能对复杂应用是必需的。

但增量性能原则也切实约束了我们的浏览器实现。例如，甚至遍历整个布局树所花的时间都与整个页面成正比，而不是与所做的改动成正比，所以我们连这一点都负担不起。

为了实现增量性能，我们需要区别对待初始渲染与后续的重新渲染。⁴ 页面首次加载时，渲染所花的时间与页面大小成正比。但我们会把初始渲染当作一个缓存。后续的渲染会让这个缓存的一部分失效并重新计算，所花时间与改动的大小成正比，却不会触及页面的大部分内容。⁵ 在真实浏览器中，渲染管线的每一步都需要做到增量，但本章聚焦于布局。⁶

这种「缓存并失效」方法的关键在于追踪改动的效应。当页面的某个部分（比如某个 style 属性）变化时，依赖它的其他东西（比如该元素的尺寸）也会随之变化。所以我们需要构建一张细致的依赖图（dependency graph），细到每个布局字段的层面，并用这张图来决定重新计算什么。它类似于我们的 needs_style 和 needs_layout 标志，只是规模大幅提升。因此，本章的大部分内容都是关于在依赖图中追踪依赖关系，并构建能帮助我们的抽象。

为了使用这些抽象，我们需要大幅重构布局引擎。但让布局增量化能让我们跳过布局中最昂贵的两个部分：构建布局树，以及遍历它来计算布局字段。完成之后，对于文本编辑这样的小改动，重新布局将在一毫秒以内完成。

> **深入探索**
> 增量性能原则是让浏览器成为一个优秀平台的部分原因。请记住，Web 是声明式的：网页只负责描述页面看起来什么样，而实现这份描述是浏览器的职责。对我们浏览器工程师来说，这带来了大量复杂性。但从 Web 整体来想一想——它不仅涉及浏览器工程师，还涉及 Web 开发者和用户。在浏览器中实现复杂的失效算法，让 Web 开发者可以专注于做出更有趣的应用，也给用户更好、更灵敏的体验。声明式的 Web 让失效算法只需编写一次，然后自动让所有人受益。

## 16.3 幂等性

如果想实现这种「缓存并失效」的思路，第一个拦路虎是我们的浏览器每次运行布局阶段时都会从头重建布局树：

```python
class Frame:
    def render(self):
        if self.needs_layout:
            self.document = DocumentLayout(self.nodes, self)
            self.document.layout(self.frame_width, self.tab.zoom)
            # ...
```

每次都新建一个 DocumentLayout 从头开始，意味着我们丢弃了所有旧的布局信息、从零开始；这实际上等于把整棵树全部失效。所以我们的第一个优化必须避免这一点，尽可能复用布局对象。这既节省了分配内存的时间，又因为保留了旧的布局信息而使「缓存并失效」方法成为可能。

不过在动手写代码之前，先回顾一下布局对象是如何创建的。在你的浏览器代码中搜索 Layout——所有布局类的名字都以它结尾。你应该会看到布局对象只在少数几个地方被创建：

- DocumentLayout 对象由 Frame 在 render 中创建；
- BlockLayout 对象由以下两者之一创建：
  - DocumentLayout，在 layout 中；或
  - BlockLayout，在 layout 中；
- LineLayout 对象由 BlockLayout 在 new_line 中创建；
- 其余所有对象都由 BlockLayout 在 add_inline_child 中创建。

先从 DocumentLayout 开始。它在 render 中创建，而它的两个参数 nodes 和 self 每次都相同。这意味着每次都会创建出一模一样的 DocumentLayout。⁷ 这很浪费；让我们只在 load 中创建一次 DocumentLayout：

```python
class Frame:
    def load(self, url, payload=None):
        # ...
        self.document = DocumentLayout(self.nodes, self)
        self.set_needs_render()
    def render(self):
        if self.needs_layout:
            self.document.layout(self.frame_width, self.tab.zoom)
            # ...
```

接下来，看看 DocumentLayout 在哪里构造 BlockLayout：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        child = BlockLayout(self.node, self, None, self.frame)
        # ...
```

构造参数同样不可能改变，所以同样可以跳过对这个布局对象的重建，像这样：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        if not self.children:
            child = BlockLayout(self.node, self, None, self.frame)
        else:
            child = self.children[0]
        # ...
```

先别急着带着这些改动运行浏览器！复用布局对象意味着我们会在同一个对象上多次运行 layout。布局并不是被设计成这样工作的，这会导致各种奇怪的行为。例如，DocumentLayout 创建子 BlockLayout 之后会把它追加（append）到 children 数组：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        # ...
        self.children.append(child)
        # ...
```

但我们不想把同一个子对象追加不止一次！

这里的问题叫作幂等性（idempotence）：对 layout 的重复调用不应反复改变状态。更正式地说，如果一个函数连续调用两次，只要输入和依赖相同就得到相同的结果，它就是幂等的（idempotent）。给字段赋值是幂等的：第二次赋相同的值是无操作（no-op）。但 append 这类方法不是幂等的。

我们需要修复所有非幂等的方法调用。在 DocumentLayout 中，我们可以把 append 改成赋值：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        # ...
        self.children = [child]
        # ...
```

BlockLayout 也在它的 children 数组上调用 append。我们可以通过在 layout 中重置 children 数组来修复。我会分别在 block 和 inline 两种情形下放置各自的重置代码：

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            self.children = []
            # ...
        else:
            self.children = []
            # ...
```

这让 BlockLayout 的 layout 函数变成幂等的，因为每次调用都会赋一个新的 children 数组。

在试运行浏览器之前，让我们通读所有其他布局方法，记下任何可能不幂等的子程序调用。我找到了：⁸

- 在 new_line 中，BlockLayout 会向它的 children 数组追加元素。
- 在 add_inline_child 中，BlockLayout 会向某个 LineLayout 子对象的 children 数组追加元素。
- 在 add_inline_child 中，BlockLayout 会调用 get_font，TextLayout 和 InputLayout 的方法也会调用它。
- 基本上每个布局方法都会调用 dpx。

new_line 和 add_inline_child 只会通过 layout 被调用，而 layout 会重置 children 数组，所以它们不会破坏幂等性。get_font 函数本身就是一个缓存，多次调用会返回同一个字体对象，保持了幂等。而 dpx 只是做算术，给定相同输入总是返回相同结果。换句话说，我们所有的布局方法现在都是幂等的。

因此，在同一个对象上多次调用 layout 是安全的——而这正是我们现在在做的事。更一般地，既然一个幂等函数被调用多少次都无所谓，我们就可以跳过多余的调用！这使得幂等性成为本章其余部分的基础——本章讲的全是跳过冗余工作。

> **深入探索**
> HTTP 也有一个幂等性的概念 [5]，但它与我们这里讨论的概念有微妙的区别，因为 HTTP 同时涉及客户端和服务器。在 HTTP 中，幂等性只覆盖请求对服务器状态的影响，而不覆盖响应。例如，用 GET 两次请求同一个页面可能得到不同的响应（如果页面变了），但这个请求仍是幂等的，因为它没有对服务器做出任何改变。而且 HTTP 的幂等性也只覆盖客户端可见的状态，所以比如第一次 GET 请求可能命中缓存而第二次没有，或者每次请求可能各自添加一条日志，这些都无妨。

## 16.4 依赖

到目前为止，我们只复用了两个布局对象：DocumentLayout 和根 BlockLayout。来看看其他的 BlockLayout，它们是在这里创建的：

```python
class BlockLayout:
    def layout(self):
        self.children = []
        # ...
        if mode == "block":
            previous = None
            for child in self.node.children:
                next = BlockLayout(child, self, previous, self.frame)
                self.children.append(next)
                previous = next
        # ...
```

这段代码比创建根 BlockLayout 的代码复杂一些：child 和 previous 参数来自 node.children，而这个 children 数组是可能变化的——比如 contenteditable 编辑或 innerHTML 调用。⁹ 此外，为了运行这段代码，节点的 layout_mode 必须是 block，而 layout_mode 本身也会读取节点的 children。¹⁰ 这让我们更难知道什么时候需要重建这些 BlockLayout。

回想一下，幂等性意味着在输入和依赖相同的情况下再次调用函数会得到相同的结果。这里输入可能变化，所以只有当节点的 children 字段没有变化时，我们才能避免多余的重复执行。于是我们需要一种能知道 children 字段是否变化的方法。我们将使用一个脏位（dirty flag）：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.children_dirty = True
```

我们以前见过脏位——比如 needs_layout 和 needs_draw——但布局更复杂，我们需要更严谨地思考脏位。每个脏位保护某个特定的字段；这个脏位保护的是 BlockLayout 的 children 字段。脏位有一个生命周期：它可以被置位（set）、检查（check）和复位（reset）。脏位初始为 True，当字段的一个输入或依赖变化时被置为 True，把受保护的字段标记为不可用。然后，在使用受保护字段之前必须检查脏位。只有当受保护字段被重新计算后，脏位才复位为 False。

那就用这种方式来分析 children_dirty 脏位。如果脏位所保护字段的任何依赖发生变化，脏位就必须被置位。在这里，这个脏位保护 BlockLayout 的 children 字段，而后者又依赖相关联 Element 的 children 字段。这意味着，任何时候修改 Element 的 children 字段，我们都需要为相关联的 BlockLayout 置位脏位：

```python
class JSContext:
    def innerHTML_set(self, handle, s, window_id):
        # ...
        obj = elt.layout_object
        while not isinstance(obj, BlockLayout):
            obj = obj.parent
        obj.children_dirty = True
```

同样，每当编辑 contenteditable 元素时也要置位脏位，因为这同样可能影响节点的 children：

```python
class Frame:
    def keypress(self, char):
        elif self.tab.focus and \
            "contenteditable" in self.tab.focus.attributes:
            # ...
            obj = self.tab.focus.layout_object
            while not isinstance(obj, BlockLayout):
                obj = obj.parent
            obj.children_dirty = True
```

受保护字段的所有依赖都置位脏位，这一点很重要。这可能很有挑战，因为它要求我们对哪些字段依赖哪些字段保持警惕。但如果我们忘记置位脏位，有时就会漏掉对受保护字段的重新计算，这意味着页面会显示错误。这类 bug 通常表现为不可预测的布局故障，而且非常难以调试——所以我们必须小心。

好，现在我们会置位脏位了，下一步是在使用受保护字段之前检查它。BlockLayout 在三个地方使用它的 children 字段：递归对所有子对象调用 layout、计算自身高度，以及绘制自身。让我们在每个地方都加一个检查：

```python
class BlockLayout:
    def layout(self):
        # ...
        assert not self.children_dirty
        for child in self.children:
            child.layout()
        assert not self.children_dirty
        self.height = sum([child.height for child in self.children])
    def paint(self, display_list):
        assert not self.children_dirty
        # ...
```

跳过这些断言（assertion）很诱人，毕竟它们本不该被触发，但这样的防御式编程能更早抓住 bug，也让调试更容易。以错误的顺序让字段失效，或者在某个其实很关键的时刻跳过计算，都很容易发生——你宁愿那触发一次崩溃，而不是一次微妙而错误的渲染——至少在调试一个玩具浏览器时是这样！¹¹

最后，当字段被重新计算后，我们需要复位脏位。在这里，我们在重新计算完 children 数组后复位脏位：

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            # ...
            self.children_dirty = False
        else:
            # ...
            self.children_dirty = False
```

至此，脏位生命周期的三个环节都完成了，你应该可以运行浏览器并在本章页面上测试它。即使编辑文本或调用 innerHTML，也不应看到任何断言失败。增量地推进并频繁测试——这会让调试更容易。

现在 children_dirty 脏位正确工作了，我们可以依靠它来避免冗余工作。如果 children 不脏，我们就不需要重建 BlockLayout 的子对象：

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            if self.children_dirty:
                # ...
                self.children_dirty = False
```

如果你在最内层那个 if 里加一条 print 语句，就会在每次创建 BlockLayout 子对象时看到控制台输出。在编辑文本时试一下：它应当完全不会发生，编辑也会稍微流畅一些。

## 16.5 受保护字段

像 children_dirty 这样的脏位是布局失效的传统做法，但它有缺点。正确使用它们意味着要留意字段之间的依赖关系，知道每个字段何时被读、何时被写。而且很容易忘记检查或置位一个脏位，从而导致难以发现的 bug。在我们这个简单的浏览器里或许还做得来，但真实浏览器的布局系统要复杂得多，错误几乎不可避免。

存在一种更好的方法。首先，让我们试着把脏位与它所保护的字段合并成一个对象：

```python
class ProtectedField:
    def __init__(self):
        self.value = None
        self.dirty = True
```

这就明确了哪个脏位保护哪个字段。让我们用 ProtectedField 替换现有的脏位：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.children = ProtectedField()
        # ...
```

接下来，为脏位生命周期的每一步添加方法。我会说，我们标记（mark）一个受保护字段来置位它的脏位：

```python
class ProtectedField:
    def mark(self):
        if self.dirty: return
        self.dirty = True
```

注意那个提前返回：标记一个已经脏了的字段什么也不做。这一点稍后会变得重要。现在，在 innerHTML_set 和 keypress 中调用 mark：

```python
class JSContext:
    def innerHTML_set(self, handle, s, window_id):
        # ...
        obj.children.mark()
class Frame:
    def keypress(self, char):
        elif self.tab.focus and \
            "contenteditable" in self.tab.focus.attributes:
            # ...
            obj.children.mark()
```

在「get」一个 ProtectedField 的值之前，先检查脏位：

```python
class ProtectedField:
    def get(self):
        assert not self.dirty
        return self.value
```

现在我们可以在 layout 以及除此之外的很多地方用 get 来读取 children 字段：

```python
class BlockLayout:
    def layout(self):
        # ...
        for child in self.children.get():
            child.layout()
        self.height = \
            sum([child.height for child in self.children.get()])
```

get 的好处是它让脏位操作自动化，因而不可能被忘记。它还让代码更易读一点。

最后，为了复位脏位，我们让调用者在「set」字段时传入一个新值。这保证了脏位和值总是一起更新：

```python
class ProtectedField:
    def set(self, value):
        self.value = value
        self.dirty = False
```

遗憾的是，使用 set 需要做一点重构。例如在 BlockLayout 中，我们需要在一个局部变量中构建 children 数组，最后再把它 set 到 children 字段上：

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            if self.children.dirty:
                children = []
                previous = None
                for child in self.node.children:
                    next = BlockLayout(
                        child, self, previous, self.frame)
                    children.append(next)
                    previous = next
                self.children.set(children)
```

但好处是，set 与 get 一样把脏位操作自动化了，使它们不容易搞砸。这让我们有可能去思考更复杂、更有雄心的失效算法，从而让布局更快。

> **深入探索**
> 失效不足（under-invalidation）[8] 是「在改变依赖时忘记置位字段的脏位」的技术名称。它经常引发这样一种 bug：某个改动必须重复多次才能最终「生效」。换句话说，这种 bug 造成了意外的非幂等性！这类 bug 很难发现 [9]，因为它们通常只在特定的改动序列下才会出现。

## 16.6 递归失效

让我们借助 ProtectedField 类来避免每次行内布局都重建全部 LineLayout 及其子对象。一切从这里开始：

```python
class BlockLayout:
    def layout(self):
        if mode == "block":
            # ...
        else:
            self.children = []
            self.new_line()
            self.recurse(self.node)
```

new_line 和 recurse 方法，以及它们调用的 word、input、iframe、image 和 add_inline_child 等辅助方法，负责换行（line wrapping）：它们检查宽度、创建新行等等。如果 children 字段不脏，我们想跳过这一切，但这会比块级布局模式的情形更有挑战：换行过程中会读取很多不同的字段，而 children 字段依赖所有这些字段。把所有这些字段都改造成 ProtectedField 将是一项有挑战的工程。

我们会一步一步来，先从 zoom 开始——几乎每个方法都会读它。缩放级别最初是在 DocumentLayout 中设置的：

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.zoom = ProtectedField()
        # ...
    def layout(self, width, zoom):
        # ...
        self.zoom.set(zoom)
        # ...
```

每个 BlockLayout 也有自己的 zoom 字段，我们可以保护它：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.zoom = ProtectedField()
        # ...
```

不过在 BlockLayout 中，zoom 的值来自其父对象的 zoom 字段。我们可能会想写成这样：

```python
class BlockLayout:
    def layout(self):
        parent_zoom = self.parent.zoom.get()
        self.zoom.set(parent_zoom)
        # ...
```

但请记住，对于脏位我们必须始终考虑置位它（用 mark）、检查它（用 get）和复位它（用 set）。我们加上了 get 和 set，可是谁来标记 zoom 的脏位呢？¹²

当一个字段的依赖变化时，我们标记它的脏位。例如，innerHTML_set 和 keypress 改变 HTML 树，而布局树的 children 字段依赖 HTML 树，所以这些处理器会调用 children 字段上的 mark。既然子对象的 zoom 字段依赖其父对象的 zoom 字段，当 zoom 字段变化时我们就需要标记所有子对象。所以在 DocumentLayout 中，我们必须这样做：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        # ...
        self.zoom.set(zoom)
        child.zoom.mark()
        # ...
```

类似地，在拥有多个子对象的 BlockLayout 中，我们必须这样做：

```python
class BlockLayout:
    def layout(self):
        # ...
        for child in self.children.get():
            child.zoom.mark()
```

但这样一来，我们又回到了手动调用方法、努力不漏掉任何调用的老路。我们需要的是一种无缝的做法：set 一个字段时，应当自动标记所有依赖它的字段。

为此，每个 ProtectedField 都需要追踪所有依赖它的字段，它们被称为它的失效目标（invalidations）：

```python
class ProtectedField:
    def __init__(self):
        # ...
        self.invalidations = set()
```

例如，我们可以把子对象的 zoom 字段加入其父对象 zoom 字段的 invalidations：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.parent.zoom.invalidations.add(self.zoom)
```

然后，为了自动化 mark 调用，我们添加一个 notify 方法来标记每个失效目标：

```python
class ProtectedField:
    def notify(self):
        for field in self.invalidations:
            field.mark()
```

然后 set 就可以自动调用 notify：

```python
class ProtectedField:
    def set(self, value):
        self.notify()
        self.value = value
        self.dirty = False
```

这是一种进步，但仍然可能从一开始就忘记添加失效关系。我们可以进一步自动化。想一想：为什么子对象的 zoom 需要依赖父对象的？因为我们在计算子对象的 zoom 时会读取父对象的。所以添加失效关系这件事可以作为 get 的一部分来完成！让我们做一个 get 的变体，叫作 read，它带一个 notify 参数，表示被读取的字段一旦变化时要让哪个字段失效：

```python
class ProtectedField:
    def read(self, notify):
        self.invalidations.add(notify)
        return self.get()
```

现在 zoom 的计算只需要用 read，所有标记和依赖逻辑都会被自动处理：

```python
class BlockLayout:
    def layout(self):
        parent_zoom = self.parent.zoom.read(notify=self.zoom)
        self.zoom.set(parent_zoom)
```

实际上，这种「直接复制父对象的值」的模式相当常见，所以我们为它加一个快捷方式：

```python
class ProtectedField:
    def copy(self, field):
        self.set(field.read(notify=self))
class BlockLayout:
    def layout(self):
        self.zoom.copy(self.parent.zoom)
        # ...
```

BlockLayout 还会在 input、image、iframe、word 和 add_inline_child 这些方法中读取 zoom 字段，而它们都是计算 children 字段的一部分。在这些方法中，我们可以用 read 既得到 zoom 的值，又在 zoom 值将来变化时让 children 字段失效：

```python
class BlockLayout:
    def input(self, node):
        zoom = self.zoom.read(notify=self.children)
        # ...
```

在上面提到的其他每个方法中做同样的事情。另外，去保护其他每种布局对象类型上的 zoom 字段（现在的种类已经不少了！），用 copy 代替写入、用 read 代替直接读取。运行你的浏览器，确保即使放大或缩小缩放级别也不会崩溃，以确保你做对了。

现在——保护 zoom 字段并没有让浏览器变快。我们仍在到处复制缩放级别，而且还多了一些检查脏位和更新失效关系的工作。但保护 zoom 字段意味着当缩放级别变化时，我们可以让 children 以及依赖它的其他字段失效，这有助于判断什么时候必须重建 LineLayout 和 TextLayout 元素。

> **深入探索**
> 真实浏览器（至少目前）并不使用像 ProtectedField 这样的自动依赖追踪。原因之一是性能：ProtectedField 会增加大量对象和方法调用，很容易因为过度使用而意外让性能变差。让太多受保护字段失效也可能造成级联式的工作量。最后，大多数浏览器引擎代码库里有大量历史代码，把它们重构成新的做法需要大量时间。

## 16.7 保护宽度

换行依赖的另一个字段是 width。让我们把它也改造成 ProtectedField，并顺便用上新的 read 方法。与 zoom 一样，width 最初是在 DocumentLayout 中设置的：

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.width = ProtectedField()
        # ...
    def layout(self, width, zoom):
        # ...
        self.width.set(width - 2 * dpx(HSTEP, zoom))
        # ...
```

然后，BlockLayout 从父对象复制它：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.zoom = ProtectedField()
        # ...
    def layout(self):
        # ...
        self.width.copy(self.parent.width)
        # ...
```

width 字段在换行过程中会被读取。例如，add_inline_child 需要它来判断是否要另起一行。我们将用 read 建立这个依赖：

```python
class BlockLayout:
    def add_inline_child(self, node, w, child_class,
        frame, word=None):
        width = self.width.read(notify=self.children)
        if self.cursor_x + w > width:
            self.new_line()
        # ...
```

顺便说一句，是否另起一行的决定还取决于 w，它是 add_inline_child 的一个输入。如果你翻看 add_inline_child 的调用者，会发现大多数情况下这个参数只依赖 zoom，但在 word 中它依赖一个字体对象：

```python
class BlockLayout:
    def word(self, node, word):
        zoom = self.zoom.read(notify=self.children)
        node_font = font(node.style, zoom)
        w = node_font.measureText(word)
        self.add_inline_child(
            node, w, TextLayout, self.frame, word)
```

注意，字体依赖节点的样式（style），而样式是可能变化的，比如通过 style_set 函数。为了处理这一点，我们需要保护 style：

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.style = ProtectedField()
        # ...
class Text:
    def __init__(self, text, parent):
        # ...
        self.style = ProtectedField()
        # ...
```

style 字段是在 style 方法中计算的，该方法分多个阶段计算出一个新的样式字典。让我们在一个局部变量里构建这个新字典，最后再设置它：

```python
def style(node, rules, frame):
    old_style = node.style.value
    new_style = {}
    # ...
    node.style.set(new_style)
    for child in node.children:
        style(child, rules, frame)
```

在 style 内部，有一条代码路径会读取父节点的样式。我们需要在这些情况下标记依赖：

```python
def style(node, rules, frame):
    for property, default_value in INHERITED_PROPERTIES.items():
        if node.parent:
            parent_style = node.parent.style.read(notify=node.style)
            new_style[property] = parent_style[property]
        else:
            new_style[property] = default_value
```

然后 style_set 就可以标记 style 字段：¹³

```python
class JSContext:
    def style_set(self, handle, s, window_id):
        # ...
        elt.style.mark()
```

最后，在 word（以及 add_inline_child 中的类似代码）中，我们可以依赖 style 字段：

```python
class BlockLayout:
    def word(self, node, word):
        # ...
        style = self.children.read(node.style)
        node_font = font(style, zoom)
        # ...
```

确保 style 字段的所有其他用法要么用 read 要么用 get；哪个场合该用哪个应该相当清楚。

现在，我们已经保护了换行过程中读取的所有字段。这意味着 children 字段的脏位现在能正确追踪是否可以跳过换行。让我们利用这一点：

```python
class BlockLayout:
    def layout(self):
        # ...
        if mode == "block":
            if self.children.dirty:
                # ...
        else:
            if self.children.dirty:
                # ...
```

我们还需要确保从现在起只通过 set 修改 children。这对 add_inline_child 和 new_line 是个问题，它们目前直接向 children 字段追加。有几种可能的修复方式，但为了省事，¹⁴ 我打算用第二个不受保护的字段 temp_children 来构建子对象列表，最后再把它 set 为 children 字段的新值：

```python
class BlockLayout:
    def layout(self):
        # ...
        if mode == "block":
            # ...
        else:
            if self.children.dirty:
                self.temp_children = []
                self.new_line()
                self.recurse(self.node)
                self.children.set(self.temp_children)
                self.temp_children = None
```

注意，用完之后我把 temp_children 复位为 None，以确保代码的其他部分不会不小心用到它。这样一来，new_line 可以修改 temp_children，而它最终会成为 children 的值：

```python
class BlockLayout:
    def new_line(self):
        self.previous_word = None
        self.cursor_x = 0
        last_line = self.temp_children[-1] \
            if self.temp_children else None
        new_line = LineLayout(self.node, self, last_line)
        self.temp_children.append(new_line)
```

在 add_inline_child 中你也应该做类似的事情：

```python
class BlockLayout:
    def add_inline_child(self, node, w, child_class,
        frame, word=None):
        # ...
        line = self.temp_children[-1]
        # ...
```

多亏这些修复，我们的浏览器现在会避免重建布局树中任何没有变化的部分，这应该能让重新布局快上一些。如果你一直在跟着加上恰当的 read 和 get 调用，你的浏览器应该接近能用了。有一个棘手的情形：tree_to_list，它可能同时处理受保护和不受保护的 children 字段。我用类型检查解决了这个问题：

```python
def tree_to_list(tree, list):
    # ...
    children = tree.children
    if isinstance(children, ProtectedField):
        children = children.get()
    for child in children:
        tree_to_list(child, list)
    # ...
```

做完所有这些改动后，你的浏览器应该又能工作了，而且现在它对大多数元素都会跳过行内布局。

注意，我们现在有相当多的受保护字段，但只根据脏位跳过对 children 的重算。这是因为重算 children 很慢，而其他大多数字段的计算其实非常快。检查脏位既花时间又让代码杂乱，所以我们只在做值得的地方这么做。

> **深入探索**
> 在真实浏览器中，布局阶段有时会一分为二：先构建布局树，再构建一个单独的片段树（fragment tree）[10]。¹⁵ 在 Chromium 中，片段树是不可变的（immutable），失效是通过比较前一个和新的片段树来完成的，而不是使用脏位，不过其效果与本书描述的相当类似。

## 16.8 行内元素的宽度

至此，BlockLayout 有了受保护的 width 字段，但其他布局对象类型还没有。让我们补上，因为之后会用到。LineLayout 相当简单：

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.width = ProtectedField()
        # ...
    def layout(self):
        # ...
        self.width.copy(self.parent.width)
        # ...
```

在 TextLayout 中，我们同样需要处理字体（因而让 width 依赖 style）：

```python
class TextLayout:
    def __init__(self, node, word, parent, previous):
        # ...
        self.width = ProtectedField()
        # ...
    def layout(self):
        # ...
        style = self.width.read(self.node.style)
        zoom = self.width.read(self.zoom)
        self.font = font(style, zoom)
        self.width.set(self.font.measureText(self.word))
        # ...
```

在 EmbedLayout 中，我们只需保护 width 字段：

```python
class EmbedLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.width = ProtectedField()
        # ...
```

layout 方法中计算 x 坐标时也有一处对 width 的引用。目前你可以直接用 get。

最后是各种替换型内容（replaced content）。在 InputLayout 中，宽度只依赖缩放级别：

```python
class InputLayout(EmbedLayout):
    def layout(self):
        # ...
        zoom = self.zoom.read(notify=self.width)
        self.width.set(dpx(INPUT_WIDTH_PX, zoom))
        # ...
```

IframeLayout 和 ImageLayout 非常相似，宽度依赖缩放级别，还依赖元素的 width 和 height 属性。所以，如果这些属性被 JavaScript 修改，我们就需要让 width 字段失效：

```python
class JSContext:
    def setAttribute(self, handle, attr, value, window_id):
        # ...
        obj = elt.layout_object
        if isinstance(obj, IframeLayout) or \
        isinstance(obj, ImageLayout):
            if attr == "width" or attr == "height":
                obj.width.mark()
```

除此之外，IframeLayout 和 ImageLayout 的处理与 InputLayout 完全一样。搜索你的代码，确保你总是通过 get 和 read 这类方法与 width 交互，并检查浏览器能否工作，包括测试 contenteditable 之类的用户交互。

> **深入探索**
> 这里定义的 ProtectedField 类是一种单子（monad）[11]，这是 Haskell [12] 等编程语言中使用的一种编程模式。简言之，单子描述了在计算中连接各个步骤的方式，不过其细节出了名地令人困惑 [13]。幸运的是，在本章中我们并不需要思考一般意义上的单子，只需要思考 ProtectedField。

## 16.9 布局字段的失效

既然讲到这儿，让我们花点时间保护所有其他的布局字段，包括 x、y 和 height。做完之后，我们就可以讨论如何通过跳过不必要的遍历来进一步加速布局。

与 width 一样，我们从 DocumentLayout 和 BlockLayout 开始。首先是 x 和 y 坐标。在 DocumentLayout 中，直接用 set：

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.x = ProtectedField()
        self.y = ProtectedField()
        # ...
    def layout(self, width, zoom):
        # ...
        self.x.set(dpx(HSTEP, zoom))
        self.y.set(dpx(VSTEP, zoom))
        # ...
```

BlockLayout 的 x 坐标就是其父对象的 x 坐标，所以直接复制过来：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.x = ProtectedField()
        # ...
    def layout(self):
        # ...
        self.x.copy(self.parent.x)
        # ...
```

而 y 坐标有时要参考前一个兄弟节点：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.y = ProtectedField()
    def layout(self):
        # ...
        if self.previous:
            prev_y = self.previous.y.read(notify=self.y)
            prev_height = self.previous.height.read(notify=self.y)
            self.y.set(prev_y + prev_height)
        else:
            self.y.copy(self.parent.y)
        # ...
```

再来处理高度。对 DocumentLayout，只需读取子对象的高度：

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.height = ProtectedField()
        # ...
    def layout(self, width, zoom):
        # ...
        self.height.copy(child.height)
```

BlockLayout 类似，只是要遍历多个子对象：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.height = ProtectedField()
        # ...
    def layout(self):
        # ...
        children = self.children.read(notify=self.height)
        new_height = sum([
            child.height.read(notify=self.height)
            for child in children
        ])
        self.height.set(new_height)
```

注意，在最后这段代码中，我们先读取 children 字段，再遍历子对象列表并读取它们各自的 height 字段。与前面的布局字段不同，height 字段依赖的是子对象的字段，而不是父对象的（见图 16.2）。

*图 16.2　布局树中宽度与高度的依赖方向相反。*

（图中示意：zoom 与 width 沿「Tab/Frame → DocumentLayout → BlockLayout → LineLayout → TextLayout/EmbedLayout」自顶向下传播；而 height 的依赖方向相反，自底向上汇聚。）

BlockLayout 和 DocumentLayout 的布局字段就都覆盖了。一定要去把这些布局类型的 paint 方法（以及 DrawCursor 辅助函数）都改好——但注意，浏览器目前还不能正常运行，因为 BlockLayout 假定其子对象的 height 字段是受保护的，但如果那些子对象是 LineLayout，它们的 height 还没有保护。我们接下来就处理这个。

> **深入探索**
> 脏位并不是实现增量性能的唯一方式；另一种选择是追踪增量（delta）。例如，在 Adapton [14] 项目中，每个把输入转换为输出的计算，也能把输入的增量转换为输出的增量。Google Docs 背后的协作技术「操作变换（Operational Transform）」[15] 也基于这一原理，数据库中的差分数据流（differential dataflow）[16] 亦是如此。不过，脏位的实现内存开销要小得多，这使它们更适合浏览器。

## 16.10 保护行内布局

我们还需要保护 LineLayout、TextLayout 和 EmbedLayout 的字段，它们的 layout 方法工作方式略有不同。是的，这些布局对象都有 x、y 和 height 字段，但它们还会计算供其他布局对象使用的 font、ascent 和 descent 字段。我们必须把所有这些都保护起来。既然我们已经积累了相当多的 ProtectedField 经验，就一口气把所有字段做完。

先从 TextLayout 开始：

```python
class TextLayout:
    def __init__(self, node, word, parent, previous):
        # ...
        self.x = ProtectedField()
        self.y = ProtectedField()
        self.height = ProtectedField()
        self.font = ProtectedField()
        self.ascent = ProtectedField()
        self.descent = ProtectedField()
        # ...
```

我们需要在 layout 中计算这些字段。所有与字体相关的字段都相当直白：

```python
class TextLayout:
    def layout(self):
        # ...
        zoom = self.zoom.read(notify=self.font)
        style = self.node.style.read(notify=self.font)
        self.font.set(font(style, zoom))
        f = self.font.read(notify=self.width)
        self.width.set(f.measureText(self.word))
        f = self.font.read(notify=self.ascent)
        self.ascent.set(f.getMetrics().fAscent * 1.25)
        f = self.font.read(notify=self.descent)
        self.descent.set(f.getMetrics().fDescent * 1.25)
        f = self.font.read(notify=self.height)
        self.height.set(linespace(f) * 1.25)
```

注意，我把 width 改成了读取 font 字段，而不是直接读取 zoom 和 style。反复计算 f 看起来有点怪，但请记住，每个 read 调用都为一个布局字段建立了对另一个布局字段的依赖。我喜欢把每个 f 看作只在其所属字段的计算范围内有效。

我们还需要计算 TextLayout 的 x 坐标。它可以用前一个兄弟节点的 font、x 坐标和宽度：

```python
class TextLayout:
    def layout(self):
        # ...
        if self.previous:
            prev_x = self.previous.x.read(notify=self.x)
            prev_font = self.previous.font.read(notify=self.x)
            prev_width = self.previous.width.read(notify=self.x)
            self.x.set(
                prev_x + prev_font.measureText(' ') + prev_width)
        else:
            self.x.copy(self.parent.x)
```

EmbedLayout 基本相同。至于它的子类，这里是 InputLayout：

```python
class InputLayout(EmbedLayout):
    def layout(self):
        super().layout()
        zoom = self.zoom.read(notify=self.width)
        self.width.set(dpx(INPUT_WIDTH_PX, zoom))
        font = self.font.read(notify=self.height)
        self.height.set(linespace(font))
        height = self.height.read(notify=self.ascent)
        self.ascent.set(-height)
        self.descent.set(0)
```

这里是 ImageLayout；它有一个 img_height 字段，我打算把它当作计算 height 的中间步骤而不加保护：

```python
class ImageLayout(EmbedLayout):
    def layout(self):
        # ...
        font = self.font.read(notify=self.height)
        self.height.set(max(self.img_height, linespace(font)))
        height = self.height.read(notify=self.ascent)
        self.ascent.set(-height)
        self.descent.set(0)
```

最后是 IframeLayout 计算其高度的方式，相当直白：

```python
            self.height.set(dpx(IFRAME_HEIGHT_PX + 2, zoom))
```

```python
        isinstance(obj, ImageLayout):
```

这样行内布局对象就都覆盖了。剩下的只有 LineLayout。先是 x 和 y：

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.x = ProtectedField()
        self.y = ProtectedField()
        # ...
    def layout(self):
        # ...
        self.x.copy(self.parent.x)
        if self.previous:
            prev_y = self.previous.y.read(notify=self.y)
            prev_height = self.previous.height.read(notify=self.y)
            self.y.set(prev_y + prev_height)
        else:
            self.y.copy(self.parent.y)
        # ...
```

不过 height 有点复杂：它要计算所有子对象中最大的 ascent 和 descent，并用它们来设置高度以及子对象的 y。我认为处理这段代码最简单的办法，是给 LineLayout 添加 ascent 和 descent 字段来保存最大的上升值和下降值，然后让 height 以及子对象的 y 字段依赖它们。

我们这么做，先声明受保护字段：

```python
class LineLayout:
    def __init__(self, node, parent, previous):
        # ...
        self.ascent = ProtectedField()
        self.descent = ProtectedField()
```

然后在 layout 中，先处理没有子对象的情形：

```python
class LineLayout:
    def layout(self):
        # ...
        if not self.children:
            self.height.set(0)
            return
```

注意，我们不需要读取 children 字段，因为在 LineLayout 中它不受保护；它在 LineLayout 创建时由 BlockLayout 填充，之后不再修改。

接下来，计算最大的 ascent 和 descent：

```python
class LineLayout:
    def layout(self):
        # ...
        self.ascent.set(max([
            -child.ascent.read(notify=self.ascent)
            for child in self.children
        ]))
        self.descent.set(max([
            child.descent.read(notify=self.descent)
            for child in self.children
        ]))
```

然后，我们可以重新计算每个子对象的 y 坐标：

```python
class LineLayout:
    def layout(self):
        # ...
        for child in self.children:
            new_y = self.y.read(notify=child.y)
            new_y += self.ascent.read(notify=child.y)
            new_y += child.ascent.read(notify=child.y)
            child.y.set(new_y)
```

最后，我们重新计算这一行的高度：

```python
class LineLayout:
    def layout(self):
        # ...
        max_ascent = self.ascent.read(notify=self.height)
        max_descent = self.descent.read(notify=self.height)
        self.height.set(max_ascent + max_descent)
```

经过这些改动，每个布局对象的字段现在都受保护了。和之前一样，确保这些字段的所有用法都用 read 和 get，并确保浏览器仍能运行，包括在 contenteditable 期间。你现在很可能还需要修复 Frame 和 Tab 中对 height 和 y 的几处使用，比如钳制滚动偏移的那些。

> **深入探索**
> 就在写这一节之前，我¹⁶ 花了几周时间清除 Chrome 无障碍代码中的一些失效不足 bug。起初，这些 bug 只会在某些负载很重的自动化测试机器上出现！结果发现，在那些机器上，HTML 解析器会更频繁地让出（yield）¹⁷，触发了不同且不正确的渲染路径。像这样的深层 bug 要耗费数不清的时间去排查，这正是为什么从一开始就用健壮的抽象来避免它们如此重要。

## 16.11 跳过无效果更新

我们现在有相当多的布局字段了，那来看看实际上发生了多少失效。在 ProtectedField 的 set 方法里加一条 print 语句，看看哪些字段在被重新计算：

```python
class ProtectedField:
    def set(self, value):
        if self.value != None:
            print("Change", self)
        self.notify()
        self.value = value
        self.dirty = False
```

这个 if 检查避免了在初始页面布局期间打印，所以它只会显示我们的失效优化工作得怎么样。你看到的打印越少，变化的字段就越少，我们能够跳过的工作也越多。

试着在一个大网页（比如本章）上用 contenteditable 编辑一些文本——你会看到满屏的输出，成千上万行打印出来的东西。有点难以理解为什么会这样，所以我们给 ProtectedField 加一个好看的可打印形式，再加一个用于调试的 name 参数：¹⁸

让我们修复它们。先解决 style。style 被反复重算的原因很简单：即使它不脏，我们也会重算。如果它不脏就跳过：

```python
def style(node, rules, frame):
    if node.style.dirty:
        # ...
    for child in node.children:
        style(child, rules, frame)
```

现在应该几乎不会再有任何样式重算了。但那些布局字段的重算呢？为什么会发生？嗯，这里第一个被重算的字段是 zoom，而它又追溯到 DocumentLayout：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        self.zoom.set(zoom)
        # ...
```

每次布局页面时，我们都会 set zoom 参数，而且我们不得不这么做，因为用户可能放大或缩小了页面。但每次 set 一个字段，都会通知每一个依赖它的字段。这两件事结合在一起，意味着我们每一帧都在重算 zoom 字段，以及依赖 zoom 的一切。

这一切之所以浪费，是因为 zoom 通常并不变化。所以我们应该只在值发生变化时才通知依赖者：

```python
class ProtectedField:
    def set(self, value):
        if value != self.value:
            self.notify()
        # ...
```

这个改动是安全的，因为如果新值与旧值相同，任何下游的计算实际上都不需要改变。这个小调整应该能把字段变化的数量降到最低：

```text

Change ProtectedField(<div class="demo" ...>, children)
Change ProtectedField(<div class="demo" ...>, height)
```

这里发生的全部事情，就是重建 contenteditable 元素的子对象（我们必须这么做，以便纳入新文本），并检查它的高度是否变化（这是必要的，以防我们折行到了更多的行上）。

## 16.12 跳过遍历

既然所有布局字段都受保护了，我们就可以通过检查它们的脏位来判断是否有字段需要重算。但要检查所有这些脏位，我们就得访问每个布局对象，这可能需要很长时间。相反，我们应该用脏位来最小化需要访问的布局对象数量。

基本思路围绕这个问题展开：我们到底需不需要在一个给定节点上调用 layout？layout 方法做三件事：创建子布局对象、计算布局属性，以及递归出更多对 layout 的调用。这些步骤在以下情况下可以被跳过：

- 我们不需要创建子布局对象，即 children 字段不脏；
- 我们不需要重算布局字段，因为它们不脏；以及
- 我们不需要递归调用 layout。

最后一个条件还没有对应的脏位，所以我们加一个。我把它叫作 has_dirty_descendants，因为它追踪是否有任何后代拥有一个脏的 ProtectedField：¹⁹

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.has_dirty_descendants = False
```

把这个也加到其他每种布局对象上。

现在，只要有任何脏位被置位，我们就需要置位 has_dirty_descendants。我们可以通过给 ProtectedField 增加一个额外的（可选的²⁰）parent 参数来实现：

```python
class ProtectedField:
    def __init__(self, obj, name, parent=None):
        # ...
        self.parent = parent
```

确保为每种布局对象类型中的每个 ProtectedField 都传这个参数。例如 BlockLayout：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        self.children = ProtectedField(self, "children", self.parent)
        self.zoom = ProtectedField(self, "zoom", self.parent)
        self.width = ProtectedField(self, "width", self.parent)
        self.height = ProtectedField(self, "height", self.parent)
        self.x = ProtectedField(self, "x", self.parent)
        self.y = ProtectedField(self, "y", self.parent)
```

然后，每当 mark 或 notify 被调用时，我们沿父链向上走，置位后代脏位：

```python
class ProtectedField:
    def set_ancestor_dirty_bits(self):
        parent = self.parent
        while parent and not parent.has_dirty_descendants:
            parent.has_dirty_descendants = True
            parent = parent.parent
    def mark(self):
        # ...
        self.set_ancestor_dirty_bits()
```

注意，如果后代脏位已经置位，while 循环会提前退出。这是因为置位该位的那次调用已经置位了所有祖先的后代脏位。²¹

我们还需要在布局之后清掉后代脏位：

```python
class BlockLayout:
    def layout(self):
        # ...
        for child in self.children.get():
            child.layout()
        self.has_dirty_descendants = False
```

有了后代脏位，我们就可以用它们来跳过布局，包括递归调用：

```python
class BlockLayout:
    def layout(self):
        if not self.layout_needed(): return
        # ...
```

这里的 layout_needed 方法只是检查所有脏位：

```python
class BlockLayout:
    def layout_needed(self):
        if self.zoom.dirty: return True
        if self.width.dirty: return True
        if self.height.dirty: return True
        if self.x.dirty: return True
        if self.y.dirty: return True
        if self.children.dirty: return True
        if self.has_dirty_descendants: return True
        return False
```

对其他每种布局对象做同样的事情。在 DocumentLayout 中，你要稍微小心一点，因为它接收框架宽度和缩放级别作为参数；如果对应的 Frame 变量变化了，你必须标记 DocumentLayout 的那些字段：²²

```python
class IframeLayout(EmbedLayout):
    def layout(self):
        if self.node.frame:
            # ...
            self.node.frame.document.width.mark()
```

缩放级别在 Tab 中变化：

```python
class Tab:
    def zoom_by(self, increment):
        # ...
        for id, frame in self.window_id_to_frame.items():
            frame.document.zoom.mark()
    def reset_zoom(self):
        # ...
        for id, frame in self.window_id_to_frame.items():
            frame.document.zoom.mark()
```

跳过不需要的 layout 方法应当带来明显的提速，小布局现在更新布局大约花 7 ms，编辑现在流畅多了。²³ 不过，在图 16.4 中我还追踪了 paint，向你展示为什么 render 总体上仍要约 230 ms。（让浏览器变快需要优化一切！我不会实现它，但 paint 也可以快得多——见练习 16.10。）

> **深入探索**
> ProtectedField 类似于观察者模式（observer pattern）[21]，即当一段状态变化时运行一段回调代码。这种模式在 UI 框架 [22] 中很常见。通常这些观察者会急切地重算依赖的结果，但我们的回调——mark 和 notify——只是置一个稍后清理的脏位。这意味着我们的失效算法是一种惰性观察者（lazy observer）[23]。惰性通过批量更新来帮助性能。

## 16.13 细粒度样式失效

遗憾的是，在添加失效机制的过程中，我们无意间破坏了平滑的动画。基本问题是这样的：假设某个元素的 opacity 或 transform 属性变化了，比如通过 JavaScript。这个属性不引发布局，所以它本应完全通过合成来动画。然而，改变任何样式属性都会让 Element 的 style 字段失效，而那又会让 children 字段失效，导致布局树被重建。这可不行。

归根结底，核心问题是 ProtectedField 粒度太粗导致的过度失效（over-invalidation）。例如，children 字段并不依赖整个样式字典，只依赖其中少数几个与字体相关的字段。我们需要让 style 成为一个由 ProtectedField 组成的字典，而不是一个装着字典的 ProtectedField：

```python
class Element:
    def __init__(self, tag, attributes, parent):
        # ...
        self.style = dict([
            (property, ProtectedField(self, property))
            for property in CSS_PROPERTIES
        ])
        # ...
```

在 Text 中做同样的修改。CSS_PROPERTIES 字典包含我们支持的每个 CSS 属性，以及它们的默认值：

```python
CSS_PROPERTIES = {
    "font-size": "inherit", "font-weight": "inherit",
    "font-style": "inherit", "color": "inherit",
    "opacity": "1.0", "transition": "",
    "transform": "none", "mix-blend-mode": None,
    "border-radius": "0px", "overflow": "visible",
    "outline": "none", "background-color": "transparent",
    "image-rendering": "auto",
}
```

当从 JavaScript 设置样式属性时，我会通过调用一个新的 dirty_style 函数让所有字段失效：

```python
def dirty_style(node):
    for property, value in node.style.items():
        value.mark()
class JSContext:
    def style_set(self, handle, s, window_id):
        # ...
        dirty_style(elt)
        # ...
```

但这还不是全部。还有其他会让样式失效的代码，尤其是可能影响 :focus 这类伪类的代码：

```python
class Frame:
    def focus_element(self, node):
        # ...
        if self.tab.focus:
            # ...
            dirty_style(self.tab.focus)
        if node:
            #...
            dirty_style(node)
```

类似地，在 style 中，如果节点的任何样式属性是脏的，我们就需要重算它的样式：

然后，在解析继承时，我们让样式的一个字段具体地依赖父对象样式的一个字段：

解析百分比字体大小时也一样：

然后，一旦 new_style 全部算好，我们逐个设置节点样式的每个字段：

```python
            field.set(new_style[property])
```

现在我们只需要更新浏览器其余部分来使用细粒度的样式字段。大多数情况下，这意味着把 style.get()[property] 替换成 style[property].get()：

```python
def paint_visual_effects(node, cmds, rect):
    opacity = float(node.style["opacity"].get())
    blend_mode = node.style["mix-blend-mode"].get()
    translation = parse_transform(node.style["transform"].get())
    if node.style["overflow"].get() == "clip":
        border_radius = float(node.style["border-radius"].get()[:-2])
        # ...
    # ...
```

不过，font 方法需要一点工作。到目前为止，我们一直是读取节点的样式并把它传给 font：

```python
class BlockLayout:
    def word(self, node, word):
        zoom = self.children.read(self.zoom)
        style = self.children.read(node.style)
        node_font = font(style, zoom)
        # ...
```

这行不通了，因为现在我们需要读取 style 的三个不同属性。为了保持紧凑，我打算重写 font，把要失效的字段作为参数传入：

```python
def font(css_style, zoom, notify):
    weight = css_style['font-weight'].read(notify)
    style = css_style['font-style'].read(notify)
    try:
        size = float(css_style['font-size'].read(notify)[:-2]) * 0.75
    except:
        size = 16
    font_size = dpx(size, zoom)
    return get_font(font_size, weight, style)
```

现在，在换行期间请求字体时，我们可以简单地把 self.children 传给 notify 参数：

```python
class BlockLayout:
    def word(self, node, word):
        zoom = self.zoom.read(notify=self.children)
        node_font = font(node.style, zoom, notify=self.children)
        # ...
```

同样，如果我们正在计算的是 font 字段，就传入 font 字段：

```python
class TextLayout:
    def layout(self):
        if self.font.dirty:
            zoom = self.zoom.read(notify=self.font)
            self.font.set(font(
                self.node.style, zoom, notify=self.font))
```

记得把 font 方法的所有其他用法都更新到这个新接口。这种「目标传递风格（destination-passing style）」是向辅助方法添加失效的常用方式。

最后，既然我们给样式加上了细粒度失效，在处理动画时就可以只失效正在动画的那个属性：

```python
class Tab:
    def run_animation_frame(self, scroll):
        for (window_id, frame) in self.window_id_to_frame.items():
            for node in tree_to_list(frame.nodes, []):
                for (property_name, animation) in \
                    node.animations.items():
                    value = animation.animate()
                    if value:
                        node.style[property_name].set(value)
                        # ...
```

当 opacity 或 transform 这样的属性被改变时，它不会让任何布局字段失效（因为这些属性不影响任何布局字段），于是动画将再次完全跳过布局。

> **深入探索**
> CSS 样式依赖于选择器匹配了哪些元素，而随着页面变化，这一点本身也可能需要失效。²⁴ 浏览器有聪明的算法来避免为页面上的每个选择器重做选择器匹配。例如，Chromium 为每个选择器构造失效集（invalidation sets）[24]，告诉它需要复查哪些「选择器-元素」匹配。像 :has() 这样的新选择器需要更复杂 [25] 的失效策略，但要让重新样式化保持快速，这种复杂性是必要的。

## 16.14 分析依赖

得益于 ProtectedField 抽象，布局现在既快又正确。然而，由于我们的依赖大多是通过 read 隐式建立的，很难说清从任何一个给定操作出发，最终会让哪些字段失效。这就让人难以理解哪些操作快、哪些操作慢，尤其是随着我们添加新的样式和布局特性。这种对可审计性的担忧在真实浏览器中同样存在。毕竟，真实浏览器有数百万行而不是数千行代码，支持数千个 CSS 属性。它们的依赖图远比我们的浏览器复杂。

因此，我们想让依赖图更容易看清，不过可以先看看图 16.5，感受一下这项任务的规模。在此过程中，我们还可以把关于这张图形状的不变量集中起来。这会让我们的浏览器在未来得到加固（hardening）[26]，不易因意外而引入 bug，同时还能提升性能。

*图 16.5　我们浏览器中布局字段的依赖图。尽管已经简化，这张依赖图仍然相当复杂。*

（图中示意：TextLayout 的 width、height、ascent、descent、font 等字段依赖其 style['font-weight']、style['font-style']、style['font-size'] 等样式字段以及父对象的 x、y；LineLayout 的 height 依赖各子对象的 ascent 与 descent；ImageLayout 等替换型布局对象也有各自的 width、height、ascent、font 字段及其依赖。）

一个简单的第一步，是显式列出每个 ProtectedField 的依赖。我们可以把它做成一个可选的构造参数：

```python
class ProtectedField:
    def __init__(self, obj, name, parent=None, dependencies=None):
        # ...
        if dependencies != None:
            for dependency in dependencies:
                dependency.invalidations.add(self)
```

而且，如果在构造函数中传入了依赖，我们就可以「冻结（freeze）」这个 ProtectedField，使 read 不再添加新的依赖，只检查依赖是否已声明：

```python
class ProtectedField:
    def __init__(self, obj, name, parent=None, dependencies=None):
        # ...
        self.frozen_dependencies = (dependencies != None)
        if dependencies != None:
            for dependency in dependencies:
                dependency.invalidations.add(self)
    def read(self, notify):
        if notify.frozen_dependencies:
            assert notify in self.invalidations
        else:
            self.invalidations.add(notify)
        return self.get()
```

例如，在 DocumentLayout 中，我们现在可以明确指出它的字段没有外部依赖，因此必须被显式标记：²⁵

```python
class DocumentLayout:
    def __init__(self, node, frame):
        # ...
        self.zoom = ProtectedField(self, "zoom", None, [])
        self.width = ProtectedField(self, "width", None, [])
        self.x = ProtectedField(self, "x", None, [])
        self.y = ProtectedField(self, "y", None, [])
        self.height = ProtectedField(self, "height")
```

但注意 height 缺了 dependencies 参数。DocumentLayout 的 height 依赖其子对象的高度，而那个子对象在 layout 被调用之前并不存在。像这样的「向下」依赖意味着我们无法在每个 ProtectedField 构造时就把它们全部冻结。但我们每冻结一个受保护字段，依赖图就更容易审计一分。

我们还可以冻结 BlockLayout 中的 zoom、width、x 和 y 字段。对 y 来说，依赖关系取决于布局对象有没有前一个兄弟节点：

```python
class BlockLayout:
    def __init__(self, node, parent, previous, frame):
        # ...
        if self.previous:
            y_dependencies = [self.previous.y, self.previous.height]
        else:
            y_dependencies = [self.parent.y]
        self.y = ProtectedField(
            self, "y", self.parent, y_dependencies)
        # ...
```

对 BlockLayout 的 height，出于与 DocumentLayout 相同的原因，我们无法在构造函数中冻结它。但我们可以在 children 字段计算完成后立刻冻结它。让我们加一个 set_dependencies 方法来做这件事：²⁶

```python
class ProtectedField:
    def set_dependencies(self, dependencies):
        for dependency in dependencies:
            dependency.invalidations.add(self)
        self.frozen_dependencies = True
```

现在我们可以在 DocumentLayout 中冻结 height：

```python
class DocumentLayout:
    def layout(self, width, zoom):
        if not self.children:
            child = BlockLayout(self.node, self, None, self.frame)
            self.height.set_dependencies([child.height])
```

类似地，在 BlockLayout 中：

```python
class BlockLayout:
    def layout(self):
```

其他布局对象也可以冻结它们的字段。在 TextLayout、EmbedLayout 及其子类中，我们可以冻结所有字段：

```python
class TextLayout:

            self.node.style['font-size']])
```

在 LineLayout 中，由于一行先被创建、之后才被布局的这种方式有点复杂，我们需要把 ascent 和 descent 的冻结推迟到第一次调用 layout 时：

```python
class LineLayout:
    def __init__(self, node, parent, previous):

        self.ascent = ProtectedField(self, "ascent", self.parent)
        self.descent = ProtectedField(self, "descent", self.parent)

    def layout(self):

            self.ascent.set_dependencies(
            [child.ascent for child in self.children])
            self.descent.set_dependencies(
            [child.descent for child in self.children])
            self.initialized_fields = True
        # ...
```

最后一个布局类是 EmbedLayout。那里的依赖都很直白，只有两件事例外：首先，和 TextLayout 一样，如果有前一个兄弟节点，x 就依赖前一个的 x；其次，由于宽高比的存在，height 依赖 width：

在 init_style 内部，我们需要冻结每个样式字段的依赖。这很容易：只有可继承的字段才有依赖：

```python
def init_style(node):
    node.style = dict([
            (property, ProtectedField(node, property, None,
                [node.parent.style[property]] \
                    if node.parent and \
                        property in INHERITED_PROPERTIES \
                    else []))
            for property in CSS_PROPERTIES
        ])
```

通过冻结除 children 之外的所有布局和样式字段，我们只要看看布局对象类型的构造函数，就能对我们的浏览器依赖图有很好的把握。这很好，能帮助我们在添加更多样式和布局特性时避免环和过长的依赖链。

但要获得真实浏览器所需的那种极致性能，还有一个额外的好处。所有这些精巧的 ProtectedField 增加了大量开销，主要因为它们占用更多内存、需要更多函数调用。事实上，本章很可能让你的浏览器在初始页面加载时明显变慢了。²⁷ 其中一部分可以通过跳过 assert 来改善，²⁸ 但这绝对不理想。

幸运的是，编译时代码生成和宏这类技术可以用来在幕后把 ProtectedField 对象变成直线代码（straight-line code）。设置某个 ProtectedField 可以在静态已知的失效目标上直接置脏位，脏位可以内联进布局对象，read 函数可以在编译期检查依赖是否已声明。²⁹ 这类技术超出了本书的范围，但我把它留作一道进阶练习。

> **深入探索**
> 真实浏览器也用断言来抓 bug，很像本章的 ProtectedField 抽象。但为了不让浏览器在用户那里变慢，非必要的断言在最终用户运行的发布版（release build）中会被「编译掉」。调试版（debug build）则是浏览器工程师在调试或开发新特性时使用的版本，自动化测试也用它。调试版还会编译进诸如消毒器（sanitizer）[29] 之类的调试特性，而发布版则采用轮廓引导优化（profile-guided optimization）[30] 这类重量级优化。

## 16.15 小结

本章通过优化的缓存失效，介绍了局部样式与布局的概念。主要收获有：

- 缓存与失效是加速关键浏览器交互的强大方式，因此是真实浏览器中的一项核心技术。
- 让渲染幂等，使我们既能跳过冗余工作，又能保证页面看起来一样。
- 优秀的浏览器以增量性能原则为目标：一次改动的开销应与改动的规模成正比，而不是与整个页面的规模成正比。
- 缓存失效困难且易错，值得像 ProtectedField 这样精心设计的抽象。
- 失效可以用来跳过对象的分配、计算，甚至遍历。

## 16.17 练习

**16.1　清空元素。** 实现无参数调用时的 replaceChildren DOM 方法 [31]。该方法应删除给定元素的所有子节点。务必正确处理失效。

**16.2　保护布局阶段。** 把 needs_style 和 needs_layout 脏位替换掉，改为让 Frame 上的 document 字段成为一个 ProtectedField。确保动画仍能正确工作：opacity 或 transform 的动画不应触发布局，而其他属性的动画则应该。

**16.3　迁移子对象。** 实现带多个参数调用时的 replaceChildren DOM 方法。此时，参数是文档中其他位置的元素，³⁰ 它们会先从当前的父对象中移除，然后挂到这个元素上。务必正确处理失效。

**16.4　样式的后代脏位。** 为样式信息添加后代脏位，让样式阶段不必遍历样式未发生变化的节点。

**16.5　调整浏览器大小。** 也许早在练习 2.3，你就实现过对调整浏览器窗口大小的支持。（而当我们改用 SDL 时，你多半又放弃了它。）重新实现对浏览器调整大小的支持；你需要向 SDL_CreateWindow 传入 SDL_WINDOW_RESIZABLE 标志并监听 SDL_WINDOWEVENT_RESIZED 事件。确保失效正常工作：调整窗口大小应当调整页面大小。失效对让调整大小变快有多大帮助？分别测试垂直和水平方向的调整。

**16.6　匹配子对象。** 如果你在练习 9.2 中还没有实现 appendChild 方法 [32]，现在加上它。appendChild 有趣的地方在于：它虽然确实会改变布局对象的 children 字段，但只是通过在末尾添加新的子对象。在这种情况下，你可以保留所有既有的布局对象子节点。至少在块级模式 BlockLayout 的情形下应用这一优化。

**16.7　失效 previous。** 如果你在练习 9.2 中还没有实现 insertBefore 方法 [33]，现在加上它。与 appendChild 一样，我们希望尽可能跳过布局对象的重建。但该方法还可能改变布局对象的 previous 字段；在所有块级模式的 BlockLayout 上保护该字段，然后尽可能少地重建布局树。

**16.8　:hover 伪类。** 有一个 :hover 伪类，用来标识鼠标正悬停在其上的元素 [34]。实现它：把鼠标悬停事件发送给活动 Tab，并通过命中测试找出哪个元素正被悬停。尽量避免在这次命中测试中强制布局 [35]；一种做法是在 Tab 上存一个 pending_hover，在 render 期间布局之后运行命中测试，然后再执行一次 render 来让被悬停元素的样式失效。

**16.9　优化掉 ProtectedField。** 正如本章最后一节所说，创建所有这些 ProtectedField 对象对真实浏览器来说太昂贵了。看看你能否找到完全避免创建这些对象的方法。取决于你实现浏览器所用的语言，你可能可以使用编译期宏来帮忙；在 Python 中，这可能需要通过重构把 ProtectedField 的 API 形态从面向对象改成函数式。

**16.10　优化 paint。** 即使让文本输入的布局变快之后，paint 仍然慢得令人痛苦。修复它：在帧与帧之间保存显示列表，为每个布局对象添加「是否需要 paint」的脏位，并就地修改显示列表而不是每次重建。
