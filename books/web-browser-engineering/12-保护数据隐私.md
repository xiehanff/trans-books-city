# 第 10 章　保护数据隐私

*Chapter 10: Keeping Data Private*

我们的浏览器已经长大，现在能运行（小型的）Web 应用了。只差最后一步——通过 Cookie 实现用户身份——它就能运行各种各样的个性化在线服务。但能力越大，责任越大：我们的浏览器现在必须保护 Cookie 的安全，防范那些企图窃取它们的对手。幸运的是，浏览器拥有一整套精巧的系统来控制对 Cookie 的访问，并防止它们被滥用。

> **警告**
>
> Web 安全是一个庞大的话题，涵盖浏览器安全、网络安全和应用安全。它还涉及对用户的教育，让攻击者无法诱骗用户泄露自己的敏感数据。本章无法覆盖所有这些内容：如果你要编写 Web 应用或其他安全敏感的代码，单凭这本书是不够的。

## 10.1 Cookie

就我们目前已实现的功能而言，Web 服务器没有办法判断两个 HTTP 请求是来自同一个用户还是两个不同的用户；我们的浏览器实际上是匿名的。¹ 这意味着它无法在任何地方「登录」，因为已登录用户的请求与未登录用户的请求无法区分。

Web 用 Cookie（cookie）解决了这个问题。Cookie——这个名字本身毫无意义，不必深究——是你的浏览器代表某个 Web 服务器存储的一小段信息。Cookie 把你的浏览器与其他任何浏览器区分开来，并随每个 Web 请求一起发送，这样服务器就能分辨哪些请求来自谁。实际上，Cookie 就是一种去中心化的、由服务器授予的浏览器身份。

下面是技术细节。HTTP 响应可以包含一个 Set-Cookie 头。该头包含一个键–值对；例如，下面这个头把 foo Cookie 的值设为 bar：

```text
Set-Cookie: foo=bar
```

示意图（浏览器与服务器之间的往返）：

```text
浏览器 → 服务器：GET /
服务器 → 浏览器：Set-Cookie: ...
浏览器 → 服务器：GET /login（带 Cookie: ...）
服务器 → 浏览器：<form ...>
```

*图 10.1　服务器通过 Set-Cookie 头把 Cookie 分配给浏览器，此后浏览器通过 Cookie 头表明自己的身份。*

浏览器会记住这个键–值对，下次向同一台服务器发请求时（Cookie 是特定于站点的），浏览器会在 Cookie 头中把它回传：

```text
Cookie: foo=bar
```

服务器可以设置多个 Cookie，也可以设置过期日期之类的参数，但图 10.1 所示的这种 Set-Cookie/Cookie 事务才是核心原理。

让我们用 Cookie 为我们的留言簿（guest book）编写一个登录系统。每个用户将由存储在 token Cookie 中的一个长长的随机数来标识。² 服务器要么从 Cookie 头中提取一个 token，要么为新访客生成一个：

```python
import random

def handle_connection(conx):
    # ...
    if "cookie" in headers:
        token = headers["cookie"][len("token="):]
    else:
        token = str(random.random())[2:]
    # ...
```

当然，我们得告诉新访客记住他们新生成的 token：

```python
def handle_connection(conx):
    # ...
    if 'cookie' not in headers:
        template = "Set-Cookie: token={}\r\n"
        response += template.format(token)
    # ...
```

第一段代码在所有请求头解析完毕之后、在 do_request 中处理请求之前运行；第二段代码则在 do_request 返回之后、服务器正在组装 HTTP 响应时运行。

经过这两处代码修改，留言簿的每位访客现在都拥有了唯一的身份。我们可以用这个身份来存储每个用户的信息。让我们在服务器端的 SESSIONS 变量中完成这件事：³

```python
SESSIONS = {}

def handle_connection(conx):
    # ...
    session = SESSIONS.setdefault(token, {})
    status, body = do_request(session, method, url, headers, body)
    # ...
```

SESSIONS 把 token 映射到会话（session）数据字典。setdefault 方法既从字典中取出一个键，又会在该键不存在时设置一个默认值。我通过 do_request 把这个会话数据传递给 show_comments 和 add_entry 等各个页面处理函数：

```python
def do_request(session, method, url, headers, body):
    if method == "GET" and url == "/":
        return "200 OK", show_comments(session)
    # ...
    elif method == "POST" and url == "/add":
        params = form_decode(body)
        add_entry(session, params)
        return "200 OK", show_comments(session)
    # ...
```

你还需要修改 add_entry 和 show_comments 的参数列表来接受这个新参数。现在我们有了构建登录系统的基础。

> **深入探索**
>
> Cookie 的原始规范 [1] 里说，把它们称为「cookies」并没有什么「令人信服的理由」，但用这个词来指代程序之间交换的不透明标识符，其实由来已久；Wikipedia [2] 把它追溯到至少 1979 年，而且在 Web 之前，X11 [3] 就曾用 cookie 来做认证。

## 10.2 登录系统

我希望用户先登录再向留言簿发帖。最起码，这意味着：

- 用户使用用户名和密码登录。
- 服务器检查登录信息是否有效。
- 用户必须已登录才能添加留言簿条目。
- 服务器显示每条留言簿条目是谁添加的。

开始写代码吧。我们先硬编码两对用户名–密码：

```python
LOGINS = {
    "crashoverride": "0cool",
    "cerealkiller": "emmanuel"
}
```

用户通过访问 /login 来登录：

```python
def do_request(session, method, url, headers, body):
    # ...
    elif method == "GET" and url == "/login":
        return "200 OK", login_form(session)
    # ...
```

这个页面显示一个带用户名和密码输入框的表单：⁴

```python
def login_form(session):
    body = "<!doctype html>"
    body += "<form action=/ method=post>"
    body += "<p>Username: <input name=username></p>"
    body += "<p>Password: <input name=password type=password></p>"
    body += "<p><button>Log in</button></p>"
    body += "</form>"
    return body
```

注意，这个表单把数据 POST 到 / 这个 URL。我们要在一个新函数中处理这些 POST 请求，由它检查密码并完成登录：

```python
def do_request(session, method, url, headers, body):
    # ...
    elif method == "POST" and url == "/":
        params = form_decode(body)
        return do_login(session, params)
    # ...
```

这个 do_login 函数检查密码，并通过把用户名存入会话数据来让人登录：⁵

```python
def do_login(session, params):
    username = params.get("username")
    password = params.get("password")
    if username in LOGINS and LOGINS[username] == password:
        session["user"] = username
        return "200 OK", show_comments(session)
    else:
        out = "<!doctype html>"
        out += "<h1>Invalid password for {}</h1>".format(username)
        return "401 Unauthorized", out
```

注意，会话数据（包括 user 键）存储在服务器上，用户无法直接修改。这是好事，因为我们只希望在用户于登录表单中提交正确密码时，才在会话数据中设置 user 键。

现在我们可以通过检查会话数据来判断用户是否已登录。让我们只向已登录的用户显示评论表单：

```python
def show_comments(session):
    # ...
    if "user" in session:
        out += "<h1>Hello, " + session["user"] + "</h1>"
        out += "<form action=add method=post>"
        out +=   "<p><input name=guest></p>"
        out +=   "<p><button>Sign the book!</button></p>"
        out += "</form>"
    else:
        out += "<a href=/login>Sign in to write in the guest book</a>"
    # ...
```

同样，add_entry 必须在发帖之前检查用户是否已登录：

```python
def add_entry(session, params):
    if "user" not in session: return
    if 'guest' in params and len(params['guest']) <= 100:
        ENTRIES.append((params['guest'], session["user"]))
```

注意，来自会话的用户名被存进了 ENTRIES：⁶

```python
ENTRIES = [
    ("No names. We are nameless!", "cerealkiller"),
    ("HACK THE PLANET!!!", "crashoverride"),
]
```

打印留言簿条目时，我们会显示它们的作者：

```python
def show_comments(session):
    # ...
    for entry, who in ENTRIES:
        out += "<p>" + entry + "\n"
        out += "<i>by " + who + "</i></p>"
    # ...
```

在一个正常的 Web 浏览器里试一试吧。你应该能进入留言簿主页，点击登录链接，用上面某一对用户名–密码登录，然后就能发布条目。⁷ 当然，这个登录系统有一大堆不安全之处。⁸ 但本书的关注点是浏览器而不是服务器，所以一旦你确信一切正常，我们就切回我们的浏览器，实现 Cookie。

> **深入探索**
>
> 另一种比较冷门的浏览器认证系统是 TLS 客户端证书（TLS client certificates）[8]。用户从服务器下载一个公钥/私钥对，之后浏览器在向该服务器发起请求时用它们证明自己的身份。另外，如果你见过主机名前面带 username:password@ 的 URL，那是 HTTP 认证（HTTP authentication）[9]。请不要在新网站中使用这两种方法（除非有充分的理由）。

## 10.3 实现 Cookie

首先，我们需要浏览器里有一个存放 Cookie 的地方；这个数据结构传统上被称为「Cookie 罐」（cookie jar）：⁹

```python
COOKIE_JAR = {}
```

由于 Cookie 是特定于站点的，我们的 Cookie 罐会把站点映射到 Cookie。注意，Cookie 罐是全局的，并不局限于某个特定的标签页。也就是说，如果你登录了某个网站，又打开了第二个标签页，那么在那个标签页里你同样是已登录状态。¹⁰

浏览器访问页面时，需要发送该站点对应的 Cookie：

```python
class URL:
    def request(self, payload=None):
        # ...
        if self.host in COOKIE_JAR:
            cookie = COOKIE_JAR[self.host]
            request += "Cookie: {}\r\n".format(cookie)
        # ...
```

对称地，浏览器在看到 Set-Cookie 头时也要更新 Cookie 罐：¹¹

```python
class URL:
    def request(self, payload=None):
        # ...
        if "set-cookie" in response_headers:
            cookie = response_headers["set-cookie"]
            COOKIE_JAR[self.host] = cookie
        # ...
```

现在你应该可以用你的浏览器登录留言簿并向它发帖了。而且，你应该能同时用两个浏览器打开留言簿——比如你的浏览器和一个真正的浏览器——以两个不同用户的身份登录并发帖。

既然我们的浏览器支持 Cookie 并用它们来登录，我们就得确保 Cookie 数据不会被恶意行为者染指。毕竟 Cookie 就是浏览器的身份，一旦有人偷走了它，服务器就会以为那个人是你。我们必须防止这种事。

> **深入探索**
>
> 曾经有人尝试在 RFC 2965 [10] 中「清理」Cookie 规范，包括人类可读的 Cookie 描述、限定于特定端口的 Cookie 等。这需要引入 Cookie2 和 Set-Cookie2 头；这些新头并不受欢迎。它们如今已被废弃 [11]。

## 10.4 跨站请求

Cookie 是特定于站点的，所以不应该把一台服务器的 Cookie 发送给另一台服务器。¹² 但如果攻击者足够聪明，他们也许能让服务器或浏览器帮他们窃取 Cookie 的值。

攻击者窃取你私人数据最容易的方式，就是直接开口索要。当然，浏览器里并没有哪个 API 能让一个网站去索要另一个网站的 Cookie。但确实有一个向另一个网站发起请求的 API，它叫 XMLHttpRequest。¹³

XMLHttpRequest 从 JavaScript 发送异步 HTTP 请求。由于我在这里使用 XMLHttpRequest 只是为了说明安全问题，我将实现一个最小化的版本。具体来说，我只支持同步请求。¹⁴ 这个最小化的 XMLHttpRequest 用起来像这样：

```javascript
x = new XMLHttpRequest();
x.open("GET", url, false);
x.send();
// 使用 x.responseText
```

我们用 JavaScript 定义 XMLHttpRequest 对象及其方法。open 方法只是保存方法和 URL：¹⁵

```javascript
function XMLHttpRequest() {}
XMLHttpRequest.prototype.open = function(method, url, is_async) {
    if (is_async) throw Error("Asynchronous XHR is not supported");
    this.method = method;
    this.url = url;
}
```

send 方法调用一个导出函数：¹⁶

```javascript
XMLHttpRequest.prototype.send = function(body) {
    this.responseText = call_python("XMLHttpRequest_send",
        this.method, this.url, body);
}
```

XMLHttpRequest_send 函数只是调用 request：¹⁷

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        full_url = self.tab.url.resolve(url)
        headers, out = full_url.request(body)
        return out
```

有了 XMLHttpRequest，网页就可以响应用户操作发起 HTTP 请求，使网站更具交互性（见图 10.2）。这个 API 以及 fetch [14] 等更新的类似 API，正是网站实现点赞、悬停预览、无需重新加载页面即可提交表单等功能的方式。

示意图（单页应用中的请求流转）：

```text
页面（Page）中的脚本 → 浏览器：XMLHttpRequest
浏览器 → 服务器：GET Request
服务器 → 浏览器：HTML
页面 → 浏览器：XMLHttpRequest
浏览器 → 服务器：Request
服务器 → 浏览器：JSON（或任意内容）
```

*图 10.2　利用 XMLHttpRequest 的单页应用（single-page application）架构。*

> **深入探索**
>
> XMLHttpRequest 对象有 setRequestHeader [15] 和 getResponseHeader [16] 方法来控制 HTTP 头。不过，这可能让脚本得以干扰 Cookie 机制或其他安全措施，因此有些请求 [17] 和响应 [18] 头是无法从 JavaScript 访问的。

## 10.5 同源策略

然而，新的能力带来新的责任。用 XMLHttpRequest 发送的 HTTP 请求会带上 Cookie。这是有意为之：当你「点赞」时，服务器需要把这个「赞」关联到你的账户。但这也意味着 XMLHttpRequest 可以访问私人数据，因此需要加以保护。

假设攻击者想知道你在我们留言簿服务器上的用户名。你登录后，留言簿会把你的用户名显示在页面上（写着「Hello, 某某」的地方），所以带上你的 Cookie 读取留言簿页面，就足以确定你的用户名。

利用 XMLHttpRequest，攻击者的网站¹⁸ 可以请求留言簿页面：

```javascript
x = new XMLHttpRequest();
x.open("GET", "http://localhost:8000/", false);
x.send();
user = x.responseText.split(" ")[2].split("<")[0];
```

这里的问题在于：一台服务器的网页内容被发送给了运行在另一台服务器所分发网站上的脚本。由于这些内容派生自 Cookie，这就泄露了私人数据。

为了防止这类问题，浏览器制定了同源策略（same-origin policy）[19]：像 XMLHttpRequest¹⁹ 这样的请求只能发往同一个「源」（origin）——即协议（scheme）、主机名和端口都相同——上的网页。²⁰ 这样一来，一个网站的私人数据必须留在该网站上，无法泄露给另一台服务器上的攻击者。

让我们为浏览器实现同源策略。我们需要把请求的 URL 与我们当前所在页面的 URL 进行比较：

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        # ...
        if full_url.origin() != self.tab.url.origin():
            raise Exception("Cross-origin XHR request not allowed")
        # ...
```

origin 函数只需把 URL 的路径部分去掉：

```python
class URL:
    def origin(self):
        return self.scheme + "://" + self.host + ":" + str(self.port)
```

现在攻击者无法读取留言簿网页了。但他们能往里写吗？其实……

> **深入探索**
>
> 同源策略有一个有趣的变种，涉及图片和 HTML 的 <canvas> 元素。drawImage 方法 [20] 允许把一张图片绘制到画布上，即使该图片是从另一个源加载的。但为了防止该图片被 getImageData [21] 等方法读回，向画布写入跨源数据会使其被「污染」（taint）[22]，从而阻止各种读取方法。

## 10.6 跨站请求伪造

同源策略阻止了跨源的 XMLHttpRequest 调用。但同源策略并不约束点击链接、填写表单这类普通的浏览器行为。这就给了一种称为跨站请求伪造（cross-site request forgery，常缩写为 CSRF）的攻击以可乘之机。

在跨站请求伪造攻击中，攻击者不再使用 XMLHttpRequest，而是使用一个提交到留言簿的表单：

```html
<form action="http://localhost:8000/add" method=post>
    <p><input name=guest></p>
    <p><button>Sign the book!</button></p>
</form>
```

尽管这个表单位于坏人的网站上，但当你提交它时，浏览器会向留言簿发出 HTTP 请求。这意味着它会带上留言簿的 Cookie，于是就是已登录状态，于是留言簿的代码会允许发帖。而用户根本无从知道一个表单会提交到哪台服务器——攻击者的网页完全可以在这件事上撒谎——所以他们可能发布了自己并不想发布的内容。²¹

当然，攻击者读不到响应，所以这并不会向攻击者泄露私人数据。但它能让攻击者冒充用户行事！用这种方式发一条评论并不可怕（尽管无良广告商会为它付钱！），但发起一笔银行转账就很可怕了。而且如果网站有修改密码的表单，甚至可能由此找到接管账户的门路。

不幸的是，我们不能简单地把同源策略套用到表单提交上。²² 那么如何防御这种攻击呢？首先，服务器可以做些事情。通常的建议是：给服务器提供的每个表单一个唯一的身份，并确保每个 POST 请求都来自其中之一。做法是在表单里嵌入一个称为 nonce（一次性随机数）的秘密值，并拒绝不带正确秘密值的表单提交。²³ 你只能从服务器拿到 nonce，而且 nonce 与用户会话绑定，²⁴ 所以攻击者无法把它嵌到自己的表单里。

要实现这个修复，在表单被请求时生成一个 nonce 并保存到用户会话中：²⁵

```python
def show_comments(session):
    # ...
    if "user" in session:
        nonce = str(random.random())[2:]
        session["nonce"] = nonce
        # ...
        out += "<input name=nonce type=hidden value=" + nonce + ">"
```

表单提交时，服务器检查随表单一起提交的 nonce 是否正确：²⁶

```python
def add_entry(session, params):
    if "nonce" not in session or "nonce" not in params: return
    if session["nonce"] != params["nonce"]: return
    # ...
```

现在这个表单就只能从我们的网站提交了。对应用中的每个表单重复这个 nonce 修复，它就能免受 CSRF 攻击。但服务器端的解决方案很脆弱（要是漏掉了某个表单怎么办？），而且指望天底下每个网站都做对更是痴人说梦。更好的办法是由浏览器提供一个失效保护（fail-safe）后备机制。

> **深入探索**
>
> 有一种不常见的攻击，思路与跨站请求伪造类似，叫做点击劫持（click-jacking）[23]。在这种攻击中，一个透明 iframe 中的外部网站被叠放在攻击者的网站之上。用户以为自己在某一个网站上点击，实际上却在另一个网站上执行操作。如今，网站可以通过 Content-Security-Policy 的 frame-ancestors 指令 [24] 或较旧的 X-Frame-Options 头 [25] 来防止这种情况。

## 10.7 SameSite Cookie

对于表单提交，这个失效保护方案就是 SameSite Cookie。其思想是：如果服务器把自己的 Cookie 标记为 SameSite，浏览器就不会在跨站表单提交中发送它们。²⁷

在 Set-Cookie 头中像这样把 Cookie 标记为 SameSite：

```text
Set-Cookie: foo=bar; SameSite=Lax
```

SameSite 属性可以取值 Lax、Strict 或 None，而且在我写作本书时，各浏览器现有的默认值与计划中的默认值各不相同。我们的浏览器将只实现 Lax 和 None 两种取值，并默认为 None。当 SameSite 设为 Lax 时，Cookie 不会随跨站 POST 请求发送，但会随同站 POST 请求或跨站 GET 请求发送。²⁸

首先，让我们修改 COOKIE_JAR，让它存储「Cookie/参数」对，然后从 Set-Cookie 头中解析出这些参数：

```python
def request(self, payload=None):
    if "set-cookie" in response_headers:
        cookie = response_headers["set-cookie"]
        params = {}
        if ";" in cookie:
            cookie, rest = cookie.split(";", 1)
            for param in rest.split(";"):
                if '=' in param:
                    param, value = param.split("=", 1)
                else:
                    value = "true"
                params[param.strip().casefold()] = value.casefold()
        COOKIE_JAR[self.host] = (cookie, params)
```

在 HTTP 请求中发送 Cookie 时，浏览器只发送 Cookie 的值，不发送参数：

```python
def request(self, payload=None):
    if self.host in COOKIE_JAR:
        cookie, params = COOKIE_JAR[self.host]
        request += "Cookie: {}\r\n".format(cookie)
```

这样我们就存储了 Cookie 的 SameSite 参数。但要真正用上它，我们还需要知道 HTTP 请求是从哪个站点发出的。让我们给 request 加一个新的 referrer（引用页）参数来跟踪它：²⁹

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
```

我们的浏览器在三处调用 request，每一处都需要传入顶层 URL。在 load 的开头，它发起对页面的初始请求。像这样修改它：

```python
class Tab:
    def load(self, url, payload=None):
        headers, body = url.request(self.url, payload)
        # ...
```

这里 url 是要访问的新 URL，而 self.url 是发起请求的来源页面的 URL。务必让这一行位于 load 的顶部，赶在 self.url 被修改之前！

稍后，浏览器会通过更多 request 调用来加载样式和脚本：

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        for script in scripts:
            # ...
            try:
                header, body = script_url.request(url)
            except:
                continue
            # ...
        # ...
        for link in links:
            # ...
            try:
                header, body = style_url.request(url)
            except:
                continue
            # ...
        # ...
```

对这些请求来说，顶层 URL 就是正在加载的新 URL。因为正是新页面让我们去请求这些特定的样式和脚本，所以由它来定义哪些资源属于同一站点。

类似地，由 XMLHttpRequest 触发的请求把标签页的 URL 作为自己的顶层 URL：

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        # ...
        headers, out = full_url.request(self.tab.url, body)
        # ...
```

现在 request 函数可以在发送 SameSite Cookie 之前检查 referrer 参数了。记住：SameSite Cookie 只在 GET 请求时发送，或者在新 URL 与顶层 URL 的主机名相同时发送：³⁰

```python
def request(self, referrer, payload=None):
    if self.host in COOKIE_JAR:
        # ...
        cookie, params = COOKIE_JAR[self.host]
        allow_cookie = True
        if referrer and params.get("samesite", "none") == "lax":
            if method != "GET":
                allow_cookie = self.host == referrer.host
        if allow_cookie:
            request += "Cookie: {}\r\n".format(cookie)
        # ...
```

注意，我们检查了 referrer 是否已设置——在新标签页中加载第一个网页时，它还没有值。

现在我们的留言簿可以把它的 Cookie 标记为 SameSite 了：

```python
def handle_connection(conx):
    if 'cookie' not in headers:
        template = "Set-Cookie: token={}; SameSite=Lax\r\n"
        response += template.format(token)
```

SameSite 提供了一种「纵深防御」（defense in depth），是一道失效保护，确保即使我们在某处漏掉了一个 nonce，我们仍然能免受 CSRF 攻击。但不要删掉我们先前加的 nonce！它们对旧浏览器很重要，而且在多域名等场景下更灵活。

> **深入探索**
>
> Web 最初并非围绕安全来设计，这导致事后打上了不少别扭的补丁 [29]。这些补丁可能难看，但对向后兼容的坚持是 Web 的一大优点，而且至少较新的 API 可以围绕更一致的策略来设计。
>
> 为此，尽管 SameSite 有完整的规范，现实中的浏览器仍然只支持该特性的不同子集，或采用不同的默认值。例如，Chrome 默认为 Lax，而 Firefox 和 Safari 则不然。同样，Chrome 把协议（https 或 http）纳入「站点」定义的一部分，³¹ 但其他浏览器可能不这么做。造成这种局面的主要原因是需要与现有网站保持向后兼容。

## 10.8 跨站脚本

现在其他网站无法滥用我们浏览器的 Cookie 去读写私人数据了。看起来很安全了！但我们自己的网站呢？既然 JavaScript 能够访问 Cookie，原则上在我们的浏览器上运行的任何脚本都能读到 Cookie 的值。这看上去无害——我们的浏览器不是只运行 comment.js 吗？但实际上……

一个 Web 服务需要保护自己不被滥用。看看我们留言簿中输出留言簿条目的这段代码：

```python
out += "<p>" + entry + "\n"
out += "<i>by " + who + "</i></p>"
```

注意，entry 可以是任何内容，包括用户可能塞进我们评论表单的任何东西。其中包括 HTML 标签，比如一个自定义的 <script> 标签！于是，一个恶意用户可以发布这样一条评论：

```text
Hi! <script src="http://my-server/evil.js"></script>
```

服务器随后会输出这段 HTML：

```html
<p>Hi! <script src="http://my-server/evil.js"></script>
<i>by crashoverride</i></p>
```

每个用户的浏览器随后都会下载并运行 evil.js 脚本，它可以把³² Cookie 发送给攻击者。攻击者随后就能冒充其他用户，以他们的名义发帖，或滥用这些用户拥有的任何其他能力。

这里的核心问题是：用户评论本应是数据，浏览器却把它们当作代码来解释。在 Web 应用中，这类漏洞通常称为跨站脚本（cross-site scripting，常写作 XSS），不过「把数据误当作代码解释」是各种程序中都很常见的安全问题。

标准的修复方法是对数据进行编码，使其无法被解释为代码。例如，在 HTML 中，可以写 &lt; 来显示一个小于号。³³ Python 有一个 html 模块可用于这类编码：

```python
import html

def show_comments(session):
    # ...
    out += "<p>" + html.escape(entry) + "\n"
    out += "<i>by " + html.escape(who) + "</i></p>"
    # ...
```

这是一个很好的修复，每个应用都应该一丝不苟地做好这种转义（escaping）。但只要任何地方有一段文本忘了编码——那就是一个安全漏洞。所以浏览器还提供了额外的防线。

> **深入探索**
>
> 由于我们在第 6 章实现的 CSS 解析器非常宽容，有些 HTML 页面也会被解析成合法的 CSS。由此产生一种攻击：把一个外部 HTML 页面当作样式表引入，再观察它应用的样式。类似的一种攻击 [31] 是把外部 JSON 文件当作脚本引入。设置 Content-Type 头可以借助浏览器的跨源读取阻断（Cross-Origin Read Blocking）[32] 策略来防止这类攻击。

## 10.9 内容安全策略

其中一层防线就是 Content-Security-Policy（内容安全策略）头。这个头的完整规范相当复杂，但在最简单的情形下，该头被设为关键字 default-src 后跟一个以空格分隔的服务器列表：

```text
Content-Security-Policy: default-src http://example.org
```

这个头要求浏览器不要加载来自所列源之外的任何资源（包括 CSS、JavaScript、图片等）。如果我们的留言簿使用了 Content-Security-Policy，那么即使攻击者成功让一个 <script> 被加进了页面，浏览器也会拒绝加载和运行该脚本。

让我们实现对这种头的支持。首先，我们需要 request 返回响应头：

```python
class URL:
    def request(self, referrer, payload=None):
        # ...
        return response_headers, content
```

务必更新 request 的所有现有用法，让它们忽略返回的头。

接下来，加载页面时我们需要提取并解析 Content-Security-Policy 头：³⁴

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        self.allowed_origins = None
        if "content-security-policy" in headers:
            csp = headers["content-security-policy"].split()
            if len(csp) > 0 and csp[0] == "default-src":
                self.allowed_origins = []
                for origin in csp[1:]:
                    self.allowed_origins.append(URL(origin).origin())
        # ...
```

这个解析必须发生在请求任何 JavaScript 或 CSS 之前，因为我们现在需要检查这些请求是否被允许：

```python
class Tab:
    def load(self, url, payload=None):
        # ...
        for script in scripts:
            script_url = url.resolve(script)
            if not self.allowed_request(script_url):
                print("Blocked script", script, "due to CSP")
                continue
            # ...
```

注意，我们需要先把相对 URL 解析成绝对 URL，才能判断它们是否被允许。给加载 CSS 的代码加上类似的检查。

XMLHttpRequest 的 URL 也需要检查：³⁵

```python
class JSContext:
    def XMLHttpRequest_send(self, method, url, body):
        full_url = self.tab.url.resolve(url)
        if not self.tab.allowed_request(full_url):
            raise Exception("Cross-origin XHR blocked by CSP")
        # ...
```

allowed_request 检查既要处理没有 Content-Security-Policy 的情况，也要处理有的情况：

```python
class Tab:
    def allowed_request(self, url):
        return self.allowed_origins == None or \
            url.origin() in self.allowed_origins
```

留言簿现在可以发送 Content-Security-Policy 头了：

```python
def handle_connection(conx):
    # ...
    csp = "default-src http://localhost:8000"
    response += "Content-Security-Policy: {}\r\n".format(csp)
    # ...
```

为了验证我们的实现能工作，让留言簿请求一个来自允许服务器列表之外的脚本：

```python
def show_comments(session):
    # ...
    out += "<script src=https://example.com/evil.js></script>"
    # ...
```

如果你把一切都实现正确了，浏览器就应该阻断这个恶意脚本³⁶并在控制台中报告。

那么，我们大功告成了吗？留言簿彻底安全了吗？呃……没有。Web 应用安全远不止本书讲的这些，还有太多太多的内容。而且与本书其余部分一样，还有许多其他涉及安全与隐私的浏览器机制。让我们接受这样一个事实就好：留言簿比以前更安全了。

> **深入探索**
>
> 在一个复杂的网站上，部署 Content-Security-Policy 可能会意外弄坏一些东西。因此，浏览器可以使用 report-to 指令 [33] 自动把 Content-Security-Policy 违规报告给服务器。Content-Security-Policy-Report-Only [34] 头让浏览器报告内容安全策略的违规，但并不真正阻断请求。

## 10.10 总结

我们以 Cookie 的形式给浏览器添加了用户数据，随即就背负起保护这些数据、确保它们不被滥用的沉重负担。这包括：

- 用同源策略缓解跨站 XMLHttpRequest；
- 用 nonce 和 SameSite Cookie 缓解跨站请求伪造；
- 用转义和 Content-Security-Policy 缓解跨站脚本。

我们也看到了一个更普遍的教训：浏览器能力的每一次增强，都会带来它在保护用户数据方面责任的相应加重。在 Web 浏览器的整个设计中，安全都是一个无处不在的考量。

> **警告**
>
> 本书的目的在于讲解 Web 浏览器的内部原理，而不是讲授 Web 应用安全。要让这个留言簿真正安全，还有很多事情要做，更不用说防御拒绝服务攻击、处理垃圾信息和恶意滥用了。在编写安全关键的代码之前，请先查阅其他资料。

## 10.12 练习

### 10.1 新的输入控件

为 hidden 和 password 输入元素添加支持。hidden 输入不应显示出来，也不应占用空间；而 password 输入元素应将其内容显示为星号而不是字符。

### 10.2 证书错误

访问 HTTPS 页面时，Web 服务器可能发送无效的证书（certificate）（badssl.com [35] 托管了多种可用于测试的无效证书）。这种情况下，wrap_socket 函数会抛出证书错误；请捕获这些错误并向用户显示一条警告信息。对所有其他 HTTPS 页面，在地址栏中绘制一个挂锁（即字符 \N{lock}）。

### 10.3 脚本访问

实现 document.cookie JavaScript API。读取该字段应返回一个包含 Cookie 值和参数的字符串，其格式与 Cookie 头相似。写入该字段则更新 Cookie 的值和参数，就像收到一个 Set-Cookie 头那样。另外实现 HttpOnly Cookie 参数；带此参数的 Cookie 不能从 JavaScript 读取或写入 [36]。

### 10.4 Cookie 过期

添加对 Cookie 过期的支持。Cookie 的过期日期在 Set-Cookie 头中设置；如果同一个 Cookie 再次被设置且日期更晚，过期日期可以被覆盖。在服务器端，把过期日期保存在 SESSIONS 变量中，并用它删除过旧的会话以节省内存。

### 10.5 跨源资源共享（CORS）

Web 服务器可以选择加入 [37] 允许跨源 XMLHttpRequest。其工作方式是：对于跨源 HTTP 请求，浏览器发出该请求并附带一个 Origin 头，其值为发起请求站点的源；该请求会带上目标源的 Cookie。为满足同源策略，浏览器随后会丢弃响应。但服务器可以发送 Access-Control-Allow-Origin 头，如果它的值是请求方的源或特殊的 * 值，浏览器就会把响应返回给脚本。你的浏览器发出的所有请求都会是 CORS 标准所称的「简单请求」（simple requests）。

### 10.6 Referer

当你的浏览器访问网页，或加载 CSS、JavaScript 文件时，它会发送一个 Referer 头³⁷，其中包含它出发的 URL。网站常把它用于统计分析。请在你的浏览器中实现它。不过，有些 URL 包含不想泄露给其他网站的私人数据，因此浏览器支持 Referrer-Policy 头，³⁸ 它可以取 no-referrer³⁹（离开此页面时永不发送 Referer 头）或 same-origin（仅在导航到同源的另一个页面时才发送）这样的值。请实现 Referrer-Policy 的这两个值。
