## 导言

谈到编程语言的工作原理时，我们总喜欢借用奇幻小说里的比喻：编译器（compiler）是魔法，从事编译器工作的人是巫师，说不定还跟龙有点关系。但在大多数程序员的日常生活中，编译器的表现更像科幻小说里的万能翻译耳机，而不是什么神奇的魔法造物。它们既不炫目，也不戏剧化；不会要求你投入大量注意力。它们只是在后台嗡嗡运转，把你流利使用（或敲出）的语言翻译成机器的陌生语言。

不知为何，科幻作品里的角色似乎很少关心他们的翻译器是怎么工作的。但一旦你写了一段时间代码，就很难不好奇你的编译器到底在做什么。几年前，这份好奇心彻底征服了我，于是我决定通过自己写一个编译器来深入了解编译器。对我来说，为一种真正的、我自己用过的编程语言写编译器很重要。我还希望我的编译器生成的汇编（assembly）代码无需模拟器或虚拟机就能运行。但当我四处寻找时，我发现大多数编译器构造指南用的都是运行在理想化处理器上的玩具语言。其中一些指南非常出色，但并不完全符合我的需求。

一位朋友向我推荐了 Abdulaziz Ghuloum 的一篇短文《An Incremental Approach to Compiler Construction》（http://scheme2006.cs.uchicago.edu/11-ghuloum.pdf），我终于摆脱了困境。这篇文章讲解了如何把 Scheme 编译到 x86 汇编，从最简单的程序入手，每次只增加一个新的语言构造。我并不特别想写一个 Scheme 编译器，于是把文章的方法移植到了我更感兴趣的语言：C。随着项目的推进，我从 x86 换成了它的现代对应物 x64 汇编，还扩展了对 C 更大子集的支持，并添加了一些优化遍（pass）。到这个时候，我已经远远超出了 Ghuloum 原来的 scheme（方案，双关语，抱歉），但他的基本策略效果始终非常出色：一次只关注语言的一小部分，这让我很容易保持正轨，也能清楚地看到自己在不断取得进展。在本书中，你将完成同一个项目。在此过程中，你会更深入地理解你编写的代码，以及运行这些代码的系统。

## 本书适合谁

我为那些好奇编译器如何工作的程序员写了这本书。许多关于编译器构造的书是写给大学或研究生课程的教科书，而本书旨在让自学这个主题的人也能读懂。完成这个项目不需要任何关于编译器、解释器或汇编代码的前置知识。对计算机体系结构有基本了解会有所帮助，但并非必需；我会在重要概念出现时加以讨论，并偶尔向你指出提供更多背景信息的外部资源。话虽如此，这本书并不是写给编程新手的。你应当能独立编写有一定规模的程序，并且熟悉二进制数、正则表达式（regular expression）以及图和树等基本数据结构。你需要对 C 足够熟悉，能够阅读和理解小型 C 程序，但不必是 C 专家。我们会随着讲解逐步深入这门语言的方方面面。

虽然本书面向初学者，但对已经有一些编译器经验的人来说也很有价值。也许你在大学课程或个人项目中实现过一门玩具语言，现在想做点更实际的东西。也许你过去做过解释器，想尝试把程序一路编译到机器码。如果你属于这一类，本书会覆盖一些你已经了解的内容，但也会带来大量新的挑战。至少，我保证你会学到一些关于 C 的知识。

## 为什么要写一个 C 编译器

我假设你已经接受了「写一个编译器」这个想法——毕竟你已经拿起了这本书。我想稍微谈谈我们为什么特别要为 C 写编译器。简短的回答是：C 是一门（相对）简单的语言，但不是玩具语言。就其核心而言，C 简单到即使你从未写过编译器也能实现它。但它也是一个特别清晰的例子，展示了编程语言是如何被它们运行的系统和使用它们的人塑造的。C 的某些方面会随目标硬件而变化；另一些随操作系统而变化；还有一些故意不加规定，以给编译器作者留下更多灵活性。这门语言的一些部分是流传下来的历史产物，为了支持遗留代码而保留至今；另一些则是让 C 更安全、更可靠的较新尝试。

C 这些凌乱的部分值得我们去应对，原因有二。首先，你会建立起一个扎实的思维模型，明白你的编译器如何与系统中其他所有组件协同配合。其次，你会体会到不同人群带给这门语言的不同视角：从努力消除歧义和不一致性的规范作者，到寻求性能提升的编译器实现者，再到只希望代码能正常工作的普通程序员。

我希望这个项目会让你换一种眼光看待所有编程语言：不再是一整套固化在语言标准中的规则，而是设计、实现和使用这些语言的人之间持续进行的协商。一旦你开始这样看待编程语言，它们就会变得更丰富、更有趣，用起来也没那么令人沮丧。

## 从一万英尺高空看编译

在继续之前，我们先从宏观层面看一看源代码如何变成可执行文件，以及编译器在整个过程中的位置。我们顺便澄清一些术语，并复习一点点计算机体系结构。编译器是把代码从一种编程语言翻译成另一种编程语言的程序。它只是让代码跑起来的整套系统中的一个部分（尽管常常是最复杂的部分）。我们将构建的编译器把 C 程序翻译成汇编代码，即我们希望处理器执行的指令的一种文本表示。

不同的处理器理解不同的指令；我们将专注于 x64 指令集，它也被称为 x86-64 或 AMD64。大多数人的电脑运行的就是它。（你可能会遇到的另一种指令集是 ARM。大多数智能手机和平板电脑使用 ARM 处理器，而且它们也开始出现在笔记本电脑上。）

处理器不理解文本，所以它无法直接运行我们的汇编代码。我们需要把汇编转换成目标代码（object code），也就是处理器能够解码并执行的二进制指令。例如，汇编指令 ret 对应字节 0xc3。汇编器（assembler）负责这种转换，接收汇编程序并输出目标文件（object file）。最后，链接器（linker）把我们最终程序需要包含的所有目标文件组合起来，解析对其他文件中变量或函数的引用，并添加一些关于如何真正启动程序的信息。最终结果是一个可以运行的可执行文件。这是对实际过程的极度简化，但足以让我们起步。

除编译器、汇编器和链接器之外，编译一个 C 程序还需要另一个工具：预处理器（preprocessor），它在编译器之前运行。预处理器剔除注释、执行 #include 等预处理指令，并展开宏，生成可以编译的预处理后代码。整个过程大致如图 1 所示。

当你用 gcc 或 clang 这样的命令编译程序时，你实际上调用的是编译器驱动（compiler driver）——一个负责依次调用预处理器、编译器、汇编器和链接器的小包装程序。你会编写自己的编译器和编译器驱动，但不会编写自己的预处理器、汇编器或链接器，而是使用系统上已安装的这些工具。

## 你将构建什么

在本书的进程中，你将为 C 的一个大型子集构建编译器。你可以用任何你喜欢的编程语言来编写编译器；我会以伪代码的形式给出实现的关键部分。本书分为三个部分。在第 I 部分「基础」（The Basics）中，你将实现 C 的核心特性：表达式、变量、控制流语句和函数调用。

**第 1 章　最小的编译器（A Minimal Compiler）**　在本章中，你将构建一个能处理最简单的 C 程序（只返回整数常量的程序）的可用编译器。你将了解编译的各个阶段、如何在内部把 C 程序表示为抽象语法树（abstract syntax tree, AST），以及如何阅读简单的汇编程序。

**第 2 章　一元运算符（Unary Operators）**　接下来，你将通过实现两个一元运算符——取负和按位取反——开始扩展你的编译器。本章引入了 TACKY，一种新的中间表示（intermediate representation, IR），它在抽象语法树与汇编代码之间架起桥梁。本章还讲解如何在汇编中执行取负和按位取反，以及汇编程序如何把值存储在一块称为栈（stack）的内存区域中。

**第 3 章　二元运算符（Binary Operators）**　在本章中，你将实现执行加法和减法等基本算术运算的二元运算符。你将使用一种叫作优先级爬升（precedence climbing）的技术，以正确的结合性和优先级解析算术表达式，并学习如何在汇编中做算术。

**第 4 章　逻辑与关系运算符（Logical and Relational Operators）**　在这里，你将添加对逻辑 AND、OR、NOT 运算符以及 >、==、!= 等关系运算符的支持。本章介绍几种新的汇编指令，包括条件指令和跳转指令。

**第 5 章　局部变量（Local Variables）**　接下来，你将扩展编译器以支持局部变量的声明、使用和赋值。你将在本章添加一个新的编译器阶段来执行语义分析（semantic analysis）。该阶段会检测诸如使用未声明变量之类的编程错误。

**第 6 章　if 语句与条件表达式（if Statements and Conditional Expressions）**　在本章中，你将添加对 if 语句（编译器的第一个控制流结构）以及形如 a ? b : c 的条件表达式的支持。把 TACKY 用作中间表示在这里会得到回报：你可以用现有的 TACKY 指令实现这两种语言构造，因此无需改动后面的编译器阶段。

**第 7 章　复合语句（Compound Statements）**　在这里，你将添加对复合语句的支持。复合语句把多条语句和声明组织在一起，并控制标识符的作用域。你将仔细研究 C 的作用域规则，并学习如何在语义分析阶段应用这些规则。

**第 8 章　循环（Loops）**　本章涵盖 while、do 和 for 循环，以及 break 和 continue 语句。你将编写一个新的语义分析遍，把 break 和 continue 语句与包含它们的循环关联起来。

**第 9 章　函数（Functions）**　在本章中，你将实现函数调用以及 main 之外其他函数的声明。这里有两个主要任务：编写类型检查器（type checker）来检测诸如以错误数量的参数调用函数之类的语义错误；以及生成汇编代码。你将全面了解类 Unix 系统的调用约定（calling convention），它规定了函数调用在汇编中如何工作。通过一丝不苟地遵循这些约定，你将能够编译调用外部库的代码。

**第 10 章　文件作用域变量声明与存储类说明符（File Scope Variable Declarations and Storage-Class Specifiers）**　接下来，你将添加对文件作用域变量声明以及 extern 和 static 说明符的支持。本章讨论 C 标识符的若干性质，包括链接性（linkage）和存储期（storage duration）；逐步讲解如何在语义分析阶段确定标识符的链接性和存储期，并介绍这些性质如何影响你最终生成的汇编。本章还引入一块新的内存区域——数据段（data section），并描述如何定义和操作存储在其中的值。

在第 II 部分「int 之外的类型」（Types Beyond int）中，你将实现更多类型。我们会在这里最深入地审视 C 中那些凌乱、令人困惑和出人意料的细节。

**第 11 章　长整数（Long Integers）**　在本章中，你将实现 long 类型，并为后续章节添加更多类型打下基础。你将学习如何在类型检查期间推断每个表达式的类型，以及如何在汇编中对不同大小的值进行操作。

**第 12 章　无符号整数（Unsigned Integers）**　在这里，你将实现无符号整数类型。本章深入探讨 C 标准关于整数类型转换的规则，并介绍若干执行无符号整数运算的新汇编指令。

**第 13 章　浮点数（Floating-Point Numbers）**　接下来，你将添加浮点（floating-point）double 类型。本章描述浮点数的二进制表示以及浮点舍入误差的风险，介绍一组执行浮点运算的新汇编指令，并讲解传递浮点参数和返回值的调用约定。

**第 14 章　指针（Pointers）**　在本章中，你将实现指针类型以及取地址和指针解引用（dereference）运算符。你将在类型检查器中验证指针操作，并向 TACKY 中间表示添加显式的内存访问指令。

**第 15 章　数组与指针算术（Arrays and Pointer Arithmetic）**　本章接着第 14 章继续，添加对数组类型以及若干相关语言特性的支持：下标运算符（subscript operator）、指针算术（pointer arithmetic）和复合初始化器（compound initializer）。本章深入探讨数组与指针之间的关系，并阐明类型检查器应当如何分析这些类型。

**第 16 章　字符与字符串（Characters and Strings）**　本章涵盖字符类型、字符常量（character constant）和字符串字面量（string literal）。你将了解 C 程序使用字符串字面量的各种方式，并添加新的 TACKY 和汇编构造来表示字符串常量。在本章末尾，你将编译几个执行输入/输出（I/O）操作的示例程序。

**第 17 章　支持动态内存分配（Supporting Dynamic Memory Allocation）**　在本章中，你将实现 void 类型和 sizeof 运算符，这将使你能够编译调用 malloc 及其他内存管理函数的程序。这里最大的挑战是在类型检查器中处理 void。由于 void 是一个没有任何值的类型，类型检查器对它的处理方式将与你目前实现的其他类型大不相同。

**第 18 章　结构（Structures）**　结构（structure）以及 . 和 -> 成员访问（member access）运算符是你在本书中添加的最后一批语言特性。要实现它们，你需要用到前面各章学到的所有技能。在语义分析阶段，你将根据 C 的作用域规则解析结构标签，并分析结构类型声明以确定它们在内存中的布局。在生成 TACKY 时，你会把成员访问运算符翻译成一连串简单的内存访问指令。在生成汇编时，你将遵循把结构作为参数和返回值传递的调用约定。

在第 III 部分「优化」（Optimizations）中，你不会再添加任何新的语言特性，而是实现若干经典编译器优化，以生成更高效的汇编代码。第 III 部分与第 I、II 部分有很大不同，因为这些优化并不针对 C；它们对用任何语言编写的程序同样有效。

**第 19 章　优化 TACKY 程序（Optimizing TACKY Programs）**　在本章中，你将添加一个针对 TACKY 程序的优化阶段。该阶段包含四种不同的优化：常量折叠（constant folding）、不可达代码消除（unreachable code elimination）、死存储消除（dead store elimination）和复制传播（copy propagation）。这四种优化协同工作，使每一种都比单独使用时更加有效。本章介绍几种理解程序行为的工具，包括控制流图（control-flow graph）和数据流分析（data-flow analysis）。你将使用这些工具来发现在不改变程序行为的前提下优化程序的方法。

**第 20 章　寄存器分配（Register Allocation）**　作为项目的压轴，你将编写一个寄存器分配器（register allocator），让它找出如何把汇编程序中的值保存在寄存器（register）而不是内存中。你将使用图着色（graph coloring）来寻找从值到寄存器的有效映射。当寄存器分配器的初始版本可以工作后，你将使用另一种技术——寄存器合并（register coalescing）——让它变得更加高效，并删除一些不必要的汇编指令。

**后续步骤（Next Steps）**　我们将以一些建议收尾，谈谈如何继续学习并独立扩展你的编译器。

第 II 部分和第 III 部分都建立在第 I 部分之上，但它们彼此独立。你可以完成其中任何一个、两个都完成，或者都不完成。附录包含一些有用的信息，可供你随时查阅。

**附录 A　用 GDB 或 LLDB 调试汇编代码（Debugging Assembly Code with GDB or LLDB）**　本附录逐步讲解如何使用 GDB（GNU 调试器）和 LLDB（LLVM 调试器）来调试汇编程序。当你的编译器生成了有错误的汇编时，这些工具会帮你弄清楚到底发生了什么。

**附录 B　汇编生成与代码输出表（Assembly Generation and Code Emission Tables）**　本附录中的表格总结了如何把每种 TACKY 构造转换为汇编，以及在代码输出（code emission）期间如何打印每种汇编构造。我们更新这些遍的所有章节都包含类似的表格，展示该章的改动内容；本附录把它们汇总在一起。

最后要说清楚一点：本书覆盖面很广，但并没有覆盖所有内容。C 中有一些非常重要的部分我们不会实现：仅举几例，函数指针、可变参数列表、typedef，以及 const 之类的类型限定符。与其塞进尽可能多的特性，我们会深入钻研确实实现的那些特性，让你真正理解它们如何工作、为何如此。这样，你将学到继续自行扩展所需的所有技能和概念。

## 如何使用本书

每一章都是实现某个特定特性的详细指南。在每章开头，我会讨论你即将构建的特性，以及开始之前需要理解的任何重要概念。然后，我们会一步步讲解如何更新编译器的每个阶段来支持这个新特性。对于特别棘手或特别重要的步骤，我会附上伪代码。不必觉得必须严格照着伪代码实现；它的作用是阐明你要完成的目标，而不是规定实现过程中的所有细节。

每一章都建立在前一章的基础上，所以你需要按顺序完成各章，只有一个例外：你可以不先完成第 II 部分而直接跳到第 III 部分。

### 测试套件

每一章都包含若干检查点，你可以在这些地方停下来，用本书的测试套件（test suite）测试你的编译器，它位于 https://github.com/nlsandler/writing-a-c-compiler-tests。对于每一章，测试套件都包含一组无效的测试程序（你的编译器应当以错误消息拒绝它们）和一组有效的测试程序（你的编译器应当成功编译它们）。请使用附带的 test_compiler 脚本来运行测试。

### 额外加分特性

一些章节会提到你可以自行实现的附加语言特性；我把它们称为「额外加分」（extra credit）特性。额外加分特性与本章涵盖的主要特性相关，可以用你已学过的技术来实现，但细节要你自己摸索。你可能需要查看几个测试程序的汇编输出，弄清楚该如何处理它们。你还需要查阅外部参考资料，比如 C 标准和 x64 指令集的文档（你可以在「其他资源」（Additional Resources，page xxxvi）中找到这些资源的链接）。额外加分特性完全可选；试试那些看起来有趣的，跳过那些不感兴趣的。

这些特性的测试包含在测试套件中，但默认不会运行。你可以通过向 test_compiler 传递适当的命令行选项来运行它们。

## 关于选择实现语言的一些建议

虽然可以用任何编程语言编写编译器，但有些语言比另一些更适合这项任务。我们要构建的是 C 编译器，但我不推荐用 C 来编写它。尽管 C 作为编程语言有其长处，这个项目却用不上其中任何一点。选择一门内存管理更轻松、标准库更丰富的语言会让你省力得多。

你还应该考虑使用支持模式匹配（pattern matching）的语言。你可以把它想象成一种增强版的 switch 语句，它允许你为结构不同、携带数据不同的值定义不同的分支。（注意，这与正则表达式匹配不是一回事，尽管后者偶尔也被称为「模式匹配」。）我们的第一段伪代码就展示了模式匹配的实际应用：

```text
greet(someone):
    match someone with
    | ImportantPerson(title, last_name) ->
        say("Good day to you, {title} {last_name}!")
    | Friend(first_name) -> say("Hello, {first_name}!")
    | Stranger -> say("Howdy, stranger!")
    | Animal(name, species) ->
        say("Hi, {name}! Who's a good {species}? It's you!")
```

事实证明，模式匹配对于分析和变换程序极其有用，因为程序中通常包含多种类型的表达式、语句等等，就像这样：

```text
do_something(expr):
    match expr with
    | Constant(int) -> do_something_for_int(int)
    | BinaryExpr(op, left, right) ->
        do_something(left)
        do_something(right)
    // handle more kinds of expressions
```

本书的伪代码处处使用模式匹配，所以如果你使用一门支持模式匹配的语言，跟着学起来会轻松许多。

很长一段时间里，模式匹配都是 ML、Haskell 等函数式语言的专属。（这些语言在编程语言学术界非常流行，这并非巧合。）最近，几乎所有其他语言社区都注意到了模式匹配的好处，它正在进入更多主流语言。Rust 和 Swift 都支持模式匹配，Python 在 3.10 版本中加入了它，Java 则从版本 16 开始逐步构建对它的支持。在你开始用自己最喜欢的语言写编译器之前，先做一点调查，看看它对模式匹配的支持程度如何。根据调查结果，你可能决定使用该语言最新最强的版本、使用一个模式匹配库（例如 C++ 就有好几个），或者改用你的第二喜欢的语言。你也可能决定无视我的建议；模式匹配确实有帮助，但没有它你也能完成。

## 系统要求

要完成这个项目，你需要一台配备 x64 处理器的 macOS 或 Linux 系统（或者一台配备 Apple Silicon 处理器的 Mac，它可以不太费力地模拟 x64）。如果你用的是 Windows 机器，就需要用 Windows Subsystem for Linux（WSL）搭建一个 Linux 环境。WSL 的安装说明见 https://docs.microsoft.com/en-us/windows/wsl/install。

本项目有两个依赖。要运行 test_compiler，你需要 Python 3.8 或更高版本。你可能已经安装了较新的 Python；如果没有，可以从 https://www.python.org/downloads 下载，或者用系统的包管理器安装。（更详细的安装说明见本书网页 https://norasandler.com/book/#setup。）要检查你安装的 Python 版本是否合适，请运行：

```bash
$ python3 --version
```

你还需要一个真正的 C 编译器（严格地说，是一个真正的 C 编译器驱动）来调用预处理器、汇编器和链接器。测试脚本同样依赖编译器驱动。在 Linux 上，使用 GCC 作为编译器驱动。在 macOS 上，使用 Xcode 自带的 Clang 版本。（测试脚本使用 gcc 命令来调用编译器驱动；Xcode 的 Clang 会同时以 clang 和别名 gcc 两个名称安装。）最好再安装一个能单步调试汇编代码的调试器，帮助你调试编译器产生的代码。我建议在 Linux 上用 GDB 调试，在 macOS 上用 LLDB。

### 在 Linux 上安装 GCC 和 GDB

如果你运行的是 Linux，应当使用 GCC 作为编译器驱动，GDB 作为调试器。要检查它们是否已经安装，请运行：

```bash
$ gcc -v
$ gdb -v
```

如果其中任何一个命令不存在，可以用系统的包管理器安装。例如，要在 Ubuntu 上安装这两个工具，请运行：

```bash
$ sudo apt-get install gcc gdb
```

### 在 macOS 上安装命令行开发者工具

macOS 上最简单的选择是安装 Xcode 命令行开发者工具，其中包含 Clang 编译器和 LLDB 调试器。要检查它们是否已经安装，请运行：

```bash
$ clang -v
```

如果这些工具尚未安装，当你尝试运行这条命令时，系统会提示你安装它们。

本书中的示例都是用 GCC 编译的，所以如果你用 Clang 编译它们，得到的汇编有时会略有不同。这些差异不会影响你完成本项目。

### 在 Apple Silicon 上运行

如果你的电脑配备 Apple Silicon 处理器（Apple 的 ARM 芯片），你需要使用 Rosetta 2 来运行你编译出的程序。最简单的解决方案是把所有东西——包括你的编译器和测试脚本——都作为 x64 二进制在 Rosetta 2 下运行。要打开一个 x64 shell，请运行：

```bash
$ arch -x86_64 zsh
```

你可以在这个 shell 中运行你的编译器、Clang、编译出的程序以及 test_compiler，一切都会正常工作。只需确保把你的编译器本身构建为在 x64 而不是 ARM 上运行。

如果 arch 命令不能用，可能是 Rosetta 2 尚未安装。要安装它，请运行：

```bash
$ softwareupdate --install-rosetta --agree-to-license
```

### 验证你的环境

测试脚本提供了一个 --check-setup 选项，你可以用它来确认系统设置正确。运行以下命令以下载测试套件并验证你的环境：

```bash
$ git clone https://github.com/nlsandler/writing-a-c-compiler-tests.git
$ cd writing-a-c-compiler-tests
$ ./test_compiler --check-setup
All system requirements met!
```

如果测试脚本没有报告任何问题，你就可以开始了！

## 其他资源

你可以在本书的网页 https://norasandler.com/book/ 上找到勘误、更新、链接和其他资源。如果你在项目或测试脚本上遇到问题，请先查看这个页面。GCC、Xcode 命令行工具以及本项目依赖的其他工具都会定期发布新版本；本书网页包含让项目适配这些工具最新版本所需的全部更新。

如果你卡住了，想查看完整可用的项目实现，请参考本书的参考实现：NQCC2——「not-quite-C」（差不多是 C 的）编译器，位于 https://github.com/nlsandler/nqcc2。它用 OCaml 编写，但其中有大量注释，即使你不是 OCaml 程序员也能看懂。

最后，这里有一些你可能会觉得有用的外部资源。如果你决定实现任何额外加分特性，或者以其他方式把你的编译器扩展到本书内容之外，它们会特别有用：

C 标准规定了 C 程序应当如何表现。我们将采用 C17（ISO/IEC 9899:2018），它是本书写作时的最新标准版本。你可以从国际标准机构（International Standards Institute, ISO）购买一份，地址是 https://www.iso.org/standard/74528.html。或者，如果花 200 美元买一份 PDF 不吸引你，可以使用免费提供的相近草案版本：https://www.open-std.org/JTC1/SC22/WG14/www/docs/n2310.pdf。这是 C23（C17 之后的下一个标准版本）的一份早期草案，带有标示改动内容的差异标记。它不是正式的 ISO 标准，所以我不建议用它来构建生产级 C 编译器，但对本项目来说已经足够接近。

System V 应用二进制接口（Application Binary Interface, ABI）定义了可执行文件在类 Unix 操作系统上遵循的一组约定。从第 9 章实现函数调用开始，它会变得很重要。你可以在 https://gitlab.com/x86-psABIs/x86-64-ABI 找到 x64 系统 System V ABI 的最新版本。

《Intel 64 Software Developer's Manual》（https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html）是 Intel 针对 x64 指令集的官方文档。我们关心的是第 2 卷，即指令集参考。还有一个更便于浏览的非官方版本：https://www.felixcloutier.com/x86/。

Compiler Explorer（https://godbolt.org）是一个非常棒的网站，你可以在上面看到各种广泛使用的编译器如何把你的代码翻译成汇编。它让比较不同编译器的输出、观察各种优化级别和编译器标志的影响变得轻而易举。

> **注意**
> C23 定于 2024 年发布，取代 C17。就我们的目的而言，C17 与 C23 之间的差异并不重要。我们不会实现 C23 引入的新语言特性，但我们也不会实现完整的 C17。我们确实实现的那部分 C 子集在两个版本的标准中几乎完全一样。如果你好奇 C23 有哪些不同，可以在 https://open-std.org/JTC1/SC22/WG14/www/docs/n3096.pdf 找到一份免费的接近最终的草案，并在 https://en.cppreference.com/w/c/23 找到一份非正式的变更列表。
