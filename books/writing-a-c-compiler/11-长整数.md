# 第二部分　整数之外的类型（Part II: Types Beyond Int）

# 第 11 章　长整数

*Chapter 11: Long Integers*

本章中，你将添加一个新类型：long。它和 int 一样是有符号整数类型；两者唯一的区别在于所能保存的取值范围。你还将添加显式强制转换（cast）操作，用于把一个值转换成不同的类型。

由于 long 与我们已支持的 int 类型非常相似，我们不需要添加多少新的汇编或 TACKY 指令，也不需要实现复杂的类型转换逻辑。相反，本章的重点是为第 II 部分余下的内容打好基础：我们将跟踪常量和变量的类型、把类型信息附加到 AST 上、识别隐式类型转换并将其显式化，以及确定汇编指令的操作数大小。除了循环标号之外，编译器的每个阶段都至少要做一点小改动。在动手之前，先来看看对 long 的运算在汇编中是什么样子。

## 汇编中的长整数

C 标准没有规定整数类型的大小，但 System V x64 ABI 规定 int 为 4 字节、long 为 8 字节。说得极度简化一些，带 long 操作数的 C 表达式最终会被翻译为作用于 quadword（8 字节操作数）的汇编指令。例如，下面这些汇编指令对 quadword 做运算来计算 2 + 2，并产生一个 quadword 结果：

```asm
movq    $2, %rax
addq    $2, %rax
```

这看起来与使用 longword（4 字节）的等价代码几乎一模一样：

```asm
movl    $2, %eax
addl    $2, %eax
```

唯一的区别是 mov 和 add 指令的后缀，以及我们使用整个 RAX 寄存器还是只用它的低 4 字节 EAX。

**注意**

word、longword 和 quadword 这些术语可以追溯到 16 位处理器的年代，那时 int 是 2 字节、long 是 4 字节。更麻烦的是，4 字节的值常常被称作 doubleword 而不是 longword。我使用 longword 一词是为了与 AT&T 汇编语法保持一致，但 Intel 的文档使用的是 doubleword。

大多数 quadword 指令只接受 8 字节操作数并产生 8 字节结果，正如大多数 longword 指令只接受 4 字节操作数并产生 4 字节结果。而 C 中的表达式常常一次用到多种操作数类型，或者把一种类型的值赋给另一种类型的对象。编译期间，我们会把这些表达式分解成简单的指令，它们要么接受单一类型的操作数并产生相同类型的结果，要么显式地执行类型转换（conversion）。幸运的是，C 标准明确告诉了我们这些类型转换发生在哪里。

### 类型转换

C 标准第 6.3.1.3 节第 1 段定义了整数类型之间的转换方式："如果该值能被新类型表示，则它保持不变。"换句话说，如果某个表达式求值得到 3，然后你把它强制转换为另一个整数类型，那么这个强制转换表达式的结果应该仍然是 3。

由于 long 比 int 大，我们可以放心地把任何 int 转换为 long 而不改变其值。我们对有符号整数使用补码（two's complement）表示，因此从 int 到 long 的转换要使用符号扩展（sign extension），你在第 3 章已经学过。具体来说，我们会使用 movsx（即 "move with sign extension"，带符号扩展的传送）汇编指令。这条指令把 4 字节的源传送到 8 字节的目的地，并把值符号扩展到目的操作数的高 4 字节。

把 long 转换为 int 则更棘手，因为这个值可能太大或太小，无法用 int 表示。第 6.3.1.3 节第 3 段接着告诉我们：当"新类型是有符号的且该值无法在其中表示时[,]要么结果是实现定义的，要么引发一个实现定义的信号"。换句话说，怎么做由我们决定。我们的实现将按照 GCC 文档中的规定，采用与 GCC 相同的方式处理这种转换："对于转换为宽度为 N 的类型，该值按模 2^N 规约到该类型的取值范围内；不引发信号"（https://gcc.gnu.org/onlinedocs/gcc/Integers-implementation.html）。

把一个值按模 2^32 规约，意思是加上或减去 2^32 的某个倍数，使它落入 int 的取值范围。举个例子。int 能表示的最大值是 2^31 – 1，即 2,147,483,647。假设你需要把下一个更大的整数值（2^31，即 2,147,483,648）从 long 转换为 int。从这个值减去 2^32，得到 –2^31，即 –2,147,483,648，这正好是 int 能表示的最小值。

实践中，我们把 long 转换为 int 的方式是丢弃它的高 4 字节。如果某个 long 的值能被 int 表示，丢弃这些字节不会改变它的值。例如，下面是 –3 的 8 字节二进制表示：

```text
11111111 11111111 11111111 11111111 11111111 11111111 11111111 11111101
```

而同一个值的 4 字节表示是：

```text
                                    11111111 11111111 11111111 11111101
```

如果 long 的值无法用 int 表示，丢弃它的高 4 字节就相当于把它的值按模 2^32 规约。回到前面的例子，long 值 2,147,483,648 的二进制表示如下：

```text
00000000 00000000 00000000 00000000 10000000 00000000 00000000 00000000
```

把它转换为 int 之后，结果值为 –2,147,483,648，其二进制表示如下：

```text
                                    10000000 00000000 00000000 00000000
```

要丢弃 long 的高位字节，只需用一条 movl 指令复制它的低位字节。例如，下面的指令会截断存放在 RCX 中的值：

```asm
movl    %ecx, %eax
```

当我们把一个值存入寄存器的低 4 字节时，该寄存器的高 4 字节会被清零。

**实现定义行为警报！**

我们已经多次遇到过未定义行为（undefined behavior），但从 long 转换到 int 时的溢出是我们遇到的第一种实现定义行为（implementation-defined behavior）。语言实现应当以可靠且有据可查的方式处理实现定义行为。通常，当某个行为是实现定义的，标准会给出若干选项供实现自行选择。在本例中，有符号整数溢出可以产生一个整数结果（就像我们的实现这样），也可以引发一个信号，但它不能让你的程序崩溃、向终端打印脏话，或者做出其他明显错误的举动。

### 静态长整型变量

具有静态存储期（static storage duration）的变量在汇编中的定义方式与类型基本无关，但静态 quadword 与 longword 之间还是有几处细小的差别。考虑下面的文件作用域变量声明：

```c
static long var = 100;
```

我们会把这个声明转换为清单 11-1 中的汇编。

```asm
    .data
    .align 8
var:
    .quad 100
```

*清单 11-1：在数据段中初始化一个 8 字节的值*

与我们为静态 int 生成的汇编相比，这里有两点不同：对齐是 8 而不是 4；我们使用 .quad 指示字来初始化一个 8 字节的值，而不是使用 .long 初始化 4 字节。

System V x64 ABI 规定 long 和 int 分别按 8 字节和 4 字节对齐。C 标准对它们的对齐和大小一样不加规定。

*清单 11-2：带 long 常量、类型信息和强制转换表达式的抽象语法树*

type AST 节点可以表示 int、long 和函数类型 ❸。这里不必定义一个全新的数据结构，我们可以直接扩展第 9 章开始在符号表条目中使用的那种类型结构。从现在起，我们将在符号表和 AST 中都使用这个数据结构。

第 9 章中，我们把 type 定义成这样：

```text
type = Int | FunType(int param_count)
```

在清单 11-2 中，我们修改了这个定义：添加了 Long，并记录关于函数类型的更多信息，包括返回类型和形参类型列表。以前我们不需要这些信息，因为每个形参的类型和返回类型都只能是 int。注意，type 的这个新的递归定义可以表示一些非法的类型，比如返回函数的函数，但解析器绝不会产生这些非法类型。

更新了 type 的表示之后，我们把类型信息附加到变量声明 ❶ 和函数声明 ❷ 上。我们不给函数声明中的 params 添加类型信息，因为函数的类型已经包含了各形参的类型。我们还扩展了 exp AST 节点来表示强制转换表达式 ❹，并定义了一个新的 const AST 节点，为 long 常量和 int 常量提供不同的构造器 ❺。类型检查时我们需要区分不同类型的常量。

如果你使用的实现语言既有有符号 64 位和 32 位整数类型，又支持在这两种类型之间进行转换，且转换语义与我们 C 实现中 long 与 int 之间的转换相同，我建议直接用它们来表示 AST 中的 ConstLong 和 ConstInt。（大多数语言都默认或通过库提供了具有这些语义的定宽整数类型。）这样在编译期把静态初始化器强制转换为正确的类型会更容易；它也会简化常量折叠（constant folding）——我们将在第 III 部分实现这项优化。如果你的实现语言没有语义合适的整数类型，你至少要确保 ConstLong 节点使用一个能表示所有 long 值的整数类型。

更新 AST 之后，我们要对文法做相应的修改，如清单 11-3 所示。

*清单 11-3：加入 long 常量、long 类型说明符和强制转换表达式的文法*

这里有两个略微棘手的细节需要处理。第一，每当我们解析一个类型说明符列表时，需要把它转换成单个 type AST 节点。long 整数可以用 long 说明符声明，也可以同时使用 long 和 int，顺序不限。清单 11-4 展示了如何把一个类型说明符列表转换成一个类型。

```text
parse_type(specifier_list):
    if specifier_list == ["int"]:
        return Int
    if (specifier_list == ["int", "long"]
        or specifier_list == ["long", "int"]
        or specifier_list == ["long"]):
        return Long
    fail("Invalid type specifier")
```

*清单 11-4：根据类型说明符列表确定类型*

这适用于没有存储类的类型，我们会在形参列表或强制转换表达式中遇到它们。对于函数和变量声明，我们将在清单 10-21 的说明符解析代码基础上构建。清单 11-5 复现了那段代码，改动以粗体标出。

```text
parse_type_and_storage_class(specifier_list):
    types = []
    storage_classes = []
    for specifier in specifier_list:
        if specifier is "int" or "long":
            types.append(specifier)
        else:
            storage_classes.append(specifier)

    type = parse_type(types)

    if length(storage_classes) > 1:
        fail("Invalid storage class")
    if length(storage_classes) == 1:
        storage_class = parse_storage_class(storage_classes[0])
    else:
        storage_class = null

    return (type, storage_class)
```

*清单 11-5：根据说明符列表确定类型和存储类*

我们仍然像清单 10-21 中那样把类型说明符与存储类说明符分开、并以同样的方式确定存储类，但这里做了几处小改动。首先，我们把 long 识别为类型说明符。其次，我们不再要求类型说明符列表恰好只有一个元素（这一改动没有以粗体标出，因为我们只是删掉了一些现有代码）。第三，不再总是把 type 设为 Int，而是使用新的 parse_type 函数来确定类型。

第二个棘手的细节是解析常量词法单元。清单 11-6 展示了如何把它们转换成 const AST 节点。

```text
parse_constant(token):
    v = integer value of token
    if v > 2^63 - 1:
        fail("Constant is too large to represent as an int or long")

    if token is an int token and v <= 2^31 - 1:
        return ConstInt(v)

    return ConstLong(v)
```

*清单 11-6：把常量词法单元转换为 AST 节点*

我们把整常量词法单元（不带 l 或 L 后缀）解析为 ConstInt 节点，除非它的值超出 int 类型的范围。类似地，我们把 long 常量词法单元（带 l 或 L 后缀）解析为 ConstLong 节点，除非它的值超出 long 的范围。如果某个整常量词法单元的值超出 int 的范围但在 long 的范围内，我们就把它解析为 ConstLong 节点。如果某个整常量或 long 常量词法单元大到 long 都无法表示，我们就抛出错误。

int 是 32 位的，因此能表示从 –2^31 到 2^31 – 1（含两端）的任何值。按照同样的逻辑，long 能表示从 –2^63 到 2^63 – 1 的任何值。你的解析器应当对照相应类型的最大值检查每个常量词法单元。不需要对照最小值检查，因为这些词法单元无法表示负数；负号是一个单独的词法单元。

## 语义分析

接下来，我们要扩展执行语义分析的各个编译遍（pass）。标识符解析只需一处很小的机械改动：扩展 resolve_exp，让它像遍历其他各类表达式那样遍历强制转换表达式。后面的章节里我不会总是明确提到这类修改；从现在起，每当我们添加包含子表达式的新表达式，请自行扩展标识符解析遍去遍历它。做完这个改动之后，我们就可以转向更有意思的问题：扩展类型检查器。

C 程序中的每个对象都有类型，同样，每个表达式的结果也有类型。例如，对两个 int 操作数执行任何二元算术运算，结果都是 int；对两个 long 操作数执行同样的运算，结果是 long；调用一个具有特定返回类型的函数，会产生该类型的结果。

在类型检查遍中，我们将为 AST 中的每个表达式标注其结果的类型。我们将用这些类型信息来确定在 TACKY 中生成的、用于保存中间结果的临时变量的类型。这进而会告诉我们每条汇编指令该用什么操作数大小，以及每个临时变量需要分配多少栈空间。

在为表达式标注类型信息的同时，我们还要识别程序中所有的隐式类型转换，并通过在 AST 中插入 Cast 表达式把它们显式化。这样，在 TACKY 生成期间就能轻松生成正确的类型转换指令。

### 向 AST 添加类型信息

在更新类型检查器之前，我们需要一种把类型信息附加到 exp AST 节点上的方法。最直观的方案如清单 11-7 所示：机械地为每个 exp 构造器添加一个 type 字段。

```text
exp = Constant(const, type)
    | Var(identifier, type)
    | Cast(type target_type, exp, type)
    | Unary(unary_operator, exp, type)
    | Binary(binary_operator, exp, exp, type)
    | Assignment(exp, exp, type)
    | Conditional(exp condition, exp, exp, type)
    | FunctionCall(identifier, exp* args, type)
```

*清单 11-7：为 exp 节点添加类型信息*

如果你使用面向对象的实现语言，并且所有 exp 都有公共基类，这就很容易：直接在基类中添加一个 type 字段即可，如清单 11-8 所示。

```text
class BaseExp {
    --snip--
    type expType;
}
```

*清单 11-8：为 exp 节点的基类添加类型*

但如果你是用代数数据类型（algebraic data type）实现 AST 的，这种方案就非常烦人。你不仅必须更新每一个 exp 构造器，而且每当想获取某个表达式的类型时，还得对每个构造器做模式匹配。清单 11-9 给出了一个没那么繁琐的方案：定义相互递归的 exp 与 typed_exp AST 节点。

```text
typed_exp = TypedExp(type, exp)
exp = Constant(const)
    | Var(identifier)
    | Cast(type target_type, typed_exp)
    | Unary(unary_operator, typed_exp)
    | Binary(binary_operator, typed_exp, typed_exp)
    | Assignment(typed_exp, typed_exp)
    | Conditional(typed_exp condition, typed_exp, typed_exp)
    | FunctionCall(identifier, typed_exp* args)
```

*清单 11-9：为 exp 节点添加类型信息的另一种方式*

无论选择哪种方案，你都需要定义两套独立的 AST 数据结构——一套带类型信息、一套不带——或者在解析器中构建 AST 时把每个 exp 初始化为 null 或占位类型。这里没有唯一正确的答案，取决于你的实现语言和个人品味。本书余下部分不会强求某种特定方案，而是用两个函数来处理 AST 中的类型信息：set_type(e, t) 返回标注了类型 t 的 e 的副本，get_type(e) 返回 e 上的类型标注。

**AST 类型化问题**

如何定义一个既能方便地标注类型信息、又不必借助 hack 或产生大量样板代码的 AST，这一难题有时被称为 AST 类型化问题（AST typing problem）。它之所以是问题，是因为没有人有一个漂亮的解法（例如，我在这里给出的几个方案都有明显的缺点）。AST 类型化问题通常在你用 ML 或 Haskell 之类的函数式语言编写编译器时出现。编译器作者们已经在这些语言中提出了各种各样的解决方案，其中有些相当精巧。如果你想了解几种不同的思路，Edward Yang 的 "The AST Typing Problem" 是一篇很好的综述（http://blog.ezyang.com/2013/05/the-ast-typing-problem/）。

### 对表达式进行类型检查

扩展完 AST 定义之后，我们将重写第 9 章定义的 typecheck_exp，让它返回它所处理的每个 exp AST 节点的新标注副本。

清单 11-10 展示了如何对变量做类型检查。

```text
typecheck_exp(e, symbols):
    match e with
    | Var(v) ->
        v_type = symbols.get(v).type
        if v_type is a function type:
            fail("Function name used as variable")
        return set_type(e, v_type)
```

*清单 11-10：对变量进行类型检查*

首先，我们在符号表中查找该变量的类型。然后，与前几章一样，验证我们没有把函数名当作变量使用。最后，我们用该变量的类型标注这个表达式并返回它。

清单 11-11 展示了如何对常量做类型检查。这很容易，因为不同类型的常量在 AST 中有不同的构造器。

```text
    | Constant(c) ->
        match c with
        | ConstInt(i) -> return set_type(e, Int)
        | ConstLong(l) -> return set_type(e, Long)
```

*清单 11-11：对常量进行类型检查*

对其余表达式，我们需要遍历它们的子表达式并一并进行标注。强制转换表达式的结果就是我们强制转换到的那个类型。清单 11-12 对它们做类型检查。

```text
    | Cast(t, inner) ->
        typed_inner = typecheck_exp(inner, symbols)
        cast_exp = Cast(t, typed_inner)
        return set_type(cast_exp, t)
```

*清单 11-12：对强制转换表达式进行类型检查*

那些求值为 1 或 0 以表示真或假的表达式——包括比较运算以及 ! 之类的逻辑运算——结果类型是 int。算术和按位表达式的结果类型与其操作数相同。这对一元表达式来说很简单，清单 11-13 对它们做类型检查。

```text
    | Unary(op, inner) ->
        typed_inner = typecheck_exp(inner, symbols)
        unary_exp = Unary(op, typed_inner)
        match op with
        | Not -> return set_type(unary_exp, Int)
        | _   -> return set_type(unary_exp, get_type(typed_inner))
```

*清单 11-13：对一元表达式进行类型检查*

二元表达式更复杂，因为两个操作数的类型可能不同。这对逻辑 && 和 || 运算无关紧要，它们可以依次对每个操作数求真值。但对比较运算和算术运算就很重要，它们需要同时使用两个操作数。C 标准定义了一组规则，称为寻常算术转换（usual arithmetic conversions），用于把算术表达式的两个操作数隐式转换为同一个类型，该类型称为公共类型（common type）或公共实类型（common real type）。

给定两个操作数的类型，清单 11-14 展示了如何找到它们的公共实类型。眼下这很简单，因为只有两种可能的类型。

```text
get_common_type(type1, type2):
    if type1 == type2:
        return type1
    else:
        return Long
```

*清单 11-14：求公共实类型*

如果两个类型已经相同，就不需要转换。如果不同，我们把较小的类型（必然是 Int）转换为较大的类型（必然是 Long），因此公共类型是 Long。一旦添加了更多类型，求公共类型就不会这么简单了。

知道了两个操作数都要转换到的公共类型之后，我们就可以用清单 11-15 中的 convert_to 辅助函数把这些类型转换显式化。

```text
convert_to(e, t):
    if get_type(e) == t:
        return e
    cast_exp = Cast(t, e)
    return set_type(cast_exp, t)
```

*清单 11-15：把隐式类型转换显式化*

如果表达式已经有正确的结果类型，convert_to 就原样返回它。否则，它把该表达式包进一个 Cast AST 节点，然后为结果标注正确的类型。

有了这两个辅助函数，我们就可以对二元表达式做类型检查了。清单 11-16 给出了 typecheck_exp 中相关的子句。

```text
    | Binary(op, e1, e2) ->
      ❶ typed_e1 = typecheck_exp(e1, symbols)
        typed_e2 = typecheck_exp(e2, symbols)
        if op is And or Or:
            binary_exp = Binary(op, typed_e1, typed_e2)
            return set_type(binary_exp, Int)
      ❷ t1 = get_type(typed_e1)
        t2 = get_type(typed_e2)
        common_type = get_common_type(t1, t2)
        converted_e1 = convert_to(typed_e1, common_type)
        converted_e2 = convert_to(typed_e2, common_type)
        binary_exp = Binary(op, converted_e1, converted_e2)
      ❸ if op is Add, Subtract, Multiply, Divide, or Remainder:
            return set_type(binary_exp, common_type)
        else:
            return set_type(binary_exp, Int)
```

*清单 11-16：对二元表达式进行类型检查*

我们首先对两个操作数做类型检查 ❶。如果运算符是 And 或 Or，不执行任何类型转换。否则，执行寻常算术转换 ❷：我们先求出公共类型，然后把两个操作数都转换为该类型。（实践中，至少有一个操作数的类型本来就是正确的，所以 convert_to 会原样返回它。）接着，我们用这些转换后的操作数构造新的 Binary AST 节点。最后，为新的 AST 节点标注正确的结果类型 ❸。如果是算术运算，结果的类型与其操作数相同，即我们刚才求出的公共类型。否则，它是一个比较运算，产生真或假的整数表示，因此结果类型是 Int。

在赋值表达式中，我们把被赋的值转换为它所赋给的对象的类型。清单 11-17 给出了这种情况的伪代码。

```text
    | Assignment(left, right) ->
        typed_left = typecheck_exp(left, symbols)
        typed_right = typecheck_exp(right, symbols)
        left_type = get_type(typed_left)
        converted_right = convert_to(typed_right, left_type)
        assign_exp = Assignment(typed_left, converted_right)
        return set_type(assign_exp, left_type)
```

*清单 11-17：对赋值表达式进行类型检查*

记住，赋值表达式的结果是赋值之后左侧的值；不出所料，其结果的类型也是左侧的类型。

条件表达式的处理与二元算术表达式非常相似：求两个分支的公共类型，把两个分支都转换为该公共类型，再用该类型标注结果。我们要对控制条件做类型检查，但不需要把它转换为任何类型。这种情况我就不给伪代码了。

最后同样重要，清单 11-18 展示了如何对函数调用做类型检查。

```text
    | FunctionCall(f, args) ->
        f_type = symbols.get(f).type
        match f_type with
        | FunType(param_types, ret_type) ->
            if length(param_types) != length(args):
                fail("Function called with the wrong number of arguments")
            converted_args = []
          ❶ for (arg, param_type) in zip(args, param_types):
                typed_arg = typecheck_exp(arg, symbols)
                converted_args.append(convert_to(typed_arg, param_type))
            call_exp = FunctionCall(f, converted_args)
          ❷ return set_type(call_exp, ret_type)
        | _ -> fail("Variable used as function name")
```

*清单 11-18：对函数调用进行类型检查*

我们先在符号表中查找函数类型。与前几章一样，需要确认我们要调用的标识符确实是一个函数，并且传入的实参数量正确。然后，我们把函数的实参和形参成对地一起遍历 ❶：对每个实参做类型检查，再把它转换为对应形参的类型。最后，用函数的返回类型标注整个表达式 ❷。

### 对 return 语句进行类型检查

函数返回一个值时，该值会被隐式转换为函数的返回类型。类型检查器需要把这种隐式转换显式化。要对 return 语句做类型检查，我们需查找外层函数的返回类型，并把返回值转换为该类型。这要求我们跟踪当前正在做类型检查的函数的名字，或至少是其返回类型。这部分伪代码我就省略了，因为它非常直接。

### 对声明进行类型检查并更新符号表

接下来，我们要更新对函数和变量声明的类型检查方式，以及我们在符号表中存储的信息。首先，我们需要为符号表中的每个条目记录正确的类型；不能想当然地认为每个变量、形参和返回值都是 int。其次，每当我们检查冲突声明时，都需要验证当前声明与先前的声明具有相同的类型。仅仅检查变量之前是否被声明为函数、或函数之前是否以不同的形参个数声明过是不够的；类型必须完全一致。例如，如果一个变量先被声明为 int，随后又被重新声明为 long，类型检查器就应当抛出错误。第三，对自动变量做类型检查时，我们需要把它的初始化器转换为该变量的类型，就像把赋值表达式的右侧转换为左侧的类型一样。

最后，我们要改变符号表中表示静态初始化器的方式。静态初始化器与常量表达式一样，现在既可以是 int 也可以是 long。清单 11-19 给出了静态初始化器的更新定义。

```text
initial_value = Tentative | Initial(static_init) | NoInitializer
static_init = IntInit(int) | LongInit(int)
```

*清单 11-19：符号表中的静态初始化器*

static_init 的这个定义看起来可能有些冗余，因为它与清单 11-2 中定义的 const AST 节点基本相同，但它们会在后续章节中逐渐分化。与 ConstInt 和 ConstLong AST 节点一样，你应该谨慎选择用实现语言中的哪些整数类型来表示这两种初始化器。尤其重要的是，确保 LongInit 能容纳任何有符号 64 位整数。

把表达式转换为静态初始化器时，你可能需要执行类型转换。例如，假设程序中包含以下声明：

```c
static int i = 100L;
```

常量 100L 在我们的 AST 中会被解析为 ConstLong。由于它被赋给一个 static int，我们需要在编译期把它从 long 强制转换为 int，并在符号表中存为 IntInit(100)。当 int 类型的变量用一个 32 位放不下的 long 常量来初始化时，这种转换尤其棘手，比如这个声明：

```c
static int i = 2147483650L;
```

按照我们前面规定的实现定义行为，我们需要从这个值反复减去 2^32，直到它小到能放进 int。结果是 –2,147,483,646，因此我们在符号表中记录的初值应当是 IntInit(-2147483646)。理想情况下，你可以使用语义本来就正确的有符号整数类型来执行类型转换，这样就不必亲自处理这些常量的二进制表示。

下面几条建议可以帮助你处理静态初始化器：

**让你的常量类型转换代码可复用**

类型检查器不是唯一需要把常量转换为其他类型的地方。第 III 部分你将在 TACKY 中实现常量折叠。常量折叠遍会求值常量表达式，其中包括类型转换。你可以把类型转换代码做成一个单独的模块，以便之后复用于常量折叠。

**不要对静态初始化器调用 typecheck_exp**

把每个静态初始化器直接转换为 static_init，不要先调用 typecheck_exp。这会让后续章节的事情变得更简单，因为那时 typecheck_exp 会以更复杂的方式变换表达式。

**测试类型检查器**

要测试类型检查遍，运行：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 11 --stage validate
```

你的编译器应当对 tests/chapter_11/invalid_types 中的测试用例抛出错误。它应当成功通过 tests/chapter_11/valid 中的每个测试用例。

## TACKY 生成

本章我们将对 TACKY AST 做几处修改。首先，为每个顶层 StaticVariable 添加一个类型，并用新定义的 static_init 构造来表示每个静态变量的初值：

```text
StaticVariable(identifier, bool global, type t, static_init init)
```

我们还会复用清单 11-2 中 AST 的 const 构造来表示常量：

```text
val = Constant(const) | Var(identifier)
```

最后，我们引入两条新指令，用于在类型之间转换值：

```text
SignExtend(val src, val dst)
Truncate(val src, val dst)
```

SignExtend 和 Truncate 指令分别用于从 int 到 long 和从 long 到 int 的转换。清单 11-20 给出了完整更新的 TACKY IR。这个清单直接使用 type、static_init 和 const 而不再定义，因为这三个构造我们已经定义过了。

```text
program = Program(top_level*)
top_level = Function(identifier, bool global, identifier* params, instruction* body)
          | StaticVariable(identifier, bool global, type t, static_init init)
instruction = Return(val)
            | SignExtend(val src, val dst)
            | Truncate(val src, val dst)
            | Unary(unary_operator, val src, val dst)
            | Binary(binary_operator, val src1, val src2, val dst)
            | Copy(val src, val dst)
            | Jump(identifier target)
            | JumpIfZero(val condition, identifier target)
            | JumpIfNotZero(val condition, identifier target)
            | Label(identifier)
            | FunCall(identifier fun_name, val* args, val dst)
val = Constant(const) | Var(identifier)
unary_operator = Complement | Negate | Not
binary_operator = Add | Subtract | Multiply | Divide | Remainder | Equal | NotEqual
                | LessThan | LessOrEqual | GreaterThan | GreaterOrEqual
```

*清单 11-20：为 TACKY 添加长整数支持*

处理 StaticVariable 的改动方式是：在 TACKY 生成期间查符号表以获取类型和初始化器信息。如果静态变量在符号表中是暂定定义，我们就根据它的类型把它初始化为 IntInit(0) 或 LongInit(0)。

处理常量更容易；其逻辑与之前各章基本相同。我们会把 Constant AST 节点直接转换为 TACKY 的 Constant，因为两者使用相同的 const 定义。

回想一下，把逻辑 && 或 || 表达式转换为 TACKY 时，我们会显式地把 1 或 0 赋给保存表达式结果的变量。由于这两种逻辑表达式的类型都是 int，我们用 ConstInt(1) 和 ConstInt(0) 来表示它们的结果。

清单 11-21 展示了如何把强制转换表达式转换为 TACKY。我们将使用上一遍添加的类型信息来确定是从什么类型转换而来。

```text
emit_tacky(e, instructions, symbols):
    match e with
    | --snip--
    | Cast(t, inner) ->
        result = emit_tacky(inner, instructions, symbols)
        if t == get_type(inner):
          ❶ return result
        dst_name = make_temporary()
        symbols.add(dst_name, t, attrs=LocalAttr)
        dst = Var(dst_name)
        if t == Long:
          ❷ instructions.append(SignExtend(result, dst))
        else:
          ❸ instructions.append(Truncate(result, dst))
        return dst
```

*清单 11-21：把强制转换表达式转换为 TACKY*

如果内层表达式已经具有我们要强制转换到的类型，那么这次强制转换没有任何效果；我们生成求值内层表达式的 TACKY，但别的什么都不做 ❶。否则，我们要么生成一条 SignExtend 指令把 int 转换为 long ❷，要么生成一条 Truncate 指令把 long 转换为 int ❸。

### 跟踪临时变量的类型

在清单 11-21 中创建临时变量 dst 时，我们把它以恰当的类型加入了符号表。对我们创建的每个临时变量都要这样做，以便在汇编生成期间能查到它们的类型。汇编生成阶段将以两种方式使用这些类型信息：确定每条汇编指令的操作数大小，以及弄清每个变量需要分配多少栈空间。

我们添加的每个临时变量都保存着某个表达式的结果，因此可以通过检查该表达式的类型标注来确定它的类型。我们再来看一看清单 3-9，它演示了如何把二元算术表达式转换为 TACKY。清单 11-22 演示同样的转换，与清单 3-9 相比的改动以粗体标出。

```text
emit_tacky(e, instructions, symbols):
    match e with
    | --snip--
    | Binary(op, e1, e2) ->
        v1 = emit_tacky(e1, instructions, symbols)
        v2 = emit_tacky(e2, instructions, symbols)
        dst_name = make_temporary()
        symbols.add(dst_name, get_type(e), attrs=LocalAttr)
        dst = Var(dst_name)
        tacky_op = convert_binop(op)
        instructions.append(Binary(tacky_op, v1, v2, dst))
        return dst
    | --snip--
```

*清单 11-22：把二元表达式转换为 TACKY 时跟踪临时变量的类型*

这里的主要改动是把 dst 加入符号表。由于 dst 保存的是表达式 e 的结果，我们查 e 的类型标注来确定 dst 的类型。与所有临时变量一样，dst 是一个局部自动变量，所以我们在符号表中给它 LocalAttr 属性。

我们把它重构成一个辅助函数，如清单 11-23 所示。

```text
make_tacky_variable(var_type, symbols):
    var_name = make_temporary()
    symbols.add(var_name, var_type, attrs=LocalAttr)
    return Var(var_name)
```

*清单 11-23：生成 TACKY 变量的辅助函数*

从现在起，每当我们在 TACKY 中生成新的临时变量，都会使用 make_tacky_variable。

### 生成额外的 Return 指令

第 5 章我曾提到，我们会在每个 TACKY 函数的末尾添加一条额外的 Return 指令，以防原 C 函数并非每条执行路径都能到达 return 语句。这条额外的指令总是可以返回 ConstInt(0)，即使函数的返回类型不是 int 也没关系。从 main 返回时，这是正确的返回类型。从其他任何缺少显式 return 语句的函数返回时，返回值是未定义的。我们仍然需要把控制权交还给调用者，但没有义务返回任何特定的值，所以就算类型不对也无关紧要。

## 汇编生成

本章我们将对汇编 AST 做几处修改。清单 11-24 给出了完整的定义，改动以粗体标出。

```text
program = Program(top_level*)
assembly_type = Longword | Quadword
top_level = Function(identifier name, bool global, instruction* instructions)
          | StaticVariable(identifier name, bool global, int alignment, static_init init)
instruction = Mov(assembly_type, operand src, operand dst)
            | Movsx(operand src, operand dst)
            | Unary(unary_operator, assembly_type, operand)
            | Binary(binary_operator, assembly_type, operand, operand)
            | Cmp(assembly_type, operand, operand)
            | Idiv(assembly_type, operand)
            | Cdq(assembly_type)
            | Jmp(identifier)
            | JmpCC(cond_code, identifier)
            | SetCC(cond_code, operand)
            | Label(identifier)
            | Push(operand)
            | Call(identifier)
            | Ret

unary_operator = Neg | Not
binary_operator = Add | Sub | Mult
operand = Imm(int) | Reg(reg) | Pseudo(identifier) | Stack(int) | Data(identifier)
cond_code = E | NE | G | GE | L | LE
reg = AX | CX | DX | DI | SI | R8 | R9 | R10 | R11 | SP
```

*清单 11-24：支持 quadword 操作数和 8 字节静态变量的汇编 AST*

最大的改动是给大多数指令标注其操作数的类型。这让我们能够在汇编发射期间为每条指令选择正确的后缀。我们还要给 Cdq 加上类型，因为 32 位版的 Cdq 把 EAX 扩展到 EDX，而 64 位版把 RAX 扩展到 RDX。只有三条带操作数但不需要类型的指令：SetCC，它只接受字节大小的操作数；Push，它总是压入 quadword；还有新的 Movsx 指令，我们稍后就会讲到。

我们不复用前面定义的源码级类型，而是定义一个新的 assembly_type 构造。这会让我们在后续章节引入更多 C 类型时更容易处理汇编类型。例如，我们将在第 12 章添加无符号整数，但汇编并不区分有符号和无符号整数。

汇编生成期间，我们将根据操作数的类型确定每条指令的类型。例如，我们会把 TACKY 指令

```text
Binary(Add, Constant(ConstInt(3)), Var("src"), Var("dst"))
```

转换为这些汇编指令：

```text
Mov(Longword, Imm(3), Pseudo("dst"))
Binary(Add, Longword, Pseudo("src"), Pseudo("dst"))
```

由于第一个操作数是 ConstInt，我们知道生成的 mov 和 add 指令应该使用 longword 操作数。我们可以假定第二个操作数和目的操作数与第一个操作数的类型相同，因为我们在 TACKY 生成期间已经插入了恰当的类型转换指令。如果操作数是变量而不是常量，我们就在符号表中查找它的类型。

我们还要根据类型确定如何经栈传递实参。清单 11-25 复现了 convert_function_call（最初在清单 9-31 中定义）的相关部分，这一改动以粗体标出。

```text
convert_function_call(FunCall(fun_name, args, dst)):
    --snip--
    // pass args on stack
    for tacky_arg in reverse(stack_args):
        assembly_arg = convert_val(tacky_arg)
        if assembly_arg is a Reg or Imm operand or has type Quadword:
            emit(Push(assembly_arg))
        else:
            emit(Mov(Longword, assembly_arg, Reg(AX)))
            emit(Push(Reg(AX)))
    --snip--
```

*清单 11-25：convert_function_call 中经栈传递 quadword*

第 9 章我们了解到，如果用 8 字节的 pushq 指令把来自内存的 4 字节操作数压入栈中，可能会出问题。为了绕开这个问题，我们用两条指令把一个 4 字节 Pseudo 压入栈：先把它复制到 EAX，再压入 RAX。8 字节 Pseudo 不需要这种变通处理；我们用一条 Push 指令把它传到栈上，与传递立即值的方式相同。

处理从 int 到 long 的转换，我们要使用符号扩展指令 movsx。目前这条指令不需要类型信息，因为它的源必须是 int，而目的必须是 long。我们把

```text
SignExtend(src, dst)
```

转换为：

```text
Movsx(src, dst)
```

要截断一个值，只需用一条 4 字节 movl 指令把它的最低 4 个字节传送到目的地。我们把

```text
Truncate(src, dst)
```

转换为：

```text
Mov(Longword, src, dst)
```

我们还调整了 StaticVariable 构造：

```text
StaticVariable(identifier name, bool global, int alignment, static_init init)
```

我们保留了 TACKY 的 static_init 构造，这样就知道每个静态变量要初始化 4 字节还是 8 字节。我们还添加了 alignment 字段，因为我们需要在汇编中指定每个静态变量的对齐。

最后，我们从汇编 AST 中删除了 DeallocateStack 和 AllocateStack 指令。这些指令只是加、减 quadword 的占位符，现在用普通的 addq 和 subq 指令就能表示了。由于 DeallocateStack 和 AllocateStack 表示的是对 RSP 的加和减，我们还在汇编 AST 中添加了 RSP 寄存器，以便在普通指令中使用它。在前几章中，我们在函数调用前用这条指令维护栈对齐：

```text
AllocateStack(bytes)
```

现在改用这条指令：

```text
Binary(Sub, Quadword, Imm(bytes), Reg(SP))
```

类似地，不再使用

```text
DeallocateStack(bytes)
```

而是使用

```text
Binary(Add, Quadword, Imm(bytes), Reg(SP))
```

在函数调用后恢复栈指针。

### 在后端符号表中跟踪汇编类型

把 TACKY 程序转换为汇编之后，我们要把符号表转换成一种更适合余下编译遍的形式。这个新符号表存储的是变量的汇编类型，而不是它们的源码类型。它还存储另外一些属性，供伪寄存器替换、指令修补和代码发射遍查找。我会把这个新符号表称为后端符号表（backend symbol table），把现有的那个称为前端符号表（frontend symbol table），或者就直接叫符号表。

后端符号表把每个标识符映射到一个 asm_symtab_entry 构造，其定义见清单 11-26。

```text
asm_symtab_entry = ObjEntry(assembly_type, bool is_static)
                 | FunEntry(bool defined)
```

*清单 11-26：后端符号表中条目的定义*

我们用 ObjEntry 表示变量（以及后续章节中的常量）。我们跟踪每个对象的汇编类型以及它是否具有静态存储期。FunEntry 表示函数。我们不需要跟踪函数的类型——这倒也好，因为 assembly_type 表示不了函数类型——但我们确实要跟踪函数是否在当前翻译单元中定义。如果你在符号表中跟踪每个函数的栈帧大小，就给 FunEntry 构造器加一个额外的 stack_frame_size 字段。我建议与现有的前端符号表一样，把后端符号表做成全局变量或单例。

在 TACKY 到汇编转换遍的最后，你应该遍历前端符号表，把每个条目转换为后端符号表中的条目。这个过程很简单，我就不提供伪代码了。你还需要更新伪寄存器替换、指令修补和代码发射遍中所有引用前端符号表的地方，让它们改用后端符号表。

### 替换 longword 与 quadword 伪寄存器

伪寄存器替换遍需要几处修改。首先，扩展它以替换新 movsx 指令中的伪寄存器。其次，每当我们为伪寄存器分配栈地址时，要在后端符号表中查找该伪寄存器的类型，以确定要分配多少空间。如果是 Quadword，就分配 8 字节；如果是 Longword，则像以前一样分配 4 字节。最后，我们要确保每个 Quadword 伪寄存器的地址在栈上按 8 字节对齐。考虑下面这段汇编片段：

```text
Mov(Longword, Imm(0), Pseudo("foo"))
Mov(Quadword, Imm(1), Pseudo("bar"))
```

假设我们在后端符号表中查到 foo 的类型是 4 字节，就照常把它分配到 -4(%rbp)。接下来我们查 bar，看到它是 8 字节。我们可以把它分配到 -12(%rbp)，也就是在 foo 下方 8 字节处。但这样一来 bar 就没有对齐，因为它的地址不是 8 字节的倍数。（记住，RBP 中的地址总是 16 字节对齐的。）为了保持正确的对齐，我们向下取整到下一个 8 的倍数，把 bar 存到 -16(%rbp)。对齐要求是 System V ABI 的一部分；如果忽视它们，你的代码可能无法与其他翻译单元中的代码正确交互。

### 修补指令

本章我们将对指令修补遍做几处更新。首先，必须为现有重写规则中的所有指令指定操作数大小。这些指令的操作数大小应当始终与被重写的原始指令相同。

接下来，我们要重写 movsx 指令。它不能用内存地址作为目的操作数，也不能用立即值作为源操作数。如果 movsx 的两个操作数都非法，我们就需要同时用 R10 和 R11 来修补它们。例如，我们把

```text
Movsx(Imm(10), Stack(-16))
```

重写为：

```text
Mov(Longword, Imm(10), Reg(R10))
Movsx(Reg(R10), Reg(R11))
Mov(Quadword, Reg(R11), Stack(-16))
```

在这条重写规则中，为每条 mov 指令使用正确的操作数大小很重要。由于 movsx 的源操作数是 4 字节，把该操作数移入寄存器时要指定 longword 操作数大小。由于 movsx 的结果是 8 字节，把结果移到它最终的内存位置时要指定 quadword 操作数大小。

三条二元算术指令（addq、imulq 和 subq）的 quadword 版本无法处理超出 int 范围的立即值，cmpq 和 pushq 也不行。如果这些指令中任何一条的源是超出 int 范围的常量，就必须先把它复制到 R10 中才能使用。

movq 指令可以把这些超大立即值移入寄存器，但不能直接移入内存，所以

```text
Mov(Quadword, Imm(4294967295), Stack(-16))
```

应当重写为：

```text
Mov(Quadword, Imm(4294967295), Reg(R10))
Mov(Quadword, Reg(R10), Stack(-16))
```

**注意**

汇编器只允许 addq、imulq、subq、cmpq 或 pushq 中出现能表示为有符号 32 位整数的立即值。这是因为这些指令都会把立即操作数从 32 位符号扩展到 64 位。如果某个立即值只能作为无符号整数才能表示为 32 位——这蕴含着它的最高位是 1——符号扩展就会改变它的值。更多细节见这个 Stack Overflow 问题：https://stackoverflow.com/questions/64289590/integer-overflow-in-gas。

我们还要修改在每个函数开头分配栈空间的方式。不再为每个函数添加 AllocateStack(bytes) 来在栈上分配空间，而是添加下面这条做同样事情的指令：

```text
Binary(Sub, Quadword, Imm(bytes), Reg(SP))
```

最后再添加一条重写规则来安抚汇编器，尽管它并非严格必需。记住，我们把 Truncate TACKY 指令转换为 4 字节 movl，这意味着我们可能生成把 8 字节立即值传送到 4 字节目的地的 movl 指令：

```text
Mov(Longword, Imm(4294967299), Reg(R10))
```

由于 movl 不能使用 8 字节立即值，汇编器会自动把这些值截断到 32 位。例如，处理指令 movl $4294967299, %r10d 时，它会把立即值 4294967299 转换为 3。GNU 汇编器执行这种转换时会发出警告，不过 LLVM 汇编器不会。为了避免这些警告，我们自己来截断 movl 指令中的 8 字节立即值。也就是说，我们把前一条指令重写为：

```text
Mov(Longword, Imm(3), Reg(R10))
```

抛开汇编器警告不谈，即使不包含这条重写规则，你的汇编程序也仍然能够工作。

## 代码发射

最后一项任务是扩展代码发射阶段。我们要为每条指令添加恰当的后缀，为静态变量发射正确的对齐和初值，并处理新的 Movsx 指令。只要一条指令用到寄存器，我们就要按照该指令的操作数大小发射正确的寄存器名。

带 4 字节操作数的指令有后缀 l，对应 longword；带 8 字节操作数的指令有后缀 q，对应 quadword。只有一个例外：cdq 的 8 字节版本有一个完全不同的助记符 cqo。Movsx 指令的源和目的操作数大小各有一个后缀。例如，movslq 把 longword 符号扩展为 quadword。目前我们发射这条指令时总是带 lq 后缀；等后续章节添加更多汇编类型后，我们会需要更多的后缀。（当汇编器能够推断出两个操作数的大小时，你也会看到这条指令写作 movsx。例如，汇编器会接受指令 movsx %r10d, %r11，因为它能从寄存器名推断出源和目的的大小。）

## 小结

你的编译器现在有类型系统（type system）了！在本章中，你为 AST 标注了类型信息，用符号表在多个编译器阶段跟踪类型信息，并在汇编生成期间添加了对多种操作数大小的支持。长整数并不是最炫目的语言特性，所以你可能觉得自己做了很多工作却没多少可展示的成果。但你在本章创建的基础设施是第 II 部分余下内容的基础。下一章，你将在此基础上实现无符号整数。
