# 第一部分　基础（Part I: The Basics）

# 第 1 章　极简编译器

*Chapter 1: A Minimal Compiler*

在本章中，你将编写一个只能处理最简单 C 程序的极简编译器。你将学习如何阅读一个简单的汇编程序，并实现四个基本的编译遍（pass），在本书其余章节中你都将在此基础上继续构建。我们先来看看这些编译遍。

## 四个编译遍

你在本章编写的编译器将分四个阶段处理源代码：

- 词法分析器（lexer）把源代码拆分成一个词法单元（token）列表。词法单元是程序中最小的语法单位，包括分隔符、算术符号、关键字和标识符。如果把程序比作一本书，词法单元就像一个个单词。

- 解析器（parser）把词法单元列表转换成抽象语法树（abstract syntax tree，AST），它以一种便于我们遍历和分析的形式表示程序。

- 汇编生成（assembly generation）遍把 AST 转换成汇编。在这一阶段，我们仍然用编译器能够理解的数据结构来表示汇编指令，而不是文本。

- 代码发射（code emission）遍把汇编代码写入文件，以便汇编器和链接器把它变成可执行文件。

这是组织编译器的一种典型方式，尽管具体的阶段和中间表示（intermediate representation，IR）各有不同。对本章来说，这样做有点大材小用——本章要处理的程序只用一个遍就能编译——但现在就搭好这个结构，会让后续章节扩展你的编译器更容易。随着实现越来越多的语言特性，你将扩展这些编译阶段，并新增一些阶段。每一章的开头都会给出编译器架构的当前示意图，其中既包括你已经实现的阶段，也包括需要添加的阶段。本章的示意图展示了你即将实现的四个阶段。在后续章节的示意图中，新增的阶段会以粗体显示。

在开始编码之前，我们先快速了解一下如何用系统上已安装的 C 编译器把 C 编译为汇编，以及如何阅读汇编程序。

## 你好，汇编！

最简单的 C 程序如清单 1-1 所示。

```c
int main(void) {
    return 2;
}
```

*清单 1-1：返回数字 2 的简单程序*

这个程序由一个函数 main 组成，其中只包含一条返回语句，返回一个整数（本例中是 2）。把这个程序保存为 return_2.c，然后用 gcc 命令把它翻译成汇编：

```bash
$ gcc -S -O -fno-asynchronous-unwind-tables -fcf-protection=none return_2.c
```

如果你用的是 macOS，这条命令可能会调用 Clang 而不是 GCC，但命令行选项的效果相同。这些选项会生成相当易读的汇编：

- `-S`：不运行汇编器或链接器。这让编译器输出汇编，而不是二进制文件。

- `-O`：优化代码。这会消除一些我们目前不需要关心的指令。

- `-fno-asynchronous-unwind-tables`：不生成展开表（unwind table），它用于调试。我们用不到它。

- `-fcf-protection=none`：禁用控制流保护（control-flow protection）。这是一项安全特性，会增加一些我们不需要关心的额外指令。在你的系统上，控制流保护可能默认已经禁用，这种情况下该选项不会有任何作用。如果你使用的是不支持该选项的旧版 GCC 或 Clang，请跳过它。

结果保存在 return_2.s 中，看起来应该与清单 1-2 类似。

```asm
    .globl main
main:
    movl    $2, %eax
    ret
```

*清单 1-2：清单 1-1 中的程序翻译成汇编*

你的 .s 文件里可能还有其他几行内容，但目前可以放心地忽略它们。清单 1-2 中的四行就是一个完整的汇编程序。汇编程序有好几种语句。第一行 .globl main 是一条汇编器指令（assembler directive），即给汇编器提供指示的语句。汇编器指令总是以句点开头。这里的 main 是一个符号（symbol），也就是一个内存地址的名字。符号既出现在汇编指令中，也出现在汇编器指令中；例如，指令 jmp main 会跳转到 main 符号所指向的地址。

.globl main 指令告诉汇编器 main 是一个全局符号。默认情况下，符号只能在定义它的那个汇编文件（因而也就是同一个目标文件，object file）中使用。但因为 main 是全局的，其他目标文件也可以引用它。汇编器把这一事实记录在目标文件中一个叫做符号表（symbol table）的节（section）里，链接器在把各个目标文件链接到一起时会用到符号表。符号表包含目标文件或可执行文件中所有符号的信息。

在第二行，我们把 main 用作其后代码的标签（label）。标签由一个字符串或数字后跟一个冒号构成。标签标记了符号所指向的位置。这个标签具体把 main 定义为下一行 movl 指令的地址。汇编器并不知道这条指令最终的内存地址，但它知道这条指令位于目标文件的哪个节中，以及它相对该节起始处的偏移量。（目标文件由若干节组成，分别存放各种类型的数据；机器指令、全局变量、调试信息等各有单独的节。运行时，不同的节会被加载到程序地址空间的不同部分。）main 的地址将位于文本节（text section）中，后者存放机器指令。由于 main 指向这个汇编文件中的第一条机器指令，它在文本节内的偏移量为 0。汇编器把这个偏移量记录在符号表里。

下一行的 movl 指令是一条机器指令（machine instruction），它会出现在最终的可执行文件中。清单 1-2 中的 movl 指令把值 2 移入一个寄存器（register）——一种非常小而快的存储槽位，拥有自己的名字，就位于 CPU 之上。这里，我们把 2 移入名为 EAX 的寄存器，它能容纳 32 位。按照我们平台的调用约定（calling convention），返回值通过 EAX（或者 RAX，即 64 位的等价寄存器，取决于返回值的类型）传回调用者。由于调用者也知道这一约定，函数返回后它就可以从 EAX 中取回返回值。movl 中的 l 后缀表示这条指令的操作数是长字（longword），即 32 位整数（在 x64 汇编中，与大多数现代 C 实现不同，long 意味着 32 位）。movq 指令操作的是四字（quadword），即 64 位整数。当我想在不指定大小的情况下统称这类指令时，就只写 mov。

最后是另一条机器指令 ret，它把控制权交还给调用者。你在这里看到的可能是 retq 而不是 ret，因为这条指令隐式地操作 64 位返回地址。我略过了很多细节，包括调用约定究竟是什么、由谁制定，以及 ret 如何知道调用者在哪里。等到第 9 章添加函数调用时，我会重新讨论这些问题。

> **注意**
>
> 本书中所有汇编清单均使用 AT&T 语法。在其他地方，你可能会看到以 Intel 语法书写的 x64 汇编。它们是同一种语言的两种不同记法；最大的区别在于二者放置指令操作数的顺序不同。

看到这里，很自然要问：调用者到底是谁？毕竟 main 是这个程序里唯一的函数。你可能还会奇怪为什么需要 .globl main 指令，因为看起来并不存在其他可能引用 main 的目标文件。答案是：链接器会附加一小段名为 crt0 的包装代码（wrapper code），负责在 main 运行之前做设置、在其退出之后做收尾。（crt 代表 C Runtime，即 C 运行时。）这段包装代码做以下事情：

- 调用 main 函数。这正是 main 需要全局可见的原因；如果不是全局的，crt0 就无法调用它。

- 从 main 取回返回值。

- 调用 exit 系统调用，并把 main 的返回值传给它。随后，exit 负责完成操作系统内部终止进程所需的全部工作，并把该返回值转换成退出码（exit code）。

总而言之，你不必担心进程的启动与收尾，可以把 main 当成普通函数来对待。

链接器还会通过一个叫做符号解析（symbol resolution）的过程，把符号表中的每个条目与一个内存地址关联起来。然后它执行重定位（relocation），把所有使用符号的地方更新为使用相应的地址。（实际上，链接过程比这复杂得多！想了解更多，参见第 21 页的「延伸资源」。）

要验证 return_2.s 中的汇编能够工作，可以对它进行汇编和链接、运行它，然后用 `$?` 这个 shell 操作符检查退出码：

```bash
$ gcc return_2.s -o return_2
$ ./return_2
$ echo $?
2
```

注意，你可以像传普通源文件一样把汇编文件传给 gcc 命令。它会假定任何扩展名为 .s 的输入文件包含的都是汇编，因此会直接汇编并链接这些文件，而不会先尝试编译它们。

## 编译器驱动

正如你在引言中学到的，编译器本身单独存在并没有多大用处。你还需要一个编译器驱动（compiler driver）来调用预处理器、编译器、汇编器和链接器。因此，在着手编写编译器之前，你要先编写编译器驱动。它应通过三个步骤把源文件转换成可执行文件：

1. 运行下面的命令对源文件进行预处理：

```bash
gcc -E -P INPUT_FILE -o PREPROCESSED_FILE
```

这条命令对 INPUT_FILE 进行预处理，然后把结果写入 PREPROCESSED_FILE。选项 -E 告诉 GCC 只运行预处理器，不运行编译过程的后续步骤。默认情况下，预处理器会输出行标记（linemarker），为预处理输出的每一部分标明其原始源文件以及在该源文件中的起始行号。（由于 #include 指令，一个预处理后的文件可能包含来自多个源文件的代码。）选项 -P 告诉预处理器不要输出行标记；我们的词法分析器和解析器将无法处理它们。按照惯例，PREPROCESSED_FILE 应该使用 .i 扩展名。

2. 编译预处理后的源文件，输出一个扩展名为 .s 的汇编文件。这一步你只能先写个占位实现，因为你的编译器还没写。用完之后删除预处理文件。

3. 汇编并链接该汇编文件以生成可执行文件，使用下面的命令：

```bash
gcc ASSEMBLY_FILE -o OUTPUT_FILE
```

用完之后删除汇编文件。

你的编译器驱动必须具备特定的命令行接口，以便本书的测试脚本 test_compiler 能够运行它。它必须是一个命令行程序，接受一个 C 源文件的路径作为其唯一参数。如果该命令执行成功，它必须在输入文件所在的同一目录中生成一个同名的可执行文件（去掉文件扩展名）。换句话说，如果你运行 ./YOUR_COMPILER /path/to/program.c，它就应当在 /path/to/program 生成一个可执行文件，并以退出码 0 终止。如果你的编译器编译失败，编译器驱动应返回非零退出码，并且不应写入任何汇编文件或可执行文件；test_compiler 正是靠这一点来验证你的编译器能在无效程序中捕获错误。最后，你的编译器驱动还应支持以下选项，test_compiler 会用它们来测试中间阶段：

- `--lex`：指示它运行词法分析器，但在解析之前停止

- `--parse`：指示它运行词法分析器和解析器，但在汇编生成之前停止

- `--codegen`：指示它执行词法分析、解析和汇编生成，但在代码发射之前停止

这些选项都不应产生任何输出文件，并且只要没有遇到错误，都应以退出码 0 终止。你可能还想添加一个 -S 选项，指示编译器输出汇编文件，但不进行汇编或链接。运行第 III 部分的测试时需要这个选项；第 I 和第 II 部分并不要求它，但它对调试很有用。

写好编译器驱动之后，你就可以着手编写真正的编译器了。你需要实现本章开头列出的四个编译遍：生成词法单元列表的词法分析器；把这些词法单元变成抽象语法树的解析器；把抽象语法树转换为汇编的汇编生成遍；以及把汇编写入文件的代码发射遍。先从词法分析器开始。

## 词法分析器

词法分析器应读入源文件并生成一个词法单元列表。在动手编写词法分析器之前，你需要知道可能遇到哪些词法单元。下面是清单 1-1 中的全部词法单元：

- `int`：一个关键字（keyword）

- `main`：一个标识符（identifier），值为 "main"

- `(`：一个左圆括号

- `void`：一个关键字

- `)`：一个右圆括号

- `{`：一个左花括号

- `return`：一个关键字

- `2`：一个常量（constant），值为 "2"

- `;`：一个分号

- `}`：一个右花括号

我在这里用了两个词法分析方面的术语。标识符是一个 ASCII 字母或下划线，后跟字母、下划线和数字的任意组合。标识符区分大小写。整数常量（integer constant）由一个或多个数字组成。（我们将在第 II 部分添加字符常量和浮点常量。本书不会实现十六进制或八进制整数常量。）

注意，上面这份词法单元列表中，标识符和常量带有值，而其他类型的词法单元没有。可能的标识符有很多（例如 foo、variable1 和 my_cool_function），因此词法分析器生成的每个标识符词法单元都必须保留其具体的名字。类似地，每个常量词法单元都需要保存一个整数值。相比之下，return 关键字只有一种可能，因此 return 关键字词法单元不需要存储任何额外信息。尽管目前 main 是唯一会用到的标识符，你也应该把词法分析器构建成日后能支持任意标识符的样子。另外注意，不存在空白（whitespace）词法单元。如果我们要编译的是像 Python 那样空白有意义的语言，就需要引入空白词法单元。

每种词法单元都可以用一个正则表达式（regular expression，regex）来识别。表 1-1 以 Perl 兼容正则表达式（Perl Compatible Regular Expressions，PCRE）语法给出了每个词法单元对应的正则表达式。

*表 1-1：词法单元及其正则表达式*

| 词法单元 | 正则表达式 |
| --- | --- |
| 标识符 | `[a-zA-Z_]\w*\b` |
| 常量 | `[0-9]+\b` |
| int 关键字 | `int\b` |
| void 关键字 | `void\b` |
| return 关键字 | `return\b` |
| 左圆括号 | `\(` |
| 右圆括号 | `\)` |
| 左花括号 | `{` |
| 右花括号 | `}` |
| 分号 | `;` |

对一个程序做词法单元化处理的过程大致如清单 1-3 所示。

```text
while input isn't empty:
    if input starts with whitespace:
        trim whitespace from start of input
    else:
        find longest match at start of input for any regex in Table 1-1
        if no match is found, raise an error
        convert matching substring into a token
        remove matching substring from start of input
```

*清单 1-3：把字符串转换成词法单元序列*

注意，标识符、关键字和常量必须终止于词边界（word boundary），由 \b 表示。例如，123;bar 的前三个数字匹配常量的正则表达式，你应该把它们转换成常量 123。这是因为 ; 不属于 \w 字符类，所以 3 和 ; 之间的边界是一个词边界。然而，123bar 的前三个数字并不匹配常量的正则表达式，因为这些数字后面紧跟的是 \w 字符类中的更多字符，而不是词边界。如果你的词法分析器遇到 123bar 这样的字符串，它应当报错，因为这个字符串的开头无法匹配任何词法单元的正则表达式。

现在你可以编写自己的词法分析器了。下面是几点值得牢记的提示：

**像对待其他标识符一样对待关键字。**

标识符的正则表达式同样能匹配关键字。不要试图一步到位地同时找出下一个词法单元的结尾并判断它是不是关键字。先找到词法单元的结尾；然后，如果它看起来像标识符，再检查它是否与某个关键字匹配。

**不要按空白切分。**

一上来就按空白切分字符串不是个好主意，因为空白并不是词法单元之间唯一的边界。例如，main(void) 包含四个词法单元，其中却没有任何空白。

**你只需要支持 ASCII 字符。**

本书的测试程序只包含 ASCII 字符。C 标准提供了一种叫做通用字符名（universal character names）的机制，用于在标识符中使用非 ASCII 字符，但我们不会实现它。许多 C 实现允许直接使用 Unicode 字符，不过你同样不需要支持。

写好词法分析器之后，下一步就是测试它。

**测试词法分析器**

你将用 tests/chapter_1 中的所有程序来测试词法分析器。tests/chapter_1/invalid_lex 中的程序包含无效词法单元，因此应当使词法分析器失败并给出恰当的错误消息。tests/chapter_1/invalid_parse 和 tests/chapter_1/valid 中的程序只包含有效词法单元，词法分析器应当能顺利处理它们。使用下面的命令来测试你的词法分析器会在 tests/chapter_1/invalid_lex 中的程序上失败，而在其他所有程序上成功：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 1 --stage lex
```

这条命令只测试词法分析器成功还是失败，并不会检查词法分析器到底生成了哪些词法单元。可以考虑自己编写一些测试，验证它对有效程序生成正确的词法单元列表，对无效程序发出恰当的错误消息。

## 解析器

现在你已经有了一个词法单元列表，接下来要弄清楚这些词法单元是如何分组为语言构造（language construct）的。在包括 C 在内的大多数编程语言中，这种分组是层次化的：程序中的每个语言构造都由若干更简单的构造组成。单个词法单元代表最基础的构造，比如变量、常量和算术运算符。树这种数据结构是表达这种层次关系的天然方式。正如本章开头提到的，解析器将接受词法分析器生成的词法单元列表，并生成一种称为抽象语法树的树状表示。解析器建好 AST 之后，汇编生成阶段将遍历它，弄清楚应该生成哪些汇编代码。

编写解析器有两种途径：手写，或者使用 Bison、ANTLR 之类的解析器生成器（parser generator）自动生成解析代码。使用解析器生成器更省事，但本书采用手写解析器。原因有几点。最重要的一点是，手写解析器能让你扎实地理解解析器的工作原理；使用解析器生成器时，很容易对其生成的代码一知半解。此外，许多解析器生成器学习曲线陡峭，与其先花时间精通某个特定工具，不如先学会递归下降解析（recursive descent parsing）这样的通用技术。

与解析器生成器生成的解析器相比，手写解析器还有一些实用优势：它们可以更快、更易于调试，更加灵活，并且对错误处理的支持也更好。事实上，GCC 和 Clang 用的都是手写解析器，这说明手写解析器绝非纯粹的学术练习。

话虽如此，如果你更愿意使用解析器生成器，那也完全没问题。这完全取决于你希望从本书中收获什么。不过要注意，我不会讨论如何使用那些工具，这部分得靠你自己摸索。如果你走这条路，请务必调研一下你选定的实现语言中有哪些可用的解析库。

无论选择哪种方案，你都需要设计解析器应生成的抽象语法树。我们先来看一个 AST 的示例。

### 抽象语法树示例

考虑清单 1-4 中的 if 语句。

```c
if (a < b) {
    return 2 + 2;
}
```

*清单 1-4：一条简单的 if 语句*

- 条件，即 a < b

- 语句体，即 return 2 + 2;

这两个构造都还可以进一步分解。例如，条件是一个二元运算（binary operation），有三个子节点：

- 左操作数，变量 a

- 运算符，<

- 右操作数，变量 b

### AST 定义

本书使用一种专为描述 AST 而设计的语言来给出 AST 描述，即 Zephyr 抽象语法描述语言（Zephyr Abstract Syntax Description Language，ASDL）。我在这里采用 ASDL，是把它当作一种便捷的、与编程语言无关的记法。你不会在编译器里直接使用 ASDL，而是要在你选定的实现语言中定义等价的数据结构。接下来的几段是对 ASDL 非常简略的介绍。你可以在第 21 页的「延伸资源」中找到描述这门完整语言的原始论文的链接。

清单 1-5 给出了你将在本章实现的 C 语言极小子集（形如清单 1-1 的程序）的 ASDL 定义。

```text
program = Program(function_definition)
function_definition = Function(identifier name, statement body)
statement = Return(exp)
exp = Constant(int)
```

*清单 1-5：本章的抽象语法树定义*

清单 1-5 中的每一行描述了如何构建一种类型的 AST 节点。注意，图 1-2 中的每个 AST 节点在 ASDL 中都有与之对应的定义。这棵 AST 的根是 program 节点。目前，这个节点恰好只能有一个类型为 function_definition 的子节点。函数定义有两个子节点：类型为 identifier 的函数名，以及类型为 statement 的函数体。就目前而言，一个函数由单条语句构成，没有参数。之后，你会添加对函数参数以及更复杂函数体的支持。还要注意，定义中的 name 和 body 是字段名（field name）——它们是不会改变 AST 结构的、面向人类的标签。字段名在 ASDL 中是可选的。当字段名存在时，它紧跟在字段类型之后，就像 identifier name 中那样。

在 ASDL 中，identifier 是表示函数名和变量名的内建类型；它们本质上就是字符串，但我们希望把它们与 "Hello, World!" 之类的字符串字面量区分开，因为二者出现在 AST 的不同位置。由于 identifier 是内建类型，它没有子节点。function_definition 节点的另一个子节点是 statement。目前唯一的语句种类是 return 语句。这种语句有一个子节点：它的返回值，类型为 exp——expression（表达式）的缩写。目前唯一的 exp 是整数常量；int 是 ASDL 的另一个内建类型，到这里 AST 就定义完了。

当然，return 语句并非 C 中唯一的语句，常量也不是唯一的表达式。在后续章节中，我们会添加新的构造器（constructor）来表示其他种类的语句和表达式。例如，我们会为 statement 添加一个 If 构造器来表示 if 语句：

```text
statement = Return(exp) | If(exp condition, statement then, statement? else)
```

statement? 类型表示可选的语句，因为 if 语句并不总是带有 else 子句。| 符号用于分隔各构造器。在这里，它告诉我们：一条语句既可以是由 Return 构造器定义的 return 语句，也可以是由 If 构造器定义的 if 语句。

现在轮到你用编写编译器所用的任何语言来实现清单 1-5 中的 AST 定义了。表示 AST 的标准方式因编程语言而异。如果你用 F#、ML 或 Haskell 之类的函数式语言实现编译器，可以用代数数据类型（algebraic data type）来定义 AST。Rust 的枚举基本上就是代数数据类型，因此同样可以用来表示 AST。如果你使用 Java 之类的面向对象语言，可以为每种节点类型定义一个抽象类，然后为每个构造器定义扩展或继承这些抽象类的类。例如，你可以定义一个 Exp 抽象类，以及扩展它的 Constant 类和 BinaryExp 类。

如果你仍不清楚如何编写 AST 定义，请参阅第 21 页的「延伸资源」。

### 形式文法

AST 包含了编译器后续阶段所需的全部信息。但是，它并不会告诉你每个语言构造究竟由哪些词法单元组成。例如，清单 1-5 的 AST 描述中没有任何地方说明 return 语句必须以分号结尾，也没有说明函数体必须用花括号括起来。（这正是「抽象」语法树名称的由来——与之相对，具体语法树（concrete syntax tree）会包含原始输入中的每一个词法单元。）一旦得到了 AST，这些具体细节就无关紧要了，把它们省略掉反而方便。然而，在解析词法单元序列来构建 AST 时，这些细节至关重要，因为它们指明了每个语言构造的起止位置。

因此，除了 AST 描述之外，你还需要一组规则，定义如何从词法单元列表构建语言构造。这套规则称为形式文法（formal grammar），它与 AST 描述紧密对应。清单 1-6 定义了形如清单 1-1 的 C 程序的形式文法。

```text
<program> ::= <function>
<function> ::= "int" <identifier> "(" "void" ")" "{" <statement> "}"
<statement> ::= "return" <exp> ";"
<exp> ::= <int>
<identifier> ::= ? An identifier token ?
<int> ::= ? A constant token ?
```

*清单 1-6：本章的形式文法*

清单 1-6 中的文法采用扩展巴科斯-诺尔范式（extended Backus-Naur form，EBNF）记法。这个文法的每一行都是一条产生式规则（production rule），定义了一个语言构造如何由其他语言构造和词法单元组成的序列构成。出现在产生式规则左侧的每个符号（比如 <function>）都是非终结符（non-terminal symbol）。而单个的词法单元，比如关键字、标识符和标点符号，则是终结符（terminal symbol）。所有非终结符都包在尖括号里，具体的词法单元（比如 ;）则包在引号里。<identifier> 和 <int> 符号分别表示单个的标识符词法单元和常量词法单元。由于这些词法单元不像其他终结符那样是固定的字符串，我们用一种特殊序列来描述它们：用问号包起来的、对该符号的英文文字描述。

清单 1-6 看起来与清单 1-5 的 AST 定义非常相似。事实上，两者结构相同：清单 1-5 中的每个 AST 节点都对应清单 1-6 中的一个非终结符。唯一的区别在于，清单 1-6 精确规定了在树的每个节点处会出现哪些词法单元，这有助于我们判断何时需要在 AST 中开始处理下一层的新节点，以及何时已处理完一个节点、可以向上回到它上一层的父节点。

正如后续章节会为某些 AST 节点引入多个构造器一样，它们也会为对应的符号引入多条产生式规则。例如，下面是你为支持 if 语句而给 <statement> 添加产生式规则的方式：

```text
<statement> ::= "return" <exp> ";" | "if" "(" <exp> ")" <statement> ["else" <statement>]
```

注意，EBNF 中的方括号表示可选内容，就如同 ASDL 中的问号一样。

编写解析器时你会参考这个形式文法，但不会在编译器中的任何地方显式定义这些文法规则。

### 递归下降解析

有了 AST 定义和形式文法之后，我们来谈谈如何真正动手编写解析器。我们将使用一种直截了当的技术，称为递归下降解析：为每个非终结符各用一个不同的函数来解析，并返回相应的 AST 节点。例如，当解析器预期遇到清单 1-6 中定义的 <statement> 符号时，它会调用一个函数来解析该符号并返回清单 1-5 中的 statement AST 节点。主解析函数解析 <program> 符号，它对应整个程序。每调用一个函数去处理一个新符号，解析器就下降到树中更低的一层——这就是「递归下降」中「下降」的由来。（之所以叫「递归」下降，是因为文法规则往往是递归的，这时处理它们的函数也是递归的。例如，表达式的操作数可能又是另一个表达式；我们将在下一章看到这样的例子。）

让我们走查其中一个解析函数。清单 1-7 的伪代码演示了如何解析 <statement> 符号。

```text
parse_statement(tokens):
    expect("return", tokens)
    return_val = parse_exp(tokens)
    expect(";", tokens)
    return Return(return_val)

expect(expected, tokens):
    actual = take_token(tokens)
    if actual != expected:
        fail("Syntax error")
```

*清单 1-7：解析一条语句*

当我们预期剩余词法单元列表以 <statement> 开头时，就调用 parse_statement 函数。根据清单 1-6，一个 <statement> 由三个符号组成：return 关键字、一个 <exp> 符号和一个 ; 词法单元。首先，我们调用辅助函数 expect，核实第一个词法单元确实是 return 关键字。如果是，expect 就把它丢弃，好让我们继续处理下一个词法单元；如果不是，我们就报告程序中存在语法错误。接下来，需要把 <exp> 符号变成 exp AST 节点。由于这是一个不同的非终结符，它应当由另一个函数 parse_exp 来处理——我在这里没有给出该函数的定义。我们调用 parse_exp 得到表示返回值的 AST 节点；然后再次调用 expect，核实这个表达式后面跟着的是最后一个词法单元——分号。最后，我们构造 Return AST 节点并将其返回。

注意，parse_statement 会把组成这条语句的所有词法单元从 tokens 列表中移除。parse_statement 返回后，其调用者继续处理 tokens 中剩余的词法单元。如果解析完整个程序后还留有词法单元，那就是语法错误。

目前，形式文法中的每个符号都只有一条产生式规则。在后续章节中，当某些符号拥有多条产生式规则时，解析器就需要判断该使用哪一条。它的做法是查看列表开头的几个词法单元而不移除它们。这种向前看若干个词法单元来决定使用哪条产生式规则的递归下降解析器称为预测型解析器（predictive parser）。预测解析之外的选择是带回溯（backtracking）的递归下降：依次尝试每条产生式规则，直到找到可行的那条为止。

现在你可以编写自己的递归下降解析器了。记住，你需要为清单 1-6 中的每个非终结符各编写一个解析函数。下面是几条让这项工作更轻松的提示：

**编写美化打印器（pretty-printer）。**

美化打印器是一种以人类易读的方式打印 AST 的函数。它会让调试解析器轻松得多。清单 1-1 中的程序经美化打印后的 AST 大概是这个样子：

```text
Program(
    Function(
        name="main",
        body=Return(
          Constant(2)
        )
    )
)
```

**给出信息量大的错误消息。**

这同样有助于调试解析器，而且能让你的编译器更加用户友好。像 Expected ";" but found "return" 这样的错误消息，远比一句 Fail 有用。

**测试解析器**

你的解析器应当在 tests/chapter_1/invalid_parse 中的程序上失败，在 tests/chapter_1/valid 中的程序上成功。要测试解析器，请运行：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 1 --stage parse
```

这条命令只测试解析器成功还是失败，因此你可能需要自己编写一些测试，确认它对有效程序生成正确的 AST，对无效程序给出恰当的错误。

## 汇编生成

汇编生成阶段应把 AST 转换为 x64 汇编：大致按照程序执行的顺序遍历 AST，为每个节点生成适当的汇编指令。首先，定义一个适当的数据结构来表示汇编程序，就像你编写解析器时定义数据结构来表示 AST 一样。之所以要再引入一个数据结构、而不是立刻把汇编写入文件，是为了在生成汇编代码之后还能对它进行修改。本章不需要重写任何汇编，但后续章节会需要。

我将再次使用 ASDL 来描述我们用来表示汇编的结构。定义见清单 1-8。

```text
program = Program(function_definition)
function_definition = Function(identifier name, instruction* instructions)
instruction = Mov(operand src, operand dst) | Ret
operand = Imm(int) | Register
```

*清单 1-8：汇编程序的 ASDL 定义*

它看起来和上一节的 AST 定义非常相像！事实上，这确实是一个 AST 定义，只不过是针对汇编程序而非 C 程序的。它的每个节点对应汇编中的一个构造（比如一条指令），而不是 C 中的一个构造（比如一条语句）。我会把清单 1-8 定义的数据结构称为汇编 AST，以区别于清单 1-5 定义的 AST。

我们来走查一下清单 1-8。program 类型表示整个汇编程序，由单个 function_definition 组成。函数定义有两个字段：函数名和指令列表。instruction* 中的 * 表示这个字段是一个列表。instruction 类型有两个构造器，分别表示我们的汇编程序中可以出现的两条指令：mov 和 ret。mov 指令有两个操作数：它把第一个操作数（源）复制到第二个操作数（目标）。ret 指令则没有任何操作数。operand 类型定义了指令可能的两种操作数：寄存器和立即数（immediate value，即常量）。目前你还不需要指明操作的是哪个寄存器，因为你生成的代码只会用到 EAX。后续章节中你才会引用其他寄存器。这个阶段的结构与解析器类似：你需要为每种类型的 AST 节点编写一个函数，该函数再调用其他函数来处理该节点的子节点。表 1-2 描述了应为每个 AST 节点生成的汇编。

*表 1-2：把 AST 节点转换为汇编*

| AST 节点 | 汇编构造 |
| --- | --- |
| `Program(function_definition)` | `Program(function_definition)` |
| `Function(name, body)` | `Function(name, instructions)` |
| `Return(exp)` | `Mov(exp, Register)`<br>`Ret` |
| `Constant(int)` | `Imm(int)` |

这个转换相当直接，但有两点需要注意。其一，一条语句会产生多条汇编指令。其二，这个转换只有在表达式可以表示为单个汇编操作数时才成立。目前确实如此，因为唯一的表达式就是整数常量；但等到下一章加入一元运算符后就不成立了。到那时，你的编译器将需要生成多条指令来计算一个表达式，然后再确定该表达式存放在哪里，以便把它复制到 EAX 中。

**测试汇编生成阶段**

要测试汇编生成阶段，请运行：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 1 --stage codegen
```

这条命令测试汇编生成阶段能否在不崩溃的前提下处理每个有效程序。它还会测试你的编译器是否拒绝每个无效程序——尽管你在测试词法分析器和解析器时已经确认过这一点。

## 代码发射

现在你的编译器已经能够生成汇编指令，最后一步就是把这些指令写入文件。这个文件看起来会和清单 1-2 中的汇编程序非常相似，但有几个细节因平台而异。首先，如果你用的是 macOS，就应始终在函数名前加上一个下划线。例如，main 函数的标签要生成为 _main。（在 Linux 上不要加这个下划线。）

其次，如果你用的是 Linux，则需要在文件末尾加上这一行：

```asm
    .section .note.GNU-stack,"",@progbits
```

这一行会启用一项重要的安全加固措施：它表明你的代码不需要可执行栈（executable stack）。如果一个内存区域允许处理器执行存放在其中的机器指令，这个区域就是可执行的。栈（stack）是一个存放局部变量和临时值的内存区域，下一章你会学到更多相关内容。在正常情况下，栈并不存放机器指令。让栈不可执行是对某些安全攻击的基本防御手段，但这项防御并非对所有程序都能开启，因为少数使用了某些非标准语言扩展的程序确实需要可执行栈。在汇编文件中包含这一行，就表明该文件不需要可执行栈，从而使这项安全措施得以开启。本书中生成的代码都不需要可执行栈，所以我们将始终输出这一行。（关于可执行栈的更多信息，参见第 21 页的「延伸资源」。）

代码发射阶段应遍历汇编 AST，打印遇到的每个构造，这与汇编生成阶段遍历清单 1-5 中的 AST 很类似。由于汇编 AST 与最终的汇编程序对应得极为紧密，即便你在后续章节为编译器添加更多功能，代码发射阶段也会非常简单。

表 1-3、表 1-4 和表 1-5 说明了如何打印每个汇编构造。

*表 1-3：格式化顶层汇编构造*

| 汇编顶层构造 | 输出 |
| --- | --- |
| `Program(function_definition)` | 打印函数定义。在 Linux 上，还需在文件末尾添加：`    .section .note.GNU-stack,"",@progbits` |
| `Function(name, instructions)` | `   .globl <name>`<br>`<name>:`<br>`    <instructions>` |

*表 1-4：格式化汇编指令*

| 汇编指令 | 输出 |
| --- | --- |
| `Mov(src, dst)` | `movl <src>, <dst>` |
| `Ret` | `ret` |

*表 1-5：格式化汇编操作数*

| 汇编操作数 | 输出 |
| --- | --- |
| `Register` | `%eax` |
| `Imm(int)` | `$<int>` |

务必在指令之间加上换行。你还应当输出可读性强、格式规整的汇编代码，因为在调试编译器期间，你会花大量时间阅读这些汇编。你可以像清单 1-2 那样，给除标签之外的每一行都加缩进，让汇编更易读。也可以考虑在汇编程序中加入注释。汇编中的 # 符号会把该行余下的内容注释掉，类似于 C 中的 //。

实现代码发射阶段之后，你就能把像清单 1-1 这样的简单程序编译成可以运行的可执行文件了。

**测试整个编译器**

要测试整个编译器，请运行：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 1
```

这条命令会编译 tests/chapter_1/valid 中的每个程序，运行生成的可执行文件，并验证它产生正确的退出码。它还会像之前各阶段那样，验证你的编译器拒绝每个无效的测试程序。

## 总结

在本章中，你编写了一个能把完整的 C 程序转换成可在你的计算机上运行的可执行文件的编译器。你学会了如何解读 x64 汇编编写的程序、扩展巴科斯-诺尔范式表达的形式文法，以及用 ASDL 编写的 AST 定义。你在本章学到的技能与概念——以及你实现的四个编译阶段——是你在本书其余部分所做一切的基础。

在下一章中，你将为编译器添加对一元运算符的支持。在此过程中，你将学习汇编程序如何管理栈，并实现一种新的中间表示来描述被编译的程序，使它们更易于分析、转换和优化。

## 延伸资源

想进一步了解本章引入的一些概念，请查阅以下资源。

**链接器（Linkers）**

David Drysdale 的 "Beginner's Guide to Linkers" 是不错的入门材料（https://www.lurklurk.org/linkers/linkers.html）。

Ian Lance Taylor 的链接器系列文章共有 20 篇，讲得深入得多。第一篇位于 https://www.airs.com/blog/archives/38，目录见 https://lwn.net/Articles/276782/。

Eli Bendersky 的博文 "Position Independent Code (PIC) in Shared Libraries" 概述了编译器、链接器和汇编器如何协作生成位置无关代码，聚焦于 32 位机器（https://eli.thegreenplace.net/2011/11/03/position-independent-code-pic-in-shared-libraries）。

同样出自 Eli Bendersky 的 "Position Independent Code (PIC) in Shared Libraries on x64" 在前文基础上聚焦于 64 位系统（https://eli.thegreenplace.net/2011/11/11/position-independent-code-pic-in-shared-libraries-on-x64）。

**AST 定义**

Joel Jones 的 "Abstract Syntax Tree Implementation Idioms" 对如何在各种编程语言中实现 AST 做了很好的概述（https://hillside.net/plop/plop2003/Papers/Jones-ImplementingASTs.pdf）。

Daniel Wang、Andrew Appel、Jeff Korn 和 Christopher Serra 的 "The Zephyr Abstract Syntax Description Language" 是 ASDL 的原始论文，其中包含用几种不同语言编写 AST 定义的示例（https://www.cs.princeton.edu/~appel/papers/asdl97.pdf）。

**可执行栈（Executable stacks）**

Ian Lance Taylor 的博文 "Executable Stack" 讨论了哪些程序需要可执行栈，并描述 Linux 系统如何判断一个程序的栈是否应当可执行（https://www.airs.com/blog/archives/518）。
