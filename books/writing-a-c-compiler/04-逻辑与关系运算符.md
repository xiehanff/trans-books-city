# 第 4 章　逻辑与关系运算符

*Chapter 4: Logical and Relational Operators*

既然你已经知道如何编译二元运算符，接下来就要一口气添加一大堆（外加一个一元运算符）。本章将添加三个逻辑运算符：NOT（!）、AND（&&）和 OR（||），还将添加关系运算符：<、>、== 等等。这些运算符各自测试某个条件，条件为真时结果为 1，为假时结果为 0。

&& 和 || 与我们目前见过的二元运算符不同，因为它们会短路（short-circuit）：如果在求值第一个操作数之后就能知道结果，就不会再求值第二个操作数。为了支持短路求值（short-circuit evaluation）逻辑，我们要给 TACKY 添加能让我们跳过代码块的新指令。我们还将在汇编生成这一遍（pass）中引入若干新指令，其中包括只在满足特定条件时才执行特定动作的条件汇编指令。

在进入编译器的各个遍之前，先简单讨论一下短路运算符。

## 短路运算符

C 标准保证 && 和 || 在不需要第二个操作数时会短路。例如，考虑表达式 `(1 - 1) && foo()`。由于第一个操作数的值为 0，无论 foo 返回什么，整个表达式都要求值为 0，因此我们根本不会调用 foo。类似地，如果 || 的第一个操作数非零，我们就不求值第二个操作数。

这不仅仅是一种性能优化；第二个操作数可能不会改变表达式的结果，但对它求值可能产生可见的副作用（side effect）。例如，foo 函数可能执行 I/O 或更新全局变量。如果你的编译器没有把 && 和 || 实现为短路运算符，某些编译出的程序就会行为不正确。（标准在 6.5.13 节第 4 段定义了 && 运算符的这一行为，在 6.5.14 节第 4 段定义了 || 运算符的这一行为。）

既然已经弄清楚这些运算符的工作方式，你就可以继续写代码了。

## 词法分析器

本章将添加九个新词法单元（token）：

- `!`：一个感叹号，逻辑 NOT 运算符
- `&&`：两个与符号，逻辑 AND 运算符
- `||`：两个竖线，逻辑 OR 运算符
- `==`：两个等号，"等于"运算符
- `!=`：一个感叹号后跟一个等号，"不等于"运算符
- `<`："小于"运算符
- `>`："大于"运算符
- `<=`："小于或等于"运算符
- `>=`："大于或等于"运算符

你的词法分析器（lexer）处理它们的方式应与此前添加的其他运算符相同。记住，词法分析器应始终为下一个词法单元选择尽可能长的匹配。例如，如果输入是 `<=something`，词法分析器发出的下一个词法单元应是 `<=`，而不是 `<`。

## TACKY 生成

既然词法分析器和解析器都已正常工作，我们可以涉足一块不太熟悉的领域：在 TACKY 中处理新运算符。关系运算符可以按照与已实现的二元运算符相同的方式转换为 TACKY。例如，给定表达式 `e1 < e2`，得到的 TACKY 类似于清单 4-3。

```text
<e1 的指令>
v1 = <e1 的结果>
<e2 的指令>
v2 = <e2 的结果>
Binary(LessThan, v1, v2, result)
```

*清单 4-3：在 TACKY 中实现 < 运算符*

不过，&& 和 || 不能用这种方式生成，因为它们会短路。清单 4-3 中的代码总是对 e1 和 e2 都求值，而我们需要生成有时会跳过 e2 的代码。为支持短路运算符，我们将添加一条无条件跳转指令，它让我们能跳到程序中的另一个位置。我们还将添加两条条件跳转指令，它们只在特定条件满足时才跳转。

### 为 TACKY IR 添加跳转、复制与比较

清单 4-4 给出了最新的 TACKY 中间表示（IR），包括新的跳转指令。

```text
program = Program(function_definition)
function_definition = Function(identifier, instruction* body)
instruction = Return(val)
            | Unary(unary_operator, val src, val dst)
            | Binary(binary_operator, val src1, val src2, val dst)
            | Copy(val src, val dst)
            | Jump(identifier target)
            | JumpIfZero(val condition, identifier target)
            | JumpIfNotZero(val condition, identifier target)
            | Label(identifier)
val = Constant(int) | Var(identifier)
unary_operator = Complement | Negate | Not
binary_operator = Add | Subtract | Multiply | Divide | Remainder | Equal | NotEqual
                | LessThan | LessOrEqual | GreaterThan | GreaterOrEqual
```

*清单 4-4：向 TACKY 添加比较、跳转与标签*

Jump 指令的工作方式与 C 中的 goto 完全一样：它使程序跳转到以某个标识符 target 标记的位置。Label 指令则把一个标识符与程序中的某个位置关联起来。清单 4-5 的 TACKY 片段展示了 Jump 与 Label 指令如何协同工作。

```text
Unary(Negate, Constant(1), Var("tmp"))
Jump("there")
❶ Unary(Negate, Constant(2), Var("tmp"))
Label("there")
Return(Var("tmp"))
```

*清单 4-5：带有一条 Jump 指令的 TACKY 片段*

这段程序把 -1 存入 tmp，然后执行 Jump 指令，跳转到 Label 指令处。接着执行 Return 指令，返回 -1。第二条 Unary 指令 ❶ 根本不会执行，因为我们跳过了它。

TACKY IR 中的第一条条件跳转指令 JumpIfZero 在 condition 的值为 0 时跳转到 target 指示的指令。如果 condition 是 0 以外的任何值，我们就不跳转到 target，而是照常执行下一条指令。第二条条件跳转指令 JumpIfNotZero 则相反：只有当 condition 不为 0 时才跳转到 target。严格来说这两条指令我们并不都需要，因为用其中一条能表达的任何行为，都可以用另一条加一条 Not 指令来表达。但同时添加两者能让我们为 && 和 || 运算生成更简单的 TACKY，最终翻译成更简单、更短的汇编代码。

另一条新指令是 Copy。由于 && 和 || 最终返回 1 或 0，我们用这条指令把 1 或 0 复制到保存表达式结果的临时变量中。

除了这五条新增指令之外，最新的 TACKY IR 还包括新的关系与逻辑二元运算符，以及一元 Not 运算符。

### 将短路运算符转换为 TACKY

让我们用这些新的 TACKY 指令来实现 && 和 || 运算符。表达式 `e1 && e2` 的 TACKY 应类似于清单 4-6。

```text
<e1 的指令>
v1 = <e1 的结果>
JumpIfZero(v1, false_label)
<e2 的指令>
v2 = <e2 的结果>
JumpIfZero(v2, false_label)
result = 1
Jump(end)
Label(false_label)
result = 0
Label(end)
```

*清单 4-6：在 TACKY 中实现 && 运算符*

我们首先求值 e1。如果它是 0，就短路并置 result 为 0，而不求值 e2。这通过 JumpIfZero 指令完成：如果 v1 为 0，我们直接跳到 false_label，然后用 Copy 指令把 result 置为 0。（为了可读性，我把它写作 `result = 0` 而不是 `Copy(0, result)`。在后面的章节里，我还会对 TACKY 记法做类似的可读性处理。）如果 v1 不为 0，我们仍需求值 e2。对于 v2 为 0 的情形，我们采用与 v1 为 0 完全相同的处理方式：用 JumpIfZero 跳转到 false_label。只有两个条件跳转都没有发生，我们才会到达 Copy 指令 `result = 1`。这意味着 e1 和 e2 都非零，因此我们把 result 置为 1。然后，我们跳过 `result = 0` 跳到 end 标签，以避免覆盖 result。

把 || 运算翻译成 TACKY 的任务就留给你自己完成。得到的 TACKY 会与清单 4-6 类似，但会使用 JumpIfNotZero 指令而不是 JumpIfZero。剩下的是 ! 和所有关系运算；你可以按照前几章添加的一元和二元运算的方式将它们转换为 TACKY。

### 生成标签

标签（label）与临时变量一样，必须全局唯一：如果标签 foo 出现在多个地方，像 `Jump("foo")` 这样的指令就没有意义了。你可以在标签中纳入一个全局计数器来保证唯一性，就像第 2 章处理变量名那样。

与临时变量不同，标签会出现在最终的汇编程序中，因此它们必须是汇编器认为语法有效的标识符，只应包含字母、数字、句点和下划线。选择有描述性的标签能让你的汇编程序更易读、易调试。例如，在清单 4-6 中，你可以用字符串 and_falseN 作为 false_label，其中 N 是全局计数器的当前值。

虽然标签彼此之间不能冲突，但它们与临时变量名冲突是允许的。你在这里生成的标签与用户定义的函数名冲突也没关系，尽管自动生成的标签和函数名都会成为最终汇编程序中的标签。我们会在代码发射阶段对自动生成的标签做名字修饰（mangle），使它们不会与用户定义的标识符冲突。

## 汇编中的比较与跳转

在开始汇编生成这一遍之前，我们先来讨论需要的新汇编指令。首先讨论比较两个值的 cmp 指令，以及根据比较结果把一个字节置为 1 或 0 的条件 set 指令。我们将用它们来实现 < 之类的关系运算符。接下来讨论条件与无条件跳转指令。

### 比较与状态标志

所有条件指令所依赖的"条件"是 RFLAGS 寄存器的状态。与 EAX、RSP 以及我们目前见过的其他寄存器不同，我们通常无法直接设置 RFLAGS。相反，CPU 每执行一条指令都会自动更新 RFLAGS。顾名思义，该寄存器的每一位都是一个标志（flag），报告关于上一条指令或 CPU 状态的某种事实。不同指令更新不同的标志：add、sub 和 cmp 指令会更新本节将要讨论的所有标志，而 mov 指令一个也不更新。其他指令的影响我们暂时可以忽略。在后文讨论 RFLAGS 时，凡是提到"上一条指令"或"上一个结果"，我指的是最近一条会影响我所讨论的那个标志的指令。

目前我们关心其中三个标志：

**零标志（Zero flag，ZF）**

若上一条指令的结果为 0，ZF 被置为 1。若上一条指令的结果非零，ZF 被置为 0。

**符号标志（Sign flag，SF）**

若上一个结果的最高有效位为 1，SF 被置为 1。若该结果的最高有效位为 0，SF 被置为 0。记住，在补码（two's complement）表示中，负数的最高有效位总是 1，正数的最高有效位总是 0。因此，符号标志告诉我们上一条指令的结果是正还是负。（如果上一个结果应被解释为无符号整数，它就不可能是负数，因此符号标志没有意义。）

**溢出标志（Overflow flag，OF）**

若上一条指令导致有符号整数上溢（overflow），OF 被置为 1，否则为 0。当有符号整数运算的结果无法用可用位数表示时，就发生整数上溢。正的结果超出该类型能保存的最大值时就会上溢。假设我们在操作 4 位整数。能表示的最大有符号数是 7，即二进制的 0111。如果用 add 指令给它加一，结果是 1000。把它解释为无符号整数时，值为 8；而把它解释为补码有符号整数时，值为 -8。计算的结果本应为正，但由于上溢，它看起来是负的。这次计算会把溢出标志置为 1。

在相反的情形下我们同样会遇到整数上溢：结果本应为负，却低于可能的最小值。例如，在普通算术中，-8 - 1 = -9。但如果用 sub 指令从 -8 的 4 位补码表示（即 1000）中减去一，得到的是 0111，也就是 7。这种情况下溢出标志同样会被置为 1。

无符号结果也可能大到或小到其类型无法表示，但在本书中我不会把这称为整数上溢。我会说结果发生了回绕（wrapped around），这与 C 标准以及大多数 x64 汇编讨论中对无符号运算的术语更一致。我做这种区分，是因为在 C 标准中无符号回绕遵循的规则与有符号整数上溢不同，CPU 检测它们的方式也不同。你将在第 II 部分学习如何处理无符号回绕。与 SF 一样，如果结果是无符号的，OF 就没有意义。

表 4-2 和表 4-3 总结了每种整数上溢可能发生的情形。表 4-2 描述加法的结果。

*表 4-2：加法导致的整数上溢与下溢*

| a + b | b > 0 | b < 0 |
| --- | --- | --- |
| a > 0 | 从正溢出为负 | 无溢出 |
| a < 0 | 无溢出 | 从负溢出为正 |

表 4-3 描述减法的结果；由于 a - b 与 a + (-b) 等价，它只是把表 4-2 的列交换了一下。

*表 4-3：减法导致的整数上溢与下溢*

| a - b | b > 0 | b < 0 |
| --- | --- | --- |
| a > 0 | 无溢出 | 从正溢出为负 |
| a < 0 | 从负溢出为正 | 无溢出 |

指令 `cmp b, a` 计算 a - b，与 sub 指令完全一样，对 RFLAGS 的影响也相同，但它会丢弃结果而不把它存入 a。当你只是想通过两个数相减来比较它们、又不想覆盖 a 时，这样更方便。

我们来分析指令 `cmp b, a` 之后 ZF 和 SF 的值：

- 若 a == b，则 a - b 为 0，因此 ZF 为 1，SF 为 0。
- 若 a > b，则 a - b 为正数，因此 SF 和 ZF 均为 0。
- 若 a < b，则 a - b 为负数，因此 SF 为 1，ZF 为 0。

先发出一条 cmp 指令，再检查 ZF 和 SF，你就能处理本章要实现的每一种比较。但是等等！这并不完全成立，因为 a - b 可能上溢，从而翻转 SF。我们来看看这对每种情形有什么影响：

- 若 a == b，则 a - b 为 0，不可能上溢。
- 若 a > b，则当 a 为正且 b 为负时，a - b 可能上溢。这种情形下正确的结果是正数，但如果上溢，结果将是负数。此时 SF 为 1，OF 也为 1。
- 若 a < b，则当 a 为负且 b 为正时，a - b 可能上溢。这种情形下正确的结果是负数，但实际结果将是正数。这意味着 SF 为 0，而 OF 为 1。

表 4-4 给出了我们考虑过的每种情形下这些标志的值。

*表 4-4：cmp 指令对状态标志的影响*

| | ZF | OF | SF |
| --- | --- | --- | --- |
| a == b | 1 | 0 | 0 |
| a > b，无上溢 | 0 | 0 | 0 |
| a > b，上溢 | 0 | 1 | 1 |
| a < b，无上溢 | 0 | 0 | 1 |
| a < b，上溢 | 0 | 1 | 0 |

通过检查 SF 和 OF 是否相同，就能判断 a 和 b 谁更大。如果相同，我们知道 a ≥ b。要么两者都为 0——因为没有上溢而得到了正（或 0）结果；要么两者都为 1——因为得到了一个很大的正数结果，上溢后变成了负数。如果 SF 和 OF 不同，我们知道 a < b。要么是没有上溢而得到了负数结果，要么是负数结果上溢后变成了正数。

**未定义行为警报！**

既然 add 和 sub 指令可能上溢，为什么我们在第 3 章没有考虑这一点？因为不需要：C 中的整数上溢是未定义行为（undefined behavior），标准并不告诉你会发生什么。编译器可以任意处理未定义行为——或者干脆不处理。

例如，当 C 中的表达式上溢时，结果通常会像前面那些例子一样回绕。然而，程序随机生成一个结果、引发一个信号，或者抹掉你的硬盘，也同样合规。最后一种听起来不太可能，但生产级编译器处理未定义行为的方式确实会出人意料（而且可以说是不可取的）。看看下面这个程序：

```c
#include <stdio.h>

int main(void) {
    for (int i = 2147483646; i > 0; i = i + 1)
        printf("The number is %d\n", i);
    return 0;
}
```

int 能保存的最大值是 2,147,483,647，因此表达式 i + 1 在第二次执行时会溢出。当 add 汇编指令上溢时，会产生负数结果，所以我们可能预期这个循环执行两次后就停止，因为条件 i > 0 不再成立。在不开启优化的情况下编译这个程序，结果正是如此——至少在我试过的 Clang 和 GCC 版本中是这样：

```bash
$ clang overflow.c
$ ./a.out
The number is 2147483646
The number is 2147483647
```

但如果开启优化，行为可能完全改变：

```bash
$ clang -O overflow.c
$ ./a.out
The number is 2147483646
The number is 2147483647
The number is -2147483648
The number is -2147483647
The number is -2147483646
The number is -2147483645
--snip--
```

发生了什么？编译器试图通过删除总是成功的条件检查来优化程序。i 的初始值为正，而且只在表达式 i = i + 1 中更新，因此编译器推断条件 i > 0 恒为真。只要 i 不上溢，这是正确的。当然，如果 i 上溢，它就是错误的，但那是未定义行为，所以编译器不必考虑它。于是它把这个条件完全删除，得到一个永不终止的循环。

这个例子我用的是 Clang，因为 GCC 产生了完全不同、甚至更不直观的行为。如果你在自己的机器上编译这个程序，很可能看到不同的结果。不妨用几种不同的优化级别试试，看看会发生什么。

注意，汇编中设置了溢出标志并不一定表明源程序发生了上溢。例如，当我们用 cmp 实现形如 a < 10 的表达式时，这条 cmp 指令可能设置溢出标志。但 a < 10 的结果要么是 0 要么是 1——两者都在 int 的范围内——所以表达式本身并没有上溢。无论我们在汇编中如何实现它，这个表达式都不会产生未定义行为。

C 有许多不同种类的未定义行为；整数上溢只是其中一例。不过这是一个特别糟糕的例子，因为它难以避免，而且可能带来严重后果，包括安全漏洞。为了解决这个长期存在的问题，下一版 C 标准 C23 增加了几个执行带检查整数运算的标准库函数。如果你使用新的 ckd_add、ckd_sub 和 ckd_mul 函数代替 +、- 和 * 运算符，当结果越界时，你将得到一个信息丰富的返回码，而不是未定义行为。想更多地了解这些新库函数，可以阅读 Jens Gustedt 的博文 "Checked Integer Arithmetic in the Prospect of C23"（https://gustedt.wordpress.com/2022/12/18/checked-integer-arithmetic-in-the-prospect-of-c23/）。

未定义行为不同于未指明行为（unspecified behavior）。如果程序的某个行为是未指明的，它可能有几种可能的表现方式，但不会表现得完全不可预测。例如，第 3 章我们学过，二元表达式中的操作数是无顺序的（unsequenced）（若其中之一是函数调用，则是顺序不确定的（indeterminately sequenced）），因此它们的求值顺序是未指明的。这并不意味着表达式的行为是未定义的。当我们求值表达式 `printf("Hello, ") + printf("World!")` 时，程序可以先打印 "Hello, "，也可以先打印 "World!"，但不能跑去干别的。无顺序的操作在某些情况下可能产生未定义行为——比如你对同一个变量执行两次无顺序的更新——但执行无顺序或顺序不确定的操作本身并不是未定义行为。

未指明行为是任何 C 程序的正常组成部分。只有当你的程序依赖于标准未指明的特定行为时（比如 Hello, World! 例子中那样），它才是问题。而未定义行为则始终是问题；只要它在程序的任何地方发生，你就不能指望程序的任何部分正确工作。

想进一步了解未定义行为，以及它在身后留下的一片混乱与破坏，请参阅第 91 页的"延伸资源"。

既然你已经理解如何设置 ZF、OF 和 SF，我们来看几条依赖这些标志的指令。

### 条件 set 指令

要实现一个关系运算符，我们先用 cmp 指令设置一些标志，然后基于这些标志设置表达式的结果。第二步用条件 set 指令（conditional set instruction）完成。每条条件 set 指令接受单个寄存器或内存地址作为操作数，并根据 RFLAGS 的状态把它置为 0 或 1。所有条件 set 指令完全相同，只是测试的条件不同。表 4-5 列出了本章需要的条件 set 指令。

*表 4-5：条件 set 指令*

| 指令 | 含义 | 标志 |
| --- | --- | --- |
| sete | 若 a == b 则置字节为 1 | ZF 置位 |
| setne | 若 a != b 则置字节为 1 | ZF 未置位 |
| setg | 若 a > b 则置字节为 1 | ZF 未置位且 SF == OF |
| setge | 若 a ≥ b 则置字节为 1 | SF == OF |
| setl | 若 a < b 则置字节为 1 | SF != OF |
| setle | 若 a ≤ b 则置字节为 1 | ZF 置位或 SF != OF |

与我们目前见过的其他指令不同，条件 set 指令只接受 1 字节操作数。例如，`sete %eax` 不是有效指令，因为 EAX 是 4 字节寄存器。而指令 `sete %al` 是有效的；它设置的是 AL 寄存器，即 EAX 的最低有效字节。要想条件性地把整个 EAX 寄存器置为 0 或 1，你需要在设置 AL 之前把 EAX 清零，因为条件 set 指令不会清除其高位字节。例如，假设 EAX 是

```text
11111111111111111111111111111011
```

然后执行

```asm
movl    $2, %edx
cmpl    $1, %edx
sete    %al
```

那么 EAX 中的新值是

```text
11111111111111111111111100000000
```

这当然不是 0。sete 指令把 EAX 的最后一个字节清零了，但没有清零其余字节。

如果操作数是内存地址，条件 set 指令会更新该地址处的单个字节。注意，内存地址作为操作数可以是 1 字节、4 字节或 8 字节，取决于上下文。在 `sete -4(%rbp)` 中，操作数 -4(%rbp) 表示 RBP - 4 处的单个内存字节；在 `addl $1, -4(%rbp)` 中，它表示从 RBP - 4 开始的 4 个内存字节。

### 跳转指令

jmp 汇编指令接受一个标签作为参数，并无条件跳转到该标签。跳转汇编指令操作另一个专用寄存器 RIP，它始终保存着下一条要执行指令的地址（IP 代表指令指针，instruction pointer）。为了执行一系列指令，CPU 进行取指-执行循环（fetch-execute cycle）：

1. 从 RIP 中的内存地址取出一条指令，存入一个专用的指令寄存器。（这个寄存器没有名字，因为在汇编中你无法引用它。）
2. 递增 RIP，使其指向下一条指令。x64 的指令长度并不都相同，因此 CPU 必须检查刚取出的指令的长度，并按相应字节数递增 RIP。
3. 执行指令寄存器中的指令。
4. 重复。

通常，按这些步骤执行会按照指令在内存中出现的顺序来执行指令。但 jmp 会向 RIP 放入一个新值，从而改变 CPU 接下来执行的指令。汇编器和链接器会把跳转指令中的标签转换成相对偏移量，告诉你 RIP 要递增或递减多少。考虑清单 4-7 的汇编片段。

```asm
    addl    $1, %eax
    jmp     foo
    movl    $0, %eax
foo:
    ret
```

*清单 4-7：带有一条 jmp 指令的汇编代码片段*

`movl $0, %eax` 的机器指令长 5 字节。要跳过它并改为执行 ret 指令，jmp 需要额外把 RIP 递增 5 字节。因此汇编器和链接器会把 `jmp foo` 转换为机器指令 `jmp 5`。然后，当 CPU 执行这条指令时，它会：

1. 取出指令 `jmp 5` 并存入指令寄存器。
2. 递增 RIP，使其指向下一条指令 `movl $0, %eax`。
3. 执行 `jmp 5`。这会给 RIP 加上 5 字节，使其指向 ret。
4. 取出 RIP 所指向的指令 ret，并从那里继续取指-执行循环。

注意，标签不是指令：CPU 不执行它们，它们也不会出现在最终可执行文件的 text 节（即包含机器指令的节）中。

条件跳转接受一个标签作为参数，但只有在条件成立时才跳转到该标签。条件跳转看起来很像条件 set 指令；它们依赖相同的条件，使用 RFLAGS 中相同的标志。例如，清单 4-8 的汇编在 EAX 和 EDX 寄存器相等时返回 3，否则返回 0。

```asm
    cmpl    %eax, %edx
    je      return3
    movl    $0, %eax
    ret
return3:
    movl    $3, %eax
    ret
```

*清单 4-8：带有一条条件跳转的汇编代码片段*

如果 EAX 和 EDX 中的值相等，cmpl 会把 ZF 置为 1，于是 je 跳转到 return3。随后执行 return3 之后的两条指令，函数返回 3。如果 EAX 和 EDX 不相等，je 不执行跳转，函数返回 0。类似地，jne 只在 ZF 为 0 时跳转。还有检查其他条件的跳转指令，但本章用不到。

## 汇编生成

既然你已经理解了需要的新汇编指令，我们来扩展汇编 AST 并更新汇编生成的各个遍。清单 4-9 定义了最新的汇编 AST，新增部分以粗体标出。

```text
program = Program(function_definition)
function_definition = Function(identifier name, instruction* instructions)
instruction = Mov(operand src, operand dst)
            | Unary(unary_operator, operand)
            | Binary(binary_operator, operand, operand)
            | Cmp(operand, operand)
            | Idiv(operand)
            | Cdq
            | Jmp(identifier)
            | JmpCC(cond_code, identifier)
            | SetCC(cond_code, operand)
            | Label(identifier)
            | AllocateStack(int)
            | Ret
unary_operator = Neg | Not
binary_operator = Add | Sub | Mult
operand = Imm(int) | Reg(reg) | Pseudo(identifier) | Stack(int)
cond_code = E | NE | G | GE | L | LE
reg = AX | DX | R10 | R11
```

*清单 4-9：带有比较与条件指令的汇编 AST*

由于所有条件跳转指令形式相同，我们用一条 JmpCC 指令来表示它们，并用不同的条件码（condition code）加以区分。条件 set 指令也做同样处理。在这个阶段，我们还把标签当作指令来对待，尽管 Label 其实并不是指令，因为标签不会被 CPU 执行。

为了实现 TACKY 的 JumpIfZero 和 JumpIfNotZero 指令，我们使用新的 JmpCC 汇编指令。我们把

```text
JumpIfZero(val, target)
```

转换为：

```text
Cmp(Imm(0), val)
JmpCC(E, target)
```

JumpIfNotZero 的实现方式相同，只是条件码用 NE 而不是 E。

类似地，我们用条件 set 指令实现所有关系运算符。例如，TACKY 指令

```text
Binary(GreaterThan, src1, src2, dst)
```

变为：

```text
Cmp(src2, src1)
Mov(Imm(0), dst)
SetCC(G, dst)
```

对于其他所有关系运算符，把 G 替换成相应的条件码即可。记住要在条件 set 指令之前把目的操作数清零，因为它只设置最低字节。在 cmp 指令之后紧接着执行 mov 是安全的，因为 mov 不会改变 RFLAGS。一个潜在的小麻烦是 SetCC 需要 1 字节操作数，而 dst 是 4 字节；幸运的是，我们可以在代码发射这一遍处理这个问题。如果 dst 是内存中的位置，SetCC 会设置该位置的第一个字节，这正是我们想要的行为。（由于 x64 处理器是小端（little-endian）的，第一个字节是最低有效字节，因此把该字节置为 1 就把整个 32 位值置为 1。）如果 dst 是寄存器，我们在代码发射时输出 SetCC 会使用相应的 1 字节寄存器名。汇编 AST 中的寄存器与大小无关，因此目前无论把它用作 4 字节还是 1 字节操作数，dst 的表示方式都相同。

由于 !x 等价于 x == 0，我们也用条件 set 指令实现一元 ! 运算符。我们把 TACKY 指令

```text
Unary(Not, src, dst)
```

转换为：

```text
Cmp(Imm(0), src)
Mov(Imm(0), dst)
SetCC(E, dst)
```

其余的 TACKY 指令——Jump、Label 和 Copy——很简单。TACKY 的 Jump 变成汇编的 Jmp，Label 变成 Label，Copy 变成 Mov。表 4-6 和表 4-7 总结了如何把每个新的 TACKY 构造转换为汇编。注意，这些表只包含新增构造，这与第 2、3 章的对应表格不同。

表 4-6 展示了如何把新的 Copy、Label、条件与无条件跳转指令转换为汇编，以及带新 Not 运算符的 Unary 指令和带新关系运算符的 Binary 指令。

*表 4-6：TACKY 指令到汇编的转换*

| TACKY 指令 | 汇编指令 |
| --- | --- |
| Unary(Not, src, dst) | Cmp(Imm(0), src)<br>Mov(Imm(0), dst)<br>SetCC(E, dst) |
| Binary(relational_operator, src1, src2, dst) | Cmp(src2, src1)<br>Mov(Imm(0), dst)<br>SetCC(relational_operator, dst) |
| Jump(target) | Jmp(target) |
| JumpIfZero(condition, target) | Cmp(Imm(0), condition)<br>JmpCC(E, target) |
| JumpIfNotZero(condition, target) | Cmp(Imm(0), condition)<br>JmpCC(NE, target) |
| Copy(src, dst) | Mov(src, dst) |
| Label(identifier) | Label(identifier) |

表 4-7 给出了 TACKY 中每个关系运算符对应的条件码。

*表 4-7：TACKY 比较到汇编的转换*

| TACKY 比较 | 汇编条件码 |
| --- | --- |
| Equal | E |
| NotEqual | NE |
| LessThan | L |
| LessOrEqual | LE |
| GreaterThan | G |
| GreaterOrEqual | GE |

### 替换伪寄存器

更新这一遍，把新的 Cmp 和 SetCC 指令所使用的任何伪寄存器（pseudoregister）替换为栈地址，就像你对所有其他指令所做的那样。

### 修补 cmp 指令

cmp 指令与 mov、add 和 sub 一样，不能让两个操作数都使用内存地址。我们按惯常方式改写，把

```asm
cmpl    -4(%rbp), -8(%rbp)
```

变为：

```asm
movl    -4(%rbp), %r10d
cmpl    %r10d, -8(%rbp)
```

cmp 指令的第二个操作数不能是常量。只要记得 cmp 与 sub 形式相同，这一点就说得通：sub、add 或 imul 指令的第二个操作数同样不能是常量，因为结果存放在那个操作数中。尽管 cmp 不产生结果，同样的规则仍然适用。我们把

```asm
cmpl    %eax, $5
```

改写为：

```asm
movl    $5, %r11d
cmpl    %eax, %r11d
```

沿用上一章的约定，我们用 R10 修补 cmp 指令的第一个操作数，用 R11 修补它的第二个操作数。

## 代码发射

我们已经生成了有效的汇编程序，可以准备发射它了。本章的代码发射（code emission）稍微复杂一些，原因有二。首先，我们要同时处理 1 字节和 4 字节寄存器。同一个寄存器，出现在接受 1 字节操作数的条件 set 指令中，与出现在我们迄今为止见过的其他接受 4 字节操作数的指令中，打印出的名字不同。

第二个问题是标签的发射。有些汇编标签由编译器自动生成，另一些——函数名——则是用户定义的标识符。目前唯一的函数名是 main，但最终我们将编译含有任意函数名的程序。由于标签必须唯一，自动生成的标签不能与程序中可能出现的任何函数名冲突。

我们将通过给自动生成的标签添加特殊的局部标签前缀来避免冲突。局部标签前缀在 Linux 上是 .L，在 macOS 上是 L。在 Linux 上，这些标签不会与用户定义的标识符冲突，因为 C 的标识符不能包含句点。在 macOS 上，它们不会冲突，因为我们给所有用户定义的名字都加上下划线前缀（例如 main 会变成 _main）。

局部标签还有另一个好处：当你需要调试这些代码时，它们不会让 GDB 或 LLDB 困惑。汇编器会把大多数标签放入目标文件的符号表，但会略去所有以局部标签前缀开头的标签。如果自动生成的标签出现在符号表里，GDB 和 LLDB 会把它们误认为函数名，这会在你尝试反汇编函数或查看栈回溯时造成麻烦。

除了这两个问题，代码发射相当直观。表 4-8 到表 4-10 总结了这一遍的变化。从现在起，代码发射表格将只显示相对上一章的变化，这与描述 TACKY 到汇编转换的表格类似。完整的代码发射遍概览见附录 B；其中包含三套表格，分别展示这一遍在第 I、II、III 部分结束时的样子。

表 4-8 展示了如何打印本章的新汇编指令。它对局部标签使用 .L 前缀；如果你在 macOS 上，请改用不带句点的 L 前缀。

*表 4-8：汇编指令的格式化*

| 汇编指令 | 输出 |
| --- | --- |
| Cmp(operand, operand) | `cmpl    <operand>, <operand>` |
| Jmp(label) | `jmp     .L<label>` |
| JmpCC(cond_code, label) | `j<cond_code>      .L<label>` |
| SetCC(cond_code, operand) | `set<cond_code>    <operand>` |
| Label(label) | `.L<label>:` |

cmp 指令带有 l 后缀，表明它操作 4 字节值。条件 set 指令不带表示操作数大小的后缀，因为它们只支持 1 字节操作数。跳转和标签也不使用操作数大小后缀，因为它们不接受操作数。不过，条件跳转和条件 set 指令确实需要后缀来指明测试的条件。表 4-9 给出了每个条件码对应的后缀。

Raph Levien 的 "With Undefined Behavior, Anything Is Possible" 探讨了 C 中未定义行为的一些来源，以及它当初如何进入标准的历史（https://raphlinus.github.io/programming/rust/2018/08/17/undefined-behavior.html）。
