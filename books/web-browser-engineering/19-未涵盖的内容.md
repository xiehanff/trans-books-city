# 第六部分　结语（Part 6: Conclusion）

# 附录 A　未涵盖的内容

*Appendix A: What Wasn't Covered*

希望前面 16 章的内容已经让你对 Web 浏览器的所有主要组件有了扎实的理解——从它发出的网络请求，到它安全存储你数据的方式。这个主题实在过于庞大，有些内容我不得不略去。下面列出的是我认为本书未涵盖的内容中最重要的部分，排名不分先后。

## A.1 JavaScript 执行

现代 Web 浏览器中很大一部分是高性能的 JavaScript 实现。如今，每一个主流浏览器不仅运行 JavaScript，还会在运行过程中利用运行时类型分析（runtime type analysis）将其即时编译为底层机器码。此外，像隐藏类（hidden classes）这样的技术还能在 JavaScript 本身不提供结构信息的地方推断出结构，从而降低内存占用和垃圾回收（garbage collection）压力。在这一切之上，现代浏览器还能执行 WebAssembly——一种与硬件无关的字节码格式，可供许多其他编程语言作为编译目标，有朝一日它或许能在 Web 上与 JavaScript 平起平坐。

本书没有自己构建 JavaScript 引擎，而是使用了 DukPy。我之所以这样选择，是因为虽然 JavaScript 执行是现代浏览器的核心，但它所用的技术与 Python、Lua 或 Java 等其他语言的执行相当类似。要了解现代 JavaScript 引擎的内部原理，最好的办法是读一本讲编程语言实现的书。

## A.2 文本与图形渲染

文本渲染远比表面看起来复杂得多。字母的宽度和高度各不相同。重音符号可能需要堆叠在字符上方。字符在与其他字符相邻时可能改变形状，比如连字（ligatures）以及（草书字体的）整形（shaping）。有些语言的书写方向是从右到左或从上到下。此外还有各种排版特性，比如字距调整（kerning）和字形变体（variants）。但其中最复杂的是提示（hinting）——它是嵌入字体内部的一小段计算机程序，用于对字体加以调整，使其更好地匹配离散的像素网格。文本渲染当然会影响 Skia，但它也会影响布局，决定内容在屏幕上的尺寸和位置。

更广义地说，图形学本身就相当复杂！我们的浏览器使用 Skia，它正是 Chromium 和其他一些浏览器实际使用的光栅化（rasterization）引擎。但我们完全没有讨论 Skia 究竟是如何工作的，而事实证明它相当复杂。它不仅要渲染文本，还要在基本上所有 CPU 和 GPU 上快速、高质量地应用各种混合（blend）与效果。在真实的浏览器中，事情变得更加复杂：既有精巧的合成（compositing）系统、图形进程的安全沙箱，还有各种平台特定的字体与操作系统合成集成。除此之外，实现 Canvas [1]、WebGL [2] 和 WebGPU [3] 这类暴露给 JavaScript 的底层 API 也需要付出大量额外的努力。

我在书中略过了这个主题，因为 Skia（负责图形）和 Harfbuzz（负责文本）之类的库以及各种系统库已经提供了高质量的实现，所以可以说这并非浏览器特有的内容。但这个领域确有相当的深度，最好交给专门讲述这些主题的书。

## A.3 连接安全与隐私

如今的 Web 浏览器内置了一整套复杂的加密协议，名字令人眼花缭乱，比如 AES-GCM、ChaCha20 和 HMAC-SHA512。这些协议防范的是那些有能力读取或写入网络数据包的恶意行为者。从最宏观的层面看，连接安全是通过 TLS 协议建立的（它曾在第 1 章客串出场），并由密码学家、证书颁发机构（certificate authorities）和开源项目组成的生态系统共同维护。

我之所以略去对 TLS 的深入讨论，是因为本书对完整性和校验那种不够严谨的态度，与真正的安全工程是水火不容的。一个最小化、不完整的 TLS 版本就是一个残破且不安全的 TLS 版本，这与预期目标背道而驰，在教学上也适得其反。要学习现代密码学和网络安全，最好的办法是读一本专门讲这个主题的书。

Web 隐私（privacy）[4] 是我略过的另一个重要主题。在某些方面，安全与隐私是相关的（二者当然相辅相成），但它们并不相同。而且 Web 隐私正处于变动不居之中，比如围绕第三方 Cookie（third-party cookies）[5]、指纹追踪（fingerprinting）[6]，以及是否应该提供辅助广告的 API 的种种争论。我略过这个主题，是因为许多基本概念尚未尘埃落定：隐私的标准是什么，政府、浏览器开发者、网站作者和用户在其中各自应扮演什么角色。

## A.4 网络缓存与媒体

缓存（caching）通过跳过大部分网络请求来让请求变快。然而，它之所以不只是一种单纯的优化，还在于 HTTP 在设计上就对缓存提供了大量支撑。实现一个网络缓存会显著加深对 HTTP 的理解。话虽如此，本书的网络部分篇幅已经够长了，而且在整本书中，缺少缓存从未让人感到不便，所以我决定不涉及这个主题。

另外，由于如今大部分网络带宽和电池电量都被视频播放和视频会议消耗掉，实时视频的编码、解码和渲染中蕴藏着整个复杂的世界。真实的浏览器拥有专门负责这些服务和 API 的大型团队，世界各地也有许多研究者从事视频压缩工作。视频编解码器（video codecs）非常引人入胜，但同样不是浏览器特有的内容，所以本书完全略过了它们，我建议你阅读专门讲述它们的书籍。

## A.5 更复杂的布局模式

真实浏览器使用的布局算法远比本书所涵盖的复杂得多，具备浮动布局（floating layout）、定位元素（positioned elements）、弹性盒子（flexible boxes）、网格（grids）、表格（tables）等特性。实现这些布局模式十分复杂，需要细心与精巧——尤其是当你还想要速度和增量性能的时候。这里的重要技术包括多阶段布局（multi-phase layout）¹ 以及测量-布局阶段（measure-layout phases），而且要想获得良好的性能，还必须采用精巧的缓存策略。

我在本书中略过了更复杂的布局，因为即便是书中描述的简单布局算法也已经相当复杂，而现实世界的布局算法还包含大量由旧标准和向后兼容（backwards compatibility）造成的偶然复杂性（accidental complexity），这些我不想多谈。

## A.6 浏览器 UI 与开发者工具

真实浏览器的「浏览器 UI」——即网页周围的浏览器界面（chrome），你可以在那里输入 URL、查看标签页等等——远比我们的浏览器复杂和强大。事实上，真实浏览器团队中有相当大一部分人只负责这部分工作，而不是「Web 平台」本身。现代浏览器的多进程特性也使其难以与同步的操作系统 API 交互，我们在第 14 章讨论无障碍（accessibility）时已经见过这一点。此外，许多浏览器（至少是桌面浏览器）支持强大的扩展 API（extension APIs）[7]，让开发者能够扩展浏览器 UI。为了便于实现，浏览器 UI 常常用 HTML 编写，并由浏览器自己渲染。

还有，如果没有某种调试辅助，构建复杂的 Web 应用几乎是不可能的，所以所有真实的浏览器都内置了调试器。信不信由你，在相当长的一段时间里，Web 开发者就是靠大量的 console.log 调试 [8] 过日子的（在有了方便查看控制台的办法之前，甚至靠 alert 调试！）。随着 Firefox 上颇具创新性的 Firebug [9] 浏览器扩展的出现，并最终演变成如今集成式的开发者工具，这一切发生了巨大改变。这些开发者工具与浏览器引擎本身深度集成，以实现诸如实时观察元素样式、暂停并单步执行 JavaScript 之类的功能。

我略过了这个主题，因为浏览器 UI 中的许多挑战与其他任何 UI 都一样：设计、易用性、复杂度等等。这会让本书变得乏味。即便是调试器——概念上相当有趣——也只有在你做了大量 UI 工作让它变得可用之后才有用处。遗憾的是，我还没见过哪本书是讲开发者工具的，不过很多书都会涵盖基础的用户界面开发。

## A.7 测试

真实浏览器演化出了一套令人叹为观止的测试技术，以确保它们能长期保持并提升质量。它们总共有数十万的单元（unit）[10] 测试和集成（integration）[11] 测试。最近，人们的许多注意力投向了健壮的跨浏览器测试（cross-browser tests）[12]，它允许单个自动化测试在所有浏览器上运行，以验证它们在相同输入下行为一致。如今还有一年一度的互操作性（interoperability）[13]² 基准测试，衡量浏览器在关键特性上距离这一目标还有多远。测试的幕后是代码与基础设施的整个世界，用以高效地持续运行这些测试，并提供丰富的框架 [14] 让测试变得容易。
