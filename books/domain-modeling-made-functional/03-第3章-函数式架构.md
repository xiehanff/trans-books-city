# 第 3 章 函数式架构

*Chapter 3: A Functional Architecture*

我们接下来的挑战是：如何把对领域的理解转化为软件架构，特别是基于函数式编程（functional programming）原则的架构？

在现阶段，我们其实不应该在架构上花费太多心思，因为我们对这个系统还没有真正的理解——我们正处在无知程度的顶峰！这段时间的最佳用法是做那些能减少无知的事情：事件风暴（Event Storming）、访谈，以及其他一切围绕需求收集的最佳实践。

另一方面，对“如何把领域模型实现为软件”先有个粗略的概念总是有好处的。在快节奏的开发周期中，我们常常需要在理解其余部分之前就开始实现领域的某些部分，因此需要在这些组件尚未构建之前，就有一个把它们拼装在一起的计划。此外，先构建一个简陋的原型——一个“行走骨架”（walking skeleton）——来演示系统整体如何工作，也大有益处。对具体实现的早期反馈，是发现自身知识盲区的好办法。

本章我们将简要考察一个适用于函数式领域模型的典型软件架构。我们会看到限界上下文（Bounded Context）和领域事件（Domain Event）等 DDD 概念如何落实为软件，并勾勒出本书后续章节将采用的实现思路。

当然，软件架构本身也是一个领域，所以让我们遵循自己的建议，在谈论它时使用一套“统一语言”（ubiquitous language）。我们将采用 Simon Brown 的“C4”方法的术语[12]。按照这一方法，一个软件架构由四个层次组成，可以这样描述：

- “系统上下文”（system context）是最顶层，代表整个系统。
- 系统上下文由若干“容器”（container）组成，它们是可部署单元，比如一个网站、一个 Web 服务、一个数据库等。
- 每个容器又由若干“组件”（component）组成，它们是代码中的主要结构单元。
- 最后，每个组件由若干“类”（class）——在函数式架构中则是“模块”（module）——组成，其中包含一组底层的方法或函数。

良好架构的目标之一，就是定义容器、组件和模块之间的各种边界，使得当新需求不可避免地出现时，“变更成本”（cost of change）能被控制在最小。

## 限界上下文作为自治的软件组件

先从“限界上下文”这个概念以及它与架构的关系说起。正如前面所见，一个上下文应当是一个具有明确定义边界的自治子系统，这一点很重要。不过即便有这些约束，我们仍有多种常见的架构风格可供选择。

如果整个系统被实现为单一的可部署单体（monolith，用上面的 C4 术语来说即单个容器），那么一个限界上下文可以简单到只是一个带有明确定义接口的独立模块，或者更理想一些，是一个更独立的组件，例如一个 .NET 程序集。或者，每个限界上下文也可以部署在各自的容器里——这是经典的面向服务架构（service-oriented architecture）。我们还可以更加细粒度，把每个单独的工作流（Workflow）做成一个独立部署的容器——这就是微服务架构（microservice architecture）。

然而在这个早期阶段，我们不需要选定某种具体方案。从逻辑设计到对应的可部署形态之间的转换并不关键，只要我们确保各个限界上下文保持解耦与自治即可。

前面我们强调过，把边界划对很重要，但这在项目初期很难做到；而且应当预期，随着对领域了解的深入，边界也会随之改变。重构一个单体要容易得多，所以一个好的实践是：最初先把系统构建成单体，只在确有必要时再重构为解耦的容器。除非你确定收益大于弊端，否则没必要一上来就跳到微服务、去支付“微服务溢价”[13]（即运维上的额外负担）。打造一个真正解耦的微服务架构并不容易：如果你关掉其中一个微服务，其他任何东西都跟着出问题，那你其实并没有得到微服务架构，只是得到了一个分布式单体！

## 限界上下文之间的通信

限界上下文之间如何通信？例如，当下单上下文处理完订单后，它如何通知物流上下文去实际发货？正如前面所见，答案是使用事件。例如，实现方式可能像这样：

- 下单上下文中的 Place-Order（下单）工作流发出一个 OrderPlaced（订单已下达）事件。
- OrderPlaced 事件被放入队列，或以其他方式发布。
- 物流上下文监听 OrderPlaced 事件。
- 收到事件后，创建一个 ShipOrder（发货）命令（Command）。
- ShipOrder 命令启动 Ship-Order（发货）工作流。
- Ship-Order 工作流成功完成后，发出一个 OrderShipped（订单已发货）事件。

下面是这个示例的示意图。图中，“下单”上下文与“物流”上下文各自独立成块，事件是两者之间唯一的通信媒介：OrderPlaced 事件经队列从下单上下文流向物流上下文，在那里被转换为 ShipOrder 命令并启动 Ship-Order 工作流，后者完成后再发出 OrderShipped 事件。

可以看到，这是一个完全解耦的设计：上游组件（下单子系统）和下游组件（物流子系统）彼此并不知情，只通过事件通信。如果我们想要真正自治的组件，这种解耦至关重要。

在上下文之间传输事件的具体机制，取决于我们所选择的架构。队列非常适合带缓冲的异步通信，因此会是采用微服务或代理程序（agent）的实现中的首选。在单体系统中，我们可以在内部使用同样的队列方式，也可以只是通过函数调用在上游组件和下游组件之间建立简单的直接连接。和以往一样，我们现在不必做出选择，只要把组件设计成解耦的就行。

至于把事件（如 OrderPlaced）转换为命令（如 ShipOrder）的那个处理器，它可以是下游上下文的一部分（位于该上下文的边界上），也可以由作为基础设施一部分运行的独立路由器（router）[14] 或流程管理器（process manager）[15] 来承担，这取决于你的架构，以及你希望把事件与命令之间的耦合放在哪里。

### 在限界上下文之间传输数据

一般而言，用于上下文之间通信的事件不会只是一个简单的信号，它还会携带下游组件处理该事件所需的全部数据。例如，OrderPlaced 事件可能会包含已下达的完整订单。这样一来，物流上下文就拥有了构造相应 ShipOrder 命令所需的全部信息。（如果数据太大、无法直接放进事件，可以改为传输某种指向共享数据存储位置的引用。）

被传递的这些数据对象，表面上可能与限界上下文内部定义的对象（我们称之为领域对象，domain object）相似，但它们并不相同：它们是专门为了被序列化、并作为上下文间基础设施的一部分被共享而设计的。我们把这类对象称为数据传输对象（Data Transfer Object，DTO）（尽管这个术语源自 DDD 之外[16]，而且我这里的用法与之略有出入）。换句话说，OrderPlaced 事件中包含的 OrderDTO 会携带与 Order 领域对象大体相同的信息，但其结构会为了适合自身用途而有所不同。（第 11 章“序列化”会详细讲解如何定义 DTO。）

于是，在上游上下文的边界处，领域对象被转换为 DTO，DTO 再被序列化成 JSON、XML 或其他某种序列化格式：

领域对象 → DTO → JSON/XML（或其他序列化格式）

在下游上下文，这一过程反方向重复：JSON 或 XML 被反序列化为 DTO，DTO 再被转换为领域对象，如图所示：

JSON/XML（或其他序列化格式）→ DTO → 领域对象

在实践中，被序列化的顶层 DTO 通常是事件 DTO；事件 DTO 又包含子 DTO，例如 Order 的 DTO，而后者又包含更多的子 DTO（例如表示订单行 OrderLine 的一组 DTO）。

### 信任边界与验证

限界上下文的外围起着“信任边界”（trust boundary）的作用。限界上下文内部的一切都是可信且有效的，而限界上下文之外的一切都是不可信的、可能是无效的。因此，我们要在工作流的开头和结尾加上一些“闸门”（gate），充当可信领域与不可信外部世界之间的中介。

在输入闸门处，我们始终会对输入做验证，确保它符合领域模型的约束。例如，假设 Order 的某个属性必须非空且少于五十个字符。传入的 OrderDTO 没有这类约束，可能包含任何内容；但经过输入闸门的验证之后，我们就可以确信 Order 领域对象是有效的。如果验证失败，工作流的其余部分将被跳过，并产生一个错误。（第 11 章“序列化”会讨论这类 DTO 验证。）

输出闸门的职责则不同：它要确保私有信息不会泄露到限界上下文之外，这既是为了避免上下文之间意外的耦合，也是出于安全考虑。例如，物流上下文不需要知道支付某笔订单所用的信用卡号。为此，在把领域对象转换为 DTO 的过程中，输出闸门常常会有意地“丢失”一些信息（比如卡号）。

## 限界上下文之间的契约

我们希望尽可能降低限界上下文之间的耦合，但共享的通信格式总会带来某种耦合：事件及相关 DTO 构成了限界上下文之间的一种契约（Contract）。两个上下文必须就它们的公共格式达成一致，通信才能成功进行。

那么，契约由谁来决定？上下文之间存在多种多样的关系，DDD 社区为其中一些常见的关系起了专门的名字：

- 共享内核（Shared Kernel）关系指两个上下文共享一部分公共的领域设计，因此相关团队必须协作。例如在我们的领域里，可以规定下单上下文和物流上下文必须对配送地址使用同一种设计：下单上下文接收并验证一个地址，物流上下文则使用同一个地址来发货。在这种关系中，更改某个事件或 DTO 的定义，必须先与受影响的其他上下文的拥有者协商后才能进行。
- 客户/供应商（Customer/Supplier）关系，或者说消费者驱动契约（Consumer Driven Contract）[17] 关系，指由下游上下文来定义它希望上游上下文提供的契约。只要上游上下文履行了契约规定的义务，两个领域仍然可以独立演进。在我们的领域里，计费上下文可以定义契约（“要给客户开出账单，我需要这些”），然后下单上下文只提供这些信息，多一点也不给。
- 遵奉者（Conformist）关系与消费者驱动相反：下游上下文接受上游上下文提供的契约，并调整自己的领域模型与之匹配。在我们的领域里，下单上下文可能就直接接受产品目录定义的契约，并让自己的代码原样适配上。

### 防腐层

在与外部系统通信时，可用的接口常常与我们的领域模型完全不匹配。这种情况下，需要把交互和数据转换成更适合在限界上下文内部使用的形式，否则我们的领域模型会在努力适配外部系统模型的过程中被“腐蚀”。

上下文之间的这层额外的解耦，在 DDD 术语中称为防腐层（Anti-Corruption Layer，常缩写为 ACL）。在前面的图里，“输入闸门”往往就扮演着 ACL 的角色——它防止内部纯粹的领域模型被外部世界的知识所“腐蚀”。

也就是说，防腐层的主要目的并不是执行验证或防止数据损坏，而是充当两种不同语言之间的翻译者——上游上下文使用的语言和下游上下文使用的语言。因此在我们的下单示例中，可以设置一个防腐层，把“下单”的词汇翻译成“物流”的词汇，让这两个各自拥有自己词汇表的上下文能够独立演进。

### 带关系的上下文映射图

假设我们的设计已经推进了一步，现在确定了各上下文之间的关系：

- 下单上下文与物流上下文之间将是“共享内核”关系，意味着双方将共同拥有通信契约。
- 下单与计费之间将是“消费者驱动契约”关系，意味着由计费上下文决定契约，下单系统向计费上下文提供的恰好是它所需的数据。
- 下单与产品目录之间将是“遵奉者”关系，意味着下单上下文将顺从地使用与产品目录相同的模型。
- 最后，外部的地址检查服务所使用的模型与我们的领域毫无相似之处，所以我们会在与它的交互中插入一个显式的防腐层。这是使用第三方组件时的常见模式，有助于避免厂商锁定（vendor lock-in），也让我们以后可以换用别的服务。

图中展示了我们领域的上下文映射图（context map），上面标出了这类上下文之间的关系。

可以看到，上下文映射图展示的不再只是上下文之间纯技术的关系，还包括拥有这些上下文的各个团队之间的关系，以及我们期望他们如何协作（或不协作！）。决定各个领域如何交互，往往既是技术挑战，也同样是有组织层面的挑战；有些团队会使用所谓的“逆向康威策略”（inverse Conway maneuver）[18] 来确保组织结构与架构保持一致。

## 限界上下文内的工作流

在发现过程中，我们把业务工作流看作由一个命令发起、并生成一个或多个领域事件的迷你流程。而在我们的函数式架构中，每个这样的工作流都将被映射为一个单独的函数：输入是命令对象，输出是事件对象列表。

在绘制设计图时，我们把工作流表示成一段带有输入和输出的小管道。公开工作流（即那些从限界上下文外部触发的工作流）会被画成略微“探出”边界一点的样子，如图所示。

工作流总是包含在单个限界上下文之内，绝不会跨多个上下文去“端到端”地实现某个场景。第 7 章“将工作流建模为管道”会详细讲解如何为工作流建模。

### 工作流的输入与输出

工作流的输入总是与命令相关联的数据，输出总是要传递给其他上下文的一组事件。例如在我们的下单工作流中，输入是与 PlaceOrder 命令相关联的数据，输出则是 OrderPlaced 事件等一组事件。

但请记住，我们已经确定与计费上下文之间是“客户/供应商”关系。这意味着，我们不应给计费上下文发送通用的 OrderPlaced 事件，而只应发送计费所需要的信息，多一点也不发。例如，这些信息可能只是账单地址和待计费的总额，而不包括配送地址或商品清单。

这意味着我们需要从工作流中发出一个新事件（比如叫 BillableOrderPlaced，可计费订单已下达），其结构可能像这样：

```fsharp
data BillableOrderPlaced =
    OrderId
    AND BillingAddress
    AND AmountToBill
```

我们可能还想同时发出一个 OrderAcknowledgmentSent（订单确认已发送）事件。经过这些更改，我们早前那张工作流示意图就有了误导性，需要更新：更新后的图中，PlaceOrder 工作流在收到 PlaceOrder 命令后，返回的是一组事件——OrderPlaced、面向计费上下文的 BillableOrderPlaced，以及 OrderAcknowledgmentSent。

在前面的图中，有一点很重要：工作流函数并不“发布”领域事件——它只是把这些事件返回出来。事件如何被发布，是一个独立的关注点。

### 避免在限界上下文内部使用领域事件

在面向对象设计中，在限界上下文内部引发领域事件的做法很常见。那种方式是：一个工作流对象引发 OrderPlaced 事件；接着某个处理器监听到该事件，发送订单确认；然后另一个处理器生成 BillableOrderPlaced 事件，如此等等。它可能像这样：

工作流对象引发 OrderPlaced → 处理器监听到该事件并发送订单确认 → 另一个处理器监听到该事件并生成 BillableOrderPlaced → ……

在函数式设计中，我们宁愿不采用这种方式，因为它会制造隐藏的依赖。相反，如果我们需要某个事件的“监听器”，只需把它追加到工作流的末尾，像这样：

PlaceOrder 工作流 → （在工作流末尾追加）发送订单确认 → 生成 BillableOrderPlaced → ……

这种做法更加显式——不存在带有可变状态的全局事件管理器——因此更容易理解和维护。我们会在“实现”相关章节以及“设计的演进”一章中看到它在实践中的应用。

## 限界上下文内的代码结构

现在来看看限界上下文内部的代码是如何组织的。

在传统的“分层方法”中，代码被划分为若干层：核心领域或业务逻辑层、数据库层、服务层，以及 API 或用户界面层（或它们的某种变体）。一个工作流会从顶层出发，一路向下直到数据库层，然后再返回顶层，如图所示。

然而这种方法存在很多问题。一个突出的问题是，它违背了“一起变化的代码应当放在一起”这条重要的设计原则。由于各层是“水平”拼装起来的，工作流工作方式的任何变化都意味着你要改动每一层。更好的办法是改用“垂直”切片：每个工作流包含完成自身工作所需的全部代码；当某个工作流的需求发生变化时，需要更改的只有那个特定垂直切片中的代码，如图所示。

不过，这仍然不是最理想的。为了看清这一点，我们把一个工作流拉伸成一根水平管道，再以这种方式来观察各个层。

显然，各层相互混杂，使得理解（以及测试）这些逻辑变得不必要地复杂。

### 洋葱架构

我们换个做法：把领域代码放在中心，然后让其他方面围绕它组装起来，规则是每一层只能依赖更内侧的层，而不能依赖更外侧的层。也就是说，所有依赖都必须指向内部。这就是“洋葱架构”（Onion Architecture）[19]。在这张洋葱图里，领域模型位于最中心的核心，数据库访问等基础设施关切位于外层，所有依赖箭头一律由外向内。

也存在其他类似的方法，例如六边形架构（Hexagonal Architecture）[20] 和整洁架构（Clean Architecture）[21]。

为了确保所有依赖都指向内部，我们将不得不使用依赖注入（dependency injection）在函数式编程中的等价物，这会在第 9 章“实现：组装管道”中讨论。

### 把 I/O 保持在边缘

函数式编程的一个主要目标，是使用那些可预测、无需查看内部即可推理的函数。为此，我们会尽可能使用不可变（immutable）数据，并努力确保函数拥有显式依赖而非隐藏依赖。最重要的是，我们要尽量避免函数产生副作用（side effect），包括随机性、对函数外部变量的修改，以及最重要的——任何形式的 I/O。

例如，一个对数据库或文件系统进行读写的函数会被视为“不纯的”（impure），所以我们会尽量避免在核心领域中出现这类函数。

可是，那我们该如何读写数据呢？答案是：把所有 I/O 都推到洋葱的边缘——比如，只在工作流的开头或结尾访问数据库，而不是在工作流内部访问。这还有一个附带的好处：迫使我们分离不同的关注点——核心领域模型只关心业务逻辑，而持久化和其他 I/O 是基础设施层面的关注点。

事实上，把 I/O 和数据库访问推到边缘的实践，与上一章引入的持久化无知（persistence ignorance）概念配合得非常好。如果你连从工作流内部访问数据库都做不到，你就不可能用数据库来为领域建模！（第 12 章“持久化”会更详细地讨论数据库的使用。）

## 小结

本章又介绍了几个与 DDD 相关的概念和术语，我们把它们集中归纳一下：

- 领域对象（Domain Object）是一种只在上下文边界内部使用的对象，与数据传输对象相对。
- 数据传输对象（Data Transfer Object，DTO）是一种为序列化和在上下文之间共享而设计的对象。
- 共享内核（Shared Kernel）、客户/供应商（Customer/Supplier）和遵奉者（Conformist）是限界上下文之间不同种类的关系。
- 防腐层（Anti-Corruption Layer，ACL）是一个在两个领域之间翻译概念的组件，用于降低耦合，让各领域独立演进。
- 持久化无知（Persistence Ignorance）指领域模型应当只基于领域本身的概念来构建，不应包含对数据库或其他持久化机制的任何感知。

## 接下来学什么

至此，我们已经对这个领域有了理解，也拥有了设计解决方案的总体方法，接下来可以迎接对各个工作流进行建模和实现的挑战了。在接下来的几章里，我们将使用 F# 的类型系统来定义工作流及其所使用的数据，创造出既可编译、又能让领域专家和非开发者看懂的代码。

不过，首先我们需要理解 type（类型）对函数式程序员意味着什么，以及它与面向对象设计中的 class（类）有什么不同。这就是下一章的主题。
