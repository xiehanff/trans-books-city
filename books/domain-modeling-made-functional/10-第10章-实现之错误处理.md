# 第 10 章 实现之错误处理

*Chapter 10: Implementation: Working with Errors*

如果产品代码格式不对、客户姓名过长，或者地址验证服务超时了，会发生什么？

任何系统都会有错误，而如何处理它们非常重要。一致且透明的错误处理，对任何类型的生产级系统都至关重要。

在上一章中，我们刻意从管道的各个步骤中移除了错误「效应」（即 Result 类型），以便专注于组合与依赖。

但这个效应很重要！在本章中，我们会把 Result 恢复到类型签名中，并学习如何使用它们。

更一般地，我们将探索错误处理的函数式方法，发展出一项技术，让你能够优雅地捕获错误，而不会让代码被丑陋的条件判断和 try/catch 语句污染。我们还将看到，为什么某些错误应当被视为领域错误，值得与领域驱动设计的其余部分同等的重视。

## 使用 Result 类型让错误显式化

函数式编程技术专注于尽可能让事物显式化，错误处理也不例外。我们想要创建的函数，应当明确表明自己是否成功；如果失败，错误情形有哪些。

很多时候，错误在我们的代码中被当作二等公民。但要想拥有一个健壮的、可投入生产的系统，我们应当把错误当作一等公民。对于属于领域一部分的错误，更是要加倍如此。

在上一章中，我们使用异常（exception）来抛出错误。这很方便，但这意味着所有的函数签名都具有误导性。例如，检查地址的函数有这样的签名：

```fsharp
type CheckAddressExists =
  UnvalidatedAddress -> CheckedAddress
```

这个签名毫无帮助，因为它没有指出可能出什么错。相反，我们想要的是一个全函数（total function，参见「全函数」一节），其所有可能的结果都由类型签名明确记录。正如我们在「错误的建模」中学到的，我们可以使用 Result 类型来表明函数可能成功或失败，于是签名会是这个样子：

```fsharp
type CheckAddressExists =
    UnvalidatedAddress -> Result<CheckedAddress,AddressValidationError>

and AddressValidationError =
  | InvalidFormat of string
  | AddressNotFound of string
```

这告诉我们几件重要的事情：

- 输入是一个 UnvalidatedAddress。
- 如果验证成功，输出是一个（可能不同的）CheckedAddress。
- 如果验证不成功，原因要么是格式无效，要么是地址未找到。

这展示了函数签名如何充当文档。如果另一位开发者需要使用这些函数，只需看看签名，就能对它们了解很多。

## 处理领域错误

软件系统是复杂的，我们无法用这样的类型处理每一种可以想到的错误，我们也不想那样做。因此，在做任何其他事情之前，让我们先建立一套一致的错误分类与处理方法。

我们可以把错误分为三类：

- **领域错误**。这类错误是业务流程中预期会发生的，因此必须纳入领域的设计之中，例如订单被计费拒绝、订单包含无效的产品代码。业务方通常已有处理这类事情的流程，代码也需要反映这些流程。
- **崩溃**。这类错误会让系统处于未知状态，例如无法处理的系统错误（如「内存不足」），或由程序员疏忽导致的错误（例如「除以零」或「空引用」）。
- **基础设施错误**。这类错误是架构中预期会发生、但不属于任何业务流程、也不纳入领域的错误，例如网络超时或认证失败。

有时不太清楚某个错误是不是领域错误。如果拿不准，直接问领域专家！

你：嗨，Ollie。问个小问题：如果我们访问负载均衡器时连接中断了，这是你在意的事情吗？

Ollie：？？？？

你：好吧，那我们把它归为基础设施错误，并告诉用户稍后重试。

这些不同类型的错误需要不同的实现方式。

领域错误是领域的一部分，和其他任何东西一样，因此应当纳入我们的领域建模，与领域专家讨论，并尽可能记录在类型系统中。

崩溃最好通过放弃当前工作流并抛出异常来处理，然后在最合适的最高层级（例如应用程序的 main 函数或同等位置）捕获该异常。下面是一个例子：

```fsharp
/// 一个在收到坏输入时会崩溃的工作流
let workflowPart2 input =
  if input = 0 then
    raise (DivideByZeroException())
  ...

/// 应用程序的顶层函数，
/// 捕获工作流抛出的所有异常。
let main() =

  // 用 try/with 块包裹所有工作流
  try
    let result1 = workflowPart1()
    let result2 = workflowPart2 result1
    printfn "the result is %A" result2

  // 顶层异常处理
  with
  | :? OutOfMemoryException ->
    printfn "exited with OutOfMemoryException"
  | :? DivideByZeroException ->
    printfn "exited with DivideByZeroException"
  | ex ->
    printfn "exited with %s" ex.Message
```

基础设施错误可以用上述任一方式处理。具体如何选择，取决于你所使用的架构。如果代码由许多小型服务组成，异常可能更干净；但如果你开发的是更偏单体的应用，可能想让错误处理更显式。事实上，把许多基础设施错误当作领域错误来对待往往是有用的，因为这会迫使我们这些开发者思考哪里可能出错。的确，在某些情况下，这类错误需要上报给领域专家。例如，如果远程地址验证服务不可用，业务流程应如何变化？我们该告诉客户什么？这类问题无法仅由开发团队解答，而必须由领域专家和产品负责人共同考虑。

在本章余下部分，我们只关注那些要作为领域一部分显式建模的错误。我们不想建模的崩溃和错误，就像上面展示的那样，直接抛出异常并由顶层函数捕获即可。

### 用类型为领域错误建模

在对领域建模时，我们避免使用字符串之类的基元类型，而是使用领域词汇（通用语言，Ubiquitous Language）创建领域专属的类型。

错误也应得到同等待遇。如果某些类型的错误在关于领域的讨论中出现了，它们就应当像领域中的其他事物一样被建模。通常我们会把错误建模为一个选择类型（choice type），为每种需要特别关注的错误设置一个独立的分支。

例如，我们可以像这样对下单工作流中的错误建模：

```fsharp
type PlaceOrderError =
  | ValidationError of string
  | ProductOutOfStock of ProductCode
  | RemoteServiceError of RemoteServiceError
  ...
```

ValidationError 分支将用于属性验证，例如任何长度或格式错误。

ProductOutOfStock 分支将在客户尝试购买缺货商品时使用。可能有专门的业务流程来处理这种情况。

RemoteServiceError 分支展示了如何处理一个基础设施错误。与其只是抛出异常，我们可以处理这种情况，比如在放弃之前重试一定的次数。

使用这样的选择类型的好处在于：它充当了代码中的显式文档，列出所有可能出错的事情；而且与错误关联的任何额外信息也被显式地展示出来。此外，随着需求变化，扩展（或收缩）这个选择类型不仅容易，而且安全，因为编译器会确保：任何对这个列表做模式匹配的代码，只要漏掉某个分支，就会收到警告。

在更早设计工作流的时候（第 7 章「把工作流建模为管道」），我们知道可能发生错误，但没有深究它们具体可能是什么。这是有意为之。在设计阶段，没有必要试图预先定义所有可能的错误。通常，错误情形会随着应用的开发而出现，到那时你再决定是否将它们视为领域错误。如果某个情形属于领域错误，你再把它加入选择类型。

当然，向选择类型添加新分支，很可能会在你的部分代码中引发警告，说你没有处理所有分支。这很棒，因为这会迫使你与领域专家或产品负责人讨论：针对那种情形到底该怎么做。像这样使用选择类型时，很难意外忽略某个边界情形。

### 错误处理让代码变丑

异常的一个好处是能让你的「快乐路径」（happy path）代码保持整洁。例如，上一章中我们的 validateOrder 函数看起来是这样的（伪代码）：

```fsharp
let validateOrder unvalidatedOrder =
  let orderId = ... 创建订单 ID（或抛出异常）
  let customerInfo = ... 创建客户信息（或抛出异常）
  let shippingAddress = ... 创建并验证 shippingAddress...
  // 等等
```

如果我们让每个步骤都返回错误，代码就会丑陋得多。通常，我们需要在每个潜在错误之后加上条件判断，再加上 try/catch 块来捕获潜在的异常。下面是演示这一点的更多伪代码：

```fsharp
let validateOrder unvalidatedOrder =
  let orderIdResult = ... 创建订单 ID（或返回 Error）
  if orderIdResult is Error then
      return

  let customerInfoResult = ... 创建客户信息（或返回 Error）
  if customerInfoResult is Error then
      return

  try
      let shippingAddressResult = ... 创建有效地址（或返回 Error）
      if shippingAddress is Error then
        return

      // ...

  with
    | ?: TimeoutException -> Error "service timed out"
    | ?: AuthenticationException -> Error "bad credentials"

  // 等等
```

这种方法的问题在于，现在三分之二的代码都花在了错误处理上——我们原本简洁干净的代码被毁掉了。我们面临一个挑战：如何在引入恰当的错误处理的同时，保持管道模型的优雅？

## 链接生成 Result 的函数

在处理我们的具体情况之前，我们应该退后一步，看看全局。一般而言，如果我们有一些生成 Result 的函数，怎样才能以一种干净的方式把它们组合起来？

下面是这个问题的一个可视化呈现。普通函数可以看作一段铁轨：

- 普通函数（单轨）：输入 → 函数 → 输出

*示意图：普通函数是一段单轨铁轨，输入从一端进，输出从另一端出。*

而输出 Result 的函数，则可以看作一段一分为二的铁轨：

- 输入 → 函数 → 成功轨道（Ok 值）
-           ↘ 失败轨道（Error 值）

*示意图：输出 Result 的函数是一段在出口处分成两条的铁轨。*

沿用铁路的比喻，我要把这类函数称为道岔函数（switch function）。它们也常被称为「单子式」（monadic）函数。

那么，我们应该如何连接两个这样的「道岔」函数呢？显然，如果输出是成功的，我们希望继续执行序列中的下一个函数；但如果输出是错误，我们希望绕过它，如图所示。

- 第一个道岔函数成功 → 进入第二个函数
- 第一个道岔函数失败 → 绕过第二个函数，直接汇入失败路径

怎么把这两个道岔组合起来，让两条失败轨道都连通呢？答案显而易见——像这样：

- 两个函数各自的失败轨道彼此连通：无论哪个函数失败，都会汇入同一条旁路

如果把管道中的所有步骤都按这种方式连接起来，就得到了我所说的错误处理的「两轨模型」（two-track model），或者叫「铁路式编程」（Railway-Oriented Programming），看起来像这样：

- 成功轨道 → 步骤 A → 步骤 B → 步骤 C → … → 成功输出
- 失败轨道：任一步骤出错即被甩到失败轨道 → 绕过其余所有步骤 → 失败输出

在这种方式中，上面那条轨道是快乐路径，下面那条是失败路径。你从成功轨道出发，如果幸运，会一路待在上面走到终点；但一旦出现错误，你就会被甩到失败轨道上，绕过管道中其余的步骤。

这看起来很棒，但有一个大问题：我们无法把这些生成 Result 的函数组合在一起，因为两轨输出的类型与单轨输入的类型不一样：

- 两轨输出：Result<成功值, 失败值> —— 无法直接连接到—— 单轨输入：普通值

我们如何解决这个问题？如何把一个两轨输出连接到一个单轨输入？好吧，先观察到：如果第二个函数的输入是两轨的，那连接它们就不成问题了：

- 两轨输出 → 两轨输入：完全匹配

所以，我们需要把这种单输入、双输出的「道岔」函数转换成一个两轨函数。为此，让我们创建一种特殊的「适配器积木」（adapter block）：它有一个插槽用来放置道岔函数，并把它转换成两轨函数：

- 适配器积木：两轨输入 → [插槽中的道岔函数] → 两轨输出；若输入是失败，则直接旁路

如果我们把所有步骤都转换成两轨函数，那么转换之后，就可以把它们漂亮地组合起来：

最终结果就是一个两轨管道，带有一条「成功」轨道和一条「失败」轨道，正如我们所愿。

### 实现适配器积木

我们之前讨论过「函数适配器」的概念。把道岔函数转换为两轨函数的适配器，是函数式编程工具箱中非常重要的一员——它在 FP 术语中通常被称为 bind（绑定）或 flatMap。它的实现出奇地简单。逻辑如下：

- 输入是一个「道岔」函数。输出是一个新的仅两轨函数，表示为一个 lambda：它有两轨输入和两轨输出。
- 如果两轨输入是成功，则把该输入传给道岔函数。道岔函数的输出是两轨值，因此我们不需要再对它做任何处理。
- 如果两轨输入是失败，则绕过道岔函数，直接返回失败。

代码实现如下：

```fsharp
let bind switchFn  =
  fun twoTrackInput ->
    match twoTrackInput with
    | Ok success -> switchFn success
    | Error failure -> Error failure
```

一个等价但更常见的实现，是让 bind 接受两个输入参数——「道岔」函数和一个两轨值（一个 Result）——从而去掉 lambda，像这样：

```fsharp
let bind switchFn twoTrackInput =
  match twoTrackInput with
  | Ok success -> switchFn success
  | Error failure -> Error failure
```

bind 的这两种实现是等价的：第二个实现经过柯里化（currying）后与第一个相同。

另一个有用的适配器积木，是把单轨函数转换成两轨函数的适配器。它在 FP 术语中通常被称为 map（映射）。逻辑如下：

- 输入是一个单轨函数和一个两轨值（一个 Result）。
- 如果输入的 Result 是成功，则把该输入传给单轨函数，并把输出包在 Ok 里，使其重新成为一个 Result（因为输出需要是两轨的）。
- 如果输入的 Result 是失败，则和之前一样绕过该函数。

代码实现如下：

```fsharp
let map f aResult =
  match aResult with
  | Ok success -> Ok (f success)
  | Error failure -> Error failure
```

有了 bind、map 以及另外几个类似的函数，我们就拥有了一个强大的工具箱，可以用来组合各种形状不匹配的函数。

### 组织 Result 相关函数

这些新函数应该放在代码组织的什么位置？标准做法是把它们放进一个与类型同名的模块，在这里就是 Result 模块。该模块看起来会是这样：

```fsharp
/// 定义 Result 类型
type Result<'Success,'Failure> =
    | Ok of 'Success
    | Error of 'Failure

/// 处理 Result 的函数
module Result =

  let bind f aResult = ...

  let map f aResult = ...
```

由于 Result 及其相关函数会在领域代码中到处使用，我们通常会创建一个新的工具模块（例如 Result.fs），并把它放在项目结构中领域类型之前。

### 组合与类型检查

我们一直专注于通过把「道岔」函数转换成「两轨」函数来让函数的「形状」匹配。但当然，类型检查也在同时进行，所以我们还得确保类型相互匹配，组合才能正常工作。

在成功分支上，类型可以沿轨道变化，只要每一步的输出类型与下一步的输入类型匹配即可。例如，下面三个函数可以用 bind 组合成一个管道，因为 FunctionA 的输出（Bananas）与 FunctionB 的输入匹配，FunctionB 的输出（Cherries）与 FunctionC 的输入匹配：

```fsharp
type FunctionA = Apple -> Result<Bananas,...>
type FunctionB = Bananas -> Result<Cherries,...>
type FunctionC = Cherries -> Result<Lemon,...>
```

bind 函数的用法会是这样：

```fsharp
let functionA : FunctionA = ...
let functionB : FunctionB = ...
let functionC : FunctionC = ...

let functionABC input =
  input
  |> functionA
  |> Result.bind functionB
  |> Result.bind functionC
```

另一方面，FunctionA 和 FunctionC 无法直接组合，即使有 bind 也不行，因为类型不同：

- FunctionA 的输出是 Result<Bananas,...>，而 FunctionC 的输入是 Cherries——类型不匹配

### 转换到公共错误类型

与类型可以在每一步变化的成功轨道不同，错误轨道从头到尾都是同一个统一的类型。也就是说，管道中的每个函数必须拥有相同的错误类型。

在许多情况下，这意味着我们需要微调各个错误类型，使它们彼此兼容。为此，让我们创建一个与 map 类似、但作用于失败轨道中值的函数。这个函数叫做 mapError，实现如下：

```fsharp
let mapError f aResult =
  match aResult with
  | Ok success -> Ok success
  | Error failure -> Error (f failure)
```

例如，假设我们有一个 AppleError 和一个 BananaError，还有两个分别以它们作为错误类型的函数：

```fsharp
type FunctionA = Apple -> Result<Bananas,AppleError>
type FunctionB = Bananas -> Result<Cherries,BananaError>
```

错误类型不匹配意味着 FunctionA 和 FunctionB 无法组合。我们需要做的，是创建一个两者都能转换过去的新类型——两者的一个选择类型。我们把它叫做 FruitError：

```fsharp
type FruitError =
  | AppleErrorCase of AppleError
  | BananaErrorCase of BananaError
```

然后我们可以像这样把 functionA 转换为结果类型为 FruitError 的函数：

```fsharp
let functionA : FunctionA = ...

let functionAWithFruitError input =
  input
  |> functionA
  |> Result.mapError (fun appleError -> AppleErrorCase appleError)
```

它可以像这样简化：

```fsharp
let functionAWithFruitError input =
  input
  |> functionA
  |> Result.mapError AppleErrorCase
```

下面是这个转换的示意图：

- functionA：错误轨道上的 AppleError --（mapError AppleErrorCase）--> FruitError

如果查看 functionA 和 functionAWithFruitError 的签名，可以看到它们在错误情形中的类型已经不同了，正如我们所愿：

```fsharp
// functionA 的类型
Apple -> Result<Bananas,AppleError>

// functionAWithFruitError 的类型
Apple -> Result<Bananas,FruitError>
```

类似地，我们也可以把 functionB 的错误情形从 BananaError 转换为 FruitError。把这一切拼到一起，代码会是这个样子：

```fsharp
let functionA : FunctionA = ...
let functionB : FunctionB = ...

// 把 functionA 转换为使用 "FruitError"
let functionAWithFruitError input =
  input |> functionA |> Result.mapError AppleErrorCase

// 把 functionB 转换为使用 "FruitError"
let functionBWithFruitError input =
  input |> functionB |> Result.mapError BananaErrorCase

// 现在我们可以用 "bind" 组合这些新版本
let functionAB input =
  input
  |> functionAWithFruitError
  |> Result.bind functionBWithFruitError
```

组合出来的 functionAB 的签名是：

```fsharp
val functionAB : Apple -> Result<Cherries,FruitError>
```

## 在管道中使用 bind 和 map

概念我们已经理解了，现在把它们付诸实践。我们将用这些会生成错误的函数组合出工作流管道，并在必要时对它们加以调整，使它们彼此契合。

让我们快速回顾一下管道的各个组件，聚焦于 Result，暂时忽略 Async 效应和服务依赖。

首先，ValidateOrder 在输入数据格式不正确时会返回错误，所以它是一个「道岔」函数，其签名将是：

```fsharp
type ValidateOrder =
  // 此处暂忽略额外的依赖
  UnvalidatedOrder                             // 输入
    -> Result<ValidatedOrder, ValidationError> // 输出
```

PriceOrder 步骤也可能因各种原因失败，所以它的签名将是：

```fsharp
type PriceOrder =
  ValidatedOrder                          // 输入
    -> Result<PricedOrder, PricingError>  // 输出
```

AcknowledgeOrder 和 CreateEvents 步骤总会成功，所以它们的签名是：

```fsharp
type AcknowledgeOrder =
  PricedOrder                         // 输入
    -> OrderAcknowledgmentSent option // 输出

type CreateEvents =
  PricedOrder                            // 输入
    -> OrderAcknowledgmentSent option    // 输入（来自上一步的事件）
    -> PlaceOrderEvent list              // 输出
```

让我们从组合 ValidateOrder 和 PriceOrder 开始。ValidateOrder 的失败类型是 ValidationError，而 PriceOrder 的失败类型是 PricingError。正如前面所见，这两个函数因错误类型不同而不兼容。我们需要把两个函数都转换为返回相同的错误类型——一个在整个管道中通用的错误类型，我们称之为 PlaceOrderError。PlaceOrderError 的定义如下：

```fsharp
type PlaceOrderError =
  | Validation of ValidationError
  | Pricing of PricingError
```

现在，使用 mapError，我们可以定义可组合的 validateOrder 和 priceOrder 新版本，就像前面 FruitError 例子中做的那样：

```fsharp
// 适配为返回 PlaceOrderError
let validateOrderAdapted input =
  input
  |> validateOrder // 原始函数
  |> Result.mapError PlaceOrderError.Validation

// 适配为返回 PlaceOrderError
let priceOrderAdapted input =
  input
  |> priceOrder // 原始函数
  |> Result.mapError PlaceOrderError.Pricing
```

做完这些，我们终于可以用 bind 把它们链接起来：

```fsharp
let placeOrder unvalidatedOrder =
  unvalidatedOrder
  |> validateOrderAdapted             // 适配后的版本
  |> Result.bind priceOrderAdapted // 适配后的版本
```

注意 validateOrderAdapted 函数前面不需要加 bind，因为它在管道中排第一。

接下来，acknowledgeOrder 和 createEvents 没有错误——它们是「单轨」函数——所以我们可以用 Result.map 把它们转换成两轨函数，插进管道：

```fsharp
let placeOrder unvalidatedOrder =
  unvalidatedOrder
  |> validateOrderAdapted
  |> Result.bind priceOrderAdapted
  |> Result.map acknowledgeOrder   // 用 map 转换为两轨
  |> Result.map createEvents       // 转换为两轨
```

这个 placeOrder 函数有这样的签名：

```fsharp
UnvalidatedOrder -> Result<PlaceOrderEvent list,PlaceOrderError>
```

这已经非常接近我们需要的了。

让我们分析一下这版新的工作流管道：

- 管道中的每个函数都可能产生错误，而它能产生的错误都记录在签名中。我们可以孤立地测试这些函数，并确信当它们组装到一起时不会出现任何意外行为。
- 这些函数仍然被链接在一起，但现在使用的是两轨模型。某一步中的错误，会导致管道中其余的函数被跳过。
- 顶层 placeOrder 的整体流程依然是干净的。没有额外的条件判断，也没有 try/catch 块。

不幸的是，这个 placeOrder 实现实际上无法通过编译！即使使用了 bind 和 map，函数也不总能拼在一起。特别是，acknowledgeOrder 的输出与 createEvents 的输入不匹配，因为那个输出只是事件，而不是定价后的订单。我们很快就会看到如何处理这个问题。

## 将其他类型的函数适配到两轨模型

到目前为止，我们在管道中见过两种函数「形状」：单轨函数和「道岔」函数。但当然，我们可能还需要处理许多其他类型的函数。现在就来看其中两种：

- 抛出异常的函数
- 不返回任何东西的「死端」函数

### 处理异常

我们一直避免在自己的代码中抛异常，但对于那些不受我们控制的代码——例如某个库或服务——中抛出的异常，该怎么办？之前我们曾提出，许多异常并不属于领域设计，除顶层外无需捕获。但如果我们确实想把某个异常当作领域的一部分，应该怎么做？

解决方案很直接——我们只需再创建一种「适配器积木」函数，把抛异常的函数转换成返回 Result 的函数。

例如，假设我们想捕获远程服务的超时，并将其转变为 RemoteServiceError。我们要与许多服务打交道，所以先定义一个 ServiceInfo 来记录导致错误的服务：

```fsharp
type ServiceInfo = {
  Name : string
  Endpoint: Uri
  }
```

然后我们可以定义一个基于它构建的错误类型：

```fsharp
type RemoteServiceError = {
  Service : ServiceInfo
  Exception : System.Exception
  }
```

我们把服务信息和原始的服务函数传给一个适配器积木，由它捕获其中一些异常，并在这些情况下返回 Result。下面是服务函数只接受单个参数（下面代码中的 x）时的例子：

```fsharp
/// 把抛异常的服务转换为返回 Result 的服务的
/// 「适配器积木」。
let serviceExceptionAdapter serviceInfo serviceFn x =
  try
    // 调用服务并返回成功
    Ok (serviceFn x)
  with
  | :? TimeoutException as ex ->
    Error {Service=serviceInfo; Exception=ex}
  | :? AuthorizationException as ex ->
    Error {Service=serviceInfo; Exception=ex}
```

注意，我们并没有捕获所有可能的异常，只捕获了与领域相关的那些。

如果服务函数有两个参数，我们就需要再定义一个适配器来支持这种情况，依此类推：

```fsharp
let serviceExceptionAdapter2 serviceInfo serviceFn x y =
  try
    Ok (serviceFn x y)
  with
  | :? TimeoutException as ex -> ...
  | :? AuthorizationException as ex -> ...
```

这些是能适配任何函数的通用适配器积木。在某些情况下，你可能更愿意为某个特定服务编写定制的适配器积木，例如把数据库异常转换为带有「record not found」和「duplicate key」这类领域友好分支的 DatabaseError 选择类型。

要使用这个适配器，我们先创建一个 ServiceInfo，然后传入服务函数。例如，如果服务函数是地址检查函数，代码会是这个样子：

```fsharp
let serviceInfo = {
  Name = "AddressCheckingService"
  Endpoint = ...
  }

// 抛异常的服务
let checkAddressExists address =
    ...

// 返回 Result 的服务
let checkAddressExistsR address =
    // 适配该服务
    let adaptedService =
      serviceExceptionAdapter serviceInfo checkAddressExists
    // 调用该服务
    adaptedService address
```

为了表明这个新函数是返回 Result 的变体，我们把它命名为 checkAddressExistsR，结尾加了一个 R。（在真实世界的代码中，你多半会让它直接沿用原函数的名字——对后者进行「遮蔽」。）

再次检查签名，确认我们得到了想要的东西。原函数的签名表明它总是返回 CheckedAddress：

```fsharp
checkAddressExists :
  UnvalidatedAddress -> CheckedAddress
```

但我们知道这个签名具有误导性。查看新「适配后」函数的签名，可以看到它的描述性强得多：它表明自己可能失败并返回一个错误。

```fsharp
checkAddressExistsR :
  UnvalidatedAddress -> Result<CheckedAddress,RemoteServiceError>
```

错误类型是 RemoteServiceError，所以如果想在管道中使用这个函数，我们就得在 PlaceOrderError 类型中为远程错误添加一个分支：

```fsharp
type PlaceOrderError =
  | Validation of ValidationError
  | Pricing of PricingError
  | RemoteService of RemoteServiceError // 新增！
```

然后，在创建函数的 R 版本时，我们必须把 RemoteServiceError 转换为共享的 PlaceOrderError，就像之前做的那样：

```fsharp
let checkAddressExistsR address =
  // 适配该服务
  let adaptedService =
    serviceExceptionAdapter serviceInfo checkAddressExists
  // 调用该服务
  address
  |> adaptedService
  |> Result.mapError RemoteService // 提升为 PlaceOrderError
```

### 处理「死端」函数

另一类常见的函数，可以称之为「死端」或「发射后不管」的函数：接受输入但不返回任何输出的函数。

这类函数大多在以某种方式写 I/O。例如，下面的日志函数就没有输出：

```fsharp
// string -> unit
let logError msg =
  printfn "ERROR %s" msg
```

其他例子还包括写数据库、向队列发消息等。

要让死端函数能在两轨管道中工作，我们还需要再一种适配器积木。要构造它，我们首先需要一种以输入调用死端函数、然后返回原始输入的方法——一个「直通」函数。我们把这个函数叫做 tee：

- tee：输入 → 调用 f（产生副作用）→ 返回原输入

*示意图：tee 积木让输入穿过死端函数后原样返回，从而可以接回单轨轨道。*

代码如下：

```fsharp
// ('a -> unit) -> ('a -> 'a)
let tee f x =
  f x
  x
```

签名表明，它接受任何返回 unit 的函数，产出一个单轨函数。

然后我们可以用 Result.map 把 tee 的输出转换为两轨函数：

```fsharp
// ('a -> unit) -> (Result<'a,'error> -> Result<'a,'error>)
let adaptDeadEnd f =
  Result.map (tee f)
```

这样，我们就有了把 logError 这类死端函数转换成两轨函数、从而插入管道的方法。

## 用计算表达式让生活更轻松

到目前为止，我们处理的都是直截了当的错误处理逻辑。我们已能用 bind 把生成 Result 的函数链接起来；对于那些本来不是两轨的函数，我们也能用各种「适配器」函数让它们契合两轨模型。

不过有时，工作流逻辑会更复杂。你可能需要在条件分支或循环中工作，或者处理深度嵌套的生成 Result 的函数。在这类场景下，F# 以「计算表达式」（computation expression）的形式提供了一些解脱。计算表达式是一种特殊的表达式块，它把 bind 的杂乱细节藏在幕后。

创建自己的计算表达式很容易。例如，我们可以为 Result 创建一个叫 result（小写）的计算表达式。入门只需要两个函数：

- bind，我们已经见过它与 Result 的配合使用
- return，它只是构造一个值——对 Result 而言，那就是 Ok 构造器

我们不在这里展示 result 计算表达式的实现细节——你可以在本书代码仓库的 Result.fs 文件中浏览代码。我们还是来看看计算表达式在实践中如何简化充满 Result 的代码。

在之前版本的 placeOrder 中，我们用 bind 把返回 Result 的 validateOrder 的输出连接到 priceOrder 的输入，像这样：

```fsharp
let placeOrder unvalidatedOrder =
  unvalidatedOrder
  |> validateOrderAdapted
  |> Result.bind priceOrderAdapted
  |> Result.map acknowledgeOrder
  |> Result.map createEvents
```

而有了计算表达式，我们就可以直接使用 validateOrder 和 priceOrder 的输出，就像它们没有被包在 Result 里一样。

下面是同样的代码使用计算表达式后的样子：

```fsharp
let placeOrder unvalidatedOrder =
  result {
    let! validatedOrder =
      validateOrder unvalidatedOrder
      |> Result.mapError PlaceOrderError.Validation
    let! pricedOrder =
      priceOrder validatedOrder
      |> Result.mapError PlaceOrderError.Pricing
    let acknowledgmentOption =
      acknowledgeOrder pricedOrder
    let events =
      createEvents pricedOrder acknowledgmentOption
    return events
  }
```

来看看这段代码是如何工作的：

- result 计算表达式以单词 result 开始，后面跟着花括号界定的块。
- 特殊的 let! 关键字看起来像 let，但实际上会「解包」result，取出里面的值。let! validatedOrder = ... 中的 validatedOrder 是一个普通值，可以直接传入 priceOrder 函数。
- 错误类型在整个块中必须一致，因此要用 Result.mapError 把错误类型提升到公共类型，和之前一样。错误在 result 表达式中不是显式的，但它们的类型仍然需要匹配。
- 块中最后一行使用 return 关键字，它指明整个块的值是什么。

实践中，凡是你原本会用 bind 的地方，直接用 let! 就行。对于其他不需要 bind 的函数，比如 acknowledgeOrder，直接使用普通语法即可——不需要用 Result.map。

如你所见，计算表达式让代码看起来就像我们根本没有在使用 Result，它把复杂性隐藏得很好。

我们不会深入讲解如何定义计算表达式，但那相当直截了当。例如，下面是前面用到的 result 计算表达式的一个基础定义：

```fsharp
type ResultBuilder() =
  member this.Return(x) = Ok x
  member this.Bind(x,f) = Result.bind f x

let result = ResultBuilder()
```

在本书后面我们还会见到更多计算表达式，尤其是 async 计算表达式，它以同样优雅的方式管理异步回调。

### 组合计算表达式

计算表达式的一个吸引人之处在于它们是可组合的，这是我们始终追求的品质。

例如，假设 validateOrder 和 priceOrder 是用 result 计算表达式定义的：

```fsharp
let validateOrder input = result {
  let! validatedOrder = ...
  return validatedOrder
  }

let priceOrder input = result {
  let! pricedOrder = ...
  return pricedOrder
  }
```

那么它们就可以像一个普通函数那样，在一个更大的 result 表达式中使用：

```fsharp
let placeOrder unvalidatedOrder = result {
  let! validatedOrder = validateOrder unvalidatedOrder
  let! pricedOrder = priceOrder validatedOrder
  ...
  return ...
  }
```

而 placeOrder 反过来又可以用于一个更大的 result 表达式，以此类推。

### 用 Result 验证订单

现在我们可以重新审视 validateOrder 函数的实现，这次使用 result 计算表达式来隐藏错误处理逻辑。

作为提醒，下面是不带任何 Result 的实现：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->
    let orderId =
      unvalidatedOrder.OrderId
      |> OrderId.create
    let customerInfo =
      unvalidatedOrder.CustomerInfo
      |> toCustomerInfo
    let shippingAddress =
      unvalidatedOrder.ShippingAddress
      |> toAddress checkAddressExists
    let billingAddress = ...
    let lines = ...

    let validatedOrder : ValidatedOrder = {
      OrderId  = orderId
      CustomerInfo = customerInfo
      ShippingAddress = shippingAddress
      BillingAddress = billingAddress
      Lines = lines
    }
    validatedOrder
```

但当我们把所有辅助函数都改为返回 Result 之后，这段代码就不再有效了。例如，OrderId.create 函数会返回 Result<OrderId,string>，而不是一个纯粹的 OrderId（toCustomerInfo、toAddress 等也一样）。然而，如果使用 result 计算表达式并用 let! 代替 let，我们就可以像访问普通值一样访问 OrderId、CustomerInfo 等。下面是现在的实现：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->
    result {
      let! orderId =
        unvalidatedOrder.OrderId
        |> OrderId.create
        |> Result.mapError ValidationError
      let! customerInfo =
        unvalidatedOrder.CustomerInfo
        |> toCustomerInfo
      let! shippingAddress = ...
      let! billingAddress  = ...
      let! lines = ...

      let validatedOrder : ValidatedOrder = {
        OrderId  = orderId
        CustomerInfo = customerInfo
        ShippingAddress = shippingAddress
        BillingAddress = billingAddress
        Lines = lines
      }
      return validatedOrder
    }
```

不过和之前一样，我们需要用 Result.mapError 来确保所有错误类型匹配。OrderId.create 在错误情形返回的是 string，所以我们必须用 mapError 把它提升为 ValidationError。其他辅助函数在处理简单类型时也需要做同样的事。我们假设 toCustomerInfo 和 toAddress 函数的输出已经是 ValidationError，所以不需要对它们使用 mapError。

### 处理 Result 的列表

当我们最初不使用 Result 类型来验证订单行时，可以直接用 List.map 转换每一行：

```fsharp
let validateOrder unvalidatedOrder =
  ...

  // 把每一行转换成 OrderLine 领域类型
  let lines =
      unvalidatedOrder.Lines
      |> List.map (toValidatedOrderLine checkProductCodeExists)

  // 创建并返回 ValidatedOrder
  let validatedOrder : ValidatedOrder = {
    ...
    Lines = lines
    // 等等
    }
  validatedOrder
```

但当 toValidatedOrderLine 返回 Result 之后，这种方法就不再有效了。使用 map 之后，我们得到的是 Result<ValidatedOrderLine,...> 的列表，而不是 ValidatedOrderLine 的列表。

这对我们毫无帮助：在设置 ValidatedOrder.Lines 的值时，我们需要的是「Result 包着列表」，而不是「列表包着 Result」。

```fsharp
let validateOrder unvalidatedOrder =
  ...

  let lines = // lines 是一个「Result 的列表」
      unvalidatedOrder.Lines
      |> List.map (toValidatedOrderLine checkProductCodeExists)

  let validatedOrder : ValidatedOrder = {
    ...
    Lines = lines  // 编译器错误
    //       ^ 这里期望的是「列表的 Result」
    }
  ...
```

在这里使用 result 表达式也帮不上忙——问题在于类型不匹配。于是现在的问题变成：如何把「Result 的列表」转换成「列表的 Result」？

让我们创建一个做这件事的辅助函数：它遍历 Result 的列表，只要其中任何一个坏了，整体结果就是那个错误；否则，如果全都好，整体结果就是所有成功值组成的列表。

实现它的诀窍在于记住：在 F# 中，标准列表类型是链表，是通过把每个元素前插到更小的列表上构建而成的。要解决我们的问题，我们首先需要一版新的前插操作（在 FP 世界也被称为「cons」操作符），把包含单个元素的 Result 前插到包含列表的 Result 上。实现很直截了当：

- 如果两个参数都是 Ok，把内容前插，并把得到的列表重新包进 Result。
- 否则，只要任一参数是 Error，就返回该错误。

代码如下：

```fsharp
/// 把一个 Result<单个元素> 前插到一个 Result<列表>
let prepend firstR restR =
  match firstR, restR with
  | Ok first, Ok rest -> Ok (first::rest)
  | Error err1, Ok _ -> Error err1
  | Ok _, Error err2 -> Error err2
  | Error err1, Error _ -> Error err1
```

如果查看这个 prepend 函数的类型签名，可以看到它是完全泛型的：它接受一个 Result<'a> 和一个 Result<'a list>，并把它们组合成一个新的 Result<'a list>。

有了它，我们就可以从 Result<'a> 的列表构建 Result<'a list>：从最后一个元素开始迭代（使用 foldBack），把每个 Result 元素前插到我们目前已构建的列表上。我们把这个函数叫做 sequence，并把它作为又一个有用的函数加入 Result 模块。它的实现如下：

```fsharp
let sequence aListOfResults =
  let initialValue = Ok [] // Result 内的空列表

  // 以相反顺序遍历列表，
  // 把每个元素前插到初始值上
  List.foldBack prepend aListOfResults initialValue
```

不必太纠结这段代码的工作原理。一旦写好并放进你的库中，你只需要知道如何以及何时使用它！

让我们定义一个 Result 类型来做实验（我们称之为 IntOrError），然后用一个全成功的列表测试 sequence：

```fsharp
type IntOrError = Result<int,string>

let listOfSuccesses : IntOrError list = [Ok 1; Ok 2]
let successResult =
  Result.sequence listOfSuccesses   // Ok [1; 2]
```

可以看到，Result 的列表（[Ok 1; Ok 2]）已被转换成一个包含列表的 Result（Ok [1; 2]）。

再试试全失败的列表：

```fsharp
let listOfErrors : IntOrError list = [ Error "bad"; Error "terrible" ]

let errorResult =
  Result.sequence listOfErrors  // Error "bad"
```

我们得到了另一个 Result，但这一次它包含的是一个错误（Error "bad"）。

在失败的例子中，只有第一个错误被返回。但在很多情况下，我们希望保留所有错误，尤其是在做验证的时候。用于此目的的函数式编程技术叫做 applicative（应用式）。我们会在下一节简单提及，但不会在本书中讨论详细的实现。

工具箱里有了 Result.sequence，我们终于可以编写构造 ValidatedOrder 的代码了：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->
    result {
      let! orderId = ...
      let! customerInfo = ...
      let! shippingAddress = ...
      let! billingAddress  = ...
      let! lines =
        unvalidatedOrder.Lines
        |> List.map (toValidatedOrderLine checkProductCodeExists)
        |> Result.sequence // 把 Result 的列表转换为单个 Result

      let validatedOrder : ValidatedOrder = {
        OrderId  = orderId
        CustomerInfo = customerInfo
        ShippingAddress = shippingAddress
        BillingAddress = billingAddress
        Lines = lines
      }
      return validatedOrder
    }
```

如果你关心性能，可以把 List.map 接 Result.sequence 合并成单个函数（通常称为 traverse[28]）来提高效率，但我们不在这里跑题。

我们差不多完成了，但还有最后一个波折。validateOrder 的输出，其错误情形的类型是 ValidationError。

然而在主管道中，我们需要错误情形是 PlaceOrderError。于是现在，在 placeOrder 函数中，我们需要把类型 Result<ValidatedOrder,ValidationError> 转换为类型 Result<ValidatedOrder,PlaceOrderError>。和之前一样，我们可以用 mapError 来变换错误值的类型。类似地，我们也需要把 priceOrder 的输出从 PricingError 转换为 PlaceOrderError。

下面是使用了 mapError 的整体工作流现在的样子：

```fsharp
let placeOrder : PlaceOrder =       // 函数定义
  fun unvalidatedOrder ->
    result {
      let! validatedOrder =
        validateOrder checkProductExists checkAddressExists unvalidatedOrder
        |> Result.mapError PlaceOrderError.Validation
      let! pricedOrder =
        priceOrder getProductPrice validatedOrder
        |> Result.mapError PlaceOrderError.Pricing
      let acknowledgmentOption = ...
      let events = ...
      return events
    }
```

现在的输出就是 Result<ValidatedOrder,PlaceOrderError> 了，正如我们所愿。

## 单子及其他

本书尽量避免太多行话，但有一个词在函数式编程中反复出现，那就是单子。那我们就暂停一下，现在来稍微谈谈单子。这个以 m 开头的词以吓人著称，但事实上，我们在本章中就已经创建并使用过一个了！

单子（monad）只是一种编程模式，它允许你把「单子式」函数串联成序列。好，那什么是「单子式」函数？它是接受一个「普通」值并返回某种「增强」值的函数。在本章发展出的错误处理方法中，「增强」值就是包在 Result 类型中的值，所以单子式函数正是我们一直在打交道的、生成 Result 的「道岔」函数。

严格地说，「单子」只是对具备三个组成部分的东西的称呼：

- 一种数据结构
- 一些相关的函数
- 一些关于这些函数必须如何工作的规则

在我们的场景中，数据结构就是 Result 类型。

要成为单子，这个数据类型还必须有两个相关函数：return 和 bind：

- return（也称为 pure）是把普通值变成单子类型的函数。由于我们使用的类型是 Result，return 函数就是 Ok 构造器。
- bind（也称为 flatMap）是让你把单子式函数（在我们的场景中，即生成 Result 的函数）串联起来的函数。我们在本章前面已经看过如何为 Result 实现 bind。

关于这些函数应当如何工作的规则，被称为「单子定律」（monad laws），听起来吓人，实际上只是确保实现正确、不做怪事的常识性准则。我不会在这里展开单子定律——你在互联网上很容易找到它们。

喏，单子就是这么回事。希望你能看出，它并不像你可能以为的那样神秘。

### 用 applicative 并行组合

既然谈到了这里，我们也来聊聊一个相关的模式：applicative（应用式）。

applicative 与单子类似；但单子是把单子式函数串联成序列，applicative 则允许你并行地组合单子式的值。例如，如果需要做验证，我们大概会用 applicative 方法把所有错误都组合起来，而不是只保留第一个。遗憾的是，本书没有篇幅深入细节，不过 fsharpforfunandprofit.com 上有详细的讨论。[29]

在本书中，我不会频繁使用「单子」或「applicative」这些术语，但今后如果你真的遇到它们，你也能知道它们是什么意思。

**术语提示**

本章涉及的关键词：bind 函数、Result 类型、map 函数、错误处理相关函数、单子、applicative。

供参考，下面是本章引入的一些术语：

- 在错误处理的语境下，bind 函数把一个生成 Result 的函数转换为两轨函数。它用于把生成 Result 的函数「串联」起来。更一般地说，bind 函数是单子的一个关键组成部分。
- 在错误处理的语境下，map 函数把一个单轨函数转换为两轨函数。
- 单子式的组合方式，指用 bind 串联地（in series）组合函数。
- applicative 式的组合方式，指并行地组合结果。

## 添加 Async 效应

在最初的设计中，我们不只使用了错误效应。在管道的大部分地方，我们还使用了 async 效应。一般来说，组合效应可能很棘手，但由于这两个效应经常一起出现，我们将定义一个 asyncResult 计算表达式，与之前定义的 AsyncResult 类型配套。我们不会在这里展示实现，但你可以在本书的代码仓库中找到它。

使用 asyncResult 就像使用 result 一样。例如，validateOrder 的实现如下：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->
    asyncResult {
      let! orderId =
        unvalidatedOrder.OrderId
        |> OrderId.create
        |> Result.mapError ValidationError
        |> AsyncResult.ofResult   // 把 Result 提升为 AsyncResult
      let! customerInfo =
        unvalidatedOrder.CustomerInfo
        |> toCustomerInfo
        |> AsyncResult.ofResult
      let! checkedShippingAddress = // 提取检查过的地址
        unvalidatedOrder.ShippingAddress
        |> toCheckedAddress checkAddressExists
      let! shippingAddress =        // 处理检查过的地址
        checkedShippingAddress
        |> toAddress
        |> AsyncResult.ofResult
      let! billingAddress = ...
      let! lines =
        unvalidatedOrder.Lines
        |> List.map (toValidatedOrderLine checkProductCodeExists)
        |> Result.sequence // 把 Result 的列表转换为单个 Result
        |> AsyncResult.ofResult
      let validatedOrder : ValidatedOrder = {
        OrderId  = orderId
        CustomerInfo = customerInfo
        ShippingAddress = shippingAddress
        BillingAddress = billingAddress
        Lines = lines
      }
      return validatedOrder
    }
```

除了把 result 换成 asyncResult，我们还必须确保现在一切都是 AsyncResult。例如，OrderId.create 的输出只是一个 Result，所以我们必须用辅助函数 AsyncResult.ofResult 把它「提升」为 AsyncResult。

我们还把地址验证拆分成了两部分。原因在于，当我们把所有效应都加回来之后，CheckAddressExists 函数返回的是一个 AsyncResult：

```fsharp
type CheckAddressExists =
  UnvalidatedAddress -> AsyncResult<CheckedAddress,AddressValidationError>
```

这个错误类型与我们的工作流不匹配，所以我们创建一个辅助函数（toCheckedAddress）来处理该结果，把服务专属的错误（AddressValidationError）映射为我们自己的 ValidationError：

```fsharp
/// 调用 checkAddressExists 并把错误转换为 ValidationError
let toCheckedAddress (checkAddress:CheckAddressExists) address =
  address
  |> checkAddress
  |> AsyncResult.mapError (fun addrError ->
    match addrError with
    | AddressNotFound -> ValidationError "Address not found"
    | InvalidFormat -> ValidationError "Address has bad format"
    )
```

toCheckedAddress 函数的输出仍然是在 CheckedAddress 外面包着一层 AsyncResult，所以我们用 let! 把它解包成 checkedAddress 值，然后照常把它传入验证阶段（toAddress）。

把主要的 placeOrder 函数转换为使用 asyncResult 也同样简单：

```fsharp
let placeOrder : PlaceOrder =
  fun unvalidatedOrder ->
    asyncResult {
      let! validatedOrder =
        validateOrder checkProductExists checkAddressExists unvalidatedOrder
        |> AsyncResult.mapError PlaceOrderError.Validation
      let! pricedOrder =
        priceOrder getProductPrice validatedOrder
        |> AsyncResult.ofResult
        |> AsyncResult.mapError PlaceOrderError.Pricing
      let acknowledgmentOption = ...
      let events = ...
      return events
    }
```

管道其余的代码可以用同样的方式转换为使用 asyncResult，但我们不在这里展示。你可以在代码仓库中查看完整实现。

## 小结

现在，融合了类型安全的错误处理方式与 async 效应的管道修订版实现就完成了。上面的 placeOrder 主实现仍然十分清晰，没有丑陋的错误处理代码来打断流程。是的，为了让所有类型正确对齐，我们确实做了一些别扭的转换，但这份额外的努力是值得的：它换来了所有管道组件都能毫无问题地协同工作的信心。
