# 第 5 章　局部变量

*Chapter 5: Local Variables*

到目前为止，你只能编译返回常量表达式的程序。本章将实现局部变量（local variable），让你能编译有趣得多的程序。你的编译器需要支持表达能力更强的文法，才能解析声明变量、给变量赋值和引用变量的 C 程序。它还需要应对变量被错误声明和错误使用的各种情形。为了捕获这些潜在错误，你将添加一个语义分析（semantic analysis）阶段，它在本章开头的示意图中以粗体标出。该阶段验证变量没有在同一作用域（scope）中被重复声明，也没有在声明之前被使用。它还会为每个变量指派一个唯一的标识符，让你能在 TACKY 中安全地引用它。

幸运的是，编译器中的 TACKY 和汇编中间表示（IR）已经支持变量，因为它们已经在用临时变量保存中间结果。这意味着在 TACKY 生成之后，你不需要再改动编译器的任何部分。在进入编译器的各个遍（pass）之前，先定义我们需要支持的语言特性。

## 变量、声明与赋值

要让变量多少有点用处，我们需要实现几个新的语言特性。首先，需要支持变量声明。C 中的每个局部变量都必须先声明才能使用。变量声明由变量的类型、名字，以及一个指定其初始值的可选表达式（称为初始化式，initializer）组成。下面是一个带初始化式的声明：

```c
int a = 2 * 3;
```

下面是一个不带初始化式的声明：

```c
int b;
```

其次，必须支持在表达式中使用变量的值，例如 `b + 1`。和整数常量一样，变量本身就是一个完整的表达式，但它也可以出现在更复杂的逻辑和算术表达式中。

最后，我们需要支持变量赋值。在 C 中，你用赋值运算符（=）更新变量。C 中的变量赋值和加法、减法等一样，是一个表达式。这意味着它会求值出某个结果，你可以在 return 语句中使用这个结果，或把它用作更大表达式的一部分。赋值表达式的结果是被更新后的目标变量的值。例如，表达式 `2 * (a = 5)` 的值是 10：先把值 5 赋给变量 a，再把 a 的新值乘以 2。由于赋值是一个表达式，你可以在 `a = b = c` 这样的表达式中一次完成多个赋值。与我们目前见过的其他二元运算不同，赋值是右结合的，因此 `a = b = c` 等价于 `a = (b = c)`。求值这个表达式时，先完成赋值 `b = c`，然后把这个表达式的结果（即 b 的新值）赋给 a。

变量赋值是我们遇到的第一个带副作用（side effect）的表达式。也就是说，它不只是归约为一个值，还会对执行环境产生某种影响。在 `2 * (a = 5)` 中，子表达式 `a = 5` 有一个值（5），也有一个副作用（更新 a）。大多数时候，我们只关心变量赋值的副作用，而不关心它求值出的值。

只有当某个动作在所讨论的语言构造之外可见时，它才算一个副作用。例如，更新局部变量是赋值表达式的副作用，因为变量的新值在该表达式之外可见。但它不是包含该赋值表达式的函数的副作用，因为这个影响在那个函数之外不可见。另一方面，更新全局变量则既是该表达式的副作用，也是该函数的副作用。

既然我们要实现带副作用的表达式，顺便也应该支持表达式语句（expression statement）：它求值一个表达式，但不使用其结果。给变量赋值的语句，例如

```c
foo = 3 * 3;
```

就是表达式语句。这个表达式的副作用是把值 9 赋给 foo。整个表达式的结果也是 9，但这个结果没有在任何地方被使用；只有更新 foo 的副作用会影响程序。

也可能存在完全没有副作用的表达式语句：

```c
1 + a * 2;
```

你通常不会见到没有副作用的表达式语句，因为它们毫无用处，但它们完全合法。

任何表达式都可以出现在 = 运算符的右边，但只有部分表达式可以出现在它的左边。给变量、数组元素和结构体成员赋值是合理的：

```c
x = 3;
array[2] = 100;
my_struct.member = x * 2;
```

但给常量或逻辑、算术表达式的结果赋值就没有意义：

```c
4 = 5;
foo && bar = 6;
a - 5 = b;
```

可以出现在赋值左侧的表达式称为左值（lvalue）。本章要处理的左值只有变量。更复杂的左值留到第 II 部分再讲。

**未定义行为警报！**

局部变量带来了产生未定义行为（undefined behavior）的新机会，你在第 4 章已经了解过它。例如，除了少数例外，使用未初始化变量的值会导致未定义行为。考虑下面的函数：

```c
int foo(void) {
    int a;
    return a;
}
```

这个函数可能为 a 分配栈空间但不初始化，然后返回那块未初始化内存中碰巧已有的任何值。在这种情况下，尽管 foo 的返回值不可预测，程序其余部分仍会正常运行。但由于 foo 的行为是未定义的，它也可能做出完全不同的事情；调用 foo 可能让程序崩溃，甚至让其他函数在之后行为异常。

再看一个更微妙的例子，它包含两个无顺序的（unsequenced）变量赋值：

```c
int main(void) {
    int a;
    (a = 4) + (a = 5);
    return a;
}
```

记住，像 + 这样的二元运算符的操作数是无顺序的；它们可以按任意顺序求值。看起来这个程序有两种可能的行为：返回 4 或返回 5。但对同一变量执行多次无顺序的赋值是未定义行为，因此这个程序的行为方式没有任何限制。实践中它很可能返回 4 或 5，但这并无保证。

类似地，如果你在无顺序的表达式中既使用变量的值又对它赋值，行为同样是未定义的，例如：

```c
int main(void) {
    int a = 0;
    return (a = 1) + a;
}
```

这些例子并没有穷尽涉及局部变量的所有可能的未定义行为，但它们说明了：看似只影响程序一小部分的问题，如何能让整个程序的行为变为未定义。

既然你已经理解了本章要添加的语言特性，我们来扩展编译器。

## 解析器

和往常一样，我们将更新抽象语法树（AST）和文法来支持本章的新语言构造。我们还会更新优先级爬升（precedence climbing）代码，以正确解析赋值表达式。

### 更新后的 AST 与文法

先扩展 AST 定义，以支持使用、声明变量和给变量赋值。为了在表达式中使用变量，我们给 exp AST 节点添加一个 Var 构造器。由于变量赋值也是表达式，我们还要为 exp 添加一个 Assignment 构造器。清单 5-1 给出了更新后的 exp 定义。

```text
exp = Constant(int)
    | Var(identifier)
    | Unary(unary_operator, exp)
    | Binary(binary_operator, exp, exp)
    | Assignment(exp, exp)
```

*清单 5-1：exp AST 节点的定义，包括 Var 和 Assignment*

Var 节点保存变量名。Assignment 由两部分组成：被更新的左值，以及我们要赋给该左值的表达式。解析程序时，我们允许赋值左侧出现任何表达式；到语义分析阶段，再确保该表达式是合法的左值。我们在语义分析而不是解析时验证左值，是因为后面的章节还需要支持更复杂的左值。

接下来，扩展 statement AST 节点以支持表达式语句。我们添加一个新的 Expression 构造器，它接受单个 exp 节点作为参数。我们还添加一个 Null 构造器来表示空语句（null statement），即没有表达式的表达式语句：

```text
statement = Return(exp) | Expression(exp) | Null
```

空语句没有任何内容，就是一个分号。当文法要求一条语句，而你又不想让这条语句做任何事时，空语句就是占位符。清单 5-2 取自 C 标准第 6.8.3 节第 5 段，说明了你可能为什么需要空语句。

```c
char *s;
/* ... */
while ( ❶ *s++ != '\0')
  ❷ ;
```

*清单 5-2：C 标准中空语句的例子*

在这个例子中，while 循环逐个遍历字符直到遇到空字节，以此找到以空字符结尾的字符串的末尾。循环体不需要做任何事情，因为所有工作都在控制表达式 ❶ 中完成，但完全省略循环体在语法上是非法的。这时就可以使用空语句 ❷。空语句其实和局部变量没有多大关系，但从技术上讲它是一种表达式语句，所以我们在这里一并实现。（实现起来也容易。）

我们还需要一个 AST 节点来表示变量声明：

```text
declaration = Declaration(identifier name, exp? init)
```

声明由一个名字和一个可选的初始化式组成。（exp? 中的问号表示该字段是可选的。）第 II 部分会在声明中加入类型信息，但目前还不需要，因为 int 是唯一可能的类型。

声明是一个独立的 AST 节点，而不是另一种语句，因为声明根本不是语句！概念上，区别在于语句是在程序运行时执行的，而声明只是告诉编译器某个标识符存在、之后可以使用。这一区别在 TACKY 生成时会一目了然：我们会把带初始化式的声明当作普通的变量赋值来处理，而不带初始化式的声明则直接消失。

从解析器的角度看，更具体的区别是：程序中有些位置可以出现语句，但不能出现声明。例如，if 语句的体总是一条语句：

```c
if (a == 2)
    return 4;
```

它不能是声明，因为声明不是语句。所以下面这样是非法的：

```c
if (a == 2)
    int x = 0;
```

听说 if 的体是单条语句可能令人意外，因为 if 的体看起来常常是一列语句和声明，例如：

```c
if (a == 2) {
    int x = 0;
    return x;
}
```

但用花括号包裹的一列语句和声明实际上是一条单独的语句，称为复合语句（compound statement）。我们会在第 7 章实现复合语句；目前的关键点是，我们需要在 AST 中区分语句和声明。

最后，我们需要改变函数体的定义方式，以便解析包含多条声明和多个语句的函数，例如清单 5-3。

```c
int main(void) {
    int a;
    a = 2;
    return a * 2;
}
```

*清单 5-3：包含一条声明和多个语句的程序*

到目前为止，我们把函数体定义为单条语句：

```text
function_definition = Function(identifier name, statement body)
```

现在则需要把它定义为一列语句和声明，它们统称块项（block item）。我们添加一个新的 AST 节点来表示块项：

```text
block_item = S(statement) | D(declaration)
```

然后就可以把函数体表示为一列块项：

```text
function_definition = Function(identifier name, block_item* body)
```

这里的星号表示 body 是一个列表。把以上内容汇总起来，清单 5-4 给出了新的 AST 定义，本章新增的部分以粗体标出。

```text
program = Program(function_definition)
function_definition = Function(identifier name, block_item* body)
block_item = S(statement) | D(declaration)
declaration = Declaration(identifier name, exp? init)
statement = Return(exp) | Expression(exp) | Null
exp = Constant(int)
    | Var(identifier)
    | Unary(unary_operator, exp)
    | Binary(binary_operator, exp, exp)
    | Assignment(exp, exp)
unary_operator = Complement | Negate | Not
binary_operator = Add | Subtract | Multiply | Divide | Remainder | And | Or
                | Equal | NotEqual | LessThan | LessOrEqual
                | GreaterThan | GreaterOrEqual
```

*清单 5-4：带有变量、赋值表达式和表达式语句的抽象语法树*

清单 5-5 给出了更新后的文法。

```text
<program> ::= <function>
<function> ::= "int" <identifier> "(" "void" ")" "{" {<block-item>} "}"
<block-item> ::= <statement> | <declaration>
<declaration> ::= "int" <identifier> ["=" <exp>] ";"
<statement> ::= "return" <exp> ";" | <exp> ";" | ";"
<exp> ::= <factor> | <exp> <binop> <exp>
<factor> ::= <int> | <identifier> | <unop> <factor> | "(" <exp> ")"
<unop> ::= "-" | "~" | "!"
<binop> ::= "-" | "+" | "*" | "/" | "%" | "&&" | "||"
          | "==" | "!=" | "<" | "<=" | ">" | ">=" | "="
<identifier> ::= ? 一个标识符词法单元 ?
<int> ::= ? 一个常量词法单元 ?
```

*清单 5-5：带有变量、赋值表达式和表达式语句的文法*

清单 5-5 引入了几种新的 EBNF 记法。把一组符号用花括号括起来表示它可以重复零次或多次，因此 {<block-item>} 表示一个 <block-item> 符号的列表。注意未加引号的花括号（表示重复）与加了引号的花括号（表示字面 { 和 } 词法单元）之间的区别。在 <function> 的规则中，`"{" {<block-item>} "}"` 表示一个 { 词法单元，随后是一列 <block-item> 符号，最后是一个 } 词法单元。清单 5-6 中的伪代码展示了如何解析函数定义中的块项列表。

```text
parse_function_definition(tokens):
    // 按之前的做法解析到左花括号为止的所有内容……
    --snip--
    function_body = []
    while peek(tokens) != "}":
        next_block_item = parse_block_item(tokens)
        function_body.append(next_block_item)
    take_token(tokens)
    return Function(name, function_body)
```

*清单 5-6：解析块项列表*

不断解析块项，直到遇见右花括号，它标志着函数体的结束。然后你可以从输入流中移除这个花括号，完成函数定义的处理。

正如 EBNF 记法中花括号表示重复，把一组符号用方括号括起来表示它是可选的。我们用 `["=" <exp>]` 表示声明中可选的初始化式。要处理这个可选构造，你的声明解析代码应检查文法规则中的标识符后面跟的是 = 词法单元（说明初始化式存在），还是 ; 词法单元（说明初始化式不存在）。

解析 <block-item> 时，你需要一种办法判断当前块项是语句还是声明。做法是：窥视第一个词法单元；如果是关键字 int，它就是声明，否则就是语句。

清单 5-5 还为 <factor> 符号添加了一条新产生式，对应新的 Var 构造器；同时添加了一个新的二元运算符 = 来表示变量赋值。尽管我们不会用 Binary AST 节点表示变量赋值，但它在文法中和其他二元运算符一模一样。这样我们就可以用已经实现的优先级爬升算法解析变量赋值，只是需要做一些调整。

### 改进的优先级爬升算法

用现有优先级爬升代码解析赋值表达式只有一个问题：= 运算符是右结合的，而我们的代码只能处理左结合运算符。为了唤起记忆，我们再来看一遍优先级爬升伪代码。我们在清单 3-7 见过这个算法的完整版本，这里把它重印为清单 5-7。

```text
parse_exp(tokens, min_prec):
    left = parse_factor(tokens)
    next_token = peek(tokens)
    while next_token is a binary operator and precedence(next_token) >= min_prec:
        operator = parse_binop(tokens)
        right = parse_exp(tokens, ❶ precedence(next_token) + 1)
        left = Binary(operator, left, right)
        next_token = peek(tokens)
    return left
```

*清单 5-7：用优先级爬升解析左结合运算符*

当我们递归调用 parse_exp 时，会把最小优先级设置得比当前运算符的优先级更高 ❶。因此，如果 next_token 是 +，而剩余的 tokens 是 b + 4，递归调用 parse_exp 就只会返回 b，因为 + 无法满足最小优先级要求。我们就是这样得到 `(left + b) + 4` 这样的左结合表达式的。

但如果 next_token 是右结合的，那么在递归调用 parse_exp 时再次遇到同一个词法单元，我们不应该停下来，而应该把它包含进右侧表达式中。为此，需要把右侧的最小优先级设置为当前词法单元的优先级。换句话说，处理 = 这样的右结合词法单元时，递归调用应该是：

```text
right = parse_exp(tokens, precedence(next_token))
```

假设你正在解析 `a = b = c`。你会把左侧解析为因子 a，然后递归调用 parse_exp 处理 b = c。如果这个递归调用的最小优先级是 precedence("=") + 1，它就只会解析下一个因子 b。但如果最小优先级是 precedence("=")，它就会解析整个赋值，返回 b = c 作为表达式的右侧。最终结果是 `a = (b = c)`，这正是我们想要的。

除此之外，解析变量赋值与其他二元表达式的唯一区别是：我们需要构造 Assignment AST 节点，而不是 Binary 节点。清单 5-8 给出了包含这些调整的更新版优先级爬升伪代码。

```text
parse_exp(tokens, min_prec):
    left = parse_factor(tokens)
    next_token = peek(tokens)
    while next_token is a binary operator and precedence(next_token) >= min_prec:
        if next_token is "=":
            take_token(tokens) // 从词法单元列表中移除 "="
            right = parse_exp(tokens, precedence(next_token))
            left = Assignment(left, right)
        else:
            operator = parse_binop(tokens)
            right = parse_exp(tokens, precedence(next_token) + 1)
            left = Binary(operator, left, right)
        next_token = peek(tokens)
    return left
```

*清单 5-8：扩展后的优先级爬升算法*

最后，我们需要把 = 加入优先级表。表 5-1 列出了我为所有二元运算符使用的优先级值，新运算符以粗体标出。它的优先级低于我们目前实现的所有其他运算符。

*表 5-1：二元运算符的优先级值*

| < | 35 |

## 语义分析

到目前为止，我们唯一需要担心的错误是语法错误。只要能解析一个程序，就可以确定其余的编译遍都会成功。现在，一个程序可能在语法上正确，但在语义上无效；换句话说，它可能根本说不通。例如，程序可能给一个不可赋值的表达式赋值：

```c
2 = a * 3; // 错误：不能给常量赋值
```

也可能在同一作用域中两次声明同一个变量：

```c
int a = 3;
int a; // 错误：a 已经被声明过了！
```

还可能在变量声明之前就使用它：

```c
int main(void) {
    a = 4; // 错误：a 尚未声明！
    return a;
}
```

这些例子使用的都是合法语法，但编译它们时应该报错。语义分析阶段负责检测这类错误。这一阶段最终会包含多个不同的遍，分别验证程序的不同方面。本章我们将添加第一个语义分析遍：变量解析（variable resolution）。

变量解析这一遍会跟踪整个程序中哪些变量在作用域内，并通过找到对应的声明来解析每个变量引用。如果程序多次声明同一变量或使用了未声明的变量，它会报告错误。它还会用全局唯一的标识符重命名每个局部变量。例如，它可能把程序

```c
int main(void) {
    int a = 4;
    int b = a + 1;
    a = b - 5;
    return a + b;
}
```

转换成类似这样：

```c
int main(void) {
    int a0 = 4;
    int b1 = a0 + 1;
    a0 = b1 - 5;
    return a0 + b1;
}
```

（当然，这一遍实际上转换的是 AST 而不是源文件，但为了可读性，我用 C 源代码的形式展示这些例子。）

这个转换看起来帮助不大——变量名 a 和 b 本来就是唯一的——但一旦引入多个变量作用域，它就至关重要，因为不同作用域中的不同变量可以同名。例如，我们可能把程序

```c
int main(void) {
    int a = 2;
    if (a < 5) {
        int a = 7;
        return a;
    }
    return a;
}
```

转换为：

```c
int main(void) {
    int a0 = 2;
    if (a0 < 5) {
        int a1 = 7;
        return a1;
    }
    return a0;
}
```

这样就能清楚地看到 a0 和 a1 是两个不同的变量，从而简化后续的编译阶段。

### 变量解析

现在来编写变量解析这一遍。在这一遍中，我们将构造一个从用户定义的变量名到后续阶段所用唯一名字的映射。我们按顺序处理各个块项，边检查错误边替换变量名。遇到变量声明时，我们向映射中添加一个新条目，把该变量名映射到我们生成的唯一名字。之后，看到使用变量的表达式时，我们就把变量名替换为映射中相应的唯一名字。清单 5-9 的伪代码演示了如何解析一条变量声明。

```text
resolve_declaration(Declaration(name, init), variable_map):
  ❶ if name is in variable_map:
        fail("Duplicate variable declaration!")
    unique_name = make_temporary()
  ❷ variable_map.add(name, unique_name)
  ❸ if init is not null:
        init = resolve_exp(init, variable_map)
  ❹ return Declaration(unique_name, init)
```

*清单 5-9：解析一条变量声明*

首先，检查被声明的变量是否已存在于变量映射中 ❶。如果存在，说明它此前在这个函数里已被声明过，这是一次重复声明。这种情况下我们抛出错误。接下来，在变量映射中把用户定义的变量名与一个自动生成的唯一名字关联起来 ❷。

更新变量映射之后，我们处理声明的初始化式（如果有的话）❸。对 resolve_exp 的调用会返回初始化式的一个新副本，其中所有变量都已重命名；如果初始化式使用了未声明的变量，则抛出错误。最后，返回 Declaration 节点的一个副本 ❹，它使用新的自动生成名字代替旧的用户定义名字，同时带上从 resolve_exp 得到的新初始化式。

在 resolve_declaration 中生成的标识符不能与 TACKY 临时变量的名字冲突。如果你用全局计数器生成唯一标识符，请在语义分析和 TACKY 生成两个阶段使用同一个计数器。

这些标识符也不能与函数名或全局变量名冲突。（第 10 章你会看到，全局变量和函数一样保留原始名字，而不像局部变量那样被重命名。）你可以沿用惯用技巧：生成在 C 中语法上不合法的标识符。我建议在自动生成的名字中包含变量的原始名字，便于调试；例如，可以把 a 重命名为 a.0，把 b 重命名为 b.1。

**注意**

你可能已经注意到，上一节的例子使用的是 C 中语法合法的自动生成标识符，比如 a0 和 b1，因为那些例子是以 C 源代码的形式给出的。这些例子中的命名方案在实践中行不通，因为重命名后的变量可能与函数名冲突，也可能彼此冲突。例如，名为 a 和 a1 的两个局部变量都可能被重命名为 a12。

**在变量自己的初始化式中使用该变量**

由于清单 5-9 在处理初始化式之前更新了变量映射，它会欣然接受一个使用了被初始化变量自身的初始化式。看这个例子：

```c
int foo = foo + 1;
```

当我们处理初始化式 foo + 1 时，变量 foo 已在映射中，因此变量解析这一遍不会报错。这与 C 标准一致：变量确实在其自身的初始化式中就已进入作用域。不过，这条声明并不完全合法。它会导致未定义行为，因为在 foo + 1 中使用 foo 时它还未初始化。（记住，编译器不必检测未定义行为，所以这里不报错也没问题。）

在另一些情况下，在变量自己的初始化式中使用该变量是有意义的。例如，在

```c
unsigned int foo = sizeof foo;
```

中，我们仍然在初始化 foo 之前使用它，但我们只关心 foo 的大小，而不是它的值。C 标准的附录 J 指出，当"某个左值……用在需要所指派对象之值的上下文中，而该对象未初始化"时（着重号为本书所加），会产生未定义行为。由于 sizeof 不需要 foo 的值，这条声明没有未定义行为。

解析 return 语句或表达式语句时，只需处理其中的内层表达式，如清单 5-10 所示。

```text
resolve_statement(statement, variable_map):
    match statement with
    | Return(e) -> return Return(resolve_exp(e, variable_map))
    | Expression(e) -> return Expression(resolve_exp(e, variable_map))
    | Null -> return Null
```

*清单 5-10：解析一条语句*

解析表达式时，我们检查表达式中的所有变量使用和赋值是否合法。清单 5-11 展示了具体做法。

```text
resolve_exp(e, variable_map):
    match e with
    | Assignment(left, right) ->
        if left is not a Var node:
            fail("Invalid lvalue!")
        return Assignment( ❶ resolve_exp(left, variable_map), ❷ resolve_exp(right, variable_map))
    | Var(v) ->
        if v is in variable_map:
            return Var( ❸ variable_map.get(v))
        else:
            fail("Undeclared variable!")
    | --snip--
```

*清单 5-11：解析一个表达式*

遇到 Assignment 表达式时，我们检查左侧是合法的左值；目前这要求它必须是 Var。然后递归解析左侧 ❶ 和右侧 ❷ 子表达式。遇到 Var 时，我们把变量名替换为变量映射中的唯一标识符 ❸。如果它不在变量映射中，说明它尚未声明，于是抛出错误。由于赋值的两侧都用 resolve_exp 递归处理，resolve_exp 中的 Var 分支也能处理赋值表达式左侧的变量。

处理其他类型的表达式时，我们用 resolve_exp 递归处理其所有子表达式。最终，变量解析这一遍应返回一个完整的 AST，其中使用自动生成的名字，而非用户定义的变量名。

**typedef 的麻烦**

我们的编译器结构有一个重大局限：先解析整个程序，然后再解析变量。这种做法对本书要实现的 C 子集来说没问题，但要实现完整的语言，你需要在解析程序的同时解析标识符。具体来说，我们的方法无法处理 typedef，它允许你为任意类型声明名字：

```c
typedef int foo;
```

问题在于，某些语句在 foo 这样的标识符指代类型时是一种解析方式，在它指代函数或变量时是另一种解析方式。举个简单的例子：

```c
return (foo) * x;
```

如果 foo 是某个类型的名字，这条语句会解引用 x，把结果转换（cast）为 foo 类型，然后返回它。但如果 foo 是变量，这条语句就会把 foo 与 x 相乘并返回结果。更麻烦的是，类型名和变量名遵循相同的作用域规则。因此，正如同一标识符在程序的不同位置可能指代两个不同的变量，它也可能在一个位置指代变量，在另一个位置指代类型。要判断给定标识符指代的是类型还是变量，你必须在解析程序的同时解析标识符。由于 C 构造的正确解析方式可能依赖于程序中已解析的其他部分，我们说 C 具有上下文有关文法（context-sensitive grammar）。（相比之下，如果每条产生式都可以孤立应用，不必考虑它之前的任何内容，这种语言就具有上下文无关文法（context-free grammar）。）

生产级 C 编译器通常在解析程序期间维护一张符号表（symbol table，类似于我们的变量映射）来处理 typedef。其中一些编译器把符号表中的信息回馈给词法分析器，让后者把类型名解释为与其他标识符不同的词法单元类型；这种做法称为词法分析器 hack（lexer hack）。另一些编译器对所有标识符使用同一种词法单元类型，把区分类型名和其他标识符的工作全部放在解析器中完成。如果你想自己实现 typedef，我推荐后一种做法。

下面简单勾勒如何改造我们的实现来支持 typedef。首先，你需要把所有变量解析逻辑移入解析器。解析程序时应随解析过程传递一个变量映射。解析器应把声明加入映射，并边解析边重命名变量。它还应验证变量在使用前已声明、没有相互冲突的声明，等等。准备好添加 typedef 时，你可以在这张映射中同时跟踪类型名，记录映射中每个条目指代的是类型还是其他实体。你可以在解析期间把类型名转换成唯一的 ID，然后在单独的一遍中把这些名字替换为相应的类型；也可以在解析程序时立即把类型名替换为相应的类型。无论哪种方式，你的解析器都拥有足够的信息来区分类型和其他标识符。后续章节将添加的其他语义分析遍仍应与解析器保持分离。

如果你决定自己实现 typedef，我推荐阅读 Eli Bendersky 的博文 "The Context Sensitivity of C's Grammar, Revisited"，它逐一分析了你需要处理的一些特别棘手的边界情况（https://eli.thegreenplace.net/2011/05/02/the-context-sensitivity-of-cs-grammar-revisited）。

## TACKY 生成

本章完全不需要修改 TACKY IR。我们已经能用 TACKY 的 Var 构造器引用变量，用 Copy 指令给变量赋值。TACKY IR 不包含变量声明，因为它不需要。我们在语义分析阶段已经从变量声明中提取了所需的全部信息，现在可以丢弃它们了。

尽管 TACKY 本身不需要变化，TACKY 生成这一遍却需要：我们要扩展这一遍来处理 AST 的最新增补。首先处理本章添加的两种新表达式，然后处理 AST 的其他增补，包括表达式语句和声明。

### 变量与赋值表达式

我们把 AST 中的每个 Var 转换为 TACKY 中的 Var，保持标识符不变。由于标识符是自动生成的，我们可以保证它不会与 TACKY 程序中的其他标识符冲突。处理 Assignment AST 节点时，我们先发射求值右侧的指令，再发射一条 Copy 指令把结果复制到左侧。清单 5-12 展示了这两种表达式的处理方式。

```text
emit_tacky(e, instructions):
    match e with
    | --snip--
    | Var(v) -> return Var(v)
    | Assignment(Var(v), rhs) ->
        result = emit_tacky(rhs, instructions)
        instructions.append(Copy(result, Var(v)))
        return Var(v)
```

*清单 5-12：把变量和赋值表达式转换为 TACKY*

这种处理变量赋值的方式效率不高：我们常常先求值右侧，把结果存入一个临时变量，再把它复制到变量 v，而不是把结果直接存入 v、彻底省掉临时变量。第 III 部分实现的优化会消除其中一些多余的复制。

### 声明、语句与函数体

现在处理声明。如前所述，我们可以在这个阶段丢弃变量声明；在 TACKY 中，使用变量之前不需要声明。但我们确实需要发射 TACKY 来初始化变量。如果声明包含初始化式，就按普通变量赋值处理；如果声明没有初始化式，则完全不发射任何 TACKY。

我们还需要处理表达式语句和空语句。把表达式语句转换为 TACKY 时，只需处理其内层表达式。这会返回一个新的临时变量，其中保存表达式的结果，但在 TACKY 生成期间我们不会再使用该变量。空语句不会发射任何 TACKY 指令。

最后，处理函数由多个块项（而非单条语句）构成这一事实。我们按顺序处理函数体中的各个块项，为每一个发射 TACKY。假设我们正在编译清单 5-13 中的 C 函数。

```c
int main(void) {
    int b;
    int a = 10 + 1;
    b = a * 2;
    return b;
}
```

*清单 5-13：一个包含变量声明和赋值表达式的 C 函数*

假设在变量解析阶段我们把 a 和 b 重命名为 a.1 和 b.0，并且所有临时变量都采用命名方案 tmp.n，其中 n 是全局计数器的值。那么，我们会为函数体生成清单 5-14 所示的 TACKY 指令。（与上一章的清单 4-6 一样，本清单对 Copy 指令使用 dst = src 的记法，而不是 Copy(src, dst)；类似地，对 Binary 指令使用 dst = src1 + src2 这样的记法，而不是 Binary(Add, src1, src2, dst)。）

```text
tmp.2 = 10 + 1
a.1 = tmp.2
tmp.3 = a.1 * 2
b.0 = tmp.3
Return(b.0)
```

*清单 5-14：用 TACKY 实现清单 5-13*

对于清单 5-13 中 b 的声明，我们不会生成任何 TACKY，因为它不含初始化式。a 的声明会转换为清单 5-14 的前两条指令，它们计算 10 + 1 并把结果复制给 a。表达式语句 b = a * 2; 转换为接下来的两条指令，return 语句则转换为最后的 Return 指令。

至此，你已经知道如何把整个 AST 转换为 TACKY。但事情还没完；还有最后一个边界情况要考虑。

### 没有 return 语句的函数

既然 AST 现在支持不止一种语句，我们可能遇到没有 return 语句的函数，例如清单 5-15。

```c
int main(void) {
    int a = 4;
    a = 0;
}
```

*清单 5-15：没有 return 语句的 main 函数*

调用这个函数会发生什么？C 标准对 main 给出一个答案，对其他任何函数给出另一个答案。（我先忽略返回类型为 void、不返回值的函数，因为我们还没有实现它们。）第 5.1.2.2.3 节说"到达终止 main 函数的 } 时返回值 0"，因此清单 5-15 的代码等价于清单 5-16。

```c
int main(void) {
    int a = 4;
    a = 0;
    return 0;
}
```

*清单 5-16：返回 0 的 main 函数*

其他函数的情况更复杂。根据第 6.9.1 节第 12 段，"除非另有说明，如果到达了终止函数的 }，且调用者使用了函数调用的值，则行为未定义。"这隐含地涵盖两种可能的情形。第一种情形如清单 5-17 所示，调用者试图使用函数的返回值。

```c
#include <stdio.h>

int foo(void) {
    printf("I'm living on the edge, baby!");
    // 没有 return 语句
}

int main(void) {
    return foo(); // 尝试使用 foo 的返回值
}
```

*清单 5-17：函数没有返回任何值时，试图使用它的返回值*

这会导致未定义行为，意味着一切皆有可能；标准对会发生什么不做任何保证。第二种情形如清单 5-18 所示，我们调用了函数但不使用其返回值。

```c
#include <stdio.h>

int foo(void) {
    printf("I'm living on the edge, baby!");
    // 没有 return 语句
}

int main(void) {
    foo();
    return 0;
}
```

*清单 5-18：调用函数但不使用其返回值*

这个程序没有未定义行为；它保证打印 I'm living on the edge, baby! 然后以状态码 0 退出。编译 foo 这样的函数时，我们并不知道它的调用者中是否有人使用其返回值，所以只能假定它属于清单 5-18 那样的程序。具体来说，我们需要在 foo 结束时恢复调用者的栈帧（stack frame）并把控制权交还给调用者。由于我们并不返回任何特定值，EAX 可以随意设置，也可以完全不设置。

处理这两种情形最简单的办法是：在每个函数体末尾额外添加一条 TACKY 指令 Return(Constant(0))。这既为 main 也为清单 5-18 那样的程序给出了正确行为。如果函数本来就以 return 语句结尾，这条额外指令永远不会执行，因此不会改变程序的行为。第 III 部分将介绍如何在不需要时消除这条多余的 Return 指令。

扩展完 TACKY 生成阶段后，就可以测试整个编译器了！由于我们没有改动 TACKY IR，汇编生成和代码发射阶段也不需要改动。

```bash

```

## 附加挑战：复合赋值、自增与自减

既然你的编译器已经支持简单赋值运算符 =，你可以选择实现几个复合赋值运算符（compound assignment operator）：+=、-=、*=、/= 和 %=。如果你在第 3 章实现了按位二元运算符，这里也应该添加对应的复合赋值运算符：&=、|=、^=、<<= 和 >>=。

你还可以添加自增和自减运算符 ++ 和 --。这两个运算符各自有两种截然不同的用法：作为前缀运算符用于 `++a` 这样的表达式，或作为后缀运算符用于 `a++` 这样的表达式。前缀形式的 ++ 或 -- 会把操作数加一或减一，并求值为其新值；后缀形式的 ++ 或 -- 同样把操作数加一或减一，但求值为操作数的原始值。与本章的其他语言构造一样，实现复合赋值、自增和自减运算符不需要改动 TACKY 生成之后的任何部分。

要在测试套件中包含自增和自减运算符的测试用例，运行时请使用 --increment 标志。要包含复合赋值的测试用例，请使用 --compound 标志。只有同时使用 --compound 和 --bitwise 标志时，测试脚本才会运行 |= 这类按位复合赋值运算符的测试用例。

你可以用 --extra-credit 标志一次测试所有额外加分特性。命令

```bash
$ ./test_compiler /path/to/your_compiler --chapter 5 --extra-credit
```

等价于：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 5 --bitwise --compound --increment
```
