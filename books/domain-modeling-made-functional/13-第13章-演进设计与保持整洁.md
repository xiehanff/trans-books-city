# 第 13 章 演进设计与保持整洁

*Chapter 13: Evolving a Design and Keeping It Clean*

我们已经完成了领域模型和实现,但众所周知,这并不是故事的终点。领域模型往往在起步时干净优雅;可随着需求变更(requirement change)不断累积,模型变得杂乱,各个子系统相互纠缠、难以测试。因此,这是我们最后的挑战:能否在演进模型的同时,不让它沦为一个"大泥球"(big ball of mud)?

领域驱动设计从来不是一个静态的、一次性的过程,而是开发者、领域专家和其他相关方之间持续协作的过程。因此,当需求变更时,我们必须始终从重新审视领域模型开始,而不是仅仅修补实现。

本章将考察若干可能的需求变更,并一路跟进:先看它们如何影响我们对领域模型的理解,再去修改实现。此外,我们还会看到,设计中大量使用类型意味着,当模型发生变更时,我们可以高度确信代码不会被意外破坏。

我们将考察四类变更:

- 为工作流添加一个新步骤
- 更改工作流的输入
- 更改一个关键领域类型(订单)的定义,并观察这一变化如何波及整个系统
- 对工作流整体进行改造,以符合业务规则(business rule)

## 需求变更 1:添加运费

第一个需求变更,我们来看如何计算运输和配送费用。假设公司想用一套特殊的计算方式向客户收取运费。我们该如何整合这个新需求?

首先,我们需要一个计算运费的函数。假设这家公司位于加利福尼亚州,那么寄往邻近州的运费是一个价格(比如 5 美元),寄往偏远州的运费是另一个价格(比如 10 美元),而寄往其他国家则是又一个价格(20 美元)。

这个计算的第一版实现如下:

```fsharp
/// 计算订单的运费
let calculateShippingCost validatedOrder =
  let shippingAddress = validatedOrder.ShippingAddress
  if shippingAddress.Country = "US" then
    // 美国境内运输
    match shippingAddress.State with
    | "CA" | "OR" | "AZ" | "NV" ->
      5.0 // 本地
    | _ ->
      10.0 // 偏远
  else
    // 美国境外运输
    20.0
```

遗憾的是,这种针对特殊条件进行多重分支的条件逻辑,既难以理解也难以维护。

### 用活动模式简化业务逻辑

要让逻辑更易维护,一种办法是把以领域为中心的"归类"与实际的定价逻辑分开。F# 有一个称为活动模式(active pattern)[42] 的特性,可以把条件逻辑转换成一组命名的选择,并像对可区分联合类型的分支那样对它们做模式匹配——就好比你为每个选择显式定义了一个可区分联合类型。活动模式非常适合这类归类工作。

要针对这个需求采用活动模式的方案,我们先定义一组模式,分别对应每一种运输类别:

```fsharp
let (|UsLocalState|UsRemoteState|International|) address =
  if address.Country = "US" then
    match address.State with
    | "CA" | "OR" | "AZ" | "NV" ->
      UsLocalState
    | _ ->
      UsRemoteState
  else
    International
```

然后,在运费计算本身中,我们就可以对这些类别做模式匹配:

```fsharp
let calculateShippingCost validatedOrder =
  match validatedOrder.ShippingAddress with
  | UsLocalState -> 5.0
  | UsRemoteState -> 10.0
  | International -> 20.0
```

像这样把归类与业务逻辑分离之后,代码清晰多了,而且活动模式各分支的名称本身就起到了文档的作用。

当然,定义活动模式本身依然比较复杂,但那段代码只做归类,不含任何业务逻辑。如果归类逻辑发生了变化(比如 "UsLocalState" 包含的州不同了),我们只需要修改活动模式,无需改动定价函数。我们干净利落地分离了关注点。

### 在工作流中创建新阶段

接下来,我们要在下单工作流中使用这个运费计算。一种选择是修改定价阶段,把运费逻辑加进去。但那样就得改动本来正常工作的代码并使之更复杂,进而可能引入 bug。与其改动稳定的代码,不如充分发挥组合(composition)的威力,在工作流中新增一个阶段来完成计算并更新 PricedOrder:

```fsharp
type AddShippingInfoToOrder = PricedOrder -> PricedOrderWithShippingInfo
```

这个新阶段随后可以插在 PriceOrder 与下一个阶段 AcknowledgeOrder 之间。

通常,随着设计的演进,我们会发现更多需要记录的细节。例如,客户可能既想知道价格,也想知道运输方式(比如 FedEx 或 UPS)(即便这样描述可能仍过于简化)。因此,我们需要一些新类型来承载这些额外信息:

```fsharp
type ShippingMethod =
  | PostalService
  | Fedex24
  | Fedex48
  | Ups48

type ShippingInfo = {
  ShippingMethod : ShippingMethod
  ShippingCost : Price
  }

type PricedOrderWithShippingMethod = {
  ShippingInfo : ShippingInfo
  PricedOrder : PricedOrder
  }
```

注意,我们现在又创建了一个订单类型——PricedOrderWithShippingInfo,其中包含了新的运输信息。你很可能会觉得这是小题大做,并考虑直接在 PricedOrder 类型中加一个 ShippingInfo 字段了事。但创建一个全新类型有几个好处:

- 如果把 AcknowledgeOrder 步骤改为接受 PricedOrderWithShippingInfo 作为输入,你就不可能把各阶段的顺序弄错。

- 如果我们把 ShippingInfo 作为 PricedOrder 的一个字段,那么在运输计算完成之前,它应该初始化成什么?简单地初始化为一个默认值,可能就是一个等待发作的 bug。

最后一个问题:运费应该如何存储在订单中?是作为头部的一个字段,像这样?

```fsharp
type PricedOrder = {
  ...
  ShippingInfo : ShippingInfo
  OrderTotal : Price
  }
```

还是作为一种新的订单行,像这样?

```fsharp
type PricedOrderLine =
  | Product of PricedOrderProductLine
  | ShippingInfo of ShippingInfo
```

第二种做法意味着订单总额永远可以由各行求和得到,不需要额外的特殊逻辑把头部字段也计入。缺点是可能不小心误加两行 ShippingInfo,而且我们还得操心各行打印顺序的问题。

我们选择把运输信息存储在头部。现在,完成工作流中 AddShippingInfoToOrder 阶段所需的一切都齐备了。我们只需按以下要求编写一个函数:

- 它实现上面定义的 AddShippingInfoToOrder 函数类型。

- 它接受一个用于计算运费的依赖——也就是我们上面设计的 calculateShippingCost 函数。

- 它取得运费,并将其加到 PricedOrder 上,生成一个 PricedOrderWithShippingInfo。

由于所有这些要求都由类型表达,想写出一个错误的实现竟然出奇地难!它大致会是这个样子:

```fsharp
let addShippingInfoToOrder calculateShippingCost : AddShippingInfoToOrder  =
  fun pricedOrder ->
    // 创建运输信息
    let shippingInfo = {
      ShippingMethod = ...
      ShippingCost = calculateShippingCost pricedOrder
      }

    // 将其添加到订单
    {
    OrderId = pricedOrder.OrderId
    ...
    ShippingInfo = shippingInfo
    }
```

然后,它会像这样插入到顶层工作流中:

```fsharp
// 建立各管道阶段的局部版本
// 使用偏应用把依赖"烘焙"进去
let validateOrder unvalidatedOrder = ...
let priceOrder validatedOrder = ...
let addShippingInfo = addShippingInfoToOrder calculateShippingCost

// 用这些新的单参数函数组装管道
unvalidatedOrder
|> validateOrder
|> priceOrder
|> addShippingInfo
...
```

### 向管道添加阶段的其他理由

在这个例子中,我们是因为需求变更才向管道添加了新组件。但像这样增删组件,其实是添加任何一种功能的绝佳方式。只要一个阶段与其他阶段相互隔离,并且符合所需的类型,你就可以放心地添加或删除它。用这种方式可以做到的事情包括:

- 可以添加一个用于运营透明性(operational transparency)的阶段,更容易看清管道内部发生了什么。日志、性能指标、审计等,都可以轻松地以这种方式加入。

- 可以添加一个做授权检查的阶段,若授权失败,就把你送上失败路径,跳过管道的其余部分。

- 甚至可以在组合根(composition root)中,基于配置或来自输入的上下文,动态地增删阶段。

## 需求变更 2:为 VIP 客户提供支持

现在来看一个影响工作流整体输入的变更。假设业务方想支持 VIP 客户——享受特殊待遇的客户,比如免运费,或者免费升级为隔夜送达。

我们该如何建模?

一件我们不该做的事,是在领域中对业务规则的输出建模(比如给订单加一个"免运费"标志)。相反,我们应该存储业务规则的输入("该客户是 VIP"),然后让业务规则基于这个输入去工作。这样一来,当业务规则变化时(它们一定会变!),我们就不必更改领域模型。

我们假定客户的 VIP 状态已经以某种方式与其在网站上的登录相关联,因此在下单领域里不需要由我们自己判定。那么,VIP 状态应该怎么建模?是作为 CustomerInfo 中的一个标志,像这样?

```fsharp
type CustomerInfo = {
  ...
  IsVip : bool
  ...
  }
```

还是建模为一组客户状态中的一种,像这样?

```fsharp
type CustomerStatus =
  | Normal of CustomerInfo
  | Vip of CustomerInfo

type Order = {
  ...
  CustomerStatus : CustomerStatus
  ...
  }
```

把它建模成客户状态的缺点在于,可能还存在与它正交的其他客户状态,比如新客户与回头客、持有会员卡的客户等等。

最佳方案是一种折中:使用一个表示"VIP"这一维度上状态的选择类型,独立于其他客户信息。

```fsharp
type VipStatus =
  | Normal
  | Vip

type CustomerInfo = {
  ...
  VipStatus : VipStatus
  ...
  }
```

以后如果需要其他种类的状态,也可以照同样的方式轻松添加。例如:

```fsharp
type LoyaltyCardId = ...
type LoyaltyCardStatus =
  | None
  | LoyaltyCard of LoyaltyCardId

type CustomerInfo = {
  ...
  VipStatus : VipStatus
  LoyaltyCardStatus : LoyaltyCardStatus
  ...
  }
```

### 为工作流添加新输入

那我们就假定采用新的 VipStatus 字段。一如既往,先更新领域模型,再看看它会把我们引向何处。

我们先为状态定义一个类型,然后把它作为 CustomerInfo 的一个字段:

```fsharp
type VipStatus = ...

type CustomerInfo = {
  ...
  VipStatus : VipStatus
  }
```

不过,这样一改,构造 CustomerInfo 的代码立刻出现编译错误:

```fsharp
No assignment given for field 'VipStatus' of type 'CustomerInfo'
```

这体现了 F# 记录类型的一个优点:构造时必须提供所有字段。一旦新增了字段,在你提供它之前,编译器会一直报错。

那么,我们从哪里能得到 VipStatus?从作为工作流输入的 UnvalidatedCustomerInfo 那里。而它又来自哪里?来自用户填写的订单表单——DTO。因此,我们需要在 UnvalidatedCustomerInfo 和 DTO 中也添加对应字段。不过,对这两者来说,用一个简单的字符串即可,并以 null 表示值缺失。

```fsharp
module Domain =
  type UnvalidatedCustomerInfo = {
    ...
    VipStatus : string
    }

module Dto =
  type CustomerInfo = {
    ...
    VipStatus : string
    }
```

现在,终于可以使用 UnvalidatedCustomerInfo 中的状态字段以及其他所有字段,来构造一个 ValidatedCustomerInfo 了:

```fsharp
let validateCustomerInfo unvalidatedCustomerInfo =
  result {
    ...

    // 新字段
    let! vipStatus =
      VipStatus.create unvalidatedCustomerInfo.VipStatus

    let customerInfo : CustomerInfo = {
      ...
      VipStatus = vipStatus
      }
    return customerInfo
  }
```

### 将免运费规则加入工作流

需求之一是给 VIP 免运费,所以我们需要把这个逻辑加到工作流的某个地方。同样地,与其修改稳定的代码,不如像图所示的那样,直接向管道再添加一段。

*图:在下单管道中,于 AddShippingInfoToOrder 之后、AcknowledgeOrder 之前插入新的 FreeVipShipping 管道段:PricedOrderWithShippingMethod → FreeVipShipping → PricedOrderWithShippingMethod*

和之前一样,我们先定义一个表示新段的类型:

```fsharp
type FreeVipShipping =
  PricedOrderWithShippingMethod -> PricedOrderWithShippingMethod
```

然后创建实现该类型的工作流段,并把它插入工作流。代码就没必要展示了——我想到目前为止你已经知道这是怎么回事了。

## 需求变更 3:支持促销代码

再来看另一个场景:销售团队想做些促销活动,想提供一个促销代码(promotion code),客户下单时提供该代码即可获得折扣价。

与销售团队讨论之后,我们得到了这些新需求:

- 下单时,客户可以选择性地提供一个促销代码。

- 如果提供了代码,某些商品将适用不同(更低)的价格。

- 订单应显示出已应用促销折扣。

这些变更中有一些很容易,但最后一条看似简单的需求,却会在整个领域中激起惊人而深远的连锁反应。

### 在领域模型中加入促销代码

先从新的促销代码字段开始。一如既往,先更新领域模型,看看它会把我们引向何处。

我们先为促销代码定义一个类型,然后把它作为订单的一个可选字段:

```fsharp
type PromotionCode = PromotionCode of string

type ValidatedOrder = {
  ...
  PromotionCode : PromotionCode option
  }
```

PromotionCode 没有特别的验证规则,但用一个专门的类型而不仅仅是个字符串仍是好主意,免得它与领域中的其他字符串混淆。

与前面的 VipStatus 字段一样,新增字段会触发一连串编译错误。此时,我们还需要在 UnvalidatedOrder 和 DTO 中添加对应字段。注意,尽管 ValidatedOrder 中的该字段被显式标记为可选,DTO 中却可以使用非可选的字符串,并假定 null 表示值缺失。

```fsharp
type OrderDto = {
  ...
  PromotionCode : string
  }

type UnvalidatedOrder = {
  ...
  PromotionCode : string
  }
```

### 更改定价逻辑

如果促销代码存在,我们要做一种定价计算;如果不存在,则做另一种。在领域里该如何为此建模?

我们已经用函数类型为定价计算建过模:

```fsharp
type GetProductPrice = ProductCode -> Price
```

但现在,我们需要根据促销代码来提供不同的 GetProductPrice 函数。逻辑如下:

- 如果促销代码存在,提供一个返回与该促销代码关联价格的 GetProductPrice 函数。

- 如果促销代码不存在,提供原来的 GetProductPrice 函数。

于是,我们需要的是一个"工厂"函数:给定可选的促销代码,返回合适的 GetProductPrice 函数,像这样:

```fsharp
type GetPricingFunction = PromotionCode option -> GetProductPrice
```

不过,像这样传入一个 option 有点含糊不清,或许我们应该创建一个更具自说明性的新类型?

```fsharp
type PricingMethod =
  | Standard
  | Promotion of PromotionCode
```

它在逻辑上等价于 option,但用在领域模型中更清晰。ValidatedOrder 类型现在变成了这样:

```fsharp
type ValidatedOrder = {
  ... // 同前
  PricingMethod : PricingMethod
  }
```

GetPricingFunction 则是这样:

```fsharp
type GetPricingFunction = PricingMethod -> GetProductPrice
```

还有一处必须修改。在原设计中,我们向工作流的定价阶段注入的是一个 GetProductPrice 函数。现在,则需要改为向定价步骤注入 GetPricingFunction 这个"工厂"函数:

```fsharp
type PriceOrder =
  GetPricingFunction  // 新的依赖
    -> ValidatedOrder // 输入
    -> PricedOrder    // 输出
```

一旦对领域模型做了这些修改,实现代码中又会冒出一堆编译错误。但是,这些编译器错误是你的朋友!它们会指引你该做些什么来修复实现。这个过程枯燥但直截了当。而一旦你完成修改、实现重新编译通过,你就可以非常有把握地相信一切都能正常工作。

### 实现 GetPricingFunction

我们来快速看一下 GetPricingFunction 可能如何实现。我们假定每个促销代码都关联着一个由 (ProductCode, Price) 对组成的字典。这样的话,实现可能像下面这样:

```fsharp
type GetStandardPriceTable =
  // 无输入 -> 返回标准价格
  unit -> IDictionary<ProductCode,Price>

type GetPromotionPriceTable =
  // 促销码输入 -> 返回该促销码的价格
  PromotionCode -> IDictionary<ProductCode,Price>

let getPricingFunction
  (standardPrices:GetStandardPriceTable)
  (promoPrices:GetPromotionPriceTable)
  : GetPricingFunction =

  // 原始的定价函数
  let getStandardPrice : GetProductPrice =
    // 缓存标准价格
    let standardPrices = standardPrices()
    // 返回查找函数
    fun productCode -> standardPrices.[productCode]

  // 促销定价函数
  let getPromotionPrice promotionCode : GetProductPrice =
    // 缓存促销价格
    let promotionPrices = promoPrices promotionCode
    // 返回查找函数
    fun productCode ->
      match promotionPrices.TryGetValue productCode with
      // 在促销价格中找到了
      | true,price -> price
      // 没有在促销价格中找到
      // 因此使用标准价格
      | false, _ -> getStandardPrice productCode

  // 返回一个符合 GetPricingFunction 的函数
  fun pricingMethod ->
    match pricingMethod with
    | Standard ->
      getStandardPrice
    | Promotion promotionCode ->
      getPromotionPrice promotionCode
```

我们不会逐行详细解释这段代码——它相当自解释。但你可以看到,我们用上了许多最爱的函数式编程技巧:用类型确保代码正确(GetProductPrice),用类型让领域逻辑清晰(PricingMethod 中的各个选择),以函数作为参数(类型为 GetPromotionPriceTable 的 promoPrices),以及以函数作为输出(类型为 GetPricingFunction 的返回值)。

### 在订单行中记录折扣

需求之一是"订单应显示出已应用促销折扣"。这该怎么做?

要回答这个问题,我们需要知道下游系统是否需要了解促销的详情。如果不需要,最简单的选择就是向订单行列表中添加一条"注释行"。注释中不需要任何特别的细节,只要有一段描述折扣的文字即可。

这意味着我们需要更改"订单行"的定义。到目前为止,我们一直假设订单的各行总是引用特定的商品。但现在,我们需要声明:出现了一种不引用商品的新订单行。这是对领域模型的一次修改。我们把 PricedOrderLine 的定义改成反映这一点,将它变为一个选择类型:

```fsharp
type CommentLine = CommentLine of string

type PricedOrderLine =
  | Product of PricedOrderProductLine
  | Comment of CommentLine
```

CommentLine 类型不需要任何特别的验证,或许只需确保字符数不要太多。

如果我们确实需要跟踪比一条注释更多的细节,可以改为定义一个 DiscountApplied 分支,其中包含诸如折扣金额之类的数据。使用 Comment 的好处在于,物流上下文和计费上下文完全不必了解促销的任何信息,这样即使促销逻辑发生变化,它们也不会受到影响。

现在,由于我们把 PricedOrderLine 改成了选择类型,还需要一个新的 PricedOrderProductLine 类型,用来容纳面向商品的那些行的细节,比如价格、数量等等。

最后,很显然,ValidatedOrderLine 与 PricedOrderLine 在设计上如今已分道扬镳。这证明了在领域建模期间保持类型分离是个好主意——你永远不知道什么时候会需要这样的变更;如果当初两者共用同一个类型,我们就无法保持模型的整洁。

要添加注释行,priceOrder 函数需要修改:

- 首先,从 GetPricingFunction "工厂"取得定价函数。

- 接着,对每一行,使用该定价函数设置价格。

- 最后,如果使用了促销代码,就向订单行列表追加一条特殊的注释行。

```fsharp
let toPricedOrderLine orderLine = ...

let priceOrder : PriceOrder =
  fun getPricingFunction validatedOrder ->
    // 从 getPricingFunction "工厂"取得定价函数
    let getProductPrice = getPricingFunction validatedOrder.PricingMethod

    // 为每一行设置价格
    let productOrderLines =
      validatedOrder.OrderLines
      |> List.map (toPricedOrderLine getProductPrice)

    // 如有需要,添加特殊的注释行
    let orderLines =
        match validatedOrder.PricingMethod with
        | Standard ->
          // 保持不变
          productOrderLines
        | Promotion promotion ->
          let promoCode = promotion|> PromotionCode.value
          let commentLine =
            sprintf "Applied promotion %s" promoCode
            |> CommentLine.create
            |> Comment // 提升为 PricedOrderLine
          List.append productOrderLines [commentLine]

    // 返回新订单
    {
        ...
        OrderLines = orderLines
    }
```

### 更复杂的定价方案

在很多情况下,定价方案可能变得更为复杂:多种销售促销、代金券、会员积分方案等等。如果出现了这种情况,多半是一个信号,说明定价需要变成一个独立的限界上下文(bounded context)。还记得关于把限界上下文划分正确的讨论吗?这些就是线索:

- 一套独特的词汇(带有诸如 "BOGOF"(买一送一)[43] 这样的行话)

- 一支专门管理价格的团队

- 仅属于这个上下文的数据(比如历史购买记录和代金券使用情况)

- 具备自治的能力

如果定价是业务的重要组成部分,那么它能够独立演进、并与下单、物流和计费等领域保持解耦,就同样重要。下面这张示意图展示了定价作为一个独立的限界上下文,与下单紧密相关,但如今在逻辑上已相互分离:

*示意图:下单上下文与定价上下文并列。定价上下文内部自行管理标准价格表、各促销代码对应的价格表以及定价逻辑;下单上下文通过调用定价上下文提供的能力获取价格,两者之间只通过明确定义的契约交互。定价上下文与下单、物流、计费等其他上下文在逻辑上分离,可独立演进。*

### 演进限界上下文之间的契约

我们引入了一种新的订单行——CommentLine,物流系统需要了解它,才能正确打印订单。这意味着,发往下游的 OrderPlaced 事件也需要随之修改。

这样一来,我们刚刚破坏了下单上下文与物流上下文之间的契约。

这样可持续吗?也就是说,每次向下单领域添加一个新概念,我们真的都得去修改事件和 DTO、破坏契约吗?当然不是。但就现状而言,我们已经在限界上下文之间引入了耦合,而这绝对不是我们想要的。

正如前面"限界上下文之间的契约"一节所讨论的,解决这个问题的一个好办法是使用"消费者驱动"的契约。在这种方式下,由(下游)消费者决定需要从(上游)生产者那里获得什么,而生产者必须提供这些数据,且仅此而已。

在这种情形下,让我们想一想物流上下文真正需要什么。它不需要价格,不需要运费,也不需要折扣信息。它需要的只是商品清单、每件商品的数量,以及收货地址。所以,我们来设计一个表示这些内容的类型:

```fsharp
type ShippableOrderLine = {
  ProductCode : ProductCode
  Quantity : float
  }

type ShippableOrderPlaced = {
  OrderId : OrderId
  ShippingAddress : Address
  ShipmentLines : ShippableOrderLine list
  }
```

这比原来的 OrderPlaced 事件类型简单多了。而且,正因为数据更少,当下单领域发生变化时,它也不太可能随之改变。

有了这个新事件类型,我们应该重新设计下单工作流的 PlaceOrderEvent 输出。现在我们有:

- 一个用于记录日志并发送到客服上下文的 AcknowledgmentSent

- 一个发送到物流上下文的 ShippableOrderPlaced

- 一个发送到计费上下文的 BillableOrderPlaced

```fsharp
type PlaceOrderEvent =
  | ShippableOrderPlaced of ShippableOrderPlaced
  | BillableOrderPlaced of BillableOrderPlaced
  | AcknowledgmentSent  of OrderAcknowledgmentSent
```

### 打印订单

那么,打印订单怎么办?当订单打包完毕、准备发货时,会打印一份原始订单的副本放进包裹里。我们既然有意减少了物流部门可获得的信息,它又该如何把订单打印出来?

问题的关键在于意识到:物流部门只需要某种可以打印的东西,但它并不真正关心内容是什么。换句话说,下单上下文可以向物流部门提供一份 PDF 或 HTML 文档,然后让它去打印这份文档。

这个文档可以作为二进制大对象(blob)放进上面的 ShippableOrderPlaced 类型中;我们也可以把一份 PDF 转储到共享存储中,让物流上下文通过 OrderId 去访问它。

## 需求变更 4:添加营业时间约束

到目前为止,我们看到的都是新增数据和行为。现在来看一种新的情况:为工作流的使用方式添加新的约束。新的业务规则是:

- 只能在营业时间内接受订单。

出于某种原因,业务方决定系统只应在营业时间内可用(也许是基于这样一种假设:凌晨四点还在访问网站的人,多半不是真实的客户)。那么,我们该如何实现这条规则?

我们可以用一招以前见过的技巧:创建一个"适配器"函数。这一次,我们要创建一个"仅营业时间"函数,它接受任意函数作为输入,输出一个行为完全相同的"包装"或"代理"函数,只是在营业时间之外被调用时会抛出错误。

转换后的函数与原函数的输入输出完全相同,因此可以在任何原本使用原函数的地方使用它。下面就是这个转换函数的代码:

```fsharp
/// 判断是否为营业时间
let isBusinessHour hour =
  hour >= 9 && hour <= 17

/// 转换器
let businessHoursOnly getHour onError onSuccess =
  let hour = getHour()
  if isBusinessHour hour then
    onSuccess()
  else
    onError()
```

可以看到,这是完全通用的代码:

- onError 参数用于处理营业时间之外的情形。

- onSuccess 参数用于处理营业时间之内的情形。

- 一天中的小时数由 getHour 函数参数确定,而不是硬编码的。这让我们可以注入一个假(dummy)函数,方便进行单元测试。

在我们的场景中,原工作流接受一个 UnvalidatedOrder,并返回一个错误类型为 PlaceOrderError 的 Result。因此,我们传入的 onError 也必须返回同类型的 Result,所以我们给 PlaceOrderError 类型添加一个 OutsideBusinessHours 分支:

```fsharp
type PlaceOrderError =
  | Validation of ValidationError
  ...
  | OutsideBusinessHours  // 新增!
```

现在,改造原始下单工作流所需的一切都齐备了:

```fsharp
let placeOrder unvalidatedOrder =
    ...

let placeOrderInBusinessHours unvalidatedOrder =
  let onError() =
    Error OutsideBusinessHours
  let onSuccess() =
    placeOrder unvalidatedOrder
  let getHour() = DateTime.Now.Hour
  businessHoursOnly getHour onError onSuccess
```

最后,在应用程序的顶层(组合根),我们用新的 placeOrderInBusinessHours 函数替换原来的 placeOrder 函数。由于它的输入输出与原函数完全相同,两者完全兼容。

## 处理更多的需求变更

显然,对于可能被提出的各类变更,我们这里只是浅尝辄止。下面是另外一些值得思考的变更,以及可能的应对方式:

- VIP 只应在美国境内享受免运费。为支持这一点,我们只需要修改工作流中 freeVipShipping 段的代码。现在应该很清楚了:拥有大量像这样的小段,确实有助于把复杂性控制在可控范围内。

- 客户应能把订单拆分成多次发货。这种情况下,需要一些执行拆分的逻辑(工作流中的一个新段)。从领域建模的角度看,唯一的变更在于:工作流的输出包含一个要发给物流上下文的发货清单,而不是单一发货。

- 客户应能查看订单的状态:是否已发货、是否已全额支付,等等。这条比较棘手,因为关于订单状态的知识分散在多个上下文中:物流上下文知道发货状态,计费上下文知道计费状态,等等。最佳做法可能是创建一个新上下文(或许叫"客户服务"),专门处理这类客户询问。它可以订阅其他上下文发出的事件,并据此更新状态。任何关于状态的查询都将直接发往这个上下文。

## 本章小结

在本章中,我们随着四个需求变更演进了设计,看到了类型驱动的领域建模,以及用函数组装工作流的组合式方法所带来的好处。

类型驱动的设计意味着,当我们在领域类型中新增一个字段时(比如给 ValidatedOrder 添加 VipStatus),立刻就会得到编译错误,迫使我们明确数据从何而来。这又引导我们去修改其他类型,如此往复,直到所有编译错误消失。

同样地,在促销代码的例子中,当我们把其中一个依赖从 GetProductPrice 换成更复杂的 GetPricingFunction 时,也触发了一批编译错误。但当代码修复完毕、编译错误消失之后,我们就可以相当确信实现又能正确工作了。

我们还看到了使用函数组合构建工作流的优势。我们可以轻松地向工作流添加新段,而让其他段保持原封不动。当然,不修改既有代码,就意味着引入 bug 的机会更少。

最后,在"营业时间"的例子中,我们看到,多亏了"函数类型即接口",我们才能在保持与现有代码即插即用兼容的同时,以强大的方式变换整个函数。

## 全书总结

本书涵盖了很多内容,从限界上下文这样的高层抽象,一路讲到序列化格式的细枝末节。

许多重要主题我们没能来得及讨论:Web 服务、安全性、运营透明性等等。不过,在研读本书的过程中,我希望你已经掌握了些技巧与能力,可以应用于任何设计问题。

我们来回顾一下书中谈到的最重要的一些实践:

- 在开始低层设计之前,我们应致力于建立对领域的深刻而共享的理解。我们学到一些发现技巧(事件风暴)和沟通技巧(使用统一语言),它们能在这个过程中提供巨大帮助。

- 我们应确保将解空间划分为自治、解耦、可独立演进的限界上下文,并确保每个工作流都表示为一条带有显式输入和输出的独立管道。

- 在编写任何代码之前,我们应尝试用基于类型的表示法来捕获需求,既捕获领域中的名词,也捕获动词。如前所见,名词几乎总能用代数类型系统来表示,而动词则用函数来表示。

- 我们应尽可能在类型系统中捕获重要的约束和业务规则。我们的座右铭是"让非法状态不可表示"(make illegal states unrepresentable)。

- 我们还应尽量把函数设计成"纯"(pure)且"完全"(total)的,使得每个可能的输入都有明确记载的输出(没有异常),并且所有行为都完全可预测(没有隐藏的依赖)。

在为下单工作流走完这一整套流程之后,我们得到了一组详尽的类型,并用它们来指导和约束实现。

然后,在实现过程中,我们反复使用了这样一些重要的函数式编程技巧:

- 仅用小函数的组合来构建完整的工作流

- 每当出现依赖,甚至只是某个我们想推迟的决定,就把它参数化为函数的参数

- 使用偏应用把依赖"烘焙"进函数,使函数更容易被组装,并隐藏不需要暴露的实现细节

- 创建能把其他函数变换成各种形态的特殊函数。特别是,我们认识了 bind——那块用来把返回错误的函数转换成易于组合的双轨(two-track)函数的"适配器积木"

- 通过把彼此不同的类型"提升"(lift)到公共类型,来解决类型不匹配的问题

在本书中,我旨在让你相信:函数式编程与领域建模是天作之合。我希望我做到了,也希望你现在有信心走出书本,把所学应用到自己的应用程序中去。
