# 第 18 章　结构体

*Chapter 18: Structures*

本章中，你将添加最后一项语言特性：结构体（structure）。你还将实现访问结构体成员的 `.` 和 `->` 运算符。作为第 II 部分一个恰如其分的收尾，你将运用前面各章学到的许多技能、概念和技术。在标识符解析（identifier resolution）遍中，你将把结构体标签（tag）与函数名、变量名一起解析。在类型检查器中，你将把结构体定义记录到类型表（type table）中，就像你已经在符号表中记录函数声明和变量声明一样。在 TACKY 生成阶段，你将在第 14 章用于处理解引用指针及其他对象上的操作的策略基础上继续构建。而在后端，你将实现 System V 调用约定（calling convention）中规定如何把结构体作为函数参数和返回值传递的那一部分。由于联合体（union）与结构体是近亲，你可能也想实现它们。我们不会详细讲解联合体，但你可以把它作为一个附加挑战特性来实现。

## 声明结构体类型

你必须先声明一个结构体类型，然后才能使用它。结构体类型声明有两种。第一种如清单 18-1 所示，指定了结构体的成员。

```c
struct complete_struct {
    long member1;
    double member2;
};
```

*清单 18-1：一个完整的结构体类型声明*

这个清单声明了一个完整的（complete）结构体类型，它有两个成员（member）：一个 long 和一个 double。标识符 complete_struct 是这个类型的标签，我们之后可以在程序中用它来指定这个类型。完整的结构体类型必须至少有一个成员，因此声明一个成员列表为空的结构体类型是非法的：

```c
struct empty {};
```

第二种结构体类型声明如清单 18-2 所示，它指定了结构体的标签，但没有指定它的成员。

```c
struct incomplete_struct;
```

*清单 18-2：一个不完整的结构体类型声明*

清单 18-2 声明了一个不完整的（incomplete）结构体类型。正如你在上一章学到的，不完整类型只能在某些有限的场合使用。例如，你不能定义一个 struct incomplete_struct 类型的变量，但你可以定义一个指向 struct incomplete_struct 的指针。（这是因为我们知道一个指针需要多少内存，却不知道这个结构体需要多少内存。）我们会说，不带成员列表的结构体声明声明（declare）了一个类型，而带成员列表的结构体声明既声明又定义（define）了一个类型。这与你在 C 标准和其他地方看到的术语有所不同；特别是，当人们谈论“类型定义”时，他们通常指的是用 typedef 关键字引入的别名。

结构体标签只在声明它的作用域内可见，就像函数名和变量名一样。如果一个结构体标签是在文件作用域声明的，它从声明处直到文件末尾都可见。如果它是在块作用域声明的，它直到该块结束都可见。如果两个带有相同标签的结构体类型声明出现在同一个作用域中，它们总是声明同一个类型；如果它们出现在不同的作用域中，它们声明的是不同的类型。（类型声明没有链接（linkage），所以你不能对它们使用 static 或 extern 关键字。）你可以多次声明同一个结构体类型，但不能多次定义它。

一旦结构体类型的定义进入了作用域，它就是完整的了，如清单 18-3 所示。

```c
❶ struct s;

struct s *ptr = 0;

struct s {
    int a;
    int b;
}; ❷

❸ struct s x = {0,0};
```

*清单 18-3：先声明一个不完整类型，再补全它*

在 ❶ 和 ❷ 之间，struct s 是一个不完整类型。在程序中这两点之间定义一个 struct s 类型的变量是不合法的，但定义 ptr——一个指向 struct s 的指针——是合法的。在指定成员列表的那条类型声明结束 ❷ 之后，struct s 成了一个完整类型，因此用这个类型定义变量 ❸ 是合法的。

当同一个结构体标签在两个不同的作用域中声明时，其中一个可以遮蔽（shadow）另一个，如清单 18-4 所示。

```c
#include <stdio.h>

❶ struct s {
    int a;
};

int main(void) {
    printf("Outer struct size: %lu\n", ❷ sizeof (struct s));

  ❸ struct s {
        long l;
    };

    printf("Inner struct size: %lu\n", ❹ sizeof (struct s));
    return 0;
}
```

*清单 18-4：一个结构体类型遮蔽另一个*

首先，我们在文件作用域定义一个 struct s 类型 ❶。它的大小是 4 字节，因为它只包含一个 int。main 中第一个 sizeof 表达式引用的是这个类型 ❷。接着，我们在块作用域定义另一个 struct s 类型 ❸，遮蔽了第一个类型。这个类型只包含一个 long，所以它的大小是 8 字节。struct s 的这两个定义并不冲突，因为它们出现在不同的作用域中。在第二个 sizeof 表达式 ❹ 中，说明符 struct s 引用的是内层作用域中定义的那个 8 字节结构体类型。运行这个程序会得到以下输出：

```bash
$ ./listing_18_4
Outer struct size: 4
Inner struct size: 8
```

即使一个结构体的标签被遮蔽了，它的成员仍然可见。考虑清单 18-5。

```c
int main(void) {

  ❶ struct shadow {
        int x;
    };
    struct shadow outer;
    outer.x = 2;
    {
      ❷ struct shadow {
            int y;
        };
        struct shadow inner;
        inner.y = 3;
      ❸ return outer.x + inner.y;
    }
}
```

*清单 18-5：使用带被遮蔽结构体类型的变量*

在这个清单中，我们首先声明一个结构体类型 struct shadow ❶。然后我们用这个类型定义一个变量 outer。在内层作用域中，我们声明另一个带相同标签的结构体类型 ❷，它遮蔽了外层的声明。接着我们用这个新类型声明一个变量 inner。在 return 语句中，我们仍然可以访问这两个变量的成员 ❸。即使在内层作用域中，编译器也知道最初的 struct shadow 类型，并且它仍然知道 outer 属于那个类型；我们只是无法再用这个被遮蔽的标签来指定那个类型而已。

为了把所有结构体类型理清楚，我们将像处理变量名一样处理结构体标签：在标识符解析遍中，我们会把每个用户定义的标签替换为一个唯一的标识符。

### 结构体成员声明

结构体的成员可以具有任何完整类型，包括 int 这样的基本类型，以及数组、指针或其他结构体这样的派生类型。但是，用一个不完整类型声明结构体成员是非法的，因为那样就无法确定整个结构体的大小。这正如 C 标准 6.7.2.1 节第 3 段所说，意味着“结构体不得包含其自身的实例”。也就是说，一个 struct s 不能包含 struct s 类型的成员。另一方面，结构体可以包含指向自身的指针，因为指针类型总是完整的。最经典的例子如清单 18-6 所示，是链表中的一个节点，它保存一个值和一个指向下一个列表项的指针。

```c
struct linked_list_node ❶ {
    int val;
    struct linked_list_node *next;
}; ❷
```

*清单 18-6：一个包含指向自身指针的结构体类型定义*

在 ❶ 之后，struct linked_list_node 作为一个不完整类型可见，因此我们可以把成员 next 声明为指向这个类型的指针。在 ❷ 之后，这个类型就是完整的了。

把函数声明为结构体成员也是非法的。结构体可以保存函数指针——和其他任何指针一样，函数指针是完整类型——但我们不支持函数指针，所以这一点对我们来说无关紧要。

### 标签与成员的名字空间

结构体标签与函数、变量处于不同的名字空间（namespace）。这意味着同一个标识符既可以作为标签，又可以作为函数名或变量名，两个标识符谁也不会遮蔽或冲突谁。例如，在同一个作用域中声明类型 struct s 和变量 s 是完全合法的。之所以能维持这些独立的名字空间，是因为 struct 关键字告诉编译器某个特定的标识符是一个结构体标签。

类似地，每个结构体的成员列表本身就是自己的名字空间。一个结构体成员可以与任何函数、变量或结构体类型同名，包括与包含它的那个结构体类型同名，就像下面这个例子：

```c
struct s {
    int s;
};
```

不同结构体中的成员同名也是合法的：

```c
struct s1 {
    int x;
};

struct s2 {
    int x;
};
```

当标识符 x 出现在像 var->x 这样的表达式中时，编译器可以根据上下文判断它指的是 s1 中的成员、s2 中的成员，还是某个函数或变量。毫不意外，同一个结构体的两个成员同名是非法的。

### 我们不实现的结构体类型声明

C 语法不区分结构体类型说明符和类型声明，因此你可以在声明一个新结构体类型的同时，在某个更大的构造中使用这个结构体类型。例如在清单 18-7 中，一条声明同时定义了一个新的结构体类型 struct s 和一个 struct s 类型的变量 x。

```c
struct s {
    int member;
} x;
```

*清单 18-7：在同一条声明中定义并指定一个结构体类型*

为了简化解析和语义分析，我们要求每条声明恰好声明一个函数、变量或类型。我们不支持像清单 18-7 那样同时声明一个新类型和某种其他实体的声明。对不完整类型也是如此。C 标准允许你隐式声明一个不完整的结构体类型，只需指定它即可：

```c
struct s *f(void);
```

即使 struct s 还没有被声明，这条声明也是合法的：它同时把 struct s 声明为一个不完整类型，并声明了一个返回指向 struct s 的指针的函数。但我们的实现不允许这样做。相反，我们要求先单独声明 struct s：

```c
struct s;
struct s *f(void);
```

要求类型在使用之前先声明，还意味着你不能把一个结构体声明嵌套在另一个里面，比如清单 18-8 中那样。

```c
struct outer {
    struct inner {
        int a;
        long l;
    } i;
    double d;
};
```

*清单 18-8：在同一条声明中声明一个内层结构体类型并用该类型声明成员 i*

我们还会施加其他一些限制。我们会拒绝不带标签的结构体声明和不带名字的结构体成员，尽管 C 标准允许它们。我们也不支持位域（bit-field）成员——位域使我们能够寻址结构体中的单个位。

## 操作结构体

你可以用 `.` 运算符访问结构体的成员：

```c
struct s var;
--snip--
long l = var.member1;
```

如果你有一个指向结构体的指针，你可以用 `->` 运算符访问结构体的成员。继续用同一个例子：

```c
struct s *ptr = &var;
long l2 = ptr->member1;
```

`.` 和 `->` 运算符只能应用于完整的结构体类型。你不能访问不完整结构体类型的成员，因为这些成员还没有被定义。

结构体是聚合类型（aggregate type），就像数组一样。但结构体不像数组那样退化（decay）为指针，所以你可以用几种数组做不到的方式使用它们。例如，你可以把它们作为函数参数和返回值传递。你也可以给它们赋值，如清单 18-9 所示。

```c
struct s foo;
struct s bar;
--snip--
foo = bar;
```

*清单 18-9：给结构体赋值*

你也可以给结构体的单个成员赋值，只要它们是左值。用 `->` 运算符指定的结构体成员总是左值：

```c
ptr->member2 = 2.0;
```

回想一下，所有被解引用的指针都是左值。`->` 运算符产生一个被解引用的指针，就像 `*` 和 `[]` 运算符一样，因此同样的规则也适用。

如果一个结构体是左值，你用 `.` 运算符访问的它的任何成员也都是左值。如果结构体不是左值，它的成员也不是。因此，这个赋值表达式是合法的：

```c
var.member2 = 2.0;
```

但是，由于函数调用的结果不是左值，这是非法的：

```c
return_struct().member2 = 2.0;
```

结构体还可以出现在少数几种其他表达式中，基本上都在你的意料之中。它们可以出现在条件表达式的分支中，只要两个分支具有相同的结构体类型。你可以用 sizeof 求它们的大小，也可以把它们强制转换为 void，但不能在结构体类型与其他类型之间进行其他任何强制转换。而如果一个结构体或结构体成员是左值，你就可以取它的地址。

初始化结构体有两种方式。你可以用同一结构体类型的表达式来初始化它：

```c
struct s return_struct(void);
struct s var = return_struct();
```

或者，你可以用复合初始化器（compound initializer）逐个初始化每个成员，如清单 18-10 所示。

```c
struct example {
    int member1;
    double member2;
    char array[3];
};

struct example var = {1, 2.0, ❶ {'a', 'b', 'c'}};
```

*清单 18-10：用复合初始化器初始化结构体*

复合初始化器按顺序初始化结构体的成员。清单 18-10 中的初始化器用值 1 初始化 member1，用 2.0 初始化 member2。内层的复合初始化器初始化 array 中的三个数组元素 ❶。注意，数组和结构体的复合初始化器语法完全相同。（指定初始化器（designated initializer）用于初始化聚合对象中的特定子对象，它针对数组元素和结构体成员的语法各不相同，但我们不会实现指定初始化器。）通过嵌套复合初始化器，你可以初始化结构体数组、包含其他结构体的结构体等等。

## 结构体在内存中的布局

到这里，我们已经相当清楚结构体类型在源代码中是如何工作的了。现在让我们看看在运行时它们在内存中是如何布局的。这一布局一部分由 C 标准规定，一部分由 System V ABI 规定。按照 ABI 的精确规定来布局结构体非常重要，这样我们编译出的代码才能与使用结构体的其他代码互操作。

结构体的成员在内存中的排列顺序与原始结构体声明中的顺序相同。第一个成员的地址必须与结构体整体的地址相同；你总可以把指向结构体的指针转换成指向其第一个成员的指针，反之亦然。每个后续成员将存储在具有正确对齐（alignment）的最早空闲地址处。让我们以清单 18-10 中的 struct example 类型为例。清单 18-11 重新给出了 struct example 的定义。

```c
struct example {
    int member1;
    double member2;
    char array[3];
};
```

*清单 18-11：一个包含多个对齐要求不同的成员的结构体类型*

第一个成员必须从结构体的最开头开始。因为 member1 是一个 int，它占据结构体的前 4 个字节。结构体中的字节通常从零开始编号，所以我们说 member1 占据第 0 到第 3 字节。因此，下一个未使用的空间在第 4 字节。但 member2 是一个 double，它是 8 字节对齐的；它的起始地址必须是 8 的倍数。于是，member2 将存储在第 8 到第 15 字节。我们说 member2 相对于结构体开头的字段偏移（field offset）是 8 字节。在 member1 和 member2 之间，即第 4 到第 7 字节，有 4 字节的填充（padding）。

最后一个成员 array 占 3 个字节，对齐为 1 字节。由于不需要任何填充来正确对齐它，我们把它紧挨在 member2 之后存储，即第 16 到第 18 字节。

在结构体末尾、array 之后，我们还需要填充。根据 System V ABI，类型的大小必须是它的对齐的倍数。ABI 还规定，结构体的对齐与其对齐要求最严格的成员相同。struct example 中对齐要求最严格的成员是 double 类型的 member2。因此，整个结构体必须 8 字节对齐，它的大小必须是 8 的倍数。struct example 的三个成员以及它们之间的填充共占 19 字节。我们将在结构体末尾添加 5 字节填充，使其总大小达到 24 字节。图 18-1 展示了整个结构体的布局。

```text
struct example（总大小 24 字节，对齐 8 字节）

  偏移 0–3：    member1 (int)
  偏移 4–7：    填充（4 字节）
  偏移 8–15：   member2 (double)
  偏移 16–18：  array (char[3])
  偏移 19–23：  填充（5 字节）
```

*图 18-1：结构体在内存中的布局*

成员之间的填充保证了每个成员都会落在正确对齐的内存地址上。如果整个结构体的起始地址是 8 的倍数，而 member2 相对于结构体开头的偏移也是 8 的倍数，我们就知道 member2 的运行时内存地址也将是 8 的倍数。结构体末尾的填充保证了结构体数组中的每个元素都会有正确的对齐；如果 struct example 对象数组的第一个元素是 8 字节对齐的，且其总大小为 24 字节，那么后续每个元素也都将 8 字节对齐。

现在你已经理解了如何在 C 中使用结构体以及它们在内存中如何布局，让我们开始动手实现它们。

## 词法分析器

本章中你将添加三个新词法单元：

- **struct** —— 一个关键字，表示结构体类型说明符
- **.** —— 句点，即结构体成员访问运算符
- **->** —— 箭头，即通过指针访问结构体成员的运算符

请记住，句点既可以是结构体成员访问运算符，也可以是浮点常量的一部分。只有当句点后面跟的是非数字字符时，我们才把它识别为一个 `.` 词法单元。如果句点后面跟的是数字，那它要么是某个浮点常量的开头，要么就是非法的。例如，如果词法分析器看到输入 .100u，它应当尝试把这整个输入解析为一个常量。由于它不匹配任何一种常量的正则表达式，词法分析器随后会抛出错误。它不应当把它词法分析为一个 `.` 词法单元再跟一个常量 100u。

**测试词法分析器**

要测试词法分析器，运行：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 18 --stage lex
```

词法分析器应当拒绝 tests/chapter_18/invalid_lex 中的测试程序；这些程序中包括后面跟数字、但不属于合法浮点常量的 `.` 字符。词法分析器应当接受本章所有其他的测试程序。

## 解析器

本章我们将向 AST 添加几个新构造：结构体声明、结构体类型说明符，以及两个新的结构体运算符。清单 18-12 给出了结构体声明的 AST 定义。

```text
struct_declaration = (identifier tag, member_declaration* members)
member_declaration = (identifier member_name, type member_type)
```

*清单 18-12：在 AST 中表示结构体声明*

struct_declaration 由一个标签和一个成员列表组成。要表示一个不完整的结构体类型声明，我们把成员列表留空。（记住，完整的结构体类型必须至少有一个成员。）我们用 member_declaration 表示每个成员，它包括一个成员名和一个类型。

接下来，我们扩展 declaration AST 节点，使它既支持函数声明和变量声明，也支持结构体类型声明：

```text
declaration = --snip-- | StructDecl(struct_declaration)
```

我们还要扩展 type AST 节点，使它包含像 struct s 这样的结构体类型说明符：

```text
type = --snip-- | Structure(identifier tag)
```

最后，我们添加两个新表达式：`.` 和 `->` 运算符，它们分别被称为结构体成员运算符（structure member operator）和结构体指针运算符（structure pointer operator）。我们使用更简洁的名字 Dot 和 Arrow：

```text
exp = --snip--
    | Dot(exp structure, identifier member)
    | Arrow(exp pointer, identifier member)
```

这两个运算符都接受一个表达式作为第一个操作数，接受一个结构体成员的名字作为第二个操作数。清单 18-13 给出了完整的 AST，本章的改动以粗体标出。

```text
program = Program(declaration*)
declaration = FunDecl(function_declaration) | VarDecl(variable_declaration)
            | StructDecl(struct_declaration)
```

<struct-declaration> 可以包含一个花括号括起来的结构体成员列表 ❶。这个成员列表是可选的，但如果有花括号，其中必须至少有一个成员。

结构体成员声明的形式与变量声明相同；它包括一列类型说明符和一个声明器，并以分号结尾。但与变量声明不同的是，结构体成员不能有初始化器或存储类。我们要施加一条文法中没有体现的语法要求：解析器应当拒绝结构体成员声明中的函数声明器，尽管 <member-declaration> 文法规则允许它们。例如，解析器应当拒绝这条声明：

```c
struct contains_function {
    int foo(void);
};
```

结构体类型说明符由两个词法单元组成：struct 关键字和一个指定结构体标签的标识符词法单元。这个说明符不能与其他类型说明符组合，但可以被指针、数组或函数声明器修饰。

新的 `.` 和 `->` 运算符是后缀运算符，就像我们在第 15 章添加的下标运算符一样。这三个后缀运算符的优先级都比任何前缀运算符高。新的 <postfix-op> 符号包含全部三个运算符，这确保它们都按正确的优先级解析。

## 语义分析

我们已经有一段时间没有对标识符解析遍做过实质性改动了。现在，我们要让它把结构体标签与函数名、变量名一起解析。这一遍将为每个结构体类型分配一个唯一的 ID，替换其最初由用户定义的标签。如果程序试图在声明某个结构体类型之前指定它，这一遍还会抛出错误。

在类型检查器中，我们将引入一个新表来跟踪结构体定义。在对初始化器、成员访问运算符以及其他针对结构体的操作做类型检查时，我们将引用这些定义。在后面的阶段中，我们还会用它们来生成 TACKY 和汇编。

### 解析结构体标签

我们来看看在标识符解析期间如何处理结构体标签。我们重命名这些标签的方式与重命名局部变量的方式基本相同。我们将维护一个从用户定义标签到唯一标识符的映射。当我们发现一个新结构体类型的声明时，就生成一个新标识符并把它加入映射。而当我们遇到一个结构体类型说明符时，就用映射中相应的唯一标识符替换它。因为结构体标签存在于与函数和变量分开的名字空间中，我们将在一个单独的映射中跟踪它们。

#### 定义结构体标签映射

在现有的标识符映射中，我们为每个用户定义的函数名或变量名跟踪三件事：我们将用来替换它的唯一标识符、它是否具有链接，以及它是否是在当前作用域中定义的。在结构体标签映射中，我们将跟踪每个标签的唯一标识符以及它是否是在当前作用域中定义的，但不跟踪链接，因为这个概念不适用于类型。动手定义这个数据结构吧。然后，我们再看如何在类型说明符和声明中解析标签。

#### 解析类型说明符

清单 18-15 展示了如何解析一个类型说明符。

```text
resolve_type(type_specifier, structure_map):
    match type_specifier with
    | Structure(tag) ->
        if tag is in structure_map:
            unique_tag = structure_map.get(tag).new_tag
          ❶ return Structure(unique_tag)
        else:
          ❷ fail("Specified an undeclared structure type")
    | Pointer(referenced_t) ->
        resolved_t = resolve_type(referenced_t, structure_map)
        return Pointer(resolved_t)
    | Array(elem_t, size) -> 
        --snip--
    | FunType(param_ts, ret_t) -> 
        --snip--
    | t -> return t
```

*清单 18-15：替换类型说明符中的结构体标签*

resolve_type 函数接受一个类型说明符，返回该说明符的一个副本，其中所有结构体标签都已被替换为唯一 ID。当 resolve_type 遇到一个结构体类型时，它把标签替换为 structure_map 中相应的标识符 ❶。如果标签不在 structure_map 中，说明这个结构体尚未被声明，因此它抛出错误 ❷。要解析像 Pointer 这样的派生类型，我们递归地解析其组成类型。我省略了 Array 和 FunType 的伪代码，它们的处理方式与 Pointer 相同。任何其他类型我们都原样返回。我们将用 resolve_type 处理 AST 中的每一个类型说明符，包括函数声明和变量声明、强制转换表达式和 sizeof 表达式中的说明符，以及结构体成员声明中的说明符。

#### 解析结构体类型声明

接下来看清单 18-16 中的伪代码，它展示了如何解析一条结构体类型声明。

```text
resolve_structure_declaration(decl, structure_map):
    prev_entry = structure_map.get(decl.tag) ❶
    if (prev_entry is null) or (not prev_entry.from_current_scope):
        unique_tag = make_temporary()
        structure_map.add(decl.tag, MapEntry(new_tag=unique_tag, from_current_scope=True)) ❷
    else:
        unique_tag = prev_entry.new_tag ❸
    processed_members = []
    for member in decl.members:
        processed_type = resolve_type(member.member_type, structure_map) ❹
        processed_member = (member_name=member.member_name, member_type=processed_type)
        processed_members.append(processed_member)
    resolved_decl = (tag=unique_tag, members=processed_members)
    return resolved_decl ❺
```

*清单 18-16：把结构体类型声明加入结构体标签映射*

首先，我们在结构体标签映射中查找这条声明的标签 ❶。如果这个标签还没有被声明过，或者它是在外层作用域中声明的，那么这条声明就引入了一个新类型。因此我们生成一个新标识符并把它加入结构体标签映射 ❷。如果这个结构体的标签已经在当前作用域中声明过，那么当前这条声明只是对同一类型的重复声明。这种情况下，我们不生成新的唯一 ID，而是使用映射中已有的那个 ❸。

至此，结构体标签映射已是最新。现在我们转换结构体类型声明本身。如果这条声明指定了结构体的成员，我们就对每个成员的类型调用 resolve_type 来解析它们 ❹。我们把声明中的用户定义标签替换为 unique_tag，即我们在函数前面生成或查到的那个 ID。最后，我们返回转换后的声明 ❺。

注意，我们是先在 structure_map 中加入新标签，再处理任何结构体成员。这让我们能够接受自引用的结构体，比如清单 18-6 中的链表节点：

```c
struct linked_list_node {
    int val;
    struct linked_list_node *next;
};
```

还要注意，我们不为结构体成员生成唯一的名字。变量和函数需要唯一标识符，因为它们全都存储在单个符号表中；结构体标签需要唯一，因为它们全都存储在单个类型表中；但结构体成员不会全部存储在一张表里。相反，我们会为每个结构体类型维护一个单独的成员列表，因此不同结构体中同名的成员不会互相冲突。

我们还要对标识符解析遍做两处更新。第一，在每个新作用域开始时，我们会复制一份结构体标签映射，并把其中每个条目的 from_current_scope 属性设为 False，就像我们对标识符映射所做的那样。第二处改动纯属机械性：我们会扩展 resolve_exp 来处理新的 Dot 和 Arrow 表达式，处理方式与它处理所有其他种类的表达式相同。这两处改动都很直接，我就跳过它们的伪代码了。

### 类型检查结构体

就像类型检查器在符号表中记录每个函数和每个变量的信息一样，它也会在类型表中记录每个完整结构体类型的信息。我们先定义类型表；然后看看如何把结构体类型声明转换为类型表条目；最后，我们将利用类型表中的信息对声明、表达式和初始化器做类型检查。

#### 定义类型表

类型表把我们在上一阶段生成的结构体标签映射到 struct_entry 构造。清单 18-17 定义了 struct_entry。

```text
struct_entry = StructEntry(int alignment, int size, member_entry* members)
member_entry = MemberEntry(identifier member_name, type member_type, int offset)
```

*清单 18-17：类型表中的一个条目*

struct_entry 描述一个结构体类型的对齐、大小和成员。我们用 member_entry 构造描述每个成员，它指定成员的名字、它的类型，以及它相对于结构体开头的以字节计的偏移。一个 struct_entry 应当支持两种访问成员的方式：按名字查找特定成员，以及按顺序获取整个成员列表。如果你使用的实现语言支持，你可能想把成员表示为一个有序字典。

与符号表一样，类型表应当是一个全局变量或单例，让你能够从编译器的任何阶段方便地访问它。（为了清晰起见，本节的伪代码中我们会显式地传递它。）

接下来，我们看看在遍历 AST 的过程中如何把结构体定义加入类型表。

#### 填充类型表

当类型检查器遇到一个完整结构体类型的定义时，它应当先验证这个定义，再把它转换为一个 struct_entry 并加入类型表。类型检查器可以忽略任何不带成员列表的结构体类型声明；不带成员列表的声明要么声明一个不完整类型，要么重复声明一个已定义的类型。

要验证一个结构体类型定义，我们首先检查这个结构体是否已经在类型表中。如果在，说明同一作用域中同一标签还有另一个定义，因此我们抛出错误。然后，我们确保结构体中没有成员同名，没有成员具有不完整类型，也没有成员类型指定了元素类型不完整的数组。（记住，元素类型不完整的数组在任何地方都是非法的，不只是在结构体定义中。）你可能还想验证没有结构体成员具有函数类型，但这并非严格必要，因为我们已经在解析期间验证过了。

在验证结构体类型满足所有这些要求之后，我们将计算每个成员的偏移以及整个结构体的大小和对齐。在本章前面，我们已经看过如何执行这些计算并走了一个例子。现在看清单 18-18，它用伪代码演示了整个过程。

```text
typecheck_struct_declaration(struct_decl, type_table):
  ❶ if struct_decl.members is empty:
        return
  ❷ validate_struct_definition(struct_decl, type_table)

    // 为每个成员定义一个 member_entry
  ❸ member_entries = []
    struct_size = 0
    struct_alignment = 1
    for member in struct_decl.members:
        member_alignment = alignment(member.member_type, type_table)
      ❹ member_offset = round_up(struct_size, member_alignment)
      ❺ m = MemberEntry(member.member_name, member.member_type,
                        member_offset)
        member_entries.append(m)
        struct_alignment = max(struct_alignment, member_alignment)
        struct_size = member_offset + size(member.member_type, type_table)

    // 为整个结构体定义一个 struct_entry
  ❻ struct_size = round_up(struct_size, struct_alignment)
    struct_def = StructEntry(struct_alignment, struct_size, member_entries)
  ❼ type_table.add(struct_decl.tag, struct_def)
```

*清单 18-18：计算一个结构体定义*

我们首先检查这条声明是否包含成员列表 ❶。如果不包含，我们立即返回，不对类型表做任何修改。如果包含成员列表，我们验证它满足本节前面描述的那些要求 ❷。validate_struct_definition 的伪代码我就不给了，因为它并不复杂。

然后是真正有趣的部分：算出每个成员在内存中的布局。这里我们要为每个结构体成员定义一个 member_entry ❸。在此过程中，我们将维护一个结构体大小（以字节计）的累计值 struct_size。我们还会跟踪目前为止见过的最严格的成员对齐 struct_alignment。

要计算一个结构体成员的偏移，我们取下一个可用偏移（由 struct_size 给出），并把它向上取整到该成员的对齐 ❹。（每种类型的大小和对齐如何查找，我们稍后再讲。）我们构造它的 member_entry ❺，然后更新 struct_alignment 和 struct_size。

处理完每个成员之后，我们把 struct_size 向上取整到其对齐的最近倍数，算出结构体的总大小 ❻。这个取整后的大小会把结构体末尾的任何填充都算进去。最后，我们把整个 struct_entry 加入类型表 ❼。

#### 在辅助函数中处理结构体

我们已经把大量类型检查逻辑集中到少数几个辅助函数中，包括 is_scalar 和 is_complete。你可能还写过几个辅助函数来查找每种类型的大小、对齐等属性，尽管我还没有提供它们的伪代码。现在我们要扩展这些辅助函数，让它们也处理结构体类型。

我们在清单 17-12 中定义过 is_scalar。清单 18-19 给出更新后的定义，本章新增的内容以粗体标出。

*清单 18-19：检查一个类型是否是标量*

结构体类型不是标量，所以这个改动非常简单。我猜你也写过类似的辅助函数来判断一个类型是否是算术类型、是否是整数类型等等。它们需要类似的简单更新，我们就不在这里展开了。

*清单 18-20：检查一个类型是否完整*

如果一个结构体类型在类型表中，它就是完整的；否则它是不完整的。正如我们之前看到的，一个结构体类型可能在程序中的某个点不完整，而在之后变得完整。在类型检查期间，类型表告诉我们结构体类型在 AST 的当前节点处是否完整。考虑清单 18-21 中的代码片段。

```c
❶ struct s;
❷ struct t {
    struct s member;
};
❸ struct s {
    int a;
    int b;
};
```

*清单 18-21：用不完整的结构体类型声明一个变量*

由于 struct s 的第一条声明 ❶ 没有指定任何成员，我们不会把它加入类型表。接着，当我们验证 struct t 的定义 ❷ 时，我们会在类型表中查找 struct s。（严格地说，我们要查找的是标识符解析阶段替换 s 的那个唯一标识符。）当我们找不到它时，我们会正确地得出 struct s 不完整的结论并抛出错误。如果 struct t 的声明出现在 struct s 的定义 ❸ 之后，我们就会在处理 struct t 之前把 struct s 加入类型表，也就不会抛出错误了。

我们还需要查找类型大小和对齐的辅助函数。清单 18-22 展示了 alignment 函数的伪代码。


*清单 18-22：计算一个类型的对齐*

要求一个结构体的对齐，我们在类型表中查找它。要求一个数组的对齐，我们递归地计算其元素类型的对齐。其他类型的对齐由 ABI 规定，我们直接硬编码。size 的伪代码我就不提供了，它与 alignment 类似。

> **注意**
>
> 我们在前面学到过，如果一个数组类型的变量大小达到 16 字节或更大，它就必须 16 字节对齐。清单 18-22 没有反映这一要求，因为它计算的是类型的对齐，而不是变量的对齐。如果你还没有写过，你恐怕需要另写一个辅助函数来计算变量的对齐。

我们在前面各章定义的其他辅助函数应该不需要任何修改就能正确处理结构体。考虑 convert_by_assignment，我们用它对赋值表达式以及其他所有需要把一个值“如同赋值”般转换到特定类型的地方做类型检查。清单 18-23 重复给出清单 17-11 中这段代码的最新版本。

```text
convert_by_assignment(e, target_type):
    if get_type(e) == target_type:
        return e
    if get_type(e) is arithmetic and target_type is arithmetic:
        return convert_to(e, target_type)
    if is_null_pointer_constant(e) and target_type is a pointer type:
        return convert_to(e, target_type)
    if target_type == Pointer(Void) and get_type(e) is a pointer type:
        return convert_to(e, target_type)
    if target_type is a pointer type and get_type(e) == Pointer(Void):
        return convert_to(e, target_type)
    else:
        fail("Cannot convert type for assignment")
```

*清单 18-23：把表达式转换为目标类型*

如果我们传给 convert_by_assignment 一个已经具有正确结构体类型的表达式，它会原样返回该表达式。在其他任何源类型或目标类型为结构体类型的情形中，它都会失败。这正是正确的行为，因为没有任何办法能转换到结构体类型或从结构体类型转换出来。

#### 处理不完整结构体类型

我们需要对不完整结构体类型施加若干限制。我们先验证这些类型在声明中的使用，再验证它们在表达式中的使用。

声明（但不是定义）一个带有不完整结构体类型参数或返回值的函数是合法的。（记住，函数定义是带函数体的函数声明。）如果 struct s 是不完整类型，类型检查器应当接受这条声明：

```c
void take_a_struct(struct s incomplete);
```

但应当拒绝这个定义：

```c
void take_a_struct(struct s incomplete) {
    return;
}
```

类似地，我们将接受带不完整结构体类型的变量声明，但拒绝这些变量的任何定义，包括暂定定义（tentative definition）。（这比 C 标准更严格，标准在少数有限情形下允许对不完整类型变量的暂定定义。）具体来说，只有当带不完整结构体类型的变量声明具有 extern 存储类且没有初始化器时，我们才接受它。

声明就处理到这里；现在考虑表达式。在表达式中使用不完整类型的变量只有一种方式。你可以取它的地址，如下面的例子所示：

```c
extern struct s my_incomplete_struct;
struct s *ptr = &my_incomplete_struct;
```

之后你就可以像使用任何其他指向不完整类型的指针一样使用 ptr。

类似地，解引用一个指向不完整结构体的指针然后再取它的地址，从而得到你一开始的那个指针，也是合法的（尽管没什么特别的用处）：

```c
struct s *another_ptr = &*ptr;
```

对带不完整结构体类型的表达式的任何其他使用都是无效的。你甚至不能把它强制转换为 void，也不能把它用作表达式语句，所以类型检查器应当拒绝以下两条语句：

```c
(void) my_incomplete_struct;
*ptr;
```

我们将扩展 typecheck_and_convert 来捕获这些无效表达式。清单 18-24 给出该函数更新后的定义，其中相对清单 15-19 中原始定义的改动以粗体标出。

```text
typecheck_and_convert(e, symbols, type_table):
    typed_e = typecheck_exp(e, symbols, type_table)
    match get_type(typed_e) with
    | Array(elem_t, size) ->
        --snip--
    | Structure(tag) ->
        if tag is not in type_table:
            fail("Invalid use of incomplete structure type")
        return typed_e
    | _ -> return typed_e
```

*清单 18-24：在 typecheck_and_convert 中拒绝不完整结构体类型*

记住，typecheck_and_convert 处理 AST 中的每一个表达式，静态初始化器（必须是常量）以及 SizeOf 和 AddrOf 表达式的操作数（它们不做数组退化）除外。这使得 typecheck_and_convert 成为放置新验证逻辑的最方便的地方，尽管它与这个函数最初的目的——把数组隐式转换为指针——毫无关系。有了这个新验证，我们就能在每一种表达式中正确处理不完整类型：我们将允许 AddrOf 表达式中出现不完整结构体类型，已有的验证会拒绝 SizeOf 表达式中所有的不完整类型（包括 void），而 typecheck_and_convert 会在其他所有地方拒绝不完整结构体类型。注意，typecheck_and_convert 仍然接受 void 表达式；在若干允许 void 表达式而不允许带不完整结构体类型表达式的地方，它们仍是合法的。

不完整类型所需的所有其他验证，我们已经实现过了。例如，我们已经要求指针算术表达式中的指针操作数指向完整类型，也已经要求数组类型说明符中的元素类型是完整的。

#### 类型检查成员访问运算符

接下来，我们对 `.` 和 `->` 运算符做类型检查。对这两者，我们都要验证表达式、确定成员的类型，并把它记录为整个表达式的类型。清单 18-25 演示了如何对 `.` 运算符做类型检查。

```text
typecheck_exp(e, symbols, type_table):
    match e with
    | --snip--
    | Dot(structure, member) ->
        typed_structure = typecheck_and_convert(structure, symbols, type_table)
      ❶ match get_type(typed_structure) with
        | Structure(tag) ->
          ❷ struct_def = type_table.get(tag)
          ❸ member_def = <find member in struct_def.members>
            if member_def is not found:
                fail("Structure has no member with this name")
            member_exp = Dot(typed_structure, member)
          ❹ return set_type(member_exp, member_def.member_type)
        | _ -> fail("Tried to get member of non-structure")
    | Arrow(pointer, member) ->
        --snip--
```

*清单 18-25：类型检查 . 运算符*

我们首先调用 typecheck_and_convert 对第一个操作数 structure 做类型检查（如果 structure 具有不完整类型，它会抛出错误）。然后，我们验证 structure 确实是一个结构体 ❶。如果是，我们在类型表中查找它的类型 ❷，再在得到的类型表条目中查找 member ❸。最后，我们用成员的类型标注这个表达式 ❹。如果 structure 不是结构体，或者没有这个名字的成员，我们就抛出错误。

类型检查 `->` 运算符的伪代码我就不提供了，因为它几乎完全相同；唯一的区别是我们要验证第一个操作数是一个指向结构体的指针，而不是结构体本身。

#### 验证左值

一个 `->` 表达式总是左值。要确定一个 `.` 表达式是不是左值，类型检查器必须递归地检查它的第一个操作数是不是左值。例如，类型检查器应当拒绝表达式 f().member = 3。因为 f() 不是左值，f().member 也不是。

这意味着我们可能会遇到不是左值的数组！显式地取这种数组的地址是类型错误，比如清单 18-26 中那样。

```c
struct s {
    int arr[3];
};

struct s f(void);

int main(void) {
    int *pointer_to_array[3] = &(f().arr);
    --snip--
}
```

*清单 18-26：非法地取一个非左值的地址*

不过，这些数组仍然会退化为指针，所以它们的地址仍会被隐式地加载。例如，清单 18-27 中的程序是完全合法的。

```c
struct s {
    int arr[3];
};

struct s f(void);

int main(void) {
    return f().arr[0];
}
```

*清单 18-27：把一个非左值数组隐式转换为指针*

在对这个程序做类型检查时，我们会像对其他任何数组类型的表达式一样，插入 AddrOf 来取 f().arr 的地址。

> **临时生命周期的奇特情形**
>
> 这里发生了一件有点古怪的事情。表达式 f().arr 不是左值，但要拥有一个我们能加载的地址，它又必须指代一个对象。C 标准 6.2.4 节第 8 段解决了这个两难问题：“一个具有结构体或联合体类型的非左值表达式，如果该结构体或联合体包含一个数组类型的成员……它指代一个具有自动存储期和临时生命周期（temporary lifetime）的对象……它的生命周期在包含它的完整表达式求值结束时结束。任何修改具有临时生命期的对象的行为都会导致未定义行为。”
>
> 具有临时生命周期的对象类似于我们在 TACKY 生成期间创建的临时变量。编译器分配它来保存某个表达式的结果，而在该表达式求值之后就再也不会使用它。关键的区别在于，在源程序中有可能获得指向临时生命周期对象的指针。这让人很容易在不经意间在该对象的生命周期结束之后使用它。考虑这个例子，你可能以为它等价于清单 18-27 中的 return 语句：
>
> ```c
> int *arr_pointer = f().arr;
> return arr_pointer[0];
> ```
>
> f() 返回的结构体的生命周期在我们完成对表达式 f().arr 的求值之后就结束了。这意味着 arr_ptr 指向一个生命周期已经结束的对象，因此对它做下标运算是未定义行为。

#### 类型检查条件表达式中的结构体

类型检查器应当接受两个分支具有相同结构体类型的条件表达式。它应当拒绝只有一个分支具有结构体类型，或者两个分支具有两个不同结构体类型的条件表达式。要判断两个结构体类型是否相同，比较它们的标签，而不是它们的内容。

#### 类型检查结构体初始化器

最后，我们来处理结构体初始化器。正如你在本章前面学到的，你可以用一个该结构体类型的单个表达式或一个复合初始化器来初始化结构体。第一种情形不需要对类型检查器做任何修改。

要处理复合初始化器，我们要对照相应的成员类型对初始化列表中的每一项做类型检查，如清单 18-28 所示。

```text
typecheck_init(target_type, init, symbols, type_table):
    match target_type, init with
    | Structure(tag), CompoundInit(init_list) ->
        struct_def = type_table.get(tag) ❶
        if length(init_list) > length(struct_def.members): ❷
            fail("Too many elements in structure initializer")
        i = 0
        typechecked_list = []
        for init_elem in init_list: ❸
            t = struct_def.members[i].member_type
            typechecked_elem = typecheck_init(t, init_elem, symbols, type_table)
            typechecked_list.append(typechecked_elem)
            i += 1
        while i < length(struct_def.members): ❹
            t = struct_def.members[i].member_type
            typechecked_list.append(zero_initializer(t))
            i += 1
        return set_type(CompoundInit(typechecked_list), target_type)
    | --snip--
```

*清单 18-28：类型检查结构体的复合初始化器*

我们先在类型表中查找这个结构体 ❶。在调用 typecheck_init 之前，我们应当已经验证过 target_type 是完整的，所以此时可以安全地假设该结构体已被定义。接着，我们确保初始化列表不会太长 ❷。与处理数组初始化器时一样，我们会拒绝元素过多的初始化列表，但接受元素太少、不足以初始化整个对象的初始化列表。

执行完这项检查后，我们遍历初始化列表 ❸。要对每个初始化器做类型检查，我们在结构体的成员列表中查找相应的成员类型，然后递归调用 typecheck_init 确保该初始化器与那个类型兼容。最后，我们用零填充任何未被初始化的结构体成员 ❹。

更新完 typecheck_init 之后，你还需要扩展 zero_initializer 来处理结构体类型。要把一个结构体初始化为零，zero_initializer 应当对每个成员类型递归调用自身，并把结果放进一个复合初始化器中返回。

#### 初始化静态结构体

如果一个结构体具有静态存储期（static storage duration），我们会像对数组那样，把它的初始值作为一个 static_init 列表存储在符号表中。关键区别在于，我们还要初始化结构体中的填充。让我们回到清单 18-10 的例子：

```c
struct example {
    int member1;
    double member2;
    char array[3];
};

struct example var = {1, 2.0, {'a', 'b', 'c'}};
```

我们已经算出这个结构体在 member1 和 member2 之间有 4 字节填充，在 array 之后有 5 字节填充。如果 var 是一个静态变量，我们将用清单 18-29 中的构造来表示它的初始值。

```text
Initial([IntInit(1),
       ❶ ZeroInit(4),
         DoubleInit(2.0),
         CharInit(97),
         CharInit(98),
         CharInit(99),
       ❷ ZeroInit(5)])
```

*清单 18-29：把清单 18-10 中的初始化器表示为 static_init 列表*

我们用 ZeroInit 构造初始化填充 ❶❷，因为 C 标准要求静态结构体中的填充被初始化为零。清单 18-30 演示了如何生成清单 18-29 那样的静态初始化器列表。

```text
create_static_init_list(init_type, initializer, type_table):
    match init_type, initializer with
    | Structure(tag), CompoundInit(init_list) ->
      ❶ struct_def = type_table.get(tag)
        if length(init_list) > length(struct_def.members):
            fail("Too many elements in structure initializer")
        current_offset = 0
        static_inits = []
        i = 0
        for init_elem in init_list:
            member = struct_def.members[i]
            if member.offset != current_offset:
              ❷ static_inits.append(ZeroInit(member.offset - current_offset))
          ❸ more_static_inits = create_static_init_list(member.member_type,
                                                        init_elem,
                                                        type_table)
            static_inits.append_all(more_static_inits)
            current_offset = member.offset + size(member.member_type,
                                                  type_table)
            i += 1
        if struct_def.size != current_offset:
          ❹ static_inits.append(ZeroInit(struct_def.size - current_offset))
        return static_inits
    | Structure(tag), SingleInit(e) ->
      ❺ fail("Cannot initialize static structure with scalar expression")
    | --snip--
```

*清单 18-30：为结构体生成静态初始化器*

要处理静态结构体的复合初始化器，我们首先在类型表中查找该结构体 ❶。我们确保初始化列表不会太长，就像在 typecheck_init 中对非静态初始化器所做的那样。然后，我们遍历初始化列表，为其中的每个元素在结构体的成员列表中查找相应的成员定义。在此过程中，我们更新 current_offset 变量来跟踪到目前为止已经初始化了多少字节。

每当我们处理一个结构体成员的初始化器时，首先检查我们已初始化的字节数是否达到了预期的偏移。如果还不够，我们就用一个 ZeroInit 初始化器补上必要的填充 ❷。然后，我们递归调用 create_static_init_list，为该结构体成员本身创建初始化器列表 ❸。接下来，我们根据刚刚初始化的成员的偏移和大小更新 current_offset。

初始化完每个结构体成员之后，如有必要，我们再添加一个 ZeroInit，把结构体填充到正确的大小 ❹。这最后一个 ZeroInit 会把所有未被显式初始化的结构体成员以及最后一个成员之后的尾部填充都清零。

由于不存在结构体类型的常量，用一个 SingleInit 表达式初始化静态结构体是类型错误 ❺。

## TACKY 生成

本节中，我们将引入最后一条 TACKY 指令：

```text
CopyFromOffset(identifier src, int offset, val dst)
```

这条指令与我们在第 15 章添加的 CopyToOffset 指令相对应。CopyFromOffset 中的 src 标识符是某个聚合变量的名字，offset 是该变量中某个子对象的字节偏移，而 dst 是我们要把该子对象复制到的变量。清单 18-31 给出了完整的 TACKY IR，包括新的 CopyFromOffset 指令。

```text
program = Program(top_level*)
top_level = Function(identifier, bool global, identifier* params, instruction* body)
          | StaticVariable(identifier, bool global, type t, static_init* init_list)
          | StaticConstant(identifier, type t, static_init init)
instruction = Return(val?)
            | SignExtend(val src, val dst)
            | Truncate(val src, val dst)
            | ZeroExtend(val src, val dst)
            | DoubleToInt(val src, val dst)
            | DoubleToUInt(val src, val dst)
            | IntToDouble(val src, val dst)
            | UIntToDouble(val src, val dst)
            | Unary(unary_operator, val src, val dst)
            | Binary(binary_operator, val src1, val src2, val dst)
            | Copy(val src, val dst)
            | GetAddress(val src, val dst)
            | Load(val src_ptr, val dst)
            | Store(val src, val dst_ptr)
            | AddPtr(val ptr, val index, int scale, val dst)
            | CopyToOffset(val src, identifier dst, int offset)
            | CopyFromOffset(identifier src, int offset, val dst)
            | Jump(identifier target)
            | JumpIfZero(val condition, identifier target)
            | JumpIfNotZero(val condition, identifier target)
            | Label(identifier)
            | FunCall(identifier fun_name, val* args, val? dst)
val = Constant(const) | Var(identifier)
unary_operator = Complement | Negate | Not
binary_operator = Add | Subtract | Multiply | Divide | Remainder | Equal | NotEqual
                | LessThan | LessOrEqual | GreaterThan | GreaterOrEqual
```

*清单 18-31：向 TACKY IR 添加 CopyFromOffset*

你不仅可以用 CopyToOffset 和 CopyFromOffset 指令访问结构体中的子对象，还可以像对标量变量那样，用 Copy、Load 和 Store 把整个结构体从一个位置复制到另一个位置，或用 Return 和 FunCall 在函数之间传递它们。我们将把结构体类型的变量表示为普通的 TACKY Var。

接下来，我们把成员访问运算符转换为 TACKY。然后，我们处理结构体的复合初始化器。对于大多数可以使用结构体的构造，比如函数调用、return 语句和条件表达式，我们不会改变处理方式。我们也不需要为新的顶层 StructDecl 构造做任何事情；在这个阶段我们会丢弃结构体声明，就像我们丢弃不带函数体的函数声明和不带初始化器的变量声明一样。

### 实现成员访问运算符

在前面的章节中，你学到过可以用三种方式使用一个对象：对它做左值转换、给它赋值，或者取它的地址。现在有了第四种选择：如果对象是结构体，你可以访问它的一个成员。而由于该结构体成员本身也是对象，你可以对它做左值转换、给它赋值、取它的地址，或者访问它的一个成员。让我们看看在每种情形下应当生成的 TACKY。然后，在第 14 章处理解引用指针的方法的基础上，我们将引入一种新的 exp_result 来指定结构体成员。

#### 在 TACKY 中访问结构体成员

要实现对结构体成员的任何一种操作，我们都要先在类型表中查找该成员的偏移。首先考虑这样的情形：结构体本身是一个 TACKY 变量，而不是被解引用的指针或某个更大结构体中的子对象。要对一个结构体成员做左值转换，我们使用 CopyFromOffset 指令。我们会把 <struct>.<member> 翻译为：

```text
<instructions for struct>
s = <result of struct>
result = CopyFromOffset(s, <member offset>)
```

我们会用 CopyToOffset 给结构体成员赋值，把 <struct>.<member> = <right> 转换为：

```text
<instructions for struct>
dst = <result of struct>
<instructions for right>
src = <result of right>
CopyToOffset(src, dst, <member offset>)
```

要取一个结构体成员的地址，我们先加载包含它的对象的地址，再加上该成员的偏移。我们会把 &<struct>.<member> 转换为：

```text
<instructions for struct>
s = <result of struct>
result = GetAddress(s)
result = AddPtr(ptr=result, index=<member offset>, scale=1)
```

要处理一串嵌套的成员访问，我们把它们的偏移全部加起来，然后根据序列中最后一个成员的使用方式发出相应的指令。考虑清单 18-32 中的结构体声明。

```c
struct inner {
    char c;
    int i;
};

struct outer {
    int member1;
    struct inner member2;
};
```

*清单 18-32：声明一个包含嵌套结构体的结构体*

如果 my_struct 是一个 struct outer，而我们需要对 my_struct.member2.i 做左值转换，我们将发出：

```text
result = CopyFromOffset("my_struct", 8)
```

因为 member2 在 struct outer 中的偏移是 4 字节，而 i 在 struct inner 中的偏移是 4 字节，所以 my_struct.member2.i 所指代的对象相对于 my_struct 的开头的总偏移是 8 字节。

最后，考虑如何通过被解引用的指针访问结构体成员。最地道的做法是使用箭头运算符，形如 <exp>-><member>。它等价于表达式 (*<exp>).<member>。要实现这两个表达式中的任何一个，你都要把成员偏移加到指针上，然后解引用结果。与任何被解引用的指针一样，究竟是发出 Load 或 Store 指令，还是直接使用指针的值，取决于它如何被使用。假设 inner_struct_pointer 的类型是 struct inner *。我们将把表达式

```c
inner_struct_pointer->i = 1
```

转换为：

```text
ptr = AddPtr(ptr=inner_struct_pointer, index=4, scale=1)
Store(1, ptr)
```

我们可以用完全相同的指令实现等价表达式

```c
(*inner_struct_pointer).i = 1
```

现在我们知道了想要生成哪些指令，接下来相应地更新 TACKY 生成遍。

#### 用 SubObject 指定结构体成员

让我们扩展 exp_result 构造，以指定某个聚合对象的一个成员。清单 18-33 给出 exp_result 更新后的定义。

```text
exp_result = PlainOperand(val)
           | DereferencedPointer(val)
           | SubObject(identifier base, int offset)
```

*清单 18-33：扩展 exp_result 以表示子对象*

SubObject 的 base 参数是一个聚合对象，而不是指针。第二个参数 offset 是进入该对象的字节偏移。SubObject 指定的对象可能是标量，也可能本身是聚合对象。在清单 18-34 中，我们用这个构造来表示 Dot 运算符的结果。

```text
emit_tacky(e, instructions, symbols, type_table):
    match e with
    | --snip--
    | Dot(structure, member) ->
        struct_def = <look up structure's type in the type table>
        member_offset = <look up member offset in struct_def>
        inner_object = emit_tacky(structure, instructions, symbols, type_table)
        match inner_object with
        | PlainOperand(Var(v)) -> return SubObject(v, member_offset) ❶
        | SubObject(base, offset) -> return SubObject(base, offset + member_offset) ❷
        | DereferencedPointer(ptr) -> ❸
            dst_ptr = make_tacky_variable(Pointer(get_type(e)), symbols)
            instr = AddPtr(ptr=ptr, index=Constant(ConstLong(member_offset)),
                           scale=1, dst=dst_ptr)
            instructions.append(instr)
            return DereferencedPointer(dst_ptr)
```

*清单 18-34：把 Dot 运算符转换为 TACKY*

首先，我们在类型表中查找 member 在结构体中的偏移。然后，我们对这个表达式的第一个操作数不做左值转换地处理它。得到的对象要么是一个普通的 TACKY 变量，要么是某个 TACKY 变量的子对象，要么是一个被解引用的指针。（我们知道结果不会是常量，因为 TACKY 中不存在结构体类型的常量。）

如果 inner_object 只是一个变量，我们返回一个 SubObject，指定该变量中位于 member_offset 处的对象 ❶。如果 inner_object 本身是某个更大变量中的子对象，我们把它的偏移加到 member_offset 上 ❷。这样就处理了嵌套的成员运算符，比如我们在本节前面考虑过的表达式 my_struct.member2.i。

最后，如果内层的结构体是一个被解引用的指针，我们就用指针算术访问该结构体成员 ❸。由于 DereferencedPointer(ptr) 指代整个结构体，ptr 必须指向该结构体的开头。我们把 member_offset 加到 ptr 上，得到指向指定结构体成员的指针。然后，我们解引用这个指针来指定该结构体成员本身。

#### 处理 SubObject

接下来，我们要在左值转换、赋值表达式和 AddrOf 表达式中处理 SubObject 构造。要对一个 SubObject 做左值转换，我们用 CopyFromOffset 指令把它复制到一个新变量中，如清单 18-35 所示。

```text
emit_tacky_and_convert(e, instructions, symbols, type_table):
    result = emit_tacky(e, instructions, symbols, type_table)
    match result with
    | SubObject(base, offset) ->
        dst = make_tacky_variable(get_type(e), symbols)
        instructions.append(CopyFromOffset(base, offset, dst))
        return dst
    | --snip--
```

*清单 18-35：对一个 SubObject 做左值转换*

反过来，当一个 SubObject 出现在赋值表达式的左侧时，我们用一条 CopyToOffset 指令写入它，如清单 18-36 所示。

```text
emit_tacky(e, instructions, symbols, type_table):
    match e with
    | --snip--
    | Assignment(left, right) ->
        lval = emit_tacky(left, instructions, symbols, type_table)
        rval = emit_tacky_and_convert(right, instructions, symbols, type_table)
        match lval with
        | SubObject(base, offset) ->
            instructions.append(CopyToOffset(rval, base, offset))
            return PlainOperand(rval)
        | --snip--
```

*清单 18-36：给一个 SubObject 赋值*

最后，清单 18-37 展示了如何计算一个 SubObject 的地址。我们加载基对象的地址，再加上偏移。

```text
    | AddrOf(inner) ->
        v = emit_tacky(inner, instructions, symbols, type_table)
        match v with
        | SubObject(base, offset) ->
            dst = make_tacky_variable(get_type(e), symbols)
            instructions.append(GetAddress(Var(base), dst))
            instructions.append(AddPtr(ptr=dst,
                                       index=Constant(ConstLong(offset)),
                                     ❶ scale=1,
                                       dst=dst))
            return PlainOperand(dst)
        | --snip--
```

*清单 18-37：取一个 SubObject 的地址*

我们复用同一个临时变量 dst，让它先指向结构体的基址，再指向其成员。我们也可以生成两个不同的临时变量，但没有必要。由于 SubObject 构造中的偏移以字节为单位，这条 AddPtr 指令的 scale 是 1 ❶。

#### 实现 Arrow 运算符

实现了 Dot 之后，实现 Arrow 就很容易了。要计算 ptr->member，我们先求值并对 ptr 做左值转换。然后，我们用 AddPtr 加上 member 的偏移。这会得到一个指向指定结构体成员的指针。最后，我们用 DereferencedPointer 构造解引用这个指针。这部分伪代码我就省略了；你已经见过如何把 (*ptr).member 转换为 TACKY，把 ptr->member 转换为 TACKY 与之非常相似。

我们不需要任何额外的逻辑来处理 Arrow 表达式的结果。这个表达式总是产生一个 DereferencedPointer 构造，而我们已经知道如何处理它。

#### 省略无用的 AddPtr 指令

结构体中的第一个成员的偏移总是零。作为一个可选的优化，你可以在计算这个成员的地址时跳过 AddPtr 指令。这会影响清单 18-34 和清单 18-37，也会影响 Arrow 的实现（我没有给出它的伪代码）。在这三种情形下，如果 member_offset 是 0，你都不需要生成 AddPtr 指令。

### 把复合初始化器转换为 TACKY

作为本节的收尾，我们把结构体的复合初始化器转换为 TACKY。基本方法与前几章相同：我们依次求值初始化列表中的每个表达式，用一条 CopyToOffset 指令把每个表达式的结果复制到目的地中正确的偏移处。但现在我们需要查询类型表来找到每个表达式的正确偏移。我们还需要计算深藏在嵌套结构体、结构体数组、包含数组的结构体等之中的子对象的偏移。

清单 18-38 演示了如何在遍历结构体或数组的复合初始化器的过程中跟踪这些偏移并发出 CopyToOffset 指令。

```text
compound_initializer_to_tacky(var_name, offset, init, instructions, symbols, type_table):
    match init, get_type(init) with
    | SingleInit(String(s)), Array(elem_t, size) ->     --snip--
    | SingleInit(e), t ->
        v = emit_tacky_and_convert(e, instructions, symbols, type_table)
        instructions.append(CopyToOffset(v, var_name, offset)) ❶
    | CompoundInit(init_list), Structure(tag) ->
        members = type_table.get(tag).members
        for mem_init, member in zip(init_list, members):
            mem_offset = offset + member.offset ❷
            compound_initializer_to_tacky(var_name, mem_offset, mem_init, instructions,
                                          symbols, type_table)
    | CompoundInit(init_list), Array(elem_t, size) -> 
        --snip--
```

*清单 18-38：把复合初始化器转换为 TACKY*

compound_initializer_to_tacky 的参数包括 var_name（被初始化的数组或结构体变量的名字）、offset（当前子对象在该变量中的字节偏移）和 init（初始化器本身）。在初始化整个变量的顶层调用中，offset 参数将是 0。

在基本情况中，我们用单个表达式的值初始化一个子对象。这个表达式可能是初始化数组的字符串字面量；这种情况的伪代码我省略了，我们在第 16 章讲过。否则，我们对表达式求值，并用一条 CopyToOffset 指令把结果复制到相应位置 ❶。即使结果具有结构体类型，我们也可以用一条指令把它复制到目的地。

当我们遇到结构体的复合初始化器时，我们在类型表中查找该结构体的成员列表。我们把初始化列表中每一项的偏移计算为相应的成员偏移加上起始 offset 参数 ❷。然后，我们递归地处理该项。数组复合初始化器的情形我就不再赘述了，因为你已经知道如何处理它。

我们的实现在这里略微偏离了 C 标准。在某些情形下，标准要求把填充初始化为零；清单 18-38 没有初始化结构体的填充，而且我们的测试也不会检查非静态结构体中填充的值。

> **关于填充的一切**
>
> C 标准试图确保填充以一种一致、可预测的方式被初始化。遗憾的是，它并没有真正做到，因此很容易无意间让填充处于未初始化状态。这带来潜在的安全风险，因为未初始化的填充可能泄露先前存储在内存中该位置的敏感数据。Jens Gustedt 2012 年的博文《C11 缺陷：填充的初始化》（"C11 Defects: Initialization of Padding"）对标准中这个令人困惑的角落做了很好的概述（https://gustedt.wordpress.com/2012/10/24/c11-defects-initialization-of-padding/）。
>
> 幸运的是，到了 C23，情况有所改善。这一修订引入了形如 {} 的空初始化器，它把整个联合体或聚合对象初始化为零，包括其中的填充。这并没有完全解决 Gustedt 指出的那些不一致，但它让每一个只想把结构体清零的 C 程序员的日子好过了一些。关于这个特性（以及 C23 的一大批其他改动）的一篇精彩介绍，参见 JeanHeyd Meneide 的博文《Ever Closer—C23 Draws Nearer》（https://thephd.dev/ever-closer-c23-improvements）。

到这里，你已经知道如何把两个成员访问运算符和结构体复合初始化器都转换为 TACKY 了。实现完这些转换之后，你就可以测试这一编译遍了。

## System V 调用约定中的结构体

本章汇编生成中最棘手的部分是处理函数调用。一如既往，我们需要按照 System V x64 调用约定传递参数和返回值。传递和返回结构体的规则特别繁琐，所以在动手修改后端之前，我们先来看看这些规则。

### 对结构体分类

在 System V x64 ABI 中，每个参数和返回值都有一个类别（class），它决定了函数调用期间如何传送这个值。我们已经遇到过 ABI 定义的两个类别，尽管我当时没有用“类别”这个词来描述它们。具有整数、字符和指针类型的值都属于 INTEGER 类别；它们通过通用寄存器传送。double 类型的值都属于 SSE 类别；它们通过 XMM 寄存器传送。

本章我们将遇到第三个类别：MEMORY，用于必须在内存中传送的大值。我们之前已经在内存中传递过函数参数了，但通过内存传递返回值是一个新概念；稍后我们会看到它究竟是如何工作的。

ABI 给出了一个相当复杂的算法来对结构体和联合体分类。我们可以使用这个算法的一个简化版本，因为有一大堆类型我们并不处理，比如 float 和联合体。本节我们将走一遍简化后的结构体分类规则。完整的算法参见第 553 页“延伸资源”中列出的文档。

#### 把结构体拆分成八字节组

我们将为结构体的每个 8 字节块分配一个单独的类别。ABI 把这些块称为八字节组（eightbyte）。如果结构体的大小不能被 8 整除，最后一个八字节组可能不足 8 字节（这让这个术语有点名不副实）。考虑清单 18-39，它声明了一个 12 字节的结构体。

```c
struct twelve_bytes {
    int i;
    char arr[8];
};
```

*清单 18-39：一个有两个八字节组的结构体*

这个结构体的第一个八字节组包含 i 和 arr 的前四个元素。第二个八字节组长 4 字节，包含 arr 的最后四个元素。图 18-2 展示了这个结构体在内存中的布局。

```text
struct twelve_bytes（总大小 12 字节）

  偏移 0–3：   i (int)              ┐
  偏移 4–7：   arr[0]–arr[3]        ┘ 第 1 个八字节组（完整 8 字节）
  偏移 8–11：  arr[4]–arr[7]        ── 第 2 个八字节组（仅 4 字节）
```

*图 18-2：struct twelve_bytes 在内存中的布局*

图 18-2 说明，像 arr 这样的嵌套数组可以跨越多个八字节组。嵌套的结构体也可以。考虑清单 18-40 中的结构体声明。

```c
struct inner {
    int i;
    char ch2;
};

struct nested_ints {
    char ch1;
    struct inner nested;
};
```

*清单 18-40：一个包含跨越两个八字节组的嵌套结构体的结构体类型*

图 18-3 展示了 struct nested_ints 在内存中的布局。

```text
struct nested_ints（总大小 12 字节）

  偏移 0：     ch1 (char)           ┐
  偏移 1–3：   填充                 │
  偏移 4–7：   nested.i (int)       ┘ 第 1 个八字节组
  偏移 8：     nested.ch2 (char)    ┐
  偏移 9–11：  填充                 ┘ 第 2 个八字节组（仅部分使用）
```

*图 18-3：struct nested_ints 在内存中的布局*

这个结构体的第一个八字节组存放两个标量值：ch1 和嵌套成员 nested.i。第二个八字节组存放 nested.ch2。当我们对一个结构体分类时，我们关心的是每个八字节组包含哪些标量值，而不关心这些值被怎样组合成嵌套的结构体或数组。就我们的分类算法而言，struct nested_ints 等价于清单 18-41 中定义的 struct flattened_ints 类型。

```c
struct flattened_ints {
    char c;
    int i;
    char a;
};
```

*清单 18-41：一个与 struct nested_ints 在内存中布局相同的结构体*

这个结构体在内存中看起来与 struct nested_ints 完全一样：它的第一个八字节组存放一个 char 和一个 int，第二个八字节组存放另一个 char。

#### 对八字节组分类

如果一个结构体大于 16 字节——换句话说，如果它由三个或更多八字节组组成——我们会把每个八字节组都归入 MEMORY 类别。例如，struct large 由四个八字节组组成，它们全都被归为 MEMORY：

```c
struct large {
    int i;
    double d;
    char arr[10];
};
```

如果一个结构体的大小是 16 字节或更小，我们就根据其内容把每个八字节组归入 INTEGER 或 SSE 类别。一个八字节组如果包含 double 就属于 SSE 类别，如果包含其他任何内容则属于 INTEGER 类别。例如，清单 18-39 中 struct twelve_bytes 的两个八字节组都属于 INTEGER 类别。我们也会把清单 18-40 中 struct nested_ints 的两个八字节组和清单 18-41 中 struct flattened_ints 的两个八字节组都归入 INTEGER 类别，因为它们都不包含 double。

清单 18-42 定义了另外几个结构体类型。我们来逐个给它们分类。

```c
struct two_ints {
    int i;
    int i2;
};

struct nested_double {
    double array[1];
};

struct two_eightbytes {
    double d;
    char c;
};
```

*清单 18-42：更多结构体类型*

struct two_ints 由单个八字节组组成，属于 INTEGER 类别。struct nested_double 由单个八字节组组成，属于 SSE 类别。struct two_eightbytes 由两个八字节组组成：第一个属于 SSE 类别，因为它包含一个 double；第二个属于 INTEGER 类别，因为它包含一个 char。

### 传递结构体类型的参数

一旦我们对一个结构体分好了类，就能确定如何把它作为参数传递。如果一个结构体由一个或两个八字节组组成，我们就把该结构体的每个八字节组放进其类别的下一个可用寄存器中传递。如果结构体由单个 INTEGER 类别的八字节组组成，我们就在下一个通用传参寄存器中传递它。如果它由单个 SSE 类别的八字节组组成，我们就在下一个可用的 XMM 传参寄存器中传递它。如果它由一个 INTEGER 八字节组和一个 SSE 八字节组组成，我们就在一个通用寄存器中传递第一个八字节组，在下一个 XMM 寄存器中传递第二个八字节组，依此类推。如果没有足够的可用寄存器来传递整个结构体，我们就把整个结构体压入栈中。

来看几个例子。首先，在清单 18-43 中，我们重复给出清单 18-42 中定义的 struct two_eightbytes 类型，并声明一个接受该类型参数的函数。

```c
struct two_eightbytes {
    double d;
    char c;
};

void pass_struct(struct two_eightbytes param);
```

*清单 18-43：一个带 struct two_eightbytes 参数的函数声明*

假设 x 是一个 struct two_eightbytes 类型的变量，存储在栈上地址 -16(%rbp) 处。我们可以把函数调用 pass_struct(x) 转换为清单 18-44 中的汇编。

```asm
movsd   -16(%rbp), %xmm0
movq    -8(%rbp), %rdi
call    pass_struct
```

*清单 18-44：在两个寄存器中传递结构体参数*

由于这个结构体的第一个八字节组属于 SSE 类别，我们在第一个 XMM 传参寄存器 XMM0 中传递它。结构体的第二个八字节组属于 INTEGER 类别，所以我们在第一个通用传参寄存器 RDI 中传递它。

接下来看清单 18-45。这个清单声明的函数带有一个需要压入栈中的结构体参数。

```c
struct two_longs {
    long a;
    long b;
};

void a_bunch_of_arguments(int i0, int i1, int i2, int i3, int i4,
                          struct two_longs param, int i5);
```

*清单 18-45：一个带必须通过内存传递的结构体参数的函数声明*

调用 a_bunch_of_arguments 时，我们把参数 i0 到 i4 分别放在寄存器 EDI、ESI、EDX、ECX 和 R8D 中传递。这样一来，剩下的寄存器就不够传递 param 参数了；它的两个八字节组都属于 INTEGER 类别，但可用的通用传参寄存器只剩 R9 一个。因此，我们要把整个结构体压入栈中。然后，由于 R9D 仍然空闲，我们用它来传递 i5。如果 arg 是一个具有静态存储期的 struct two_longs，我们可以把函数调用

```c
a_bunch_of_arguments(0, 1, 2, 3, 4, arg, 5);
```

转换为清单 18-46 中的汇编。

```asm
movl    $0, %edi
movl    $1, %esi
movl    $2, %edx
movl    $3, %ecx
movl    $4, %r8d
movl    $5, %r9d
❶ pushq   arg+8(%rip)
pushq   arg(%rip)
call    a_bunch_of_arguments
```

*清单 18-46：在栈上传递结构体*

由于 arg 位于数据节中，我们用 RIP 相对寻址访问它。这里我们用到了一点新的汇编语法：arg+8(%rip) 表示标签 arg 之后 8 字节处的地址。因此，我们的第一条 push 指令会把结构体的第二个八字节组（包含成员 b）压入栈中 ❶。图 18-4 说明这样可以保持结构体在内存中的布局。

```text
数据节中的 arg：  偏移 0 处是 a，偏移 8 处是 b

第一条 pushq arg+8(%rip)  先把 b 压入栈中
第二条 pushq arg(%rip)    再把 a 压入栈中，位于 b 的下方

两条指令执行后，栈顶从低地址到高地址为：
    0(%rsp)：a      8(%rsp)：b
与 arg 在内存中的布局完全一致
```

*图 18-4：把结构体压入栈*

清单 18-46 中的两条 pushq 指令把 arg 的一个副本以正确的布局压入栈中。被调用者设置好自己的栈帧之后，就可以在 16(%rbp) 处访问 arg，这正是我们通常期望找到函数第一个栈参数的位置。

如果一个结构体属于 MEMORY 类别，我们将总是把它压入栈中。考虑清单 18-47 中的结构体类型声明和函数声明。

```c
struct pass_in_memory {
    double w;
    double x;
    int y;
    long z;
};

void accept_struct(struct pass_in_memory arg);
```

*清单 18-47：一个带属于 MEMORY 类别的结构体参数的函数声明*

清单 18-48 演示了如何把存储在 -32(%rbp) 处的一个结构体作为参数传递给 accept_struct。

```asm
pushq   -8(%rbp)
pushq   -16(%rbp)
pushq   -24(%rbp)
pushq   -32 (%rbp)
call    accept_struct
```

*清单 18-48：在栈上传递属于 MEMORY 类别的结构体*

在这个例子中，与清单 18-46 一样，我们通过从后往前把结构体压入栈中来保持它在内存中的布局。

### 返回结构体

如果一个结构体能装进单个寄存器，返回它就很简单。我们把属于 INTEGER 类别的结构体放在 RAX 中返回，把属于 SSE 类别的结构体放在 XMM0 中返回。如果一个结构体的大小在 8 到 16 字节之间，我们用两个寄存器返回它。为了适应这些结构体，我们再指定两个传送返回值的寄存器：RDX 和 XMM1。我们把结构体的每个八字节组放进相应类别的下一个可用返回寄存器中传送。例如，如果结构体的第一部分属于 SSE 类别而第二部分属于 INTEGER 类别，我们就在 XMM0 中传送第一部分，在 RAX 中传送第二部分。如果两部分都属于 SSE 类别，我们就在 XMM0 和 XMM1 中传送该结构体；如果两部分都属于 INTEGER 类别，我们就在 RAX 和 RDX 中传送它。

如果一个结构体属于 MEMORY 类别，情况还会更加棘手。这种情况下，由调用者为返回值分配空间，并把该空间的地址放在 RDI 寄存器中传给被调用者，就好像它是第一个整数参数一样。这意味着真正的第一个整数参数必须放在 RSI 中传递，第二个放在 RDX 中，依此类推。要返回一个值，被调用者把它复制到 RDI 指向的空间中，再把指针本身复制到 RAX 中。让我们看清单 18-49 中的例子。

```c
struct large_struct {
    long array[3];
};

struct large_struct return_a_struct(long i) {
    struct large_struct callee_result = {{0, 1, i}};
    return callee_result;
}

int main(void) {
  ❶ struct large_struct caller_result = return_a_struct(10);
    --snip--
}
```

*清单 18-49：调用通过内存返回结构体的函数*

由于 struct large_struct 是 24 字节，我们将通过内存返回 return_a_struct 函数的结果。在 main 中，我们调用 return_a_struct 并把结果赋给 caller_result ❶。假设 main 已经在 -24(%rbp) 处为 caller_result 预留了栈空间，清单 18-50 展示了如何实现这次函数调用。

```asm
leaq    -24(%rbp), %rdi
movq    $10, %rsi
call    return_a_struct
```

*清单 18-50：以汇编调用 return_a_struct*

首先，我们把 caller_result——它将保存 return_a_struct 的结果——的地址放进 RDI 传递。然后，我们把参数 10 放进下一个可用的传参寄存器 RSI 中传递。最后，我们发出 call 指令。图 18-5 展示了 call 指令执行前一刻程序的状态。

```text
        ┌───────────────────┐
RDI ──► │ -24(%rbp)：       │  caller_result（尚未初始化）
        │ caller_result    │
        └───────────────────┘
RSI  =  10（return_a_struct 的第一个参数）
RBP ──► 当前栈帧的底部
RSP ──► 当前栈帧的顶部
```

*图 18-5：调用 return_a_struct 之前栈和寄存器的状态*

和往常一样，RSP 和 RBP 分别指向当前栈帧的顶部和底部。RDI 指向尚未初始化的 caller_result。RSI 保存着 return_a_struct 的第一个参数 10。

注意，清单 18-50 并没有为 return_a_struct 的结果分配额外的栈空间；它只是加载 caller_result 变量的地址。这通常是没问题的，但有一个注意事项：根据 ABI，保存返回值的内存“不得与被调用者通过此参数以外的名字可见的任何数据重叠”。例如，如果你要实现函数调用 var = foo(1, 2, &var)，那么一方面把 var 的地址放进 RDI 作为返回值的存储位置，另一方面又把它作为普通参数放进 RCX，就会违反 ABI。相反，你需要分配额外的栈空间来保存 foo 的结果，并在函数返回之后把结果复制到 var。我们不需要担心这种情形，因为在 TACKY 生成期间，我们会为每次函数调用的结果生成一个新变量。

现在看清单 18-51，它用汇编实现了 return_a_struct。

```asm
return_a_struct:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $32, %rsp
    movq    $0, -24(%rbp)
    movq    $1, -16(%rbp)
    movq    %rsi, -8(%rbp)
  ❶ movq    -24(%rbp), %r10
    movq    %r10, (%rdi)
    movq    -16(%rbp), %r10
    movq    %r10, 8(%rdi)
    movq    -8(%rbp), %r10
    movq    %r10, 16(%rdi)
  ❷ movq    %rdi, %rax
    --snip--
```

*清单 18-51：通过内存返回结构体*

在函数开头，我们设置栈帧，在 -24(%rbp) 处为局部变量 callee_result 分配栈空间，然后初始化它。返回 result 的汇编代码从 ❶ 开始。首先，我们把 result 逐次 8 字节地复制到 RDI 指向的内存位置；我们把前 8 字节复制到 (%rdi)，接下来的 8 字节复制到 8(%rdi)，最后 8 字节复制到 16(%rdi)。然后，我们把指向返回值的指针从 RDI 复制到 RAX ❷。最后，我们执行函数尾声，这部分没有出现在这个清单中。图 18-6 展示了函数尾声执行前一刻程序的状态。

```text
被调用者的栈帧：
    -24(%rbp) 起：callee_result = {0, 1, 10}（已复制到 RDI 指向的内存）

RAX ──► 调用者栈帧中的 caller_result（main 中的 -24(%rbp)），现已保存返回值 {0, 1, 10}
RDI 仍指向同一地址（ABI 并不要求如此）
```

*图 18-6：从 return_a_struct 返回之前栈和寄存器的状态*

调用者栈帧中的 caller_result 变量现在保存着函数的返回值，而 RAX 保存着 caller_result 的地址。在这个例子中，RDI 寄存器也保存着那个地址，但这不是 ABI 所要求的。

关于结构体的调用约定，需要了解的内容我们都讲完了。现在可以着手改造汇编生成遍了！

## 汇编生成

这一遍会有几处变化。首先，我们需要生成汇编，把整个结构体从一个位置复制到另一个位置。Copy、Load、Store 和 CopyToOffset 指令都可以同时传送标量值和聚合值。我们需要实现的新指令 CopyFromOffset 也是如此。其次，我们要实现刚学过的 System V 调用约定。

我们先从汇编 AST 的几个小改动开始。

### 扩展汇编 AST

在清单 18-46 中，我们使用了操作数 arg+8(%rip) 来访问 RIP 相对标号加上常量偏移处的数据。我们经常需要这类操作数来访问具有静态存储期的结构体的成员。汇编 AST 已经可以指定大多数内存地址的常量偏移，但不能指定 RIP 相对地址的偏移。我们将通过给 Data 操作数添加一个偏移来消除这个限制：

```text
operand = --snip-- | Data(identifier, int)
```

我们还将引入两条新的汇编指令。首先是左移指令 shl。这条指令接受一个立即数作为源操作数，接受一个内存地址或寄存器作为目的操作数。它把目的操作数向左移动其源操作数指定的位数。例如，指令

```asm
shlq    $8, %rax
```

把 RAX 中的值向左移动 1 字节，把最低字节置为 0。如果这条指令执行前 RAX 中的值是 0x8，执行后就是 0x800。shl 指令将帮助我们把控不规则大小的结构体复制到寄存器中，以便把它们作为参数和返回值传递。因为我们无法直接访问寄存器内的每个单独字节，我们将用 shl 把每个字节移到位。

其次，我们将添加双操作数形式的逻辑右移指令 shr。（我们在第 13 章添加过它的单操作数形式，即把操作数右移 1 位。）与 shl 类似，它把目的操作数向右移动其源操作数指定的位数。它的用途与 shl 类似，帮助我们把控不规则大小的结构体从寄存器传出到内存中。

> **注意**
>
> shl 指令也有一个我们不会用到的单操作数形式；它是我们已经熟悉的 shr 单操作数形式的对应物。这两条指令还有另一种我们不会用到的形式，即使用 CL 寄存器作为源操作数的形式。

我们将扩展 binary_operator 来表示 shl 和 shr：

```text
binary_operator = --snip-- | Shl | ShrTwoOp
```

新的二元 shr 指令得到了一个相当难看的名字 ShrTwoOp，以便与汇编 AST 中已有的一元 Shr 指令区分开。

清单 18-52 给出了更新后的汇编 AST，这些改动以粗体标出。

```text
program = Program(top_level*)
assembly_type = Byte | Longword | Quadword | Double | ByteArray(int size, int alignment)
top_level = Function(identifier name, bool global, instruction* instructions)
          | StaticVariable(identifier name, bool global, int alignment, static_init* init_list)
          | StaticConstant(identifier name, int alignment, static_init init)
instruction = Mov(assembly_type, operand src, operand dst)
            | Movsx(assembly_type src_type, assembly_type dst_type, operand src, operand dst)
            | MovZeroExtend(assembly_type src_type, assembly_type dst_type,
                            operand src, operand dst)
            | Lea(operand src, operand dst)
            | Cvttsd2si(assembly_type dst_type, operand src, operand dst)
            | Cvtsi2sd(assembly_type src_type, operand src, operand dst)
            | Unary(unary_operator, assembly_type, operand)
            | Binary(binary_operator, assembly_type, operand, operand)
            | Cmp(assembly_type, operand, operand)
            | Idiv(assembly_type, operand)
            | Div(assembly_type, operand)
            | Cdq(assembly_type)
            | Jmp(identifier)
            | JmpCC(cond_code, identifier)
            | SetCC(cond_code, operand)
            | Label(identifier)
            | Push(operand)
            | Call(identifier)
            | Ret
unary_operator = Neg | Not | Shr
binary_operator = Add | Sub | Mult | DivDouble | And | Or | Xor | Shl | ShrTwoOp
operand = Imm(int) | Reg(reg) | Pseudo(identifier) | Memory(reg, int) | Data(identifier, int)
        | PseudoMem(identifier, int) | Indexed(reg base, reg index, int scale)
cond_code = E | NE | G | GE | L | LE | A | AE | B | BE
reg = AX | CX | DX | DI | SI | R8 | R9 | R10 | R11 | SP | BP
    | XMM0 | XMM1 | XMM2 | XMM3 | XMM4 | XMM5 | XMM6 | XMM7 | XMM14 | XMM15
```

*清单 18-52：带静态操作数偏移和移位指令的汇编 AST*

转换类型和 TACKY 操作数都非常简单。结构体类型与数组类型一样，被转换为 ByteArray 汇编类型。要把一个结构体类型转换为汇编类型，你需要在类型表中查找它的大小和对齐。我们将把结构体类型的 TACKY 变量转换为 PseudoMem 汇编操作数，就像处理数组那样。即便到第 III 部分实现寄存器分配之后，我们也总是把数组和结构体存储在内存而非寄存器中。

你遇到的一些 TACKY 变量可能具有不完整的结构体类型。（记住，声明一个带不完整类型的 extern 变量并取它的地址是合法的，但定义它或以任何其他方式使用它都是非法的。）像其他结构体类型的变量一样，把这些变量转换为 PseudoMem 操作数。把这些变量加入后端符号表时，你可以给它们一个占位的汇编类型；那个占位类型永远不会被用到。

接下来，我们处理 Copy、Load、Store、CopyToOffset 和 CopyFromOffset 指令。然后，我们再处理函数调用。

### 复制结构体

要把一个结构体复制到新位置，你不需要考虑它成员的类型或偏移；你只需要复制正确数量的字节。为了减少所需的 mov 指令数量，先每次复制 8 字节，直到剩余不足 8 字节；然后每次复制 4 字节；最后，当剩余不足 4 字节时，每次复制 1 字节。（x64 汇编中还有一条 2 字节的 mov 指令，但我们的汇编 AST 不支持它。）例如，如果 a 和 b 都是 20 字节的结构体，你应当把

```text
Copy(Var("a"), Var("b"))
```

转换为清单 18-53 中的汇编。

```text
Mov(Quadword, PseudoMem("a", 0), PseudoMem("b", 0))
Mov(Quadword, PseudoMem("a", 8), PseudoMem("b", 8))
Mov(Longword, PseudoMem("a", 16), PseudoMem("b", 16))
```

*清单 18-53：为非标量值实现 Copy*

第一条 Mov 指令把 a 的前 8 字节复制到 b；第二条指令把 a 的接下来 8 字节复制到 b 中相应的偏移处；最后一条指令复制剩下的 4 字节。这些 Mov 指令是非法的，因为它们的源操作数和目的操作数都在内存中，但指令修复遍会改写它们。

你可以用同样的方法翻译 Load 和 Store 指令。例如，如果 y 是一个 6 字节的结构体，你要把

```text
Load(Var("ptr"), Var("y"))
```

翻译为清单 18-54。

```text
Mov(Quadword, Pseudo("ptr"), Reg(AX))
Mov(Longword, Memory(AX, 0), PseudoMem("y", 0))
Mov(Byte, Memory(AX, 4), PseudoMem("y", 4))
Mov(Byte, Memory(AX, 5), PseudoMem("y", 5))
```

*清单 18-54：为非标量值实现 Load*

第一条指令把指针复制到 RAX 寄存器。接下来的每条 Mov 指令把存储在 RAX 中的地址的某个偏移处的一块数据复制到 y 中相应的偏移处。

你也可以用一串 Mov 指令为非标量值实现 CopyToOffset；唯一的区别是你要把指定的偏移加到每条指令的目的操作数上。再举一个 6 字节结构体 y 的例子，你要把

```text
CopyToOffset(src=Var("y"), dst="z", offset=8)
```

翻译为清单 18-55。

```text
Mov(Longword, PseudoMem("y", 0), PseudoMem("z", 8))
Mov(Byte, PseudoMem("y", 4), PseudoMem("z", 12))
Mov(Byte, PseudoMem("y", 5), PseudoMem("z", 13))
```

*清单 18-55：为非标量值实现 CopyToOffset*

最后，你需要实现新的 CopyFromOffset 指令。与其他复制数据的 TACKY 指令一样，它既接受标量操作数，也接受非标量操作数。我不会详细讲这条指令；你的处理方式应当与 CopyToOffset 基本相同。

我建议你写一个我称之为 copy_bytes 的辅助函数，它生成汇编指令，把任意数量的字节从一个 Memory 或 PseudoMem 操作数复制到另一个。你可以用这个辅助函数实现全部五条 TACKY 复制指令。之后在需要通过内存传递结构体参数和返回值时，它还会再次派上用场。

实现完 CopyFromOffset 并扩展其他复制指令以支持非标量值之后，你就可以着手处理函数调用了。

### 在函数调用中使用结构体

由于传递和返回结构体的规则很复杂，在深入伪代码之前，我们先讨论总体策略。首先，我们要写一个函数来对结构体类型的每个八字节组分类。然后，我们要扩展 classify_parameters 辅助函数——我们在第 13 章引入它，用于辅助调用者和被调用者两侧的参数传递。记住，这个函数返回三个列表：通过通用寄存器传递的操作数、通过 XMM 寄存器传递的操作数，以及通过栈传递的操作数。更新这个函数之后，这些列表中可能既包含标量值，也包含结构体值的八字节组。

接下来，我们将引入另一个辅助函数 classify_return_value，以类似的方式拆分返回值。它将返回一个通过通用寄存器返回的操作数列表、一个通过 XMM 寄存器返回的操作数列表，以及一个指示返回值是否通过内存传递的布尔标志。只有当两个列表都为空时，这个标志才为 True。

classify_return_value 处理标量值时，会返回一个空列表、一个只含单个元素的列表，以及一个 False 标志。而处理结构体时，它可能产生更有趣的结果。它的主要目的是把标量返回值和结构体返回值整理成相同的形状，以便我们用统一的方式处理它们。

有了这些辅助函数之后，我们将更新把 FunCall TACKY 指令转换为汇编的方式。在大多数情况下，我们可以像前几章那样传递参数。我们把从 classify_parameters 得到的每个操作数复制到相应的寄存器中或压入栈中，而不必操心它是标量值还是结构体的一部分。只有少数细节会变。首先，我们要考虑这样一种情况：如果 RDI 中保存着为返回值预留的空间的地址，它就可能不可用。我们还需要传送无法用单条 mov 指令处理的不规则大小的八字节组。我们将写一个新的辅助函数把这些八字节组移入寄存器。

获取函数的返回值则需要更大的改动。我们将用 classify_return_value 了解返回值的每个部分在哪里，然后把每个部分从相应的寄存器或内存地址复制到它的最终目的地。这还需要另一个辅助函数来把不规则大小的八字节组从寄存器中复制出来。

最后，我们处理被调用者一侧。这里与调用者一侧一样，处理参数的方式只会稍有变化，但处理返回值的方式变化相当大。我们同样会使用 classify_return_value 来确定把返回值的每个部分放到哪里。

*清单 18-58：扩展 classify_parameters 以支持结构体*

这个函数的第一处改动是新的布尔参数 return_in_memory。顾名思义，它指示函数的返回值是否通过内存传递。如果是，那个内存地址将通过 RDI 寄存器传递，这样其他参数可用的通用寄存器就少了一个。我们将相应地设置 int_regs_available。于是，在处理整数或指针类型的参数时，我们将使用 int_regs_available 而不是常量 6 作为可用通用寄存器的数量。（double 类型参数的处理方式与第 13 章完全相同，所以我把清单中的那部分截掉了。）

现在到了有趣的部分：处理结构体类型的参数。我们首先调用 classify_structure ❶。然后，检查该结构体的第一个八字节组是否属于 MEMORY 类别 ❷。如果是，结构体的其余部分必然也是。如果不是，我们就尝试把每个八字节组分配给寄存器。我们把每个八字节组转换为一个 PseudoMem 操作数 ❸，再根据它的类别加入 tentative_doubles 或 tentative_ints 两个列表之一。我们知道 v 是变量而不是常量，因为 TACKY 中不存在聚合常量；那个变量的名字将作为 PseudoMem 操作数的基址。

把一个八字节组加入 tentative_ints 时，我们需要确定与它关联的汇编类型。大多数八字节组恰好长 8 字节，所以我们把它们关联到 Quadword 类型。但结构体的最后一个八字节组可能更短。我们将用 get_eightbyte_type 辅助函数 ❹ 找到每个八字节组的汇编类型，稍后我们会讲它。这个函数接受两个参数：八字节组的偏移和结构体的总大小。它会用这两个参数算出八字节组的大小，而大小决定了它的汇编类型。

把整个结构体拆分到两个临时列表之后，我们检查是否有足够的空闲寄存器同时容纳它们 ❺。如果有，就把这两个列表追加到与它们对应的正式列表中。如果没有足够的寄存器，或者结构体属于 MEMORY 类别，我们就改为把每个八字节组加入 stack_args ❻。对通过栈传递的每个八字节组，我们都用 get_eightbyte_type 确定其类型。

*清单 18-59：把一个八字节组关联到一个 assembly_type*

这里的目标是确定把这个八字节组移入寄存器或压入栈时该使用多大的操作数。首先，我们计算从这个八字节组开头到整个结构体末尾之间的字节数 ❶。如果结构体中剩下的字节数多于 8，这就不是最后一个八字节组，所以我们使用 Quadword 类型。如果这个八字节组恰好长 8 字节、4 字节或 1 字节，我们分别使用 Quadword、Longword 或 Byte 类型。

否则，这个八字节组的大小就是不规则的；它不是汇编指令的合法操作数大小。这种情况下，我们用 ByteArray 类型记录该八字节组的精确字节大小 ❷。（这个 ByteArray 中的对齐是个占位值；之后我们用不到它。）我们无法安全地用单条 Mov 指令传送不规则大小的八字节组。正如你在第 9 章学到的，越过一个值的末尾读取内存——例如用 8 字节的 pushq 指令压入一个 4 字节的值——可能触发内存访问违例。出于同样的逻辑，用 8 字节的 movq 指令传送 5、6 或 7 字节的操作数，或用 4 字节的 movl 指令传送 3 字节的操作数，都是不安全的。我们稍后会看到如何传送不规则大小的八字节组。

注意，get_eightbyte_type 不考虑八字节组的类别；对任何全长的八字节组它都返回 Quadword，即使它属于 SSE 类别。这是正确的，因为我们只用 get_eightbyte_type 查找将通过通用寄存器或栈传送的值的类型。当我们把结构体的 8 字节压入栈时，并不关心这些字节里是浮点值还是整数。

*清单 18-60：对返回值分类*

如果返回值是 double，两个列表中的第一个——它包含通过通用寄存器返回的操作数——将为空。第二个列表（保存通过 XMM 寄存器返回的操作数）将包含该返回值。指示返回值通过内存传递的标志将是 False ❶。如果返回值是某种其他标量类型，我们把它连同它的类型加入通过通用寄存器返回的操作数列表。通过 XMM 寄存器返回的操作数列表将为空，标志仍为 False ❷。

```asm

movb    x(%rip), (%rsp)
movb    x+1(%rip), 1(%rsp)
movb    x+2(%rip), 2(%rsp)
```

#### 在寄存器中传送不规则结构体

我们还需要实现 copy_bytes_to_reg 和 copy_bytes_from_reg，它们把控不规则大小的八字节组传入和传出通用寄存器。这比在 copy_bytes 中那样在两个内存位置之间复制更棘手，因为我们无法直接访问通用寄存器中的每个单独字节。我们可以用相应的 1 字节别名（比如 AL 或 DIL）访问通用寄存器的最低字节，但无法单独访问它的其他字节。（每个寄存器的次低字节也有自己的别名——例如 AH 是 RAX 的次低字节——但我们的汇编 AST 不支持这些别名。即使支持，我们仍然无法访问其他 6 个字节。）

我们将用新的移位指令来绕过这一限制。让我们回到上一个例子中 3 字节的全局变量 x。如果需要把 x 复制到 RDI 中，我们将发出以下指令：

```asm
movb    x+2(%rip), %dil
shlq    $8, %rdi
movb    x+1(%rip), %dil
shlq    $8, %rdi
movb    x(%rip), %dil
```

我们先把 x 的最后一个字节复制到 RDI 的最低字节中（它的别名是 DIL）。然后，我们发出一条 shl 指令，把 RDI 向左移 1 字节。这把我们刚复制的字节移到 RDI 的次低字节，并把 DIL 清零。接着，我们把 x 的中间字节复制到 DIL 中，再发出一条 shl 指令。此时，x 的最后 2 个字节已经在寄存器中的正确位置上了，所以我们只需把 x 的第一个字节移入 DIL，就完成了。图 18-7 展示了每条指令执行后 RDI 的内容（以十六进制表示），假设 x 包含字节 0x1、0x2 和 0x3，而 RDI 的初始值为 0。

```text
movb x+2(%rip), %dil   之后：RDI = 0x03
shlq $8, %rdi          之后：RDI = 0x0300
movb x+1(%rip), %dil   之后：RDI = 0x0302
shlq $8, %rdi          之后：RDI = 0x030200
movb x(%rip), %dil     之后：RDI = 0x030201
```

*图 18-7：一次一字节地把结构体传入寄存器*

别让这里的字节顺序迷惑了你：因为我们的系统是小端（little-endian）的，当我们把值从 RDI 复制到内存或反过来时，RDI 中最低有效（最右边）的字节对应最低的内存地址。这意味着——有点反直觉——把值左移会把每个字节移到对应更高内存地址的位置。如果在把这个结构体复制进 RDI 之后，我们发出指令

```asm
movl    %edi, -4(%rbp)
```

那么内存中的内容将如图 18-8 所示。

```text
地址：      -4      -3      -2      -1
内容：      0x01    0x02    0x03    0x00
            └── 结构体（3 字节）──┘   （多写 1 字节）
```

*图 18-8：从寄存器复制结构体之后内存中的内容*

现在结构体在内存中按正确的顺序排列了。（这条 movl 指令还会在结构体末尾之后多写 1 字节的内存，只要你不把那个字节另作他用就没有问题。我们将一次 1 字节地在寄存器中传入和传出不规则大小的结构体，但与我们交互的其他翻译单元中的代码在安全时可能会以 4 字节和 8 字节为单位传送它们。）

这就是 copy_bytes_to_reg 的基本思想；现在来实现它。清单 18-62 给出伪代码。

```text
copy_bytes_to_reg(src_op, dst_reg, byte_count):
    offset = byte_count - 1
    while offset >= 0:
        src_byte = add_offset(src_op, offset)
        emit(Mov(Byte, src_byte, Reg(dst_reg)))
        if offset > 0:
            emit(Binary(Shl, Quadword, Imm(8), Reg(dst_reg)))
        offset -= 1
```

*清单 18-62：生成把字节从内存复制到寄存器的指令*

这个函数把 byte_count 个字节从 src_op 复制到 dst_reg。由于 src_op 是结构体的一部分，我们可以假设它是一个接受偏移的内存操作数，比如 PseudoMem 或 Memory。我们按相反的顺序遍历 src_op 的字节：从它最后一个字节（偏移为 byte_count - 1）开始，到字节零结束。我们用一个简单的辅助函数 add_offset 构造每个字节的汇编操作数。这个函数的伪代码我就不给了，它只是把指定的偏移加到 src_op 上。例如，如果 src_op 是 PseudoMem("x", 2)，那么 add_offset(src_op, 3) 应当返回 PseudoMem("x", 5)。

有了当前字节的汇编操作数后，我们发出一条 Mov 指令，把该字节复制到目的寄存器。接下来，除最后一次循环迭代外，我们都发出一条 Shl 指令，把整个寄存器左移 8 位。然后，我们把偏移减一，继续处理下一个字节。

要把字节从寄存器中复制出来，整个过程倒过来即可。下面是我们如何把 RDI 中的 3 个字节复制到栈上 -4(%rbp) 处：

```asm
movb    %dil, -4(%rbp)
shrq    $8, %rdi
movb    %dil, -3(%rbp)
shrq    $8, %rdi
movb    %dil, -2(%rbp)
```

首先，我们把 RDI 的最低字节复制到内存。然后，我们把 RDI 右移 1 字节，此时 DIL 中包含的是结构体的次低字节。我们重复这一过程，直到传送完全部字节。清单 18-63 给出生成这些指令的伪代码。

```text
copy_bytes_from_reg(src_reg, dst_op, byte_count):
    offset = 0
    while offset < byte_count:
        dst_byte = add_offset(dst_op, offset)
        emit(Mov(Byte, Reg(src_reg), dst_byte))
        if offset < byte_count - 1:
            emit(Binary(ShrTwoOp, Quadword, Imm(8), Reg(src_reg)))
        offset += 1
```

*清单 18-63：生成把字节从寄存器复制到内存的指令*

与清单 18-62 一样，我们可以假设 dst_op 是一个带偏移的内存操作数。我们按顺序遍历 dst_op 的字节，从字节零开始。每次迭代中，我们把 src_reg 的最低字节复制到 dst_op 的当前字节。然后，除最后一次迭代外，我们都把 src_reg 右移 8 位。

有了这两个辅助函数，我们就完成了函数调用的实现。接下来处理被调用者一侧。

#### 设置函数参数

在函数开头，我们把每个参数复制到该函数的栈帧中。现在我们也要复制结构体类型的参数。主要的麻烦在于，RDI 中保存的可能不是普通参数，而是指向返回值目的地的指针。让我们回顾一下清单 13-30 中的 set_up_parameters，看看它有哪些变化。清单 18-64 给出 set_up_parameters 的新定义，本章的改动以粗体标出。

*清单 18-64：把函数参数复制到栈*

我们添加了一个 return_in_memory 标志，并把它传递给 classify_parameters。这个标志还决定了我们如何处理 RDI 中的值。如果 RDI 指向返回值的目的地，我们就把它复制到栈上第一个空闲的槽位 -8(%rbp) 处；需要返回值时，我们会从这个槽位把它取回。（在下一节中，我们会更新伪操作数替换遍，避免它把某个局部变量分配到同一个位置而覆盖这个指针。）这种情况下，我们还要像在清单 18-61 中传参时那样递增 reg_index，这样我们就从 RSI 而不是 RDI 开始查找普通参数。

要从寄存器中复制不规则大小的操作数，我们使用清单 18-63 中的 copy_bytes_from_reg 辅助函数。要复制通过栈传递的不规则大小的操作数，我们使用 copy_bytes 辅助函数。如果操作数的类型是 Byte、Longword、Quadword 或 Double，无论它表示的是标量值还是结构体的一块，我们都用单条 Mov 指令把它复制到位。

#### 实现 Return

清单 18-65 演示了如何把 Return 指令转换为汇编。

```text
convert_return_instruction(Return(retval)):

        emit(Ret)

    int_retvals, double_retvals, return_in_memory = classify_return_value(retval)

        return_storage = Memory(AX, 0)

        t = assembly_type_of(retval)

        for (t, op) in int_retvals: ❸
            r = int_return_registers[reg_index]

            else:
                emit(Mov(t, op, Reg(r)))
            reg_index += 1

        reg_index = 0
        for op in double_retvals: ❹
            r = double_return_registers[reg_index]

            reg_index += 1

```

*清单 18-65：实现 Return 指令*

假设函数返回一个值而不是 void，我们首先对这个值分类。然后，检查需要通过内存还是寄存器返回它。要通过内存返回，我们首先从 -8(%rbp) 取回指向目的地的指针。我们把这个指针复制到 RAX，这是 System V 调用约定所要求的 ❶。然后，我们把返回值复制到 RAX 指向的内存块。我们用 copy_bytes 辅助函数 ❷ 执行这次复制。

如果返回值通过一个或多个寄存器传递，我们遍历 int_retvals 中的操作数，把每个操作数复制到相应的通用寄存器 ❸。然后遍历 double_retvals，把这些值复制到 XMM0 和 XMM1 ❹。把返回值的每个部分都复制到正确位置之后，我们发出一条 Ret 指令。

最后，我们将扩展后端符号表，以跟踪哪些函数通过内存传递返回值。清单 18-66 展示了如何更新我们对后端符号表条目的定义。

*清单 18-66：后端符号表条目的更新定义*

正如你所料，如果一个函数通过栈传递其返回值，我们就把 return_on_stack 设为 True；如果它通过寄存器传递其返回值或返回 void，就设为 False。伪操作数替换遍将用这个标志判断从 -8(%rbp) 开始的四字（quadword）是否可用，或者它是否保存着指向返回值传递内存的指针。如果一个函数的返回类型是 void 以外的不完整类型（在函数被声明但从未定义或调用时可能出现这种情形），return_on_stack 标志永远不会被用到，所以直接把它设为 False 即可。

### 替换伪操作数

我们将对这一遍做两处小改动。第一，我们要为 Data 操作数提供偏移。例如，如果 v 是静态变量，我们会把

```text
PseudoMem("v", 0)
```

转换为

```text
Data("v", 0)
```

并把

```text
PseudoMem("v", 10)
```

转换为：

```text
Data("v", 10)
```

第二，我们需要避免覆盖 -8(%rbp) 中的返回值指针。在开始分配栈空间之前，我们会查询后端符号表，看这个函数的返回值是否会通过内存传递。如果会，我们就把从 -8(%rbp) 开始的四字保留给返回值指针，只在地址低于 -8(%rbp) 的位置为伪寄存器分配空间。例如，如果我们遇到的第一个伪寄存器是 Longword，我们就把它映射到 -12(%rbp)。

本章中，指令修复遍不会改变。我们在代码生成期间发出的 shl 和 shr 指令已经是合法的，不需要修复，因为目的操作数总是寄存器，而源操作数总是立即数 8。

## 代码发射

代码发射遍需要两处小改动。第一，我们要在 Data 操作数中包含偏移。例如，我们将把 Data("x", 4) 发射为：

```asm
x+4(%rip)
```

如果偏移为零，包含或省略它都可以。

第二，我们将把新的 Shl 和 ShrTwoOp 汇编指令分别发射为 shl 和 shr。它们使用通常的操作数大小后缀。

## 附加挑战：联合体

结构体类型和联合体类型有很多共同之处。它们的类型声明语法相同，并且在同一个名字空间中声明标签。它们遵循相同的类型规则，支持相同的操作，包括 `->` 和 `.` 运算符。区别在于，结构体的成员在内存中是顺序排列的，而联合体的所有成员都从同一个地址开始，写入其中一个就会覆盖其他成员。从编译器的角度看，联合体基本上就是每个成员的偏移都为零的结构体。这使得把你在本章完成的工作扩展到支持联合体相对容易。尽管如此，这个挑战比之前的附加挑战特性都要大。这是一个独立添加新语言特性的机会。

如果你实现联合体类型，有几点需要记住。首先，记住我们限制了结构体可以在哪里声明，以便让编译更容易。联合体的测试用例也遵循同样的限制；也就是说，你不需要支持匿名联合体声明，或作为其他类型或变量声明之一部分的联合体声明。

在类型检查器中，你要把联合体定义加入类型表。结构体标签和联合体标签共享同一个名字空间，所以在同一作用域中定义同名的结构体类型和联合体类型是错误的。你需要跟踪每个联合体的大小和对齐（如何计算它们可以查阅 System V ABI）。你还需要对联合体的复合初始化器做类型检查。联合体初始化器应当只有一个元素，它初始化联合体的第一个成员。（C 提供了指定初始化哪个联合体成员的语法，但你不必实现它。）

在后端，System V 调用约定对待联合体的方式与结构体类似；一个联合体将根据其大小和成员类型，通过内存、两个寄存器或一个寄存器传递。欲了解所有繁琐的细节，请参见“延伸资源”中的链接。祝你好运！

你可以使用 --union 标志来测试你的编译器对联合体类型的支持：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 18 --union
```

或者，你也可以使用 --extra-credit 标志来测试所有附加挑战特性。
