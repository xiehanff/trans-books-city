# 第 4 章 理解类型
*Chapter 4: Understanding Types*

在第 2 章中，我们记录了订单处理系统中某一个工作流的领域驱动需求。接下来的挑战，是把这些非正式的需求转换为可编译的代码。

我们采用的方法，是用 F# 的“代数类型系统（algebraic type system）”来表示这些需求。在本章中，我们将学习什么是代数类型、它们如何定义和使用，以及它们如何表示领域模型。然后在下一章中，我们将运用所学的知识精确地对下单工作流建模。

## 理解函数

在理解类型之前，我们需要先理解函数式编程（functional programming）中最基本的概念——函数。

如果你还记得高中数学，函数是一种带有输入和输出的黑盒。你可以把它想象成一小段铁轨，上面架着一座“变换隧道”。某个东西从一端进去，经过某种变换，再从另一端出来。

例如，假设这个特定的函数会把苹果变成香蕉。我们描述一个函数的方式，是把输入和输出写下来、中间用一个箭头分隔，如图所示（苹果 → 变换隧道 → 香蕉）。

### 类型签名

“苹果 -> 香蕉”这样的描述称为类型签名（type signature，也称函数签名）。这个特定的签名很简单，但类型签名可能变得非常复杂。理解并使用类型签名是用 F# 编码的关键一环，所以让我们确保真正理解它们的工作原理。

下面是两个函数：add1 给它唯一的输入 x 加 1；add 把它的两个输入 x 和 y 相加：

```fsharp
let add1 x = x + 1   // 签名是：int -> int

let add x y = x + y  // 签名是：int -> int -> int
```

如你所见，let 关键字用于定义函数。参数之间用空格分隔，没有括号，也没有逗号。与 C# 或 Java 不同，这里没有 return 关键字；函数定义中的最后一个表达式就是函数的输出。

尽管 F# 关心输入和输出的类型，但你几乎不需要显式声明它们，因为在大多数情况下，编译器会自动为你推断类型（type inference）。[22]

对于 add1，推断出的 x 的类型（箭头之前）是 int，推断出的输出类型（箭头之后）也是 int，所以类型签名是 `int -> int`。

对于 add，推断出的 x 和 y 的类型是 int，推断出的输出类型（最后一个箭头之后）也是 int。add 有两个参数，每个参数之间都由箭头分隔，所以类型签名是 `int -> int -> int`。

如果你使用的是 Visual Studio 之类的 IDE（集成开发环境），把鼠标悬停在函数定义上就能看到它的类型签名；不过这是一本书，所以在需要明确说明时，我们会把类型签名以注释的形式写在定义的上方。它只是注释，编译器并不会使用。

由多行组成的函数通过缩进来书写（类似 Python），没有花括号。下面是一个例子：

```fsharp
// squarePlusOne : int -> int
let squarePlusOne x =
  let square = x * x
  square + 1
```

这个例子还表明：你可以在函数内部定义子函数（`let square = ...`），而且同样，最后一行（square + 1）就是返回值。

### 带泛型类型的函数

如果函数对任何类型都能工作，编译器就会自动推断出泛型类型（generic type），比如下面这个 areEqual 函数：

```fsharp
// areEqual : 'a -> 'a -> bool
let areEqual x y =
  (x = y)
```

对于 areEqual，推断出的 x 和 y 的类型是 `'a`。撇号加字母是 F# 表示泛型类型的方式。事实也确实如此：x 和 y 可以是任何类型，只要它们是同一种类型。

顺便一提，这段代码表明 F# 中的相等判断用的是 =，而不是类 C 语言中的 ==。作为对比，下面是 C# 中用泛型实现同样 areEqual 的代码，大致长这样：

```csharp
static bool AreEqual<T>(T x, T y)
{
  return (x == y);
}
```

> **术语警示：“值”、“对象”与“变量”**
>
> 在函数式编程语言中，大多数东西被称为“值”。在面向对象语言中，大多数东西被称为“对象”。那么“值”和“对象”的区别是什么？
>
> 值只是类型的一个成员，是某个可以用作输入或输出的东西。例如，1 是 int 类型的值，"abc" 是 string 类型的值，等等。
>
> 函数也可以是值。如果我们定义一个简单的函数，比如 `let add1 x = x + 1`，那么 add1 就是一个类型为 `int -> int` 的（函数）值。
>
> 值是不可变的（这也正是它们不叫“变量”的原因）。值也没有任何附加的行为，它们只是数据。
>
> 与之相反，对象是数据结构及其相关行为（方法）的封装。一般而言，对象被认为应当拥有状态（也就是可变的），而且所有改变内部状态的操作都必须由对象自身提供（通过“点”表示法调用）。
>
> 所以，在函数式编程的世界里（那里并不存在对象），你应该使用“值”这个术语，而不是“变量”或“对象”。

## 类型的组合

在函数式编程中，你会经常听到“组合”（composition）这个词——它是函数式设计的基石。组合的意思很简单：你可以把两个东西结合起来，做成一个更大的东西，就像搭乐高积木一样。

在函数式编程的世界里，我们用组合从较小的函数构建新函数，从较小的类型构建新类型。现在我们先讨论类型的组合；函数组合则留到后面的第 8 章“理解函数”再谈。

在 F# 中，新类型通过两种方式由较小的类型构建：

- 通过把它们“与”（AND）在一起
- 通过把它们“或”（OR）在一起

### “AND”类型

我们先从用 AND 构建类型开始。例如，我们可以说：做水果沙拉，需要一个苹果、一根香蕉，还要一些樱桃：

在 F# 中，这类类型称为记录类型（record type）。FruitSalad 记录类型的定义可以这样写：

```fsharp
type FruitSalad = {
  Apple: AppleVariety
  Banana: BananaVariety
  Cherries: CherryVariety
}
```

花括号表明这是一个记录类型，三个字段分别是 Apple、Banana 和 Cherries。

### “OR”类型

构建新类型的另一种方式是使用 OR。例如，我们可以说：做水果点心，需要的是一个苹果、或一根香蕉、或一些樱桃：

这类“选择”类型（choice type）对建模来说会极其有用（我们在整本书中都会看到这一点）。下面是用选择类型定义的 FruitSnack：

```fsharp
type FruitSnack =
  | Apple of AppleVariety
  | Banana of BananaVariety
  | Cherries of CherryVariety
```

这样的选择类型在 F# 中称为可区分联合（discriminated union，DU）。它可以这样解读：

一个 FruitSnack，要么是一个 AppleVariety（带有 Apple 标签），要么是一个 BananaVariety（带有 Banana 标签），要么是一个 CherryVariety（带有 Cherries 标签）。

竖线分隔每个选择；标签（比如 Apple 和 Banana）是必需的，因为有时两个或更多选择可能是同一类型，需要靠标签来区分。

水果的品种本身也定义为 OR 类型，在这里的用法与其他语言中的枚举（enum）类似：

```fsharp
type AppleVariety =
  | GoldenDelicious
  | GrannySmith
  | Fuji

type BananaVariety =
  | Cavendish
  | GrosMichel
  | Manzano

type CherryVariety =
  | Montmorency
  | Bing
```

可以这样解读：

一个 AppleVariety，要么是 GoldenDelicious，要么是 GrannySmith，要么是 Fuji，等等。

> **术语警示：“积类型”与“和类型”**
>
> 使用 AND 构建的类型称为积类型（product type）。
>
> 使用 OR 构建的类型称为和类型（sum type），也叫标签联合（tagged union），或者用 F# 的术语来说，称为可区分联合。在本书中我常常把它们称作选择类型，因为我认为这个词最能描述它们在领域建模中扮演的角色。

### 简单类型

我们经常会定义只有单个选择的选择类型，比如：

```fsharp
type ProductCode =
  | ProductCode of string
```

这种类型几乎总会被简化写成：

```fsharp
type ProductCode = ProductCode of string
```

为什么要创建这样的类型？因为这是创建“包装器”（wrapper）的便捷方式——一个把基本类型（如 string 或 int）作为内部值包含起来的类型。

在领域建模时，我们会大量见到这类类型。在本书中，我会把这些只含单个分支的可区分联合称为“简单类型”（simple type），以区别于记录类型和可区分联合这样的复合类型。关于它们的更多讨论，见“简单类型”一节。

### 代数类型系统

现在我们可以给“代数类型系统”下定义了。它没有听起来那么吓人——一个代数类型系统只不过是这样一种系统：每个复合类型都是通过把较小的类型 AND 或 OR 在一起组合而成的。F# 和大多数函数式语言一样（但与面向对象语言不同），内置了代数类型系统。

用 AND 和 OR 来构建新的数据类型应该会让你觉得眼熟——我们在记录领域时用过的正是同样的 AND 和 OR。很快我们就会看到，代数类型系统确实是领域建模的一件利器。

## 使用 F# 类型

在 F# 中，类型的定义方式和构造方式非常相似。

例如，要定义一个记录类型，我们使用花括号，然后为每个字段写出“名字:类型”形式的定义，像这样：

```fsharp
type Person = {First:string; Last:string}
```

要构造这种类型的一个值，我们使用同样的花括号，但改用 = 为字段赋值，像这样：

```fsharp
let aPerson = {First="Alex"; Last="Adams"}
```

而要用模式匹配（pattern matching）解构这种类型的值，我们使用同样的语法，只是这次写在等号左边，像这样：

```fsharp
let {First=first; Last=last} = aPerson
```

这段代码的意思是：值 first 和 last 会被设置为记录中对应字段的内容。对于记录，我们还可以使用更熟悉的点语法，因此上面的代码等价于：

```fsharp
let first = aPerson.First
let last = aPerson.Last
```

构造与解构之间的这种对称性同样适用于可区分联合。要定义选择类型，我们用竖线分隔每个选择，每个选择都写成“分支标签 of 类型”的形式，像这样：

```fsharp
type OrderQuantity =
  | UnitQuantity of int
  | KilogramQuantity of decimal
```

构造选择类型的方式，是把任意一个分支标签当作构造函数（constructor function）来用，并把关联的信息作为参数传入，像这样：

```fsharp
let anOrderQtyInUnits = UnitQuantity 10
let anOrderQtyInKg = KilogramQuantity 2.5
```

分支并不是子类——UnitQuantity 和 KilogramQuantity 本身并不是类型，它们只是 OrderQuantity 类型的不同分支。在上面的例子中，这两个值的类型相同：都是 OrderQuantity。

要解构选择类型，我们必须使用模式匹配（`match..with` 语法），为每个分支提供一个测试，像这样：

```fsharp
let printQuantity aOrderQty =
  match aOrderQty with
  | UnitQuantity uQty ->
    printfn "%i units" uQty
  | KilogramQuantity kgQty ->
    printfn "%g kg" kgQty
```

作为匹配过程的一部分，与特定分支关联的数据也会被提取出来。在上面的例子中，如果输入匹配 UnitQuantity 分支，uQty 值就会被绑定。

把前面定义的两个值传入后，模式匹配的结果如下：

```fsharp
printQuantity anOrderQtyInUnits // "10 units"
printQuantity anOrderQtyInKg    // "2.5 kg"
```

## 通过组合类型构建领域模型

可组合的类型系统是做领域驱动设计（domain-driven design）的得力助手，因为只需把类型按不同的方式混合搭配，我们就能快速创建出复杂的模型。例如，假设我们要跟踪一个电商网站的支付情况。我们来看看在一次设计讨论中，可以如何用代码把它勾勒出来。

首先，我们从一些针对基本类型的包装器开始，比如 CheckNumber。它们就是前面讨论过的“简单类型”。这样做赋予了它们有意义的名字，也让领域的其余部分更容易理解。

```fsharp
type CheckNumber = CheckNumber of int
type CardNumber = CardNumber of string
```

接下来，我们构建一些底层类型。CardType 是一个 OR 类型——在 Visa 或 Mastercard 之间做选择；而 CreditCardInfo 是一个 AND 类型，是一个包含 CardType 和 CardNumber 的记录：

```fsharp
type CardType =
  Visa | Mastercard        // 'OR' 类型

type CreditCardInfo = {    // 'AND' 类型（记录）
  CardType : CardType
  CardNumber : CardNumber
  }
```

然后，我们再定义另一个 OR 类型 PaymentMethod，表示“现金、支票或刷卡”三选一。它已经不再是一个简单的“枚举”了，因为其中一些选择带有数据：Check 分支带有一个 CheckNumber，Card 分支带有 CreditCardInfo：

```fsharp
type PaymentMethod =
  | Cash
  | Check of CheckNumber
  | Card of CreditCardInfo
```

我们还可以再定义几个基本类型，比如 PaymentAmount 和 Currency：

```fsharp
type PaymentAmount = PaymentAmount of decimal
type Currency = EUR | USD
```

最后，顶层类型 Payment 是一个记录，包含一个 PaymentAmount、一个 Currency 和一个 PaymentMethod：

```fsharp
type Payment = {
  Amount : PaymentAmount
  Currency:  Currency
  Method:  PaymentMethod
  }
```

就是这么回事。在大约 25 行代码里，我们已经定义了一组相当有用的类型。

当然，这些类型没有直接关联任何行为，因为这是一个函数式模型，而不是面向对象模型。为了记录可以执行的动作，我们转而定义表示函数的类型。

例如，如果想表明存在一种用 Payment 类型为未支付发票付款、最终得到已支付发票的方式，我们可以定义这样的函数类型：

```fsharp
type PayInvoice =
  UnpaidInvoice -> Payment -> PaidInvoice
```

它的含义是：给定一个 UnpaidInvoice，再给定一个 Payment，我们就能创建出一个 PaidInvoice。

再比如，把一笔支付从一种货币转换为另一种货币：

```fsharp
type ConvertPaymentCurrency =
  Payment -> Currency -> Payment
```

其中第一个 Payment 是输入，第二个参数（Currency）是要转换到的目标货币，第二个 Payment——也就是输出——是转换后的结果。

## 为可选值、错误和集合建模

趁着我们正在讨论领域建模，来谈谈一些常见的情形，以及如何用 F# 类型系统来表示它们，即：

- 可选值或缺失值
- 错误
- 不返回值的函数
- 集合

### 为可选值建模

到目前为止我们使用的类型——记录类型和选择类型——在 F# 中都不允许为 null。这意味着，在领域模型中每当我们引用某个类型时，它都是一个必需的值。

那么，我们该如何为缺失或可选的数据建模呢？

答案是思考缺失数据到底意味着什么：它要么存在，要么不存在。那里要么有点什么，要么什么都没有。我们可以用一个名为 Option 的选择类型来建模，它的定义如下：

```fsharp
type Option<'a> =
  | Some of 'a
  | None
```

Some 分支表示在关联的值 `'a` 中存有数据；None 分支表示没有数据。再说一次，`'a` 中的撇号是 F# 表示泛型类型的方式——也就是说，Option 类型可以用来包装任何其他类型。C# 或 Java 中的等价物大致是 `Option<T>`。

你不需要自己定义 Option 类型。它是 F# 标准库的一部分，并且附带了一组丰富的辅助函数。

因此，要在领域模型中表示可选数据，我们就把类型包在 `Option<..>` 里，就像在 C# 或 Java 中做的那样。例如，假设我们有一个 PersonalName 类型，名和姓是必需的，而中间名缩写是可选的，就可以这样建模：

```fsharp
type PersonalName = {
  FirstName : string
  MiddleInitial: Option<string>  // 可选
  LastName : string
  }
```

F# 还支持把 option 标签放在类型后面，这样更易读，也更常用：

```fsharp
type PersonalName = {
  FirstName : string
  MiddleInitial: string option
  LastName : string
  }
```

### 为错误建模

假设我们有一个可能失败的过程：“支付成功了，或者因为卡片已过期而失败。”该怎么建模？F# 确实支持抛出异常（exception），但我们常常希望在类型签名中显式记录“可能发生失败”这一事实。这正好适合用一个只有两个分支的选择类型，所以我们来定义一个 Result 类型：

```fsharp
type Result<'Success,'Failure> =
  | Ok of 'Success
  | Error of 'Failure
```

我们将用 Ok 分支在函数成功时持有返回值，用 Error 分支在函数失败时持有错误数据。当然，我们希望这个类型能够容纳任何类型的数据，因此定义中使用了泛型类型。

如果你使用的是 F# 4.1 或更高版本（或 Visual Studio 2017），就不需要自己定义 Result 类型，它已经是 F# 标准库的一部分。如果使用更早版本的 F#，你也能只用几行代码轻松定义它以及它的辅助函数。

为了表示一个函数可能失败，我们用 Result 类型包装它的输出。例如，如果 PayInvoice 函数可能失败，就可以这样定义：

```fsharp
type PayInvoice =
  UnpaidInvoice -> Payment -> Result<PaidInvoice,PaymentError>
```

这表明与 Ok 分支关联的类型是 PaidInvoice，与 Error 分支关联的类型是 PaymentError。接着，我们可以把 PaymentError 定义为一个选择类型，为每种可能的错误各设一个分支：

```fsharp
type PaymentError =
  | CardTypeNotRecognized
  | PaymentRejected
  | PaymentProviderOffline
```

这种记录错误的方式将在第 10 章“实现之错误处理”中详细讨论。

### 为“完全没有值”建模

大多数编程语言都有 void 的概念，用在函数或方法不返回任何东西的时候。

在 F# 这样的函数式语言中，每个函数都必须返回点什么，所以我们不能用 void，而是使用一个特殊的内置类型——单元类型（unit type）。单元类型只有一个值，写作一对圆括号：`()`。

假设你有一个函数，用来更新数据库中的客户记录。输入是一个客户记录，但没有有用的输出。在 F# 中，我们会把类型签名写成用 unit 作为输出类型，像这样：

```fsharp
type SaveCustomer = Customer -> unit
```

（当然，实践中它会比这复杂得多！关于数据库操作的详细讨论，见第 12 章“持久化”。）

另外，假设你有一个没有输入却返回有用结果的函数，比如生成随机数的函数。在 F# 中，你同样可以用 unit 表示“没有输入”，像这样：

```fsharp
type NextRandom = unit -> int
```

当你在签名中看到单元类型时，这就是存在副作用（side effect）的强烈信号。某处的什么东西正在改变状态，只是对你隐藏了。一般来说，函数式程序员会尽量避免副作用，或者至少把副作用限制在代码中受限的区域里。

### 为列表和集合建模

F# 的标准库支持多种不同的集合（collection）类型：

- list 是固定大小的不可变集合（用链表实现）。
- array 是固定大小的可变集合，可以按索引获取单个元素，也可以按索引给元素赋值。
- ResizeArray 是大小可变的数组，也就是说，可以向数组中添加元素，或从中移除元素。它是 C# 的 `List<T>` 类型在 F# 中的别名。
- seq 是惰性集合，每个元素都在需要时才返回。它是 C# 的 `IEnumerable<T>` 类型在 F# 中的别名。

此外还有内置的 Map（类似 Dictionary）和 Set 类型，但它们很少在领域模型中直接使用。

对于领域建模，我建议始终使用 list 类型。和 option 一样，它可以用作类型的后缀（这让代码非常好读），像这样：

```fsharp
type Order = {
  OrderId : OrderId
  Lines : OrderLine list // 一个集合
  }
```

创建列表时，可以使用列表字面量，用方括号和分号（不是逗号！）作分隔符：

```fsharp
let aList = [1; 2; 3]
```

也可以用 `::` 运算符（也称为“cons”）把一个值前插到已有列表上：

```fsharp
let aNewList = 0 :: aList  // 新列表是 [0;1;2;3]
```

要解构列表以便访问其中的元素，可以使用类似的模式。可以像这样匹配列表字面量：

```fsharp
let printList1 aList =
  // 匹配列表字面量
  match aList with
  | [] ->
    printfn "list is empty"
  | [x] ->
    printfn "list has one element: %A" x
  | [x;y] ->       // 用列表字面量匹配
    printfn "list has two elements: %A and %A" x y
  | longerList ->  // 匹配其余任何情况
    printfn "list has more than two elements"
```

或者，也可以用“cons”运算符来匹配，像这样：

```fsharp
let printList2 aList =
  // 用 "cons" 匹配
  match aList with
  | [] ->
    printfn "list is empty"
  | first::rest ->
    printfn "list is non-empty with the first element being: %A" first
```

## 在文件和项目中组织类型

还有最后一件你应该知道的事。F# 对声明顺序有严格的规则：文件中靠前的类型不能引用文件中更靠后的类型；编译顺序中靠前的文件也不能引用编译顺序中更靠后的文件。这意味着，在编写类型时，你必须考虑如何组织它们。

一种标准做法是把所有领域类型放进一个文件（比如 Types.fs 或 Domain.fs），然后把依赖这些类型的函数放到编译顺序中更靠后的位置。如果类型很多、需要拆分到多个文件，就把共享的类型放在前面，特定于子领域的类型放在后面。你的文件列表可能像这样：

```fsharp
Common.Types.fs
Common.Functions.fs
OrderTaking.Types.fs
OrderTaking.Functions.fs
Shipping.Types.fs
Shipping.Functions.fs
```

在单个文件内，这条规则意味着要把简单类型放在文件顶部，把（依赖它们的）更复杂的类型按依赖顺序放在更靠下的位置：

```fsharp
module Payments =
  // 简单类型放在文件顶部
  type CheckNumber = CheckNumber of int

  // 领域类型放在文件中部
  type PaymentMethod =
    | Cash
    | Check of CheckNumber // 在上面定义
    | Card of ...

  // 顶层类型放在文件底部
  type Payment = {
    Amount: ...
    Currency: ...
    Method: PaymentMethod  // 在上面定义
    }
```

当你自顶向下地开发模型时，依赖顺序的约束有时会带来不便，因为你常常想把底层类型写在高层类型的下面。在 F# 4.1 中，你可以在模块或命名空间级别使用 rec 关键字来解决这个问题。rec 关键字允许类型引用模块中任何位置的其他类型。

```fsharp
module rec Payments =
  type Payment = {
    Amount: ...
    Currency: ...
    Method: PaymentMethod  // 在下方定义
    }

  type PaymentMethod =
    | Cash
    | Check of CheckNumber // 在下方定义
    | Card of ...

  type CheckNumber = CheckNumber of int
```

对于更早版本的 F#，你可以使用 and 关键字，允许一个类型定义引用紧接在它下面的类型定义。

```fsharp
type Payment = {
    Amount: ...
    Currency:  ...
    Method:  PaymentMethod // 在下方定义
    }

and PaymentMethod =
  | Cash
  | Check of CheckNumber   // 在下方定义
  | Card of ...

and CheckNumber = CheckNumber of int
```

这种乱序的写法用于草图阶段没有问题，可一旦设计定型、准备投入生产，通常最好还是把类型按正确的依赖顺序排列。这既能与其他 F# 代码保持一致，也便于其他开发者阅读。

关于在项目中组织类型的真实案例，请参阅本书的代码仓库。
