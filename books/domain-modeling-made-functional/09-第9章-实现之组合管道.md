# 第 9 章 实现之组合管道

*Chapter 9: Implementation: Composing a Pipeline*

到目前为止，我们已经花了大量时间只用类型来对领域建模，却还没有实现任何东西！现在就来弥补这一点。

在接下来的两章里，我们将使用之前所做的设计（第 7 章「把工作流建模为管道」），并用函数式原则把它实现出来。

回顾一下该章的设计：工作流可以被看作一系列文档变换——一条管道——管道中的每一步都设计成一节「管子」。

从技术角度看，我们的管道包含下面这些阶段：

1. 从一个 UnvalidatedOrder 开始，将其转换成 ValidatedOrder；如果验证失败则返回错误。
2. 接收验证步骤的输出（ValidatedOrder），通过添加一些额外信息把它变成 PricedOrder。
3. 接收定价步骤的输出，据此创建确认函（acknowledgment letter）并发送它。
4. 创建一组表示发生了什么的事件并返回它们。

我们想把它变成代码，既保留原始需求，又不纠缠于技术细节。

下面这个例子展示了我们希望代码长成什么样——用之前讨论过的管道方式，把每一步的函数连接起来：

```fsharp
let placeOrder unvalidatedOrder =
  unvalidatedOrder
  |> validateOrder
  |> priceOrder
  |> acknowledgeOrder
  |> createEvents
```

这段代码——一系列步骤——很容易理解，即使对非开发人员也是如此。那么我们来看看要实现它需要些什么。实现这个工作流有两部分工作：先创建各个步骤，然后把它们组合起来。

首先，我们把管道中的每一步实现为一个独立的函数，并确保它是无状态的（stateless）且没有副作用，这样它就可以被独立测试和独立推理。

接下来，我们只需把这些较小的函数组合成一个较大的函数。理论上听起来很简单。但正如我们之前提到的，一旦真正尝试，就会遇到一个问题：按目前设计出来的函数并不能很好地拼在一起——一个函数的输出与下一个函数的输入不匹配。为了克服这个问题，我们需要学习如何操纵每个步骤的输入和输出，使它们能够被组合。

这些函数无法组合，原因有二：

- 有些函数带有不属于数据管道的额外参数，但实现上又需要它们——我们之前称之为「依赖」。
- 我们用 Result 之类的包装类型在函数签名中显式地标明了「效应」，比如错误处理。但这意味着输出中带效应的函数，无法直接连接到输入只是未包装的普通数据的函数。

本章将处理第一个问题——作为依赖的输入，我们会看到如何以函数式的等价做法实现「依赖注入」。如何处理效应则留到下一章。

因此，在第一轮编写真实代码时，我们将实现所有步骤而不考虑 Result、Async 之类的效应。这样可以让我们专注于组合的基础。

## 使用简单类型

在开始实现工作流本身的各步骤之前，我们需要先实现「简单类型」，例如 OrderId 和 ProductCode。

由于大多数类型都带有某种约束，我们将遵循之前讨论过的受约束类型的实现大纲。

因此，对每个简单类型，我们至少需要两个函数：

- 一个 create 函数，从 string 或 int 之类的基本类型构造该类型——例如 OrderId.create 会从一个 string 创建 OrderId，如果字符串格式不对则抛出错误。
- 一个 value 函数，用于提取内部的基本类型值。

我们通常把这些辅助函数与简单类型放在同一个文件里，用一个与类型同名的模块来承载它们。例如，下面是 Domain 模块中 OrderId 的定义，连同它的辅助函数：

```fsharp
module Domain =
  type OrderId = private OrderId of string

  module OrderId =
    /// 为 OrderId 定义一个"智能构造函数"
    /// string -> OrderId
    let create str =
        if String.IsNullOrEmpty(str) then
          // 目前先用异常而不是 Result
          failwith "OrderId must not be null or empty"
        elif str.Length > 50 then
          failwith "OrderId must not be more than 50 chars"
        else
          OrderId str

    /// 从 OrderId 中提取内部值
    /// OrderId -> string
    let value (OrderId str) = // 在参数中直接解包！
      str                     // 返回内部值
```

create 函数与准则版本类似，不同之处在于：因为我们暂时回避效应，所以出错时用异常而不是返回 Result。

value 函数演示了如何一步完成模式匹配并提取内部值——直接在参数里完成。

## 用函数类型指导实现

在建模章节中，我们定义了专门的函数类型来表示工作流的每一步。现在到了实现阶段，如何确保代码符合这些类型呢？

最简单的做法就是按平常的方式定义函数，然后相信以后使用它时，如果写错了会得到类型检查错误。例如，我们可以像下面这样定义 validateOrder 函数，完全不引用我们之前设计的 ValidateOrder 类型：

```fsharp
let validateOrder
  checkProductCodeExists // 依赖
  checkAddressExists     // 依赖
  unvalidatedOrder =     // 输入
    ...
```

这是大多数 F# 代码的标准做法。但如果想明确表示我们正在实现某个特定的函数类型，可以换一种风格：把函数写成一个值（不带参数），并用函数类型做注解，函数体则写成一个 lambda。看起来像这样：

```fsharp
// 定义一个函数签名
type MyFunctionSignature = Param1 -> Param2 -> Result

// 定义一个实现该签名的函数
let myFunc: MyFunctionSignature =
  fun param1 param2 ->
    ...
```

把这种方式应用到 validateOrder 函数上，得到：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->
    // ^依赖                ^依赖             ^输入
      ...
```

这样做的好处是：所有参数和返回值的类型都由该函数类型确定，因此如果实现中有错误，会在函数定义内部的本地位置立刻报错，而不是等到后面组装函数时才在别处报错。

下面是一个类型检查发挥作用的例子，我们不小心把一个整数传给了 checkProductCodeExists 函数：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->
    if checkProductCodeExists 42 then
      //       编译器错误 ^
      // 此表达式应具有类型 ProductCode
      // 但此处是 int
      ...
    ...
```

如果没有函数类型来确定参数的类型，编译器会使用类型推断，可能得出 checkProductCodeExists 处理整数的结论，从而导致在别处出现（可能令人困惑的）编译错误。

## 实现验证步骤

现在可以开始实现验证步骤了。验证步骤接收未验证的订单——所有字段都是基本类型——并将其转换成一个正规的、经过完整验证的领域对象。

我们为这一步建模的函数类型如下：

```fsharp
type CheckAddressExists =
  UnvalidatedAddress -> AsyncResult<CheckedAddress,AddressValidationError>

type ValidateOrder =
  CheckProductCodeExists    // 依赖
    -> CheckAddressExists   // AsyncResult 依赖
    -> UnvalidatedOrder     // 输入
    -> AsyncResult<ValidatedOrder,ValidationError list>  // 输出
```

如前所述，本章我们要消除效应，因此可以去掉 AsyncResult 部分，得到：

```fsharp
type CheckAddressExists =
  UnvalidatedAddress -> CheckedAddress

type ValidateOrder =
  CheckProductCodeExists    // 依赖
    -> CheckAddressExists   // 依赖
    -> UnvalidatedOrder     // 输入
    -> ValidatedOrder       // 输出
```

下面把它转换为实现。从 UnvalidatedOrder 创建 ValidatedOrder 的步骤如下：

1. 从未验证订单中对应的 OrderId 字符串创建 OrderId 领域类型。
2. 从未验证订单中对应的 UnvalidatedCustomerInfo 字段创建 CustomerInfo 领域类型。
3. 从未验证订单中对应的 ShippingAddress 字段（一个 UnvalidatedAddress）创建 Address 领域类型。
4. 对 BillingAddress 以及所有其他属性做同样处理。

一旦 ValidatedOrder 的所有组件都就绪，就可以按通常的方式创建记录了。

代码如下：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->

    let orderId =
      unvalidatedOrder.OrderId
      |> OrderId.create

    let customerInfo =
      unvalidatedOrder.CustomerInfo
      |> toCustomerInfo   // 辅助函数

    let shippingAddress =
      unvalidatedOrder.ShippingAddress
      |> toAddress        // 辅助函数

    // 对 unvalidatedOrder 的每个属性依此类推

    // 当所有字段就绪后，用它们
    // 创建并返回一个新的 "ValidatedOrder" 记录
    {
      OrderId = orderId
      CustomerInfo = customerInfo
      ShippingAddress = shippingAddress
      BillingAddress = ...
      Lines = ...
    }
```

可以看到，我们用到了一些尚未定义的辅助函数，例如 toCustomerInfo 和 toAddress。这些函数从未验证类型构造领域类型。例如，toAddress 会把 UnvalidatedAddress 类型转换成对应的领域类型 Address，并且当未验证地址中的基本类型值不满足约束（例如非空、长度不超过 50 个字符）时抛出错误。

一旦这些辅助函数就位，把未验证订单（或任何非领域类型）转换为领域类型的逻辑就很直白了：对领域类型（这里是 ValidatedOrder）的每个字段，找到非领域类型（UnvalidatedOrder）中对应的字段，再用某个辅助函数把这个字段转换成领域类型。

转换订单的子组件时也可以采用完全相同的做法。例如，下面是 toCustomerInfo 的实现，它从一个 UnvalidatedCustomerInfo 构建出 CustomerInfo：

```fsharp
let toCustomerInfo (customer:UnvalidatedCustomerInfo) : CustomerInfo =
  // 创建 CustomerInfo 的各个属性
  // 如果无效则抛出异常
  let firstName = customer.FirstName |> String50.create
  let lastName = customer.LastName |> String50.create
  let emailAddress = customer.EmailAddress |> EmailAddress.create

  // 创建 PersonalName
  let name : PersonalName = {
    FirstName = firstName
    LastName = lastName
    }

  // 创建 CustomerInfo
  let customerInfo : CustomerInfo = {
    Name = name
    EmailAddress = emailAddress
    }
  // ……然后返回它
  customerInfo
```

### 创建有效且已核验的地址

toAddress 函数要更复杂一些，因为它不仅要把原始基本类型转换为领域对象，还必须核验该地址确实存在（使用 CheckAddressExists 服务）。下面是完整实现，注释附在代码中：

```fsharp
let toAddress (checkAddressExists:CheckAddressExists) unvalidatedAddress =
  // 调用远程服务
  let checkedAddress = checkAddressExists unvalidatedAddress
  // 用模式匹配提取内部值
  let (CheckedAddress checkedAddress) = checkedAddress

  let addressLine1 =
    checkedAddress.AddressLine1 |> String50.create
  let addressLine2 =
    checkedAddress.AddressLine2 |> String50.createOption
  let addressLine3 =
    checkedAddress.AddressLine3 |> String50.createOption
  let addressLine4 =
    checkedAddress.AddressLine4 |> String50.createOption
  let city =
    checkedAddress.City |> String50.create
  let zipCode =
    checkedAddress.ZipCode |> ZipCode.create
  // 创建地址
  let address : Address = {
    AddressLine1 = addressLine1
    AddressLine2 = addressLine2
    AddressLine3 = addressLine3
    AddressLine4 = addressLine4
    City = city
    ZipCode = zipCode
    }
  // 返回地址
  address
```

注意，这里引用了 String50 模块中的另一个构造函数 String50.createOption，它允许输入为 null 或空，并在这种情况下返回 None。

toAddress 函数需要调用 checkAddressExists，所以我们把它加成了一个参数；现在从父函数 validateOrder 把该函数传下来：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->

    let orderId = ...
    let customerInfo = ...
    let shippingAddress =
      unvalidatedOrder.ShippingAddress
      |> toAddress checkAddressExists // 新增参数

    ...
```

你可能会奇怪：toAddress 明明有两个参数，为什么我们只传了一个？第二个参数（收货地址）其实也在提供，只是通过管道过程提供而已。这就是我们之前谈过的部分应用技术的一个例子。

### 创建订单行

创建订单行列表就更复杂一些了。首先，我们需要一种方法把单个 UnvalidatedOrderLine 转换为 ValidatedOrderLine。我们把它叫做 toValidatedOrderLine：

```fsharp
let toValidatedOrderLine checkProductCodeExists
(unvalidatedOrderLine:UnvalidatedOrderLine) =
  let orderLineId =
    unvalidatedOrderLine.OrderLineId
    |> OrderLineId.create
  let productCode =
    unvalidatedOrderLine.ProductCode
    |> toProductCode checkProductCodeExists // 辅助函数
  let quantity =
    unvalidatedOrderLine.Quantity
    |> toOrderQuantity productCode  // 辅助函数
  let validatedOrderLine = {
    OrderLineId = orderLineId
    ProductCode = productCode
    Quantity = quantity
    }
  validatedOrderLine
```

它与前面的 toAddress 函数类似。其中用到了两个辅助函数 toProductCode 和 toOrderQuantity，我们稍后讨论。

现在，既然有了转换单个元素的方法，我们就可以用 List.map（相当于 C# LINQ 中的 Select）一次性转换整个列表，得到可用于 ValidatedOrder 的 ValidatedOrderLine 列表：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductCodeExists checkAddressExists unvalidatedOrder ->

    let orderId = ...
    let customerInfo = ...
    let shippingAddress = ...

    let orderLines =
      unvalidatedOrder.Lines
      // 用 `toValidatedOrderLine` 转换每一行
      |> List.map (toValidatedOrderLine checkProductCodeExists)
    ...
```

接下来看辅助函数 toOrderQuantity。这是在限界上下文边界上做验证的好例子：输入是来自 UnvalidatedOrderLine 的未经验证的原始 decimal，而输出（OrderQuantity）是一个选择类型，每个分支有不同的验证。代码如下：

```fsharp
let toOrderQuantity productCode quantity =
  match productCode with
  | Widget _ ->
    quantity
    |> int                  // 把 decimal 转成 int
    |> UnitQuantity.create  // 转成 UnitQuantity
    |> OrderQuantity.Unit   // 提升为 OrderQuantity 类型
  | Gizmo _ ->
    quantity
    |> KilogramQuantity.create  // 转成 KilogramQuantity
    |> OrderQuantity.Kilogram   // 提升为 OrderQuantity 类型
```

我们用 ProductCode 选择类型的分支来指导构造。例如，如果 ProductCode 是 Widget，就把原始 decimal 转成 int，再据此创建 UnitQuantity。GizmoCode 分支同理。

但不能就此止步。如果就此止步，一个分支会返回 UnitQuantity，另一个返回 KilogramQuantity。这是两个不同的类型，会引发编译错误。通过把两个分支都转换成选择类型 OrderQuantity，我们确保两个分支返回同一类型，编译器也就满意了！

另一个辅助函数 toProductCode 乍一看应该很容易实现。我们希望尽可能用管道风格写函数，所以代码应该长这样：

```fsharp
let toProductCode (checkProductCodeExists:CheckProductCodeExists) productCode =
  productCode
  |> ProductCode.create
  |> checkProductCodeExists
  // 返回 bool（不理想）
```

但现在有问题了。我们希望 toProductCode 函数返回 ProductCode，可 checkProductCodeExists 函数返回 bool，这意味着整条管道返回 bool。因此，我们得想办法让 checkProductCodeExists 返回 ProductCode 才行。糟糕，难道这意味着要修改规格说明吗？幸运的是，不用。我们来看看怎么做。

### 创建函数适配器

我们手上是一个返回 bool 的函数，但真正想要的是一个返回原始 ProductCode 输入的函数（如果一切顺利的话）。与其修改规格说明，不如创建一个「适配器」函数：它以原函数为输入，产出一个「形状」合适、能用于管道的新函数。

下面是最直白的实现，参数是返回 bool 的谓词函数和要检查的值：

```fsharp
let convertToPassthru checkProductCodeExists productCode =
  if checkProductCodeExists productCode then
    productCode
  else
    failwith "Invalid Product Code"
```

这个实现的有趣之处在于：编译器判定它是完全泛型的——根本不局限于我们这个特定场景！看一下函数签名，你会发现完全没提到 ProductCode 类型：

```fsharp
val convertToPassthru :
  checkProductCodeExists:('a -> bool) -> productCode:'a -> 'a
```

事实上，我们无意中创造了一个泛型适配器，能把任何谓词函数转换成适合管道使用的「直通」函数。此时再把参数叫做 checkProductCodeExists 或 productCode 就没有意义了——它们什么都可能是。这也是标准库函数的参数名都那么短的原因：函数参数叫 f、g，其他值叫 x、y。

那么，我们用更抽象的名字重写这个函数，像这样：

```fsharp
let predicateToPassthru f x =
  if f x then
    x
  else
    failwith "Invalid Product Code"
```

现在硬编码的错误消息就显得扎眼了，所以把它也参数化。最终版本如下：

```fsharp
let predicateToPassthru errorMsg f x =
  if f x then
    x
  else
    failwith errorMsg
```

注意我们把错误消息放在参数列表的最前面，这样可以用部分应用把它预先「烘焙」进去。

这个函数的签名是：

```fsharp
val predicateToPassthru : errorMsg:string -> f:('a -> bool) -> x:'a -> 'a
```

可以这样解读：「你给我一个错误消息和一个 'a -> bool 类型的函数，我还给你一个 'a -> 'a 类型的函数。」因此这个 predicateToPassthru 函数是一个「函数变换器」——你喂给它一个函数，它把它变换成另一个函数。

这种技术在函数式编程中极其常见，因此理解其中的原理、并在见到这个模式时能认出它，非常重要。就连不起眼的 List.map 函数也可以看作函数变换器——它把「普通」函数 'a -> 'b 变换成作用于列表的函数（'a list -> 'b list）。

好，现在用这个泛型函数创建一版新的 toProductCode，供实现使用：

```fsharp
let toProductCode (checkProductCodeExists:CheckProductCodeExists) productCode =

  // 创建一个局部的 ProductCode -> ProductCode 函数，
  // 适合在管道中使用
  let checkProduct productCode =
    let errorMsg = sprintf "Invalid: %A" productCode
    predicateToPassthru errorMsg checkProductCodeExists productCode

  // 组装管道
  productCode
  |> ProductCode.create
  |> checkProduct
```

就这样——现在我们有了一份可以继续完善的 validateOrder 实现草图。注意，诸如「产品代码必须以 W 或 G 开头」这样的底层验证逻辑，并没有在我们的验证函数里显式实现，而是内建在 OrderId、ProductCode 等受约束简单类型的构造函数中。使用类型可以增强我们对代码正确性的信心——仅凭「能够从 UnvalidatedOrder 成功创建出 ValidatedOrder」这一事实，我们就可以相信它已被验证！

## 实现其余步骤

既然已经知道如何实现 validateOrder，我们可以用同样的技术构建其余的管道函数。

下面是定价步骤函数最初的设计（含效应）：

```fsharp
type PriceOrder =
  GetProductPrice      // 依赖
    -> ValidatedOrder  // 输入
    -> Result<PricedOrder, PlaceOrderError>  // 输出
```

但同样，我们暂时消除效应，留下这个设计：

```fsharp
type GetProductPrice = ProductCode -> Price
type PriceOrder =
  GetProductPrice      // 依赖
    -> ValidatedOrder  // 输入
    -> PricedOrder     // 输出
```

下面是实现概要。它只是把每个订单行转换为 PricedOrderLine，再用它们构建一个新的 PricedOrder：

```fsharp
let priceOrder : PriceOrder =
  fun getProductPrice validatedOrder ->
    let lines =
      validatedOrder.Lines
      |> List.map (toPricedOrderLine getProductPrice)
    let amountToBill =
      lines
      // 取出每一行的价格
      |> List.map (fun line -> line.LinePrice)
      // 把它们加总为一个 BillingAmount
      |> BillingAmount.sumPrices
    let pricedOrder : PricedOrder = {
      OrderId  = validatedOrder.OrderId
      CustomerInfo = validatedOrder.CustomerInfo
      ShippingAddress = validatedOrder.ShippingAddress
      BillingAddress = validatedOrder.BillingAddress
      Lines = lines
      AmountToBill = amountToBill
      }
    pricedOrder
```

顺便说一句，如果管道中有很多步骤，你暂时不想实现（或不知道怎么实现），可以直接抛出一个「尚未实现」的错误，像这样：

```fsharp
let priceOrder : PriceOrder =
  fun getProductPrice validatedOrder ->
    failwith "not implemented"
```

在勾勒实现草图时，使用「尚未实现」异常很方便。它让我们能确保项目始终处于完全可编译的状态。例如，我们可以用这种方法构建某个管道阶段的占位版本，使其符合函数类型，并在正式实现就绪之前先与其他阶段配合使用。

回到 priceOrder 的实现，我们引入了两个新的辅助函数：toPricedOrderLine 和 BillingAmount.sumPrices。

我们把 BillingAmount.sumPrices 函数加进了共享的 BillingAmount 模块（与 create 和 value 并列）。它只是把一组 Price 加总，再包装成 BillingAmount。为什么当初要定义 BillingAmount 类型？因为它与 Price 是不同的东西，两者的验证规则也可能不同。

```fsharp
/// 将一组价格求和，构成一个账单金额
/// 如果总额超出范围则抛出异常
let sumPrices prices =
  let total = prices |> List.map Price.value |> List.sum
  create total
```

toPricedOrderLine 函数与之前看到的类似。它是一个只转换单个订单行的辅助函数：

```fsharp
/// 将 ValidatedOrderLine 转换为 PricedOrderLine
let toPricedOrderLine getProductPrice (line:ValidatedOrderLine) : PricedOrderLine =
  let qty = line.Quantity |> OrderQuantity.value
  let price = line.ProductCode |> getProductPrice
  let linePrice = price |> Price.multiply qty
  {
    OrderLineId = line.OrderLineId
    ProductCode = line.ProductCode
    Quantity = line.Quantity
    LinePrice = linePrice
  }
```

在这个函数里，我们又引入了一个辅助函数 Price.multiply，用于把 Price 乘以数量。

```fsharp
/// 将 Price 乘以一个 decimal 数量。
/// 如果新价格超出范围则抛出异常。
let multiply qty (Price p) =
  create (qty * p)
```

定价步骤至此完成！

### 实现确认步骤

下面是确认步骤的设计（已去除效应）：

```fsharp
type HtmlString = HtmlString of string
type CreateOrderAcknowledgmentLetter =
  PricedOrder -> HtmlString

type OrderAcknowledgment = {
  EmailAddress : EmailAddress
  Letter : HtmlString
  }
type SendResult = Sent | NotSent
type SendOrderAcknowledgment =
  OrderAcknowledgment -> SendResult

type AcknowledgeOrder =
  CreateOrderAcknowledgmentLetter     // 依赖
    -> SendOrderAcknowledgment        // 依赖
    -> PricedOrder                    // 输入
    -> OrderAcknowledgmentSent option // 输出
```

实现如下：

```fsharp
let acknowledgeOrder : AcknowledgeOrder =
  fun createAcknowledgmentLetter sendAcknowledgment pricedOrder ->
    let letter = createAcknowledgmentLetter pricedOrder
    let acknowledgment = {
      EmailAddress = pricedOrder.CustomerInfo.EmailAddress
      Letter = letter
      }

    // 如果确认函发送成功，
    // 返回相应的事件，否则返回 None
    match sendAcknowledgment acknowledgment with
    | Sent ->
      let event = {
        OrderId = pricedOrder.OrderId
        EmailAddress = pricedOrder.CustomerInfo.EmailAddress
        }
      Some event
    | NotSent ->
      None
```

实现很简单，不需要任何辅助函数，轻松搞定！

不过 sendAcknowledgment 这个依赖怎么办？总有一天我们得为它选定一个实现。但目前完全可以先放着不管。这正是用函数参数化依赖的一大好处——你可以把决策推迟到最后责任时刻，同时仍能构建和组装大部分代码。

### 创建事件

最后，只需创建要从工作流返回的事件了。我们给需求加一点小变化：只有当账单金额大于零时，才应发送账单事件。设计如下：

```fsharp
/// 发送给发货上下文的事件
type OrderPlaced = PricedOrder

/// 发送给账单上下文的事件
/// 只会在 AmountToBill 不为零时创建
type BillableOrderPlaced = {
    OrderId : OrderId
    BillingAddress: Address
    AmountToBill : BillingAmount
    }

type PlaceOrderEvent =
    | OrderPlaced of OrderPlaced
    | BillableOrderPlaced of BillableOrderPlaced
    | AcknowledgmentSent  of OrderAcknowledgmentSent

type CreateEvents =
  PricedOrder                            // 输入
    -> OrderAcknowledgmentSent option    // 输入（来自上一步的事件）
    -> PlaceOrderEvent list              // 输出
```

我们不需要创建 OrderPlaced 事件，因为它与 PricedOrder 是同一个东西；OrderAcknowledgmentSent 事件已在上一环节创建，因此也不需要再创建。

不过 BillableOrderPlaced 事件是需要的，所以我们来写一个 createBillingEvent 函数。由于需要判断账单金额是否为零，该函数必须返回一个可选的事件。

```fsharp
// PricedOrder -> BillableOrderPlaced option
let createBillingEvent (placedOrder:PricedOrder) : BillableOrderPlaced option =
  let billingAmount = placedOrder.AmountToBill |> BillingAmount.value
  if billingAmount > 0M then
    let order = {
      OrderId = placedOrder.OrderId
      BillingAddress = placedOrder.BillingAddress
      AmountToBill = placedOrder.AmountToBill
    }
    Some order
  else
    None
```

现在我们有了一个 OrderPlaced 事件、一个可选的 OrderAcknowledgmentSent 事件和一个可选的 BillableOrderPlaced 事件。该怎么返回它们呢？我们将采用「最小公倍数」的做法，把所有东西都转换成一个公共类型。

我们之前决定为每个事件各建一个 choice（PlaceOrderEvent），然后返回这些 choice 的列表。所以首先要把每个事件转换为该选择类型。对 OrderPlaced 事件，直接使用 PlaceOrderEvent.OrderPlaced 构造函数即可；而 OrderAcknowledgmentSent 和 BillableOrderPlaced 是可选的，需要用 Option.map。

```fsharp
let createEvents : CreateEvents =
  fun pricedOrder acknowledgmentEventOpt ->
    let event1 =
      pricedOrder
      // 转换为公共的选择类型
      |> PlaceOrderEvent.OrderPlaced
    let event2Opt =
      acknowledgmentEventOpt
      // 转换为公共的选择类型
      |> Option.map PlaceOrderEvent.AcknowledgmentSent
    let event3Opt =
      pricedOrder
      |> createBillingEvent
      // 转换为公共的选择类型
      |> Option.map PlaceOrderEvent.BillableOrderPlaced

    // 如何返回所有事件？
    ...
```

现在它们类型一致了，但有些是可选的。这又该怎么办？我们再使一次同样的招数，把它们全都转换成一个更一般的类型——这次是列表。

对 OrderPlaced，可以用 List.singleton 把它转换为列表；对两个可选值，可以创建一个叫 listOfOption 的辅助函数：

```fsharp
/// 将一个 Option 转换为 List
let listOfOption opt =
  match opt with
  | Some x -> [x]
  | None -> []
```

这样一来，三个事件的类型就一致了，我们可以把它们放进另一个列表里返回：

```fsharp
let createEvents : CreateEvents =
  fun pricedOrder acknowledgmentEventOpt ->
    let events1 =
      pricedOrder
      // 转换为公共的选择类型
      |> PlaceOrderEvent.OrderPlaced
      // 转换为列表
      |> List.singleton
    let events2 =
      acknowledgmentEventOpt
      // 转换为公共的选择类型
      |> Option.map PlaceOrderEvent.AcknowledgmentSent
      // 转换为列表
      |> listOfOption
    let events3 =
      pricedOrder
      |> createBillingEvent
      // 转换为公共的选择类型
      |> Option.map PlaceOrderEvent.BillableOrderPlaced
      // 转换为列表
      |> listOfOption

    // 返回所有事件
    [
    yield! events1
    yield! events2
    yield! events3
    ]
```

这种把不兼容的东西转换或「提升」到共享类型的做法，是解决组合问题的关键技术。例如，下一章我们将用它来处理不同 Result 类型之间的不匹配。

## 将管道各步骤组合起来

现在可以把各步骤的实现组合成管道、完成整个工作流了。我们希望代码长成这样：

```fsharp
let placeOrder : PlaceOrderWorkflow =
  fun unvalidatedOrder ->
    unvalidatedOrder
    |> validateOrder
    |> priceOrder
    |> acknowledgeOrder
    |> createEvents
```

但有个问题：除了 UnvalidatedOrder 之外，validateOrder 还有两个额外的输入。就目前而言，没有办法轻松地把 PlaceOrder 工作流的输入连接到 validateOrder 函数，因为输入和输出对不上。

priceOrder 有两个输入，因此也无法连接到 validateOrder 的输出。

正如我们指出的，把「形状」不同的函数组合起来是函数式编程的主要挑战之一，人们为此发展出了许多技术。大多数解决方案都牵涉令人生畏的「单子」，所以我们目前采用一种非常简单的做法，也就是前文介绍过的部分应用。我们要做的是只给 validateOrder 传入三个参数中的两个，得到一个只有一个输入的新函数。

代码如下：

```fsharp
let validateOrderWithDependenciesBakedIn =
  validateOrder checkProductCodeExists checkAddressExists

// 部分应用之后的新函数签名：
// UnvalidatedOrder -> ValidatedOrder
```

当然，这名字难听极了！幸运的是，在 F# 中，你可以在局部为新函数沿用同一个名字——这叫「遮蔽」：

```fsharp
let validateOrder =
  validateOrder checkProductCodeExists checkAddressExists
```

或者，也可以在名字里加一个撇号来表示它是原函数的变体，像这样：

```fsharp
let validateOrder' =
  validateOrder checkProductCodeExists checkAddressExists
```

可以用同样的方式把依赖烘焙进 priceOrder 和 acknowledgeOrder，使它们也变成只有一个输入参数的函数。

现在主工作流函数 placeOrder 大致如下：

```fsharp
let placeOrder : PlaceOrderWorkflow =

  // 用部分应用把依赖烘焙进去，
  // 建立各管道阶段的局部版本
  let validateOrder =
    validateOrder checkProductCodeExists checkAddressExists
  let priceOrder =
    priceOrder getProductPrice
  let acknowledgeOrder =
    acknowledgeOrder createAcknowledgmentLetter sendAcknowledgment

  // 返回工作流函数
  fun unvalidatedOrder ->

    // 用这些新的单参数函数组装管道
    unvalidatedOrder
    |> validateOrder
    |> priceOrder
    |> acknowledgeOrder
    |> createEvents
```

有时即便这样做了，函数还是拼不到一起。在我们的例子中，acknowledgeOrder 的输出只是事件，而不是已定价订单，因此与 createEvents 的输入不匹配。

我们可以为此写个小适配器，或者干脆改用更命令式的代码风格，把每一步的输出显式赋值给一个值，像这样：

```fsharp
let placeOrder : PlaceOrderWorkflow =
  // 返回工作流函数
  fun unvalidatedOrder ->
    let validatedOrder =
      unvalidatedOrder
      |> validateOrder checkProductCodeExists checkAddressExists
    let pricedOrder =
      validatedOrder
      |> priceOrder getProductPrice
    let acknowledgmentOption =
      pricedOrder
      |> acknowledgeOrder createAcknowledgmentLetter sendAcknowledgment
    let events =
      createEvents pricedOrder acknowledgmentOption
    events
```

它不如管道优雅，但依然易于理解和维护。

下一个问题：checkProductCodeExists、checkAddressExists、priceOrder 以及其他依赖从哪里来？我们不想把它们定义成全局的，所以来看看如何「注入」这些依赖。

## 注入依赖

我们有不少底层辅助函数，例如 toValidProductCode，它们接收一个表示服务的函数参数。这些函数位于设计相当深的地方，那么如何把依赖从顶层一路传递到需要它们的函数呢？

如果是面向对象编程，我们会使用依赖注入，可能还会用 IoC 容器。在函数式编程中，我们不想那样做，因为依赖会变成隐式的。相反，我们始终希望以显式参数的方式传递依赖，这样才能保证依赖一目了然。

函数式编程中有不少处理这类事情的技术，比如「Reader 单子」和「Free 单子」，但这是一本入门书，所以我们采用最简单的做法：把所有依赖传给顶层函数，顶层函数再传给内层函数，内层函数又继续传给更内层的函数，依此类推。

假设我们按之前的定义实现了这些辅助函数：

```fsharp
// 底层辅助函数
let toAddress checkAddressExists unvalidatedAddress =
  ...

let toProductCode checkProductCodeExists productCode =
  ...
```

它们各自都有一个表示依赖的显式参数。

现在，创建订单行的过程中需要创建产品代码，这意味着 toValidatedOrderLine 需要用到 toProductCode，也就意味着 toValidatedOrderLine 也需要带上 checkProductCodeExists 参数：

```fsharp
// 辅助函数
let toValidatedOrderLine checkProductExists unvalidatedOrderLine =
//                       ^ 供下面的 toProductCode 使用

  // 创建订单行的各个组件
  let orderLineId = ...
  let productCode =
    unvalidatedOrderLine.ProductCode
    |> toProductCode checkProductExists // 使用服务

  ...
```

再往上一层，validateOrder 函数需要同时使用 toAddress 和 toValidatedOrderLine，因此它又需要把这两个服务作为额外参数传进来：

```fsharp
let validateOrder : ValidateOrder =
  fun checkProductExists // toValidatedOrderLine 的依赖
    checkAddressExists   // toAddress 的依赖
    unvalidatedOrder ->

      // 用依赖构建已验证的地址
      let shippingAddress =
        unvalidatedOrder.ShippingAddress
        |> toAddress checkAddressExists

      ...

      // 用依赖构建已验证的订单行
      let lines =
        unvalidatedOrder.Lines
        |> List.map (toValidatedOrderLine checkProductExists)

      ...
```

就这样沿着链条一路向上，直到一个负责设置所有服务及其他依赖的顶层函数。在面向对象设计中，这个顶层函数通常称为「组合根」，我们在这里也沿用这个术语。

placeOrder 工作流函数应该充当组合根吗？不应该，因为服务的设置通常会涉及读取配置等操作。更好的做法是把所需的服务作为参数提供给 placeOrder 工作流本身，像这样：

```fsharp
let placeOrder
  checkProductExists               // 依赖
  checkAddressExists               // 依赖
  getProductPrice                  // 依赖
  createOrderAcknowledgmentLetter  // 依赖
  sendOrderAcknowledgment          // 依赖
  : PlaceOrderWorkflow =           // 函数定义

    fun unvalidatedOrder ->
      ...
```

这样还有一个额外的好处：整个工作流非常容易测试，因为所有依赖都可以被伪造。

实践中，组合根函数应尽可能靠近应用程序的入口——控制台应用的 main 函数，或者 Web 服务等长运行应用的 OnStartup/Application_Start 处理器。

下面是一个使用 Suave 框架的 Web 服务组合根示例。[27] 首先设置各项服务，然后把所有依赖传给各工作流，最后设置路由，把输入引导到相应的工作流：

```fsharp
let app : WebPart =

  // 设置工作流使用的服务
  let checkProductExists = ...
  let checkAddressExists = ...
  let getProductPrice = ...
  let createOrderAcknowledgmentLetter = ...
  let sendOrderAcknowledgment = ...
  let toHttpResponse = ...

  // 通过把服务部分应用到工作流上，
  // 设置 "placeOrder" 工作流
  let placeOrder =
    placeOrder
      checkProductExists
      checkAddressExists
      getProductPrice
      createOrderAcknowledgmentLetter
      sendOrderAcknowledgment

  // 设置其他工作流
  let changeOrder = ...
  let cancelOrder = ...

  // 设置路由
  choose
    [ POST >=> choose
      [ path "/placeOrder"
          >=> deserializeOrder // 将 JSON 转换为 UnvalidatedOrder
          >=> placeOrder       // 执行工作流
          >=> postEvents       // 将事件投递到队列
          >=> toHttpResponse   // 根据输出返回 200/400 等
        path "/changeOrder"
          >=> ...
        path "/cancelOrder"
          >=> ...
      ]
    ]
```

可以看到，如果路径是 /placeOrder，我们就启动「下单」流程：先反序列化输入，然后调用主要的 placeOrder 管道，接着投递事件，再把输出转换为 HTTP 响应。除 placeOrder 外的其他函数我们没有篇幅展开讨论，但反序列化技术会在「序列化」一章中讨论。

### 依赖太多怎么办？

validateOrder 有两个依赖。如果需要四个、五个甚至更多呢？如果其他步骤也需要大量别的依赖，依赖数量就可能爆炸式增长。真遇到这种情况该怎么办？

首先，可能你的函数承担了太多职责。能把它拆成更小的部分吗？如果拆不了，可以把这些依赖归入一个记录结构，然后作为一个参数传递。

一种常见情况是子函数的依赖本身又特别复杂。例如，假设 checkAddressExists 函数要访问一个需要 URI 端点和凭据的 Web 服务：

```fsharp
let checkAddressExists endPoint credentials =
  ...
```

难道我们还得把这两个额外的参数也传给 toAddress 的调用方，像这样？

```fsharp
let toAddress checkAddressExists endPoint credentials unvalidatedAddress =
//                          只有 ^ 这两个参数 ^ 是 checkAddressExists 需要的

  // 调用远程服务
  let checkedAddress = checkAddressExists endPoint credentials unvalidatedAddress
  //                     多传入 ^ 两个额外参数 ^
  ...
```

然后我们又得把这些额外参数传给 toAddress 的调用方，如此这般一路传到顶层？

```fsharp
let validateOrder
  checkProductExists
  checkAddressExists
  endPoint    // 只有 checkAddressExists 需要
  credentials // 只有 checkAddressExists 需要
  unvalidatedOrder =
    ...
```

不，我们当然不该这么做。这些中间函数根本不应该知道 checkAddressExists 函数的依赖是什么。好得多的做法是：在顶层函数之外先把底层函数设置好，然后直接传入一个预先烘焙好全部依赖的子函数。

例如，在下面的代码中，我们在设置阶段把 URI 和凭据烘焙进 checkAddressExists 函数，此后它就可以当作单参数函数使用了。这个简化后的函数可以像以前一样随处传递：

```fsharp
let placeOrder : PlaceOrderWorkflow =

  // 初始化信息（例如来自配置）
  let endPoint = ...
  let credentials = ...

  // 生成一个新版的 checkAddressExists，
  // 把凭据烘焙进去
  let checkAddressExists = checkAddressExists endPoint credentials
  // 等等

  // 设置工作流的各个步骤
  let validateOrder =
    validateOrder checkProductCodeExists checkAddressExists
    //               新的 checkAddressExists ^
    //               是一个单参数函数
  // 等等

  // 返回工作流函数
  fun unvalidatedOrder ->
    // 用这些步骤组装管道
    ...
```

这种通过传入「预先构建」的辅助函数来减少参数的做法是一种常见技术，有助于隐藏复杂性。当一个函数被传给另一个函数时，它的「接口」——即函数类型——应当尽可能精简，所有依赖都隐藏起来。

## 测试依赖

像这样传入依赖的一大好处是：核心函数变得非常容易测试，因为可以轻松提供假造但可用的依赖，完全不需要专门的模拟库。

例如，假设我们想测试验证中与产品代码相关的部分是否正常工作。一个测试应检查：如果 checkProductCodeExists 成功，整个验证就成功。另一个测试应检查：如果 checkProductCodeExists 失败，整个验证就失败。现在来看看怎么写这些测试。

开始前先给个小提示：F# 允许创建包含空格和标点的标识符，只要用双反引号把它们括起来。在普通代码里这样做不是好主意，但对测试函数来说可以接受，因为它让测试输出可读性大大提高。

下面是「成功」情形的示例代码，采用的是测试的 Arrange/Act/Assert（准备/执行/断言）模式：

```fsharp
open NUnit.Framework

[<Test>]
let ``If product exists, validation succeeds``() =
  // 准备：建立服务依赖的桩（stub）版本
  let checkAddressExists address =
    CheckedAddress address // 成功
  let checkProductCodeExists productCode =
    true                   // 成功

  // 准备：设置输入
  let unvalidatedOrder = ...

  // 执行：调用 validateOrder
  let result = validateOrder checkProductCodeExists checkAddressExists ...

  // 断言：检查结果是一个 ValidatedOrder，而不是错误
  ...
```

可以看到，checkAddressExists 和 checkProductCodeExists 这两个函数（代表服务）的桩版本写起来毫无难度，而且可以直接在测试里就地定义。

这里用 NUnit 框架来演示测试，但你可以使用任何 .NET 测试框架，更好的选择是 F# 友好的库，比如 FsUnit、Unquote、Expecto 或 FsCheck。

编写失败情形的代码时，只需把 checkProductCodeExists 函数改成对任何产品代码都失败即可：

```fsharp
let checkProductCodeExists productCode =
  false  // 失败
```

完整的测试如下：

```fsharp
[<Test>]
let ``If product doesn't exist, validation fails``() =
  // 准备：建立服务依赖的桩（stub）版本
  let checkAddressExists address = ...
  let checkProductCodeExists productCode =
    false // 失败

  // 准备：设置输入
  let unvalidatedOrder = ...

  // 执行：调用 validateOrder
  let result = validateOrder checkProductCodeExists checkAddressExists ...

  // 断言：检查结果是失败
  ...
```

当然，本章我们约定服务失败是通过抛出异常来表示的，而这正是我们想要避免的。下一章会修复这个问题。

这只是一个小例子，但我们已经能看到函数式编程原则给测试带来的实际好处：

- validateOrder 函数是无状态函数。它不修改任何东西，相同的输入总是得到相同的输出。这让函数易于测试。
- 所有依赖都是显式传入的，让人容易理解它的工作方式。
- 所有副作用都被封装在参数里，而不是直接在函数本身中。这同样让函数易于测试，也易于控制副作用是什么。

测试是个大话题，这里没有篇幅深入。下面是一些值得研究的流行 F# 友好测试工具：

- FsUnit 用 F# 友好的语法包装 NUnit、XUnit 等标准测试框架。
- Unquote 会展示通往测试失败的所有中间值（相当于「展开调用栈」）。
- 如果你只熟悉 NUnit 这类「基于示例」的测试方法，那真应该研究一下「基于属性」的测试方法。FsCheck 是 F# 最主要的基于属性测试的库。
- Expecto 是一个轻量级 F# 测试框架，用普通函数作为测试夹具，而不需要 [<Test>] 这样的特殊属性。

## 组装完成的管道

本章中我们看到的代码都是零散的片段。现在把所有内容汇总起来，看看完整的管道是如何组装的。

我们把实现某个工作流的所有代码放在同一个模块中，以工作流命名（例如 PlaceOrderWorkflow.fs）。

- 文件顶部放类型定义。
- 之后是各步骤的实现。
- 最底部把各步骤组装成主工作流函数。

为节省篇幅，这里只展示文件内容的概要。如果你想看完整文件，本章的全部代码都可以在本书配套的代码仓库中找到。

## 结语

本章我们完全专注于实现管道的各个步骤以及处理依赖。每个步骤的实现都只聚焦于一次增量变换，因而易于推理，也易于单独测试。

到了组合这些步骤的时候，类型并不总是能对上，于是我们引入了三种重要的函数式编程技术：

- 使用「适配器函数」把函数从一种「形状」变换成另一种形状——本例中是把 checkProductCodeExists 的输出从 bool 变成 ProductCode。
- 把各种不同的类型「提升」到一个公共类型，就像我们对事件所做的那样，把它们全部转换成公共的 PlaceOrderEvent 类型。
- 使用部分应用把依赖烘焙进函数，使函数更容易被组合，同时向调用方隐藏不需要的实现细节。

本书后面还会再次用到这些技术。

还有一个方面我们没有处理。本章我们回避了效应的处理，而是用异常来做错误处理。这对组合来说很方便，但对文档化却很糟糕——它导致欺骗性的函数签名，而不是我们偏好的那种更明确的签名。下一章将纠正这一点：我们会把所有 Result 类型加回函数类型中，并学习如何使用它们。
