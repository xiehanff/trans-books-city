# 第 2 章 理解领域

*Chapter 2: Understanding the Domain*

在上一章中，我们纵观了全局——对领域（domain）和关键业务事件做了一次概览——并把解决方案空间划分成若干个限界上下文（Bounded Context）。在此过程中，我们学习了领域驱动设计（Domain-Driven Design，DDD），以及共享模型的重要性。

在本章中，我们将选取其中一个特定的工作流（Workflow），尝试深入地理解它。到底是什么触发了它？需要哪些数据？它需要与哪些别的限界上下文协作？

我们会看到，认真倾听是这一过程中的关键技能。我们要避免把自己的心智模型强加到领域之上。

## 领域专家访谈

为了获得想要的理解，让我们对一位领域专家（domain expert）——订单处理部门的 Ollie——做一次深入访谈。

领域专家通常都很忙，一般没法在开发者身上花太多时间。不过，命令/事件（command/event）方法的一个好处在于：我们不需要开一整天的会，而是可以做一系列简短的访谈，每次只聚焦一个工作流，这样领域专家更有可能挤出时间来配合。

在访谈的第一部分，我们希望停留在较高的层面，只关注工作流的输入和输出。这有助于我们避免被那些（目前还）与设计无关的细节淹没。

你："Ollie，咱们只聊一个工作流——下单流程。要启动这个流程，你需要什么信息？"

Ollie："嗯，一切都从这张纸开始：客户填写后邮寄给我们的订单表单。在计算机化的版本里，我们希望客户在线填写这张表单。"

Ollie 给你看了一个像这样的东西：

这是一张订单表单（order form）：顶部有两个勾选框 "Quote"（报价）和 "Order"（订单）；下面是客户信息部分，包含 Name（姓名）和 Email（邮箱）；接着是 Shipping Address（收货地址）和 Billing Address（账单地址）两组地址栏；再往下是一个订单行表格，每行有 Product Code（产品代码）、Quantity（数量）和 Price（价格）三列；表格底部是 Total（合计）栏，其中价格和合计栏在收到表单时尚未填写。

这时你可能会以为这是一个典型的电商模型。

你："明白了。所以客户会在网站上浏览产品页面，然后点击把商品加入购物车，最后结账，对吗？"

Ollie："不，当然不是。我们的客户已经确切知道自己要订什么。我们只要一个简单的表单，让他们直接输入产品代码和数量就行。他们可能一次订购两三百种商品，要是先在产品页面里点来点去找每样东西，那可太慢了。"

这是一个重要的教训。你的任务是学习领域，所以要克制住对任何事情妄下结论的冲动，比如（在这个例子中）客户将如何使用系统。好的访谈意味着大量的倾听！了解一个领域的最佳方式，是把自己当成人类学家，不带任何先入为主的观念。理想情况下，在敲定设计之前，我们应该做深入的调研（比如观察人们工作、可用性测试等）。不过在这个案例里，我们愿意冒点风险跳过这些步骤，相信 Ollie 对客户需求的理解足以代表他们。

### 理解非功能性需求

现在正是退后一步、讨论这个工作流的背景和规模的好时机。

你："抱歉，我误解了客户是谁。让我再了解一些背景信息。比如，谁在使用这个流程？使用频率如何？"

Ollie："我们是一家 B2B 公司[11]，所以我们的客户是其他企业。我们大约有 1000 家客户，他们通常每周下一次单。"

你："那大约是每个工作日两百份订单。有没有什么时候会忙得多，比如节假日旺季？"

Ollie："没有。全年都相当稳定。"

这很好——我们知道不需要为超大规模设计，也不需要为尖峰流量设计。那么，客户对系统的期望是什么呢？

你："你刚才说客户都是专家？"

Ollie："他们整天都在采购东西，所以是的，他们是那个领域的专家。他们知道自己要什么，只需要一种高效的方式完成订购。"

这些信息会影响我们对设计的思考。为新手设计的系统与为专家设计的系统往往截然不同。如果客户是专家，我们就不想在路上设置障碍，或者做任何拖慢他们速度的东西。

你："那延迟（latency）呢？他们需要多快得到响应？"

Ollie："他们需要在工作日结束前得到确认。对我们的业务来说，速度不如一致性重要。我们的客户想确保我们会以可预测的方式响应并交付。"

这些都是 B2B 应用的典型需求：可预测性、稳健的数据处理，以及对每件事的审计记录（audit trail），以防出现任何疑问或纠纷。

### 理解工作流的其余部分

让我们继续访谈。

你："好的，你们对每份表单都做些什么？"

Ollie："首先我们检查产品代码是否正确。有时会有笔误，或者产品根本不存在。"

你："你怎么知道一个产品不存在？"

Ollie："我去查产品目录。那是一个列着所有产品和价格的小册子，每个月出版一本新的。瞧，最新的那本就放在我桌上。"

产品目录听起来像另一个限界上下文。我们先记下一笔，以后再详细研究它。眼下先跳过，只需记住这个工作流需要从那个上下文获取什么：产品列表及其价格。

你："然后呢？"

Ollie："然后我们把商品费用加总，写到最底下的 Total（合计）栏里，再复印两份：一份给发货部门，一份给计费部门。原件留在我们的档案里。"

你："然后呢？"

Ollie："然后我们扫描订单，用电子邮件发给客户，这样他们就能看到价格和应付金额。我们把这叫作'订单确认'（order acknowledgment）。"

好，到目前为止都说得通。之后某个时候，你还会想更深入地了解验证是怎么做的、订单是怎么传给其他部门的。不过还有一个问题。

你："表单上标着 'Quote' 和 'Order' 的那两个框是干什么用的？"

Ollie："如果勾了 'Order' 框，它就是订单；勾了 'Quote' 框，它就是报价。这不是明摆着嘛。"

你："那报价和订单有什么区别？"

Ollie："报价是客户只想让我们算算价格，但并不真正发货。对于报价，我们只是在表单上填好价格再寄回给客户。我们不会给发货部门和计费部门送副本，因为没他们什么事。"

你："明白了。订单和报价足够相似，所以你们对两者用同一张订单表单，但它们各自关联着不同的工作流。"

### 思考输入与输出

让我们暂停一下，把目前为止了解到的关于工作流输入和输出的东西记录下来。

首先，输入显然是一张订单表单（其确切定义我们很快需要充实）。

但输出是什么？我们见过"完成的订单"这个概念（基于输入、但经过了验证并算好了价格）。但它不能是输出，因为我们不会直接拿它做什么。那"订单确认"呢？它可以是输出吗？恐怕不行。发送订单确认是下单工作流的副作用（side effect），而不是输出。

工作流的输出应当永远是它所生成的那些事件——领域事件（Domain Event），也就是在其他限界上下文中触发动作的东西。在我们的例子里，工作流的输出会是一个类似 "OrderPlaced" 的事件，随后它被发给发货和计费上下文。（事件究竟如何到达那些部门，留待以后再讨论；眼下它与设计无关。）

我们把 "Place Order"（下单）工作流及其输入和输出梳理如下：

- 输入：Order Form（订单表单）
- 其他输入：Product Catalog（产品目录，来自产品目录上下文）
- 工作流：Place Order（下单）
- 输出：Order Placed 事件，发送给 Shipping（发货）上下文与 Billing（计费）上下文
- 副作用：向客户发送订单确认（acknowledgment），连同已下的订单

## 克制数据库驱动设计的冲动

到了这个阶段，如果你和大多数开发者一样，就会忍不住立刻开始勾勒底层设计和实现。

比如，你可能会看着那张订单表单，看出它由客户信息、若干地址、一个订单行列表等组成。

如果你数据库经验丰富，第一反应可能是去想表以及表之间的关系。你可能会设想一张 Order 表、一张 OrderLine 表，以及 Customer、Address、Product 表。然后你可能想描述它们之间的关系，如图所示。

在这幅关系图中：Order 表通过外键关联到 Customer 表，并带有指向 Address 表的收货地址和账单地址外键；OrderLine 表通过外键关联到 Order 表和 Product 表；订单与报价之间则不做区分，只靠 Order 表上的一个标志位来标识。

但如果你这么做，就犯了一个错误。在领域驱动设计中，我们让领域来驱动设计，而不是让数据库模式（schema）驱动设计。

更好的做法是从领域出发对它建模，而不考虑任何特定的存储实现。毕竟，在真实世界的纸面系统里根本没有数据库。"数据库"这个概念显然不是通用语言（Ubiquitous Language）的一部分。用户并不关心数据是如何持久化的。

在 DDD 术语里，这叫作持久化无知（persistence ignorance）。这是一条重要原则，因为它迫使你专注于准确地建模领域，而不必担心数据在数据库中的表示。

为什么这很重要？嗯，如果你总是从数据库的视角出发做设计，最后往往会为了迁就数据库模型而扭曲设计。

数据库驱动模型带来扭曲的一个例子是：在上面的图里，我们已经忽略了订单和报价之间的差异。当然，在数据库里我们可以用一个标志位来区分它们，但两者的业务规则和验证规则是不同的。比如，我们以后可能会了解到 Order 必须有账单地址，而 Quote 不需要。这很难用外键来建模。这层细微差别在数据库设计中丢失了，因为同一个外键要为两类关系承担双重职责。

当然，设计可以修正以处理这个问题，而且在讲持久化的那一章，我们会看到如何把领域驱动设计持久化到关系数据库中。但现在，我们真想专注于不带偏见地倾听需求。

## 克制类驱动设计的冲动

如果你是一位经验丰富的面向对象开发者，那么"不偏向特定数据库模型"的想法你并不陌生。的确，依赖注入（dependency injection）这样的面向对象技术就在鼓励你把数据库实现与业务逻辑分离。

但如果你用对象而不是领域来思考，同样可能给设计引入偏差。

例如，当 Ollie 说话时，你脑子里可能已经在创建类了，就像图中那样。

在这幅类图中：一个抽象基类 OrderBase 承载两者共有的数据（客户信息、收货地址、账单地址、订单行列表等）；Order 和 Quote 作为它的两个子类，各自扩展自己特有的字段。

让类来驱动设计，可能与让数据库来驱动设计同样危险——同样地，你并没有真正在倾听需求。

在上面的初步设计里，我们把订单和报价分开了，却引入了一个现实中并不存在的人造基类 OrderBase。这是对领域的扭曲。试试去问领域专家什么是 OrderBase 吧！

这里的教训是：在收集需求期间，我们应该保持开放的心态，不要把自己的技术观念强加于领域。

## 记录领域

好，我们想避免被技术实现带偏，那么应该如何记录这些需求呢？

我们可以用可视化图（比如 UML），但它们往往难以使用，也不够详细，捕捉不到领域的某些细微之处。

在本书后面的部分，我们会看到如何用代码创建精确的领域模型，但现在，我们先创造一种简单的、基于文本的语言，用来捕捉领域模型：

对于工作流，我们会记录输入和输出，然后只用一些简单的伪代码表示业务逻辑。

对于数据结构，我们用 AND 表示两个部分都是必需的，比如 Name AND Address；用 OR 表示任一部分即可，比如 Email OR PhoneNumber。

于是，用这套迷你语言，我们可以像这样记录 Place Order 工作流：

```fsharp
Bounded context: Order-Taking

Workflow: "Place order"
   triggered by:
      "Order form received" event (when Quote is not checked)
   primary input:
      An order form
   other input:
      Product catalog
   output events:
      "Order Placed" event
   side-effects:
      An acknowledgment is sent to the customer,
      along with the placed order
```

与该工作流关联的数据结构可以这样记录：

```fsharp
bounded context: Order-Taking

data Order =
    CustomerInfo
    AND ShippingAddress
    AND BillingAddress
    AND list of OrderLines
    AND AmountToBill

data OrderLine =
    Product
    AND Quantity
    AND Price

data CustomerInfo = ???   // 尚不清楚
data BillingAddress = ??? // 尚不清楚
```

Provide Quote（提供报价）工作流及其关联的数据结构可以用类似的方式记录。

注意，我们并没有试图创建类层次结构或数据库表或任何别的东西。我们只是尝试以一种略带结构的方式捕捉领域。

这种基于文本的设计的优点是：它对非程序员来说不吓人，这意味着可以拿给领域专家看，并一起协作完善。

最大的问题是：我们能否让代码也看起来这么简单？在后面的章节——第 5 章《用类型做领域建模》（Domain Modeling with Types）——中，我们会尝试做到这一点。

## 深入订单处理工作流

输入和输出已经记录好了，接下来让我们详细地理解这个订单处理工作流。

你："Ollie，能详细讲讲你是怎么处理一张订单表单的吗？"

Ollie："早上收到邮件之后，我做的第一件事就是分拣。订单表单放一堆，其他信函放另一堆。然后，对每张表单，我会看 Quote 框有没有勾；勾了的话，就把它放到 Quotes（报价）堆里稍后处理。"

你："为什么要这样？"

Ollie："因为订单永远更重要。订单能赚钱，报价可不赚钱。"

Ollie 说到了收集需求时一件非常重要的事情。作为开发者，我们倾向于关注技术问题，把所有需求一视同仁。企业可不这么想。赚钱（或省钱）几乎总是一个开发项目背后的驱动力。如果你拿不准什么优先级最高，就跟着钱走！就本例而言，我们要把系统设计成（能赚钱的）订单优先于报价。

继续……

你："处理一张订单表单时，你做的第一件事是什么？"

Ollie："我做的第一件事是检查客户的名字、邮箱、收货地址和账单地址是否有效。"

与 Ollie 进一步讨论后，我们了解到，地址是用 Ollie 电脑上的一个特殊应用程序来检查的。Ollie 输入地址，电脑查询它们是否存在，还会把它们转换成快递公司喜欢的标准格式。

我们又学到了新东西。这个工作流需要与上下文之外的某个第三方地址检查服务通信。我们在事件风暴（Event Storming）时漏掉了这一点，所以得记上一笔。

如果名字和地址无效，Ollie 会用红笔在表单上标出问题，并把它放到无效表单堆上。稍后，Ollie 会打电话给客户，要求更正这些信息。

我们现在知道了三个堆：寄来的订单表单（来自邮件）、寄来的报价（稍后处理）、无效订单表单（也是稍后处理）。

纸堆是大多数业务流程中非常重要的一部分。再强调一遍：有些纸堆比其他纸堆更重要，我们千万不要忘记在设计里捕捉这一点。到了实现阶段，"一叠纸"正好对应一个队列（queue），但现在我们还是得提醒自己远离技术细节。

Ollie："之后，我检查表单上的产品代码。有时一眼就能看出是错的。"

你："怎么看出来？"

Ollie："因为这些代码有特定的格式。widget 的代码以 W 开头后跟四个数字，gizmo 的代码以 G 开头后跟三个数字。"

你："还有其他类型的产品代码吗？或者近期可能会有？"

Ollie："没有。产品代码的格式多年没变过了。"

你："那些格式看起来正确的产品代码呢？你会检查它们是真实存在的产品吗？"

Ollie："会。我在我那份产品目录里查。如果有代码不在里面，我就在表单上标出错误，把它放进无效订单堆。"

让我们暂停一下，看看产品代码这里都发生了什么：

首先，Ollie 看代码的格式：是否以 W 或 G 开头等。用编程术语来说，这是纯粹的语法（syntactic）检查。做这件事不需要访问产品目录。

接着，Ollie 检查代码是否存在于产品目录中。对 Ollie 而言，这是在书里查找；而在软件系统里，这就对应一次数据库查询。

你："问个傻问题。假如产品团队的某个人能即时回答你的所有问题，你还需要自己那份产品目录吗？"

Ollie："可要是他们正忙呢？或者电话线路坏了呢？这其实不是速度问题，而是控制权问题。我不想因为别人不在而中断我的工作。有自己那份产品目录，几乎每张订单表单我都能处理，不用依赖产品团队。"

所以这其实是关于依赖管理，而不是性能。我们之前已经讨论过自治对限界上下文的重要性（见《正确划分上下文》一节）。这一点在领域中建模可能很重要——也可能不重要——但无论如何，你都应该意识到各部门需要能够独立工作这一需求。

你："好，现在假设所有产品代码都没问题。接下来呢？"

Ollie："我检查数量。"

你："数量是整数还是浮点数（float）？"

Ollie："浮？你是说浮在水面上那个浮吗？"

通用语言时刻到了！小贴士：领域专家不会使用"float"这样的编程术语。

你："那你们管那些数字叫什么？"

Ollie："我叫它们'订购数量'（order quantities），这还用说！"

好，我们可以看到 OrderQuantity 需要成为通用语言中的一个词，ProductCode、AmountToBill 等也一样。

我们再试一次：

你："订购数量带小数吗？还是都是整数？"

Ollie："看情况。"

"看情况。"一听到这话，你就知道事情要变复杂了。

你："取决于什么？"

Ollie："取决于产品是什么。widget 按件卖，gizmo 按公斤卖。要是有人订 1.5 个 widget，那当然是搞错了。"

你奋笔疾书，飞快地记着笔记。

你："好，假设所有产品代码和订购数量都没问题。接下来呢？"

Ollie："接下来，我在订单的每一行填上价格，然后加总算出应付总金额。再接着，像我之前说的，我把订单表单复印两份。原件归档，一份副本放进发货发件筐，另一份副本放进计费发件筐。最后，我扫描原件，附在一封标准的确认信里，用电子邮件发回给客户。"

你："最后一个问题。这么多订单表单摊在周围，你会不会偶尔把处理过的和还没验证的搞混？"

Ollie："不会。每次对它们做了什么，我都会做上某种标记。比如，一张表单验证完了，我就在这个角上做个记号，这样我就知道验证过了。价格算没算过，看 'Total' 栏填没填就知道。这样一来，我总能把处于不同阶段的订单表单区分开。"

这里是个停下来消化所学内容的好地方。

## 在领域模型中表示复杂性

随着我们钻进这个工作流的深处，领域模型变得复杂多了。这是好事。宁可现在花时间理解复杂性，也不要等到编码进行到一半才补课。正如人们所说："几周的编程可以帮你省下几小时的规划。"

现在这个工作流的示意图是这样的：

这幅更新后的工作流图在原有输入/输出的基础上，补充了内部的各个步骤和三堆表单：来自邮件的订单表单先经过分拣，勾选了 Quote 的表单进入"报价堆"（优先级较低，稍后处理）；订单表单则进入验证步骤（ValidateOrder），该步骤依赖外部的地址检查服务（CheckAddressExists）与产品目录（CheckProductCodeExists）；验证不通过的表单进入"无效订单堆"稍后处理；验证通过的订单进入计价步骤（PriceOrder），通过产品目录获取价格（GetProductPrice）；计价后的订单（PricedOrder）生成确认信发送给客户（副作用），并最终产出 "Order Placed" 领域事件，发送给发货与计费上下文。

但这张图并没有反映出我们学到的全部内容。看看我们能不能做得更好，用基于文本的语言把所有这些新信息都捕捉下来。

### 表示约束

我们先从最基础的值开始：产品代码和数量。我们已经了解到，它们并不只是简单的字符串和整数，而是以各种方式受到约束。

```fsharp
context: Order-Taking

data WidgetCode = string starting with "W" then 4 digits
data GizmoCode = string starting with "G" then 3 digits
data ProductCode = WidgetCode OR GizmoCode
```

在上面这个片段里，Ollie 使用的词（比如 WidgetCode）也被用在了设计中，我们把它们视为通用语言的一部分。此外，我们记录了 WidgetCode 和 GizmoCode 上的约束，然后把 ProductCode 定义为在这两种类型之间的一个选择。

可这是不是太严格了？如果要处理一种新的产品类型怎么办？这是我们经常遇到的问题。太严格，会让修改变得困难；但太自由，我们就根本谈不上有设计。

正确的答案一如既往地取决于上下文。不过总体而言，从领域专家的视角捕捉设计很重要。检查不同种类的代码是验证过程的重要组成部分，所以它应该反映在领域的设计中——这个设计的目标是自我文档化（self-documenting）。而且，如果我们不在这里把不同种类的产品代码记录下来、作为模型的一部分，反正也得在别的地方记录。

另外，如果需求真的变了，我们的模型也很容易修改；新增一种产品代码只需要多加一行。

最后，记住：设计严格并不意味着实现也必须严格。例如，验证过程的自动化版本可以只把奇怪的代码标记出来交人工审批，而不是直接拒掉整张订单。

那么，数量的需求该如何记录？下面是提议的设计：

```fsharp
data OrderQuantity = UnitQuantity OR KilogramQuantity

data UnitQuantity = integer between 1 and ?
data KilogramQuantity = decimal between ? and ?
```

正如我们对产品代码所做的那样，我们把 OrderQuantity 定义为一个选择——这里是在 UnitQuantity 和 KilogramQuantity 之间。

不过，写下这些的时候，我们意识到还没有给 UnitQuantity 和 KilogramQuantity 设定上界。总不能允许 UnitQuantity 达到几十亿吧？

让我们和领域专家确认一下。Ollie 给出了我们需要的上限：

订购数量允许的最大件数是 1000。

最低重量是 0.05 千克，最高是 100 千克。

这类约束很重要，必须捕捉下来。我们绝不希望生产环境出现件数意外为负、或者重量高达几十万吨的情况。下面是更新后的规格，把这些约束记录在内：

```fsharp
data UnitQuantity = integer between 1 and 1000
data KilogramQuantity = decimal between 0.05 and 100.00
```

### 表示订单的生命周期

现在来看 Order。在之前的设计草稿里，我们对 Order 有一个简单的定义：

```fsharp
data Order =
    CustomerInfo
    AND ShippingAddress
    AND BillingAddress
    AND list of OrderLines
    AND AmountToBill
```

但现在很清楚，这个设计太简单了，没有捕捉到 Ollie 看待订单的方式。在 Ollie 的心智模型里，订单是有生命周期（life cycle）的：它们从未验证状态开始（直接来自邮件），然后被"验证"，再被"计价"。

一开始订单没有价格，到最后有了。上面那个简单的 Order 定义抹掉了这一区别。

在纸面表单上，Ollie 通过在每阶段结束后给订单做标记来区分这些阶段，因此未验证的订单一眼就能与已验证的区分开，已验证的又能与已计价的区分开。

我们需要在领域模型中捕捉这些同样的阶段，不只是为了文档化，更是为了明确（例如）未计价的订单不应该被送到发货部门。

最简单的做法是为每个阶段创建新的名字：UnvalidatedOrder、ValidatedOrder 等。这确实意味着设计写起来更长、更枯燥，但好处是一切都清清楚楚。

我们先从最初寄到的未验证订单和报价开始。可以这样记录：

```fsharp
data UnvalidatedOrder =
    UnvalidatedCustomerInfo
    AND UnvalidatedShippingAddress
    AND UnvalidatedBillingAddress
    AND list of UnvalidatedOrderLine

data UnvalidatedOrderLine =
    UnvalidatedProductCode
    AND UnvalidatedOrderQuantity
```

这份文档明确表达了：在工作流开始时，CustomerInfo 尚未验证，ShippingAddress 尚未验证，等等。

下一个阶段是订单已通过验证。可以这样记录：

```fsharp
data ValidatedOrder =
    ValidatedCustomerInfo
    AND ValidatedShippingAddress
    AND ValidatedBillingAddress
    AND list of ValidatedOrderLine

data ValidatedOrderLine =
    ValidatedProductCode
    AND ValidatedOrderQuantity
```

这表明所有组成部分此刻都已检查过并且有效。

下一个阶段是为订单计价。已计价订单（Priced Order）和已验证订单一样，除了以下几点：

每一行现在都关联了一个价格。也就是说，PricedOrderLine 是 ValidatedOrderLine 加上 LinePrice。

订单整体关联了一个 AmountToBill，按各行价格之和计算。

对应的模型如下：

```fsharp
data PricedOrder =
    ValidatedCustomerInfo
    AND ValidatedShippingAddress
    AND ValidatedBillingAddress
    AND list of PricedOrderLine  // 不同于 ValidatedOrderLine
    AND AmountToBill             // 新增

data PricedOrderLine =
    ValidatedOrderLine
    AND LinePrice                // 新增
```

最后一个阶段是创建订单确认。

```fsharp
data PlacedOrderAcknowledgment =
    PricedOrder
    AND AcknowledgmentLetter
```

现在你可以看到，这个设计已经捕捉到了相当多的业务逻辑——比如这些规则：

未验证的订单没有价格。

已验证订单中的所有行都必须是已验证的，而不只是一部分。

这个模型比我们最初想的复杂得多。但我们只是在反映业务的实际运作方式。如果我们的模型没有这么复杂，就说明我们没有恰当地捕捉需求。

现在，如果我们还能在代码中保留这些区别，那么代码就会准确地反映领域，我们也就有了一个真正的"领域驱动"设计。

### 充实工作流的各个步骤

应该不难看出，工作流可以分解成更小的步骤：验证、计价等。让我们对每个步骤应用同样的输入/输出方法。

首先，整个工作流的输出比我们之前想的要复杂一点。最初唯一的输出是 "Order placed" 事件，但现在工作流可能的结果如下：

我们向发货/计费发送一个 "Order placed" 事件，或者

我们把订单表单加入无效订单堆，并跳过其余步骤。

让我们用伪代码记录整个工作流，并把 ValidateOrder 之类的步骤拆成单独的子步骤：

```fsharp
workflow "Place Order" =
    input: OrderForm
    output:
       OrderPlaced event (put on a pile to send to other teams)
       OR InvalidOrder (put on appropriate pile)

    // 步骤 1
    do ValidateOrder
    If order is invalid then:
        add InvalidOrder to pile
        stop

    // 步骤 2
    do PriceOrder

    // 步骤 3
    do SendAcknowledgmentToCustomer

    // 步骤 4
    return OrderPlaced event (if no errors)
```

整体流程记录好了，现在我们可以为每个子步骤补充额外的细节。

比如，验证表单的子步骤以 UnvalidatedOrder 为输入，输出是 ValidatedOrder 或 ValidationError。我们还要记录该子步骤的依赖：它需要产品目录的输入（我们称之为 CheckProductCodeExists 依赖）以及外部地址检查服务（CheckAddressExists 依赖）。

```fsharp
substep "ValidateOrder" =
    input: UnvalidatedOrder
    output: ValidatedOrder OR ValidationError
    dependencies: CheckProductCodeExists, CheckAddressExists

    validate the customer name
    check that the shipping and billing address exist
    for each line:
        check product code syntax
        check that product code exists in ProductCatalog

    if everything is OK, then:
        return ValidatedOrder
    else:
        return ValidationError
```

计算价格的子步骤以 ValidatedOrder 为输入，并依赖产品目录（我们称之为 GetProductPrice）。输出是 PricedOrder。

```fsharp
substep "PriceOrder" =
    input: ValidatedOrder
    output: PricedOrder
    dependencies: GetProductPrice

    for each line:
        get the price for the product
        set the price for the line
    set the amount to bill ( = sum of the line prices)
```

最后，末尾的子步骤以 PricedOrder 为输入，创建并发送确认。

```fsharp
substep "SendAcknowledgmentToCustomer" =
    input: PricedOrder
    output: None

    create acknowledgment letter and send it
    and the priced order to the customer
```

这份需求文档现在看起来更像代码了，但它仍然可以由领域专家阅读和检查。

## 总结

需求收集到此为止，因为等到本书第二部分进入建模阶段时，我们手头的材料已经足够多了。但首先来回顾一下本章所学。

我们看到，做设计时不要一头扎进实现细节，这一点很重要：DDD 既不是数据库驱动的，也不是类驱动的。相反，我们专注于不带假设地捕捉领域，也不预设任何特定的编码方式。

我们还看到，认真倾听领域专家会揭示出大量的复杂性，哪怕是在像这样相对简单的系统里。比如，我们原以为只会有一个单一的"Order"，但进一步调查发现了订单在整个生命周期中的许多变体，每个变体的数据和行为都略有不同。
