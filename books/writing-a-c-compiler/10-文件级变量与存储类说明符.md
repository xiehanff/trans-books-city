# 第 10 章　文件级变量声明与存储类说明符

*Chapter 10: File-Scope Variable Declarations and Storage-Class Specifiers*

我们将通过实现几个与函数声明和变量声明相关的重要特性，为第 I 部分收尾。我们会添加对文件作用域（file scope）变量声明的支持——也就是位于源文件顶层的声明——并引入 static 和 extern 关键字。这些关键字是存储类说明符（storage-class specifier），用于控制声明的链接（linkage）以及所声明对象的存储期（storage duration，即该对象在内存中存在多长时间）。

本章的大部分篇幅将花在语义分析阶段，确定每个声明的链接和存储期。我们还需要几个新的汇编器指令（assembler directive）来定义和初始化不同种类的变量，不过编译器后端的改动相对简单。先来回顾一下 C 标准对声明和存储类说明符的规定。即使你已经相当熟悉 C，我也建议阅读下面这一节。这部分语言特性在编译器开发者眼中与在 C 程序员眼中大不相同，主要是因为你的编译器需要支持任何理智的 C 程序员都不会用到的行为。

## 声明的方方面面

源文件中的每个声明都有几个需要跟踪的性质，本节将逐一考察。这些性质包括声明的作用域（scope）、链接，以及它除了是声明之外是否同时也是定义（definition）。（声明的类型也很重要，但本章不会涉及类型方面的新内容。）我们还需要跟踪程序中每个变量的存储期。

确定这些性质的规则极为繁复。它们取决于标识符指的是函数还是变量、声明出现在文件作用域还是块作用域（函数体内），以及声明使用了哪种存储类说明符。static 说明符有两种截然不同的含义，分别适用于不同的上下文。extern 说明符则有多个看似互不相关的作用，这些作用同样取决于上下文。（其余的存储类说明符——auto、register、_Thread_local 和 typedef——各有杂七杂八的用途，我就不在这里展开讲了。我们不会实现它们。）总而言之，C 标准的这一部分是一团乱麻，但我们会尽力蹚过去。

C 中围绕声明的术语可能不一致，所以动手之前先说清楚我对几个术语的用法：

- **文件**（file）或**源文件**（source file）指经过预处理的源文件，C 标准（以及上一章）称之为“翻译单元”（translation unit）。

- **静态变量**（static variable）指具有静态存储期的变量（将在第 212 页“存储期”一节讨论），而不只是用 static 存储类说明符声明的变量。所有带 static 说明符声明的变量都是静态变量，但并非所有静态变量都用该说明符声明。

- **自动变量**（automatic variable）指具有自动存储期的变量（同样在“存储期”一节讨论），与静态存储期相对。我们在前面各章遇到的所有变量都是自动变量。

- **外部变量**（external variable）指任何具有内部链接或外部链接的变量，而不只是用 extern 存储类说明符声明的变量。后面会看到，所有外部变量同时也是静态变量，但并非所有静态变量都是外部变量。

### 作用域

函数和变量遵循相同的作用域规则。变量既可以在文件作用域声明，也可以在块作用域（block scope）声明，与函数一样。文件作用域变量与函数、块作用域变量一样，必须先声明后使用，并且可能被后面的块作用域标识符遮蔽。既然你已经知道确定标识符作用域的规则，这里就没有多少可说的了。

### 链接

到目前为止，函数声明一直具有外部链接（external linkage）：同一个函数名的每个声明都指向同一个函数定义。我们此前见过的局部变量声明则没有链接（no linkage）：同一个变量名的不同声明总是指向不同的对象。默认情况下，文件作用域的变量声明与函数声明一样具有外部链接。只要同一个标识符出现多个文件作用域声明，编译器要么把这些声明协调一致，使之全部指向同一实体，要么抛出错误。

借助 static 说明符，我们还可以声明具有内部链接（internal linkage）的函数和变量。内部链接的工作方式与外部链接类似，区别在于具有内部链接的声明绝不会指向其他文件中的实体。为了说明两者的区别，来看一个由两个源文件组成的程序。清单 10-1 展示了第一个文件。

```c
❶ int foo(void) {
    return 1;
}

❷ int bar(void) {
    return 2;
}
```

*清单 10-1：定义两个具有外部链接的函数的源文件*

清单 10-2 展示了第二个文件。

```c
❸ int foo(void);
❹ static int bar(void);

int main(void) {
    return foo() + bar();
}

❺ static int bar(void) {
    return 4;
}
```

*清单 10-2：声明一个具有内部链接的函数（bar）和两个具有外部链接的函数（foo 和 main）的源文件*

在清单 10-1 中，我们定义了两个具有外部链接的函数：foo ❶ 和 bar ❷。清单 10-2 也包含标识符 foo ❸ 和 bar ❹❺ 的声明。首先搞清楚 foo 在清单 10-2 中的含义。由于 ❸ 处的声明不含 static 说明符，它具有外部链接。因此，声明 ❶ 和 ❸ 指向同一个函数，该函数定义在 ❶ 处。

接下来考虑 bar。由于 ❹ 处的声明包含 static 说明符，它具有内部链接。这意味着它不指向 ❷ 处的定义，而是声明了一个全新的函数。这个函数的定义出现在后面的 ❺ 处。由于声明 ❹ 和 ❺ 都具有内部链接且位于同一文件中，它们指向同一个函数。因此，main 将使用 ❺ 处 bar 的定义计算 1 + 4 并返回 5。

注意，具有内部链接的标识符不会遮蔽具有外部链接的标识符，反之亦然。清单 10-2 中 bar 的声明并没有遮蔽清单 10-1 中 ❷ 处的定义；确切地说，那个定义从一开始就在清单 10-2 中不可见，因为清单 10-2 中没有任何声明指向它。如果同一标识符在同一文件中既以内部链接又以外部链接声明，行为是未定义的，大多数编译器会抛出错误。

C 标准第 6.2.2 节给出了确定标识符链接的规则，我在此做个总结。一个声明的链接取决于两点：它包含哪种存储类说明符（如果有），以及它是在块作用域还是文件作用域声明的。不带存储类说明符的函数声明始终被当作带有 extern 说明符来处理，我们稍后会讨论这一点。不带存储类说明符的变量声明若出现在块作用域，则没有链接；若出现在文件作用域，则具有外部链接。

在文件作用域，static 说明符表示函数或变量具有内部链接。在块作用域，static 说明符控制的是存储期而非链接。在块作用域用该说明符声明的变量没有链接，与不带说明符声明的变量一样。在块作用域声明 static 函数是非法的，因为函数没有存储期。

extern 说明符更复杂一些。如果在使用 extern 声明某个标识符时，该标识符的一个先前声明可见，且那个先前声明具有内部或外部链接，那么新声明将具有与先前声明相同的链接。如果没有可见的先前声明，或先前声明没有链接，那么 extern 声明将具有外部链接。

在清单 10-3 中，我们用 extern 声明一个已经可见的标识符。

```c
static int a;
extern int a;
```

*清单 10-3：在先前声明可见时用 extern 声明标识符*

a 的第一个声明因为 static 关键字而具有内部链接。由于第二个声明是在第一个声明可见之处用 extern 关键字声明的，它也将具有内部链接。

而在清单 10-4 中，我们在没有可见先前声明之处使用 extern。

```c
int main(void) {
    extern int a;
    return a;
}

int a = 5;
```

*清单 10-4：用 extern 在块作用域声明具有外部链接的变量*

main 内部对 a 的声明与文件后面 a 的定义都具有外部链接，所以它们指向同一个对象。因此，main 将返回 5。

当一个具有外部链接的变量被局部变量遮蔽时，可以用 extern 把它带回作用域。清单 10-5 展示了这是如何工作的。

```c
int a = 4;
int main(void) {
    int a = 3;
    {
      ❶ extern int a;
        return a;
    }
}
```

*清单 10-5：用 extern 把被遮蔽的具有外部链接的变量带回作用域*

当我们在 main 中用 extern 说明符声明 a ❶ 时，没有任何具有内部或外部链接的先前声明可见。（a 最初的文件作用域声明具有外部链接，但它被第二个块作用域声明遮蔽了。块作用域声明可见，但它没有链接。）因此，这个 extern 声明具有外部链接。由于 a 早先的文件作用域声明同样具有外部链接，这两个声明指向同一个变量。接着我们在下一行的 return 语句中使用这个变量。于是 main 返回 4。

前面提到过，不带存储类说明符的函数声明始终被当作带有 extern 说明符来处理。想想这条规则会如何影响清单 10-6 中函数定义的链接。

```c
static int my_fun(void);
int my_fun(void) {
    return 0;
}
```

*清单 10-6：带 static 说明符的函数声明，随后是该函数不带存储类说明符的定义*

正如清单 10-3 所示，如果某个先前声明可见，带 extern 说明符的声明会沿用该标识符先前声明的链接。由于我们把 my_fun 的定义当作带有 extern 说明符来处理，它将沿用前一行声明的链接，即内部链接。这条规则意味着，在函数声明上写 extern 永远是多余的（内联函数是个例外，但我们不会实现它）。

接下来讨论本章的新概念：存储期。

### 存储期

存储期是变量的性质；函数没有存储期。C 标准第 6.2.4 节第 1–2 段给出了如下描述：“对象具有存储期，存储期决定了它的生存期（lifetime）。……对象的生存期是程序执行过程中保证为其保留存储的那一部分。在整个生存期内，对象存在、拥有恒定的地址，并保留其最后存储的值。”换言之，在对象的生存期内，你可以照常使用它：可以写入它、读取它、取回你最后写入的值。在这段时间里，对象不会被释放，也不会被重新初始化。

本章我们将考虑两种存储期：自动存储期（automatic storage duration）和静态存储期（static storage duration）。前面各章见过的所有变量都具有自动存储期。具有自动存储期的变量，其生存期从进入声明它的块开始，到退出该块时结束。这意味着，举例来说，你不能用自动变量来记录一个函数被调用了多少次。要理解原因，请看清单 10-7，它试图做的正是这件事。

```c
#include <stdio.h>

int recursive_call(int count_was_initialized) {
    int count;
    if(!count_was_initialized) {
        count = 0;
        count_was_initialized = 1;
    }
    count = count + 1;
    printf("This function has been called %d times\n", count);
    if (count < 20) {
        recursive_call(count_was_initialized);
    }
    return 0;
}
```

*清单 10-7：错误地尝试在多次函数调用之间共享自动变量的值*

清单 10-7 中的 recursive_call 函数试图在第一次被调用时初始化局部变量 count，然后在后续每次调用时递增它。这行不通，因为 count 具有自动存储期；recursive_call 的每次调用都会分配一个新的、未初始化的 count 副本，并在该次调用返回时将其释放。

另一方面，如果变量具有静态存储期，它的生存期会贯穿程序运行的全程。具有静态存储期的变量在程序启动之前被初始化一次，其生存期在程序退出时结束。

确定存储期的规则很简单：所有在文件作用域声明的变量都具有静态存储期，所有在块作用域用 static 或 extern 关键字声明的变量也是如此。所有在块作用域不带存储类说明符声明的变量都具有自动存储期。标准还定义了分配存储期（allocated storage duration），我们将在第 II 部分添加 malloc 支持时讨论它；还定义了线程存储期（thread storage duration），本书不会实现。

我们可以用一个静态计数器来修复清单 10-7。清单 10-8 给出了 recursive_call 的正确实现。

```c
#include <stdio.h>

int recursive_call(void) {
  ❶ static int count = 0;
    count = count + 1;
    printf("This function has been called %d times\n", count);
    if (count < 20) {
        recursive_call();
    }
    return 0;
}
```

*清单 10-8：正确地在多次函数调用之间共享静态变量的值*

现在，由于 count 是用 static 关键字声明的 ❶，它具有静态存储期。我们将在程序启动之前只分配一次 count 并将其初始化为 0。然后，在 recursive_call 的每次调用中递增的都是同一个 count 变量。

当执行到 recursive_call 内部 count 的声明处时，我们不会再次初始化它。声明标记的是变量被引入作用域的程序位置，而不是执行期间它被初始化的时刻。要理解静态变量的作用域与生存期互不相关，这一点很重要。在第 7 章中，我把变量的作用域描述为程序中可以使用它的那部分。现在我们需要细化这个定义，明确它是程序源代码中可以使用该变量的那部分。而变量的生存期是程序执行过程中该变量拥有地址和值的那段时间。对自动变量而言，作用域与生存期联系得如此紧密，以至于这种区分几乎无关紧要：变量的生存期从开始执行它处于作用域内的那个块开始，到执行完该块时结束。但静态变量的生存期独立于它的作用域。例如在清单 10-8 中，count 的生存期贯穿程序全程，而它的作用域只从它在 recursive_call 中的声明处延伸到函数末尾。

由于静态变量在程序启动前初始化，它们的初始化器必须是常量。清单 10-9 展示了两个文件作用域声明，其中一个带非法的初始化器。

```c
int first_var = 3;
int second_var = first_var + 1;
```

*清单 10-9：带合法与非法初始化器的文件作用域变量声明*

first_var 和 second_var 都具有静态存储期，因为它们是在文件作用域声明的。first_var 的初始化器是常量，因此合法。而 second_var 的初始化器非法，因为在程序启动之前无法计算 first_var + 1 这样的表达式。

> **注意**
>
> C 标准允许用常量表达式（如 1 + 1）初始化静态变量，因为常量表达式可以在编译时求值。为了让生活轻松一点，我们的编译器只支持在初始化器（initializer）中使用常量值，不支持常量表达式。

### 定义与声明

上一章中，我们必须区分函数定义和函数声明。本章将把这一区分扩展到变量。如果一个变量被定义，我们的汇编程序就需要为它分配存储空间，并可能对它初始化。如果它只是被声明而未被定义，我们不为它分配存储空间，而是依靠链接器在其他目标文件中找到定义。与函数一样，一个变量可以声明多次，但只能定义一次。

识别函数定义很容易，因为它们有函数体。判断什么算变量定义则要棘手一些。我们来把规则过一遍，让你知道哪些变量声明同时也是定义、哪些不是。我们还会讨论如何（以及何时）初始化那些没有显式初始化器的变量定义。

首先，每个带初始化器的变量声明都是定义。这不足为奇，因为如果没有为变量分配存储空间，就无法初始化它。其次，每个没有链接的变量声明都是定义。一个没有链接而又不是定义的变量声明将毫无用处：没有链接的变量不能被声明多次，所以你不可能在程序的其他地方再定义它。

如何初始化一个没有链接的变量取决于它的存储期。回想一下，前面各章的局部变量在栈上分配空间，但不一定被初始化。而局部静态变量，稍后会看到，在另一块内存区域中分配空间，并且总会被初始化。如果没有提供显式的初始化器，它们会被初始化为零。

如果一个变量声明带有 extern 说明符而没有初始化器，它就不是定义。注意，块作用域的 extern 变量声明不能带初始化器，因此它们永远不是定义。（这与你可以声明块作用域函数、但不能定义它们类似。）我们可以用 extern 说明符声明定义在同一文件其他位置的变量，如清单 10-10。

```c
extern int three;

int main(void) {
    return three;
}

int three = 3;
```

*清单 10-10：在文件开头声明外部变量，在文件末尾定义它*

清单开头的声明把 three 引入作用域，清单末尾的定义确定它的初始值 3。extern 说明符还允许我们声明定义在其他文件中的变量，如清单 10-11。

```c
extern int external_var;

int main(void) {
    return 1 + external_var;
}
```

*清单 10-11：声明变量而不定义它*

由于 external_var 没有定义在这个文件中，编译器不会为它分配空间或初始化它。链接器要么在其他文件中找到它的定义，要么抛出错误。

一个具有内部或外部链接、不带 extern 说明符、也不带初始化器的变量声明是暂定定义（tentative definition）。清单 10-12 给出了一个例子。

```c
int x;

int main(void) {
    return x;
}
```

*清单 10-12：一个暂定定义*

x 在这个文件中唯一的定义就是第一行的暂定定义。如果一个变量只被暂定定义，我们会把它初始化为零。因此，清单 10-12 的第一行会被当作与下面这个非暂定定义完全相同：

```c
int x = 0;
```

如果一个文件中既包含某变量的暂定定义，又包含它的显式初始化定义，如清单 10-13 所示，显式定义优先。

```c
int x;

int main(void) {
    return x;
}

int x = 3;
```

*清单 10-13：先有暂定定义，后有显式定义*

这个清单以 x 的暂定定义开头，以非暂定定义结尾。非暂定定义优先，所以 x 被初始化为 3。第一行被当作单纯的声明来处理，与它包含 extern 说明符时的待遇完全一样。

虽然把一个变量定义多次是非法的，但一个变量有多个暂定定义完全没问题。考虑清单 10-14 中的文件作用域声明。

```c
int a;
int a;
extern int a;
int a;
```

*清单 10-14：三个暂定定义和一个声明*

这里，a 有三个暂定定义，还有一个由于带 extern 说明符而不算定义的声明。因为 a 没有非暂定的定义，它会被初始化为零。因此，清单 10-14 的编译效果就如同它包含下面这一行：

```c
int a = 0;
```

至此，你已经理解了声明最重要的性质。你知道如何确定一个声明的链接、存储期，以及它是仅仅声明实体还是同时定义实体。你也理解了这些性质如何影响你能对一个标识符做什么。接下来，我们谈谈哪些地方会出问题。

### 错误情形

本章我们需要检测一大堆错误情形。其中一些在前面各章已经见过，不过细节会因新的语言构造而有所变化；我们要处理的另一些错误情形则是全新的。

#### 冲突的声明

声明发生冲突的方式有很多种。我们的编译器已经能检测其中一些。例如，当同一个标识符的两个声明出现在同一个局部作用域且至少一个没有链接时，它能检测到这个错误。之所以是错误，是因为你无法把该标识符后来的使用解析到单个实体。

前面提到过，用内部链接和外部链接声明同一标识符同样是错误。即使两个声明位于源文件中完全不同的部分，这也是问题。例如，清单 10-15 包含冲突的声明。

```c
int main(void) {
    extern int foo;
    return foo;
}

static int foo = 3;
```

*清单 10-15：链接冲突的变量声明*

在 main 中声明 foo 的那一点上，没有其他声明可见。（变量何时可见取决于它在程序源代码中的声明位置，而不是它在程序执行期间何时被初始化。）根据前面讨论的规则，这意味着 foo 具有外部链接。然而在清单后面，foo 又以内部链接在文件作用域声明。不能用内部链接和外部链接同时定义同一对象，所以这是非法的。

> **未定义行为警报！**
>
> 用内部链接和外部链接声明同一标识符会导致未定义行为。严格来说，标准并不要求编译器在声明链接冲突时报错，但它们几乎总会报错。有趣的是，下面这个程序展示了一个边界情形：GCC 会报错，Clang 却不会：

```c
static int foo = 0;

int main(void) {
    int foo = 1;
    {
        extern int foo;
        return foo;
    }
}
```

我一直弄不清 GCC 为什么拒绝这个程序，直到在 GCC bug 追踪系统（https://gcc.gnu.org/bugzilla/show_bug.cgi?id=90472#c3）里看到 Joseph Myers 的一段精彩解释。这个边界情形的决定性特征是：对一个已在作用域内、但被遮蔽的变量做块作用域 extern 声明。foo 的第一个声明具有内部链接。main 中的 extern 声明本应具有外部链接，因为它出现在第一个声明不可见之处。那样就会与第一个声明冲突。GCC 报告这一冲突并编译失败。然而，Clang 给这个 extern 声明赋予了内部链接，若无其事地继续编译，就好像第一个声明可见似的。我们会按照 Clang 的方式处理这个边界情形，不抛出错误。

最后，同一实体的两个声明如果类型不同也会冲突。用同一个名字声明外部变量和函数是非法的。同样，即便在清单 10-16 这样的程序里——冲突的声明位于程序中完全不同的部分——也是如此。

```c
int foo = 3;

int main(void) {
    int foo(void);
    return foo();
}
```

*清单 10-16：类型冲突的声明*

由于 foo 的两个声明都具有外部链接，它们本应指向同一实体，但这是不可能的，因为一个是函数声明、一个是变量声明。因此这个程序非法。

#### 多重定义

我们已经知道，在同一个程序中多次定义函数是非法的。多次定义外部变量同样非法。如果外部变量在同一个文件中被定义多次，你的编译器应当报错。如果函数或变量定义在多个文件中，你的编译器无法捕获这个错误，但链接器会。

> **未定义行为警报！**
>
> 暂定定义只在声明它的文件内部才是“暂定”的。它仍然会与定义在其他文件中的同名变量冲突。来看一个由两个源文件组成的程序。第一个文件如下：

```c
int var = 4;
```

第二个文件如下：

```c
int var;
int main(void) {
    return var;
}
```

这个程序的行为是未定义的，因为 var 被定义了多次。第一个文件显式定义并初始化了 var。第二个文件包含 var 的一个暂定定义，由于 var 没有在该文件其他地方定义，这个暂定定义应当被当作定义对待。

如果一个变量定义在两个不同的文件中，我们通常会在链接时得到错误。但只要编译器选项合适，Clang 和 GCC 都能毫无错误、毫无警告地编译这个程序。它们之所以能避免链接时错误，靠的是公共符号（common symbol）——它本质上是二进制层面的暂定定义。公共符号告诉链接器为某个符号分配空间并初始化，除非该符号定义在另一个目标文件中。

我们的实现不使用公共符号，因此无法编译这个程序。

#### 缺少定义

这类错误对函数和变量都存在。如果你使用了一个被声明却从未被定义的标识符，链接器试图寻找定义而失败时，你会在链接时得到错误。由于这是链接时错误，你的编译器不需要检测它。

#### 非法初始化器

前面已经看到，静态变量的初始化器必须是常量。块作用域的 extern 声明不能带任何初始化器，连常量初始化器也不行。

#### 存储类说明符的使用限制

不能把 extern 或 static 说明符用于函数形参或 for 循环头部声明的变量。也不能把 static 用于块作用域的函数声明。（可以对它们使用 extern，但没有任何效果。）

## 汇编中的链接与存储期

在扩展编译器的各个阶段——尤其是语义分析阶段——时，理解上一节的概念如何落实到汇编会很有帮助。我先谈链接，再谈存储期。链接相当直白：如果一个标识符具有外部链接，我们就为对应的汇编标签发射 .globl 指令；如果标识符没有外部链接，我们就不发射 .globl 指令。.globl 指令对函数名和变量名一视同仁。

再谈存储期。前面各章处理的具有自动存储期的变量都位于栈上。静态变量则位于内存中另一块区域——数据段（data section，即 .data 段）。（有些静态变量位于关系密切的 BSS 段，稍后讨论。）与栈一样，数据段是程序可以读写的内存区域。

不过，栈被划分为一个个栈帧，由完善的调用约定管理；而数据段是一大块整体内存，无论当前执行到哪个函数，它都存在。这使得数据段成为存放静态存储期变量的理想位置：数据段中的对象不会因为我们调用函数、从函数返回而被释放或覆盖。我们没有像 RSP 或 RBP 那样指向数据段特定位置的专用寄存器，也不需要它们；稍后会看到，我们可以直接按名字引用该段中的变量。

默认情况下，汇编器写入 text 段（text section），即存放机器指令的内存区域。.data 指令让汇编器改为写入数据段。清单 10-17 在数据段中初始化一个变量。

```asm
    .data
    .align 4
var:
    .long 3
```

*清单 10-17：在数据段初始化变量*

清单 10-17 的第一行表明我们要写入数据段。下一行的 .align 指令决定下一个写入值的对齐（alignment）；4 字节对齐意味着该值的字节地址必须能被 4 整除。.align 指令的含义因平台而异。在 Linux 上，.align n 产生 n 字节对齐；在 macOS 上，.align n 产生 2^n 字节对齐。也就是说，.align 4 在 Linux 上使下一个值按 4 字节对齐，而在 macOS 上按 16 字节对齐。

第三行是一个标签；数据段中的位置可以像 text 段中的位置一样加标签。最后一行把 32 位整数 3 写入当前段；由于前面的 .data 指令，当前段就是数据段。在 x64 汇编中 long 表示 32 位，所以 .long 指令总是写入一个 32 位整数。（回想一下，movl 等使用 32 位操作数的指令，其 l 后缀就代表 long。）

与其他任何标签一样，var 标签默认只在本目标文件内部可见。我们可以加上 .globl 指令，使它在其他目标文件中也可见：

```asm
    .globl var
```

前面提到，有些静态变量存放在 BSS 段。（出于晦涩的历史原因，BSS 的全称是 Block Started by Symbol。）这个段的工作方式与数据段几乎完全相同，只是它只存放初始化为零的变量。这是节省磁盘空间的一个技巧：可执行文件或目标文件只需记录 BSS 段的大小而无须记录其内容，因为内容全是零。

清单 10-18 在 BSS 段中初始化一个变量。

```asm
    .bss
    .align 4
var:
    .zero 4
```

*清单 10-18：在 BSS 段初始化变量*

这段代码与清单 10-17 有两处不同。第一，我们用 .bss 指令写入 BSS 段而不是数据段。第二，我们用 .zero n 指令写入 n 个字节的零。例如，.zero 4 把一个 4 字节整数初始化为零。无论处理数据段还是 BSS 段，.align 指令的用法、标签的声明、.globl 指令的取舍都完全一样。

如果变量在你编译的文件中只是被声明而未被定义，你不会向数据段或 BSS 段写入任何内容。

最后来看看如何在汇编指令中引用数据段中的标签。下面这行把立即数 4 写入标签 var 标记的内存地址：

```asm
movl    $4, var(%rip)
```

var(%rip) 这样的操作数使用 RIP 相对寻址（RIP-relative addressing），即相对于指令指针来引用内存地址。显然，我们不能像引用栈变量那样相对于 RBP 和 RSP 来引用数据段中的符号。我们也不能在链接时把它们替换成绝对地址，因为我们编译的是位置无关代码（position-independent code），它可以被加载到程序内存的任何位置。取而代之，我们利用 RIP 寄存器——它保存着当前指令在程序 text 段中的地址——来计算 var 之类的变量在程序数据段中的地址。

RIP 相对寻址的细节颇为复杂，我就不在这里展开了。我要再次推荐 Eli Bendersky 关于位置无关代码的几篇精彩博文，链接见第 1 章“延伸资源”（第 21 页）。

> **全局偏移量表**
>
> 在位置无关代码中，查找静态变量地址的方法其实有两种。第一种是 RIP 相对寻址。第二种是在全局偏移量表（global offset table，GOT）中查找地址。程序通常用 GOT 访问动态链接库中的变量，因为这些变量的地址可能距当前指令指针太远，RIP 相对寻址无法表示。我们的实现不会使用 GOT，因为它比 RIP 相对寻址更复杂。在 macOS 上，这意味着你将无法编译访问标准库或其他动态链接库所定义全局变量的代码。在 Linux 上，影响略有不同：你仍然可以编译访问动态链接库所定义全局变量的可执行文件，但无法编译使用全局变量的动态链接库——即使这些变量就定义在你试图编译的那个库里。（这就是上一章提到的、我们生成共享库能力所受的限制。）要理解 Linux 上为什么会这样，你需要深入链接器和加载器的内部机制。更多细节可参见 MaskRay 的博文 “Copy Relocations, Canonical PLT Entries and Protected Visibility”（https://maskray.me/blog/2021-01-09-copy-relocations-canonical-plt-entries-and-protected）。
>
> 如果你想扩展编译器来使用 GOT，我建议等到第 14 章实现指针之后再做，那样你才能扎实掌握如何在汇编中处理内存地址。

既然你已经理解了存储期、链接和变量初始化在 C 和汇编中分别如何运作，就可以动手扩展编译器了。

## 解析器

本章我们将对 AST 做两处修改：把变量声明加为一种顶层构造，并给函数声明和变量声明都加上可选的存储类说明符。清单 10-19 给出了更新后的 AST 定义。

```text
program = Program(declaration*)
declaration = FunDecl(function_declaration) | VarDecl(variable_declaration)
variable_declaration = (identifier name, exp? init, storage_class?)
function_declaration = (identifier name, identifier* params,
                        block? body, storage_class?)
storage_class = Static | Extern
block_item = S(statement) | D(declaration)
block = Block(block_item*)
for_init = InitDecl(variable_declaration) | InitExp(exp?)
statement = Return(exp)
          | Expression(exp)
          | If(exp condition, statement then, statement? else)
          | Compound(block)
          | Break
          | Continue
          | While(exp condition, statement body)
          | DoWhile(statement body, exp condition)
          | For(for_init init, exp? condition, exp? post, statement body)
          | Null
exp = Constant(int)
    | Var(identifier)
    | Unary(unary_operator, exp)
    | Binary(binary_operator, exp, exp)
    | Assignment(exp, exp)
    | Conditional(exp condition, exp, exp)
    | FunctionCall(identifier, exp* args)

binary_operator = Add | Subtract | Multiply | Divide | Remainder | And | Or
                | Equal | NotEqual | LessThan | LessOrEqual
```

*清单 10-19：带文件作用域变量和存储类说明符的抽象语法树*

我们已经定义过同时涵盖函数声明和变量声明的 declaration AST 节点。既然现在支持文件作用域变量声明，我们将在顶层使用 declaration 节点。

清单 10-20 展示了文法的相应改动。

```text
<program> ::= {<declaration>}
<declaration> ::= <variable-declaration> | <function-declaration>
<variable-declaration> ::= {<specifier>}+ <identifier> ["=" <exp>] ";"
<function-declaration> ::= {<specifier>}+ <identifier> "(" <param-list> ")" (<block> | ";")
<param-list> ::= "void" | "int" <identifier> {"," "int" <identifier>}
<specifier> ::= "int" | "static" | "extern"
<block> ::= "{" {<block-item>} "}"
<block-item> ::= <statement> | <declaration>
<for-init> ::= <variable-declaration> | [<exp>] ";"
<statement> ::= "return" <exp> ";"
              | <exp> ";"
              | "if" "(" <exp> ")" <statement> ["else" <statement>]
              | <block>
              | "break" ";"
              | "continue" ";"
              | "while" "(" <exp> ")" <statement>
              | "do" <statement> "while" "(" <exp> ")" ";"
              | "for" "(" <for-init> [<exp>] ";" [<exp>] ")" <statement>
              | ";"
<exp> ::= <factor> | <exp> <binop> <exp> | <exp> "?" <exp> ":" <exp>
<factor> ::= <int> | <identifier> | <unop> <factor> | "(" <exp> ")"
           | <identifier> "(" [<argument-list>] ")"
<argument-list> ::= <exp> {"," <exp>}
<unop> ::= "-" | "~" | "!"
<binop> ::= "-" | "+" | "*" | "/" | "%" | "&&" | "||"
          | "==" | "!=" | "<" | "<=" | ">" | ">=" | "="
<identifier> ::= ? An identifier token ?
<int> ::= ? A constant token ?
```

*清单 10-20：带文件作用域变量和存储类说明符的文法*

与清单 10-19 一致，我们把 <program> 定义为 <declaration> 符号的列表。我们还引入了新的 <specifier> 符号，它同时代表类型说明符和存储类说明符，并且要求每个声明都以一列说明符开头。这里我们增加了一点新的 EBNF 记法：把某项用花括号包起来再加一个 + 符号，表示它必须至少重复一次。因此，{<specifier>}+ 表示一个非空的说明符列表。注意 <param-list> 规则没有变化；我们仍要求每个形参用单个 int 关键字声明，而不是一列说明符。如果解析器遇到 static 或 extern 形参，应当抛出错误。

### 解析类型与存储类说明符

我们把类型说明符和存储类说明符归并为单个符号，因为它们在声明中可以以任意顺序出现。换句话说，声明

```c
static int a = 3;
```

等价于：

```c
int static a = 3;
```

等到第 II 部分添加更多类型说明符后，事情会更复杂。一个声明可能包含多个类型说明符（如 long 和 unsigned），它们相对于存储类说明符和彼此之间都可以以任意顺序出现。

为了构造 AST，解析器需要先消耗声明开头的一列说明符，再把它们转换为恰好一个类型和至多一个存储类说明符。清单 10-21 的伪代码概述了如何处理说明符列表。

```text
parse_type_and_storage_class(specifier_list):
    types = []
    storage_classes = []
  ❶ for specifier in specifier_list:
        if specifier is "int":
            types.append(specifier)
        else:
            storage_classes.append(specifier)

    if length(types) != 1:
        fail("Invalid type specifier")
    if length(storage_classes) > 1:
        fail("Invalid storage class")

  ❷ type = Int

    if length(storage_classes) == 1:
      ❸ storage_class = parse_storage_class(storage_classes[0])
    else:
        storage_class = null

    return (type, storage_class)
```

*清单 10-21：确定声明的类型和存储类*

我们先把列表划分成类型说明符和存储类说明符两部分 ❶，然后验证两个列表。类型说明符列表必须恰好包含一个值；存储类说明符列表可以为空，也可以恰好包含一个值。最后返回结果。目前 Int 是唯一可能的类型 ❷。如果存储类说明符列表不为空，就把其中的唯一元素转换为对应的 storage_class AST 节点 ❸。（我省略了 parse_storage_class 的伪代码，因为它实在没什么内容。）如果存储类说明符列表为空，则该声明没有存储类。

清单 10-21 比我们眼下的需要略复杂一些，但等后面各章添加更多类型说明符时，它很容易扩展。

### 区分函数声明与变量声明

我们剩下一个难题：不解析完整的一列类型和存储类说明符，就无法区分 <function-declaration> 和 <variable-declaration> 这两个文法符号。等到后面各章支持更复杂的声明后，这两个符号会共享更多解析逻辑。这意味着为这两个文法符号分别编写解析函数并不现实；你应当编写单个函数来解析两者并返回一个 declaration AST 节点。唯一可能出现一种声明而不允许另一种声明的位置是 for 循环的初始化子句。处理这种情况，只需解析整个声明，然后如果发现它是函数声明就报错。

## 语义分析

接下来，我们要扩展标识符解析遍（identifier resolution pass）和类型检查遍（type checking pass）。在标识符解析遍中，我们将处理顶层变量声明，并检查同一作用域内的重复声明。在类型检查遍中，我们会把存储类和链接信息加入符号表，因为生成汇编时需要这些信息。我们还将在类型检查器中处理剩下的错误情形。

### 标识符解析：解析外部变量

与函数一样，外部变量在标识符解析遍中不会被重命名。我们的标识符映射会记录每个标识符是否具有链接（内部或外部）。直到类型检查遍之前，我们无须区分内部链接和外部链接。

处理块作用域和文件作用域的变量声明需要不同的代码，因为在不同作用域下确定链接的规则不同。清单 10-22 演示了如何解析文件作用域的变量声明。

```text
resolve_file_scope_variable_declaration(decl, identifier_map):
    identifier_map.add(decl.name, MapEntry(new_name=decl.name,
                                           from_current_scope=True,
                                           has_linkage=True))
    return decl
```

*清单 10-22：解析文件作用域变量声明*

你很快会看到，这比处理块作用域变量声明的代码简单得多。我们不需要生成唯一名字，因为外部变量在整个阶段都保留原名。我们不需要担心该变量先前的声明；任何先前声明必定也具有内部或外部链接，因此它们指向同一对象，在标识符映射中对应同一条目。（文件作用域声明可能以其他方式冲突，但我们会在类型检查器中处理那些冲突。）无论声明是否带 static，我们都可以统一处理。由于无须区分内部链接与外部链接，我们继续沿用上一章的布尔属性 has_linkage。对文件作用域标识符，该属性恒为 True。我们也不需要递归处理初始化器，因为它应当是常量，因而不应包含任何需要重命名的变量。如果初始化器不是常量，我们会在类型检查时发现。

现在考虑块作用域的变量。如果一个变量用 extern 关键字声明，我们就在标识符映射中记录它具有链接，并保留其原名。否则，我们照过去处理局部变量的方式处理它。如果同一标识符在同一作用域中既以有链接的方式、又以无链接的方式声明，我们就无法维护一致的标识符映射，因此抛出错误。清单 10-23 的伪代码展示了具体做法。

```text
        --snip--
```

*清单 10-23：解析块作用域变量声明*

首先检查是否存在冲突的声明 ❶。如果该标识符已在当前作用域中声明过，我们检查先前声明的链接。如果先前声明具有链接且当前声明也具有链接（由 extern 关键字表明），则两者指向同一对象。这种情况下，两个声明是一致的，至少就标识符解析而言如此。如果两个标识符之一或全部没有链接，它们指向两个不同的对象，于是抛出错误。

假定没有冲突，我们更新标识符映射。如果该声明具有链接，它保留当前名字 ❷；否则我们给它改名 ❸。注意，无链接变量在这里的处理方式与它是否带 static 无关。还要注意，我们不需要递归处理 extern 变量的初始化器，因为它们根本不应带初始化器。（我省略了解析无链接变量初始化器的代码，因为那与前面各章相同。）

这一遍处理函数声明的方式不需要改动，只有一个小例外：如果块作用域函数声明包含 static 说明符，应当抛出错误。在标识符解析期间做这个检查很容易，就在你验证块作用域函数声明不带函数体的同一位置。不过，在类型检查器甚至解析器中抛出这个错误同样可行。

### 类型检查：跟踪静态函数与静态变量

接下来，我们将更新符号表并处理其余错误情形。我们要向符号表添加几项新信息。第一，记录每个变量的存储期。第二，记录具有静态存储期的变量的初始值。第三，记录函数和具有静态存储期的变量是否全局可见。这些信息中的每一项都会影响我们之后生成的汇编。

我们加给类型检查器的大部分逻辑严格来说并不是类型检查，因为标识符的存储类和链接独立于它的类型。但类型检查器是放置这些逻辑的天然场所，因为我们将在符号表中同时跟踪每个标识符的类型、链接和存储类。

#### 符号表中的标识符属性

对每一类标识符——函数、具有静态存储期的变量、具有自动存储期的变量——我们需要在符号表中跟踪不同的信息。清单 10-24 给出了表示所有这些信息的一种方式。

```text
identifier_attrs = FunAttr(bool defined, bool global)
                 | StaticAttr(initial_value init, bool global)
                 | LocalAttr

initial_value = Tentative | Initial(int) | NoInitializer
```

*清单 10-24：各类标识符在符号表中的属性*

StaticAttr 表示我们需要为具有静态存储期的变量跟踪的属性。initial_value 类型让我们能区分带初始化器的变量定义、不带初始化器的暂定定义以及 extern 变量声明。FunAttr 表示函数，LocalAttr 表示函数形参和具有自动存储期的变量。符号表的每个条目都应同时包含类型（如上一章所定义）和 identifier_attrs。

既然我们能在符号表中表示所需的信息，就来看看需要做类型检查的三类声明：函数声明、文件作用域变量声明和块作用域变量声明。

#### 函数声明

这里的逻辑大部分保持不变。我们仍会检查当前声明与任何先前声明的类型一致、函数没有被定义多次。唯一的区别是，我们还会记录函数是否全局可见。清单 10-25 的伪代码展示了我们如何对函数声明做类型检查，相对清单 9-21 的改动以粗体标出，部分未变化的代码被省略。（为了配合符号表表示法的变化，我还对代码做了些调整，尽管逻辑基本相同；这些调整未加粗。）

首先看函数的存储类 ❶。如果是 static，函数将不全局可见，因为它的链接是内部的。如果是 extern（或完全省略——两者等价），我们暂且认为函数全局可见，因为它的链接是外部的。不过，这会随作用域中其他声明的不同而改变。

## TACKY 生成

我们需要对 TACKY 中间表示（IR）做两处增补。第一，给函数定义加一个新的 global 字段，对应最终汇编输出中的 .globl 指令：

```text
Function(identifier, bool global, identifier* params, instruction* body)
```

第二，加一个表示静态变量的顶层构造：

```text
StaticVariable(identifier, bool global, int init)
```

我们将用这个构造同时表示外部静态变量和局部静态变量。最终，我们会把每个 StaticVariable 构造翻译成一组汇编器指令，用于在数据段或 BSS 段初始化一个对象。清单 10-28 给出了完整的 TACKY IR，相对上一章的改动以粗体标出。

```text
program = Program(top_level*)
top_level = Function(identifier, bool global, identifier* params, instruction* body)
          | StaticVariable(identifier, bool global, int init)
instruction = Return(val)
            | Unary(unary_operator, val src, val dst)
            | Binary(binary_operator, val src1, val src2, val dst)
            | Copy(val src, val dst)
            | Jump(identifier target)
            | JumpIfZero(val condition, identifier target)
            | JumpIfNotZero(val condition, identifier target)
            | Label(identifier)
            | FunCall(identifier fun_name, val* args, val dst)
val = Constant(int) | Var(identifier)
unary_operator = Complement | Negate | Not
binary_operator = Add | Subtract | Multiply | Divide | Remainder | Equal | NotEqual
                | LessThan | LessOrEqual | GreaterThan | GreaterOrEqual
```

*清单 10-28：向 TACKY 添加静态变量和 global 属性*

我们把 function_definition 节点改名为 top_level，因为它不再只表示函数。注意，把程序翻译成 TACKY 时，我们会把局部静态变量的定义移到顶层；它们变成 StaticVariable 构造，而不是函数体中的指令。

遍历 AST 并将其转换为 TACKY 时，我们会为每个顶层 Function 设置新的 global 属性，这个属性可以在符号表中查到。对于文件作用域变量声明以及带 static 或 extern 说明符的局部变量声明，我们不生成任何 TACKY。取而代之，遍历完 AST 后，我们将执行一个额外步骤：检查符号表中的每个条目，并为其中一些条目生成 StaticVariable 构造。最终的 TACKY 程序既包含从原始 AST 转换来的函数定义，也包含从符号表生成的变量定义。

清单 10-29 演示了如何把符号表条目转换为 TACKY 变量定义。

```text
convert_symbols_to_tacky(symbols):
    tacky_defs = []
    for (name, entry) in symbols:
        match entry.attrs with
        | StaticAttr(init, global) ->
            match init with
            | Initial(i) -> tacky_defs.append(StaticVariable(name, global, i))
            | Tentative -> tacky_defs.append(StaticVariable(name, global, 0))
            | NoInitializer -> continue
        | _ -> continue
    return tacky_defs
```

*清单 10-29：把符号表条目转换为 TACKY*

我们逐个查看符号表条目，判断它是否应被转换为 StaticVariable。如果它没有 StaticAttr 属性，我们跳过它，因为它不是静态变量。如果它的初始值是 NoInitializer，我们跳过它，因为它没有定义在这个翻译单元中。任何未被跳过的符号都被转换为 TACKY 的 StaticVariable 并加入 TACKY 程序。带暂定定义的静态变量被初始化为零。

目前，先处理 AST 还是先处理符号表无关紧要。但从第 16 章开始，先处理 AST、后处理符号表将变得重要。在那一章，我们会在把 AST 转换为 TACKY 的过程中向符号表添加新的静态对象；之后遍历符号表时，再把这些新条目转换为 TACKY 构造。

把新的 TACKY 构造转换为汇编很简单，因为我们只是把 TACKY 的几个字段传递给等价的汇编构造。表 10-3 总结了这一转换的最新更新，新增构造和对现有构造的改动以粗体标出。附录 B 给出了本章完整的 TACKY 到汇编转换遍，它也是第 I 部分中这一遍的最终版本。

*表 10-3：将 TACKY 顶层构造转换为汇编*

| TACKY 顶层构造 | 汇编顶层构造 |
| --- | --- |
| Program(top_level_defs) | Program(top_level_defs) |
| Function(name, global, params, instructions) | Function(name, global, [Mov(Reg(DI), param1), Mov(Reg(SI), param2), \<从寄存器复制接下来四个形参\>, Mov(Stack(16), param7), Mov(Stack(24), param8), \<从栈复制其余形参\>] + instructions) |
| StaticVariable(name, global, init) | StaticVariable(name, global, init) |

其余所有 TACKY 构造转换为汇编的方式不变。特别地，无论 TACKY 的 Var 操作数具有静态存储期还是自动存储期，我们都会把它转换为汇编的 Pseudo 操作数。这意味着 Pseudo 这个名字不再那么贴切；伪寄存器一词通常指理论上可以放进寄存器的操作数，而静态变量做不到。我们不会费事去重命名这个操作数，但你应当记住，我们是在以一种略微不寻常的方式使用“伪寄存器”这个术语。

### 根据存储期替换伪寄存器

接下来，我们要调整把伪寄存器替换为具体位置的方式。前几章中，每个伪寄存器都被分配一个栈上位置。这一次，并非每个变量都属于栈；有些存放在数据段或 BSS 段。我们将通过查符号表来区分二者。回想一下，在伪寄存器替换遍中，我们会逐步构建一个从伪寄存器到具体地址的映射。遇到不在这个映射中的伪寄存器时，我们就去符号表里查它。如果发现它具有静态存储期，就把它映射到同名的 Data 操作数；否则照常给它分配一个新的栈槽。（如果它不在符号表中，说明它是 TACKY 临时值，具有自动存储期。）例如，若 foo 是静态变量，汇编指令

```text
Mov(Imm(0), Pseudo("foo"))
```

应当被改写为：

```text
Mov(Imm(0), Data("foo"))
```

由于静态变量不在栈上，它们不计入我们需要为每个函数跟踪的栈总大小。

### 修补指令

你已经写过若干在任一操作数或两个操作数都是内存地址时适用的改写规则。记住，Data 操作数也是内存地址！例如，遇到指令

```text
Mov(Data("x"), Stack(-4))
```

应当应用 Mov 指令的源和目的都在内存时的常规改写规则。改写后的汇编为：

```text
Mov(Data("x"), Reg(R10))
Mov(Reg(R10), Stack(-4))
```

除此之外，这一遍不会变化。

## 代码发射

作为本章的收尾，你要扩展代码发射遍来处理清单 10-30 中的改动。你应当根据汇编 AST 中的 global 属性，为函数加上或省略 .globl 指令。你还应当在每个函数定义的开头加上一条 .text 指令。该指令告诉汇编器写入 text 段；既然现在还要写入数据段和 BSS 段，就需要加上它了。

发射 Data 操作数时使用 RIP 相对寻址。例如，Data("foo") 在 Linux 上是 foo(%rip)，在 macOS 上是 _foo(%rip)。把每个 StaticVariable 发射为一列汇编器指令。在 Linux 上，对于 StaticVariable(name, global, init)，若 global 为真且 init 非零，你应当发射清单 10-31 中的汇编。

```asm
    .globl <name>
    .data
    .align 4
<name>:
    .long <init>
```

*清单 10-31：全局可见、非零初始化的静态变量的汇编*

若 global 为真且 init 为零，你应当发射清单 10-32 中的汇编。

```asm
    .globl <name>
    .bss
    .align 4
<name>:
    .zero 4
```

*清单 10-32：初始化为零的全局静态变量的汇编*

若 global 为假，则发射不带 .globl 指令的清单 10-31 或 10-32。

在 macOS 上，StaticVariable 的发射内容几乎相同，只有几处细小差别。第一，符号照常以下划线开头。第二，应使用 .balign 指令而不是 .align。前面指出过 .align 指令的行为是平台相关的，.align 4 在 macOS 上会产生 16 字节对齐的值。.balign 指令的用法与 .align 完全一样，只是行为在各平台上一致：.balign n 总是把值对齐到 n 字节而不是 2^n 字节。（在 Linux 上 .balign 和 .align 可以互换，用哪个都行。）
