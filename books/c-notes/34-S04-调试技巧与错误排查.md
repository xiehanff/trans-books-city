# S04 - 调试技巧与常见错误排查

写 C 语言不遇到 bug 是不可能的，关键是怎么快速定位和解决。这一章讲实用的调试方法和工具。

---

## 常见 C 语言错误类型

### 段错误（Segmentation Fault）

程序访问了不该访问的内存地址，操作系统直接干掉进程。

常见原因：

```c
// 1. 解引用空指针
int *p = NULL;
*p = 10;  // 崩

// 2. 访问已释放的内存
int *p = malloc(sizeof(int));
free(p);
*p = 10;  // 崩（可能）

// 3. 数组越界
int arr[10];
arr[100000] = 1;  // 可能崩

// 4. 栈溢出
void recursive() {
    int big[1000000];  // 栈上申请太大
    recursive();       // 无限递归
}
```

段错误是最直接的崩溃，相对好调试——至少知道位置不对。

### 内存泄漏（Memory Leak）

分配的内存没有释放，进程占用的内存越来越多。

```c
void leak() {
    int *p = malloc(sizeof(int) * 100);
    // 忘了 free(p)，每次调用泄漏 400 字节
}

// 更隐蔽的情况：指针被覆盖
void leak2() {
    int *p = malloc(sizeof(int));
    p = malloc(sizeof(int));  // 第一块内存地址丢了，永远无法释放
    free(p);  // 只释放了第二块
}
```

小程序可能运行到结束都没事，长期运行的服务器程序会耗尽内存。

### 野指针与悬空指针

**野指针**：未初始化的指针，指向随机地址。

```c
int *p;          // 未初始化，内容是垃圾值
printf("%d", *p); // 未定义行为，可能崩
```

**悬空指针**：指向已释放内存的指针。

```c
int *p = malloc(sizeof(int));
*p = 10;
free(p);
// 此时 p 就是悬空指针，虽然值还是之前的地址
*p = 20;  // 危险操作，可能修改了别人正在用的内存
```

解决方法：释放后置 NULL。

```c
free(p);
p = NULL;
```

### 缓冲区溢出

写入数据超过缓冲区大小，覆盖了相邻内存。

```c
char buf[10];
strcpy(buf, "this string is way too long");  // 灾难

// 正确做法
strncpy(buf, "this string is way too long", sizeof(buf) - 1);
buf[sizeof(buf) - 1] = '\0';

// 或用 snprintf
snprintf(buf, sizeof(buf), "%s", "this string is way too long");
```

经典的安全漏洞来源，很多远程攻击代码执行都源于此。

### 栈溢出

栈空间用完了，通常是递归太深或局部变量太大。

```c
// 递归无终止条件
void infinite() {
    infinite();
}

// 局部变量太大
void big_local() {
    char big[10 * 1024 * 1024];  // 10MB，栈上一般没这么大
}
```

栈大小可以用 `ulimit -s` 查看（Linux），默认通常是 8MB。

### 未定义行为

标准没规定结果的行为，编译器可以随便处理。

```c
int i = 0;
int a = i++ + ++i;  // 未定义行为，不同编译器结果不同

int arr[10];
arr[10] = 1;  // 越界访问，未定义行为

int *p = (int*)0x12345;  // 随意地址
*p = 1;  // 未定义行为

printf("%d %d", i);  // 参数不够，未定义行为
```

未定义行为最危险——可能偶发、可能换个编译器就出问题、可能看着正常实际埋雷。

## GDB 调试进阶

编译时加 `-g` 选项保留调试信息：

```bash
gcc -g -o myapp myapp.c
```

启动调试：

```bash
gdb ./myapp
# 或直接带参数
gdb --args ./myapp arg1 arg2
```

### 断点类型

**普通断点**

```gdb
(gdb) break main          # 在 main 函数入口打断点
(gdb) break 25           # 在第 25 行打断点
(gdb) break file.c:30    # 在 file.c 第 30 行打断点
(gdb) break func_name    # 在函数入口打断点
(gdb) info breakpoints   # 查看所有断点
(gdb) delete 1           # 删除断点 1
(gdb) disable 1          # 禁用断点 1
(gdb) enable 1           # 启用断点 1
```

**条件断点**

只在满足条件时才停下来：

```gdb
(gdb) break 25 if i == 100
(gdb) break func if x > 0
# 已有断点加条件
(gdb) condition 1 i == 100
```

适合在循环中定位特定情况，不用手动 continue 几百次。

**监视点（Watchpoint）**

某个变量值变化时自动停下来：

```gdb
(gdb) watch variable_name    # 变量变化时停止
(gdb) watch *0x7fffffffdc    # 监视某个地址
(gdb) rwatch variable_name   # 变量被读取时停止
(gdb) awatch variable_name   # 被读或写时停止
(gdb) info watchpoints       # 查看监视点
```

追踪"谁改了这个变量"的神器。

### 调用栈分析

```gdb
(gdb) backtrace    # 或 bt，打印调用栈
(gdb) bt 10        # 只打印 10 层
(gdb) bt full      # 带局部变量值

# 假设 bt 输出：
# #0  func2 () at test.c:20
# #1  0x0000000000401156 in func1 () at test.c:30
# #2  0x0000000000401178 in main () at test.c:40

(gdb) frame 1      # 切到 #1 这一层
(gdb) up           # 往上一层（#0 -> #1）
(gdb) down         # 往下一层（#1 -> #0）
(gdb) frame        # 查看当前栈帧信息
```

切到不同栈帧后，可以用 `print` 看那一层的局部变量。

### 查看内存：x 命令

`x` 是 examine 的缩写，直接看内存内容：

```gdb
(gdb) x/10x 0x12345    # 以十六进制显示 10 个单元
(gdb) x/10i 0x12345    # 显示 10 条指令
(gdb) x/10s 0x12345    # 显示 10 个字符串

# 格式：x/NFU addr
# N = 单元数量
# F = 格式：x(十六进制) d(十进制) u(无符号) o(八进制) t(二进制) a(地址) i(指令) c(字符) s(字符串)
# U = 单元大小：b(1字节) h(2字节) w(4字节) g(8字节)

(gdb) x/20xb arr       # 显示 arr 开头 20 字节，十六进制
(gdb) x/10dw &count    # 显示 count 开头 10 个 int，十进制
```

### 多线程调试基础

```gdb
(gdb) info threads           # 列出所有线程
(gdb) thread 2               # 切到线程 2
(gdb) thread apply all bt    # 所有线程的调用栈
(gdb) set scheduler-locking on   # 只跑当前线程，其他线程暂停
(gdb) set scheduler-locking off  # 恢复
```

多线程 bug 往往是竞态条件，用 `scheduler-locking` 单步调试一个线程时不被其他线程干扰。

### 核心转储文件分析

程序崩溃时生成 core 文件，事后分析：

```bash
# 先开启 core dump
ulimit -c unlimited

# 运行程序，崩溃后生成 core 或 core.12345 文件
./myapp

# 用 gdb 分析
gdb ./myapp core
# 或 gdb ./myapp core.12345
```

进入 gdb 后直接 `bt` 看崩溃时的调用栈。

## Valgrind 内存检测

Valgrind 是内存检测的瑞士军刀，能查泄漏、越界、未初始化等问题。

### 安装与基本使用

```bash
# Ubuntu/Debian
sudo apt install valgrind

# CentOS/RHEL
sudo yum install valgrind

# 基本使用
valgrind --leak-check=full ./myapp

# 更详细的输出
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./myapp
```

不用重新编译，任何可执行文件都能直接跑。

### 检测内存泄漏

```c
// leak.c
#include <stdlib.h>

void func() {
    int *p = malloc(sizeof(int) * 10);
    // 忘了 free
}

int main() {
    func();
    return 0;
}
```

```bash
gcc -g -o leak leak.c
valgrind --leak-check=full ./leak
```

输出示例：

```
==12345== HEAP SUMMARY:
==12345==     in use at exit: 40 bytes in 1 blocks
==12345==   total heap usage: 1 allocs, 0 frees, 40 bytes allocated
==12345==
==12345== 40 bytes in 1 blocks are definitely lost in loss record 1 of 1
==12345==    at 0x4C2FB0F: malloc (in /usr/lib/valgrind/vgpreload_memcheck-amd64-linux.so)
==12345==    by 0x400544: func (leak.c:4)
==12345==    by 0x400553: main (leak.c:9)
```

直接定位到泄漏的位置。

### 检测未初始化值

```c
// uninit.c
#include <stdio.h>

int main() {
    int x;
    if (x > 0) {
        printf("positive\n");
    }
    return 0;
}
```

```bash
gcc -g -o uninit uninit.c
valgrind ./uninit
```

输出：

```
==12345== Conditional jump or move depends on uninitialised value(s)
==12345==    at 0x40054B: main (uninit.c:5)
```

### 检测非法读写

```c
// invalid.c
#include <stdlib.h>

int main() {
    int *p = malloc(10 * sizeof(int));
    p[10] = 1;  // 越界写
    int x = p[-1];  // 越界读
    free(p);
    return 0;
}
```

```bash
gcc -g -o invalid invalid.c
valgrind ./invalid
```

输出：

```
==12345== Invalid write of size 4
==12345==    at 0x400544: main (invalid.c:5)
==12345== Invalid read of size 4
==12345==    at 0x400551: main (invalid.c:6)
```

## AddressSanitizer (ASan)

Valgrind 的缺点是慢，程序可能慢 10-50 倍。ASan 是编译器内置的检测工具，性能损耗小得多（约 2 倍）。

### GCC/Clang 编译选项

```bash
# 开启 ASan
gcc -fsanitize=address -g -o myapp myapp.c

# 同时开启未定义行为检测
gcc -fsanitize=address,undefined -g -o myapp myapp.c

# 更详细的错误信息
gcc -fsanitize=address -fno-omit-frame-pointer -g -o myapp myapp.c
```

### 比 Valgrind 更快的运行时检测

ASan 在编译时插桩，运行时检测。对于越界访问、use-after-free 等问题，ASan 能当场抓住：

```c
// use_after_free.c
#include <stdlib.h>

int main() {
    int *p = malloc(sizeof(int));
    *p = 1;
    free(p);
    return *p;  // use after free
}
```

```bash
gcc -fsanitize=address -g -o use_after_free use_after_free.c
./use_after_free
```

输出：

```
=================================================================
==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000010
READ of size 4 at 0x602000000010 thread T0
    #0 0x40067b in main use_after_free.c:7
    #1 0x7f... in __libc_start_main
...
0x602000000010 is located 0 bytes inside of 4-byte region [0x602000000010,0x602000000014)
freed by thread T0 here:
    #0 0x4ed... in free (/usr/lib/x86_64-linux-gnu/libasan.so.5+0x10dcd0)
    #1 0x40066b in main use_after_free.c:6
```

告诉你：哪里读的、哪里释放的、内存申请在哪里。

### 输出解读

ASan 的错误报告结构：

1. **错误类型**：heap-use-after-free、heap-buffer-overflow、stack-buffer-overflow 等
2. **操作类型**：READ 或 WRITE
3. **位置**：哪个文件的哪一行
4. **内存信息**：这块内存的状态（已释放、栈上、堆上等）

常见错误类型：

| 错误类型 | 含义 |
|---------|------|
| heap-use-after-free | 释放后使用 |
| heap-buffer-overflow | 堆越界 |
| stack-buffer-overflow | 栈越界 |
| global-buffer-overflow | 全局变量越界 |
| stack-use-after-scope | 变量离开作用域后使用 |
| memory-leaks | 内存泄漏（需要额外选项） |

检测内存泄漏：

```bash
gcc -fsanitize=address -fsanitize=leak -g -o myapp myapp.c
# 或设置环境变量
export ASAN_OPTIONS=detect_leaks=1
./myapp
```

ASan 和 Valgrind 选哪个：

- 开发阶段用 ASan，性能损失小，迭代快
- 无法重新编译时（第三方程序）用 Valgrind
- CI/CD 中两个都跑

## 静态分析工具

在代码运行前就发现问题。

### cppcheck 简介

```bash
# 安装
sudo apt install cppcheck

# 基本用法
cppcheck myapp.c

# 检查整个目录
cppcheck --enable=all src/

# 输出到文件
cppcheck --enable=all src/ 2> report.txt
```

示例输出：

```
[error.c:5]: (error) Null pointer dereference
[error.c:10]: (error) Array 'arr[10]' accessed at index 10, which is out of bounds.
[error.c:15]: (warning) Memory leak: p
```

`--enable=all` 会检查更多信息，包括风格问题。日常可以用 `--enable=warning,performance`。

### clang-tidy 简介

基于 Clang 的静态分析，功能更强，需要编译数据库：

```bash
# 安装
sudo apt install clang-tidy

# 生成 compile_commands.json（CMake 项目）
cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON ..

# 运行检查
clang-tidy myapp.c --

# 使用 compile_commands.json
clang-tidy -p build/ src/myapp.c

# 检查所有文件
clang-tidy -p build/ src/*.c

# 自动修复
clang-tidy -p build/ -fix src/myapp.c
```

常用检查项：

```bash
# 只检查特定问题
clang-tidy -p build/ -checks='modernize-*' src/myapp.c

# 检查 bugprone 规则
clang-tidy -p build/ -checks='bugprone-*' src/myapp.c

# 列出所有检查项
clang-tidy --list-checks
```

## 常见错误模式与修复

### 数组越界

```c
int arr[10];
for (int i = 0; i <= 10; i++) {  // 应该是 i < 10
    arr[i] = 0;
}
```

修复：边界检查用 `<` 而非 `<=`，下标从 0 开始。

### 格式化字符串漏洞

```c
char buf[100];
fgets(buf, sizeof(buf), stdin);
printf(buf);  // 危险！用户输入可能包含 %s %x 等
```

正确写法：

```c
printf("%s", buf);
```

### 使用未初始化变量

```c
int x;
printf("%d\n", x);  // 未初始化

int *p;
*p = 10;  // 未初始化的指针
```

修复：声明时初始化，或用之前赋值。

```c
int x = 0;
int *p = NULL;

if (p != NULL) {
    *p = 10;
}
```

### 返回栈上变量地址

```c
int* get_value() {
    int value = 42;
    return &value;  // 返回局部变量地址
}

int *p = get_value();
// 此时 p 指向的内存已经被回收
```

修复：返回动态分配的内存，或用静态变量/全局变量，或让调用者传入缓冲区。

```c
// 方案 1：动态分配
int* get_value() {
    int *p = malloc(sizeof(int));
    *p = 42;
    return p;
}

// 方案 2：调用者提供缓冲区
void get_value(int *out) {
    *out = 42;
}
```

### double-free

```c
int *p = malloc(sizeof(int));
free(p);
free(p);  // 重复释放，崩溃或内存损坏
```

修复：释放后置 NULL，并检查。

```c
free(p);
p = NULL;

free(p);  // free(NULL) 是安全的，什么都不做
```

## 调试技巧总结

### 打印调试 vs 断点调试

**打印调试**

优点：
- 简单直接，不需要学习工具
- 适合复杂流程跟踪
- 适合多进程、分布式场景

缺点：
- 需要重新编译
- 可能影响性能
- 输出多时信息淹没

```c
#define DEBUG 1
#if DEBUG
#define LOG(fmt, ...) fprintf(stderr, "[%s:%d] " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__)
#else
#define LOG(fmt, ...)
#endif

LOG("x = %d, y = %d", x, y);
```

**断点调试**

优点：
- 不改代码
- 可以查看任意变量
- 可以单步、条件中断

缺点：
- 学习曲线
- 多线程、异步场景复杂
- 需要能复现问题

什么时候用什么：

- 问题能稳定复现，用 GDB
- 复杂流程逻辑问题，先打日志定位范围
- 生产环境问题，依赖日志（无法 attach）
- 并发问题，日志 + 核心转储

### 二分法定位问题

不知道问题出在哪，逐一排查：

1. 用 git bisect 自动二分（如果 bug 是某次提交引入的）
2. 在代码中间位置打断点或加日志，看是否正常运行到
3. 如果能，问题在后半段；如果不能，问题在前半段
4. 重复直到定位到具体函数或代码块

### 减法调试（逐步注释代码）

大块代码出问题，逐步排除：

1. 注释掉一半代码
2. 如果问题消失，说明在注释的那一半
3. 如果问题还在，说明在没注释的那一半
4. 重复直到找到具体位置

类似二分法，但适用于代码逻辑块。

---

调试是程序员日常，工具只是辅助，核心是对程序执行流程的理解。遇到问题先想"可能是什么原因"，再用工具验证假设，效率比盲人摸象高得多。
