# 第 12 章 构建中间件

*Chapter 12: Building the Middleware*

中间件（middleware）是把我们稍后要创建的前端连接到后端容器中已有 MongoDB 实例的软件“粘合剂”。在本章中，我们将配置 Mongoose，把它连接到我们的数据库，然后为应用创建一个 Mongoose 模型。在下一章中，我们将通过编写 GraphQL API 来完成中间件。

这部分中间件属于 Next.js，因此我们要在应用容器中开展工作。不过，由于 Docker 守护进程会确保本地应用目录中的文件即时同步到应用容器内的工作目录，我们可以使用本地的代码编辑器或 IDE 来修改本地机器上的文件。无需连接容器 shell，更不必与 docker compose 交互；所有改动都应该会立刻显示在 http://localhost:3000 上。

## 连接 Mongoose

现在可以开始动手做中间件了。我们先把 Mongoose 添加到应用中。连接到应用容器的终端：

```bash
$ docker exec -it foodfinder-application npm install mongoose
```

这里我们使用 npm install mongoose 来安装这个包。只要容器还在运行，我们就不必立即重建前端镜像，因为我们已经把包直接安装进了正在运行的容器。

### 编写数据库连接

为了把 Next.js 应用连接到 MongoDB 实例，我们将定义环境变量 `MONGO_URI`，并为它指定一个与后端暴露的端口和位置相匹配的连接字符串。在应用根目录中、`tsconfig.json` 文件旁边新建一个 `.env.local` 文件，并向其中加入这一行：

```bash
MONGO_URI=mongodb://backend:27017/foodfinder
```

现在我们可以把应用连接到 Docker 容器在 27017 端口上暴露的 MongoDB 实例了。在根文件夹 `code/foodfinder-application` 中创建一个名为 `middleware` 的文件夹，所有与中间件相关的 TypeScript 文件都将放在这里。在该文件夹中新建一个文件 `db-connect.ts`，并把代码清单 12-4 中的代码粘贴进去。

```typescript
import mongoose, {ConnectOptions} from "mongoose";

const MONGO_URI = process.env.MONGO_URI || " ";

if (!MONGO_URI.length) {
    throw new Error(
        "Please define the MONGO_URI environment variable (.env.local)"
    );
}
let cached = global.mongoose;

if (!cached) {
    cached = global.mongoose = {conn: null, promise: null};
}

async function dbConnect(): Promise<any> {

    if (cached.conn) {
        return cached.conn;
    }

    if (!cached.promise) {

        const opts: ConnectOptions = {
            bufferCommands: false,
            maxIdleTimeMS: 10000,
            serverSelectionTimeoutMS: 10000,
            socketTimeoutMS: 20000,
        };

        cached.promise = mongoose
            .connect(MONGO_URI, opts)
            .then((mongoose) => mongoose)
            .catch((err) => {
                throw new Error(String(err));
            });
    }

    try {
        cached.conn = await cached.promise;
    } catch (err) {
        throw new Error(String(err));
    }

    return cached.conn;
}

export default dbConnect;
```

*代码清单 12-4：db-connect.ts 中把应用连接到数据库的 TypeScript 代码*

我们导入了 `mongoose` 包和 `ConnectOptions` 类型，二者都是连接数据库所必需的。随后，我们从环境变量中加载连接字符串，并验证该字符串不为空。

接下来，我们建立连接缓存。我们使用一个全局变量在热重载（hot-reload）之间维持连接，并确保对 `dbConnect` 函数的多次调用总是返回同一个连接。否则，应用就有可能在每次热重载或每次函数调用时创建新连接，这两种情况都会很快耗尽内存。如果还没有缓存的连接，我们就用一个占位对象来初始化它。

我们创建了异步函数 `dbConnect`，由它真正打开并管理连接。数据库是远程的，并非即时可用，因此我们使用一个 async 函数，并将其作为模块的默认函数导出。在函数体内，我们先检查是否已存在缓存的连接，如果存在就直接返回；否则就创建一个新连接。为此，我们先定义连接选项，然后创建新连接；这里我们使用 promise 模式，以提醒我们处理异步调用有两种可能的方式。最后，我们等待连接就绪，然后返回 Mongoose 实例。

现在，只需从 `middleware/db-connect` 模块导入 `dbConnect` 函数并 await 这个 Mongoose 连接，就能通过 Mongoose 打开到 MongoDB 的缓存连接。

### 修复 TypeScript 警告

在 IDE 中，你应该立刻就能看到 TSC 对使用 `global.mongoose` 发出的警告。仔细看这条消息——`Element implicitly has an 'any' type because type 'typeof globalThis' has no index signature.ts (7017)`——它会告诉我们，需要向 `globalThis` 对象添加 `mongoose` 属性。

正如第 3 章所讨论的，我们使用 `custom.d.ts` 文件来定义自定义全局类型。在根目录中、`middleware` 文件夹旁边新建一个文件 `custom.d.ts`。只要把代码清单 12-5 中的代码粘贴进去，全局命名空间中就应该会包含类型为 `mongoose` 的 `mongoose` 属性，TSC 也就能找到它了。

```typescript
import mongoose from "mongoose";

declare global {
    var mongoose: mongoose;
}
```

*代码清单 12-5：custom.d.ts 中用于定义自定义全局类型 mongoose 的代码*

有了这个自定义全局类型定义（type definition），TSC 就不会再抱怨 `global.mongoose` 缺少类型定义了。接下来，我们可以为全栈应用创建 Mongoose 模型了。

## Mongoose 模型

正如你在第 11 章的种子脚本（seed script）中看到的，我们的应用有一个数据库，其中包含一个由表示位置数据的文档组成的集合。我们将为这个位置集合创建一个 Mongoose 模型。在第 7 章你已了解到，这需要有一个接口（interface）来为 TypeScript 标注文档类型、一个向模型描述文档的 schema、一个类型定义（type definition），以及一组定义 Mongoose 模型所需的自定义类型。此外，我们还将创建一组自定义类型，用于在应用的 `locations` 模型上执行 CRUD 操作。

在 Next.js 根目录中、`middleware` 文件夹旁边创建一个 `mongoose` 文件夹及其子文件夹 `locations`。`mongoose` 文件夹将存放所有与 Mongoose 总体相关的文件，而 `locations` 文件夹将包含所有专属于位置模型的文件。

### 创建 schema

在第 7 章你已了解到，schema 描述数据库文档的结构，并且需要先创建 TypeScript 接口再创建 schema，以便相应地为 schema 和模型标注类型。严格来说，在 6.3.1 之后的 Mongoose 版本中，我们已不必自己定义这个接口，而是可以从 schema 自动推断出接口作为类型。在 `mongoose/locations` 文件夹中创建文件 `schema.ts`，并把代码清单 12-6 中的代码粘贴进去。

```typescript
import {Schema, InferSchemaType} from "mongoose";

export const LocationSchema: Schema = new Schema<LocationType>({
    address: {
        type: "String",
        required: true,
    },
    street: {
        type: "String",
        required: true,
    },
    zipcode: {
        type: "String",
        required: true,
    },
    borough: {
        type: "String",
        required: true,
    },
    cuisine: {
        type: "String",
        required: true,
    },
    grade: {
        type: "String",
        required: true,
    },
    name: {
        type: "String",
        required: true,
    },
    on_wishlist: {
        type: ["String"],
        required: true,
    },
    location_id: {
        type: "String",
        required: true,
    },
});

export declare type LocationType = InferSchemaType<typeof LocationSchema>;
```

*代码清单 12-6：mongoose/locations/schema.ts 文件*

我们导入了 `Schema` 构造函数和用于推断 schema 类型的 `InferSchemaType`，二者都是 Mongoose 模块的一部分。然后我们定义 schema 并直接将其导出。这个 schema 本身很简单。位置集合中的文档有几个含义自明的属性，除 `on_wishlist` 属性是字符串数组之外，其余全部标注为字符串类型。为了让应用保持简单，我们会把把某个位置加入心愿单的用户 ID 直接存储在该位置的文档中，而不是为每个用户的心愿单单独创建 Mongoose 模型和 MongoDB 文档。对于真实应用来说，这并不是一个好设计，但就我们的目的而言已经足够。最后，我们直接从 schema 推断并导出 `LocationType`，而不再手动创建接口。

### 创建位置模型

schema 和所需的接口就绪之后，就该创建模型了。在 `mongoose/location` 文件夹中创建文件 `model.ts`，并把代码清单 12-7 中的代码粘贴进去。

```typescript
import mongoose, {model} from "mongoose";
import {LocationSchema, LocationType} from "mongoose/locations/schema";

export default mongoose.models.locations ||
    model<LocationType>("locations", LocationSchema);
```

*代码清单 12-7：mongoose/locations/model.ts 文件*

从 Mongoose 包导入所需的依赖之后，我们从先前创建的 `schema.ts` 文件中导入 `LocationSchema` 和 `LocationType`。然后，我们用它们来创建并导出 `locations` 模型——除非已经存在一个初始化好的名为 `locations` 的模型，在这种情况下，我们返回已有的那个。

至此，我们已经成功创建了 Mongoose 模型并将其连接到数据库。现在，我们可以通过 Mongoose 的 API 访问 MongoDB 实例，并对 `locations` 集合中的文档执行创建、读取、更新和删除操作。

为了验证一切是否正常，可以创建一个临时的 REST API，它先初始化与数据库的连接，然后通过模型查询所有文档。可以在应用的 `pages/api` 文件夹中新建文件 `test-middleware.ts`，并把代码清单 12-8 中的代码粘贴进去。

```typescript
import type {NextApiRequest, NextApiResponse} from "next";

import dbConnect from "middleware/db-connect";
import Locations from "mongoose/locations/model";

export default async function handler(
    req: NextApiRequest, res: NextApiResponse<any>

    await dbConnect();
    const locations = await Locations.find({});
    res.status(200).json(locations);
```

这个 API 从 Next.js 导入了所需的依赖，还导入了 `dbConnect` 函数和我们先前创建的 `Locations` 模型。在这个异步 API 处理器（handler）中，它先调用 `dbConnect` 函数，并等待 Mongoose 连接到数据库；然后在 `Locations` 模型上以空的过滤对象调用 Mongoose 的 find API。一旦收到位置数据，API 处理器就会把它们发送给客户端。

## 模型的服务

第 6 章讨论过，我们通常会把数据库 CRUD 操作抽象成服务调用，以便简化后续 GraphQL API 的实现。我们现在要做的正是这件事，第一步先梳理所需的功能。

我们需要一个公共服务来查询所有可用的位置，以便在应用的概览页面中展示它们。为了显示某个位置的详情，我们还需要另一个公共服务来查找特定的位置。我们选择把位置的 ID 作为该服务的参数，然后按 ID 查找位置。为了支持心愿单功能，我们需要一个能够更新用户心愿单的服务，以及另一个可用于判断给定位置当前是否在用户心愿单上的服务；根据判断结果，我们将显示 Add To（加入）或 Remove From（移除）按钮。

为了设计查找并返回位置的服务调用，我们将为每个公共 API 创建一个公共函数，并创建一个统一的内部函数 `findLocations`，由它调用 Mongoose 的 find 函数。公共 API 负责构造 Mongoose 用来过滤集合中文档的过滤对象，换句话说，也就是构造数据库查询；同时，它还负责设置要传给 Mongoose API 的其他选项。这样的设计应当能减少我们需要编写的代码量，并避免重复。

### 创建位置服务的自定义类型

你可能已经注意到，统一的 `findLocations` 函数的参数需要用到两个自定义类型：一个参数定义与心愿单相关的查找操作的属性，另一个是位置的 ID。在 `mongoose/location` 文件夹中创建文件 `custom.d.ts` 来定义这些类型，如代码清单 12-9 所示。

```typescript
export declare type FilterLocationType = {
    location_id: string | string[];
};

export declare type FilterWishlistType = {
    on_wishlist: {
        $in: string[];
    };
};
```

*代码清单 12-9：mongoose/locations/custom.d.ts 文件*

我们定义并直接导出这两个自定义类型。`FilterLocationType` 很简单，它定义了一个只含一个属性的对象，即位置 ID，其取值是字符串或字符串数组。我们用它按 ID 查找位置。第二个类型是 `FilterWishlistType`，我们将用它来查找 `on_wishlist` 属性中包含用户 ID 的所有位置。我们把 Mongoose 的 `$in` 操作符的值设置为一个字符串数组。

### 创建位置服务

服务的自定义类型创建完毕之后，就可以实现这些服务了。照例，我们在 `mongoose/location` 文件夹中创建文件 `services.ts`，并把代码清单 12-10 中的代码加入其中。

```typescript
import Locations from "mongoose/locations/model";
import {
    FilterWishlistType,
    FilterLocationType,
} from "mongoose/locations/custom";
import {LocationType} from "mongoose/locations/schema";
import {QueryOptions} from "mongoose";

async function findLocations(
    filter: FilterLocationType | FilterWishlistType | {}
): Promise<LocationType[] | []> {
    try {
    let result: Array<LocationType | undefined> = await Locations.find(
            filter
        );
        return result as LocationType[];
    } catch (err) {
        console.log(err);
    }
    return [];
}

export async function findAllLocations(): Promise<LocationType[] | []> {
    let filter = {};
    return await findLocations(filter);
}

export async function findLocationsById(
    location_ids: string[]
): Promise<LocationType[] | []> {
    let filter = {location_id: location_ids};
    return await findLocations(filter);
}

export async function onUserWishlist(
    user_id: string
): Promise<LocationType[] | []> {
    let filter: FilterWishlistType = {
        on_wishlist: {
            $in: [user_id],
        },
    };
    return await findLocations(filter);
}

export async function updateWishlist(
    location_id: string,
    user_id: string,
    action: string
) : Promise<LocationType | null | {}>
 {
    let filter = {location_id: location_id};
    let options: QueryOptions = {upsert: true, returnDocument: "after"};
    let update = {};

    switch (action) {
        case "add":
            update = {$push: {on_wishlist: user_id}};
            break;
        case "remove":
            update = {$pull: {on_wishlist: user_id}};
            break;
    }

    try {
        let result: LocationType | null = await Locations.findOneAndUpdate(
            filter,
            update,
            options
        );
        return result;
    } catch (err) {
        console.log(err);
    }
    return {};
}
```

*代码清单 12-10：mongoose/locations/services.ts 文件*

导入依赖之后，我们创建真正在模型上调用 Mongoose 的 find API 并等待数据库返回数据的函数。所有使用 find 的公共服务都将通过这个函数查询数据库，因此它是我们所有服务的基石。它唯一的参数——过滤对象——可以传给模型的 find 函数，以检索符合过滤条件的文档。过滤对象要么是一个返回所有位置的空对象，要么是我们的自定义类型 `FilterLocationType` 或 `FilterWishlistType`。一旦拿到数据库返回的数据，我们就把它转换为 `LocationType`，然后返回。如果发生错误，我们就记录日志，并返回一个空数组，以符合已定义的返回类型：`LocationType` 数组或空数组。

接下来的三个函数是公共服务，它们将为其他 TypeScript 模块和用户界面提供数据库访问。它们都遵循相同的结构。首先，在 `findLocationsById` 函数中，我们把过滤对象设置为一个特定的参数；然后用这个服务专属的过滤对象调用 `findLocations` 函数。由于每个服务调用的都是同一个函数，这些服务也具有相同的返回签名，各自返回位置数组或空数组。第一个服务使用空对象，因此不做任何过滤，而是返回集合中的所有文档。`findLocationsById` 函数使用 `FilterLocationType`，返回与给定位置 ID 匹配的文档。

下一个函数 `onUserWishlist` 使用了一个稍微复杂些的过滤对象。它的类型是 `FilterWishlistType`，我们把它传给 `findLocations` 函数，以获取 `on_wishlist` 数组中包含给定用户 ID 的所有位置。注意，我们在声明时就显式地为过滤对象标注了类型。这偏离了第 3 章给出的建议，但我们在这里这样做，是为了确保 TSC 会校验对象的属性，因为在这种情况下它无法从用法中推断出类型。

最后，我们实现 `updateWishlist` 函数。它与前面的几个函数略有不同，但整体结构应该似曾相识。同样，我们用第一个参数构造过滤对象，并用第二个参数——用户 ID——来更新 `on_wishlist` 数组。不过，与前面的函数不同的是，我们用另一个参数来指明是要把用户 ID 加入数组还是从数组中移除。在这里使用 switch/case 语句是减少对外暴露服务数量的便捷方式。根据 action 参数，我们向 update 对象填入 `$push` 操作符（把用户 ID 加入 `on_wishlist` 数组）或 `$pull` 操作符（把用户 ID 从数组中移除）。我们把该对象传给 Mongoose 的 findOneAndUpdate API，查找第一个与过滤条件匹配的文档，直接更新该记录，然后返回更新后的文档或空对象。

## 总结

我们已经成功创建了中间件的第一部分。借助本章的代码，我们可以使用 Mongoose 模型对 MongoDB 集合中的文档执行创建、读取、更新和删除操作。为了执行这些操作，我们搭建了服务，稍后会把它们接入即将编写的 GraphQL API。在下一章中，我们将删除用于测试的临时 API 中间件，并用真正的 GraphQL API 取而代之。
