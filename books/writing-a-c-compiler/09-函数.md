# 第 9 章　函数

*Chapter 9: Functions*

函数（function）是可以在一处定义、在另一处调用的一段代码，是所有主流编程语言中的基础概念。它实在太基础了，以至于处理器专门设有用于函数调用的指令。本章中，你将按照类 Unix 系统的标准调用约定（calling convention）来实现函数调用和函数定义——该约定精确定义了函数调用在汇编层面应当如何工作。调用约定让分别编译的二进制文件（甚至可能由不同源语言编写）得以互操作。只要遵循系统的调用约定，你就能编译调用外部库（包括标准库）中函数的程序。你编译的程序终于能够执行 I/O 操作了！其他编译器构建的程序也将能够使用你的编译器构建的库。

本章的大部分篇幅将花在语义分析和汇编代码生成上。在语义分析阶段，我们将添加一个新的类型检查遍（type checking pass，在本章开头示意图中以粗体标出）。这一遍目前还相当简陋，但随着我们在第 II 部分中不断添加新类型，我们会逐步充实它。在汇编生成阶段，我们将深入研究系统的调用约定，它告诉我们如何建立栈帧（stack frame）、传递实参和返回值，以及把控制权从一个函数转移到另一个函数。

先来准确界定我们要实现的特性。

## 声明、定义与调用函数

本章中，你将实现函数调用、函数声明和函数定义。函数声明（function declaration）告诉你一个函数的名字和类型。声明把函数名引入作用域，以便之后调用它。函数定义（function definition）是包含函数体的声明。（所有函数定义都是声明，但并非所有声明都是定义。）你的编译器已经对函数定义有了一定支持，因为它能编译 main。现在你要把它推广到编译其他函数。

### 声明与定义

如清单 9-1 所示的函数声明必须包含函数的返回类型、函数名，以及每个形参的类型和名字。

```c
int foo(int param1, int param2, int param3);
```

*清单 9-1：一个函数声明*

目前，函数的返回类型和所有形参的类型都必须是 int。我们已经见过，如果一个函数没有形参，它的形参列表就是 void 关键字：

```c
int foo(void);
```

函数定义看起来就像清单 9-1 中的函数声明，再加上一个函数体。清单 9-2 给出了一个函数定义的例子。

```c
int foo(int param1, int param2, int param3) {
    return param1 + param2 + param3;
}
```

*清单 9-2：一个函数定义*

同一个函数你可以声明任意多次，但所有声明必须兼容：返回类型、形参类型和形参个数必须相同。形参名可以因声明而异，因为只有函数定义中的形参名会被使用。例如，清单 9-3 是完全合法的。

```c
int foo(int x, int y, int z);

int main(void) {
    return foo(1, 2, 3);
}

int foo(int param1, int param2, int param3);

  int foo(int a, int b, int c) {
    return a + b + c;
}
```

*清单 9-3：用不同的形参名多次声明同一个函数*

虽然多次声明一个函数是合法的，但一个函数不能被定义多次；否则当这个函数被调用时，将无从判断该执行哪个定义。

你可以在两个地方声明函数：顶层和其他函数体内。清单 9-4 同时包含这两种声明。

```c
int foo(int a, int b);

int main(void) {
    int foo(int a, int b);
    return foo(1, 2);
}
```

*清单 9-4：嵌套的与顶层的函数声明*

但是，你不能在另一个函数体内定义函数。C 标准只支持顶层的函数定义，所以它不允许清单 9-5 这样的程序。

```c
int main(void) {
    int foo(int a, int b) {return a + b;};
    return foo(1, 2);
}
```

*清单 9-5：嵌套的函数定义（不受支持）*

有些编译器把嵌套函数定义作为一种语言扩展来支持，可以顺利编译清单 9-5。我们不会实现这个语言扩展；我们只坚持实现 C 标准中的特性。

**我们不实现的一些东西**

C 提供了几种略有差别的函数声明方式。为了让事情简单，我们不会支持全部方式，只处理清单 9-1 中给出的那种形式。例如，我们不支持旧式函数定义（old-style function definition），它长这样：

```c
int foo(param1, param2, param3)
int param1, param2, param3;
{
    return param1 + param2 + param3;
}
```

在本书使用的 C 标准参考版本 C17 中，旧式函数定义是一个过时（obsolescent）特性。如果某个特性将来可能被移除、不应在新代码中使用，C 标准就会把它标记为过时的。标准的下一个版本 C23 确实把这个特性从语言中移除了。

我们还会拒绝没有形参列表的函数声明，比如这个：

```c
int foo();
```

按照 C17 标准，一个既没有形参列表也没有函数体的函数声明不提供关于该函数形参的任何信息。换句话说，这个声明表明某个名为 foo 的函数在作用域内且返回整数，但它没告诉我们这个函数有多少个形参。

空的形参列表在 C17 中同样属于过时特性。在 C23 中，它们是允许的，但含义变了：空形参列表不再表示声明一个未指明形参的函数，而是声明一个没有形参的函数。换句话说，在 C23 中，声明 int foo(); 和 int foo(void); 是等价的。

对于不是定义的函数声明，C 标准允许只给出形参的类型而省略形参名，但我们会要求每个形参都有名字。从形参列表中省略标识符并不是过时特性；我们只是懒得去管它。

我们还略去了几个更重要的特性，包括参数数量可变的函数（变参函数），以及 inline 或 _Noreturn 这样的函数说明符（function specifier）。最后，我们不会实现函数指针（function pointer），即保存函数地址的变量。如果你想自己实现函数指针，我建议等到第 15 章添加数组之后再动手。C 的类型系统对数组类型表达式和函数类型表达式的处理方式惊人地相似：在大多数上下文中，数组类型的表达式会被隐式转换为指针，函数类型的表达式会被隐式转换为函数指针。

### 函数调用

函数调用（function call）由函数名后跟一对括号括起来的、以逗号分隔的一串实参组成：

```c
foo(1, 2, 3);
```

函数声明中的标识符叫函数形参（parameter），而传给函数调用的表达式叫函数实参（argument）。例如在清单 9-6 中，a、b、c 是 foo 的形参，而 a + b 和 2 * c 是传给 bar 的实参。

```c
int foo(int a, int b, int c) {
    return bar(a + b, 2 * c);
}
```

*清单 9-6：函数形参与函数实参*

正如清单 9-7 所示，函数在被调用之前必须已声明，但不一定已定义。

```c
int foo(int arg1, int arg2, int arg3);

int main(void) {
    return foo(1, 2, 3);
}
```

*清单 9-7：先声明再调用函数*

foo 的定义可以出现在同一文件靠后的位置，也可以出现在单独的库中。找到程序所调用的每个函数的定义，是链接器而非你的编译器的职责。如果链接器找不到定义，链接就会失败。

在声明之前调用函数是非法的，所以清单 9-8 是无效的。

```c
int main(void) {
    return foo(1, 2, 3);
}

int foo(int arg1, int arg2, int arg3);
```

*清单 9-8：在声明之前调用函数*

实践中，许多编译器对调用未声明函数的程序只是警告而不拒绝。我们的实现更严格，会在语义分析阶段拒绝清单 9-8 这样的程序。

以错误数量的实参调用函数，或者把变量当函数调用，同样是非法的。（如果我们实现函数指针的话，第二点它会是例外。）

### 标识符链接性

函数名和变量名都是标识符。它们存在于同一个命名空间，遵循相同的作用域规则。函数名和变量名一样，可能被内层作用域中的其他声明遮蔽。考虑清单 9-9，其中变量名 foo 遮蔽了函数名 foo。

```c
int foo(int a, int b);

int main(void) {
    int foo = 3;
    return foo;
}
```

*清单 9-9：变量名遮蔽函数名*

这个程序编译无误并返回 3。函数名也可以遮蔽变量名，如清单 9-10 所示。

```c
int main(void) {
    int a = 3;
    if (a > 0) {
        int a(void);
        return a();
    }
    return 0;
}
```

*清单 9-10：函数名遮蔽变量名*

这里函数名 a 遮蔽了变量名 a；只要函数 a 定义在别处，这个程序同样能编译通过。

但在其他方面，函数声明与我们目前见过的局部变量声明的解析方式大相径庭。每个局部变量声明都引用一个不同的变量，即使其中一些变量同名（在变量解析遍中给每个变量起唯一的名字时，我们把这一点明确化了）。但同名的多条函数声明都引用同一个函数。考虑清单 9-11，它包含三条使用 incr 这个名字的函数声明。

```c
int two(void) {
    int incr(int i);
    return incr(1);
}

int incr(int i);

int main(void) {
    return two() + incr(3);
}

int incr(int i) {
    return i + 1;
}
```

*清单 9-11：引用同一个定义的多条函数声明*

这些声明最终都引用同一个函数定义。这段清单并不是声明了三个都叫 incr 的不同函数，而是包含同一个函数的三条声明。

在 C 标准中，声明的链接性（linkage）决定了它如何关联到同一标识符的其他声明。链接性有几种。按照 C 标准第 6.2.2 节第 2 段，“每一个具有外部链接性（external linkage）的特定标识符声明都表示同一个对象或函数。”在清单 9-11 中，incr 的每一条声明都具有外部链接性，所以这些声明全都引用同一个函数定义。具有外部链接性的声明即使出现在不同的翻译单元（translation unit，也就是预处理后的源文件）中，也可以引用同一个对象或函数。

考虑一个由两个不同文件组成的程序。在其中一个文件（清单 9-12）中，我们定义一个函数。

```c
int library_fun(int a, int b) {
    return a + b;
}
```

*清单 9-12：在一个文件中定义库函数*

在另一个文件（清单 9-13）中，我们声明并使用该函数。

```c
int library_fun(int a, int b);

int main(void) {
    return library_fun(1, 2);
}
```

*清单 9-13：在另一个文件中声明并调用库函数*

尽管 library_fun 在两个不同的文件中都有声明，链接器会识别出这两条声明指的是同一个东西：清单 9-12 中 library_fun 的定义。然后它会把清单 9-13 的二进制代码中每一处 library_fun 的使用都更新为指向清单 9-12 中的定义。

本章中，所有函数标识符都具有外部链接性。而局部变量没有链接性（no linkage）。C 标准第 6.2.2 节第 2 段说：“每一个无链接性的标识符声明都表示一个独立实体。”局部变量不能和另一个局部变量引用同一个对象，也不能和具有外部链接性的标识符（比如函数名）引用同一个东西。

**注意**

看起来标识符的链接性只取决于它是函数还是变量，但下一章你会看到事实并非如此。我们将实现具有外部链接性的全局变量声明，还将实现具有第三种链接性——内部链接性（internal linkage）——的函数声明和变量声明。具有内部链接性的声明可以与同一翻译单元中的其他声明相链接，但不能与其他翻译单元中的声明相链接。

由于给定函数名的所有声明必须引用同一个函数定义，它们即使出现在不同作用域中也必须彼此兼容。清单 9-14 包含两条不兼容的函数声明。

```c
int main(void) {
    int f(int x);
    int ret = f(1);
    if (ret) {
        int f(int a, int b);
        return f(0, 1);
    }
    return 0;
}
```

*清单 9-14：相互冲突的函数声明*

f 的这两条声明应当引用同一个函数，因为它们都具有外部链接性。但没有任何函数定义能同时满足这两条声明，因为二者的形参个数不同。由于这两条声明冲突，这段代码无法通过编译。

**链接期的标识符链接性**

如果了解链接器如何处理每一种标识符，链接性会更容易理解。具有外部链接性的标识符在最终汇编程序中成为全局符号（global symbol）。我们已经见过全局符号，它用 .globl 指令声明：

```asm
    .globl main
main:
```

因为 main 是全局的，链接器可以解析出现在其他目标文件中对它的引用。在一个目标文件中定义全局符号、在其他目标文件中使用它，这很正常；但如果同一个全局符号在两个不同的目标文件中都有定义，链接就会失败。

具有内部链接性的标识符在汇编程序中表现为局部符号（local symbol）。局部符号的声明方式与全局符号相同，只是不带 .globl 指令：

```asm
local:
```

链接器会解析同一目标文件内对局部符号的引用，但不会解析其他目标文件中对它们的引用。比如，如果两个目标文件都包含名为 foo 的局部符号，链接器会认为它们指的是两个不同的对象。

如果标识符没有链接性，链接器根本感知不到它，因为它不对应汇编程序中的任何符号。它只对应某个相对 RBP 偏移处的栈地址。

介绍完函数的这些背景知识，我们就可以着手改编译器了。但我们不会立刻从词法分析器开始。首先需要更新编译器驱动。

## 编译库

在前几章中，我们只能编译独立可执行文件。我们编译的每个源文件都定义了一个 main 函数，也就是程序的入口点。既然现在能处理其他函数了，我们也应该能编译没有入口点的库。你的编译器把源代码翻译成汇编时，并不关心处理的是库还是可执行文件。但你的编译器驱动确实关心，因为链接器期望一个完整的程序包含 main。如果用你现在的编译器驱动编译一个没有 main 函数的源文件，会得到链接器错误，大致像这样：

```text
/usr/bin/ld: . . ./x86_64-linux-gnu/Scrt1.o: in function `_start':
(.text+0x24): undefined reference to `main'
collect2: error: ld returned 1 exit status
```

这个错误的意思是，链接器试图把你的代码与 crt0（调用 main 的包装代码）链接在一起，但失败了。

gcc 命令接受一个 -c 命令行标志，告诉它不要调用链接器；有这个标志时，它会生成目标文件而不是可执行文件。为了配合测试套件，你的编译器驱动也应当识别 -c 标志。收到该标志时，编译器驱动应当先照常把源程序转换为汇编，然后运行以下命令把汇编程序转换为目标文件：

```bash
gcc -c ASSEMBLY_FILE -o OUTPUT_FILE
```

输出文件名应当是原文件名加上 .o 后缀。换句话说，./YOUR_COMPILER -c /path/to/program.c 应当在 /path/to/program.o 生成一个目标文件。

**注意**

如果你想编译并分发一个真正的库，仅生成目标文件是不够的；你要创建共享库（shared library，Linux 上是 .so 文件，macOS 上是 .dylib 文件）。愿意的话，你可以给编译器驱动添加另一个选项来生成共享库；你的驱动可以用适当的标志调用 GCC 或 Clang，把汇编程序转换成共享库而不是目标文件。但你的编译器生成共享库的能力有一个重大限制，尤其是在 Linux 上；我们将在第 10 章详细讨论。

至此，你可能还想扩展编译器驱动以接受多个输入源文件。测试套件不要求这个特性，但如果你想编译多文件程序就会需要它。要处理多个源文件，编译器驱动应当把每个源文件分别转换为汇编，再用 gcc 命令把它们汇编并链接到一起。

## 解析器

为了支持函数调用、声明和定义，我们需要在几处扩展 AST。先从函数调用开始，它是一种表达式：

```text
exp = Constant(int)
    | Var(identifier)
    | Unary(unary_operator, exp)
    | Binary(binary_operator, exp, exp)
    | Assignment(exp, exp)
    | Conditional(exp condition, exp, exp)
    | FunctionCall(identifier, exp* args)
```

函数调用的 AST 节点包含函数名和一个实参列表。每个实参都是一个表达式。

接下来，我们重构 declaration 节点，使它既能表示函数声明也能表示变量声明：

```text
declaration = FunDecl(function_declaration) | VarDecl(variable_declaration)
variable_declaration = (identifier name, exp? init)
```

我们把 function_definition 节点改名为 function_declaration。（稍后我们会依次介绍这个节点的其他改动。）variable_declaration 节点包含的信息与前几章的 declaration 相同：变量名和可选的初始化器。但它看起来和我们至今见过的其他 AST 节点有点不一样：它没有像 FunDecl 或 VarDecl 那样的具名构造器。当 ASDL 中的一个节点有多个构造器时——比如 declaration 节点和大多数其他 AST 节点——每个构造器都需要一个不同的名字，以便区分。但由于 variable_declaration 节点只有一个构造器，我们不必给这个构造器命名。用 ASDL 的行话说，恰好只有一个无名构造器的节点定义是积类型（product type）。我们到目前为止使用的其他节点都是和类型（sum type），因为它们都有具名构造器。积类型只是一种语法上的便利，让我们免于使用笨拙、冗余的构造器名。

现在来更新 function_declaration。这是现有的 function_definition 节点：

```text
function_definition = Function(identifier name, block body)
```

这里需要做几处修改。首先，如前所述，我们要把它改名为更贴切的 function_declaration。我们还要加入函数形参，并让函数体可选，这样这个节点就能同时表示函数声明和函数定义。最后，为了与 variable_declaration 保持一致，我们去掉 Function 构造器名，把它也变成积类型。修改后用于表示函数声明与定义的 AST 节点是：

```text
function_declaration = (identifier name, identifier* params, block? body)
```

最后，我们需要修改程序（program）的顶层定义。现在，一个程序不再只是单个 main 函数，而是一列函数定义和声明：

```text
program = Program(function_declaration*)
```

清单 9-15 给出了完整更新后的 AST。

```text
program = Program(function_declaration*)
declaration = FunDecl(function_declaration) | VarDecl(variable_declaration)
variable_declaration = (identifier name, exp? init)
function_declaration = (identifier name, identifier* params, block? body)
block_item = S(statement) | D(declaration)
block = Block(block_item*)
for_init = InitDecl(variable_declaration) | InitExp(exp?)
statement = Return(exp)
          | Expression(exp)
          | If(exp condition, statement then, statement? else)
          | Compound(block)
          | Break
          | Continue
          | While(exp condition, statement body)
          | DoWhile(statement body, exp condition)
          | For(for_init init, exp? condition, exp? post, statement body)
          | Null
```

*清单 9-16：带函数调用、声明与定义的文法*

清单 9-16 中的 <param-list> 和 <argument-list> 符号在 AST 中没有对应的节点。我把它们分别从函数声明和函数调用的产生式规则中提取出来，是为了让那些规则更易读。<param-list> 在函数没有形参时只包含 void 关键字；否则它包含一个以逗号分隔的形参列表，每个形参带类型和名字。<argument-list> 由以逗号分隔的一列表达式组成。注意，<param-list> 在函数声明中是必需的，而 <argument-list> 在函数调用中是可选的。解析以逗号分隔的实参或形参列表与解析块项列表类似：只需逐个消费列表元素之间的 , 词法单元，看到 ) 词法单元时停止。

## 语义分析

在变量解析遍中，我们给每个局部变量起一个新的、唯一的名字。但具有外部链接性的实体不应被重命名。两条都声明了名为 var 的局部变量的声明引用的是不同的内存地址，所以我们给它们分配不同的名字。而两条都声明了名为 fun 的函数的声明引用的是同一段代码，所以这些声明在整个编译过程中应当保持同一个名字。此外，具有外部链接性的对象必须保留源代码中的原始名字，因为链接器在符号解析期间要依赖这个名字。除非每个目标文件在编译时都保留了 fun 这个名字，否则链接器无法把调用 fun 的目标文件与定义 fun 的目标文件链接起来。

因此，我们需要更新变量解析遍：重命名无链接性的标识符，而保持具有外部链接性的标识符不变。（由于这一遍此后既要处理函数也要处理变量，我将把它改称为标识符解析（identifier resolution），不再叫变量解析。）我们会照旧检查所有常见的错误情形，比如重复声明和未声明的标识符；我们还要验证不存在嵌套的函数定义。捕获重复声明的逻辑会稍有变化，因为同一作用域内多次声明一个具有外部链接性的名字是合法的。例如，清单 9-17 是完全合法的。

```c
int main(void) {
    int foo(void);
    int foo(void);
    return foo();
}
```

*清单 9-17：同一作用域内的多条函数声明*

因为 foo 的两条声明都具有外部链接性，它们引用同一个函数，所以并不冲突。标识符的重复声明只有在它们引用不同实体时才冲突；因为当你在同一作用域中稍后使用该标识符时，无从判断它应指向哪个实体。

还有几个别的错误情形需要检查。我们必须验证函数的每一条声明的形参个数都相同，且没有函数被定义多次。此外，我们必须验证变量不会被当作函数使用、函数调用时的实参数量正确。这些错误与我们已有检查的错误情形不太相似，因为它们其实与哪些标识符在作用域内无关。它们是类型错误（type error），即对象的不同声明类型冲突，或对象被以其类型不支持的方式使用时发生的错误。

我们将定义一个独立的类型检查遍来捕获这些错误。这一遍还会构建一张符号表（symbol table），存储程序中每个标识符的类型，以及我们需要追踪的标识符的其他一些属性。在后面的编译器阶段中我们会回头查阅这张符号表。（它不同于目标文件中供链接器在符号解析时使用的符号表。我们在类型检查器中构建的符号表是编译器内部的。）

到本章末尾，语义分析阶段将由三遍组成：标识符解析、类型检查和循环标记（loop labeling）。循环标记遍相对于另外两遍可以安排在任意位置。

### 扩展标识符解析

我们来更新标识符解析遍，以处理函数调用、函数声明和函数定义。标识符映射（identifier map）中的每个条目需要多追踪一项新信息：它是否具有外部链接性。构建标识符映射时，不要想当然地认为函数总是具有外部链接性而变量总是没有。这个假设眼下成立，但下一章就不成立了。

我们还会更新伪代码中的几个名字：把 variable_map 改为 identifier_map，并把标识符映射中的 from_current_block 字段改名为 from_current_scope，因为函数声明可以出现在块之外的顶层。

#### 函数调用

函数名和变量名一样，必须先出现在标识符映射中才能使用。清单 9-18 展示了 resolve_exp 应当如何处理函数调用。

```text
resolve_exp(e, identifier_map):
    match e with
    | --snip--
    | FunctionCall(fun_name, args) ->
        if fun_name is in identifier_map:
            new_fun_name = identifier_map.get(fun_name).new_name
            new_args = []
            for arg in args:
                new_args.append(resolve_exp(arg, identifier_map))
            return FunctionCall(new_fun_name, new_args)
        else:
            fail("Undeclared function!")
```

*清单 9-18：解析函数调用*

首先，我们在标识符映射中查找函数名，确认它在程序的这个位置处于作用域内。然后，我们用标识符映射中的新名字替换这个名字。在合法程序中，这个新名字与原名字相同，因为我们不会重命名具有外部链接性的标识符。但我们还必须考虑非法程序。也许 fun_name 其实是某个局部变量的名字而不是函数；这种情况下，试图像调用函数一样调用它是类型错误。在这里解析 fun_name 使我们能在类型检查期间捕获这个类型错误。至于这个函数调用的实参数量是否正确，我们也留到类型检查遍去确认。

替换函数名之后，我们对每个函数实参递归调用 resolve_exp，就像对一元、二元和三元表达式中的子表达式递归解析一样。

#### 函数声明

接下来考虑函数声明。无论函数声明出现在块中还是顶层，我们几乎可以用完全相同的方式处理它。首先，把函数名加入当前作用域。然后，处理它的形参，把它们加入一个新的内层作用域。最后，如果有函数体，也一并处理。清单 9-19 展示了如何解析函数声明。

```text
resolve_function_declaration(decl, identifier_map):
    if decl.name is in identifier_map:
        prev_entry = identifier_map.get(decl.name)
      ❶ if prev_entry.from_current_scope and (not prev_entry.has_linkage):
            fail("Duplicate declaration")

  ❷ identifier_map.add(decl.name, MapEntry(
        new_name=decl.name, from_current_scope=True, has_linkage=True
    ))

  ❸ inner_map = copy_identifier_map(identifier_map)
    new_params = []
    for param in decl.params:
        new_params.append(resolve_param(param, inner_map))

    new_body = null
    if decl.body is not null:
        new_body = resolve_block(decl.body, inner_map)
    return (decl.name, new_params, new_body)
```

*清单 9-19：解析函数声明*

在更新标识符映射之前，我们必须确认没有非法地重复声明某个标识符 ❶。如果该标识符尚不在作用域内，就没有冲突。如果它是在外层作用域中声明的，也没问题；新声明会遮蔽已有的声明。到这里为止，与我们处理变量声明的方式完全相同。但是，我们还要考虑链接性。具有外部链接性的标识符的多条声明可以出现在同一作用域中。我们已经知道这条新声明具有外部链接性（因为它是函数声明），所以只要旧声明也具有外部链接性，它就是合法的。但如果旧声明没有链接性（因为它声明的是局部变量），我们就要抛出错误。标识符映射中的 has_linkage 属性告诉我们一个标识符是否具有外部链接性。（下一章它会追踪标识符是否具有任何链接性，包括内部链接性和外部链接性。）

如果没有冲突的声明，我们把这个名字加入 identifier_map ❷。我们不为函数生成新名字；这个映射条目的 new_name 属性就应当是原始名字。因为这条声明具有外部链接性，has_linkage 属性应为 True。

接下来解析形参名。声明中的函数形参列表开启一个新作用域，所以我们复制一份标识符映射来跟踪它们 ❸。形参名可以遮蔽外层作用域中的名字，但同一函数声明中的两个形参不能同名。所以，这样是合法的：

```c
int a;
int foo(int a);
```

但这样不合法：

```c
int foo(int a, int a);
```

我略去了 resolve_param 的伪代码，它应当与你解析变量声明的现有代码相同：确认形参名尚未在当前作用域中声明过，为它生成唯一的名字，加入标识符映射，然后返回新名字。你可以写一个辅助函数同时用于解析形参和局部变量声明，因为二者的逻辑是一样的。

我们解析函数形参有两个原因。第一，需要验证没有重复的形参名。第二，需要确保处理函数体时形参在作用域内。处理没有函数体的函数声明时，第二点无关紧要；我们本可以只检查重复形参而不重命名它们、不更新内层作用域。不过，我认为无论有无函数体都用统一的方式处理函数声明最为简单。

清单 9-19 的最后一步是处理函数体（如果有的话）。我们照常用 resolve_block 处理；只需确保传入 inner_map，这样函数形参才在作用域内。函数名本身也在作用域内，因为我们在复制之前已把它加入外层映射；因此我们能处理递归调用自身的函数。

函数形参和函数体位于同一作用域，所以处理函数体时应当传入 inner_map 本身，而不是它的副本。例如，这样是非法的：

```c
int foo(int a) {
    int a = 3;
    return a;
}
```

变量声明 int a = 3; 是非法的重复声明，因为它与形参 a 处于同一作用域。

至此，我们可以返回更新后的 function_declaration 节点。函数名本身没有变化，但新节点中的形参列表以及函数体中声明的所有变量都已被重命名。

#### 局部声明

局部变量声明的处理方式与前几章完全相同；只需确保在标识符映射中记录这些声明没有链接性。处理局部函数声明时，先检查它是否带函数体。如果有，抛出错误；否则调用我们在清单 9-19 中定义的 resolve_function_declaration。

#### 顶层处理

最后，把这一切整合起来处理函数声明列表。按顺序逐个处理，边处理边构建标识符映射。你加入的每个函数名在处理后续函数声明时仍保持作用域内。而函数的形参名和局部变量在后续函数中不可见，因为它们被加入了内层作用域。

### 编写类型检查器

剩下的验证工作全都是类型检查。每个标识符，无论是函数还是变量，都有一个类型。变量可以有 int、long、double 等类型，不过在项目的这个阶段每个变量的类型都是 int。函数的类型取决于它的返回类型和形参的类型。例如，一个函数的类型可以是“接受三个 int 形参并返回 int 的函数”。目前我们只支持接受 int 形参、返回 int 结果的函数，所以只有形参个数会变化。

类型检查遍验证一个标识符的所有声明和使用都具有兼容的类型。例如，如果你声明 x 是变量，就不能把它当函数调用：

```c
int x = 3;
return x();
```

不能用不同的类型在多处声明同一个函数：

```c
int foo(int a, int b);
int foo(int a);
```

不能用错误数量的实参调用函数：

```c
int foo(int a, int b);

int main(void) {
    return foo(1);
}
```

同一个函数也不能定义多次：

```c
int foo(void) {
    return 1;
}

int foo(void) {
    return 2;
}
```

最后这种错误严格说不是类型错误，但在这里检查最容易。

为了对程序做类型检查，我们要把每个标识符的类型记录在符号表中。我们还会记录遇到的每个函数是已定义还是仅声明；也就是它有没有函数体。符号表将是我们获取程序中每个标识符信息的中心来源。本章中我们主要用符号表来捕获类型错误。在后续章节中，我们会往这张表中添加更多信息，并找到它更多的用途。

要构建符号表，我们需要一种在编译器中表示类型的方法，就像我们需要一种表示 AST 的方法一样。目前，你的类型定义应当长这样：

```text
type = Int | FunType(int param_count)
```

每个变量的类型都是 int，而关于函数类型我们唯一需要的信息就是它有几个形参。我们会在第 II 部分添加更多类型。

我们将按惯常方式遍历程序来构建符号表。遇到函数或变量声明时，我们把它的类型记录到符号表中。类型检查器不像标识符解析遍那样变换 AST，所以各个类型检查方法不会返回变换后的 AST 节点；它们只是添加符号表条目并报告错误。（在第 II 部分中，类型检查器会变换 AST。）

清单 9-20 展示了如何对变量声明做类型检查。

```text
typecheck_variable_declaration(decl, symbols):
    symbols.add(decl.name, Int)
    if decl.init is not null:
        typecheck_exp(decl.init, symbols)
```

*清单 9-20：对变量声明做类型检查*

此时每个变量都有唯一的名字，所以我们知道这条声明不会与符号表中已有条目冲突。我们把它加入符号表，然后（如果它有初始化器）对初始化器做类型检查。函数要更棘手一些。因为一个函数可以声明多次，它可能已经在符号表中有条目。所以，把函数加入符号表之前，你需要对照已有条目对它进行验证。清单 9-21 给出了对函数声明做类型检查的伪代码。

```text
typecheck_function_declaration(decl, symbols):
    fun_type = FunType(length(decl.params))
    has_body = decl.body is not null
    already_defined = False

    if decl.name is in symbols:
        old_decl = symbols.get(decl.name)
      ❶ if old_decl.type != fun_type:
            fail("Incompatible function declarations")
        already_defined = old_decl.defined
      ❷ if already_defined and has_body:
            fail("Function is defined more than once")

  ❸ symbols.add(decl.name, fun_type, defined=(already_defined or has_body))

  ❹ if has_body:
        for param in decl.params:
            symbols.add(param, Int)
        typecheck_block(decl.body)
```

*清单 9-21：对函数声明做类型检查*

我们首先检查该函数没有被以不同类型声明过 ❶。然后确认我们没有重新定义一个已经定义过的函数 ❷。函数符号表条目中的 defined 属性记录我们是否已对该函数的一个定义做过类型检查。（变量的符号表条目不需要这个属性。）

验证之后，我们把函数加入符号表 ❸。如果已有条目，这会将其覆盖。这没有问题，因为类型不会变。我们只需在设置 defined 属性时把旧条目考虑进来。如果该函数已经定义过，或者当前这条声明带函数体，我们就把 defined 设为 True。最后，如果当前声明带函数体 ❹，我们把函数的每个形参加入符号表，然后对函数体做类型检查。

请记住，符号表包含我们迄今做过的所有类型检查的每一条声明，哪怕它已不在作用域内。考虑这个例子：

```c
int main(void) {
  ❶ int foo(int a);
    return foo(1);
}

❷ int foo(int a, int b);
```

嵌套的函数声明 ❶ 在该函数再次被声明 ❷ 时已不在作用域内。尽管如此，当我们对声明 ❷ 做类型检查时，声明 ❶ 仍在符号表中。所以我们会发现这两条声明冲突并抛出错误。

我们不仅要验证声明，还要验证标识符的使用。标识符可以用作 Var AST 节点中的变量，也可以用作 FunctionCall AST 节点中的函数名。这两种情况下，你都应该验证标识符具有预期的类型。清单 9-22 演示了如何对这两类表达式做类型检查。

```text
typecheck_exp(e, symbols):
    match e with
    | FunctionCall(f, args) ->
        f_type = symbols.get(f).type
      ❶ if f_type == Int:
            fail("Variable used as function name")
      ❷ if f_type.param_count != length(args):
            fail("Function called with the wrong number of arguments")
      ❸ for arg in args:
            typecheck_exp(arg, symbols)
    | Var(v) ->
      ❹ if symbols.get(v).type != Int:
            fail("Function name used as variable")
    | --snip--
```

## TACKY 生成

既然确信输入程序是合法的，我们把它转换为 TACKY。我们需要对 TACKY IR 做几处修改。第一，需要一条新的 TACKY 指令来表示函数调用。第二，需要在 TACKY 函数定义中加入形参。最后，我们要把整个 TACKY 程序定义为一列函数而不是单个函数。清单 9-23 给出了更新后的 TACKY IR 定义。

```text
program = Program(function_definition*)
function_definition = Function(identifier, identifier* params, instruction* body)
instruction = Return(val)
            | Unary(unary_operator, val src, val dst)
            | Binary(binary_operator, val src1, val src2, val dst)
            | Copy(val src, val dst)
            | Jump(identifier target)
            | JumpIfZero(val condition, identifier target)
            | JumpIfNotZero(val condition, identifier target)
            | Label(identifier)
            | FunCall(identifier fun_name, val* args, val dst)
val = Constant(int) | Var(identifier)
unary_operator = Complement | Negate | Not
binary_operator = Add | Subtract | Multiply | Divide | Remainder | Equal | NotEqual
                | LessThan | LessOrEqual | GreaterThan | GreaterOrEqual
```

*清单 9-23：向 TACKY 添加函数调用*

这些修改与清单 9-15 中对 AST 的修改密切对应。不过 TACKY IR 需要的改动比 AST 少，因为我们不在 TACKY 中表示函数声明。与不带初始化器的变量声明一样，不带函数体的函数声明在 IR 生成期间被丢弃。只有函数定义会被转换为 TACKY。

新的 FunCall 指令需要一个函数名、一个实参列表和一个存放返回值的目标。与其他 TACKY 指令的操作数一样，函数实参必须是常量或变量，不能是表达式。

要把整个程序转换为 TACKY，就逐个处理顶层函数声明，把每个函数定义转换为 TACKY 的 function_definition，并丢弃所有不带函数体的声明。要把函数调用转换为 TACKY，就生成求值每个实参的指令，并构造由得到的 TACKY 值组成的列表。函数调用 fun(e1, e2, …) 的 TACKY 将类似清单 9-24。

```text
<instructions for e1>
v1 = <result of e1>
<instructions for e2>
v2 = <result of e2>
--snip--
result = FunCall(fun, [v1, v2, . . .])
```

*清单 9-24：把函数调用转换为 TACKY*

这与我们处理其他含嵌套子表达式的表达式（如一元和二元运算）的方法相同。现在只是把它推广到任意数量的嵌套表达式，因为一个函数可以有任意数量的实参。

记得在每个函数体末尾添加一条 Return(0) 指令，确保即使某些执行路径缺少 return 语句，函数也会返回调用者。接下来，我们要攻克本章最棘手的部分：在汇编中实现函数调用。

## 汇编生成

本章我们要对 TACKY 到汇编的转换遍做两处大改动：把函数形参放到栈上以便在函数体中访问，以及把新的 FunCall 指令转换为汇编。我们还会对伪寄存器替换遍和指令修补遍做几处小改动。但在动手之前，我们需要理解将要使用的调用约定。

### 理解调用约定

调用约定（calling convention）是调用者（caller）与被调用者（callee）之间关于函数如何被调用的契约。它回答这样的问题：

实参如何传给被调用者？放在寄存器里还是栈上？

函数的返回值如何传回调用者？

函数结束时，由被调用者还是调用者负责把实参从栈上移除？

被调用者可以覆写哪些寄存器，必须保存哪些寄存器？

共享的调用约定让调用者和被调用者能够协同工作。调用者知道往哪儿放实参，被调用者知道去哪儿找它们。被调用者知道把返回值存在哪里，调用者知道被调用者返回后去哪里取。被调用者和调用者都知道自己需要保存哪些寄存器，以确保被调用者不会破坏调用者在函数调用之后还要使用的任何值。这保证了双方都能访问到自己需要的信息。

调用约定是一个更大规范的一部分，该规范称为应用二进制接口（application binary interface，ABI），它使由不同编译器构建的目标文件能够链接在一起。只要这些目标文件共享同一 ABI，它们就能互操作。除调用约定外，ABI 还规定了不同的 C 类型在内存中如何表示，这在第 II 部分中很重要。组成 ABI 的其余大多数细节——比如可执行文件格式——由汇编器、链接器和操作系统处理，所以我们不必操心。

如果你的编译器遵循所在平台的调用约定，你就能编译依赖标准库以及任何你想用的其他库的程序。你将能编译发起系统调用、执行 I/O 操作的程序。你仍然无法编译标准库本身——它依赖各种我们尚未实现的语言特性——但由于它已经编译好并安装在你的系统上，你可以链接它。

每个类 Unix 系统都使用 System V ABI 定义的标准调用约定。（这个 ABI 得名于 Unix System V，Unix 的一个早期商业版本。）由于我们的目标是 macOS 和 Linux，我们将使用 System V 调用约定。System V ABI 针对不同处理器架构有不同版本；我们将使用面向 x64 处理器的版本。Windows 有自己的 ABI，我们不必管它。如果你是在 Windows Subsystem for Linux 上做这个项目，你仍然可以使用 System V 调用约定。接下来我们看看这个调用约定如何工作。

### 用 System V ABI 调用函数

上一节我列举了调用约定必须回答的几个问题。我们来看看 System V 调用约定如何回答这些问题，以及它提出的其他要求：

**实参传递**

函数的前六个整数实参按顺序通过 EDI、ESI、EDX、ECX、R8D 和 R9D 寄存器传递（64 位整数改用这些寄存器的 64 位名字传递：RDI、RSI、RDX、RCX、R8 和 R9）。其余实参按逆序压入栈。例如，要实现函数调用 foo(a, b, c, d, e, f, g, h)，你先把变量 a 复制到 EDI，再把 b 复制到 ESI，依此类推直到 f。然后，把最后一个实参 h 压入栈。最后，把 g 压入栈。

**返回值**

我们已经知道，函数的返回值通过 EAX 传递（返回 64 位整数时用 RAX）。执行 ret 指令时，返回值必须位于 EAX 中。

**实参清理**

被调用者返回后，由调用者把所有实参从栈上移除。被调用者不清理实参。

**调用者保存与被调用者保存寄存器**

如果一个寄存器是调用者保存（caller-saved）的，被调用者就允许覆写它。因此，调用者如果之后还需要该寄存器的值，就必须在发出 call 指令之前把它保存到栈上，然后等函数返回后再从栈中弹出该值。（如果寄存器中的值在函数调用之后不会再使用，调用者就不必保存。）如果一个寄存器是被调用者保存（callee-saved）的，函数返回时它的内容必须与函数开始时相同。如果被调用者需要使用该寄存器，通常在函数序言（prologue）期间把寄存器的值压入栈，然后在函数尾声（epilogue）期间再弹回。寄存器 RAX、R10、R11 以及所有实参传递寄存器都是调用者保存的；其余寄存器都是被调用者保存的。

**栈对齐**

System V ABI 要求栈 16 字节对齐（stack alignment）。换句话说，当我们发出 call 指令时，栈指针 RSP 中存储的地址必须能被 16 整除。ABI 提出这一要求是因为某些指令要求 16 字节对齐的操作数。如果栈本身就 16 字节对齐，维持这些操作数的正确对齐就容易多了。

完整的 System V x64 ABI 可以在 https://gitlab.com/x86-psABIs/x86-64-ABI 找到。不过，看一个例子可能比读规范更有用。考虑清单 9-25。

```c
int fun(int a, int b, int c, int d, int e, int f, int g, int h) {
    return a + h;
}

int caller(int arg) {
    return arg + fun(1, 2, 3, 4, 5, 6, 7, 8);
}
```

*清单 9-25：包含函数调用的 C 程序*

清单 9-26 给出了 fun 的汇编代码。它比你的编译器生成的版本更优化，为的是把 System V 调用约定展示得更清楚。

```asm
    .globl fun
fun:
    pushq   %rbp
    movq    %rsp, %rbp
    # 把第一个实参复制到 EAX
    movl    %edi, %eax
    # 把最后一个实参加到 EAX
    addl    24(%rbp), %eax
    # 尾声
    movq    %rbp, %rsp
    popq    %rbp
    ret
```

*清单 9-26：清单 9-25 中 fun 的汇编代码*

清单 9-27 给出了从 caller 调用 fun 的汇编代码。

```asm
    # 在函数调用前保存 RDI
    pushq   %rdi
    # 调整栈对齐
    subq    $8, %rsp
    # 前六个实参经寄存器传递
    movl    $1, %edi
    movl    $2, %esi
    movl    $3, %edx
    movl    $4, %ecx

    movl    $6, %r9d

```

*清单 9-27：清单 9-25 中调用 fun 的汇编代码*

我们把这个函数调用走一遍，看看程序状态在每一步如何变化。在下面这些图中，左列是栈和通用寄存器的内容，右列是 RIP 的内容，RIP 始终存放下一条要执行的指令的地址。（注意，这些图中的指令地址并不真实。这些地址暗示每条指令长 1 字节，但指令长度是变化的，而且通常不止一个字节！）

图 9-1 展示了调用 fun 之前程序的初始状态。

*图 9-1：清单 9-25 中程序的初始状态*

在图 9-1 中，RSP 和 RBP 指向同一地址。caller 中没有局部变量，所以我们不需要分配任何栈空间。这张图中的寄存器都持有 64 位值，但我们通常会使用 32 位寄存器名，比如 EDI、ESI 和 EDX，因为我们所有的函数实参和返回值都是 32 位整数。不过，在保存到栈和从栈恢复时，我们会使用 64 位寄存器名，因为 push 和 pop 要求 64 位操作数。

caller 的唯一实参 arg 通过 RDI 传递。假设 arg 的值是 15。要调用 fun，我们需要按照 System V 调用约定传递全部八个实参。前六个实参通过寄存器传递，最后两个通过栈传递。但把第一个实参复制到 RDI 会破坏 arg，而我们在函数调用之后还会用到它。所以，在传递任何实参之前，第一步就是把 arg 保存到栈上：

```asm
    # 在函数调用前保存 RDI
    pushq   %rdi
```

接下来，我们调整 RSP，使发出 call 指令时它是 16 字节对齐的。我们需要根据压入栈的实参个数和保存的寄存器个数倒推。在函数调用开始之前，我们可以假定栈指针是 16 的倍数。（为了保证这一点，我们会在函数序言中按 16 字节的倍数分配栈空间。）然后我们把一些寄存器和函数实参压入栈；每一项都是 8 字节。如果压入栈的寄存器和实参总数是偶数，那么全部压入后栈仍是 16 字节对齐的。如果栈上的寄存器和实参个数是奇数，我们就需要从栈指针再减去 8 字节来获得正确的对齐。

在这个例子中，我们压入一个寄存器 RDI，还要把两个实参 g 和 h 压入栈。在发出 call 指令之前，我们总共要向栈压入三个值，合计 24 字节。因此，保存 RDI 之后还需要再调整 8 字节的栈：

```asm
    # 调整栈对齐
    subq    $8, %rsp
```

现在可以着手设置 fun 的实参了。从前六个实参开始，它们通过寄存器传递。由于实参都是 32 位整数，这里我们用 32 位寄存器名：

```asm
    # 前六个实参经寄存器传递
    movl    $1, %edi
    movl    $2, %esi
    movl    $3, %edx
    movl    $4, %ecx
    movl    $5, %r8d
    movl    $6, %r9d
```

接下来，把剩下的两个实参按逆序压入栈：

```asm
    # 最后两个实参在栈上传递
    pushq   $8
    pushq   $7
```

这两条指令各自把一个 64 位常量压入栈，因为 push 指令只能压入 64 位值。图 9-2 展示了保存 RDI、调整栈、设置好函数实参之后程序的状态。

*图 9-2：call 指令执行前夕的程序状态*

可以看出栈确实是 16 字节对齐的，因为栈指针能被 16（十六进制表示为 0x10）整除。实参就位后，我们用 call 汇编指令调用 fun：

```asm
    # 把控制权转移给 fun
    call    fun
```

call 指令做两件事。第一，它把紧随其后的那条指令的地址——返回地址（return address）——压入栈。然后，它把标号 fun 所标记指令的地址复制到 RIP，把控制权转移过去。图 9-3 展示了 call 指令刚执行完后程序的状态。

*图 9-3：call 指令执行之后的程序状态*

我们早已熟悉的函数序言为 fun 建立栈帧，使程序进入图 9-4 所示的状态。

*图 9-4：fun 的函数序言执行后的程序状态*

在这张图中，白色背景的栈区域是 fun 的栈帧，浅灰色背景的栈区域是 caller 的栈帧。在 fun 中，我们需要计算 a + h。这要求我们访问一个经寄存器传递的形参（a）和一个经栈传递的形参（h）。fun 中的下一条指令把 a 的值复制到 EAX：

```asm
    # 把第一个实参复制到 EAX
    movl    %edi, %eax
```

接下来，我们要把经栈传递的 h 加到 EAX 中的值上。栈上的实参和局部变量一样，可以相对 RBP 寻址。我们知道 RBP 指向的栈槽保存着调用者栈帧的基地址。紧挨其下的栈槽 8(%rbp) 保存着返回地址（在 caller 中）。再往下一个值位于 16(%rbp)，是第一个栈上实参 g。（记住，栈上实参是按逆序压入的。也就是说，第一个栈上实参 g 最后压入，现在离当前栈帧最近。）下一个实参 h 在它下方 8 字节处，即 24(%rbp)，我们可以照此访问它：

```asm
    # 把最后一个实参加到 EAX
    addl    24(%rbp), %eax
```

我们压入栈的是一个 64 位常量 8，但 addl 需要 32 位操作数。因此它会把从 24(%rbp) 开始的 4 个字节解释为 32 位整数，实际上丢弃了高 32 位。由于这些位只是前导零，得到的值仍然是 8。也就是说，尽管压入栈的每个实参必须是 64 位，我们在被调用者中仍然可以把它们解释为 32 位整数。

**变参函数**

先压入最后一个实参，让我们更容易支持变参函数（variadic function），即实参个数可变的函数。最明显的例子是 printf，其实参个数取决于你传入的格式字符串。因为我们从右向左把实参压入栈，第七个实参（第一个栈上实参）永远位于 16(%rbp)，无论我们传递多少个实参。这意味着变参函数无需事先知道实参总数就能轻松遍历其实参：只要增大相对 RBP 的偏移就能取到下一个实参。如果我们按顺序压入实参，传递的实参越多，RBP 到第一个栈上实参的偏移就越大。变参函数就得先弄清自己收到了多少个实参（比如通过检查 printf 第一个实参中的格式字符串），再据此重新计算每个实参的地址。

此时，EAX 中已经是正确的返回值，可以进入函数尾声了：

```asm
    # 尾声
    movq    %rbp, %rsp
    popq    %rbp
```

注意，在这个特定程序中 movq 指令是多余的。通常这条指令会释放当前栈帧，使调用者的旧 RBP 值回到栈顶。但我们没有为 fun 分配任何栈空间，所以 RSP 和 RBP 本来就持有相同的值。

尾声把栈恢复成序言之前的样子。图 9-5 展示了此时的情形。

*图 9-5：返回调用者之前的程序状态*

我们用 ret 指令返回调用者，它把返回地址弹出栈并把控制权转移到该地址。图 9-6 展示了返回调用者之后程序的状态。

*图 9-6：返回调用者之后的程序状态*

此时，栈正处于 call 指令之前的那一刻完全相同的状态。最后一步是清理填充字节和栈上实参，并把 arg 恢复到 RDI：

```asm
    # 恢复栈和 RDI
    addq    $24, %rsp
    popq    %rdi
```

现在栈恢复到了函数调用之前的样子，RDI 也恢复为原值。RAX 寄存器中是返回值，我们可以在函数体后续部分使用它。由于其他寄存器在调用 fun 之前并未初始化，我们现在不需要清理它们。图 9-7 展示了函数调用收尾完成后的程序状态。

### 把函数调用与定义转换为汇编

我们现在要扩展汇编 AST，这是自第 4 章以来的第一次。清单 9-28 定义了新的 AST，改动以粗体标出。

```text

            | Cmp(operand, operand)
            | Idiv(operand)
            | Cdq
            | Jmp(identifier)
            | JmpCC(cond_code, identifier)
            | SetCC(cond_code, operand)
            | Label(identifier)
            | AllocateStack(int)
            | DeallocateStack(int)
            | Push(operand)
            | Call(identifier)
            | Ret

unary_operator = Neg | Not
binary_operator = Add | Sub | Mult
operand = Imm(int) | Reg(reg) | Pseudo(identifier) | Stack(int)
cond_code = E | NE | G | GE | L | LE

```

*清单 9-28：支持函数调用的汇编 AST*

首先，我们修改 Program 的顶层定义以支持多个函数定义。我们还引入三条新指令。要在函数调用前调整栈对齐，可以用已有的 AllocateStack 指令，它最终会发射为 subq 指令。要在函数调用后移除实参和填充字节，我们增加对应的 DeallocateStack 指令，它会发射为 addq。我们还需要 Push 指令来把实参压入栈。我们已经在函数序言中用过 push，但用法极其有限，以至于可以在代码发射期间机械地补上。既然现在要更广泛地使用它，就需要把它加进汇编 AST。当然，还需要 Call 指令来真正调用函数。最后，我们需要几个用于实参传递的新寄存器：CX、DI、SI、R8 和 R9。实参也会通过 DX 寄存器传递，它已经在我们的 AST 里了。与前几章一样，AST 不区分每个寄存器的不同别名：例如 DI 会根据我们要用整个寄存器、低 4 字节还是最低 1 字节，分别发射为 %rdi、%edi 或 %dil。

汇编 AST 就绪后，我们就可以更新 TACKY 到汇编的转换。记得我们对 TACKY IR 做过三处修改：把程序定义为函数列表而非单个函数，给每个函数定义加了形参，并新增了 FunCall 指令。应对第一处修改很简单：把 TACKY 中的函数列表转换为汇编中的函数列表。接下来，我们要让函数形参在汇编中可以访问。然后，我们再看如何把新的 FunCall 指令转换为汇编。

#### 在汇编中访问函数形参

函数开始时，每个形参都存放在调用约定指定的寄存器或栈位置。我们本可以在汇编代码中直接引用这些位置来访问函数形参。清单 9-26 中 fun 的汇编代码就是这么做的；需要把形参 a 和 h 相加时，我们直接引用了它们由调用约定定义的位置 %edi 和 24(%rbp)。这行得通，但有几个缺点。它要求我们在函数调用前把实参传递寄存器压入栈、调用后再弹出，就像清单 9-27 中调用 fun 前后必须压入和弹出 RDI 那样。它还容易与其他使用实参传递寄存器的指令发生冲突。例如，idiv 会写 EDX 寄存器，可能破坏存放在那里的函数形参。最后，它使伪寄存器分配阶段更复杂，因为形参必须与局部变量区别对待。

我们换一种做法来绕开这些问题：在每个函数体开头，把每个形参从调用约定定义的寄存器或内存地址复制到当前函数栈帧的一个槽位中。看一个简单的例子。清单 9-29 定义了一个带一个形参的函数。

```c
int simple(int param) {
    return param;
}
```

*清单 9-29：带单个形参的函数*

生成这个函数的汇编时，我们会在函数体开头加入一条额外的 Mov 指令：

```text
Mov(Reg(DI), Pseudo("param"))
```

这条指令把函数的第一个形参复制到伪寄存器 param 中。记住，TACKY 中 Var("param") 的每次使用都会被翻译为汇编中 Pseudo("param") 的使用。

整个函数生成的汇编将是这样的：

```text
Mov(Reg(DI), Pseudo("param"))
Mov(Pseudo("param"), Reg(AX))
Ret
```

（实际上，param 会在标识符解析期间被重命名，TACKY 生成时我们还会发射一条额外的 Return(0) 指令，但这两点细节对本例无关紧要。）

我们将照常把伪寄存器替换为栈位置。由于 param 是唯一的伪寄存器，我们把它分配到 Stack(-4)。最终我们发射清单 9-30 所示的汇编程序。

```asm
    .globl simple
simple:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $16, %rsp
    movl    %edi, -4(%rbp)
    movl    -4(%rbp), %eax
    movq    %rbp, %rsp
    popq    %rbp
    ret
```

*清单 9-30：清单 9-29 的汇编程序*

把形参复制到栈上让代码生成保持简单。我们不再需要在函数调用前保存调用者保存寄存器、调用后恢复它们，因为我们只以非常短暂的方式使用这些寄存器。经寄存器传递函数形参时，我们立即把它们保存到栈上，而不是长期留在那些寄存器里。除函数形参外，我们存放在调用者保存寄存器中的值只有返回值、idiv 指令的结果，以及指令重写阶段临时复制到 R10D 或 R11D 的值。与形参一样，这些值要么立刻被使用，要么立刻被复制到栈上。这样做的结果是，调用者保存寄存器中的值永远不需要跨函数调用存活；这就是我们不必保存或恢复它们的原因。（与此同时，被调用者也不需要保存和恢复大多数被调用者保存寄存器，因为我们根本不用它们。唯一的例外是 RBP 和 RSP，我们在函数序言和尾声中保存并恢复它们。）

同理，我们不必担心 idiv 指令破坏 EDX 中的形参。伪寄存器分配期间也不需要任何额外的逻辑来处理函数形参：可以像给局部变量分配一样把它们分配到栈位置。

另一方面，把形参复制到栈上是低效的。首先，我们生成了额外的 mov 指令。其次，我们迫使程序每次读写形参都要访问内存，而内存通常比寄存器慢。幸运的是，等到第 III 部分实现寄存器分配时，我们能消除这些多余的指令和内存访问中的大部分。

生成这些形参复制指令时，先把第一个形参从 Reg(DI) 移入伪寄存器，第二个从 Reg(SI) 移入，依此类推，直到第六个形参（如果函数的形参少于六个，则直到用完为止）。然后，把第七个形参从 Stack(16) 复制过来，第八个从 Stack(24) 复制，依此类推，直到处理完全部形参。如前所述，调用者栈帧的顶端 8(%rbp) 是返回地址，而第七个形参——第一个经栈传递的形参——永远就在它下方，即 16(%rbp)。往后，每多一个形参偏移就增加 8 字节，因为调用者把它们作为 8 字节的值压入栈（尽管被调用者把它们解释为 4 字节的值）。

#### 实现 FunCall

前面我们逐步走读了函数调用的汇编代码。现在看看如何生成这些汇编代码。清单 9-31 给出了把 FunCall TACKY 指令转换为汇编的伪代码。

```text
convert_function_call(FunCall(fun_name, args, dst)):
    arg_registers = [DI, SI, DX, CX, R8, R9]

    // 调整栈对齐
    register_args, stack_args = first 6 args, remaining args
    if length(stack_args) is odd:
        stack_padding = 8
    else:
        stack_padding = 0

    if stack_padding != 0:
        emit(AllocateStack(stack_padding))

    // 实参经寄存器传递
    reg_index = 0
    for tacky_arg in register_args:
        r = arg_registers[reg_index]
        assembly_arg = convert_val(tacky_arg)
        emit(Mov(assembly_arg, Reg(r)))
        reg_index += 1

    // 实参经栈传递
    for tacky_arg in reverse(stack_args):
        assembly_arg = convert_val(tacky_arg)
        if assembly_arg is a Reg or Imm operand:
          ❶ emit(Push(assembly_arg))
        else:
          ❷ emit(Mov(assembly_arg, Reg(AX)))
            emit(Push(Reg(AX)))

    // 发出 call 指令
    emit(Call(fun_name))

    // 调整栈指针
    bytes_to_remove = 8 * length(stack_args) + stack_padding
    if bytes_to_remove != 0:
        emit(DeallocateStack(bytes_to_remove))

    // 取回返回值
    assembly_dst = convert_val(dst)
    emit(Mov(Reg(AX), assembly_dst))
```

*清单 9-31：为函数调用发射汇编*

第一步是确保栈正确对齐。这必须在把实参压入栈之前完成；如果我们在实参与被调用者栈帧之间插入额外的填充，被调用者将找不到它们。在走读清单 9-27 的函数调用时我们看到，如果压入栈的实参和调用者保存寄存器总数是偶数，全部压入后栈仍是 16 字节对齐——无需填充。如果压入的是奇数个，就需要再从栈指针减去 8 字节以保持正确对齐。现在，多亏了上一节的形参复制技巧，我们只需要考虑压入栈的实参，不必考虑调用者保存寄存器。所以，我们只需数一数将要压入栈的实参个数，如果是奇数就发射一条 AllocateStack 指令。

接下来传递函数实参。处理每个实参时，我们用 convert_val 辅助函数把它从 TACKY 值转换为汇编操作数。（convert_val 的伪代码我略去了，因为你已经知道如何执行这个转换。）前六个实参被复制到相应的寄存器。当然，函数的实参可能少于六个；这种情况下，我们把每个实参都复制到寄存器。

如果函数的实参多于六个，多出的部分必须经栈传递。我们先压入最后一个实参，然后是倒数第二个，依此类推，直到第七个。记住，我们的实参是 4 字节整数，但每个实参需要向栈压入 8 字节（因为 ABI 要求如此，也因为 pushq 只接受 8 字节操作数）。不过，被调用者只会使用每个实参的低 4 字节。如果实参是 Reg 或 Imm 操作数，我们用一条 Push 指令传递它 ❶。如果它在内存中，我们先把实参复制到 AX，再压入 ❷。在 pushq $7 这样的指令里使用立即数，压入的是该值的 8 字节表示。压入 Reg 操作数时压入的是整个 8 字节寄存器，我们可以用对应的 4 字节别名访问其低 4 字节。（代码发射遍在大多数指令（包括 movl）中使用 %eax 这样的 4 字节寄存器别名，在 pushq 指令中使用 %rax 这样的 8 字节别名。）

如果我们在 pushq -4(%rbp) 这样的指令中直接使用 4 字节内存操作数，就会先压入操作数的 4 个字节，再跟上内存中恰好紧随其后的 4 个字节。这通常没事，虽然有点粗糙。但如果紧随操作数之后的 4 个字节不是可读内存，试图访问这些字节就会触发段错误并使程序崩溃。压入来自栈的操作数时不会出现这个问题；紧随其后的字节要么存放着当前函数的其他临时值，要么是已保存的调用者栈帧基地址。但压入静态变量时可能出现这个问题，我们将在第 10 章实现静态变量。静态变量可能恰好位于一段有效内存区域的末尾；在这种情况下，紧挨该变量之后的内存地址可能是无效的。（关于这个边界情况，可以进一步阅读 Randall Hyde 的 The Art of 64-Bit Assembly, Volume 1 [No Starch Press, 2021] 第 5.5.3.3 节 "Passing Parameters on the Stack"。）在压入之前先把操作数从内存复制到寄存器，就避免了这个问题。注意，AX 是我们唯一能用来协助把内存操作数压栈的寄存器，因为被调用者保存寄存器必须保持不动，实参已经放进了实参传递寄存器，而 R10 和 R11 已留给指令修补阶段使用。

所有实参就位后，我们发出 call 指令，把控制权转移给被调用者。call 返回后，经栈传递的实参已不再需要，填充字节更不需要。我们用 DeallocateStack 指令把这些实参与填充的总大小加回栈指针。释放这些空间后，栈指针就回到了我们开始准备函数调用之前的位置。

最后，我们取回函数的返回值。这个值会在 EAX 中，我们用一条 mov 指令把它复制到目的地。

### 替换伪寄存器

接下来，我们更新伪寄存器替换遍。这里的逻辑大部分不变：我们替换每个函数定义中伪寄存器的方式与前几章完全相同。如前所述，表示函数形参的伪寄存器不需要任何特殊处理。它们会像局部变量一样被分配到栈上的位置。

不过，我们确实需要做两处更新。第一，扩展这一遍以替换新 Push 指令中的伪寄存器。（我们现在不会直接压入伪寄存器，但第 II 部分会。）第二，改变跟踪每个函数所需栈空间的方式。以前整个遍只返回一个数字，因为程序只包含一个函数。现在我们需要为处理的每个函数返回一个栈大小。你可以把每个函数的栈大小记录在符号表中，或者在汇编 AST 中为每个函数标注它的栈大小。

注意，形参无论经栈传递还是经寄存器传递，都计入函数的栈大小，因为我们把它们复制进了函数的栈帧。

### 在指令修补期间分配栈空间

我们需要对指令修补遍做一个小调整：改变把 AllocateStack 添加到每个函数定义的方式。首先，在伪寄存器替换期间记录栈大小的地方查到每个函数所需的栈空间。然后，把该栈大小向上取整到 16 的下一个倍数。把栈帧的大小取整，使我们在函数调用期间更容易维持正确的栈对齐。

## 代码发射

现在我们要确保代码发射阶段能处理所有新指令和新操作数。这些大多相当直白，但有几个平台相关的细节需要考虑。我们已经见过，macOS 上函数名带下划线前缀，Linux 上则没有。这一点同样适用于 call 指令，所以在 macOS 上你要发射

```asm
    call _foo
```

而在 Linux 上你要发射：

```asm
    call foo
```

在 Linux 上，调用外部库中的函数与调用同一文件中定义的函数的方式也有所不同。如果 foo 没有定义在当前翻译单元中，你要发射：

```asm
    call foo@PLT
```

PLT 代表过程链接表（procedure linkage table），是 ELF 可执行文件中的一个节。（ELF 全称 Executable and Linkable Format，可执行可链接格式，是 Linux 和大多数其他类 Unix 系统上目标文件与可执行文件的标准格式；macOS 使用另一种称为 Mach-O 的文件格式。）程序通过 PLT 来调用共享库中的函数。我们已经知道，链接器把目标文件组合起来，并把符号解析为内存中的具体位置，从而生成可执行文件。在现代系统上，这些位置通常被编码为相对当前指令的偏移而不是绝对内存地址。当我们在同一个可执行文件中定义并使用某个符号时，链接器可以算出该符号相对于使用它的指令的相对偏移，从而解析这个引用。

共享库则是另一回事。程序使用共享库时，链接器不会把整个库复制进可执行文件，而是在运行时单独把库加载进内存。链接器并不确切知道这个库将位于内存中的什么地方，所以它无法解析共享库函数的名字。另一块称为动态链接器（dynamic linker）的软件必须在运行时解析这些名字。动态链接器可以用几种不同的方式解析符号，但最常见的做法是惰性绑定（lazy binding）。使用惰性绑定时，我们要到程序真正尝试调用某个函数的那一刻才去确定它的地址。PLT 正是为此而生。操作数 foo@PLT 并不指向函数 foo 本身，而是指向 PLT 中的一小段代码，这段代码会在我们尚不知道 foo 的地址时确定它，然后调用 foo。生成这段代码是链接器的职责，这段代码称为 PLT 条目（PLT entry）。

如果 foo 没有定义在当前翻译单元中，它可能定义在某个共享库中，也可能定义在链接器将纳入最终可执行文件的另一个目标文件中。后一种情况不需要 PLT：链接器能算出 foo 的地址（更准确地说，是引用它的 call 指令到它的偏移）。代码发射遍无法区分这两种情况，所以无论哪种情况都应带上 @PLT 后缀；在不需要它的时候带上这个后缀并无害处。

**注意**

关于 PLT 的工作原理以及我们需要它的原因，更深入的解释可以参见第 1 章“延伸资源”（第 21 页）中列出的两篇关于位置无关代码的博文。

在 Linux 上，要检查一个函数是否定义在当前翻译单元中——从而判断它是否需要 @PLT 修饰——你需要查符号表。macOS 处理惰性绑定的方式略有不同，完全不需要 @PLT 修饰。

## 调用库函数

更新完编译器后端之后，你就能编译调用标准库函数的程序了。你暂时还不能使用 #include 指令，因为任何标准库头文件都会用到你的编译器不支持的特性。取而代之，你需要显式声明想使用的库函数。

眼下我们能调用的库函数不多。因为我们只实现了 int 这一种类型，凡是返回类型或形参类型中用到任何非 int 类型的函数，我们都无法调用。但我们可以调用 putchar，它接受一个 int 实参并把对应的 ASCII 字符打印到 stdout。这足以让我们编译清单 9-32——一个略显非主流的 “Hello, World!” 实现。

```c
int putchar(int c);

int main(void) {
    putchar(72);
    putchar(101);
    putchar(108);
    putchar(108);
    putchar(111);
    putchar(44);
    putchar(32);
    putchar(87);
    putchar(111);
    putchar(114);
    putchar(108);
    putchar(100);
    putchar(33);
    putchar(10);
}
```

*清单 9-32：Hello, World!*

试着用你的编译器编译清单 9-32 并运行它。如果一切都实现正确，它会向 stdout 写入：

```bash
$ ./hello_world
Hello, World!
```

这是一个重要的里程碑！先花点时间享受一下成就感，再继续运行其余的测试用例。

**测试整个编译器**

要测试整个编译器，运行：

```bash
$ ./test_compiler /path/to/your_compiler --chapter 9
```

本章有几种新类型的测试。有些测试程序用 putchar 向 stdout 写内容，测试脚本会像检查返回码一样检查写到 stdout 的内容。本章另一些测试程序包含多个源文件。tests/chapter_9/valid/libraries 目录下有若干对库和客户端。每个库 <LIB>.c 包含一个或多个函数定义，与之对应的客户端程序 <LIB>_client.c 调用这些库函数。对每一对客户端和库，测试脚本会运行两个独立的测试。第一个测试用你的编译器编译客户端、用系统上安装的生产级编译器（GCC 或 Clang）编译库。第二个测试用系统编译器编译客户端、用你的编译器编译库。两种情况下，测试脚本都把客户端和库链接到一起，运行生成的可执行文件，并检查它产生预期行为。这验证了你的编译器在调用者和被调用者两侧都遵循 System V 调用约定。

我建议分几个阶段调试测试失败。首先，让不含函数实参的测试用例通过。然后，为确保你正确访问函数形参，先做 tests/chapter_9/valid/libraries 中那些自身不调用任何函数的库函数测试。由于客户端由系统编译器编译，你可以把函数定义与相应的函数调用分开测试。这些测试通过后，再做实参少于六个的函数调用测试。最后，调试实参多于六个的函数调用测试中失败的用例。

## 小结

函数调用是我们迄今为止见过的最强大、也最复杂的特性。为了实现它，你扩展了语义分析阶段以理解不同种类的标识符，并学会了 System V 调用约定的方方面面。这些努力得到了回报：你终于能编译与外部世界交互的程序了！
