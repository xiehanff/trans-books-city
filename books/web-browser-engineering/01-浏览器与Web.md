# 第一部分　引言（Part 1: Introduction）

# 导言 i：浏览器与 Web

*Introduction i: Browsers and the Web*

我——这里是 Chris 在说话——在整个成年人生中都与 Web¹ 相识相伴。对我而言，Web 多少像一位技术伙伴，无论求学还是工作，我从未远离过它。或许你也如此。而使用 Web，就意味着使用浏览器。我希望，在你阅读本书的过程中，你会像我一样爱上 Web 浏览器。

## i.1 浏览器与我

自从 20 世纪 90 年代初第一次接触 Web 及其前身²以来，我就一直痴迷于浏览器和网络化用户界面（networked user interface）这个概念。当我在 Web 上「冲浪」[5] 时——哪怕是在它最早的形态里——我感觉自己正在目睹计算的未来。从某些方面说，Web 和我是共同成长起来的：比如，Web 走向商业化的 1994 年，恰好是我上大学的那一年；在校期间我花了不少时间上网冲浪，而到我 1999 年毕业时，浏览器已经点燃了那场著名的互联网投机淘金热（dot-com speculation gold rush）。不仅如此，我如今供职的公司——Google——正是 Web 的孩子，就诞生于那个年代。

大学一年级时，我听过一场 RedHat 销售员做的宣讲。那场宣讲自然是为了推销 RedHat Linux，多半还把它称作「未来的操作系统」，畅想着「Linux 桌面元年」（year of the Linux desktop）。可当被问到 RedHat 面临的挑战时，这位销售提到的却不是 Linux，而是 Web：他说「得有人为 Linux 做一个好浏览器」。³ 即使在那时、在 Web 问世的最初几年，浏览器就已经是每台计算机必不可少的组件了。他甚至抛出了一个挑战：「做一个更好的浏览器能有多难？」是啊，能有多难？又是什么让它这么难？这个问题在我心里盘桓了很久。⁴

到底有多难呢！在 Chrome 一线奋战了十一年之后，我如今知道了他这个问题的答案：构建一个浏览器，既容易又难得超乎想象，既处处是有意为之，也满是阴差阳错。而且放眼望去，你能在同一份代码库里看到整个 Web 的演化与历史。这件事有趣得没有尽头。

我就是这样爱上 Web 浏览器的。接下来，让我告诉你你为什么会爱上它。

## i.2 历史中的 Web

Web 是一场宏大而疯狂的实验。如今，在 Web 上看视频、读新闻、与朋友联络，早已是理所当然的事。这容易让人觉得 Web 简单而显然，是已经完工、早已建好的东西。但 Web 既不简单，也不显然（更谈不上「完工」）。它是一系列实验与研究的成果，这些探索几乎可以追溯到计算技术的起点⁵，研究的正是如何帮助人们彼此连接、相互学习。

在早期，互联网是一个由计算机组成的全球网络，这些计算机大多位于大学、实验室和大型企业，通过物理线缆相连，并使用面向特定应用的协议通信。（非常）早期的 Web 基本上就建立在这个基础之上。网页是以特定格式存储在特定计算机上的文件。网页的地址指明了计算机和文件，而早期的服务器除了从磁盘读取文件之外几乎什么都不做。Web 的逻辑结构映照着它的物理结构。

此后变化巨大。如今，网页的超文本标记语言（HyperText Markup Language，HTML）通常是在运行中即时动态拼装⁶，并按需发送到你的浏览器。被拼装的各个片段本身又充满了动态内容——新闻、收件箱里的邮件，以及根据你的个人口味调整过的广告。甚至连地址都不再指明某台特定的计算机——内容分发网络（content distribution network）会把请求路由到遍布全球的成千上万台计算机中的任意一台。在更高的层面上，大多数网页并非由某人的家用计算机⁷提供，而是来自大公司的社交媒体平台或云计算服务。

尽管发生了这么多变化，有些东西始终未变——它们是构成 Web 本质的核心基石：

- 用户使用一种称为浏览器（browser）的用户代理（user agent）来访问 Web。
- Web 是一张由超链接（hyperlink）连接起来的信息网络。
- 信息通过超文本传输协议（HyperText Transfer Protocol，HTTP）来请求，并以 HTML 文档格式来组织。
- 文档由统一资源定位符（Uniform Resource Locator，URL）标识，而不是由其内容标识，且可以动态生成。
- 网页可以链接到其他格式的辅助资源，包括图像、视频、层叠样式表（Cascading Style Sheets，CSS）和 JavaScript。
- 所有这些构建要素都是开放的、标准化的，可自由使用或复用。

从哲学的角度看，也许其中某一条原则并不是根本性的。人们可以试着把 Web 的联网与渲染两个方面区分开来；可以把「链接」和「联网」从协议与数据格式的具体选择中抽象出来；也可以追问浏览器在理论上是否必要，或者主张 HTTP、URL 和超链接才是 Web 真正不可或缺的部分。

也许吧。⁸ 毕竟，Web 是一场实验；各项核心技术都在演化、生长。但 Web 并非一场意外；它的原始设计反映出的真理，不仅关乎计算技术，更关乎人类如何彼此连接、彼此交往。在托管与内容双双虚拟化的浪潮中，Web 不仅幸存下来，而且欣欣向荣，靠的正是这一原始设计的优雅与高效。

关键在于理解：这场宏大的实验尚未结束。Web 的本质会延续下去，而通过构建 Web 浏览器，你将有机会塑造它的未来。

## i.3 真实的浏览器代码库

那么，让我讲讲为浏览器做贡献是什么体验。在参与 Chrome 工作的最初几个月里的某一天，我偶然看到了实现 `<br>` [7] 标签的代码——瞧啊，就是那个亲切的老朋友 `<br>` 标签，我曾无数次用它往网页里插入换行！而它的实现，无论是在 Chrome 里，还是在本书的简易浏览器里，都几乎没几行代码。

但 Chrome 整体——它的功能、速度、安全、可靠性——着实令人惊叹。这里面投入了数千人年的工作量。而且始终有「做得更多」的压力——添加更多功能、提升性能、跟上「Web 生态系统」的步伐——为了 Web 上的数千家企业、数百万开发者⁹和数十亿用户。

在这样的代码库上工作可能令人生畏。我常常发现某行代码上一次被修改是 15 年前，出自某个我素未谋面的人之手；直到现在，我仍会发现一些我从不知道其存在的文件和类；还会看到一些看似多余、实际上却很重要的代码。那段 15 年前的代码是做什么的？这些我新见到的文件有什么用途？那段代码的存在自有其理由吗？

每一个浏览器都有数以千计未修复的缺陷（bug），小到最细微的失误，大到数不清的混乱与错配。每一个浏览器都必须被无休止地调优与优化，以榨出最后一点性能。每一个浏览器都需要艰苦细致的持续重构来降低复杂度，而这通常是小心翼翼¹⁰地引入模块化与抽象。

让浏览器有别于大多数巨型代码库的，是它们的紧迫性。浏览器几乎与任何「遗留」（legacy）代码库一样古老，却不是遗留系统：没有被抛弃，没有被半废弃，也没有被列入替换计划。恰恰相反，它们对世界经济至关重要。因此，浏览器工程师必须去修复和改进，而不是抛弃和替换。而且，由于 Web 本身的特性是高度去中心化的，浏览器所要满足的使用场景，在很大程度上并不由「拥有」或「控制」某个浏览器的公司决定。其他人——包括你——可以而且确实在贡献想法、提案和实现。

令人惊叹的是，尽管规模如此庞大、节奏如此紧张、复杂度如此之高，这里仍然大有贡献余地。今天的每一个浏览器都是开源的，这让整个 Web 开发者社区都能看到它的实现。浏览器的演化就像一个个巨型研究项目，新想法不断被提出、被试验。正如你所料，有些功能失败了，有些成功了。成功的那些最终进入规范（specification），并被其他浏览器实现。每一个浏览器都欢迎贡献——无论是修复缺陷、提议新功能，还是实现有前景的优化。

而且这份贡献是值得的，因为从事浏览器开发乐趣无穷。

## i.4 浏览器代码中的概念

HTML 和 CSS 被设计成黑盒——声明式的应用编程接口（Application Programming Interface，API）——你只需指定期望达成的结果，而由浏览器自己负责想清楚如何达成。Web 开发者不会、而且大多数时候也无法亲手绘制网页的像素。

这可能让浏览器显得神奇，也可能让人抓狂——取决于它有没有把事情做对！但这也让浏览器成为一款相当不寻常的软件：挑战独一无二，算法引人入胜，优化巧夺天工。哪怕纯粹为了乐趣，浏览器也值得研究。

支撑这一切的，是 Web 浏览器对控制反转（inversion of control）[8]、约束编程（constraint programming）[9] 和声明式编程（declarative programming）[10] 的实现。Web 把控制权反转了过来：由一个中介——浏览器——处理绝大部分渲染，而 Web 开发者只需向这个中介指定渲染参数和内容。¹¹ 进一步说，这些参数通常采用约束（constraint）的形式，描述屏幕上各元素之间相对的大小和位置关系，而不是直接给出具体数值；¹² 由浏览器求解这些约束来得到数值。同样的思想也适用于动作：网页大多只要求某个动作会发生，而不指定它何时发生。这种声明式风格意味着，从开发者的视角看，变更「立即生效」；但在幕后，浏览器可以偷懒（lazy）[12]，把变更的应用推迟到它们必须对外可见之时——要么是因为后续的 API 调用，要么是因为网页必须呈现给用户。¹³

浏览器这种不寻常的设计有其现实理由。诚然，开发者失去了一部分控制权和主动权——当像素出错时，开发者无法直接修复。¹⁴ 但他们换来的是：可以把内容部署到 Web 上而无须操心种种细节，可以让这些内容立刻在几乎所有现存的计算设备上可用，还可以让它们在将来依然可访问，大体上免于软件不可避免的过时命运。

对我来说，浏览器是算法活起来的地方。一个浏览器里包含着比任何计算机游戏都更复杂、更强大的渲染引擎（rendering engine）；一整套网络协议栈；精巧的数据结构与并行编程技术；一台虚拟机、一门解释型语言和一个即时编译器（just-in-time compiler）；一个世界级的安全沙箱（sandbox）；还有一套独一无二的动态数据存储系统。

而事实是——你无时无刻不在使用浏览器，说不定此刻正用它读这本书！这让浏览器里的算法比几乎所有其他地方的算法都更平易近人，因为 Web 早已为你所熟悉。

## i.5 浏览器的角色

Web 位于现代计算的中心。年复一年，Web 把自己的触角伸向我们用计算机所做的越来越多的事情。它早已远远超出最初基于文档的信息分享用途：如今许多人一整天都泡在浏览器里，一个别的应用都不开！此外，桌面应用如今也常常以 Web 应用（web app）的形式构建和交付：它们是由浏览器加载的网页，用起来却像安装好的应用。¹⁵ 即使在移动设备上，应用也常常内嵌一个浏览器来渲染应用用户界面（UI）的一部分。¹⁶ 或许在未来，桌面设备和移动设备都将大体上成为承载 Web 应用的容器。浏览器已经算得上计算世界中关键而不可或缺的一环。

既然如此核心，就值得弄清楚 Web 是如何工作的。尤其值得聚焦于浏览器——它是用户代理¹⁷，是 Web 各种交互的中介者，而正是它最终让 Web 的各项原则落到实处。浏览器还是 Web 的实现者：它的沙箱保障浏览安全；它的算法实现声明式文档模型；它的 UI 负责链接导航。只有当浏览器高效到极致时，网页才能加载得快、响应得流畅。

## i.6 浏览器与你

本书讲解如何构建一个简易浏览器——它虽然简单，却能显示看起来有趣的网页，并支持许多有趣的行为。你会看到，这出奇地容易，而且它演示了你要理解一个真实浏览器所需的全部核心概念。当浏览器变成代码，它就不再神秘。

本书的意图是让你在前几章的学习过程中亲手构建自己的浏览器。一旦它跑起来，你就有无穷的机会去改进性能或添加功能，其中一些会以习题的形式给出。这些习题中有许多正是真实浏览器中实现了的功能，我鼓励你亲手一试——添加功能是浏览器开发中最有乐趣的部分之一！

随后，本书会深入到细节与高级特性，基于我在 Chrome 的经验，充实一个真实浏览器渲染引擎架构的血肉。读完本书后，你应该能够钻进 Chromium、Gecko 或 WebKit 的源代码，而不至于太吃力。

我希望这本书能让你领会浏览器的深度、复杂性与力量。我希望这本书能传递出浏览器的美——它精巧的算法与数据结构，它与计算文化和计算历史的共同演化，以及它在我们这个世界的中心地位。但最重要的，我希望这本书能让你在自己身上看到那个构建未来浏览器的人。
