# 第 17 章　支持动态内存分配

*Chapter 17: Supporting Dynamic Memory Allocation*

在第 II 部分的学习过程中，你编译过的程序所调用的标准库函数范围越来越广。在第 I 部分结束时，你的编译器只支持形参和返回值类型都为 int 的函数，比如 putchar。现在，你已经能编译调用 fmax 等浮点数学函数和 puts 等字符串处理函数的程序了。本章中，你将实现调用标准库中一个特别重要的部分——内存管理函数——所需的其余特性。这些函数包括动态分配内存的 malloc、calloc 和 aligned_alloc；释放动态分配内存的 free；以及 realloc——它释放一块内存，并重新分配一块内容相同的新内存。

要编译声明并调用这些函数的程序，你需要实现 void 类型。到目前为止，我们只用 void 关键字指定空形参列表；现在我们要把它当作一个真正的类型说明符。在 C 中，void * 表示一块没有特定类型的内存的地址；所有分配内存的标准库函数都返回这种类型。void 类型自身也很有用。例如，你可以用它声明不返回值的函数，比如 free。除 void 之外，我们还将实现 sizeof 运算符，用于获取类型或对象的大小。C 程序经常用 sizeof 来确定要分配多少字节的内存。

本章那个不算秘密的小算盘，是帮你为第 18 章实现结构类型做好准备。现实中的 C 程序经常把结构存储在动态分配的内存中，那一章的很多测试也是如此。我们对类型检查器所做的改动在第 18 章同样会派上用场，因为适用于 void 的某些类型规则也适用于结构类型。

## void 类型

C 标准（6.2.5 节第 19 段）对 void 给出了如下颇为神秘的定义：“void 类型由一个空的值集合组成；它是一种无法被补全的不完整对象类型（incomplete object type）。”我们稍后再详细讨论“不完整对象类型”的含义。眼下，主要的想法是：void 是一个没有任何值的类型。你用这个类型做不了太多事情，但它确实有几处用途。

如果函数不返回任何值，你可以给它指定 void 返回类型。要离开一个 void 返回类型的函数，可以使用不带表达式的 return 语句，如清单 17-1 所示。

```c
void return_nothing(void) {
    return;
}
```

*清单 17-1：一个具有 void 返回类型的函数*

如清单 17-2 所示，你也可以完全省略 return 语句。在这种情况下，一旦控制到达函数体末尾，函数就会返回。

```c
void perform_side_effect(void) {
    extern int some_variable;
    some_variable = 100;
}
```

*清单 17-2：一个不带 return 语句的 void 函数*

void 表达式是类型为 void 的表达式；它没有值，但你可以为它的副作用而求值它。产生 void 表达式有三种方式。第一，调用 void 函数。第二，求值两个分支都是 void 的条件表达式：

```c
flag ? perform_side_effect() : return_nothing();
```

第三，把值强制转换为 void：

```c
(void) (1 + 1);
```

这里，强制转换为 void 对程序的执行没有任何影响；它唯一的用途是告诉编译器和人类读者，该表达式的值应当被丢弃。这是让编译器不再就未使用的值发出警告的常用手段。

如果你特别热衷于遵守 C 的类型规则，还可以在类似清单 17-3 的代码中强制转换为 void，使条件表达式两个分支的类型一致。

```c
int i = 0;
flag ? perform_side_effect() : (void) (i = 3);
```

*清单 17-3：一个类型为 void 的条件表达式*

如果在这个条件表达式中省略到 void 的强制转换，一个分支的类型会是 void，另一个分支的类型会是 int。这是非法的，不过大多数编译器并不会抱怨，除非你使用 -pedantic 标志启用额外警告。我们的编译器则会拒绝带单个 void 分支的条件表达式，因为它无时无刻不处于 -pedantic 模式。

void 表达式可以用在四个地方。第一，它可以作为条件表达式的一个子句出现，如清单 17-3 所示。第二，你可以把它用作独立表达式：

```c
perform_side_effect();
```

第三，它可以出现在 for 循环头部的第一个或第三个子句中，如清单 17-4 所示。

```c
for (perform_side_effect(); i < 10; perform_side_effect())
    --snip--
```

*清单 17-4：在 for 循环头部使用 void 表达式*

第四，你可以把一个 void 表达式强制转换为 void：

```c
(void) perform_side_effect();
```

最后这种用法没有多大用处，但它是合法的。

正如你已经知道的，你还可以用 void 关键字在函数声明中指定空形参列表。这是一种特殊情况，因为它实际上并不指定类型为 void 的表达式、对象或返回值。即使我们把编译器扩展到完全支持 void 类型之后，处理这个特殊情形的方式也和以前完全一样。

## 用 void * 管理内存

现在我们来看看内存管理函数如何使用 void * 表示已分配的内存。malloc 函数的签名如下：

```c
void *malloc(size_t size);
```

size 参数指定要分配的字节数。它的类型 size_t 是一种由实现定义的无符号整数类型。在 System V x64 ABI 下，size_t 是 unsigned long 的别名。因为我们不支持类型别名，我们的测试程序和示例改用这个声明：

```c
void *malloc(unsigned long size);
```

malloc 函数分配一块内存并返回它的地址。由于 malloc 并不知道将存储在这块内存中的是什么类型的对象，返回指向 int、char 或我们到目前为止见过的任何其他类型的指针都会产生误导。因此，它返回 void *。不过，你不能通过 void * 指针读或写内存。所以，在访问你用 malloc 分配的内存之前，你需要先指定它应当包含什么类型的对象，做法是把它的地址从 void * 转换为另一种指针类型。

你可以在 void * 与其他指针类型之间来回隐式转换，无需显式强制转换。例如，你可以用 malloc 分配一个包含 100 个 int 元素的数组：

```c
int *many_ints = malloc(100 * sizeof (int));
```

当你把 malloc 的结果赋给 many_ints 时，它被隐式地从 void * 转换为 int *。然后，你就可以像对任何指向 int 数组的指针一样，对 many_ints 做下标操作：

```c
many_ints[10] = 10;
```

free 函数接受一个 void * 参数，指定要释放的那块内存：

```c
void free(void *ptr);
```

这个指针必须与 malloc 或其他某个内存分配函数早先返回的值相同。下面展示了如何用 free 释放 many_ints 指向的内存：

```c
free(many_ints);
```

这次函数调用把 many_ints 的值从 int * 隐式转换回 void *，得到的正是 malloc 最初返回的那个指针。

calloc 和 aligned_alloc 函数提供了略有不同的内存分配方式；与 malloc 一样，它们以 void * 类型返回指向所分配空间的指针。realloc 函数接受一个大小值和一个指向先前分配的、现在应当被释放的存储空间的 void * 指针，并返回一个指向新分配存储块的 void * 指针，该存储块具有新的大小和原有的内容。就我们的目的而言，这些函数的细节并不重要；关键思想在于，它们都使用 void * 指针来标识自己分配和释放的那些内存块。

这些内存块是我们可以像变量一样读写的对象，但它们的生命周期以不同的方式管理。我们知道，变量要么具有自动存储期（automatic storage duration，其生命周期持续单个块的执行过程），要么具有静态存储期（static storage duration，其生命周期持续整个程序）。一块已分配的内存则具有分配存储期（allocated storage duration）：它的生命周期从被分配时开始，到被释放时结束。

编译器必须跟踪所有具有静态或自动存储期的变量，在符号表中记录它们的大小和生命周期等细节，并在数据段或栈中为它们预留空间。但编译器不需要对具有分配存储期的对象有任何了解，因为跟踪它们是程序员和内存管理库的职责。

## 完整类型与不完整类型

如果我们知道一个对象类型的大小，它就是完整类型（complete type）；如果不知道，它就是不完整类型（incomplete type）。void 类型是我们遇到的第一个不完整类型。我们不知道它的大小，因为它根本没有大小。下一章中，我们将遇到不完整的结构类型，它们的大小和成员对编译器不可见。如果编译器随后了解到更多信息，不完整的结构类型可以在程序靠后的位置补全。而 void 类型则永远无法补全。

C 标准指出，“只有当不需要该类型对象的大小时，才能使用不完整类型”（6.7.2.3 节，脚注 132）。例如，你不能用不完整类型定义变量，因为你不知道要为它分配多少空间。你也不能给不完整类型的对象赋值或使用它的值，因为你需要知道要读或写多少字节。除少数例外，其他不完整类型受到与 void 相同的限制，类型检查器将以同样的方式处理它们。

所有指针都是完整类型，即使它们指向的类型不完整；我们知道指针的大小总是 8 字节。正因如此，你可以声明 void * 类型的变量和形参、从函数返回 void * 值、把 void * 转换为其他指针类型，等等。正如你将在下一章看到的，指向不完整结构类型的指针也可以按同样的方式使用。

## sizeof 运算符

sizeof 运算符既接受表达式，也接受类型名。作用于类型名时，它返回该类型以字节计的大小。作用于表达式时，它返回该表达式类型的大小。清单 17-5 演示了这两种用法。

```c
sizeof (long);
sizeof 10.0;
```

*清单 17-5：sizeof 的两种用法*

这两个 sizeof 表达式都求值为 8，因为 long 和 double 类型都是 8 字节。注意，sizeof 表达式中的类型名必须加括号，但表达式不必。

在 sizeof 表达式中使用数组时，数组不会退化为指针。考虑清单 17-6 中的 sizeof 表达式。

```c
int array[3];
return sizeof array;
```

*清单 17-6：获取数组的大小*

这段代码返回 12，也就是包含三个 int 的数组的大小，而不是 8，也就是指针的大小。

你总是可以在不求值一个表达式的情况下确定它的类型——从而确定它的大小。事实上，C 标准要求我们不对 sizeof 表达式的操作数求值。相反，我们推断操作数的类型，并在编译时求值 sizeof。这意味着 sizeof 表达式不会产生副作用。例如，语句

```c
return sizeof puts("Shouting into the void");
```

不会调用 puts。它只会返回 4，因为 puts 函数的返回类型是 int。

你还可以把 sizeof 应用于通常会导致运行时错误的表达式，如清单 17-7 所示。

```c
double *null_ptr = 0;
return sizeof *null_ptr;
```

*清单 17-7：在不求值表达式的情况下获取它的大小*

通常情况下，解引用 null_ptr 会导致未定义行为。但这个例子是良定义的，因为它永远不会求值 *null_ptr。相反，它会返回 8，因为编译器可以确定 *null_ptr 的类型是 double。

变长数组是这条规则的唯一例外。变长数组的大小在编译时未知，必须在运行时求值。由于我们不支持变长数组，可以忽略这种情况。

*清单 17-8：加入 void、sizeof 和不带返回值的 return 语句的抽象语法树*

我们在这里做了四处小改动。第一，添加了 void 类型。第二，Return 语句中的表达式现在是可选的，这样它既能表示带返回值的 return 语句，也能表示不带返回值的 return 语句。最后，还添加了两个新表达式，分别对应 sizeof 运算符的两种用法。

接下来，我们对文法做相应的修改。这里的一个小麻烦是，除非给强制转换表达式加上括号，否则不能把 sizeof 应用于它。例如，下面这是一个语法错误：

```c
sizeof (int) a;
```

把强制转换表达式用括号括起来就能消除这个错误：

```c
sizeof ((int) a);
```

这一限制让解析器更容易区分作用于类型名的 sizeof 与作用于表达式的 sizeof。为了在文法中体现这一限制，我们需要把强制转换表达式从其他一元表达式中拆分出来，放进一个单独的符号。

我们先把类型名重构成一个符号，使它既能用于强制转换表达式，也能用于 sizeof 表达式：

```text
<type-name> ::= {<type-specifier>}+ [<abstract-declarator>]
```

接下来，我们定义新的 <cast-exp> 符号，其中一条规则用于强制转换表达式，另一条规则覆盖所有其他一元表达式：

```text
<cast-exp> ::= "(" <type-name> ")" <cast-exp>
             | <unary-exp>
```

然后，我们将更新 <unary-exp>，使其包含除强制转换之外的每个一元表达式：

```text
<unary-exp> ::= <unop> ❶ <cast-exp>
              | "sizeof" ❷ <unary-exp>
              | "sizeof" "(" <type-name> ")"
              | <postfix-exp>
```

像 -、~、! 和 & 这样的一元运算，其规则允许强制转换表达式作为操作数 ❶，而 sizeof 的规则不允许 ❷。

最后，我们用新的 <cast-exp> 符号（而不是更受限的 <unary-exp>）来表示二元或三元表达式中的一个项：

```text
<exp> ::= <cast-exp> | <exp> <binop> <exp> | <exp> "?" <exp> ":" <exp>
```

*清单 17-9：加入 void、sizeof 和可选返回值的文法*

parse_type 辅助函数把一列类型说明符转换成类型 AST 节点，它应当拒绝任何让 void 说明符与 long 或 unsigned 等其他类型说明符同时出现的声明。除此之外，解析器应当像对待任何其他类型一样对待 void。void 类型可以被指针、数组和函数声明器修饰；指向 void 的指针和返回 void 的函数都完全合法，而使用 void 的其他做法在语法上有效、在语义上非法。例如，声明元素类型为 void 的数组、定义 void 变量、声明带 void 形参的函数，都是语义错误。解析器不会捕获这些语义错误，但类型检查器会。

尽管 <param-list> 的文法规则本身没有变化，你可能仍需要修改解析它的逻辑。如果左括号后面跟着 void 关键字，你需要再多向前看一个词法单元。如果下一个词法单元是右括号，那么形参列表为空；否则列表不为空，void 关键字是某个形参声明的开头。

注意，当 void 关键字表示空形参列表时，我们不会把它转换成 AST 中的 Void 类型。例如，给定函数声明

```c
int main(void);
```

得到的 AST 节点将具有如下类型：

```text
FunType(params=[], ret=Int)
```

与前几章一样，params 列表为空；它不包含 Void。

## 类型检查器

现在我们来弄清楚如何对 void、void * 和 sizeof 做类型检查。我们先从 void * 与其他指针类型之间的隐式转换开始。尽管指针类型之间的大多数隐式转换都不被允许，但这几种情况是允许的。接下来，我们将检测 void 可能引发的所有新鲜而刺激的类型错误。最后我们处理 sizeof 运算符。

### 与 void * 之间的转换

void * 与其他指针类型之间的隐式转换在三种情况下是合法的。第一，你可以用 == 或 != 比较一个 void * 类型的值与另一种指针类型的值：

```c
int *a;
void *b;
--snip--
return a == b;
```

第二，在形如 <cond> ? <clause1> : <clause2> 的条件表达式中，一个子句可以具有 void * 类型，另一个子句可以具有另一种指针类型：

```c
int *a;
void *b;
--snip--
return flag ? a : b;
```

在这两种情况下，非 void 的指针会被转换为 void *。

第三，你可以在赋值时隐式地转换到 void * 或从 void * 转换而来。你可以把任何指针类型的值赋给 void * 类型的对象：

```c
int *a = 0;
void *b = a;
```

同样，你也可以把 void * 类型的值赋给具有另一种指针类型的对象。

这最后一种情况不仅涵盖简单赋值，还涵盖我们在第 14 章讨论过的所有“如同赋值”（as if by assignment）的转换。例如，把 void * 实参传给一个期望其他某种指针类型形参的函数是合法的：

```c
int use_int_pointer(int *a);
void *ptr = 0;
use_int_pointer(ptr);
```

并非巧合的是，这正好就是允许把空指针常量隐式转换为其他指针类型的那三种情况。为了支持与 void * 之间的隐式转换，我们将扩展第 14 章定义的两个辅助函数：get_common_pointer_type 和 convert_by_assignment。

让我们重新审视定义 get_common_pointer_type 的清单 14-14。它在这里重现为清单 17-10，本章的改动以粗体标出。

```text

    e2_t = get_type(e2)
    if e1_t == e2_t:
        return e1_t
    else if is_null_pointer_constant(e1):
        return e2_t
    else if is_null_pointer_constant(e2):
        return e1_t
    else if e1_t == Pointer(Void) and e2_t is a pointer type:
        return Pointer(Void)
    else if e2_t == Pointer(Void) and e1_t is a pointer type:
        return Pointer(Void)
    else:
        fail("Expressions have incompatible types")
```

粗体标出的代码允许 void * 与其他指针类型之间的隐式转换，但不允许 void * 与算术类型、数组类型或 void 之间的转换。接下来，我们再看一看清单 14-16，它在这里重现为清单 17-11，改动以粗体标出。

*清单 17-11：把表达式“如同赋值”般转换为目标类型*

粗体标出的新增代码允许我们在赋值时把 void * 转换为其他指针类型，或者反过来。注意，这段清单中没有任何内容会阻止我们把 void 表达式赋给 void 目标类型。不过，我们将在类型检查器的其他地方引入对 void 的限制，确保我们绝不会以 void 为目标类型调用 convert_by_assignment。例如，我们绝不会尝试把函数实参转换为 void，因为我们会拒绝带 void 形参的函数声明。

### 返回类型为 void 的函数

接下来，我们要对带表达式和不带表达式的 return 语句做类型检查。该使用哪种 return 语句取决于函数的返回类型。void 返回类型的函数不得返回表达式。任何其他返回类型的函数在返回时必须带表达式。因此，下面两个函数定义是合法的：

```c
int return_int(void) {
    return 1;
}

void return_void(void) {
    return;
}
```

而这两个都是非法的：

```c
int return_int(void) {
    return;
}

void return_void(void) {
    return 1;
}
```

你甚至不能从 void 返回类型的函数返回一个 void 表达式，因此下面这个例子同样是非法的：

```c
void return_void(void) {
    return (void) 1;
}
```

GCC 和 Clang 都接受这个程序，但如果你加上 -pedantic 标志，它们会发出警告。这个边缘情形你可以随意处理；测试套件不涉及它。

我会跳过这一节的伪代码，因为对我们现有的 return 语句类型检查逻辑来说，这是一个非常直截了当的扩展。

### 标量类型与非标量类型

有几种 C 构造要求标量表达式，包括 &&、|| 和 ! 表达式的操作数；条件表达式的第一个操作数；以及循环和 if 语句中的控制条件。它们的共同点在于，所有这些语言构造都会把表达式的值与零比较。把指针或算术值与零比较是有意义的；把非标量的值与零比较则没有。

在前面的章节中，没有办法写出违反这些类型约束的程序。数组是我们唯一的非标量类型，而在需要标量表达式的地方，数组会退化为指针。但一旦把 void 加入进来，我们就必须显式地强制执行这些约束。（尽管 void 不是聚合类型，它也不是标量。标量表达式有单个值，而 void 表达式没有值。）清单 17-12 定义了一个小小的辅助函数，告诉我们一个类型是否是标量。

```text
is_scalar(t):
    match t with
    | Void -> return False
    | Array(elem_t, size) -> return False
    | FunType(param_ts, ret_t) -> return False
    | _ -> return True
```

### 不完整类型的限制

如果一个程序在需要完整类型的地方使用了不完整类型，就会遇到类型错误。目前，我们将在三种情况下要求完整类型。第一，你不能对指向不完整类型的指针做加法、减法或下标操作，因为你无法确定它们所指数组元素的大小。第二，你不能对不完整类型应用 sizeof，因为其大小未知。第三，只要你指定数组类型，它的元素类型就必须是完整的。

> **注意**
>
> 作为一种语言扩展，Clang 和 GCC 允许对 void 指针做指针算术，也允许对 void 做 sizeof 运算。这些表达式的实现方式等同于假定 void 的大小为 1。

清单 17-15 定义了几个辅助函数来支持这些验证。

```text

    return t != Void
is_pointer_to_complete(t):

    | _ -> return False
```

### 对 void 的额外限制

在刚才实现的、适用于所有不完整类型的限制之上，我们还要对 void 额外实施两条限制：你不能声明 void 变量或形参，也不能解引用指向 void 的指针。（void 的这两种用法都处于合法性的灰色地带；详情参见侧栏“void 何时有效：一场过分详细的讨论”。）

这些对 void 的限制不适用于其他不完整类型。下一章中你会看到，你可以声明——但不能定义——具有不完整结构类型的变量。等类型被补全之后，你可以在程序中的另一个位置定义该变量。类似地，你可以声明一个以不完整结构类型作为形参或返回类型的函数，只要你在调用或定义该函数之前补全类型。最后，解引用指向不完整结构类型的指针是合法的，尽管这没有多大用处；你对解引用结果唯一能做的事就是取它的地址，而这只是把你最初那个指针又拿了回来。

> **void 何时有效：一场过分详细的讨论**
>
> 极少有 C 程序员需要声明 void 变量或解引用 void * 表达式。尽管如此，深入挖掘 C 标准对这些冷门情形的确切说法，以及几款广泛使用的编译器如何处理它们，仍然值得一做。事实证明，语言的这个角落格外混乱、定义不清，这使它成了一个有趣的例证，说明语言标准有多难编写和实现。
>
> 首先，C 标准允许你声明 extern void 变量，但不允许你使用该变量。毫不意外，给它赋值或使用它的值都是未定义行为。对具有其他不完整类型的变量来说也是如此。对大多数不完整类型的变量，你唯一能做的事就是取它们的地址：
>
> ```c
> extern struct s my_incomplete_var;
> struct s *ptr = &my_incomplete_var;
> ```
>
> 正如本书技术审稿人 Stephen Kell 向我指出的，你可能也想取 void 变量的地址。例如，如果你在编写一个检查内存布局的程序（比如调试器），可能需要引用没有特定类型的任意内存位置。大多数类 Unix 系统正是为此目的定义了几个特殊符号：etext、edata 和 end，它们的地址分别标记文本段、数据段和 BSS 段的末尾。需要访问这些符号的程序通常把它们声明为 char 或其他任意类型，像这样：
>
> ```c
> extern char etext;
> void *text_segment = &etext;
> ```
>
> 但把它们声明为 void 变量可以说更合理，因为它们其实并不指代带值的对象。可如果你这么做，取它们的地址就是非法的，因为 void 变量不是左值。C 标准 6.3.2.1 节第 1 段指出：“左值是一个……可能指代一个对象的表达式（具有 void 以外的对象类型）。”而 6.5.3.2 节第 1 段列出了对 & 运算符的约束：“一元 & 运算符的操作数应当是函数指示符、[] 或一元 * 运算符的结果，或者是一个指代对象[且满足其他几条约束]的左值。”
>
> 由于 void 变量不属于上述任何一种，我们无法取它的地址，这又意味着我们对它无能为力。实践中，Clang 和 GCC 都允许你声明 void 变量并取其地址，不过它们会警告你的代码没有严格遵循标准。Microsoft Visual Studio 编译器（MSVC）则严苛得多；它根本不允许你声明 void 变量。
>
> 你可以用不完整类型声明函数形参，而标准中没有任何迹象表明 void 形参会是个例外，所以下面这个声明似乎是合法的：
>
> ```c
> void my_sketchy_function(void a, void b);
> ```
>
> 但 GCC 会对带 void 形参的函数发出警告，而 Clang 和 MSVC 则直接拒绝它们。拒绝这类形参至少有两条充分的理由：它们没有任何可以想见的用途，而且它们可能与“单个 void 形参表示空形参列表”这一特殊情况相冲突。除了那种特殊情况之外，标准居然没有干脆地禁止 void 形参，这看起来像是一种疏漏。
>
> 最后，让我们试着弄清楚，当你解引用一个 void * 值并丢弃结果时会发生什么：
>
> ```c
> void *void_ptr = malloc(4);
> (void) *void_ptr;
> ```
>
> GCC 会对此发出警告，而截至 16.0.0 版本，Clang 也会。MSVC——它依旧是这一群体里最倔强的——则将其视为错误。标准本身完全帮不上忙。6.5.3.2 节说指针解引用运算符的操作数必须是指针，但没有对它可以指向的类型施加任何限制。它接着说：“如果操作数……指向一个对象，结果是指代该对象的左值。如果操作数的类型是‘指向 type 的指针’，结果的类型就是‘type’。如果给指针赋了无效值，一元 * 运算符的行为是未定义的。”
>
> 你很难辩称指向 void 的指针是一个“无效值”。正如我们已经看到的，良构的程序一直在使用指向 void 的指针。下一个问题是，指向 void 的指针能否指向一个对象；如果能，听起来解引用它就应该给我们一个左值。标准的其他部分暗示它确实可以指向对象。例如，介绍 malloc 和其他内存管理函数的 7.22.3 节第 1 段指出：“被分配对象的生命周期从分配开始，直到释放为止。每次这样的分配都应产生一个指向与其他任何对象不相交的对象的指针。”
>
> 这一切都表明 void_ptr 是一个指向对象的有效指针，因此 *void_ptr 应当返回一个类型为 void 的左值——只可惜 void 表达式不能是左值。这是个悖论！据 Aaron Ballman（C 标准委员会成员）所说，这意味着解引用指向 void 的指针并丢弃结果属于“因未作规定而未定义”的行为（undefined behavior by omission，https://github.com/llvm/llvm-project/issues/53631#issuecomment-1253653888）。如果 C 标准能把这些明说出来就好了，不过我猜标准委员会有更要紧的优先事项。

我们在这一节里含糊处理了一个角落情形。严格说来，对任何被解引用的指针取地址都是合法的，无论它是指向完整类型、不完整结构类型还是 void 的指针。正如我们在第 14 章看到的，对被解引用的指针取地址是一种特殊情况；两个操作互相抵消，结果是良定义的，即使解引用表达式本身会是未定义的。这意味着下面这段代码片段是合法的：

```c
void *void_ptr = malloc(4);
void *another_ptr = &*void_ptr;
```

我们的编译器会拒绝所有对 void * 操作数的解引用操作，即便在这个边缘情形下也是如此。但在这点上我们并不孤单：GCC 会就这段代码片段发出警告，而 MSVC 则完全拒绝它。（当然，只要愿意，你也可以正确处理这个边缘情形；我们的测试套件不涉及它。）

```text
          ❷ result_type = Void
        else if t1 and t2 are arithmetic types:
            result_type = get_common_type(t1, t2)
        else if t1 or t2 is a pointer type:
            result_type = get_common_pointer_type(typed_e1, typed_e2)
        else:
            fail("Cannot convert branches of conditional to a common type")
        --snip--
```

*清单 17-18：对条件表达式做类型检查*

要对条件表达式做类型检查，我们先验证它的控制条件是标量 ❶。然后，我们考察两个子句的类型。如果它们都是 void，结果也是 void ❷。否则，我们按以前的方式求结果类型：如果两个操作数都是算术类型，就实施寻常算术转换；如果其中任何一个是指针，就求它们的公共指针类型。如果这些情况都不适用——例如，一个操作数是 void 而另一个是指针或算术值——我们就抛出错误。

### 算术表达式与比较的既有验证

接下来，我们要确保既有的算术运算和比较的类型检查逻辑在混入 void 之后仍然有效。以前，我们可以假定每个表达式要么是算术类型要么是指针类型。现在我们不能再依赖这个假设了。例如，让我们重新审视演示如何对 Equal 表达式做类型检查的清单 14-15。清单 17-19 重现了那段代码，并加上了我们需要补充的验证逻辑。

```text
typecheck_exp(e, symbols):
    match e with
    | --snip--
    | Binary(Equal, e1, e2) ->
        typed_e1 = typecheck_and_convert(e1, symbols)
        typed_e2 = typecheck_and_convert(e2, symbols)
        t1 = get_type(typed_e1)
        t2 = get_type(typed_e2)
        if t1 or t2 is a pointer type:
            common_type = get_common_pointer_type(typed_e1, typed_e2)
        else if t1 and t2 are arithmetic types:
            common_type = get_common_type(t1, t2)
        else:
            fail("Invalid operands to equality expression")
        --snip--
```

*清单 17-19：对 Equal 表达式做类型检查，并加入额外验证*

> **注意**
>
> 如果你把这段代码与清单 14-15 比较，会注意到我们把对 typecheck_exp 的递归调用替换成了 typecheck_and_convert。这个改动我们在第 15 章就做了，所以这里没有加粗标出。

在第 14 章中，如果 t1 和 t2 都不是指针类型，我们就知道它们都是算术类型，于是可以直接实施寻常算术转换。现在，我们要显式检查它们要么是指针类型要么是算术类型；如果是其他任何类型，我们就报错。

更一般地，我们对每个表达式的操作数做类型检查时，应该通过接受合法类型来做，而不是通过拒绝非法类型来做。例如，我们应该验证 Multiply 和 Divide 的操作数是算术值，而不是确认它们不是指针。请花一点时间检查你对所有关系运算和算术运算的类型检查逻辑，把任何过于宽松的验证收紧。

### sizeof 表达式

sizeof 表达式的类型是 size_t；在我们的实现中，就是 unsigned long。要对 sizeof 做类型检查，我们先验证它的操作数，然后把 unsigned long 记录为结果类型，如清单 17-20 所示。

```text
typecheck_exp(e, symbols):
    match e with
    | --snip--
    | SizeOfT(t) ->
      ❶ validate_type_specifier(t)
      ❷ if not is_complete(t):
            fail("Can't get the size of an incomplete type")
        return set_type(e, ULong)
    | SizeOf(inner) ->
      ❸ typed_inner = typecheck_exp(inner, symbols)
      ❹ if not is_complete(get_type(typed_inner)):
            fail("Can't get the size of an incomplete type")
        return set_type(SizeOf(typed_inner), ULong)
```

*清单 17-20：对 sizeof 做类型检查*

如果 sizeof 作用于类型，我们强制实施在第 471 页“不完整类型的限制”一节中讨论过的两条关于不完整类型的规则：永远不能指定元素类型不完整的数组 ❶，也不能对不完整类型应用 sizeof ❷。（你也不能对函数类型应用 sizeof，但这个错误我们已经在解析器中捕获了。）

如果操作数是表达式，我们先推断该表达式的类型 ❸。为了避免把数组转换为指针，我们使用 typecheck_exp 而不是 typecheck_and_convert。确定了表达式的类型之后，我们确保该类型是完整的 ❹。

## TACKY 生成

接下来，我们把 sizeof 和 void 表达式转换为 TACKY。我们需要更新 Return 和 FunCall 指令，以处理返回类型为 void 的函数。对类型为 void 的强制转换表达式和条件表达式的处理也与其非 void 对应形式略有不同；具体来说，我们不会创建任何 void 临时变量。我们还会在这一遍中求值 sizeof 表达式，把它们替换为整数常量。要支持指向 void 的指针，我们不需要做任何改动。

### 返回类型为 void 的函数

我们将对 TACKY IR 做两处修改，以便调用 void 返回类型的函数并从中返回。第一，我们把 FunCall 指令的目标（destination）改为可选的：

```text
FunCall(identifier fun_name, val* args, val? dst)
```

对于调用 void 函数，我们把 dst 留空。对于调用其他任何函数，dst 和现在一样，是存放返回值的临时变量。我们对 Return 指令做类似的修改：

```text
Return(val?)
```

然后，我们把每个不带表达式的 return 语句翻译成不带值的 TACKY Return 指令。

void 函数可能不使用显式的 return 语句；这种情况下，控制一旦到达函数末尾它就返回。通过在每个 TACKY 函数末尾添加一条 Return 指令，我们已经正确处理了这种情况。

### 到 void 的强制转换

清单 17-21 展示了如何处理到 void 的强制转换：只需处理内层表达式，不发射任何其他指令。

```text
emit_tacky(e, instructions, symbols):
    match e with
    | --snip--
    | Cast(Void, inner) ->
        emit_tacky_and_convert(inner, instructions, symbols)
        return PlainOperand(Var("DUMMY"))
```

*清单 17-21：把到 void 的强制转换为 TACKY*

这里你想返回什么操作数都可以；调用方不会使用它。

### 带 void 操作数的条件表达式

清单 17-22 演示了我们目前如何把条件表达式转换为 TACKY。

```text
    | Conditional(condition, e1, e2) ->
        --snip--
        cond = emit_tacky_and_convert(condition, instructions, symbols)
        instructions.append(JumpIfZero(cond, e2_label))
        dst = make_tacky_variable(get_type(e), symbols)
        v1 = emit_tacky_and_convert(e1, instructions, symbols)
        instructions.append_all(
          ❶ [Copy(v1, dst),
              Jump(end),
              Label(e2_label)])
        v2 = emit_tacky_and_convert(e2, instructions, symbols)
        instructions.append_all(
          ❷ [Copy(v2, dst),

```

*清单 17-22：把非 void 条件表达式转换为 TACKY*

如果 e1 和 e2 是 void 表达式，那么 Copy 指令 ❶❷ 就有问题了。我们不应该创建类型为 void 的 dst 临时变量，更不应该向它复制任何东西。为了处理条件表达式中的 void 表达式，我们沿用清单 17-22 的基本思路，但不生成 dst，也不发射那两条 Copy 指令。清单 17-23 给出了处理 void 条件表达式的更新后的伪代码。

```text
    | Conditional(condition, e1, e2) ->
        --snip--
        cond = emit_tacky_and_convert(condition, instructions, symbols)
        instructions.append(JumpIfZero(cond, e2_label))
        if get_type(e) == Void:
            emit_tacky_and_convert(e1, instructions, symbols)
            instructions.append_all(
            [Jump(end),
              Label(e2_label)])
            emit_tacky_and_convert(e2, instructions, symbols)
            instructions.append(Label(end))

        else:
            --snip--
```

*清单 17-23：把结果为 void 的条件表达式转换为 TACKY*

由于我们没有创建临时变量 dst，我们需要向调用方返回某个别的操作数。我们可以返回一个哑值 ❶，因为我们知道调用方不会使用它。处理非 void 表达式时，我们生成与以前相同的指令，所以我略去了那种情形的伪代码。

```text

          | StaticVariable(identifier, bool global, type t, static_init* init_list)
```

## 汇编生成

作为本章的收尾，我们要为不带值的 Return 指令和不带目标的 FunCall 指令生成汇编。只需对汇编生成遍做些小改动，我们就能处理这两条指令。

通常，形如 Return(val) 的指令会被转换为如下汇编：

```asm
Mov(<val 类型>, val, <dst 寄存器>)
Ret
```

如果返回值不存在，我们就跳过 Mov 指令，只生成 Ret 指令。类似地，清单 17-26 概括了我们通常如何把 FunCall 指令转换为汇编。

```asm
<调整栈对齐>
<把实参移入通用寄存器>
<把实参移入 XMM 寄存器>
<把实参压入栈>
Call(fun_name)
<释放实参/填充>
❶ Mov(<dst 类型>, <dst 寄存器>, dst)
```

*清单 17-26：当函数返回值时把 FunCall 转换为汇编*

如果 dst 不存在，我们就不生成最后那条 Mov 指令 ❶，其余部分保持不变。表 17-1 概括了从 TACKY 到汇编转换的最新更新，其中两处小改动以粗体标出。

*表 17-1：把 TACKY 指令转换为汇编*

| TACKY 指令 | 汇编指令 |
| --- | --- |
| Return(val)<br>整数 | `Mov(<val 类型>, val, Reg(AX))`<br>`Ret` |
| Return(val)<br>double | `Mov(Double, val, Reg(XMM0))`<br>`Ret` |
| **Return(val)<br>void** | **`Ret`** |
| FunCall(fun_name, args, dst)<br>dst 存在 | `<调整栈对齐>`<br>`<把实参移入通用寄存器>`<br>`<把实参移入 XMM 寄存器>`<br>`<把实参压入栈>`<br>`Call(fun_name)`<br>`<释放实参/填充>`<br>`Mov(<dst 类型>, <dst 寄存器>, dst)` |
| **FunCall(fun_name, args, dst)<br>dst 缺失** | **`<调整栈对齐>`<br>`<把实参移入通用寄存器>`<br>`<把实参移入 XMM 寄存器>`<br>`<把实参压入栈>`<br>`Call(fun_name)`<br>`<释放实参/填充>`** |

由于汇编 AST 没有变化，我们不需要改动后端的其余部分。
