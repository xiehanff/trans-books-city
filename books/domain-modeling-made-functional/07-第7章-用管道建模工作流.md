# 第 7 章 用管道建模工作流

*Chapter 7: Modeling Workflows as Pipelines*

在前两章中,我们看到了如何以一般化的方式用类型来做领域建模。本章将把在那里学到的东西应用到下单(order-placing)工作流上。一路走来,我们还会考察若干对建模任何工作流都有用的技术。目标一如既往:产出的东西要让领域专家也能读懂。

那么,让我们重新审视 Place Order(下单)工作流中的各个步骤。下面是我们需要建模的内容概要:

```fsharp
workflow "Place Order" =
    input: UnvalidatedOrder
    output (on success):
        OrderAcknowledgmentSent
        AND OrderPlaced (to send to shipping)
        AND BillableOrderPlaced (to send to billing)
    output (on error):
        ValidationError

    // 步骤 1
    do ValidateOrder
    If order is invalid then:
        return with ValidationError

    // 步骤 2
    do PriceOrder

    // 步骤 3
    do AcknowledgeOrder

    // 步骤 4
    create and return the events
```

显然,这个工作流由一系列子步骤(substep)组成:ValidateOrder、PriceOrder 等。这当然极其常见。许多业务过程都可以被看作一系列文档转换,我们将看到,可以用同样的方式来建模工作流。我们会创建一条"管道"(pipeline)来表示业务过程,而这条管道又由一系列更小的"管件"搭建而成。每个小管件完成一种转换,然后我们把这些小管件粘合起来,组成更大的管道。这种编程风格有时被称为"面向转换的编程"(transformation-oriented programming)。

遵循函数式编程原则,我们将确保管道中的每个步骤(step)都设计成无状态(stateless)且无副作用的,这意味着每个步骤都可以被独立地测试和独立地理解。设计好管道的各个部件之后,我们只需实现并组装它们即可。

## 工作流的输入

先从工作流的输入看起。

工作流的输入应该总是一个领域对象(我们假定该输入已经从数据传输对象(Data Transfer Object,DTO)反序列化完毕)。本例中,这个对象就是此前建模过的 UnvalidatedOrder 类型:

```fsharp
type UnvalidatedOrder = {
  OrderId : string
  CustomerInfo : UnvalidatedCustomerInfo
  ShippingAddress : UnvalidatedAddress
  ...
  }
```

### 作为输入的命令

我们在本书开头就看到过,一个工作流与启动它的命令(command)相关联。因此在某种意义上,工作流真正的输入其实不是订单表单,而是命令。

对于下单工作流,我们把这条命令称为 PlaceOrder。命令应当包含工作流处理该请求所需的一切,本例中就是上面的 UnvalidatedOrder。我们多半还想记录命令的创建者、时间戳以及其他用于日志和审计的元数据,于是命令类型最终可能长成这样:

```fsharp
type PlaceOrder = {
  OrderForm : UnvalidatedOrder
  Timestamp: DateTime
  UserId: string
  // 等等
  }
```

### 用泛型共享公共结构

当然,这不会是我们要建模的唯一一条命令。每条命令都拥有其所属工作流需要的数据,但也会与其他所有命令共享一些字段,比如 UserId 和 Timestamp。我们真的需要一遍又一遍地重复实现同样的字段吗?就没有什么办法共享它们吗?

如果做的是面向对象设计,显而易见的方案是使用一个包含公共字段的基类,然后让每条具体命令继承它。

在函数式的世界里,我们可以用泛型(generics)达到同样的目的。首先定义一个 Command 类型,它包含公共字段和一个存放命令专属数据的槽位(我们称之为 Data),像这样:

```fsharp
type Command<'data> = {
  Data : 'data
  Timestamp: DateTime
  UserId: string
  // 等等
  }
```

然后,只需指定放进 Data 槽位的类型,就能创建一条工作流专属的命令:

```fsharp
type PlaceOrder = Command<UnvalidatedOrder>
```

### 在一个类型中合并多条命令

某些情况下,一个限界上下文(bounded context)的所有命令会在同一条输入通道(比如消息队列)上发送,因此我们需要某种方式把它们统一到一个可序列化的数据结构中。

解决方案很清楚:创建一个包含所有命令的选择类型(choice type)。例如,如果需要在 PlaceOrder、ChangeOrder 和 CancelOrder 之间做选择,可以创建这样一个类型:

```fsharp
type OrderTakingCommand =
  | Place of PlaceOrder
  | Change of ChangeOrder
  | Cancel of CancelOrder
```

注意,每个分支都关联着一个命令类型。我们已经定义过 PlaceOrder 类型,ChangeOrder 和 CancelOrder 也会以同样的方式定义,包含执行各自命令所需的信息。

这个选择类型会被映射为 DTO,并在输入通道上序列化和反序列化。我们要做的只是在限界上下文的边缘(洋葱架构(Onion Architecture)的"基础设施"环)增加一个新的"路由"或"分发"输入阶段。

## 把订单建模为一组状态

现在转到工作流管道的各个步骤上来。根据此前对这个工作流的理解,很明显,订单(Order)并不只是一份静态文档,而是会实实在在地经历一系列不同的状态:订单从 UnvalidatedOrder(未验证)出发,经 ValidateOrder 步骤转换到 ValidatedOrder(已验证),再经 PriceOrder 步骤转换到 PricedOrder(已定价)。

该如何建模这些状态呢?一种天真的做法是创建单一的记录类型,用各种标志位捕获所有不同的状态,像这样:

```fsharp
type Order = {
  OrderId : OrderId
  ...
  IsValidated : bool  // 验证后设置
  IsPriced : bool     // 定价后设置
  AmountToBill : decimal option // 同样在定价后设置
  }
```

但这种做法问题多多:

- 系统显然是有状态的(由各个标志位指示),但这些状态是隐式的,需要大量条件代码才能处理。

- 某些状态拥有的数据在其他状态下并不需要,把它们全部塞进一个记录会让设计变得复杂。例如,AmountToBill 只在"已定价"状态下才需要,但由于它在其他状态下不存在,我们只能把这个字段设为可选。

- 哪些字段与哪些标志位配套,并不清楚。IsPriced 置位时必须设置 AmountToBill,但设计本身并不强制这一点,我们只能依赖注释来提醒自己保持数据一致。

一个要好得多的领域建模方式,是为订单的每个状态各创建一个新类型。这让我们能够消除隐式状态和条件字段。

这些类型可以直接根据我们此前创建的领域文档定义出来。例如,ValidatedOrder 的领域文档是这样的:

```fsharp
data ValidatedOrder =
   ValidatedCustomerInfo
   AND ValidatedShippingAddress
   AND ValidatedBillingAddress
   AND list of ValidatedOrderLine
```

而下面是与它对应的 ValidatedOrder 类型定义。这是一次直截了当的翻译(额外添加了 OrderId,因为订单的标识必须在整个工作流中保持不变):

```fsharp
type ValidatedOrder = {
  OrderId : OrderId
  CustomerInfo : CustomerInfo
  ShippingAddress : Address
  BillingAddress : Address
  OrderLines : ValidatedOrderLine list
  }
```

我们可以用同样的方式为 PricedOrder 创建类型,再加上承载价格信息的额外字段。

```fsharp
type PricedOrder = {
  OrderId : ...
  CustomerInfo : CustomerInfo
  ShippingAddress : Address
  BillingAddress : Address
  // 与 ValidatedOrder 不同之处
  OrderLines : PricedOrderLine list
  AmountToBill : BillingAmount
  }
```

最后,我们可以创建一个顶层类型,在所有状态之间做选择:

```fsharp
type Order =
  | Unvalidated of UnvalidatedOrder
  | Validated of ValidatedOrder
  | Priced of PricedOrder
  // 等等
```

这就是在生命周期中任何时刻代表订单的那个对象,也是可以持久化到存储或传递给其他上下文的类型。

注意,我们不会把 Quote(报价)放进这组选择里,因为它不是订单可能进入的一个状态——它属于一个完全不同的工作流。

### 需求变化时新增状态类型

为每个状态使用独立类型的一个好处是,新增状态不会破坏现有代码。例如,如果有一个支持退款的需求,我们可以新增一个 RefundedOrder 状态,带上仅该状态需要的任何信息。由于其他状态都是独立定义的,使用它们的任何代码都不会受到这次改动的影响。

## 状态机

在上面的章节中,我们把一个带标志位的单一类型转换成了一组独立的类型,每个类型为特定的工作流阶段而设计。

这已经是我们第二次这么做了。在之前讨论过的 EmailAddress 例子中,我们把带标志位的设计转换成了拥有两个选项的设计,每个状态一个:"Unverified"(未验证)和"Verified"(已验证)。

这类情形在业务建模场景中极其常见,所以让我们暂停一下,看看把"状态"作为一种通用领域建模工具的用法。在典型的模型中,一份文档或一条记录可以处于一个或多个状态,从一个状态通往另一个状态的路径("转换"(transition))由某种命令触发,如图所示。这就是所谓的状态机(state machine)。图中示意了这一通用结构:一个文档或记录在任一时刻处于某个状态;一条命令到达后,触发一条从当前状态指向另一个状态的转换;文档随之进入新状态,后续命令又可从新状态触发进一步的转换。

现在,你可能熟悉那些拥有几十上百个状态的复杂状态机,比如语言解析器和正则表达式中所用的那种。我们不讨论那些。我们在这里讨论的状态机要简单得多、简单得多——最多只有几个状态,外加少量转换。

举几个例子:

- 刚才提到的那个:电子邮件地址可能有"Unverified"和"Verified"两种状态,通过请用户点击确认邮件中的链接,可以从"Unverified"状态转换到"Verified"状态。

- 购物车可能有"Empty"(空)、"Active"(活跃)和"Paid"(已支付)三种状态,向购物车添加一件商品可以从"Empty"状态转换到"Active"状态,完成支付则转换到"Paid"状态。

- 包裹投递可能有三种状态:"Undelivered"(未投递)、"Out for Delivery"(投递中)和"Delivered"(已投递),把包裹装上送货卡车可以从"Undelivered"状态转换到"Out for Delivery"状态,依此类推。

### 为什么使用状态机?

在这些场景中使用状态机有若干好处:

- 每个状态可以有不同的允许行为。

  例如,在购物车的例子中,只有活跃的购物车才能被支付,已支付的购物车不能再添加商品。在上一章讨论未验证/已验证邮箱设计时,我们见过一条业务规则:只能向已验证的电子邮件地址发送密码重置邮件。通过为每个状态使用各自独立的类型,我们可以把这条要求直接编码进函数签名,让编译器来确保业务规则得到遵守。

- 所有状态都被显式地记录下来。

  重要状态是隐式的、从未被文档化,这种情况太容易发生了。在购物车例子里,"空购物车"与"活跃购物车"的行为并不相同,但很少会在代码里看到这一点被明确地写出来。

- 它是一种迫使你思考每一种可能情形的设计工具。

  设计中错误的一个常见成因,是某些边缘情形没有被处理。状态机迫使所有情形都被考虑到。例如:

  - 如果我们尝试验证一封已经验证过的邮箱,应该发生什么?

  - 如果我们尝试从空购物车里移除一件商品,应该发生什么?

  - 如果我们尝试投递一个已处于"Delivered"状态的包裹,应该发生什么?

  - 诸如此类。用状态的方式来思考设计,能迫使这些问题浮出水面,让领域逻辑变得清晰。

### 如何在 F# 中实现简单的状态机

用于语言解析器等场合的复杂状态机,是由规则集或文法生成的,实现起来相当复杂。但上面描述的那种简单的、面向业务的状态机可以手工编码,完全不需要特殊的工具或库。

那么,我们应该如何实现这些简单的状态机呢?一件我们不想做的事,是把所有状态合并进一个公共记录,再用标志位、枚举或其他种种条件逻辑来区分它们。

好得多的做法是让每个状态拥有自己的类型,存放与该状态相关的数据(如果有的话)。整个状态集合则可以用一个选择类型来表示,每个状态对应一个分支。下面以购物车状态机为例:

```fsharp
type Item = ...
type ActiveCartData = { UnpaidItems: Item list }
type PaidCartData = { PaidItems: Item list; Payment: float }

type ShoppingCart =
  | EmptyCart  // 无数据
  | ActiveCart of ActiveCartData
  | PaidCart of PaidCartData
```

ActiveCartData 和 PaidCartData 两个状态各有自己的类型。EmptyCart 状态没有关联数据,所以不需要为它建专门的类型。

然后,命令处理器(command handler)由一个函数表示:接收整个状态机(该选择类型),并返回它的新版本(更新后的选择类型)。假设我们想向购物车添加一件商品。状态转换函数 addItem 接收一个 ShoppingCart 参数和要添加的商品,像这样:

```fsharp
let addItem cart item =
  match cart with
  | EmptyCart ->
    // 创建一个只含一件商品的新活跃购物车
    ActiveCart {UnpaidItems=[item]}

  | ActiveCart {UnpaidItems=existingItems} ->
    // 创建一个加入了该商品的新 ActiveCart
    ActiveCart {UnpaidItems = item :: existingItems}

  | PaidCart _ ->
    // 忽略
    cart
```

结果是一个新的 ShoppingCart,它可能处于一个新状态,也可能没有变化(当它原本处于"Paid"状态时)。

再比如,我们要为购物车中的商品付款。状态转换函数 makePayment 接收一个 ShoppingCart 参数和支付信息,像这样:

```fsharp
let makePayment cart payment =
  match cart with
  | EmptyCart ->
    // 忽略
    cart

  | ActiveCart {UnpaidItems=existingItems} ->
    // 创建一个带支付信息的新 PaidCart
    PaidCart {PaidItems = existingItems; Payment=payment}

  | PaidCart _ ->
    // 忽略
    cart
```

结果是一个新的 ShoppingCart,它可能处于"Paid"状态,也可能没有(当它原本已处于"Empty"或"Paid"状态时)。

你可以看到,从调用者的角度看,这组状态被当作一个整体(ShoppingCart 类型)进行通用操作;而在内部处理事件时,每个状态又被分别对待。

## 用类型建模工作流的每个步骤

状态机方法非常适合用来建模我们的下单工作流,有了它在手,现在来建模每个步骤的细节。

### 验证步骤

先从验证开始。在之前的讨论中,我们是这样记录"ValidateOrder"子步骤的:

```fsharp
substep "ValidateOrder" =
    input: UnvalidatedOrder
    output: ValidatedOrder OR ValidationError
    dependencies: CheckProductCodeExists, CheckAddressExists
```

我们假定已经按照此前讨论的方式定义了输入和输出类型(UnvalidatedOrder 和 ValidatedOrder)。除了输入之外,可以看到这个子步骤有两个依赖(dependency):一个用来检查产品代码是否存在,另一个用来检查地址是否存在,如图所示。图中,ValidateOrder 步骤以 UnvalidatedOrder 作为输入,同时调用两个外部依赖:CheckProductCodeExists(查询产品目录验证产品代码)和 CheckAddressExists(调用远程地址检查服务验证地址),最终输出 ValidatedOrder 或 ValidationError。

我们一直在把过程建模为带输入和输出的函数。但如何用类型来建模这些依赖呢?很简单,把它们也当作函数。函数的类型签名将成为我们稍后要实现的"接口"。

例如,要检查一个产品代码是否存在,我们需要一个函数:接收一个 ProductCode,如果它存在于产品目录中就返回 true,否则返回 false。我们可以定义一个 CheckProductCodeExists 类型来表示它:

```fsharp
type CheckProductCodeExists =
  ProductCode -> bool
  // ^输入       ^输出
```

再看第二个依赖,我们需要一个函数:接收一个 UnvalidatedAddress,如果地址有效就返回纠正后的地址,如果地址无效则返回某种验证错误。

我们还希望区分"已检查地址"(远程地址检查服务的输出)与我们的 Address 领域对象,并且在某个时刻需要在两者之间转换。眼下,我们可以先说 CheckedAddress 只是 UnvalidatedAddress 的一个包装版本:

```fsharp
type CheckedAddress = CheckedAddress of UnvalidatedAddress
```

于是,这个服务接收 UnvalidatedAddress 作为输入,返回一个 Result 类型:成功情形是 CheckedAddress 值,失败情形是 AddressValidationError 值:

```fsharp
type AddressValidationError = AddressValidationError of string

type CheckAddressExists =
  UnvalidatedAddress -> Result<CheckedAddress,AddressValidationError>
  // ^输入                    ^输出
```

定义好依赖之后,现在我们可以把 ValidateOrder 步骤定义为这样一个函数:一个主输入(UnvalidatedOrder)、两个依赖(CheckProductCodeExists 和 CheckAddressExists 服务),以及输出(要么是一个 ValidatedOrder,要么是一个错误)。这个类型签名乍一看挺吓人,但如果你把它看作前面那句话的代码等价物,就应该说得通了。

```fsharp
type ValidateOrder =
  CheckProductCodeExists    // 依赖
    -> CheckAddressExists   // 依赖
    -> UnvalidatedOrder     // 输入
    -> Result<ValidatedOrder,ValidationError>  // 输出
```

这个函数的整体返回值必须是一个 Result,因为其中一个依赖(CheckAddressExists 函数)返回 Result。Result 一旦在任何地方被用到,就会"污染"它所接触的一切,这种"Result 性"需要一路向上传递,直到抵达某个处理它的顶层函数。

我们把依赖放在参数顺序的前列,而把输入类型放在倒数第二位,紧挨着输出类型。这样做的原因是让偏应用(partial application,依赖注入的函数式等价物)更容易。实践中的具体运作方式,我们会在实现章节里讨论。

### 定价步骤

继续前进,来设计"PriceOrder"步骤。原始的领域文档如下:

```fsharp
substep "PriceOrder" =
    input: ValidatedOrder
    output: PricedOrder
    dependencies: GetProductPrice
```

又一次,我们看到了一个依赖——一个根据产品代码返回价格的函数。

我们可以定义一个 GetProductPrice 类型来记录这个依赖:

```fsharp
type GetProductPrice =
  ProductCode -> Price
```

请再次留意我们在这里做了什么。PriceOrder 函数需要来自产品目录的信息,但我们并不打算给它传递某种重量级的 IProductCatalog 接口,而是只传一个函数(GetProductPrice),它恰好代表我们在此阶段需要从产品目录得到的东西。也就是说,GetProductPrice 扮演了一个抽象——它隐藏了产品目录的存在,只向我们暴露所需的功能,分毫不差、绝不多给。

于是,定价函数本身会是这个样子:

```fsharp
type PriceOrder =
  GetProductPrice      // 依赖
    -> ValidatedOrder  // 输入
    -> PricedOrder     // 输出
```

这个函数总会成功,所以不需要返回 Result。

### 确认订单步骤

下一步是创建确认函并把它发送给客户。

先来建模确认函。眼下只说它包含一个将以电子邮件发出的 HTML 字符串。我们把 HTML 字符串建模为一个简单类型,把 OrderAcknowledgment 建模为一个记录类型,其中包含确认函本身以及要发送到的电子邮件地址:

```fsharp
type HtmlString =
  HtmlString of string

type OrderAcknowledgment = {
  EmailAddress : EmailAddress
  Letter : HtmlString
  }
```

我们怎么知道确认函的内容应该是什么?多半会基于客户信息和订单详情,用某种模板生成。与其把这份逻辑嵌进工作流,不如把它变成别人的问题!也就是说,我们假设有一个服务函数会替我们生成内容,而我们要做的只是交给它一个 PricedOrder。

```fsharp
type CreateOrderAcknowledgmentLetter =
  PricedOrder -> HtmlString
```

然后,我们把这个类型的函数作为该步骤的一个依赖。

拿到确认函之后,需要把它发送出去。该怎么做?直接调用某种 API?把确认函写入消息队列?还是别的什么?

幸运的是,我们现在不需要决定这些问题。具体实现可以暂时搁置,只聚焦在我们需要的接口上。和之前一样,此阶段的设计所需的,只是定义一个接收 OrderAcknowledgment 作为输入并替我们发送的函数;至于怎么发,我们并不关心。

```fsharp
type SendOrderAcknowledgment =
  OrderAcknowledgment -> unit
```

这里我们用 unit 类型表示:存在某种我们不关心的副作用,而函数本身不返回任何东西。

不过,这真的对吗?如果确认函已发送,我们希望从整个下单工作流返回一个 OrderAcknowledgmentSent 事件,但按这个设计,我们无法知道它到底有没有发出去。所以需要改一改。一个显而易见的选择是改为返回 bool,然后我们可以用它来决定是否创建该事件:

```fsharp
type SendOrderAcknowledgment =
  OrderAcknowledgment -> bool
```

然而,布尔值在设计里通常是个糟糕的选择,因为它们承载的信息太少。更好的做法是用一个简单的 Sent/NotSent 选择类型来代替 bool:

```fsharp
type SendResult = Sent | NotSent

type SendOrderAcknowledgment =
  OrderAcknowledgment -> SendResult
```

又或者,我们应该让服务本身(可选地)返回 OrderAcknowledgmentSent 事件本身?

```fsharp
type SendOrderAcknowledgment =
  OrderAcknowledgment -> OrderAcknowledgmentSent option
```

不过,如果这么做,我们就通过事件类型在我们的领域与服务之间制造了耦合。这里没有标准答案,所以眼下我们先坚持 Sent/NotSent 方案。以后随时可以改。

最后,"Acknowledge Order"步骤的输出应该是什么?简单,就是那个"已发送"事件——如果它被创建了的话。现在就来定义这个事件类型:

```fsharp
type OrderAcknowledgmentSent = {
  OrderId : OrderId
  EmailAddress : EmailAddress
  }
```

最后,把这一切拼在一起,定义该步骤的函数类型:

```fsharp
type AcknowledgeOrder =
  CreateOrderAcknowledgmentLetter     // 依赖
    -> SendOrderAcknowledgment        // 依赖
    -> PricedOrder                    // 输入
    -> OrderAcknowledgmentSent option // 输出
```

如你所见,函数返回的是一个可选事件,因为确认函可能并没有被发送。

### 创建要返回的事件

上一步会替我们创建 OrderAcknowledgmentSent 事件,但我们还需要创建 OrderPlaced 事件(发给装运)和 BillableOrderPlaced 事件(发给计费)。它们很好定义:OrderPlaced 事件可以直接作为 PricedOrder 的别名,而 BillableOrderPlaced 事件只是 PricedOrder 的一个子集:

```fsharp
type OrderPlaced = PricedOrder
type BillableOrderPlaced = {
  OrderId : OrderId
  BillingAddress: Address
  AmountToBill : BillingAmount
  }
```

要真正返回这些事件,我们可以创建一个专门的类型来盛放它们,像这样:

```fsharp
type PlaceOrderResult = {
  OrderPlaced : OrderPlaced
  BillableOrderPlaced : BillableOrderPlaced
  OrderAcknowledgmentSent : OrderAcknowledgmentSent option
  }
```

但工作流随时间推移极有可能新增事件,而像这样定义专门的记录类型会让修改变得困难。

不如换个思路:让工作流返回一个事件列表,其中每个事件可以是 OrderPlaced、BillableOrderPlaced 或 OrderAcknowledgmentSent 之一。

也就是说,我们定义一个 PlaceOrderEvent 选择类型,像这样:

```fsharp
type PlaceOrderEvent =
  | OrderPlaced of OrderPlaced
  | BillableOrderPlaced of BillableOrderPlaced
  | AcknowledgmentSent  of OrderAcknowledgmentSent
```

然后,工作流的最后一步会发出一个由这些事件构成的列表:

```fsharp
type CreateEvents =
  PricedOrder -> PlaceOrderEvent list
```

以后若需要处理某个新事件,直接把它加进选择类型里即可,不会破坏工作流的整体。

如果我们发现同样的事件出现在领域内的多个工作流中,甚至可以再上一层,创建一个更一般的 OrderTakingDomainEvent,作为领域中所有事件的选择类型。

## 记录效应

在之前的讨论中,我们谈过在类型签名中记录效应(effect)的问题:这个函数可能产生哪些效应?它可能返回错误吗?它做 I/O 吗?

让我们快速重访所有依赖,仔细检查是否需要像这样把任何效应显式地表达出来。

### 验证步骤中的效应

验证步骤有两个依赖:CheckProductCodeExists 和 CheckAddressExists。

先看 CheckProductCodeExists:

```fsharp
type CheckProductCodeExists = ProductCode -> bool
```

它可能返回错误吗?它是一次远程调用吗?

我们假设两者皆非。相反,我们预期本地有一份可用的产品目录缓存副本(回想一下第 2 章"理解领域"中 Ollie 关于自主性的说法),可以快速访问它。

另一方面,我们知道 CheckAddressExists 函数调用的是远程服务,而不是领域内部的本地服务,所以它除了 Result 效应之外,还应该加上 Async 效应。事实上,Async 与 Result 这两种效应经常一起使用,以至于我们通常会用 AsyncResult 别名把它们合并成一个类型:

```fsharp
type AsyncResult<'success,'failure> = Async<Result<'success,'failure>>
```

有了它,我们现在可以把 CheckAddressExists 的返回类型从 Result 改为 AsyncResult,以表明这个函数同时具有异步和错误两种效应:

```fsharp
type CheckAddressExists =
  UnvalidatedAddress -> AsyncResult<CheckedAddress,AddressValidationError>
```

现在,从类型签名就能清楚地看出:CheckAddressExists 函数在做 I/O,而且可能失败。之前谈限界上下文时我们说过,自主性是一个关键因素。那么这是否意味着,我们应该设法创建一个本地版的地址验证服务?如果把这个问题提给 Ollie,他会向我们保证这个服务拥有极高的可用性。记住,想要自主性的主要原因不是性能,而是让你能够承诺某个级别的可用性与服务。如果你的实现依赖第三方,那你就真的必须信任它(或者想办法绕开它的任何服务问题)。

与 Result 一样,Async 效应对任何包含它的代码都有传染性。因此,把 CheckAddressExists 改为返回 AsyncResult,意味着我们必须把整个 ValidateOrder 步骤也改为返回 AsyncResult:

```fsharp
type ValidateOrder =
  CheckProductCodeExists    // 依赖
    -> CheckAddressExists   // AsyncResult 依赖
    -> UnvalidatedOrder     // 输入
    -> AsyncResult<ValidatedOrder,ValidationError list>  // 输出
```

### 定价步骤中的效应

定价步骤只有一个依赖:GetProductPrice。我们同样假设产品目录在本地(例如缓存在内存中),所以没有 Async 效应。就我们所能判断的而言,访问它也不会返回错误。所以这里没有效应。

不过,PriceOrder 步骤本身很可能返回错误。比方说,某件商品被标错了价,导致整体的 AmountToBill 非常大(或为负)。这类事情应当在发生时被抓住。它也许是个极不可能出现的边缘情形,但许多现实世界的难堪正是由这类错误造成的!

如果现在要返回 Result,那么还需要一个与之配套的错误类型。我们叫它 PricingError。PriceOrder 函数现在变成这样:

```fsharp
type PricingError = PricingError of string

type PriceOrder =
  GetProductPrice                       // 依赖
    -> ValidatedOrder                   // 输入
    -> Result<PricedOrder,PricingError> // 输出
```

### 确认步骤中的效应

AcknowledgeOrder 步骤有两个依赖:CreateOrderAcknowledgmentLetter 和 SendOrderAcknowledgment。

CreateOrderAcknowledgmentLetter 函数可能返回错误吗?大概不会。而且我们假设它在本地运行、使用缓存的模板。所以总体而言,CreateOrderAcknowledgmentLetter 函数没有任何需要写进类型签名的效应。

另一方面,我们知道 SendOrderAcknowledgment 会做 I/O,所以它需要 Async 效应。那错误呢?在这个场景中,我们不关心错误的细节,而且即使出了错,我们也想忽略它、继续走快乐路径(happy path)。于是,修订后的 SendOrderAcknowledgment 将带有 Async 类型,但不带 Result 类型:

```fsharp
type SendOrderAcknowledgment =
  OrderAcknowledgment -> Async<SendResult>
```

当然,Async 效应同样会向上波及父函数:

```fsharp
type AcknowledgeOrder =
  CreateOrderAcknowledgmentLetter     // 依赖
    -> SendOrderAcknowledgment        // Async 依赖
    -> PricedOrder                    // 输入
    -> Async<OrderAcknowledgmentSent option> // Async 输出
```

## 从步骤组装工作流

现在,所有步骤的定义都已就绪;等到每一步都有了实现,我们应该只需把一步的输出接到下一步的输入,就能搭建出整体工作流。

但事情不会那么简单!把所有步骤的定义放到一处看,去掉依赖,只列出输入和输出:

```fsharp
type ValidateOrder =
  UnvalidatedOrder                                       // 输入
    -> AsyncResult<ValidatedOrder,ValidationError list>  // 输出

type PriceOrder =
  ValidatedOrder                            // 输入
    -> Result<PricedOrder,PricingError>     // 输出

type AcknowledgeOrder =
  PricedOrder                                // 输入
    -> Async<OrderAcknowledgmentSent option> // 输出

type CreateEvents =
    PricedOrder               // 输入
      -> PlaceOrderEvent list // 输出
```

PriceOrder 步骤的输入要求一个 ValidatedOrder,但 ValidateOrder 的输出是 AsyncResult<ValidatedOrder,...>,根本对不上。

类似地,PriceOrder 步骤的输出无法用作 AcknowledgeOrder 的输入,依此类推。

因此,要组合这些函数,我们不得不腾挪各个输入输出类型,让它们彼此兼容、能够拼装到一起。这是做类型驱动设计时的常见挑战,我们会在实现章节中看到具体怎么做。

## 依赖是设计的一部分吗?

在上面的代码中,我们把对其他上下文的调用(比如 CheckProductCodeExists 和 ValidateAddress)当作待记录的依赖来对待。我们对每个子步骤的设计为这些依赖添加了显式的额外参数:

```fsharp
type ValidateOrder =
  CheckProductCodeExists    // 显式依赖
    -> CheckAddressExists   // 显式依赖
    -> UnvalidatedOrder     // 输入
    -> AsyncResult<ValidatedOrder,ValidationError list>  // 输出

type PriceOrder =
  GetProductPrice                        // 显式依赖
    -> ValidatedOrder                    // 输入
    -> Result<PricedOrder,PricingError>  // 输出
```

你可能会争辩说,任何过程如何完成它的工作,都应该对我们隐藏。它为了达成目标需要与哪些系统协作,我们真的在乎吗?

如果接受这个观点,过程定义就会简化到只剩输入和输出,像这样:

```fsharp
type ValidateOrder =
  UnvalidatedOrder                                      // 输入
    -> AsyncResult<ValidatedOrder,ValidationError list> // 输出

type PriceOrder =
  ValidatedOrder                        // 输入
    -> Result<PricedOrder,PricingError> // 输出
```

哪种方式更好?

设计从来就没有标准答案,但让我们遵循这条准则:

- 对于在公共 API 中暴露的函数,向调用者隐藏依赖信息。

- 对于内部使用的函数,显式表达其依赖。

在本例中,顶层 PlaceOrder 工作流函数的依赖不应该暴露,因为调用者不需要知道它们。签名只应展示输入和输出,像这样:

```fsharp
type PlaceOrderWorkflow =
  PlaceOrder                                             // 输入
    -> AsyncResult<PlaceOrderEvent list,PlaceOrderError> // 输出
```

但对工作流的每个内部步骤,依赖应当显式写出,正如我们最初的设计所做的那样。这有助于记录每个步骤到底需要什么。如果某个步骤的依赖发生了变化,我们就修改该步骤的函数定义,而这反过来会迫使我们修改其实现。

## 完整的管道

设计的第一遍已经完成,来盘点一下目前的成果。首先,写下公共 API 的类型。我们通常会把它们全部放进一个文件,比如 DomainApi.fs 之类的。

输入如下:

```fsharp
// ----------------------
// 输入数据
// ----------------------

type UnvalidatedOrder = {
  OrderId : string
  CustomerInfo : UnvalidatedCustomer
  ShippingAddress : UnvalidatedAddress
  }
and UnvalidatedCustomer = {
  Name : string
  Email : string
  }
and UnvalidatedAddress = ...

// ----------------------
// 输入命令
// ----------------------

type Command<'data> = {
  Data : 'data
  Timestamp: DateTime
  UserId: string
  // 等等
  }

type PlaceOrderCommand = Command<UnvalidatedOrder>
```

输出以及工作流定义本身如下:

```fsharp
// ----------------------
// 公共 API
// ----------------------

/// PlaceOrder 工作流的成功输出
type OrderPlaced = ...
type BillableOrderPlaced = ...
type OrderAcknowledgmentSent = ...
type PlaceOrderEvent =
    | OrderPlaced of OrderPlaced
    | BillableOrderPlaced of BillableOrderPlaced
    | AcknowledgmentSent  of OrderAcknowledgmentSent

/// PlaceOrder 工作流的失败输出
type PlaceOrderError = ...

type PlaceOrderWorkflow =
  PlaceOrderCommand                                      // 输入命令
    -> AsyncResult<PlaceOrderEvent list,PlaceOrderError> // 输出事件
```

### 内部步骤

我们把内部步骤所使用的类型放进一个单独的实现文件(比如 PlaceOrderWorkflow.fs)。稍后,在同一个文件的底部,我们会补上实现。

先从表示订单生命周期的内部状态开始:

```fsharp
// 引入领域 API 模块中的类型
open DomainApi

// ----------------------
// 订单生命周期
// ----------------------

// 已验证状态
type ValidatedOrderLine =  ...
type ValidatedOrder = {
  OrderId : OrderId
  CustomerInfo : CustomerInfo
  ShippingAddress : Address
  BillingAddress : Address
  OrderLines : ValidatedOrderLine list
  }
and OrderId = Undefined
and CustomerInfo = ...
and Address = ...

// 已定价状态
type PricedOrderLine = ...
type PricedOrder = ...

// 所有状态合并
type Order =
  | Unvalidated of UnvalidatedOrder
  | Validated of ValidatedOrder
  | Priced of PricedOrder
  // 等等
```

然后,我们可以加上每个内部步骤的定义:

```fsharp
// ----------------------
// 内部步骤的定义
// ----------------------

// ----- 验证订单 -----

// ValidateOrder 使用的服务
type CheckProductCodeExists =
  ProductCode -> bool

type AddressValidationError = ...
type CheckedAddress = ...
type CheckAddressExists =
  UnvalidatedAddress
    -> AsyncResult<CheckedAddress,AddressValidationError>

type ValidateOrder =
  CheckProductCodeExists    // 依赖
    -> CheckAddressExists   // 依赖
    -> UnvalidatedOrder     // 输入
    -> AsyncResult<ValidatedOrder,ValidationError list>  // 输出
and ValidationError = ...

// ----- 订单定价 -----

// PriceOrder 使用的服务
type GetProductPrice =
  ProductCode -> Price

type PricingError = ...

type PriceOrder =
  GetProductPrice      // 依赖
    -> ValidatedOrder  // 输入
    -> Result<PricedOrder,PricingError> // 输出

// 等等
```

现在,所有类型都集中在一处,随时可以用来指导实现了。

## 长时工作流

不过,在继续之前,让我们重新审视关于管道的一个重要假设。我们预期:即使存在对远程系统的调用,管道也会在短时间内——以秒计——完成。

但如果这些外部服务要花长得多的时间才能完成呢?例如,如果验证是由人而不是机器完成的,而那个人要花上一整天?又或者定价由另一个部门完成,那帮人同样要花很长时间?如果这些成立,设计会受到什么影响?

首先,我们需要在调用远程服务之前把状态保存到存储中,然后等待一条告诉我们服务已完成的消息,之后还得从存储中重新加载状态,继续工作流的下一步。这比使用普通的异步调用要沉重得多,因为我们需要在每一步之间持久化状态。

这样一来,我们把原本的工作流拆成了更小的、相互独立的块,每一块由一个事件触发。你甚至可以不把它看作单一的工作流,而是一串彼此分离的迷你工作流。

这正是状态机模型作为思考框架的价值所在:每一步之前,订单从存储中加载出来——它已作为某个状态被持久化;迷你工作流把订单从原状态转换到一个新状态;结束时,新状态再次被存回存储。

这类长时工作流(long-running workflow)有时被称为 Saga(saga 模式)。[26] 每当涉及动作迟缓的人类时,它们就很常见;而且每当你想把一个工作流拆成由事件连接的、解耦且各自独立的片段时(咳……微服务),也用得上它。

在我们的例子中,工作流非常简单。如果事件和状态的数量增多、转换变得复杂,你可能就需要创建一个专门的组件——过程管理器(Process Manager)——由它负责接收传入的消息、基于当前状态决定应当采取什么行动,然后触发相应的工作流。

## 收尾

本章中,我们学习了如何只用类型来为一个工作流建模。

我们从为工作流的输入建档开始,尤其是如何建模命令。接着,我们看到了如何用状态机来为文档以及其他具有生命周期的实体建模。带着对状态的新理解,我们回到工作流,用表示输入输出状态的类型为每个子步骤建模,还花了些力气记录每个步骤的依赖和效应。

一路走来,我们创建的类型看似数以百计(其实只有三十个左右)。这真的必要吗?类型是不是太多了?看起来确实不少,但请记住,我们在努力创造的是"可执行的文档"——能够交流领域知识的代码。如果我们不创建这些类型,我们照样得去文档化"已验证订单"与"已定价订单"的差异,或者"widget 代码"与"普通字符串"的差异。何不就让文档留在代码本身之中呢?

当然,凡事总要有个平衡。我们在这里是故意走向极端,以展示把一切都在这个层面文档化会是什么样子。如果你发现这套做法在你的场景里用力过猛,尽管缩减到符合你需要的程度。一如既往,做对领域有利、对手头任务最有帮助的事。

## 接下来学什么

过去四章我们只做了建模,如今终于抵达终点,终于可以真正动手写一个实现了!

在继续之前,先澄清一件事。在本书中,我们把需求收集、建模和编码分成了各自独立的部分。这看起来像是在鼓励线性的"瀑布"式开发,但这根本不是我们的意图。在真实项目里,我们应该持续地把需求收集与建模掺在一起、把建模与原型掺在一起,想尽办法尽快把反馈交到客户或领域专家手上。事实上,用类型建模的全部意义,就在于让我们能在几分钟而不是几天之内,从需求走到建模再回到需求,因为领域专家可以直接读懂模型。

现在,我们可以开始实现章节了。作为第一步,先确保我们理解函数是如何工作的,以及如何用函数构建应用程序。我们将在下一章完成这件事。
